### 阶段一：第一次真正使用 `Canvas` —— 建立绘制直觉

这一阶段先不追求 API 数量。你以前写过 Android 自定义绘制，`Path`、坐标这些并不陌生，所以 6.2 最值得先重新建立的是 **Compose 版本的绘制模型**：`Canvas` 先像普通 Composable 一样经过布局，得到自己的宽高；进入绘制阶段以后，Compose 把这块已经确定尺寸的绘制区域作为 `DrawScope` 交给我们，我们再基于这个区域的 `size`、`center` 和局部坐标执行绘制命令。这句话基本就是阶段一最后需要真正建立起来的心智模型。

当前 Compose 官方文档仍然把 `Canvas` 定位为自定义绘制的基础入口；`Canvas` 本身实际上是围绕 `Modifier.drawBehind` 提供的一个便利 Composable，而绘制 lambda 中的接收者就是 `DrawScope`。

---

#### 一、先把第一个实验跑起来

建立文件：`Sec62A_CanvasBasics.kt`

这个例子故意不画复杂图案。我们画一个背景、左上四分之一区域、中心线、对角线和中心圆，同时允许改变 `Canvas` 的宽度。这样一次实验就能直接观察：

- `Canvas` 的尺寸从哪里来；
- `DrawScope.size` 到底表示谁的尺寸；
- `[0, 0]` 在哪里；
- `center` 怎么得到；
- 为什么根据 `size` 计算的图形会自动适配 Canvas；
- dp 和绘图坐标 px 到底是什么关系。

```kotlin
@Composable
fun Sec62A_CanvasBasics() {
    var canvasWidth by remember { mutableStateOf(280.dp) }
    var measuredSize by remember { mutableStateOf(IntSize.Zero) }

    Column(
        modifier = Modifier
            .fillMaxSize()
            .padding(24.dp),
        verticalArrangement = Arrangement.spacedBy(16.dp)
    ) {
        Text(
            text = "Canvas target width: $canvasWidth\n" +
                "Measured size: ${measuredSize.width} × ${measuredSize.height} px"
        )

        Row(
            horizontalArrangement = Arrangement.spacedBy(12.dp)
        ) {
            Button(
                onClick = {
                    canvasWidth = 220.dp
                }
            ) {
                Text("220 dp")
            }

            Button(
                onClick = {
                    canvasWidth = 340.dp
                }
            ) {
                Text("340 dp")
            }
        }

        Canvas(
            modifier = Modifier
                .width(canvasWidth)
                .height(240.dp)
                .onSizeChanged {
                    measuredSize = it
                }
        ) {
            // 整个 Canvas 的绘制区域
            drawRect(
                color = Color(0xFFF1F3F5)
            )

            // 左上角四分之一区域
            drawRect(
                color = Color(0xFF90CAF9),
                topLeft = Offset.Zero,
                size = Size(
                    width = size.width / 2f,
                    height = size.height / 2f
                )
            )

            // 水平中心线
            drawLine(
                color = Color(0xFF616161),
                start = Offset(
                    x = 0f,
                    y = center.y
                ),
                end = Offset(
                    x = size.width,
                    y = center.y
                ),
                strokeWidth = 2.dp.toPx()
            )

            // 垂直中心线
            drawLine(
                color = Color(0xFF616161),
                start = Offset(
                    x = center.x,
                    y = 0f
                ),
                end = Offset(
                    x = center.x,
                    y = size.height
                ),
                strokeWidth = 2.dp.toPx()
            )

            // 左上到右下的对角线
            drawLine(
                color = Color(0xFFE53935),
                start = Offset.Zero,
                end = Offset(
                    x = size.width,
                    y = size.height
                ),
                strokeWidth = 3.dp.toPx()
            )

            // 半径按照 Canvas 较短边的 12% 计算
            val circleRadius = minOf(
                size.width,
                size.height
            ) * 0.12f

            drawCircle(
                color = Color(0xFF43A047),
                radius = circleRadius,
                center = center
            )
        }
    }
}
```

先运行它。你应该看到一个宽 `280.dp`、高 `240.dp` 的绘制区域：左上四分之一是蓝色，灰色水平线和垂直线正好交叉于中央，红线从左上角走到右下角，绿色圆以交点为圆心。然后分别点击 `220 dp` 和 `340 dp`。这里最重要的不是“图形变大变小了”，而是观察 **哪些数据发生了变化，哪些代码完全没变**。

#### 二、第一层：`Canvas` 首先是一个参加 Layout 的 Composable

先看：

```kotlin
Canvas(
    modifier = Modifier
        .width(canvasWidth)
        .height(240.dp)
) {
    ...
}
```

这里的 `width()` 和 `height()` 干的是你已经非常熟悉的 **Layout 阶段工作**。也就是说，不能把 `Canvas` 理解成“一个无限大的画板，然后我随便往屏幕坐标上画”。它首先是 Compose 布局树中的一个节点。父布局给它 Constraints，`Modifier.width()` / `height()` 参与测量，最终 Canvas 得到实际布局尺寸。然后才轮到：

```kotlin
Canvas(...) {
    // DrawScope
}
```

执行绘制。所以这里存在明确的先后关系：

```text
父布局给 Constraints
        ↓
Canvas 测量并确定实际尺寸
        ↓
得到例如 840 × 720 px 的绘制区域
        ↓
进入 Draw 阶段
        ↓
DrawScope.size = Size(840f, 720f)
        ↓
执行 drawRect / drawLine / drawCircle ...
```

这和刚学完的 6.1 能直接接上。当时 `Shape` 的：

```kotlin
createOutline(
    size: Size,
    layoutDirection: LayoutDirection,
    density: Density
)
```

也是 **别人先确定尺寸，再把 `size` 给你，你根据这个尺寸计算几何形状**。现在 Canvas 是：

```kotlin
Canvas(...) {
    size
}
```

思想其实非常接近：不要提前猜自己的像素宽高。真正需要绘制的时候，使用 Compose 已经确定好的实际 `size` 来计算。这也是为什么 6.1 的聊天气泡能够随着组件尺寸改变，而这里的图案同样能够随着 Canvas 改变。

#### 三、`DrawScope` 是这节真正的主角

这一点非常重要：虽然课程名字叫 Canvas，但你接下来大量使用的 API 其实都属于 **`DrawScope`**。`Canvas` 的绘制 lambda，本质形式可以理解成：

```kotlin
DrawScope.() -> Unit
```

所以这里：

```kotlin
Canvas(...) {
    drawRect(...)
    drawLine(...)
    drawCircle(...)
}
```

不是 `Canvas` Composable 自己有这些成员函数。这里的 `this` 是一个 `DrawScope`，所以你才能直接访问：

```kotlin
size
center

drawRect(...)
drawLine(...)
drawCircle(...)
```

官方对 `DrawScope` 的定位也很准确：它是一个带有当前绘制边界、Density、布局方向等上下文信息的绘制环境，我们在这个局部环境中发出绘图命令。你以前 Android View 自定义绘制时可能更习惯：

```kotlin
override fun onDraw(canvas: Canvas) {
    canvas.drawRect(..., paint)
}
```

Compose 刻意把很多东西重新组织了。传统 View 思路大致是：

```text
Canvas
+ Paint
+ drawXxx()
```

Compose 更接近：

```text
DrawScope
├── 当前绘制尺寸
├── Density
├── LayoutDirection
├── 绘制变换环境
└── drawXxx(...)
```

颜色、描边、Brush 等大量绘制配置直接成为 `drawXxx()` 参数，而不是要求你维护一个不断修改状态的 `Paint`。这也是 Compose 绘制 API 和旧 View Canvas 很明显的使用体验差异。官方文档也明确提到 Compose 替开发者处理了旧 Canvas / Paint 模型中的不少状态管理细节。这阶段知道这个结构就够，不需要下钻实现。

#### 四、`size` 到底是什么

现在看这一段：

```kotlin
drawRect(
    color = Color(0xFF90CAF9),
    topLeft = Offset.Zero,
    size = Size(
        width = size.width / 2f,
        height = size.height / 2f
    )
)
```

这里出现了两个 `size`，第一次看很容易产生阅读歧义。外面的：

```kotlin
size.width
size.height
```

是 **`DrawScope.size`**，也就是整个当前绘制区域的实际尺寸。里面传给 `drawRect()` 的：

```kotlin
size = Size(...)
```

则是：我要画的这个矩形本身有多大。因此如果当前 Canvas 实际尺寸是：

```text
Canvas:
width  = 840 px
height = 720 px
```

那么：

```kotlin
Size(
    width = size.width / 2f,
    height = size.height / 2f
)
```

就是：

```text
Rectangle:
width  = 420 px
height = 360 px
```

所以它占 Canvas 的左上四分之一。而且这里有一个非常值得养成的习惯：**凡是跟组件整体比例有关的绘制，优先从 `size` 推导，不要写死像素。**比如：

```kotlin
val halfWidth = size.width / 2f
val quarterHeight = size.height / 4f
val radius = size.minDimension * 0.1f
```

这类代码天然跟当前组件尺寸绑定。官方文档同样把 `size` 作为 `DrawScope` 最核心的上下文之一。

#### 五、Compose Canvas 的局部坐标系

这一部分你以前肯定学过，所以只建立 Compose 对应关系，不重讲计算机图形学。当前 `DrawScope` 的默认坐标系：

```text
(0, 0) ───────────────→ x
  │
  │
  │
  │
  ↓
  y
```

原点在当前绘制区域左上角：

```kotlin
Offset.Zero
```

等价于：

```kotlin
Offset(
    x = 0f,
    y = 0f
)
```

右下角可以写成：

```kotlin
Offset(
    x = size.width,
    y = size.height
)
```

所以示例中的：

```kotlin
drawLine(
    start = Offset.Zero,
    end = Offset(
        x = size.width,
        y = size.height
    )
)
```

就是一条左上 → 右下的对角线。Compose 官方定义也是这一套：`[0, 0]` 位于绘制区域左上角，x 向右增长，y 向下增长。这里有一个比坐标方向更重要的概念：**这些坐标默认是 Canvas 自己的局部坐标，不是屏幕坐标。**假设这个 Canvas 最终在手机屏幕上的位置是：

```text
screen x = 80 px
screen y = 300 px
```

你仍然写：

```kotlin
Offset.Zero
```

它代表的仍然是 **Canvas 自己左上角**，而不是手机屏幕左上角。因此绝大多数自定义绘制根本没必要知道自己处于整个屏幕的什么位置。这也是 Compose 中非常健康的组件化思路：

```text
外部 Layout 决定：
“你放在哪里，你有多大。”

内部 DrawScope 决定：
“在我自己的这块区域里，我怎么画。”
```

#### 六、`center` 本质上没有神秘东西

示例用了：

```kotlin
center
```

所以：

```kotlin
drawCircle(
    center = center,
    ...
)
```

圆始终位于 Canvas 中央。你可以把它直接理解成：

```kotlin
Offset(
    x = size.width / 2f,
    y = size.height / 2f
)
```

因此这三部分：

```kotlin
start = Offset(
    x = 0f,
    y = center.y
)
```

```kotlin
end = Offset(
    x = size.width,
    y = center.y
)
```

画出水平中心线。而：

```kotlin
start = Offset(
    x = center.x,
    y = 0f
)
```

```kotlin
end = Offset(
    x = center.x,
    y = size.height
)
```

画出垂直中心线。改变 Canvas 宽度后，`center.x` 自然改变，因此中心线和圆全部自动重新定位。这里不存在什么特殊的“居中绘制算法”，就是 **根据当前 `size` 动态求坐标**。

#### 七、这里必须重新确认一次 dp 和 px

这个地方值得认真区分，因为 Compose 普通 UI 写多以后，很容易习惯满世界都是 `dp`。布局 API：

```kotlin
Modifier.width(280.dp)
Modifier.height(240.dp)
```

使用的是 `Dp`。但进入 `DrawScope` 后：

```kotlin
size.width
size.height
Offset.x
Offset.y
Size.width
Size.height
```

这些 `Float` 表示的都是 **px**。官方文档明确说明 DrawScope 绘制操作最终使用像素尺寸；需要物理尺寸保持一致时，应把 `dp` 转换为 px。所以：

```kotlin
strokeWidth = 2.dp.toPx()
```

是合理的。假设设备 density 是 `3f`：

```text
2.dp → 6 px
```

你不应该写：

```kotlin
strokeWidth = 2f
```

然后把它理解成 `2.dp`。它实际上是：

```text
2 px
```

在高密度设备上就会非常细。

---

#### 八、什么时候用比例，什么时候用 `dp.toPx()`

这个例子故意同时用了两种方式：

```kotlin
strokeWidth = 2.dp.toPx()
```

以及：

```kotlin
val circleRadius = minOf(
    size.width,
    size.height
) * 0.12f
```

它们表达的是完全不同的设计意图。如果你的设计要求是：“这根线无论 Canvas 多大，都应该是视觉上约 2dp 粗。” 使用：

```kotlin
2.dp.toPx()
```

如果你的设计要求是：“这个圆应该随着绘制区域一起变大缩小，占较短边的 12%。” 使用：

```kotlin
size.minDimension * 0.12f
```

这不是哪一种更高级，而是**你到底希望这个参数代表固定视觉尺寸，还是相对布局比例**。以后做真实日历时会大量混用：

```text
分割线粗细        → 1.dp.toPx()
事件圆角          → 6.dp.toPx()
文字与线的间距    → 8.dp.toPx()

一天时间轴总高度   → size.height
小时线 Y 坐标      → size.height × 时间比例
事件块宽度         → size.width × 某个比例
```

这才是实际自定义绘制中真正需要培养的尺寸意识。

---

#### 九、为什么第一个 `drawRect()` 没给 `size`

看这里：

```kotlin
drawRect(
    color = Color(0xFFF1F3F5)
)
```

它直接铺满 Canvas。原因是 `DrawScope` 很多绘图 API 都提供了基于当前绘制区域的默认参数。`drawRect()` 不提供 `topLeft` 时默认从当前原点开始，不提供尺寸时默认覆盖当前可用绘制范围。官方示例本身也专门利用了这一行为。所以你可以把：

```kotlin
drawRect(
    color = Color(0xFFF1F3F5)
)
```

先理解成概念上的：

```kotlin
drawRect(
    color = Color(0xFFF1F3F5),
    topLeft = Offset.Zero,
    size = size
)
```

第一个用于“铺整个区域”，第二个则自己指定了：

```kotlin
size = Size(
    size.width / 2f,
    size.height / 2f
)
```

于是只铺左上四分之一。不用现在背每一个 `drawXxx()` 的默认参数。以后看到 API 时检查一下签名即可。

#### 十、绘制命令是有顺序的

代码是：

```kotlin
drawRect(background)
drawRect(blueArea)
drawLine(horizontal)
drawLine(vertical)
drawLine(diagonal)
drawCircle(greenCircle)
```

最终看到的效果也是按这个顺序叠起来的。后画的内容可以覆盖前面已经画出的内容。所以绿色圆会覆盖中心位置上的：

- 蓝色矩形的一部分；
- 水平线；
- 垂直线；
- 红色对角线。

这一点跟传统 Canvas 完全一致，可以把它理解成：

```text
第 1 层：背景
第 2 层：蓝色矩形
第 3 层：中心线
第 4 层：红色对角线
第 5 层：绿色圆
```

不过“图层”这里只是帮助理解绘制顺序，**现在不要把它跟真正的 GraphicsLayer 或 6.4 的离屏缓冲混在一起。**这里仅仅是：同一次绘制中，命令按顺序执行。

#### 十一、现在做两个很小但非常有价值的实验

第一个实验，把圆改成固定像素：

```kotlin
drawCircle(
    color = Color(0xFF43A047),
    radius = 60f,
    center = center
)
```

然后分别切换 `220.dp` 和 `340.dp`。你应该发现：Canvas 变宽了，圆的位置跟着中心移动，但圆本身的半径仍然是 `60 px`。再恢复：

```kotlin
val circleRadius = minOf(
    size.width,
    size.height
) * 0.12f
```

注意我们这里只有**宽度**改变，高度始终是：

```kotlin
240.dp
```

因此当宽度已经大于高度时：

```kotlin
minOf(size.width, size.height)
```

仍然可能是高度。这时候你再把 Canvas 改成：

```kotlin
.height(160.dp)
```

圆才会明显跟着较短边变化。这个小实验是在提醒一个非常重要的现实：

> “响应式绘制”不是说用了 `size` 就一定会按照你脑中想象的方式变化，而是取决于你究竟用了 `width`、`height`、`minDimension`、`maxDimension`，还是某个具体比例。

复杂自定义控件后面大量 bug 都来自这里。第二个实验，把红线终点从：

```kotlin
end = Offset(
    x = size.width,
    y = size.height
)
```

临时改成：

```kotlin
end = Offset(
    x = size.width / 2f,
    y = size.height
)
```

你会直接看到：`Offset` 控制的是“这个点在当前 DrawScope 局部坐标系中的位置”，而 `Size` 控制的是“一个具有宽高的区域”。这两个类型以后会高频出现：

```kotlin
Offset(x, y)        // 位置 / 点 / 位移
Size(width, height) // 尺寸
```

不要把两者仅仅看成“都是两个 Float”。

#### 十二、为什么这个例子用了 `onSizeChanged`

我们额外写了：

```kotlin
.onSizeChanged {
    measuredSize = it
}
```

它不是 Canvas 绘制所必需的。删掉它：

```kotlin
Canvas(
    modifier = Modifier
        .width(canvasWidth)
        .height(240.dp)
) {
    ...
}
```

所有绘图仍然正常。这里加它只有一个教学目的：把最终 Layout 得到的实际像素尺寸显示到屏幕上，让你亲眼确认：

```text
280.dp
```

和：

```text
DrawScope.size.width
```

不是同一个单位体系。一个是布局层面的 `Dp` 设计尺寸，一个是测量完成后当前设备上的实际像素尺寸。真正写 Canvas 时，你通常直接使用：

```kotlin
size
```

根本不需要为了得到宽高再去 `onSizeChanged` 存一份状态。

#### 十三、把阶段一压缩成真正需要长期记住的模型

你以前已经会传统 Android 绘图，所以这一阶段不用背十几个结论。真正值得留下的是下面四条。

**第一，`Canvas` 不是脱离 Compose Layout 的无限画板。**

它首先是一个 Composable：

```kotlin
Canvas(
    Modifier.size(...)
)
```

Layout 先决定它有多大，然后才执行绘制。

**第二，真正执行绘图的是 `DrawScope`。**

```kotlin
Canvas {
    // this: DrawScope
}
```

所以后面的 `size`、`center`、`drawRect()`、`drawCircle()` 等，本质都是在当前 `DrawScope` 环境中工作。

**第三，DrawScope 使用自己的局部坐标系。**

```text
左上 = (0, 0)
右下 = (size.width, size.height)

x → 向右增加
y → 向下增加
```

大多数时候不需要关心 Canvas 在整个屏幕上的绝对位置。

**第四，绘制数据最终是 px。**

固定视觉尺寸通常：

```kotlin
2.dp.toPx()
```

跟随组件大小的几何尺寸通常：

```kotlin
size.width * 0.5f
size.height * 0.25f
size.minDimension * 0.12f
```

到这里，6.1 和 6.2 已经可以接成一条很清楚的链：

```text
Layout 确定实际尺寸
        ↓
DrawScope 得到 size
        ↓
根据 size 计算 Offset / Size / Path 等几何数据
        ↓
drawXxx() 发出绘制命令
        ↓
最终像素出现在当前 Composable 的绘制区域
```

这就是 **6.2 阶段一真正需要建立的 Compose 绘制直觉**。下一阶段再进入 `DrawScope` 的绘制参数体系：`Color / Brush`、`Fill / Stroke`、圆角矩形、椭圆、圆弧以及绘制顺序的进一步控制。

### 阶段二：`DrawScope` 核心绘制模型 —— 从“能画”到“能控制”

阶段一解决的是 **Canvas 在哪里画、画布多大、坐标从哪里开始**。这一阶段继续往前一步：同样一个几何轮廓，`DrawScope` 到底如何控制它的颜色来源、填充方式、描边、透明度以及绘制顺序。这一阶段最值得形成的模型不是背 `drawXxx()` 参数，而是：

```text
几何信息：画在哪里、画多大、是什么形状
+
绘制信息：拿什么画、填充还是描边、透明度多少
=
最终像素结果
```

建立文件：`Sec02B_DrawScopeStyling.kt`

#### 二、`Color` 与 `Brush`：它们回答的是“像素颜色从哪里来”

阶段一我们基本都是：

```kotlin
drawCircle(
    color = Color.Green,
    ...
)
```

这里非常直接：这个图元使用单一颜色绘制。但这一阶段出现了：

```kotlin
val gradientBrush = Brush.linearGradient(
    colors = listOf(
        Color(0xFF42A5F5),
        Color(0xFF7E57C2)
    ),
    start = Offset(...),
    end = Offset(...)
)
```

然后：

```kotlin
drawRoundRect(
    brush = gradientBrush,
    ...
)
```

`Brush` 可以理解为一种**颜色生成规则**。不是“这个图形是什么颜色”，而是：对于图形覆盖范围中的不同像素，应该计算出什么颜色。比如线性渐变：

```text
start                                   end
蓝 ───────────── 紫蓝 ───────────── 紫
```

`start` 与 `end` 定义渐变方向，它们仍然使用当前 `DrawScope` 的局部 px 坐标。所以：

```kotlin
start = Offset(
    x = gap,
    y = roundRectTop
)

end = Offset(
    x = size.width - gap,
    y = roundRectTop + roundRectHeight
)
```

相当于告诉渐变：从这个圆角矩形的左上方向右下方向变化。这就把阶段一的坐标系知识真正用上了。以后还会遇到：

```kotlin
Brush.horizontalGradient(...)
Brush.verticalGradient(...)
Brush.radialGradient(...)
Brush.sweepGradient(...)
```

现在不用背。需要记的是分类：

```text
Color
→ 整个绘图指令使用单一颜色来源

Brush
→ 颜色会随着空间位置发生变化
```

#### 三、`Fill` 与 `Stroke`：几何形状没有变，绘制方式变了

这部分是本阶段最重要的东西之一。代码：

```kotlin
val roundRectStyle: DrawStyle =
    if (useStroke) {
        Stroke(width = strokeWidth)
    } else {
        Fill
    }
```

然后同一个：

```kotlin
drawRoundRect(...)
```

只修改：

```kotlin
style = roundRectStyle
```

最终就能从实心圆角矩形变成轮廓。这里需要把 **geometry 和 drawing style** 分清楚。这个圆角矩形的几何区域始终由：

```kotlin
topLeft
size
cornerRadius
```

决定。也就是说：

```text
在哪里
多宽
多高
圆角多少
```

都没有变化。变化的只是：

```kotlin
style = Fill
```

还是：

```kotlin
style = Stroke(...)
```

所以可以建立这个模型：

```text
drawRoundRect
├── 几何
│   ├── topLeft
│   ├── size
│   └── cornerRadius
│
└── 绘制方式
    ├── brush / color
    ├── alpha
    └── style
```

这其实比背某个函数签名重要得多。`drawCircle()`、`drawOval()`、`drawPath()` 等大量绘图 API 都遵循类似思路。

---

#### 四、`Fill` 并不是“Stroke 宽度无限大”

这个边界需要讲清楚。

`Fill`：

```kotlin
style = Fill
```

表示填充几何区域内部。`Stroke`：

```kotlin
style = Stroke(
    width = 6.dp.toPx()
)
```

表示沿几何轮廓绘制一条具有宽度的线。例如一个矩形的理论边界在：

```text
x = 20
```

如果：

```text
strokeWidth = 6 px
```

那么这条 Stroke 可以粗略理解为以几何轮廓为中心：

```text
20 - 3px ← 边界 → 20 + 3px
```

也就是说：`Stroke` 的宽度通常分布在几何边界两侧，而不是全部向形状内部生长。这会引出一个真实开发里很常见的问题。假如：

```kotlin
drawRect(
    topLeft = Offset.Zero,
    size = size,
    style = Stroke(
        width = 20.dp.toPx()
    )
)
```

你把矩形几何边界正好放在 Canvas 最外缘，那么描边的一半会向 Canvas 外部延伸。最终外侧部分可能不可见。因此如果真的希望一圈完整描边都落在 Canvas 内部，通常需要把几何区域向内缩进：

```text
strokeWidth / 2
```

以后做边框、图表外框、选中框时，这是一个非常高频的小坑。

#### 五、为什么 `Stroke` 是一个对象，而 `Fill` 看起来只是一个值

你现在代码里：

```kotlin
Fill
```

没有参数。因为填充基本不需要进一步说明：把内部填满即可。但 `Stroke` 有很多属性：

```kotlin
Stroke(
    width = ...,
    cap = ...,
    join = ...,
    pathEffect = ...
)
```

因为“画一条轮廓线”本身还有大量细节。这一阶段真正需要掌握的是两个：

```text
width
cap
```

`join` 等到 Path 场景再看更加直观。

#### 六、`StrokeCap`：线段的数学终点和视觉终点不是完全一回事

示例底部有三根线，它们的：

```kotlin
start
end
strokeWidth
```

完全一样。只有：

```kotlin
cap
```

不同。第一根：

```kotlin
cap = StrokeCap.Butt
```

可以理解成：

```text
────────────
^          ^
start      end
```

视觉边缘基本就结束在 start / end 上。第二根：

```kotlin
cap = StrokeCap.Round
```

两端增加半圆：

```text
(────────────)
```

第三根：

```kotlin
cap = StrokeCap.Square
```

两端也会向外延伸约半个 `strokeWidth`，但端部是方形：

```text
|────────────|
```

所以这个地方必须注意：`start` 和 `end` 定义的是线段的几何中心线端点，但最终真正覆盖到哪些像素，还受到 `strokeWidth` 和 `StrokeCap` 的影响。这和刚刚说的 Stroke 围绕几何轮廓向两侧扩张，是同一个思想。以后你做日历时间轴时，如果要求一根时间线必须“视觉上恰好从某点开始”，`Butt`、`Round` 的差异就会实际影响结果。

---

#### 七、`StrokeJoin` 是什么，现在只建立定位

如果不是一条独立直线，而是多个线段连接：

```text
       /
──────
```

连接处应该长什么样，就由 `StrokeJoin` 控制。

常见有：

```kotlin
StrokeJoin.Miter
StrokeJoin.Round
StrokeJoin.Bevel
```

但这一阶段不用专门写实验。原因很简单：在单独的 `drawLine()` 上根本看不出“连接点”；等阶段四重新用 `Path + drawPath()` 时，再观察 `join` 最合适。这里知道：

```text
StrokeCap  → 一条线的端点
StrokeJoin → 多条连续线段的连接点
```

即可。

---

#### 八、`alpha` 是当前这一次绘制指令的透明度

两个椭圆：

```kotlin
drawOval(
    color = ...,
    alpha = ovalAlpha
)
```

滑动 Slider 时，你会直接看到：

```text
alpha = 1.0
→ 完全不透明

alpha = 0.5
→ 半透明

alpha = 0.0
→ 完全透明
```

注意它控制的是**这一次 draw call 的绘制结果**。这和：

```kotlin
Modifier.alpha(...)
```

概念层级不同。现在代码：

```kotlin
drawOval(
    alpha = 0.5f
)
```

只影响这一个椭圆。如果 Canvas 内还有：

```kotlin
drawLine(...)
drawCircle(...)
drawRect(...)
```

它们不会一起变透明。因此在复杂 Canvas 里，draw API 自己的 `alpha` 非常适合控制某一个视觉元素：

```text
未选中事件块
背景辅助网格
拖拽时的幽灵预览
图表中的辅助区域
```

而不是让整个 Canvas 一起透明。

---

#### 九、透明度最能帮助你看懂“绘制顺序”

两个椭圆重叠是这个案例最有价值的一部分。默认执行：

```kotlin
drawOval(red)
drawOval(blue)
```

意味着：

```text
先把红色写入像素
        ↓
再在它上方绘制蓝色
```

所以蓝色是后画的。点击：

`Reverse oval drawing order`

代码变成：

```kotlin
drawOval(blue)
drawOval(red)
```

现在红色成为后画的图形。如果：

```text
alpha = 1
```

后画的椭圆会直接覆盖前面重叠区域。但如果：

```text
alpha = 0.5
```

重叠区域会发生颜色混合，所以你仍然能看见下面的内容。

因此绘制结果不是：

```text
一堆互相独立的图形
```

而是一个连续过程：

```text
Canvas 初始像素
     ↓
draw A 修改像素
     ↓
draw B 在当前结果上继续修改
     ↓
draw C 再继续
     ↓
最终图像
```

这个心智模型以后到了 6.4 图层合成和离屏缓冲会非常重要。现在只记最基础的：**同一个 DrawScope 中，绘制命令按照代码执行顺序叠加，后画的内容位于前画内容之上。**

#### 十、`drawOval()` 的几何模型

你之前已经主动发现了 API 的几何抽象，这里继续看。

```kotlin
drawOval(
    topLeft = ...,
    size = ...
)
```

椭圆并不是要求：

```text
center + radiusX + radiusY
```

而是给一个**外接矩形**：

```text
┌─────────────────┐
│      *****      │
│   **       **   │
│  *           *  │
│   **       **   │
│      *****      │
└─────────────────┘
```

`topLeft`：

```text
外接矩形左上角
```

`size`：

```text
外接矩形宽高
```

椭圆正好内接其中。因此：

```kotlin
Size(
    width = 200f,
    height = 100f
)
```

就是横向椭圆。如果：

```kotlin
width == height
```

最终就是圆。当然画圆时更自然的 API 是：

```kotlin
drawCircle(
    center = ...,
    radius = ...
)
```

这正好又印证你上一阶段说的那个观点：API 不是因为数学信息只能这样表达，而是选择最符合目标几何对象的语义模型。

---

#### 十一、`drawRoundRect()` 也是同样的外接矩形模型

```kotlin
drawRoundRect(
    topLeft = ...,
    size = ...,
    cornerRadius = ...
)
```

前两个参数先确定矩形：

```text
topLeft + Size
```

然后：

```kotlin
CornerRadius(
    x = ...,
    y = ...
)
```

描述角部圆弧。大部分普通圆角都是：

```kotlin
CornerRadius(
    x = radius,
    y = radius
)
```

如果 x、y 不同，则得到椭圆型圆角。这和 6.1 里 Path 亲手构造圆角相比，`drawRoundRect()` 就属于典型的：如果基本绘图 API 已经能够准确描述我要的图形，就不要为了“自定义”而主动构造 Path。Path 应该留给真正无法由基础图元方便表示的复杂轮廓。

---

#### 十二、`drawArc()` 最容易弄错的是三个参数

代码：

```kotlin
drawArc(
    startAngle = 210f,
    sweepAngle = 240f,
    useCenter = false,
    ...
)
```

首先，Arc 也需要一个外接矩形：

```kotlin
topLeft
size
```

如果 `size.width == size.height`，就是在一个圆上截取圆弧。如果宽高不同，则是在椭圆上截取弧。然后是：

```kotlin
startAngle
```

它表示从哪里开始。Compose 的角度基准：

```text
                270° / -90°
                    ↑
                    |
180°  ←──────────── ○ ───────────→ 0°
                    |
                    ↓
                   90°
```

因为屏幕 y 轴向下，所以**正角度方向视觉上是顺时针**。例如：

```kotlin
startAngle = -90f
```

就是从正上方开始。

```kotlin
sweepAngle = 110f
```

就是从正上方顺时针走 `110°`。这也是为什么第二个橙色图形看起来像一个扇形区域。

---

#### 十三、`useCenter` 决定圆弧是否连接圆心

左边：

```kotlin
useCenter = false
```

并且：

```kotlin
style = Stroke(...)
```

于是就是纯粹的一段弧线：

```text
    ╭──────
  ╭─
 ╯
```

右边：

```kotlin
useCenter = true
```

于是圆弧两端会与圆心连接：

```text
      ╱
   ╱██
 ○████
   ███
```

这就是一个**扇形 sector**。所以非常简单地记：

```text
useCenter = false
→ 弧本身

useCenter = true
→ 弧 + 两端连接圆心
```

以后画：

```text
饼图
环形进度
仪表盘
时间范围弧
```

都会频繁碰到 `drawArc()`。

---

#### 十四、为什么同样是“圆弧”，这里不用 6.1 的 `Path.arcTo()`

这是 6.1 和 6.2 第一次真正出现 API 选择问题。

6.1：

```kotlin
path.arcTo(...)
```

做的是：向一个 `Path` 中加入圆弧几何。它的重点是**构造路径**。例如：

```text
lineTo
→ arcTo
→ cubicTo
→ close
```

最后组合成一个完整复杂轮廓。而：

```kotlin
drawArc(...)
```

做的是：我现在已经知道我要一个圆弧，直接把它绘制出来。因此，如果需求只是：“这里画一个 240° 的圆弧。”直接：

```kotlin
drawArc(...)
```

最合理。如果需求是：“先走一段直线，然后接一段圆弧，再连接另外几个点，最终形成一个复杂轮廓。” 那应该：

```text
Path
↓
arcTo()
↓
drawPath()
```

这就是一个非常实用的选择原则：**基础 draw API 能直接描述最终图形，就直接 draw；需要把多个几何段组合成一个整体路径，再使用 Path。**

#### 十五、这里第一次真正看到“状态只让绘制参数改变”

注意：


然后：

```kotlin
Canvas(...) {
```

```kotlin
Text(
```

#### 阶段二收尾

现在 6.2 的模型已经比第一阶段完整很多：

```text

                ↓

                ↓

                ↓

Color / Brush
                ↓

                ↓

                ↓

```

阶段二如果你把这个示例真正运行过，`Color / Brush`、`Fill / Stroke`、`alpha`、`StrokeCap`、`drawRoundRect / drawOval / drawArc` 就已经达到实际开发所需的基础深度了。

下一阶段才进入一个明显更有“绘图味”的主题：**`translate()`、`rotate()`、`scale()`、`inset()`、`withTransform()` 与裁切。** 那一阶段重点将不再是多认识几个图元，而是理解 **DrawScope 中的坐标空间是可以被改变的**。

### 阶段三：DrawScope 坐标变换 —— `translate`、`rotate`、`scale`、`inset` 与裁切

前两个阶段我们一直在直接计算坐标：想把矩形画到 `(100, 60)`，就把 `topLeft` 算成 `(100, 60)`；想绕中心画东西，就不断使用 `center.x`、`center.y`。简单图形没有问题，但复杂绘制如果所有元素都使用 Canvas 的全局局部坐标，很快就会出现大量 `baseX + ...`、`baseY + ...`。

这一阶段真正要解决的问题是：**不再永远修改图形本身的坐标，而是修改 DrawScope 当前使用的坐标空间。**

建立：`Sec02C_DrawTransform.kt`

#### 一、完整实验

这个案例分成五部分，分别观察 `translate()`、`rotate()`、`scale()`、`inset()`，最后把 `withTransform()` 和 `clipRect()` 组合起来。旋转角度和缩放比例可以实时调整。

```kotlin
@Composable
fun Sec02C_DrawTransform() {
    var rotationDegrees by remember { mutableFloatStateOf(30f) }
    var scaleFactor by remember { mutableFloatStateOf(1.15f) }

    Scaffold { innerPadding ->
        Column(
            modifier = Modifier
                .fillMaxSize()
                .padding(innerPadding)
                .verticalScroll(rememberScrollState())
                .padding(24.dp),
            verticalArrangement = Arrangement.spacedBy(12.dp)
        ) {
            Text("1. translate()：移动坐标原点")

            Canvas(
                modifier = Modifier
                    .fillMaxWidth()
                    .height(120.dp)
            ) {
                drawRect(Color(0xFFF3F4F6))

                val cardWidth = 120.dp.toPx()
                val cardHeight = 58.dp.toPx()
                val cardSize = Size(cardWidth, cardHeight)
                val margin = 16.dp.toPx()
                val top = (size.height - cardHeight) / 2f

                // 第一张：直接使用 Canvas 局部坐标定位
                drawTransformCard(
                    topLeft = Offset(
                        x = margin,
                        y = top
                    ),
                    cardSize = cardSize,
                    alpha = 0.45f
                )

                // 第二张：先移动坐标系，然后仍然从 (0, 0) 开始画
                translate(
                    left = size.width - margin - cardWidth,
                    top = top
                ) {
                    drawTransformCard(
                        topLeft = Offset.Zero,
                        cardSize = cardSize
                    )
                }
            }

            Text("2. rotate()：${rotationDegrees.toInt()}°")

            Slider(
                value = rotationDegrees,
                onValueChange = {
                    rotationDegrees = it
                },
                valueRange = -180f..180f
            )

            Canvas(
                modifier = Modifier
                    .fillMaxWidth()
                    .height(150.dp)
            ) {
                drawRect(Color(0xFFF3F4F6))

                val cardSize = Size(
                    width = 150.dp.toPx(),
                    height = 64.dp.toPx()
                )

                val cardTopLeft = Offset(
                    x = center.x - cardSize.width / 2f,
                    y = center.y - cardSize.height / 2f
                )

                // 原始未旋转区域，用于对比
                drawRoundRect(
                    color = Color(0xFF9E9E9E),
                    topLeft = cardTopLeft,
                    size = cardSize,
                    cornerRadius = CornerRadius(
                        14.dp.toPx()
                    ),
                    style = Stroke(
                        width = 1.dp.toPx()
                    )
                )

                translate(
                    left = cardTopLeft.x,
                    top = cardTopLeft.y
                ) {
                    val localPivot = Offset(
                        x = cardSize.width / 2f,
                        y = cardSize.height / 2f
                    )

                    rotate(
                        degrees = rotationDegrees,
                        pivot = localPivot
                    ) {
                        drawTransformCard(
                            topLeft = Offset.Zero,
                            cardSize = cardSize
                        )
                    }

                    drawCircle(
                        color = Color.Red,
                        radius = 4.dp.toPx(),
                        center = localPivot
                    )
                }
            }

            Text("3. scale()：${"%.2f".format(scaleFactor)}")

            Slider(
                value = scaleFactor,
                onValueChange = {
                    scaleFactor = it
                },
                valueRange = 0.5f..1.5f
            )

            Canvas(
                modifier = Modifier
                    .fillMaxWidth()
                    .height(150.dp)
            ) {
                drawRect(Color(0xFFF3F4F6))

                val cardSize = Size(
                    width = 150.dp.toPx(),
                    height = 64.dp.toPx()
                )

                val cardTopLeft = Offset(
                    x = center.x - cardSize.width / 2f,
                    y = center.y - cardSize.height / 2f
                )

                drawRoundRect(
                    color = Color(0xFF9E9E9E),
                    topLeft = cardTopLeft,
                    size = cardSize,
                    cornerRadius = CornerRadius(
                        14.dp.toPx()
                    ),
                    style = Stroke(
                        width = 1.dp.toPx()
                    )
                )

                translate(
                    left = cardTopLeft.x,
                    top = cardTopLeft.y
                ) {
                    val localPivot = Offset(
                        x = cardSize.width / 2f,
                        y = cardSize.height / 2f
                    )

                    scale(
                        scaleX = scaleFactor,
                        scaleY = scaleFactor,
                        pivot = localPivot
                    ) {
                        drawTransformCard(
                            topLeft = Offset.Zero,
                            cardSize = cardSize
                        )
                    }

                    drawCircle(
                        color = Color.Red,
                        radius = 4.dp.toPx(),
                        center = localPivot
                    )
                }
            }

            Text("4. inset()：建立更小的局部绘制区域")

            Canvas(
                modifier = Modifier
                    .fillMaxWidth()
                    .height(170.dp)
            ) {
                drawRect(Color(0xFFF3F4F6))

                drawRect(
                    color = Color(0xFF757575),
                    style = Stroke(
                        width = 2.dp.toPx()
                    )
                )

                inset(
                    left = 24.dp.toPx(),
                    top = 18.dp.toPx(),
                    right = 24.dp.toPx(),
                    bottom = 18.dp.toPx()
                ) {
                    drawRect(
                        color = Color(0xFFDDEEFF)
                    )

                    drawRect(
                        color = Color(0xFF1976D2),
                        style = Stroke(
                            width = 2.dp.toPx()
                        )
                    )

                    drawLine(
                        color = Color(0xFF78909C),
                        start = Offset.Zero,
                        end = Offset(
                            x = size.width,
                            y = size.height
                        ),
                        strokeWidth = 2.dp.toPx()
                    )

                    drawCircle(
                        color = Color(0xFF43A047),
                        radius = size.minDimension * 0.22f,
                        center = center
                    )
                }
            }

            Text("5. withTransform() + clipRect()")

            Canvas(
                modifier = Modifier
                    .fillMaxWidth()
                    .height(190.dp)
            ) {
                drawRect(Color(0xFFF3F4F6))

                val horizontalInset = 24.dp.toPx()
                val verticalInset = 18.dp.toPx()

                val clipLeft = horizontalInset
                val clipTop = verticalInset
                val clipRight = size.width - horizontalInset
                val clipBottom = size.height - verticalInset

                val transformPivot = center

                clipRect(
                    left = clipLeft,
                    top = clipTop,
                    right = clipRight,
                    bottom = clipBottom
                ) {
                    drawRect(
                        color = Color(0xFFE8F5E9),
                        topLeft = Offset(
                            x = clipLeft,
                            y = clipTop
                        ),
                        size = Size(
                            width = clipRight - clipLeft,
                            height = clipBottom - clipTop
                        )
                    )

                    val cardSize = Size(
                        width = size.width * 0.58f,
                        height = 80.dp.toPx()
                    )

                    val cardTopLeft = Offset(
                        x = center.x - cardSize.width / 2f,
                        y = center.y - cardSize.height / 2f
                    )

                    withTransform({
                        rotate(
                            degrees = rotationDegrees,
                            pivot = transformPivot
                        )

                        scale(
                            scaleX = scaleFactor,
                            scaleY = scaleFactor,
                            pivot = transformPivot
                        )
                    }) {
                        drawTransformCard(
                            topLeft = cardTopLeft,
                            cardSize = cardSize
                        )
                    }
                }

                drawRect(
                    color = Color(0xFF2E7D32),
                    topLeft = Offset(
                        x = clipLeft,
                        y = clipTop
                    ),
                    size = Size(
                        width = clipRight - clipLeft,
                        height = clipBottom - clipTop
                    ),
                    style = Stroke(
                        width = 2.dp.toPx()
                    )
                )
            }
        }
    }
}

private fun DrawScope.drawTransformCard(
    topLeft: Offset,
    cardSize: Size,
    alpha: Float = 1f
) {
    val cornerRadius = 14.dp.toPx()
    val centerY = topLeft.y + cardSize.height / 2f

    drawRoundRect(
        color = Color(0xFF42A5F5),
        topLeft = topLeft,
        size = cardSize,
        cornerRadius = CornerRadius(
            x = cornerRadius,
            y = cornerRadius
        ),
        alpha = alpha
    )

    drawLine(
        color = Color.White,
        start = Offset(
            x = topLeft.x + 16.dp.toPx(),
            y = centerY
        ),
        end = Offset(
            x = topLeft.x + cardSize.width - 16.dp.toPx(),
            y = centerY
        ),
        strokeWidth = 3.dp.toPx(),
        cap = StrokeCap.Round,
        alpha = alpha
    )

    drawCircle(
        color = Color(0xFFFFCA28),
        radius = 8.dp.toPx(),
        center = Offset(
            x = topLeft.x + 28.dp.toPx(),
            y = centerY
        ),
        alpha = alpha
    )
}
```

这个辅助函数 `drawTransformCard()` 很重要。它始终只知道一件事：**给我一个 `topLeft` 和 `Size`，我就按自己的几何规则画这张卡片。** 它不知道卡片最终有没有被平移、旋转或者缩放。坐标变换发生在它外面，这正是这一阶段希望你体会到的设计方式。

#### 二、`translate()`：不是把图形坐标全部重新计算，而是移动坐标原点

第一块案例里，两张卡片采取了两种完全不同的写法。第一张：

```kotlin
drawTransformCard(
    topLeft = Offset(
        x = margin,
        y = top
    ),
    cardSize = cardSize
)
```

我们直接告诉图形，它在 Canvas 局部坐标系里的位置。第二张却先：

```kotlin
translate(
    left = ...,
    top = ...
) {
    drawTransformCard(
        topLeft = Offset.Zero,
        cardSize = cardSize
    )
}
```

这里最值得理解的是：**`Offset.Zero` 并没有变。变的是 `(0, 0)` 对应到最终 Canvas 像素的位置。**例如原本：

```text
DrawScope 的 (0, 0) = Canvas 左上角
```

执行：

```kotlin
translate(
    left = 200f,
    top = 80f
)
```

以后，在这个 block 内：

```text
局部 (0, 0)
→ 原 Canvas 的 (200, 80)

局部 (50, 20)
→ 原 Canvas 的 (250, 100)
```

所以真正复杂的图形经常采用这种模式：

```kotlin
translate(
    left = eventLeft,
    top = eventTop
) {
    // 后面的代码完全按照自己的局部坐标绘制
    drawRect(
        topLeft = Offset.Zero,
        ...
    )

    drawCircle(
        center = Offset(...),
        ...
    )
}
```

以后你的时间轴上如果有十几个 Event Block，就没有必要让每个内部元素都写：

```text
eventLeft + ...
eventTop + ...
```

可以先把坐标原点移动到事件块左上角，然后内部完全按照自己的局部空间绘制。这就是 `translate()` 真正减少复杂度的地方。

---

#### 三、变换结束以后，坐标系自动恢复

这一点非常关键。

```kotlin
translate(...) {
    drawSomething()
}

drawSomethingElse()
```

第二个 `drawSomethingElse()` **不会继续处在刚才 translate 后的坐标空间**。`rotate()`、`scale()`、`inset()`、`clipRect()` 也是同样的作用域设计：变换仅在 lambda 内有效，lambda 退出后恢复原来的绘制状态。如果你以前写过传统 Canvas，可以把它理解成 Compose 帮你包装了经典的：

```text
save()
→ transform
→ draw
→ restore()
```

但 Compose 这里直接通过作用域表达，所以不会出现自己忘记 `restore()` 导致后续所有内容一起被移动、旋转的情况。这也是为什么这种代码可组合性很好：

```kotlin
translate(...) {
    rotate(...) {
        scale(...) {
            drawSomething()
        }
    }
}
```

每一层都有明确的生效范围。

---

#### 四、`rotate()`：旋转的是当前坐标空间，核心参数是 `pivot`

第二块实验：

```kotlin
rotate(
    degrees = rotationDegrees,
    pivot = localPivot
) {
    drawTransformCard(
        topLeft = Offset.Zero,
        cardSize = cardSize
    )
}
```

最重要的不是 `degrees`，而是：

```kotlin
pivot
```

也就是**绕哪个点旋转**。我们先使用：

```kotlin
translate(
    left = cardTopLeft.x,
    top = cardTopLeft.y
)
```

把坐标原点移动到了卡片左上角。于是卡片内部的局部坐标变成：

```text
左上角：
(0, 0)

右下角：
(cardWidth, cardHeight)

中心：
(cardWidth / 2, cardHeight / 2)
```

因此：

```kotlin
val localPivot = Offset(
    x = cardSize.width / 2f,
    y = cardSize.height / 2f
)
```

正好就是卡片自己的中心。红点就是我们特意画出来的 pivot。拖动 Slider 时，你会看到卡片围绕这个红点旋转，而灰色轮廓始终留在原位置作为参考。

这里顺便注意一个细节：`pivot` 属于**当前坐标空间**。你已经 `translate()` 进入卡片局部空间之后，就应该按照这个局部空间计算 pivot，而不是继续拿外部 Canvas 的绝对坐标硬算。这正是“局部坐标”的价值。

---

#### 五、旋转和 Layout 没有任何关系

假设 Canvas 经过 Layout 后是：

```text
宽 360dp
高 150dp
```

里面的卡片旋转 `45°` 以后，视觉上当然可能比原来的外接矩形更宽、更高。但是：

```kotlin
rotate(45f) {
    ...
}
```

不会要求 Compose：“我的内容变大了，请重新 Measure 一遍。” 也不会把旁边的兄弟 Composable 推开。Canvas 在 Layout 系统眼中仍然是原来的：

```text
360dp × 150dp
```

变化的只是 Drawing 阶段最终写出来的像素。所以必须把两件事分清：

```text
Layout：
这个节点占多大空间，放在哪里。

Draw transform：
在已经分配给我的绘制环境中，我怎么映射坐标并产生像素。
```

后面你学 `graphicsLayer` 时会再次遇到完全相同的大原则。

---

#### 六、`scale()`：改变的是“距离 pivot 有多远”

第三个实验和 `rotate()` 几乎完全相同：

```kotlin
scale(
    scaleX = scaleFactor,
    scaleY = scaleFactor,
    pivot = localPivot
) {
    drawTransformCard(...)
}
```

当：

```text
scale = 1f
```

尺寸不变。当：

```text
scale = 0.5f
```

图形中每个点距离 pivot 的距离减半。当：

```text
scale = 1.5f
```

距离放大到原来的 1.5 倍。因此 scale 的正确几何理解不是：“把 Width 和 Height 两个值乘一下。” 而是：**以 pivot 为基准，对整个当前坐标空间进行缩放。**所以卡片里的圆、线、圆角、描边等整个绘制结果都会一起参与变换，而不是只有 `Size` 被修改。

---

#### 七、`scaleX` 和 `scaleY` 可以不同

目前我们写：

```kotlin
scale(
    scaleX = scaleFactor,
    scaleY = scaleFactor
)
```

属于**等比缩放**。也可以：

```kotlin
scale(
    scaleX = 1.5f,
    scaleY = 0.7f,
    pivot = localPivot
) {
    ...
}
```

这时 x、y 两个方向使用不同的缩放比例：

```text
横向拉长
纵向压扁
```

圆会变成椭圆，矩形比例会改变。真实 App 中，普通 UI 图形通常更常使用等比缩放；非等比缩放更多用于特殊图形变换、图表或者某些视觉特效。知道能力存在即可。

---

#### 八、`inset()` 和 `translate()` 看起来很像，但本质差别非常重要

第四块是这一阶段最容易被忽略、但其实很漂亮的 API：

```kotlin
inset(
    left = 24.dp.toPx(),
    top = 18.dp.toPx(),
    right = 24.dp.toPx(),
    bottom = 18.dp.toPx()
) {
    ...
}
```

它确实会把新的局部原点向右下移动，所以看起来有点像：

```kotlin
translate(...)
```

但 **`inset()` 不只是移动坐标原点，它同时改变当前 DrawScope 的有效 `size`。**假设外部：

```text
size.width  = 1000
size.height = 500
```

执行：

```text
left   = 100
right  = 100
top    = 50
bottom = 50
```

进入 `inset` 后：

```text
新的原点位置：
相当于原坐标系的 (100, 50)

新的 width：
1000 - 100 - 100 = 800

新的 height：
500 - 50 - 50 = 400
```

因此 block 内：

```kotlin
size
center
```

都会基于这个更小的绘制区域。这就是为什么代码里：

```kotlin
drawRect(
    color = Color(0xFFDDEEFF)
)
```

没有指定 `topLeft` 和 `size`，却正好只填满蓝色的内部区域。而：

```kotlin
drawCircle(
    radius = size.minDimension * 0.22f,
    center = center
)
```

也自动以新的内部区域为基准计算。所以可以明确区分：

```text
translate()
→ 改坐标原点
→ DrawScope.size 不因此缩小

inset()
→ 改坐标原点
→ 同时缩小当前有效 size
```

以后画图表内部绘图区、卡片内容区、留边距后的图形区域时，`inset()` 很实用。

---

#### 九、为什么 `translate()` 里面使用 `center` 有时会让人困惑

既然 `translate()` 不改变 `size`，那么：

```kotlin
translate(
    left = 100f,
    top = 50f
) {
    center
}
```

这个 `center` 的数值依然是由原来的 `size` 算出来的。假设 Canvas：

```text
size = 800 × 400
```

那么：

```text
center = (400, 200)
```

translate 之后，这个局部 `(400, 200)` 映射回外部空间时已经变成：

```text
(500, 250)
```

所以复杂绘制里，我一般更建议你像案例这样：既然已经进入某个局部对象，就明确计算这个对象自己的：

```kotlin
localPivot
```

而不要到处混用外部 Canvas 的 `center`。这会让几何逻辑清晰很多。

---

#### 十、`withTransform()`：多个变换属于同一个绘制动作时集中表达

最后一个实验：

```kotlin
withTransform({
    rotate(
        degrees = rotationDegrees,
        pivot = transformPivot
    )

    scale(
        scaleX = scaleFactor,
        scaleY = scaleFactor,
        pivot = transformPivot
    )
}) {
    drawTransformCard(...)
}
```

当然也可以写成：

```kotlin
rotate(...) {
    scale(...) {
        drawTransformCard(...)
    }
}
```

结果可以表达相同类型的需求。`withTransform()` 的价值是：**需要一次应用多个绘制变换时，可以把它们集中放在同一个 transform block 中，然后统一执行后面的绘制。**它既让代码结构更清楚，也避免为每一层转换单独建立嵌套作用域。这里暂时不要研究底层 Matrix，也不要现在推矩阵乘法。应用层真正要注意的是：**多个不同类型的变换通常具有顺序意义。**特别是：

```text
translate → rotate
```

与：

```text
rotate → translate
```

在一般情况下不会得到相同结果。我们当前案例里的 `rotate + 等比 scale` 使用相同 pivot，故意没有把“变换顺序”变成本阶段新的数学负担。以后真正遇到复杂图形时再根据实际坐标空间判断。

---

#### 十一、`clipRect()`：不是改变图形，而是限制哪些像素允许留下

最后 Canvas 外面有一块绿色边框：

```kotlin
clipRect(
    left = clipLeft,
    top = clipTop,
    right = clipRight,
    bottom = clipBottom
) {
    ...
}
```

你拖大 `scaleFactor`，再旋转卡片，会发现卡片本身理论上已经超过绿色矩形，但超出的部分看不见。这里不要理解成：卡片被重新计算成了绿色矩形以内的尺寸。实际上卡片的 geometry 完全没有改变。逻辑更接近：

```text
先按正常几何规则绘制
        ↓
检查像素是不是位于 Clip Region 内
        ↓
在 → 允许留下
外 → 不允许写入
```

所以：

```text
Transform
→ 改变坐标映射

Clip
→ 限制最终可绘制区域
```

这是两个不同维度。而且和其他变换一样：

```kotlin
clipRect {
    ...
}
```

只在 block 内有效，退出以后恢复原有裁切状态。

---

#### 十二、`clipPath()` 就是把矩形裁切区域升级成任意 Path

如果矩形区域不够，比如想限制在圆形、气泡、波浪形内部，就可以使用：

```kotlin
val radius = size.minDimension * 0.35f

val clipPath = Path().apply {
    addOval(
        Rect(
            left = center.x - radius,
            top = center.y - radius,
            right = center.x + radius,
            bottom = center.y + radius
        )
    )
}

clipPath(clipPath) {
    drawRect(
        brush = Brush.linearGradient(
            colors = listOf(
                Color(0xFF42A5F5),
                Color(0xFFAB47BC)
            )
        )
    )
}
```

最终渐变矩形还是一个矩形，只是**允许显示出来的像素被 Path 限制成圆形**。这里已经和 6.1 连起来了：

```text
Path
→ 描述几何区域

clipPath(Path)
→ 把它当裁切区域

drawPath(Path)
→ 把它本身作为图形画出来
```

`drawPath()` 我们下一阶段再正式连接，所以这里不用继续展开。

---

#### 十三、坐标变换为什么在真实绘制里特别重要

假设以后你的日历时间轴有一个事件：

```text
09:30
↓
事件块左上角：
(eventLeft, eventTop)
```

事件块内部又有：

```text
状态圆点
标题
进度条
装饰线
图标
```

如果全部使用 Canvas 外部坐标：

```text
eventLeft + 12dp
eventTop + 8dp

eventLeft + 30dp
eventTop + 16dp

eventLeft + 30dp
eventTop + 42dp
...
```

代码很快会被大量基准坐标污染。更好的思路是：

```kotlin
translate(
    left = eventLeft,
    top = eventTop
) {
    // 这里开始完全把事件块左上角当 (0, 0)

    drawCircle(
        center = Offset(
            12.dp.toPx(),
            16.dp.toPx()
        ),
        ...
    )

    drawLine(
        start = Offset(...),
        end = Offset(...),
        ...
    )
}
```

这就是自定义绘制真正开始工程化之后，坐标变换比“少算两次数学题”更重要的原因：**每个局部视觉对象可以拥有自己的坐标空间。**

---

#### 十四、阶段三最重要的边界：Draw Transform 不会替你重新 Layout

目前这些：

```kotlin
translate()
rotate()
scale()
withTransform()
```

全部发生在 DrawScope 中。因此它们能做的是：改变当前绘制命令如何映射到像素。它们不能告诉父布局：“我现在旋转后变宽了，给我多留一点位置。” 也不能让兄弟节点重新排列。比如：

```text
Column

├── Canvas：150dp 高
└── Text
```

即使 Canvas 内部 `scale(2f)` 后内容视觉上超出了原来的 150dp，下面的 `Text` 不会自动向下移动。**Layout 世界并不知道你的 Draw Transform 发生了什么。**这一条后面进入第 7 章布局系统以后会变得非常重要。

---

#### 阶段三收尾

这一阶段真正需要留下来的不是五个函数签名，而是一个更高级的 DrawScope 模型：

```text
DrawScope 原始局部坐标
        ↓
translate
移动坐标原点
        ↓
rotate
旋转当前坐标空间
        ↓
scale
缩放当前坐标空间
        ↓
inset
建立更小的局部绘制区域
        ↓
clipRect / clipPath
限制允许留下的像素
        ↓
drawXxx()
```

其中最重要的四个区别可以压缩成：

| API                         | 核心作用                  |
| --------------------------- | --------------------- |
| `translate()`               | 移动坐标原点，`size` 不缩小     |
| `rotate()`                  | 围绕 pivot 旋转坐标空间       |
| `scale()`                   | 围绕 pivot 缩放坐标空间       |
| `inset()`                   | 移动原点，同时缩小有效 `size`    |
| `clipRect()` / `clipPath()` | 不改 geometry，只限制可见绘制区域 |
| `withTransform()`           | 集中组合多个坐标变换            |

到这里，Canvas 已经不只是“输入几个 Offset 然后画圆画线”了。你已经开始能够**主动建立局部坐标系来组织复杂绘制**。下一阶段会把刚学完的 6.1 正式接回来：`Path → drawPath()`、`Outline → drawOutline()`，然后明确什么时候应该用基础 `drawXxx()`，什么时候才值得构造复杂 Path。

### 阶段四：把 6.1 真正接到 Canvas 上 —— `Path`、`Outline` 与复杂图形绘制

前面三阶段我们主要使用 `drawRect()`、`drawCircle()`、`drawArc()` 这类现成图元。现在把 6.1 接回来。

6.1 的核心其实不是“画图”，而是**描述几何轮廓**：

```text
moveTo / lineTo / arcTo / cubicTo ...
                ↓
               Path
                ↓
        Outline.Generic(path)
                ↓
              Shape
```

而 6.2 多出的是最后一步：

```text
Path / Outline
       ↓
DrawScope.drawPath()
DrawScope.drawOutline()
       ↓
真正产生像素
```

所以你上一阶段自己总结得非常准确：`Path` 本身不是“绘制结果”。它首先是一份几何数据。

这一阶段建立：`Sec02D_PathDrawing.kt`

#### 一、先运行完整案例

这个案例故意不再写聊天气泡那种需要大量坐标逻辑的形状。我们画一个简单的“书签 / 标签”轮廓，重点放在 API 本身，而不是花二十分钟推几何公式。

它会验证四件事：

1. 同一个 `Path` 可以反复绘制；
2. `Fill` 与 `Stroke` 不改变 Path 本身；
3. Path 可以直接使用 `Brush`；
4. `Shape → Outline → drawOutline()` 可以和 Canvas 绘制体系连接起来。

```kotlin
@Composable
fun Sec02D_PathDrawing() {
    var useGradient by remember { mutableStateOf(true) }
    var showStroke by remember { mutableStateOf(true) }

    Scaffold { innerPadding ->
        Column(
            modifier = Modifier
                .fillMaxSize()
                .padding(innerPadding)
                .verticalScroll(rememberScrollState())
                .padding(24.dp),
            verticalArrangement = Arrangement.spacedBy(16.dp)
        ) {
            Row(
                horizontalArrangement = Arrangement.spacedBy(12.dp)
            ) {
                Button(
                    onClick = {
                        useGradient = !useGradient
                    }
                ) {
                    Text(
                        if (useGradient) {
                            "Use Color"
                        } else {
                            "Use Gradient"
                        }
                    )
                }

                Button(
                    onClick = {
                        showStroke = !showStroke
                    }
                ) {
                    Text(
                        if (showStroke) {
                            "Hide Stroke"
                        } else {
                            "Show Stroke"
                        }
                    )
                }
            }

            Canvas(
                modifier = Modifier
                    .fillMaxWidth()
                    .height(500.dp)
            ) {
                drawRect(
                    color = Color(0xFFF4F4F4)
                )

                val horizontalPadding = 24.dp.toPx()
                val itemWidth = size.width - horizontalPadding * 2f
                val itemHeight = 105.dp.toPx()

                // ---------- 1. 直接构造并绘制 Path ----------

                val firstTop = 24.dp.toPx()

                val bookmarkPath = createBookmarkPath(
                    width = itemWidth,
                    height = itemHeight
                )

                translate(
                    left = horizontalPadding,
                    top = firstTop
                ) {
                    if (useGradient) {
                        drawPath(
                            path = bookmarkPath,
                            brush = Brush.linearGradient(
                                colors = listOf(
                                    Color(0xFF42A5F5),
                                    Color(0xFF7E57C2)
                                ),
                                start = Offset.Zero,
                                end = Offset(
                                    x = itemWidth,
                                    y = itemHeight
                                )
                            )
                        )
                    } else {
                        drawPath(
                            path = bookmarkPath,
                            color = Color(0xFF42A5F5)
                        )
                    }

                    if (showStroke) {
                        drawPath(
                            path = bookmarkPath,
                            color = Color(0xFF1A237E),
                            style = Stroke(
                                width = 3.dp.toPx(),
                                join = StrokeJoin.Round
                            )
                        )
                    }
                }

                // ---------- 2. 同一个 Path，只画 Stroke ----------

                val secondTop = 165.dp.toPx()

                translate(
                    left = horizontalPadding,
                    top = secondTop
                ) {
                    drawPath(
                        path = bookmarkPath,
                        color = Color(0xFF00897B),
                        style = Stroke(
                            width = 8.dp.toPx(),
                            cap = StrokeCap.Round,
                            join = StrokeJoin.Round
                        )
                    )
                }

                // ---------- 3. Shape -> Outline -> drawOutline ----------

                val thirdTop = 305.dp.toPx()
                val outlineSize = Size(
                    width = itemWidth,
                    height = itemHeight
                )

                translate(
                    left = horizontalPadding,
                    top = thirdTop
                ) {
                    val outline = BookmarkShape.createOutline(
                        size = outlineSize,
                        layoutDirection = layoutDirection,
                        density = this
                    )

                    drawOutline(
                        outline = outline,
                        brush = Brush.horizontalGradient(
                            colors = listOf(
                                Color(0xFFFFB74D),
                                Color(0xFFEF5350)
                            )
                        )
                    )

                    drawOutline(
                        outline = outline,
                        color = Color(0xFF6D4C41),
                        style = Stroke(
                            width = 3.dp.toPx(),
                            join = StrokeJoin.Round
                        )
                    )
                }
            }
        }
    }
}

private fun createBookmarkPath(
    width: Float,
    height: Float
): Path {
    val notchDepth = width * 0.12f
    val centerY = height / 2f

    return Path().apply {
        moveTo(
            x = 0f,
            y = 0f
        )

        lineTo(
            x = width,
            y = 0f
        )

        lineTo(
            x = width - notchDepth,
            y = centerY
        )

        lineTo(
            x = width,
            y = height
        )

        lineTo(
            x = 0f,
            y = height
        )

        close()
    }
}

private val BookmarkShape = object : Shape {
    override fun createOutline(
        size: Size,
        layoutDirection: LayoutDirection,
        density: Density
    ): Outline {
        return Outline.Generic(
            path = createBookmarkPath(
                width = size.width,
                height = size.height
            )
        )
    }
}
```

#### 二、第一件必须彻底区分的事：`Path` 不负责“长什么颜色”

看：

```kotlin
val bookmarkPath = createBookmarkPath(
    width = itemWidth,
    height = itemHeight
)
```

里面只有：

```kotlin
moveTo()
lineTo()
close()
```

没有：

```text
Color
Brush
alpha
StrokeWidth
```

原因很简单：`Path` 只回答“几何边界在哪里”。比如这个 Path 可以抽象成：

```text
(0,0)
   ↓
(width,0)
   ↓
(width-notch, centerY)
   ↓
(width,height)
   ↓
(0,height)
   ↓
close
```

这是纯几何。然后你第一次：

```kotlin
drawPath(
    path = bookmarkPath,
    brush = ...
)
```

告诉 DrawScope：把这个几何区域填充成渐变。

第二次：

```kotlin
drawPath(
    path = bookmarkPath,
    color = ...,
    style = Stroke(...)
)
```

又告诉它：沿着完全相同的几何边界画一条轮廓线。所以一个很稳定的模型是：

```text
Path
= Geometry

drawPath()
= Rasterize / Draw this geometry
```

以后你看到一个复杂 Path，第一反应不要是：“它是什么颜色？” 因为 Path 根本不知道颜色。

#### 三、一个 `Path` 可以被反复使用

案例中：

```kotlin
val bookmarkPath = createBookmarkPath(...)
```

只构造了一次。但是后面我们：

```kotlin
drawPath(
    path = bookmarkPath,
    brush = ...
)
```

又：

```kotlin
drawPath(
    path = bookmarkPath,
    color = ...,
    style = Stroke(...)
)
```

再把它放到第二个位置：

```kotlin
translate(...) {
    drawPath(
        path = bookmarkPath,
        ...
    )
}
```

这点很值得注意。你不用为了：

```text
一个填充版本
一个描边版本
一个换颜色版本
```

构造三个 Path。如果**几何轮廓相同**，完全可以让它们共享同一份 Path。这其实就是我们一直强调的：

```text
Geometry
和
Drawing Style
是两个正交维度
```

#### 四、为什么这一版特意用 `translate()`

如果不用阶段三学到的变换，第二个 Path 可能写成：

```kotlin
createBookmarkPath(
    top = secondTop,
    ...
)
```

然后 Path 内部变成：

```kotlin
moveTo(
    0f,
    secondTop
)

lineTo(
    width,
    secondTop
)

...
```

这个 API 设计就开始变脏了。现在：

```kotlin
createBookmarkPath(
    width,
    height
)
```

永远假定：

```text
自己左上角 = (0,0)
```

然后外部：

```kotlin
translate(
    left = horizontalPadding,
    top = secondTop
) {
    drawPath(bookmarkPath)
}
```

决定它真正出现在哪里。这样 Path 本身只关心：**我的内部几何是什么。**外层 Canvas 才关心：**这个视觉对象应该摆在哪里。**这是上一阶段局部坐标系第一次真正和复杂 Path 结合起来。以后如果你自己画日历事件块、复杂 icon、图表元素，我强烈建议优先保持这种职责分离。

#### 五、`close()` 到底意味着什么

你在 6.1 已经用过：

```kotlin
close()
```

这里快速唤醒一下即可。假设最后一个点是：

```text
(0, height)
```

第一个点：

```text
(0, 0)
```

调用：

```kotlin
close()
```

就把当前 contour 的最后一点连接回起点。所以：

```text
A → B → C → D → E
                 ↓
              close()
                 ↓
              E → A
```

形成闭合轮廓。如果你准备：

```kotlin
style = Fill
```

通常闭合形状就应该明确 `close()`。而对于：

```text
折线
曲线
一条开放轨迹
```

则不一定要 close。

#### 六、现在终于能真正理解 `Fill` 对 Path 做了什么

第二阶段我们已经学过：

```kotlin
Fill
```

现在放到 Path 上更容易看出本质。当：

```kotlin
drawPath(
    path = bookmarkPath,
    style = Fill
)
```

DrawScope 根据这个闭合 Path 确定：哪些位置属于这个几何区域的内部。然后填充内部像素。而：

```kotlin
style = Stroke(...)
```

关注的是：沿 Path 本身的轮廓轨迹画线。所以可以粗略区分：

```text
Fill：

██████████████
████████████ /
██████████  <
████████████ \
██████████████


Stroke：

─────────────\
             <
─────────────/
```

仍然是同一个 Path，只是消费它的方式不同。

---

#### 七、`StrokeJoin` 现在终于值得正式看了

第二阶段我们只说过：

```text
StrokeCap
→ 开放线段的端点

StrokeJoin
→ 连续线段的连接处
```

现在这个 Path 有明显折角，所以：

```kotlin
Stroke(
    width = 8.dp.toPx(),
    join = StrokeJoin.Round
)
```

就有实际视觉意义了。假设两条线相交：

```text
      /
     /
────
```

连接处可以有不同策略。`Miter` 倾向保持尖角：

```text
      /\
     /
────
```

`Round` 把连接处做圆滑处理。`Bevel` 会削掉尖角。对于我们这种右侧 V 型凹口，如果 Stroke 很粗，`join` 的区别会非常明显。现在不需要把三个枚举背下来。真正需要记住：当 Path 由多段线组成并且使用粗 Stroke 时，连接处的视觉效果由 `StrokeJoin` 决定。

#### 八、`Brush + Path` 没有什么特殊规则

这一段：

```kotlin
drawPath(
    path = bookmarkPath,
    brush = Brush.linearGradient(
        ...
    )
)
```

其实没有引入新的机制。第二阶段已经学过：

```text
Brush
= 根据位置生成颜色
```

现在只是把 Brush 应用到复杂 Path。Path 决定：

```text
哪些像素属于形状
```

Brush 决定：

```text
这些位置分别应该是什么颜色
```

所以它们很好组合：

```text
Path
   ↓
建立几何区域
   ↓
Brush
   ↓
根据位置生成颜色
   ↓
drawPath
```

以后自定义图表、渐变波浪、复杂进度条都会是这一套。

#### 九、`Outline` 和 `Path` 的关系现在可以彻底讲清楚了

这是 6.1 留下来的核心关系。Compose 的：

```kotlin
Outline
```

大体有三类几何表达：

```text
Outline.Rectangle
Outline.Rounded
Outline.Generic
```

其中复杂任意轮廓：

```kotlin
Outline.Generic(
    path = ...
)
```

本质上就是包装一个 Path。我们现在的：

```kotlin
private val BookmarkShape = object : Shape {
    override fun createOutline(
        size: Size,
        layoutDirection: LayoutDirection,
        density: Density
    ): Outline {
        return Outline.Generic(
            path = createBookmarkPath(
                width = size.width,
                height = size.height
```

正是你 6.1 做过的事情。整个链条：

```text
BookmarkShape
     ↓
createOutline(size)
     ↓
createBookmarkPath(size)
     ↓
Outline.Generic(Path)
```

到这里为止依然只是**生成轮廓描述**。然后 6.2 才：

```kotlin
drawOutline(
    outline = outline,
    brush = ...
)
```

最终把 Outline 画出来。所以现在 6.1 和 6.2 已经真正连接起来了：

```text
6.1
Shape
 ↓
createOutline()
 ↓
Outline
 ↓
Path

6.2
Path / Outline
 ↓
DrawScope
 ↓
drawPath() / drawOutline()
 ↓
pixels
```

#### 十、`drawOutline()` 的价值到底在哪里

你可能马上会问：Generic Outline 里面就是一个 Path，我直接 `drawPath()` 不就行了吗？完全正确。如果你手里本来就有：

```kotlin
val path: Path
```

直接：

```kotlin
drawPath(path)
```

通常最自然。`drawOutline()` 真正方便的是：**你手里的抽象本来就是 Outline。**比如现在：

```kotlin
val outline = BookmarkShape.createOutline(...)
```

你并不应该再写：

```text
判断是不是 Generic
→ 从里面拿 Path
→ 如果 Rectangle 再另外处理
→ Rounded 再另外处理
```

直接：

```kotlin
drawOutline(outline)
```

即可。也就是说，API 选择看你手里已经有什么：

```text
手里是 Path
→ drawPath()

手里是 Outline
→ drawOutline()
```

不要为了调用 `drawOutline()` 特意把一个 Path 包成：

```kotlin
Outline.Generic(path)
```

这通常没有价值。

---

#### 十一、为什么 `Shape` 只接收 `Size`，却没有 `topLeft`

注意：

```kotlin
BookmarkShape.createOutline(
    size = outlineSize,
    ...
)
```

没有：

```text
x
y
topLeft
```

这是 Shape 一个很重要的设计思想。Shape 描述的是：**给我一块宽 `W`、高 `H` 的区域，我告诉你这块区域内部的轮廓是什么。**它默认自己的局部区域就是：

```text
(0,0)
────────────→ width
│
│
↓
height
```

至于整个对象最后放在哪里，不属于 Shape 的职责。所以我们的第三个图形：

```kotlin
translate(
    left = horizontalPadding,
    top = thirdTop
) {
    val outline = BookmarkShape.createOutline(
        size = outlineSize,
        ...
    )

    drawOutline(outline)
}
```

非常漂亮地体现了职责：

```text
translate()
→ 整个对象在哪里

Shape / Outline
→ 对象内部轮廓是什么

drawOutline()
→ 怎么把轮廓画出来
```

这跟刚才 Path 的局部坐标设计是一模一样的。

---

#### 十二、`drawOutline()` 不等于“给 Composable 设置 Shape”

这里必须避免混淆。我们以前可能：

```kotlin
Modifier
    .background(
        color = ...,
        shape = BookmarkShape
    )
```

或者：

```kotlin
Modifier.clip(BookmarkShape)
```

这里 `Shape` 是交给某个 Modifier / 图形系统使用。而现在：

```kotlin
drawOutline(
    outline = outline,
    color = ...
)
```

只是：在当前 DrawScope 中，把这个 Outline 当成一个图形直接画出来。它不会自动变成 Canvas 的 clipping shape，也不会让 Canvas 的 Layout 本身变成这个形状。例如：

```text
Canvas 布局区域仍然是矩形
```

我们只是在这个矩形绘制区域中画出了一个书签形 Outline。这和：

```kotlin
Modifier.clip(shape)
```

是不同职责。

---

#### 十三、什么时候应该使用基础 `drawXxx()`，什么时候用 Path

现在已经可以正式给出选择边界了。如果目标是：

```text
矩形
圆角矩形
圆
椭圆
直线
圆弧
```

优先：

```kotlin
drawRect()
drawRoundRect()
drawCircle()
drawOval()
drawLine()
drawArc()
```

不要因为已经学会 Path，就写：

```kotlin
val path = Path()
path.addOval(...)
drawPath(path)
```

来替代：

```kotlin
drawCircle(...)
```

后者语义明显更清楚。Path 真正值得出现的情况，是基础图元无法方便描述：

```text
聊天气泡
星形
波浪
不规则标签
Bezier 曲线
多个线段 + 圆弧组成的复杂轮廓
手绘轨迹
图表曲线
```

可以把选择原则压缩成一句：**简单几何直接画；需要组合几何段时才创建 Path。**

---

#### 十四、`Path.addRect()` / `addOval()` 和 `drawRect()` / `drawOval()` 为什么都存在

这是你前面已经感受到的重复感：

6.1：

```kotlin
path.addRect(...)
path.addOval(...)
```

现在：

```kotlin
drawRect(...)
drawOval(...)
```

它们名字很像，但层级完全不同。

```kotlin
path.addOval(...)
```

表示：把一个椭圆轮廓添加进 Path 数据里。执行结束后屏幕不会因此出现一个椭圆。而：

```kotlin
drawOval(...)
```

表示：现在直接向当前 DrawScope 绘制这个椭圆。所以：

```text
Path API
→ 修改几何描述

DrawScope API
→ 执行绘制
```

为什么要允许：

```kotlin
path.addOval()
```

因为你可能需要把这个 Oval 和其他 contour 组合起来：

```text
一个大矩形
-
两个圆形缺口
+
另一段曲线
```

然后整体做：

```kotlin
drawPath(...)
```

或者 PathOperation，再得到复杂轮廓。所以两套 API 并不重复，只是抽象层级不同。

---

#### 十五、Path 里面可以有多个 contour

这一点在真实绘制中也值得知道。假设：

```kotlin
val path = Path()

path.addRect(...)
path.addOval(...)
```

同一个 `Path` 并不意味着只能有一条连续的线。它可以包含多个独立的 contour。例如：

```text
┌─────────┐

    ○
```

矩形和圆之间完全没有连接，但都可以属于同一个 Path。然后：

```kotlin
drawPath(path)
```

一次绘制。因此 `Path` 更准确地理解为：一个可以包含一条或多条轮廓的几何描述对象。这也是为什么它能表达非常复杂的 shape。

---

#### 十六、这里顺便纠正一个很容易形成的错觉：Path 不是“绝对坐标对象”

例如：

```kotlin
val path = createBookmarkPath(
    width = 300f,
    height = 100f
)
```

内部所有点：

```text
(0,0)
(300,0)
...
```

当然被记录成了这些数值。但是最终它出现在什么地方，还取决于当前 DrawScope 的变换。同一个 Path：

```kotlin
translate(left = 20f) {
    drawPath(path)
}
```

和：

```kotlin
translate(left = 300f) {
    drawPath(path)
}
```

最终屏幕位置不同。所以更准确地说：Path 保存的是它自己坐标空间里的几何数据；最终如何映射到 Canvas，由当前绘制变换决定。到这里，你上一阶段的坐标系模型和 Path 才真正闭环。

---

#### 十七、这一阶段不继续下钻 `Outline` 源码

这里有一个很诱人的坑：

```text
drawOutline 到底内部如何区分
Outline.Rectangle
Outline.Rounded
Outline.Generic
```

确实可以继续读源码。但当前没有必要。你作为应用层开发者只要知道：

```text
Rectangle
→ 矩形轮廓

Rounded
→ RoundRect 轮廓

Generic
→ Path 任意轮廓
```

然后：

```kotlin
drawOutline(...)
```

能够消费它们即可。源码不会显著提升你接下来做日历、自定义控件的能力，所以到这里停止。

#### 阶段四收尾

现在把第 6.1 和 6.2 放到一起，可以得到一个非常完整的绘图层级：

```text

    ↓

复杂几何需求
```

### 阶段五：Canvas 的运行边界 —— State、重绘与 Compose 阶段模型

#### 一、先把 Compose 的几个阶段摆正

目前可以先使用这个应用层模型：

```text
Composition
决定 UI 结构、调用哪些 Composable、构造哪些 Modifier
        ↓
Layout
    Measurement
    Constraints → 实际 width / height

    Placement
    决定节点相对于父节点的位置
        ↓
Drawing
根据已经确定的尺寸和位置产生最终像素
```

比如：

```kotlin
Canvas(
    modifier = Modifier
        .width(280.dp)
        .height(240.dp)
) {
    println(size)
}
```

`280.dp / 240.dp` 参与的是 Layout。它们结合父布局传来的 Constraints、Density 等信息，最终得到实际像素尺寸。

等进入：

```kotlin
Canvas {
    size
}
```

这里已经到了 Drawing。此时 `size` 类似：

```text
Size(
    width = 840f,
    height = 720f
)
```

也就是**最终测量得到的绘制尺寸，单位 px**。但有一个非常重要的补充：Compose 并不是每次状态变化都从 Composition → Layout → Drawing 三阶段重新完整跑一遍。Compose 会观察 **State 到底在哪个阶段被读取**，尽量从真正需要失效的阶段开始工作。这就是这一阶段最值得亲手验证的东西。

#### 二、一个非常干净的 State 实验

创建课程文件 `Sec02E_DrawPhaseTest.kt`，在文件里增加下面这个独立实验 Composable。

```kotlin
@Composable
fun DrawPhaseStateExperiment() {
    Scaffold { innerPadding ->
        Column(
            modifier = Modifier
                .fillMaxSize()
                .padding(innerPadding)
                .padding(24.dp),
```

#### 三、第一个案例最关键的地方只有这一行

```kotlin
val currentAlpha = alphaState.floatValue
```

注意它的位置：

```kotlin
Canvas {
    val currentAlpha = alphaState.floatValue

    drawCircle(
        alpha = currentAlpha
    )
}
```

`alphaState` 这个 State 对象当然是在 Composition 时通过：

```kotlin
remember {
    mutableFloatStateOf(1f)
}
```

创建并保存的。但是：**State 对象在哪里存在，和 State 的 value 在哪里被读取，是两件不同的事情。**真正建立依赖的是：

```kotlin
alphaState.floatValue
```

这一行在哪里执行。第一组实验中，它发生在：

```kotlin
Canvas {
    ...
}
```

也就是 Drawing。因此 Compose 能知道：这个 State 的值影响的是这个 DrawScope 的绘制结果。点击按钮改变 `alphaState` 后，在这个状态没有被其他更早阶段读取的前提下，理论上你主要应该看到：

```text
DRAW-ONLY -> DRAW
```

而不是再次看到：

```text
DRAW-ONLY -> COMPOSITION
```

也就是说：

```text
State 改变
   ↓
Draw dependency invalidated
   ↓
重新 Drawing

不需要：
Composition
不需要：
重新测量 Canvas
```

这就是你之前一直提到的：“能不能只刷新绘制而避免重组？” 现在第一次有了一个非常具体的答案。

**可以。关键不是 Canvas 有什么神奇优化，而是 State 的读取发生在哪个阶段。**

---

#### 四、第二组只移动了一行代码，结果完全不同

第二组：

```kotlin
val currentAlpha = alphaState.floatValue
```

放在：

```kotlin
@Composable
private fun CompositionStatePanel() {
    ...
}
```

Composable 函数执行期间。然后 Canvas 只是捕获：

```kotlin
currentAlpha
```

```kotlin
Canvas {
    drawCircle(
        alpha = currentAlpha
    )
}
```

注意 Canvas 内部这时候没有再读取：

```kotlin
alphaState.floatValue
```

它只是拿到了一个普通 `Float`。因此依赖关系变成：

```text
Composition
     ↓
读取 alphaState.floatValue
     ↓
得到 Float
     ↓
Canvas 捕获 Float
```

状态变化之后：

```text
State 改变
   ↓
Composition 失效
   ↓
重新执行 Composition
   ↓
得到新的 Float
   ↓
后续绘制得到新结果
```

所以你应该看到：

```text
COMPOSITION-READ -> COMPOSITION
COMPOSITION-READ -> DRAW
```

这两个实验的 UI 结果完全一样：

```text
圆从 alpha 1.0
变成 alpha 0.25
```

但是内部执行路径不同。这就是 Compose 性能模型里一个非常核心的思想：**在能够满足需求的情况下，把状态读取尽量推迟到真正需要它的阶段，可以跳过前面的阶段。**但注意，不是为了“逃避重组”到处强行这样写。只有当某个值本来就只影响 Drawing，它才应该自然地在 Drawing 中读取。

#### 五、Layout 也遵循同样的原则

你现在还没系统学习自定义 Layout，所以这一阶段不写 Layout 实验。

但模型已经可以补完整：

```text
State 在 Composition 读取
        ↓
可能重新 Composition
        ↓
必要时 Layout
        ↓
Drawing


State 在 Layout 读取
        ↓
可以跳过 Composition
        ↓
Layout
        ↓
Drawing


State 只在 Drawing 读取
        ↓
可以跳过 Composition
可以跳过 Layout
        ↓
Drawing
```

这就是你之前脑中那些“黑暗里的几束亮点”真正应该连接成的基本框架。后面 7 章会把中间这一层：

```text

Measure

```

真正拆开讲。而 6.3 会继续研究：

```text

↓
Draw Modifier
↓
invalidate draw
```

现在知道总图即可。

#### 六、为什么不能在 DrawScope 里面修改 State

既然可以：

```kotlin
Canvas {
    val alpha = state.floatValue
}
```

千万不要反过来写：

```kotlin
Canvas {
    state.floatValue += 0.1f
}
```

逻辑上就会变成：

```text
Drawing
   ↓
修改 State
   ↓
State 使 Drawing 失效
   ↓
再次 Drawing
   ↓
再次修改 State
   ↓
……
```

这非常容易形成持续 invalidation，甚至逻辑循环。因此 Draw lambda 应该有非常清晰的职责：**读取绘制所需输入，然后产生绘制命令。**不要在里面：

```text
启动网络请求
修改业务 State
启动协程
写数据库
做生命周期操作
```

绘制阶段可能执行很多次，它应该尽量保持纯粹而轻量。

---

#### 七、为什么也不应该在 DrawScope 里反复创建昂贵对象

例如：

```kotlin
Canvas {
    val complicatedPath = Path().apply {
        // 大量复杂计算
    }

    val brush = Brush.linearGradient(
        ...
    )

    drawPath(
        complicatedPath,
        brush
    )
}
```

语义上当然合法。但 Draw 可能因为：

```text
动画
State
滚动
父节点刷新
图层变化
```

频繁执行。如果某个 Path 或 Brush 构造成本明显较高，而且它可以跨多次 Draw 复用，就没有必要每次重新创建。这正是后面 6.3 的：

```kotlin
drawWithCache()
```

存在的重要原因之一。本阶段先留下一个原则：**Draw block 可以频繁执行，因此坐标计算和简单对象创建没必要神经质地优化，但明显昂贵、稳定可复用的绘图资源不要无脑每帧重新构造。**什么时候缓存、缓存什么时候失效，我们放到 6.3 正式讲。

---

#### 八、`DrawScope.size` 是绘制参考范围，不等于自动裁切范围

这个边界非常容易误解。例如：

```kotlin
Canvas(
    modifier = Modifier.size(120.dp)
) {
    drawCircle(
        color = Color.Red,
        radius = 50.dp.toPx(),
        center = Offset(
            x = size.width,
            y = center.y
        )
    )
}
```

圆心就在 Canvas 的最右边：

```text
Canvas

┌────────────┐
│            │
│           (●
│            │
└────────────┘
            ↑
          圆心
```

因此圆的一半在 Canvas 自己的 `size.width` 之外。重要的是：`DrawScope.size` 告诉你当前节点的绘制尺寸，但它本身并不等于“强制所有 drawXxx 都只能出现在这个矩形里”。绘制可以使用：

```kotlin
x < 0
x > size.width
y < 0
y > size.height
```

这些坐标。超出去的内容最终能不能看见，还会受到祖先裁切、graphics layer、显式 clip 等因素影响。如果你明确希望限制：

```text
只能显示在某个区域内
```

才使用我们上一阶段学过的：

```kotlin
clipRect {
    ...
}
```

或者：

```kotlin
clipPath {
    ...
}
```

后面还会接触 Modifier 层面的 clipping。

---

#### 九、这又证明了“Draw 不改变 Layout”

假设有：

```text
Column

Canvas：120dp 高
Text："Hello"
```

Canvas 里面突然画一个巨大的圆：

```kotlin
drawCircle(
    radius = 300.dp.toPx()
)
```

这并不会让 Layout 系统发现：“哎呀，这个 Canvas 视觉上现在 600dp 高了，我应该把下面的 Text 推下去。” Layout 仍然只知道：

```text
Canvas measured height = 120dp
```

绘制内容视觉上越界，是 Drawing 自己的事情。因此以后做 UI 时有一个非常实用的判断：如果需求是：“视觉效果变大，但不应该影响兄弟节点位置。” Draw transform / `graphicsLayer` 一类方案往往合适。

如果需求是：“这个元素变大以后，下面的其他 UI 也应该跟着让出空间。” 那就不能只改变 Drawing。必须真正改变 Layout。这也是为什么 Compose 把 Layout 和 Drawing 严格区分非常有价值。

---

#### 十、`Canvas` 到底是不是传统 Android 的自定义 View

不是。这一点现在可以正式确定下来。传统 Android：

```kotlin
class MyView : View {
    override fun onMeasure(...) {
        ...
    }

    override fun onDraw(canvas: android.graphics.Canvas) {
        ...
    }
}
```

这是一个真正的 Android `View` 对象，它拥有 View 的整个测量、布局、绘制和事件体系。

Compose：

```kotlin
Canvas(
    modifier = ...
) {
    ...
}
```

并没有创建一个你的 `CanvasView : View`。它仍然存在于 Compose 自己的节点体系中。`Canvas` 只是提供了一个非常方便的：

```text
Composable
+
DrawScope
```

让你拥有一块参加 Compose Layout 的区域，并在 Drawing 阶段往里面发绘图命令。所以：

```text
传统 MyView.onDraw()
```

和：

```text
Compose Canvas { }
```

在“都可以自定义画东西”这个使用体验上很像，但底层架构不是一回事。

---

#### 十一、`Canvas` 和 `drawBehind()` 到底什么关系

到这里你已经有能力知道这个事实了。平时我们写：

```kotlin
Canvas(
    modifier = Modifier.size(200.dp)
) {
    drawCircle(...)
}
```

它特别适合：这个 Composable 本身的主要职责就是自定义绘制。比如：

```text
图表
时钟
自定义时间轴背景
签名板
绘图区域
复杂装饰图形
```

但假设你已经有一个：

```kotlin
Text(...)
```

只是想在 Text 后面画个装饰圆。如果为了画这个圆再专门套一个 Canvas：

```text
Box
├── Canvas
└── Text
```

往往显得笨重。Compose 有：

```kotlin
Modifier.drawBehind {
    ...
}
```

可以直接在这个 Composable **内容后面**进行 DrawScope 绘制。概念上：

```text
Canvas
→ 一个以自定义绘制为主要职责的 Composable

drawBehind
→ 给现有 Composable 增加背景绘制行为
```

而且两边使用的仍然都是：

```text
DrawScope
```

所以你现在学的：

```text
size
center
drawCircle
drawPath
translate
rotate
clipRect
```

以后到了 `drawBehind` 几乎全部原封不动继续使用。

---

#### 十二、另外两个兄弟 API 现在只定位，不展开

6.3 会正式讲三个非常重要的 Draw Modifier。`drawBehind`：

```text
先画你的自定义内容
再画 Composable 自己的内容
```

适合背景装饰。`drawWithContent`：

```text
你自己决定什么时候调用 drawContent()
```

因此可以：

```text
先内容 → 再特效
```

也可以：

```text
先背景 → 内容 → 前景
```

控制力更强。`drawWithCache`：

```text
为绘图构造一些可缓存对象
↓
多次 Drawing 复用
```

适合 Path、Brush、Shader 等构造成本较高的绘制资源。这一阶段**不要继续深入它们**。目前只要知道：

```text
Canvas 学到的 DrawScope 能力
并不是 Canvas 独占的。

后面 Draw Modifier
仍然使用同一个 DrawScope 绘图体系。
```

这样到了 6.3 就不会感觉换了一门技术。

---

#### 十三、最后一个容易混淆的 Canvas：`drawIntoCanvas()`

以后你还会看到：

```kotlin
drawIntoCanvas { canvas ->
    ...
}
```

注意这里的 `canvas` 和：

```kotlin
@Composable
Canvas { ... }
```

不是一个层级的东西。前者拿到的是 Compose graphics 层的：

```text
androidx.compose.ui.graphics.Canvas
```

属于更底层的绘图对象。必要时还能进一步通过：

```kotlin
canvas.nativeCanvas
```

进入 Android 原生 Canvas 互操作。所以可以先这样区分：

```text
Canvas(...)
→ Composable

DrawScope
→ 日常 Compose 自定义绘制的主要 API

drawIntoCanvas()
→ 需要更底层 Canvas 能力时的入口

nativeCanvas
→ 与传统 Android Canvas 互操作
```

对于绝大多数自定义 UI：

```kotlin
drawRect()
drawPath()
drawCircle()
...
```

已经够用。`drawIntoCanvas()` 现在知道存在即可，不值得提前深入。

#### 阶段五真正需要留下来的模型

这一阶段最重要的是把你之前零散接触到的 Compose 阶段第一次连成一条完整主线：

```text
Composition
决定 UI 结构
        ↓
Layout
Measure：多大
Place：在哪
        ↓
Drawing
最终怎么画
```

但它不是每次都从头运行：

```text
State 在 Composition 被读取
→ Composition 可能重新执行

State 只在 Layout 被读取
→ 可以跳过 Composition

State 只在 Drawing 被读取
→ 可以跳过 Composition 和 Layout
→ 仅使 Drawing 失效
```

同时：

```text
DrawScope.size
→ 已测量得到的实际 px 尺寸

Draw transform
→ 只改变视觉绘制

画到 size 外面
→ 不会扩大 Layout

Canvas
→ Compose 中的绘制 Composable
→ 不是传统 Android View

drawBehind / drawWithContent / drawWithCache
→ 后续把同一套 DrawScope 能力挂到现有 Composable 上
```

到这里，6.2 的 **Canvas / DrawScope 基础机制已经基本学完整了**。最后还剩一个阶段值得做：不再认识新概念，而是把前面的 `size + 坐标 + DrawScope + Path + State` 组合成一个真正接近你未来 App 的 **日历当天时间轴 Canvas**。那一阶段会重点验证“时间数据如何稳定映射为 Y 坐标”，也会明确 Canvas 与未来 `Layout`、手势系统各自应该负责什么。

### 阶段六：真实 App 实战 —— 用 Canvas 绘制一天时间轴

前五个阶段已经把 `Canvas / DrawScope / Path / Transform / State` 的基础机制学完了。这一阶段不再扩 API，而是做一个更接近你未来日历 App 的东西：**把“时间”稳定映射成 Canvas 上的 Y 坐标，再绘制小时网格、事件块和当前时间线。**

这一阶段最核心的问题只有一个：业务数据里的 `09:30、14:10、16:00`，怎样转换成一个随 Canvas 尺寸自动变化的几何位置？建立文件：`Sec02F_DayTimelineCanvas.kt`

#### 一、完整可运行示例

为了让绘制逻辑本身足够干净，我们显示 `08:00 ~ 18:00` 共 10 小时。Slider 用来模拟当前时间；三个事件块则模拟真实日程。

```kotlin
private data class TimelineEventUi(
    val title: String,
    val startMinute: Int,
    val endMinute: Int,
    val color: Color
)

@Composable
fun Sec02E_DayTimelineCanvas() {
    val timelineStartMinute = 8 * 60
    val timelineEndMinute = 18 * 60

    var currentMinute by remember {
        mutableIntStateOf(10 * 60 + 30)
    }

    val events = listOf(
        TimelineEventUi(
            title = "Compose study",
            startMinute = 9 * 60,
            endMinute = 10 * 60 + 15,
            color = Color(0xFF42A5F5)
        ),
        TimelineEventUi(
            title = "Lunch",
            startMinute = 11 * 60 + 30,
            endMinute = 12 * 60 + 20,
            color = Color(0xFFFFB74D)
        ),
        TimelineEventUi(
            title = "App development",
            startMinute = 14 * 60 + 10,
            endMinute = 16 * 60,
            color = Color(0xFF66BB6A)
        )
    )

    Scaffold { innerPadding ->
        Column(
            modifier = Modifier
                .fillMaxSize()
                .padding(innerPadding)
                .verticalScroll(rememberScrollState())
                .padding(24.dp),
            verticalArrangement = Arrangement.spacedBy(16.dp)
        ) {
            Text(
                text = "Current time: ${formatMinuteOfDay(currentMinute)}"
            )

            Slider(
                value = currentMinute.toFloat(),
                onValueChange = {
                    currentMinute = it.roundToInt()
                },
                valueRange = timelineStartMinute.toFloat()..
                    timelineEndMinute.toFloat(),
                steps = 19
            )

            Canvas(
                modifier = Modifier
                    .fillMaxWidth()
                    .height(600.dp)
            ) {
                val startHour = timelineStartMinute / 60
                val endHour = timelineEndMinute / 60
                val totalMinutes =
                    timelineEndMinute - timelineStartMinute

                val timeAxisWidth = 32.dp.toPx()
                val contentLeft =
                    timeAxisWidth + 12.dp.toPx()

                val eventLeft =
                    contentLeft + 8.dp.toPx()

                val eventRight =
                    size.width - 12.dp.toPx()

                fun minuteToY(minute: Int): Float {
                    val minuteFromStart =
                        minute - timelineStartMinute

                    val progress =
                        minuteFromStart.toFloat() /
                            totalMinutes.toFloat()

                    return progress * size.height
                }

                // ---------- Background ----------

                drawRect(
                    color = Color(0xFFF8F9FA)
                )

                // ---------- Time axis ----------

                drawLine(
                    color = Color(0xFFBDBDBD),
                    start = Offset(
                        x = contentLeft,
                        y = 0f
                    ),
                    end = Offset(
                        x = contentLeft,
                        y = size.height
                    ),
                    strokeWidth = 1.dp.toPx()
                )

                // ---------- Hour grid ----------

                for (hour in startHour..endHour) {
                    val hourMinute = hour * 60
                    val y = minuteToY(hourMinute)

                    drawLine(
                        color = Color(0xFFD6D9DD),
                        start = Offset(
                            x = contentLeft,
                            y = y
                        ),
                        end = Offset(
                            x = size.width,
                            y = y
                        ),
                        strokeWidth = 1.dp.toPx()
                    )

                    drawLine(
                        color = Color(0xFF757575),
                        start = Offset(
                            x = contentLeft - 8.dp.toPx(),
                            y = y
                        ),
                        end = Offset(
                            x = contentLeft,
                            y = y
                        ),
                        strokeWidth = 2.dp.toPx()
                    )
                }

                // ---------- Half-hour grid ----------

                for (hour in startHour until endHour) {
                    val halfHourMinute =
                        hour * 60 + 30

                    val y =
                        minuteToY(halfHourMinute)

                    drawLine(
                        color = Color(0xFFE5E7EB),
                        start = Offset(
                            x = contentLeft,
                            y = y
                        ),
                        end = Offset(
                            x = size.width,
                            y = y
                        ),
                        strokeWidth = 1.dp.toPx()
                    )
                }

                // ---------- Event blocks ----------

                events.forEach { event ->
                    val visibleStart =
                        maxOf(
                            event.startMinute,
                            timelineStartMinute
                        )

                    val visibleEnd =
                        minOf(
                            event.endMinute,
                            timelineEndMinute
                        )

                    if (visibleStart < visibleEnd) {
                        val eventTop =
                            minuteToY(visibleStart) +
                                3.dp.toPx()

                        val eventBottom =
                            minuteToY(visibleEnd) -
                                3.dp.toPx()

                        val eventHeight =
                            eventBottom - eventTop

                        drawRoundRect(
                            color = event.color,
                            topLeft = Offset(
                                x = eventLeft,
                                y = eventTop
                            ),
                            size = Size(
                                width = eventRight - eventLeft,
                                height = eventHeight
                            ),
                            cornerRadius = CornerRadius(
                                8.dp.toPx()
                            ),
                            alpha = 0.78f
                        )

                        drawRoundRect(
                            color = event.color,
                            topLeft = Offset(
                                x = eventLeft,
                                y = eventTop
                            ),
                            size = Size(
                                width = 5.dp.toPx(),
                                height = eventHeight
                            ),
                            cornerRadius = CornerRadius(
                                3.dp.toPx()
                            )
                        )
                    }
                }

                // ---------- Current time ----------

                if (
                    currentMinute in
                    timelineStartMinute..timelineEndMinute

                        minuteToY(currentMinute)

                    drawLine(
                        color = Color(0xFFE53935),
                        start = Offset(
                            x = contentLeft,
                            y = currentY
                        ),
                        end = Offset(
                            x = size.width,
                            y = currentY
                        ),
                        strokeWidth = 2.dp.toPx()
                    )

                    drawCircle(
                        color = Color(0xFFE53935),
                        radius = 5.dp.toPx(),

                            x = contentLeft,
                            y = currentY

            events.forEach { event ->
                Row(
                    horizontalArrangement =
                        Arrangement.spacedBy(8.dp),
```

#### 二、整个案例真正的核心只有 `minuteToY()`

```kotlin
fun minuteToY(minute: Int): Float {
    val minuteFromStart =
        minute - timelineStartMinute

    val progress =
        minuteFromStart.toFloat() /
            totalMinutes.toFloat()

    return progress * size.height
}
```

假设时间轴是：

```text
08:00 ---------------- y = 0
                       │
                       │
13:00 ---------------- y = size.height / 2
                       │
                       │
18:00 ---------------- y = size.height
```

因为整个范围：

```text
08:00 → 18:00
= 600 minutes
```

对于 `13:00`：

```text
13:00 = 780 min
08:00 = 480 min

780 - 480 = 300

300 / 600 = 0.5

y = size.height × 0.5
```

所以它永远处于 Canvas 高度正中央。对于 `09:30`：

```text
09:30 = 570
570 - 480 = 90

90 / 600 = 0.15
```

于是：

```text
y = size.height × 0.15
```

这就是日历时间轴最核心的数学模型。它不应该写成：

```kotlin
val y = 90 * 3.2f
```

因为这把数据偷偷绑定到了某一个固定像素高度。我们真正建立的是：

```text
业务时间
   ↓
归一化比例 0f..1f
   ↓
Canvas 实际 size
   ↓
最终像素坐标
```

这样 Canvas 高度从 `600.dp` 变成 `800.dp`，整个时间轴仍然自动成立。

#### 三、事件的位置和高度其实使用的是同一个映射

比如：

```text
Compose study
09:00 → 10:15
```

顶部：

```kotlin
val eventTop = minuteToY(event.startMinute)
```

底部：

```kotlin
val eventBottom = minuteToY(event.endMinute)
```

高度自然就是：

```kotlin
val eventHeight = eventBottom - eventTop
```

这比直接计算：

```text
持续 75 分钟
× 每分钟多少 px
```

更加统一，因为所有坐标都经过同一个转换函数。实际上两种数学方法最终等价，但工程上更推荐：

```text
时间点 → 坐标
```

然后：

```text
endY - startY
```

因为同一个映射函数以后还能同时处理：

```text
事件开始
事件结束
当前时间
小时线
拖拽落点
点击位置
```

整个时间轴只有一个坐标规则。

#### 四、这个映射以后还可以反过来

现在我们是：

```text
时间 → Y
```

未来做拖拽事件时，你会需要：

```text
Y → 时间
```

数学直接反过来：

```text
progress = y / size.height

minute = timelineStartMinute + progress × totalMinutes
```

也就是概念上的：

```kotlin
fun yToMinute(
    y: Float
): Int {
    val progress =
        y / size.height

    return timelineStartMinute +
        (progress * totalMinutes)
            .roundToInt()
}
```

这一阶段先不要加入手势。但你现在已经可以看到为什么时间轴特别适合 Canvas：

```text
业务世界：
09:30

        ↓ mapping

几何世界：
y = 152.4 px
```

将来手势只是把映射反过来：

```text
finger y = 152.4 px

        ↓ inverse mapping

09:30
```

等学到第 10 章手势，这条链会重新接回来。

#### 五、小时线和事件块没有两套坐标系统

小时网格：

```kotlin
val y = minuteToY(hour * 60)
```

事件：

```kotlin
val eventTop = minuteToY(event.startMinute)
```

当前时间：

```kotlin
val currentY = minuteToY(currentMinute)
```

全部经过：

```kotlin
minuteToY()
```

这是实际项目里非常值得坚持的原则：同一种业务维度，不要散落多个坐标换算公式。如果小时线用：

```text
hourHeight × hour
```

事件用：

```text
minute × anotherFactor
```

当前时间又用第三套公式，几个月之后非常容易出现几像素到几十像素的错位。现在只有一条规则，所以：

```text
10:30 的事件边界
```

和：

```text
10:30 的当前时间线
```

必然处于同一个 Y。

#### 六、为什么事件超出当前可见时间段时先裁业务数据

这里：

```kotlin
val visibleStart =
    maxOf(
        event.startMinute,
        timelineStartMinute
    )

val visibleEnd =
    minOf(
        event.endMinute,
        timelineEndMinute
    )
```

假设有事件：

```text
07:30 → 09:00
```

但页面只显示：

```text
08:00 → 18:00
```

真正应该绘制的是：

```text
08:00 → 09:00
```

而不是让：

```kotlin
minuteToY(7 * 60 + 30)
```

产生一个负 Y，然后期待 Canvas clipping 替我们处理所有事情。

当然，负坐标在绘制技术上是合法的；但这里属于**业务可见范围**，所以先把业务数据裁成当前 viewport 内的时间范围，更清晰。并且：

```kotlin
if (visibleStart < visibleEnd)
```

可以直接过滤：

```text
18:30 → 20:00
```

这种完全不在当前时间轴里的事件。这是业务层边界与图形裁切的区别：

```text
时间不在当前 viewport
→ 数据范围判断

视觉图形只能显示在某个 Shape 内
→ clipRect / clipPath
```

不要把所有边界问题都扔给 `clipRect()`。

#### 七、为什么固定间距使用 dp，而时间位置使用 `size`

这个案例正好把阶段一讲过的两种尺寸来源真正组合起来。例如：

```kotlin
val contentLeft = timeAxisWidth + 12.dp.toPx()
```

这里的 `12dp` 是视觉设计规范：时间轴和内容之间保持固定间距。所以应该使用：

```kotlin
12.dp.toPx()
```

事件 Y 坐标：

```kotlin
progress * size.height
```

则表达：这个位置占当前时间轴高度的多少比例。所以依赖 `size`。真实 Canvas 几乎都会混合这两类数据：

```text
UI Design Constant
8dp / 12dp / 16dp
        ↓
dp.toPx()

业务比例 / 几何比例
时间、百分比、进度
        ↓
× size
```

这就是正常写法，而不是要求所有数字都来自 dp 或所有数字都来自比例。

#### 八、为什么事件块本身不需要 `Path`

现在事件块只是：

```kotlin
drawRoundRect(...)
```

完全够用。这正好验证阶段四的选择原则。即使你现在已经会：

```text
Path
Outline
drawPath
drawOutline
```

也不意味着业务代码应该大量使用它们。事件块几何就是：

```text
圆角矩形
```

所以最专业的代码反而是最直接的：

```kotlin
drawRoundRect(...)
```

将来如果事件块左边需要特殊波浪形、缺口或者连接箭头，再升级成 Path。

#### 九、这里有一个故意没有解决的问题：事件重叠

真实日历一定可能出现：

```text
10:00 ───────── 11:30 Event A

       10:30 ───────── 12:00 Event B
```

现在案例会把两块画在同一列，相互覆盖。这不是 Canvas 不会画，而是这里开始出现一个新的业务 / Layout 问题：

```text
哪些事件互相重叠？
        ↓
怎么分组？
        ↓
各占几列？
        ↓
每列宽多少？
        ↓
每个事件的 x / width 是多少？
```

比如：

```text
┌────A────┬────B────┐
│         │         │
│         │         │
└─────────┴─────────┘
```

这个算法与本节的 DrawScope 基础已经不是一回事。因此当前正确做法不是趁机再塞 100 行 overlap algorithm，而是把职责留到真实 App：

```text
时间 → Y
6.2 已经解决

重叠事件 → lane / column
项目开发时根据需求实现
```

这就是“该深入的现在学，不该提前学的不要扩张课程”。

#### 十、Canvas 在真实日历里应该负责多少

这个问题很重要。假设将来你的日历页面变成：

```text
08:00 ─────────────────
       ┌──────────────┐
       │ Compose 学习 │
       └──────────────┘

09:00 ─────────────────

10:00 ─────────────────
```

我们完全可以把所有东西都塞进 Canvas，包括：

```text
文字
事件卡片
图标
时间标签
点击判断
拖拽判断
Accessibility
```

但这通常不是最优设计。一个更实际的架构可能是：

```text
Box
├── Canvas
│   ├── 小时网格
│   ├── 当前时间线
│   └── 背景装饰
│
└── Compose Event Components
    ├── Text
    ├── Icon
    ├── accessibility
    └── gestures
```

尤其当事件块本身需要：

```text
复杂文字
点击
长按
语义信息
动画
菜单
Accessibility
```

普通 Composable 往往比纯 Canvas 更合适。Canvas 很擅长的是：**大量轻量、连续、基于坐标的视觉元素。**例如：

```text
网格
刻度
连接线
当前时间线
曲线
背景区域
图表
复杂装饰
```

而一个完整的交互 UI 元素，不应该因为“Canvas 能画”就一定全部手绘。

---

#### 十一、这也是 Canvas 和未来 `Layout()` 的职责边界

你未来的日历 App 很可能同时需要：

```text
Canvas
+
Custom Layout
+
Gesture
```

但三者解决的问题不同。

`Canvas`：

```text
最终长什么样
```

`Layout`：

```text
真正的 Composable 子节点
测多大
放在哪里
```

Gesture：

```text
手指做了什么
以及怎样转换成业务行为
```

比如日历事件块如果最终是一个真正的 Composable：

```text
EventCard()
```

那它的位置可能应该由未来第 7 章的自定义 Layout 决定：

```text
startMinute
↓
计算 Y
↓
place(x, y)
```

而 Canvas 继续负责它背后的小时网格。所以不用担心：“今天学了 Canvas，以后是不是整个日历都必须 Canvas 手写？” 完全不是。真正专业的实现往往正是把三个体系组合起来。

#### 十二、这个案例中的 `TimelineEventUi` 为什么叫 UI

这里：

```kotlin
private data class TimelineEventUi(
    val title: String,
    val startMinute: Int,
    val endMinute: Int,
    val color: Color
)
```

我故意叫：

```text
TimelineEventUi
```

而不是领域对象：

```text
Event
Record
CalendarEvent
```

原因是里面存在：

```kotlin
color: Color
```

`Color` 是 Compose UI 信息。真实项目中 Repository / Domain Model 不应该为了 Canvas 携带：

```kotlin
Color
```

更合理的是：

```text
Domain Event
startTime
endTime
category
        ↓
ViewModel / UI mapping
        ↓
TimelineEventUi
startMinute
endMinute
color
```

然后 Canvas 只消费已经准备好的 UI 数据。这一点知道即可，不需要为了这个绘制课程搭完整 Clean Architecture。

#### 阶段六收尾：真正值得留下的东西

```text

↓
转换成 0..1 的相对比例
↓
乘 DrawScope.size
↓
得到当前 Canvas 的实际 px 坐标
```

```kotlin
val progress = (minute - startMinute).toFloat() / totalMinutes
val y = progress * size.height
```

于是同一套映射可以统一驱动：

```text

事件底部
当前时间线

```

而从工程职责看：

```text

→ 网格、线条、复杂连续绘制
```
