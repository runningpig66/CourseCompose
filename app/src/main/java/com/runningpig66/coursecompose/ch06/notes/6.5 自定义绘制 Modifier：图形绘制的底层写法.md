### 第一阶段：第一次真正造一个绘制 Modifier

这一阶段只完成一件事：**把你在 6.3 中已经会写的绘制逻辑，第一次封装成一个真正独立的、自定义的 Modifier。**

6.2 里你学会了在 `DrawScope` 中画东西；6.3 里你已经能用 `drawBehind`、`drawWithContent`、`drawWithCache` 把绘制插入 Modifier 链；6.4 又把绘制背后的图层与离屏缓冲补上了。到这里仍然有一个明显的问题：假如某种绘制能力要成为项目里反复使用的基础组件，例如：

```kotlin
Modifier.statusBorder(...)
Modifier.dashedBorder(...)
Modifier.timelineIndicator(...)
Modifier.selectedBackground(...)
```

我们总不能每个页面都重新写一坨 `drawWithContent { ... }`。6.5 解决的正是这一层问题：**不再只是调用 Compose 给你的绘制 Modifier，而是自己实现一个 Modifier。**

当前 Compose 官方把 `Modifier.Node` 描述为创建自定义 Modifier 的较低级 API，也是 Compose 自己实现 Modifier 所使用的机制，并明确将它作为高效实现自定义 Modifier 的方式。一个完整的 Node 型 Modifier 通常由三部分组成：`Modifier.Node`、负责创建/更新 Node 的 `ModifierNodeElement`，以及可选但通常都会提供的 Modifier factory。[Android Developers](https://developer.android.com/develop/ui/compose/custom-modifiers?hl=zh-cn)

这一阶段先把三者完整跑起来。至于“为什么 Element 和 Node 要拆成两个对象” “重组时谁销毁谁复用” “`update()` 到底什么时候执行”，全部留到第二阶段。今天先让整个机器转起来。

---

先看最终想得到什么。假设以后我们希望这样写：

```kotlin
Text(
    text = "Compose",
    modifier = Modifier
        .padding(24.dp)
        .customBorder(
            color = Color(0xFF6750A4),
            width = 4.dp,
            cornerRadius = 16.dp
        )
        .padding(24.dp)
)
```

从使用者视角看，它和：

```kotlin
Modifier.padding(...)
Modifier.background(...)
Modifier.drawBehind(...)
```

没有区别。`customBorder()` 接收几个参数，把一条自定义 Modifier 加进 Modifier 链，然后这条 Modifier 会在绘制阶段给组件画一个圆角边框。这就是我们今天真正要实现的东西。

#### 1. 可运行示例：`Sec05A_CustomBorderModifier.kt`

先完整敲下来运行。代码里我会保留少量必要注释，因为这一阶段最重要的是第一次认清三个角色。

```kotlin
private const val Sec05A = "Sec05A"

@Composable
fun Sec05A_CustomBorderModifier() {
    Column(
        modifier = Modifier
            .fillMaxSize()
            .padding(32.dp),
        verticalArrangement = Arrangement.spacedBy(32.dp)
    ) {
        Text(
            text = "自定义 DrawModifierNode",
            style = MaterialTheme.typography.titleLarge,
            modifier = Modifier
                .customBorder(
                    color = Color(0xFF6750A4),
                    width = 4.dp,
                    cornerRadius = 16.dp
                )
                .padding(24.dp)
        )

        Box(
            modifier = Modifier
                .size(width = 220.dp, height = 120.dp)
                .background(
                    color = Color(0xFFEADDFF),
                    shape = RoundedCornerShape(20.dp)
                )
                .customBorder(
                    color = Color(0xFF21005D),
                    width = 6.dp,
                    cornerRadius = 20.dp
                ),
            contentAlignment = Alignment.Center
        ) {
            Text(
                text = "同一个 Modifier\n可以复用",
                textAlign = TextAlign.Center
            )
        }
    }
}

/**
 * 对外暴露的 Modifier API。
 * 调用者只需要认识这一层。
 */
fun Modifier.customBorder(
    color: Color,
    width: Dp,
    cornerRadius: Dp
): Modifier {
    return this then CustomBorderElement(
        color = color,
        width = width,
        cornerRadius = cornerRadius
    )
}

/**
 * 描述这条 Modifier 当前携带的参数，
 * 并负责创建 / 更新真正工作的 Node。
 */
private data class CustomBorderElement(
    val color: Color,
    val width: Dp,
    val cornerRadius: Dp
) : ModifierNodeElement<CustomBorderNode>() {

    override fun create(): CustomBorderNode {
        Log.d(TAG, "Element.create()")
        return CustomBorderNode(
            color = color,
            width = width,
            cornerRadius = cornerRadius
        )
    }

    override fun update(node: CustomBorderNode) {
        Log.d(TAG, "Element.update()")

        node.color = color
        node.width = width
        node.cornerRadius = cornerRadius
    }
}

/**
 * 真正参与 Compose Modifier 节点系统并执行绘制工作的对象。
 */
private class CustomBorderNode(
    var color: Color,
    var width: Dp,
    var cornerRadius: Dp
) : Modifier.Node(), DrawModifierNode {

    override fun ContentDrawScope.draw() {
        Log.d(TAG, "Node.draw() size=$size")

        // 先绘制原本的组件内容。
        drawContent()

        val strokeWidth = width.toPx()
        val halfStrokeWidth = strokeWidth / 2f
        val radius = cornerRadius.toPx()

        drawRoundRect(
            color = color,
            topLeft = Offset(
                x = halfStrokeWidth,
                y = halfStrokeWidth
            ),
            size = Size(
                width = (size.width - strokeWidth).coerceAtLeast(0f),
                height = (size.height - strokeWidth).coerceAtLeast(0f)
            ),
            cornerRadius = CornerRadius(
                x = radius,
                y = radius
            ),
            style = Stroke(width = strokeWidth)
        )
    }
}

@PhonePreviews
@Composable
private fun Sec05A_CustomBorderModifierPreview() {
    CourseComposeTheme {
        Sec05A_CustomBorderModifier()
    }
}
```

先运行这个例子。你现在重点观察三个现象，不需要先研究代码细节。第一，两个完全不同的 Composable——一个 `Text`、一个 `Box`——都可以使用：

```kotlin
.customBorder(...)
```

说明我们做出来的不是一个“给 Text 画边框的函数”，而是一条真正独立于具体 Composable 的 **Modifier 能力**。

第二，文字和 Box 原本的内容仍然正常显示，同时边框叠加在内容上。这意味着这个 Node 并没有取代原组件，而是在绘制链中加入了自己的行为。

第三，Logcat 第一次显示页面时，你应该能看到类似：

```text
Element.create()
Node.draw() size=...
Element.create()
Node.draw() size=...
```

两个地方各使用了一次 `customBorder()`，因此它们各自拥有自己的 Modifier Node。先记住这个直觉即可。第二阶段我们才专门利用日志研究它们在重组时到底怎么变化。

#### 2. 第一层：Modifier factory 是给“使用者”看的 API

先从最外面看：

```kotlin
fun Modifier.customBorder(
    color: Color,
    width: Dp,
    cornerRadius: Dp
): Modifier {
    return this then CustomBorderElement(
        color = color,
        width = width,
        cornerRadius = cornerRadius
    )
}
```

这其实很好理解，因为你以前已经学过 Modifier 链。假设原来有：

```kotlin
Modifier
    .padding(16.dp)
    .customBorder(...)
    .padding(8.dp)
```

调用：

```kotlin
this then CustomBorderElement(...)
```

本质上就是：把我们的 `CustomBorderElement` 接到当前 Modifier 链后面。因此 `customBorder()` 本身并不负责真正绘制。这一点非常重要。以后你看到一个现代自定义 Modifier：

```kotlin
fun Modifier.xxx(...): Modifier =
    this then XxxElement(...)
```

不要把这个函数想象成“Modifier 的实现”。它更像是**公开 API 的入口**。调用者面对的是：

```kotlin
Modifier.customBorder(...)
```

真正执行工作的对象藏在后面。官方文档也把这一层称为 modifier factory：它构成了自定义 Modifier 的公共 API surface，而典型实现就是创建 Element 并把它加入 Modifier 链。[Android Developers](https://developer.android.com/develop/ui/compose/custom-modifiers?hl=zh-cn)

#### 3. 第二层：`ModifierNodeElement` 是 Node 和 Modifier 链之间的桥梁

接着看：

```kotlin
private data class CustomBorderElement(
    val color: Color,
    val width: Dp,
    val cornerRadius: Dp
) : ModifierNodeElement<CustomBorderNode>()
```

第一次看到它很容易觉得多余：我不是已经知道颜色、宽度、圆角了吗？为什么不直接 new 一个 Node 塞进去？这是 6.5 最需要慢慢建立的心智模型之一。现在先只把 `Element` 理解成：**这条 Modifier 当前是什么配置。**例如：

```kotlin
.customBorder(
    color = Color.Red,
    width = 4.dp,
    cornerRadius = 16.dp
)
```

那么对应的 `CustomBorderElement` 描述的是：

```text
color = Red
width = 4dp
cornerRadius = 16dp
```

但 Element 自己并不画。真正的绘制工作在：

```kotlin
CustomBorderNode
```

所以 Element 还必须负责两件事：

```kotlin
override fun create(): CustomBorderNode
```

和：

```kotlin
override fun update(node: CustomBorderNode)
```

官方对 `ModifierNodeElement` 的定位正是：保存创建或更新自定义 Modifier 所需要的数据，并通过 `create()` 创建 Node，通过 `update()` 把新的参数同步给已经存在的 Node。[Android Developers](https://developer.android.com/develop/ui/compose/custom-modifiers?hl=zh-cn)

今天我们先把它简化成下面这条关系：

```text
customBorder(...)
        ↓
CustomBorderElement
        ↓
CustomBorderNode
```

也就是：

```text
公开 API
   ↓
参数 / 配置描述
   ↓
真正工作的节点
```

第二阶段再回答为什么 Compose 非得这么设计。

#### 4. 第三层：真正画东西的是 `CustomBorderNode`

终于来到核心：

```kotlin
private class CustomBorderNode(
    var color: Color,
    var width: Dp,
    var cornerRadius: Dp
) : Modifier.Node(), DrawModifierNode
```

这里同时出现了两个东西：

```kotlin
Modifier.Node()
```

和：

```kotlin
DrawModifierNode
```

可以暂时这样理解。`Modifier.Node` 表示：**我是 Modifier 节点系统中的一个真正节点。**但是仅仅成为 Node，并没有说明这个 Node 能干什么。

Compose 的 Node 可以承担不同能力，比如绘制、布局、Pointer Input、Semantics 等。官方当前 API 就是通过不同的 Node capability interface 来表达这些能力；绘制对应的是 `DrawModifierNode`，布局则是 `LayoutModifierNode`。[Android Developers ](https://developer.android.com/develop/ui/compose/custom-modifiers?hl=zh-cn) 因此：

```kotlin
Modifier.Node(), DrawModifierNode
```

可以读成人话：我是一个 Modifier Node，而且我是一个负责参与绘制阶段的 Node。因为实现了：

```kotlin
DrawModifierNode
```

我们必须提供：

```kotlin
override fun ContentDrawScope.draw()
```

真正的绘制就在这里发生。

#### 5. `ContentDrawScope`：你其实已经认识它了

看这里：

```kotlin
override fun ContentDrawScope.draw() {
```

这一行看起来很“底层”，实际上你在 6.3 已经和它打过很久交道了。你之前写过：

```kotlin
Modifier.drawWithContent {
    drawRect(...)
    drawContent()
}
```

现在写：

```kotlin
override fun ContentDrawScope.draw() {
    drawRect(...)
    drawContent()
}
```

有没有发现内部世界几乎一样？因为两者都给你的是 **`ContentDrawScope`**。所以你之前掌握的：

```kotlin
size
center
drawRect()
drawCircle()
drawLine()
drawPath()
translate()
rotate()
scale()
clipPath()
drawContent()
```

这些知识完全没有作废。这也是为什么 6.5 安排在 6.2、6.3 后面。如果一上来直接讲 `DrawModifierNode`，你会同时面对 Modifier Node 系统和绘图 API，两套陌生机制会绞在一起。现在不一样。你看：

```kotlin
override fun ContentDrawScope.draw() {
    drawContent()
    drawRoundRect(...)
}
```

真正新的部分只有外壳：

```text
以前：
drawWithContent {
    ...
}

现在：
DrawModifierNode {
    override fun ContentDrawScope.draw() {
        ...
    }
}
```

**绘制本身仍然是你已经学过的那套 DrawScope 世界。**官方也明确将 `DrawModifierNode` 对应到 `ContentDrawScope`，即一个能够在布局空间中执行绘制的 Modifier Node。[Android Developers](https://developer.android.com/develop/ui/compose/custom-modifiers?hl=zh-cn)

#### 6. 为什么这里调用 `drawContent()`？

我们的代码是：

```kotlin
override fun ContentDrawScope.draw() {
    drawContent()
    drawRoundRect(...)
}
```

这个现象你在 6.3 已经验证过，所以这里只唤醒，不重讲。顺序是：

```text
drawContent()
↓
原来的 Text / Box 内容
↓
drawRoundRect()
↓
我们的边框
```

因此边框画在内容之后。如果改成：

```kotlin
override fun ContentDrawScope.draw() {
    drawRoundRect(...)
    drawContent()
}
```

就是先画边框，再继续绘制后面的内容。如果彻底删掉：

```kotlin
drawContent()
```

那么这个绘制 Modifier 就不会继续绘制它所包裹的内容。这和你学 `drawWithContent` 时的规则完全一致。官方在涉及 `DrawModifierNode` 的示例中同样指出，`drawContent()` 用于绘制 Modifier 所作用的实际内容。[Android Developers](https://developer.android.com/develop/ui/compose/touch-input/user-interactions/handling-interactions?authuser=19&utm_source=chatgpt.com) 所以不要把：

```kotlin
ContentDrawScope.draw()
```

理解成一套新的绘图系统。它只是把你已经熟悉的绘制能力，放进了一个真正的 Modifier Node 里。

#### 7. 边框代码为什么要缩进去半个 Stroke

这里有一段：

```kotlin
val strokeWidth = width.toPx()
val halfStrokeWidth = strokeWidth / 2f
```

然后：

```kotlin
topLeft = Offset(
    halfStrokeWidth,
    halfStrokeWidth
)
```

以及：

```kotlin
size = Size(
    size.width - strokeWidth,
    size.height - strokeWidth
)
```

这是纯绘图知识，不是 Modifier Node 的特殊机制。假设组件宽度是：

```text
200px
```

Stroke 宽度：

```text
10px
```

如果你直接沿着组件最外围：

```text
x = 0
```

画一条 10px 的描边，那么 Stroke 的中心落在边界线上：

```text
5px 在组件内部
5px 在组件外部
```

为了让整条边框留在当前绘制区域内，我们把路径向内缩：

```text
strokeWidth / 2
```

所以最终有效矩形是：

```text
left   = 5
top    = 5
right  = width  - 5
bottom = height - 5
```

这就是代码里：

```kotlin
topLeft = halfStrokeWidth
size = 原始 size - strokeWidth
```

的原因。这个逻辑和 Node 本身没有任何关系。换成 `Canvas` 或 `drawWithContent`，你也一样会这样处理。

#### 8. Modifier Node 并没有获得一个自己的尺寸

注意：

```kotlin
override fun ContentDrawScope.draw() {
    Log.d(TAG, "Node.draw() size=$size")
}
```

这里的：

```kotlin
size
```

仍然是**当前这条绘制 Modifier 所处绘制空间的尺寸**。例如：

```kotlin
Box(
    Modifier
        .size(220.dp, 120.dp)
        .customBorder(...)
)
```

那么 Node 并没有偷偷创建一个新的 220 × 120 View，也没有拥有自己的布局。它只是进入这个组件对应的绘制阶段，然后拿到：

```kotlin
ContentDrawScope
```

在这个空间里画东西。所以目前一定不要把 `Modifier.Node` 理解成：Compose 版本的 View。这会非常容易走偏。它更接近：**挂在 Modifier 链上的、能够参与某一种或多种阶段工作的长期节点对象。**我们这一节的 Node：

```kotlin
CustomBorderNode
```

恰好实现了：

```kotlin
DrawModifierNode
```

因此它参与的是 **Draw**。至于 Node 如果实现：

```kotlin
LayoutModifierNode
```

会怎样参与 Measure / Layout，那正是第 7 章的事情，不应该在这里提前展开。

#### 9. 把整个第一次调用过程串起来

现在来看：

```kotlin
Modifier
    .customBorder(
        color = Color.Red,
        width = 4.dp,
        cornerRadius = 16.dp
    )
```

第一次建立这条 Modifier 时，可以先形成这样一张简化模型：

```text
Modifier.customBorder(...)
        │
        │ 创建配置描述
        ▼
CustomBorderElement
        │
        │ create()
        ▼
CustomBorderNode
        │
        │ 具备 DrawModifierNode 能力
        ▼
ContentDrawScope.draw()
        │
        ├── drawContent()
        │
        └── drawRoundRect(...)
```

其中三层各自对应：

```text
Modifier factory
    ↓
给调用者使用

ModifierNodeElement
    ↓
描述参数，并负责 Node 的创建 / 更新

Modifier.Node + DrawModifierNode
    ↓
真正参与绘制阶段
```

今天你首先需要真正记住的就是这条链。

#### 10. 这和自己写一个 Composable 有什么本质区别？

这是一个很值得现在建立的边界。假如需求只是：做一个带边框的卡片。当然可以写：

```kotlin
@Composable
fun BorderCard(...) {
    Box(...) {
        ...
    }
}
```

完全没问题。但是如果需求是：给任何组件增加一种通用绘制能力。那么 Modifier 的抽象更自然。例如：

```kotlin
Text(..., Modifier.customBorder(...))

Image(..., Modifier.customBorder(...))

Box(..., Modifier.customBorder(...))

Row(..., Modifier.customBorder(...))
```

这时候我们封装的不是一个“UI 组件”，而是一种：**附加到任意 UI 节点上的行为。**这就是自定义 Modifier 真正有价值的地方。以后像：

```text
日历某一天的选中描边
时间轴上的状态标记
金额变化的强调边框
调试布局边界
特殊遮罩
自定义 loading 绘制
可复用的装饰效果
```

都可能非常适合做成 Modifier，而不值得专门造一个新的 Composable 容器。

#### 11. 为什么今天直接学 `DrawModifierNode`，而不是旧 `DrawModifier`

这里稍微定位一下，但不展开兄弟 API。你可能在旧教程或者网上看到：

```kotlin
class XxxModifier : DrawModifier
```

而且当前 Android Graphics 文档里仍然保留了直接实现 `DrawModifier` 的自定义绘制示例。[Android Developers](https://developer.android.com/develop/ui/compose/graphics/draw/modifiers?hl=zh-cn&utm_source=chatgpt.com) 所以这不是“API 已经完全不能用了”。

但 Compose 当前专门的 Custom Modifiers 文档明确指出，`Modifier.Node` 是 Compose 自身实现 Modifier 所使用的较低级 API，并称其为创建自定义 Modifier 的最有效方式。[Android Developers](https://developer.android.com/develop/ui/compose/custom-modifiers?hl=zh-cn) 因此我们这一节的主线选：

```text
ModifierNodeElement
+
Modifier.Node
+
DrawModifierNode
```

而不是花时间先学一套旧结构，再切换到 Node。第五阶段我们再专门把：

```text
Canvas
drawBehind
drawWithContent
drawWithCache
DrawModifier
DrawModifierNode
```

放在一起确定选择边界。现在没必要把自己淹死在 API 对比里。

#### 12. 第一阶段真正需要掌握到什么程度

这一阶段敲完 `Sec05A_CustomBorderModifier.kt` 后，你不需要背 `ModifierNodeElement` 的生命周期，也不需要理解为什么 `Element` 每次重组可能产生新实例，而 Node 却可以保留。那些正是下一阶段。现在只需要能不看答案解释下面这段结构：

```kotlin
fun Modifier.customBorder(...): Modifier =
    this then CustomBorderElement(...)

private data class CustomBorderElement(...)
    : ModifierNodeElement<CustomBorderNode>() {

    override fun create() = CustomBorderNode(...)
        
    override fun update(node: CustomBorderNode) {
        ...
    }
}

private class CustomBorderNode(...)
    : Modifier.Node(), DrawModifierNode {

    override fun ContentDrawScope.draw() {
        drawContent()
        drawRoundRect(...)
    }
}
```

你应该能够说出：

**第一，`customBorder()` 是公开给调用者使用的 Modifier factory，它把我们的 Element 加进 Modifier 链。**

**第二，`CustomBorderElement` 携带这次 Modifier 的参数，并负责创建和更新真正工作的 Node。**

**第三，`CustomBorderNode` 才是真正挂进 Modifier Node 系统并参与运行的对象。**

**第四，实现 `DrawModifierNode`，意味着这个 Node 获得参与绘制阶段的能力，因此需要实现 `ContentDrawScope.draw()`。**

**第五，进入 `draw()` 后，真正的绘图 API 和前面学过的 `drawWithContent` 基本是同一个世界；`drawContent()` 的含义和绘制顺序也没有改变。**

到这里，6.5 最陌生的外壳已经第一次完整跑起来了。

下一阶段才是这一节真正开始变得有意思的地方：**既然每次重组代码都会重新执行 `Modifier.customBorder(...)`，为什么已经创建出来的 `CustomBorderNode` 不必跟着不断销毁重建？`Element` 和 `Node` 为什么必须拆开？`create()`、`update()` 与 `data class` 到底是怎么配合的？** 这几个问题会把今天看到的三层结构真正串成运行模型。

#### Issue 1: 红色背景露出蓝色边框之外

你发现的红色背景露出蓝色边框之外：不是错觉，第一阶段的边框算法确实有一个几何问题
你两张 Light / Dark 截图里这个现象非常明显，尤其四个圆角附近：

```
红色 background
        ↘
      红色细边露出
     ╭────────
    ╱ 蓝色 Border
```

你代码里两边都写了：

```
RoundedCornerShape(20.dp)
```

以及：

```
cornerRadius = 20.dp
```

直觉上确实应该完全重合。问题出在我们为了防止 `Stroke` 被裁掉，已经把边框的**中心线矩形**向里面缩了半个 Stroke：

```
val halfStrokeWidth = strokeWidth / 2f

topLeft = Offset(
    halfStrokeWidth,
    halfStrokeWidth
)

size = Size(
    size.width - strokeWidth,
    size.height - strokeWidth
)
```

这一步本身是正确的。但是随后我们仍然写了：

```
val radius = cornerRadius.toPx()
```

也就是说：矩形往里缩了半个 Stroke，但是圆角中心线半径仍然保持原来的 20.dp。
假设 Stroke 是 `6.dp`。那么边框中心线是：

```
距离外边缘 3dp
```

但是我们又给中心线用了：

```
20dp radius
```

于是 Stroke 的**外侧圆角半径**实际上变成大约：

```
20dp + 3dp = 23dp
```

而红色 `background` 的外轮廓仍然是：

```
20dp
```

23dp 的圆角比 20dp **更圆、更往里收**，所以在圆角斜着的那一小段：

```
蓝色边框向内缩得更多
红色 background 就从外侧露出来了
```

你截图看到的正是这个东西。这个不是 Dark Mode、抗锯齿或者 Preview 的错。

**是我们第一阶段那段演示代码的圆角几何没有完全对齐。**

------

**修正只需要改圆角半径**

如果 `cornerRadius` 表示的是我们希望最终看到的**外轮廓半径**，那么中心线的半径应该同样往里缩半个 Stroke：

```kotlin
val strokeWidth = width.toPx()
val halfStrokeWidth = strokeWidth / 2f

val borderRadius = (
    cornerRadius.toPx() - halfStrokeWidth
).coerceAtLeast(0f)

drawRoundRect(
    color = color,
    topLeft = Offset(
        x = halfStrokeWidth,
        y = halfStrokeWidth
    ),
    size = Size(
        width = (size.width - strokeWidth).coerceAtLeast(0f),
        height = (size.height - strokeWidth).coerceAtLeast(0f)
    ),
    cornerRadius = CornerRadius(
        x = borderRadius,
        y = borderRadius
    ),
    style = Stroke(width = strokeWidth)
)
```

于是以你的 `6.dp` 边框、`20.dp` 外圆角为例：

```txt
Background 外轮廓：
radius = 20dp

Border：
中心线距离外轮廓 = 3dp
中心线 radius = 20 - 3 = 17dp
Stroke 外缘 radius = 17 + 3 = 20dp
```

这样两者的**外轮廓几何才真正一致**。你现在重新跑一下，四个角那条明显的红色露边应该基本消失。最终仍可能有极细的像素级抗锯齿混色，但不会是截图里这种清楚可辨的几何错位。

这个 Case 其实挺值钱的，因为它再次验证了 6.2 学过的事实：`Stroke` 是沿路径中心线向两边各扩展一半宽度，而不是单纯向内部画。

### 第二阶段：Element 与 Node 到底各自负责什么

这一阶段正式拆开第一阶段看到的那套“固定写法”。我们仍然不进入第 7.9 的 Modifier 嵌套关系，也不展开第 11.2 的 Node 链 diff 算法；这一阶段只解决四个核心问题：为什么已经有了 `ModifierNodeElement` 还需要 `Modifier.Node`，重组以后谁是新的谁是旧的，`create()` / `update(node)` 分别什么时候发生，以及新的 Modifier 参数最终怎样进入已经存在的 Node。这个主线保持和原第二阶段一致。

这一节的难点不在绘制。`drawRoundRect()`、`drawContent()`、`ContentDrawScope` 都已经认识了。真正需要建立的是 **Composition 中不断生成的 Modifier 描述** 与 **真正长期挂在 UI 上工作的运行时 Node** 之间的关系。

#### 3. Element 和 Node 并不是“两层重复代码”

第一阶段最容易产生的疑问就是：

```
elementNodeBorder(...)
        ↓
ElementNodeBorderElement
        ↓
ElementNodeBorderNode
```

为什么传来传去三遍 `color / width / cornerRadius`？为什么不能直接创建 Node？答案要从 Compose 的声明式模型看。你的：

```
ElementNodeBorderElement(
    color = ...,
    width = ...,
    cornerRadius = ...
)
```

代表的是：**这一轮 Composition 所描述出来的 Modifier 配置。**它是一份不可变描述：

```
这一轮我希望：
color = 蓝色
width = 6.dp
cornerRadius = 20.dp
```

而：

```
ElementNodeBorderNode
```

不是“另一份配置”。它是：**Compose 真正挂到 UI 运行时结构里、负责长期执行绘制工作的对象。**

官方文档对此区分得很明确：`ModifierNodeElement` 保存创建或更新 Modifier Node 所需要的数据，而 `Modifier.Node` 保存真正的 Modifier 逻辑和状态；Element 会随着重组重新产生，而 Node 可以跨越多次重组继续存在并被复用。[Android Developers](https://developer.android.com/develop/ui/compose/custom-modifiers?hl=en&utm_source=chatgpt.com)

所以第一条核心模型是：

```
Composition 世界                    UI 运行时世界

新的 UI 描述
     ↓
ModifierNodeElement   ───────────→   Modifier.Node
短命、不可变                         长期存在、真正工作
```

“短命”不是说 Element 创建完立刻销毁，而是说它不是需要长期维持身份和运行状态的那个对象；后续重组完全可以产生另一份新的 Element。

#### 4. 为什么重组以后 Element 会重新出现

现在点击：

```
只触发重组
```

`recomposeCount++` 以后，传给 `ElementNodeTarget()` 的参数发生变化，于是这一 Composable 重新执行。重新执行意味着这一句也重新执行：

```
.elementNodeBorder(
    color = borderColor,
    width = 6.dp,
    cornerRadius = 20.dp
)
```

而 `elementNodeBorder()` 里面明确写了：

```
val element = ElementNodeBorderElement(...)
```

所以这一轮当然会得到**一个新的 Kotlin Element 对象**。例如第一次可能是：

```
Element@227225866
```

点击按钮后可能变成：

```
Element@98123456
```

这两个对象：

```
旧 Element === 新 Element
false
```

因为它们根本不是同一个实例。这正是声明式 UI 很自然的结果：

```
状态变化
→ Composable 重新执行
→ 重新描述 UI
→ 重新描述 Modifier
→ 产生这一轮新的 Element
```

重点来了：**重新产生 Element，并不意味着重新创建 Node。**这两个概念一定要从这里彻底拆开。

------

#### 5. “只触发重组”为什么既没有 `create()`，也没有 `update()`

虽然这一轮产生了新的 `ElementNodeBorderElement` 对象，但边框参数并没有变化：

```
旧 Element：
color = 蓝色
width = 6.dp
cornerRadius = 20.dp

新 Element：
color = 蓝色
width = 6.dp
cornerRadius = 20.dp
```

而我们故意把 Element 写成：

```
private data class ElementNodeBorderElement(...)
```

`data class` 自动根据属性实现结构相等。所以这里：

```
旧 Element === 新 Element
false

旧 Element == 新 Element
true
```

第一句问的是：是不是同一个对象？不是。第二句问的是：两份 Element 描述的内容是否相等？相等。因此 Compose 看见的不是：“来了一个陌生 Modifier”。而是：“这一轮虽然重新产生了一份 Element，但它描述的东西和上一轮完全一样”。于是原来的：

```
Node@175758610
```

根本没有必要碰。既不需要：

```
create()
```

也不需要：

```
update(node)
```

Node 直接继续使用。AndroidX 当前的 Node 链实现正是按这个原则处理：新旧 Element `equals` 相等时直接 **Reuse**，Node 不执行 update。[Android Source](https://android.googlesource.com/platform/frameworks/support.git/%2B/f5330c315a8191bad8c9281a01dfad78d81c081b/compose/ui/ui/src/commonMain/kotlin/androidx/compose/ui/node/NodeChain.kt?utm_source=chatgpt.com) 所以点击“只触发重组”以后，你应该重点检查：

```
有：创建新的 Element@新的ID
有：Composition 完成：count=1 ...

没有：Element.create()
没有：Element.update()
```

这组日志比第一次启动时的日志更重要。

#### 6. 这第一次把“重组”与“运行时对象重建”分开了

以前我们学 State 时，心智模型主要到这里为止：

```
State 改变
    ↓
读取 State 的 Composition Scope 失效
    ↓
Recomposition
    ↓
Composable 再执行
```

这一套没有错。但现在第一次往后多走了一层：

```
Composable 再执行
    ↓
新的 Modifier 描述被计算出来
    ↓
新的 Element 对象
```

**到这里仍然不代表 Node 被重建。**因此以后不要把 Compose 的“重组”理解为传统意义上的：

```
把旧 UI 对象拆了
→ 创建一套新 UI 对象
```

在这个 Case 中尤其明显：

```
Composition：
确实重新执行了

Element：
确实 new 了一个

Node：
Node@175758610 原封不动活着
```

这就是声明式 UI 的“重新描述”和运行时结构的“尽量复用”同时成立。

#### 7. 第二个实验：改变 Border 参数以后，为什么出现 `update(node)`

现在点击：

```
改变 Border 参数
```

假设：

```
蓝色 → 绿色
```

这一次同样会发生重组，同样会再次调用 `elementNodeBorder()`，同样会产生新的 `ElementNodeBorderElement`。但这一次不同：

```
旧 Element：
color = 蓝色
width = 6.dp
cornerRadius = 20.dp

新 Element：
color = 绿色
width = 6.dp
cornerRadius = 20.dp
```

因此：

```
旧 Element == 新 Element
false
```

可是它们仍然是**同一种 Element 类型**：

```
ElementNodeBorderElement
```

Compose 此时没有必要扔掉 Node，因为这个 Modifier 的“种类”没有发生结构性变化，只是配置变了。于是这一次走：

```

```

而不是再次走：

```
create()
```

```
创建新的 Element@新的ElementID, color=Color(绿色...)

Element.update() -> Node@175758610,
color: Color(蓝色...) -> Color(绿色...)

Composition 完成：count=0, color=Color(绿色...)

Node.draw() -> Node@175758610,
color=Color(绿色...)
```

这里不要执着于每一条日志之间的绝对调度顺序；真正需要核对的是**对象身份和事件关系**。最关键的一组数字是：

```
第一次：
Element.create() -> Node@175758610

参数改变：
Element.update() -> Node@175758610

随后：
Node.draw() -> Node@175758610
```

三个地方是同一个 Node ID。**Node 根本没有重建。**

#### 8. 现在正式回答第一阶段的 TODO：`update(node)` 里的 `node` 是谁

第一阶段那个最陌生的函数：

```
override fun update(node: ElementNodeBorderNode) {
    node.color = color
    node.width = width
    node.cornerRadius = cornerRadius
}
```

现在就可以完全解释了。这里的：

```
node
```

~~不是新 Element 创建出来的某个临时参数，也不是 Compose 要你“顺便操作一下”的东西。它~~就是：**此前已经通过 `create()` 创建出来，并且目前仍然挂在 UI 上工作的那个旧 Node。**具体到你的实验：

```
第一次：
create()
    ↓
Node@175758610
color = 蓝色
```

随后 Composition 得到了新的 Element：

```
新 Element
color = 绿色
```

Compose 决定：

```
Element 类型没换
→ Node 可以继续用
```

所以调用：

```
newElement.update(Node@175758610)
```

于是你写的：

```
node.color = color
```

真正发生的是：

```
Node@175758610.color

蓝色
 ↓
绿色
```

因此现在可以给 `update()` 一个非常准确的定义：**把这一轮 Element 中最新的声明式配置，同步进已经存在的运行时 Node。**这句话基本就是 `update()` 的核心。

官方文档也明确规定：当相同位置上的 Modifier 属性变化时，之前创建出来的 Node 会作为参数传给 `update()`，实现者应该更新这个已有 Node，而不是创建一个新的 Node。[Android Developers](https://developer.android.com/develop/ui/compose/custom-modifiers?hl=en&utm_source=chatgpt.com)

#### 9. 为什么 `Element` 是 `val`，而 `Node` 是 `var`

现在回头看两者的属性，会发现这个设计其实非常漂亮。

Element：

```
val color
val width
val cornerRadius
```

Node：

```
var color
var width
var cornerRadius
```

Element 代表的是：**这一轮 Composition 算出来的一份配置快照。**这一份产生以后不需要再修改：

```
Element A
蓝色 / 6dp / 20dp
```

下一轮状态变了，不去修改 Element A，而是产生：

```
Element B
绿色 / 6dp / 20dp
```

所以它天然适合不可变。Node 则相反：

```
Node@175758610

第一次：
color = 蓝色

update 后：
color = 绿色

以后可能：
width = 10dp
```

Node 的价值恰恰就在于**身份可以保留，但内部运行状态能够跟着新的描述更新**。因此可以把二者概括成：

```
ModifierNodeElement
= immutable description
= 这一轮“应该是什么”

Modifier.Node
= reusable runtime object
= 真正“正在工作”的对象
```

这组对照比死记 `create()` / `update()` 更重要。

#### 10. `data class` 在这里不是语法糖，而直接影响 update 是否发生

第一阶段看到：

```
private data class ElementNodeBorderElement(...)
```

很容易认为只是为了少写：

```
equals
hashCode
toString
```

但这里 `equals()` 直接参与 Node 的更新判断。

官方对 `ModifierNodeElement` 有一个明确要求：必须正确实现 `equals()` 和 `hashCode()`；如果错误地依赖对象身份，那么新的 Element 即使参数完全相同，也可能导致没有意义的 Node update。官方也直接推荐用 `data class` 自动得到正确的结构相等实现。[Android Developers](https://developer.android.com/develop/ui/compose/custom-modifiers?hl=en&utm_source=chatgpt.com)

我们这个 Case 正好能说明。如果是：

```
旧：
Element(Blue, 6dp, 20dp)

新：
Element(Blue, 6dp, 20dp)
```

正确结果应该是：

```
equals == true
→ REUSE
→ 不 update
```

如果每次都只按对象身份判断：

```
Element@1 != Element@2
```

Compose 就会误以为配置改变了。因此：

```
data class ElementNodeBorderElement(...)
```

不是随便写出来的模板。它直接服务于：**新旧 Modifier 描述到底有没有真正发生变化。**

------

#### 11. 当前只需要知道 Node 有三种处理结果

这里值得非常克制地看一眼底层结论，但不进入第 11 章的 NodeChain diff 算法。AndroidX 当前源码把新旧 Modifier Element 的关系归纳成三个结果：

```
1. Element 相等
   ↓
   REUSE

   Node 继续使用
   不调用 update()


2. Element 不相等，但类型相同
   ↓
   UPDATE

   Node 继续使用
   调用 update(existingNode)


3. Element 类型不同
   ↓
   REPLACE

   原 Node 无法按同一种 Modifier 继续复用
```

这不是为了让你现在学习 `NodeChain` 源码，而是它正好证明了我们刚才通过日志看到的行为。当前 AndroidX 源码中的 `actionForModifiers()` 就是按“相等 → reuse；同类型 → update；否则 replace”来决定处理方式。[Android Source ](https://android.googlesource.com/platform/frameworks/support.git/%2B/f5330c315a8191bad8c9281a01dfad78d81c081b/compose/ui/ui/src/commonMain/kotlin/androidx/compose/ui/node/NodeChain.kt?utm_source=chatgpt.com) 对应到我们的两个按钮：

```
“只触发重组”
→ Element 对象不同
→ 但 data class equals == true
→ REUSE


“改变 Border 参数”
→ equals == false
→ Element 类型仍是 ElementNodeBorderElement
→ UPDATE
```

第三种 `REPLACE` 现在不用实验。Modifier 链里插入、删除、换类型以后 Compose 如何定位和匹配 Node，留给第 11.2。

#### 12. “同一个位置”现在理解到应用层即可

官方在描述 `update()` 时有一个条件：同一位置已经存在对应 Node，但 Modifier 属性发生变化。[Android Developers](https://developer.android.com/develop/ui/compose/custom-modifiers?hl=en&utm_source=chatgpt.com) 这里的“位置”现在不要和 Composition 的 slot、`key()`、Lazy list key 混在一起。目前只需要看你的 Modifier 链：


下一轮重组以后，结构仍然大致是：


因此 Compose 能够把上一轮这里的 Element 和这一轮这里的 Element 对应起来，然后判断：

```

同类型？
还是完全不同？
```

至于链条顺序改变、Modifier 数量改变以后到底怎样匹配，这就是第 11 章，不在 6.5 提前拆。

#### 14. 重组和重绘到这里必须分开

这个实验还有一个非常重要的副产品。

点击：

```

```

```
Recomposition
→ 新 Element
→ equals == true
→ Node REUSE
```

对于我们的 Border Node 来说，没有 Modifier 参数变化，所以没有 `update()`，也就没有因为这次 Node 更新而产生新的 Draw invalidation。而点击：

```

```

```
Recomposition
→ 新 Element
→ equals == false
→ update(Node)
→ Draw invalidation
→ draw()
```

所以：

```
Recomposition
≠ Draw
```

它们不是一个概念。Compose 的阶段模型本来就是：

```
Composition
Layout
Drawing
```

`DrawModifierNode` 映射到 Drawing 阶段，而不是 Composition 本身。[Android Developers](https://developer.android.com/develop/ui/compose/performance/modifier-phases?utm_source=chatgpt.com) 因此不能建立：

```
“只要发生重组，就一定重新执行这个 Draw Node”
```

这样的错误模型。反过来，以后也会看到：

```
Draw 重新执行
```

并不一定要求：

```
Composable 先重组一次
```

这一点下一阶段会成为重点。

#### 15. 为什么 Compose 非要设计成 Element + Node 两层

现在终于可以回答这节课最大的“为什么”。Compose 是声明式 UI。状态变化之后，它希望允许开发者自然地重新写：

```
“现在我的 Border 应该是什么样”
```

所以重组时重新产生一份：

```
Element
```

非常合理。但如果每次重新描述 UI 都意味着：

```
销毁 Node
创建 Node
销毁 Node
创建 Node
```

那运行时成本就没有必要地变高，而且 Node 自己也很难长期保存状态、协程或其他运行时资源。于是 Compose 把这两件事情拆开：

```
声明式描述层

ModifierNodeElement
“这一轮应该是什么”
        │
        │ compare / update
        ▼
运行时执行层

Modifier.Node
“这个真正工作的对象继续活着”
```

所以每次新描述来了以后，Compose 可以做三件很便宜的事：

```
完全没变
→ Node 原样复用

只是参数改变
→ update 原 Node

Modifier 类型真的变了
→ 才替换 Node
```

这就同时满足了两件看似矛盾的需求：

```
声明式：
我可以不断重新描述 UI

运行时：
我不需要不断重建真正工作的对象
```

这就是 `ModifierNodeElement + Modifier.Node` 这套设计最值得理解的地方。

#### 16. 再回头看第一阶段的“固定写法”

现在那三个部分已经不应该再被看作模板。

第一层：

```

```

它负责：根据这一轮参数产生 Modifier 描述，并把 Element 接入 Modifier 链。第二层：

```

```

它负责：携带这一轮不可变配置，并知道第一次怎样 `create()` Node，以及以后怎样把新配置 `update()` 到已有 Node。第三层：

```

```

它负责：作为长期存在的运行时对象真正执行 Modifier 行为；因为它实现 `DrawModifierNode`，所以它的能力是参与 Drawing。于是：


现在可以翻译成：**这里还没有可以工作的这个 Node，请第一次建立它。**而：


可以翻译成：**这里已经有一个能够继续复用的 Node，请把新一轮 Element 描述同步进去。**

第一阶段那套代码到这里就不再是“照着写才能写出来”的固定格式了，而是能够从职责一步步推出来的结构。

#### Addition 1


对，这个 TODO 的答案是：**Node 仍然会保留，但严格来说这次不是 `REUSE`，而是 `UPDATE`。**假设：

```kotlin
data class Element(
    val color: Color,      // Node 使用
    val debugTag: String   // Node 完全不用
```

```tex
↓
```

```tex

= equals == true
= 同一个 Node
= 不调用 update()

UPDATE
= equals == false，但 Element 类型相同
= 仍然是同一个 Node
= 调用 update(node)
```

#### 1. Invalidation 到底是什么意思

先把“失效”这个词解释准确。假设 `ElementNodeBorderNode` 已经完成一次绘制：

```text
Node.color = Blue
        ↓
draw()
        ↓
屏幕得到蓝色 Border
```

后来我们执行：

```kotlin
node.color = Color.Green
```

这句代码只改变了内存中的属性：

```text
Node.color

Blue → Green
```

**它本身不等于重新绘制。**Compose 还需要知道：上一次 Drawing 阶段产生的结果已经不能继续用了，这个 Node 的绘制需要重新执行。这件事情就是 **Draw invalidation**。因此更准确的过程是：

```text
修改 Node 中影响绘制的数据
        ↓
使 Draw 阶段失效
        ↓
Compose 在后续绘制过程中重新调用 draw()
        ↓
draw() 读取新的 Node 数据
        ↓
产生新的像素
```

所以 invalidation 不表示 Node 被销毁、不可用了或者“对象失效”。它表示：**这个阶段之前算出来的结果过期了，需要重新执行。**而且 `invalidateDraw()` 的含义也不是“现在立刻同步执行一次 `draw()`”，它是告诉 Compose 这个 Draw Node 已经脏了，需要安排重新绘制。

------

#### 2. `Sec05B` 中是谁帮我们触发了 Draw invalidation

上一阶段改变 Border 颜色时，我们只写了：

```kotlin
override fun update(node: ElementNodeBorderNode) {
    node.color = color
    node.width = width
    node.cornerRadius = cornerRadius
}
```

这里完全没有：

```kotlin
invalidateDraw()
```

但后面 `draw()` 仍然执行了。原因是 `Modifier.Node` 默认启用了 **自动 invalidation**。当对应的 `ModifierNodeElement.update()` 被调用以后，Compose 会自动使这个 Node 所参与的阶段失效。我们的 Node 实现了 `DrawModifierNode`，所以会触发重新绘制。[Android Developers](https://developer.android.com/develop/ui/compose/custom-modifiers?hl=en&utm_source=chatgpt.com) 因此上一阶段完整的真实流程应该补成：

```text
新 Element 与旧 Element 不相等
        ↓
update(existing Node)
        ↓
node.color = 新颜色
        ↓
Modifier.Node 默认自动 invalidation
        ↓
Draw 阶段失效
        ↓
draw()
        ↓
读取新的 node.color
```

这也是为什么第一阶段那种最普通的实现：

```kotlin
override fun update(node: XxxNode) {
    node.color = color
}
```

已经足够工作。对于一个**只有 Draw 能力，而且 Element 中所有参数都会影响绘制**的简单 Node，这通常就是最合适的写法，不需要自己控制 invalidation。问题出现在更复杂的 Node 上。

#### 3. 一个很关键的反例：Element 变了，但 Draw 根本没变

还记得你上一阶段 `Sec05B_ElementNodeUpdate.kt` 中留下的那个 TODO：如果 Element 中某个参数变化了，但这个参数根本不影响 Node 的绘制呢？默认行为下：

```text
Element 参数发生变化
        ↓
equals == false
        ↓
update(node)
        ↓
自动 invalidation
        ↓
Draw 再执行
```

即使变化的参数对绘图毫无影响，也会因为 `update()` 发生而触发自动 invalidation。这正是 `shouldAutoInvalidate` 和 `invalidateDraw()` 存在的原因。这次新建独立实验文件：

```text

→ update()
→ 确实需要重新绘制

只改变 debugVersion
→ update()
→ 但 Border 完全没有变化
→ 不应该重新绘制
```

```kotlin
private fun Modifier.controlledBorder(
    color: Color,
    width: Dp,
    cornerRadius: Dp,
    debugVersion: Int
): Modifier {
    return this then ControlledBorderElement(
        color = color,
        width = width,
        cornerRadius = cornerRadius,
        debugVersion = debugVersion
    )
}

private data class ControlledBorderElement(
    val color: Color,
    val width: Dp,
    val cornerRadius: Dp,
    val debugVersion: Int
) : ModifierNodeElement<ControlledBorderNode>() {

    override fun create(): ControlledBorderNode {
        val node = ControlledBorderNode(
            color = color,
            width = width,
            cornerRadius = cornerRadius,
            debugVersion = debugVersion
        )

        log(
            Sec05C,
            "create() -> Node@${System.identityHashCode(node)}"
        )

        return node
    }

    override fun update(node: ControlledBorderNode) {
        log(
            Sec05C,
            "Element.update() -> " +
                "color=$color, debugVersion=$debugVersion"
        )

        node.update(
            color = color,
            width = width,
            cornerRadius = cornerRadius,
            debugVersion = debugVersion
        )
    }
}

private class ControlledBorderNode(
    var color: Color,
    var width: Dp,
    var cornerRadius: Dp,
    var debugVersion: Int
) : Modifier.Node(), DrawModifierNode {

    override val shouldAutoInvalidate: Boolean
        get() = false

    fun update(
        color: Color,
        width: Dp,
        cornerRadius: Dp,
        debugVersion: Int
    ) {
        val drawChanged =
            this.color != color ||
                this.width != width ||
                this.cornerRadius != cornerRadius

        this.color = color
        this.width = width
        this.cornerRadius = cornerRadius
        this.debugVersion = debugVersion

        if (drawChanged) {
            log(Sec05C, "影响绘制的参数改变 -> invalidateDraw()")
            invalidateDraw()
        } else {
            log(Sec05C, "只有非绘制参数改变 -> 不 invalidateDraw()")
        }
    }

    override fun ContentDrawScope.draw() {
        log(
            Sec05C,
            "Node.draw() -> " +
                "Node@${System.identityHashCode(this@ControlledBorderNode)}, " +
                "debugVersion=$debugVersion"
        )

        drawContent()

        val strokeWidth = width.toPx()
        val halfStrokeWidth = strokeWidth / 2f
        val radius = (
            cornerRadius.toPx() - halfStrokeWidth
        ).coerceAtLeast(0f)

        drawRoundRect(
            color = color,
            topLeft = Offset(
                x = halfStrokeWidth,
                y = halfStrokeWidth
            ),
            size = Size(
                width = (size.width - strokeWidth).coerceAtLeast(0f),
                height = (size.height - strokeWidth).coerceAtLeast(0f)
            ),
            cornerRadius = CornerRadius(
                x = radius,
                y = radius
            ),
            style = Stroke(width = strokeWidth)
        )
    }
}
```

#### 5. `shouldAutoInvalidate = false` 到底关闭了什么

默认：

```kotlin
shouldAutoInvalidate == true
```

因此只要：

```kotlin
ModifierNodeElement.update(node)
```

发生，Compose 就会根据这个 Node 具备的能力自动做相应 invalidation。现在我们明确关闭它：

```kotlin
override val shouldAutoInvalidate: Boolean
    get() = false
```

含义很单纯：**Element 调用了 `update()` 以后，不要替我自动决定哪些阶段需要重新执行，我自己负责。**注意它**不会阻止 `update()`**。例如只改变：

```kotlin

```

```text
Element equals == false
        ↓
UPDATE
        ↓
Element.update(node)
        ↓
node.update(...)
```

关闭的只是最后一步的**自动 phase invalidation**。官方提供 `shouldAutoInvalidate = false`，正是为了让复杂 Node 根据具体参数变化只使必要的阶段失效。[Android Developers](https://developer.android.com/develop/ui/compose/custom-modifiers?authuser=8&utm_source=chatgpt.com)

点击：

```text
改变 Border 颜色
```

`color` 是 Element 的构造参数，所以：

```text
旧 Element != 新 Element
        ↓
update(existing Node)
```

进入 Node 后：

```kotlin
val drawChanged =
    this.color != color ||
        this.width != width ||
        this.cornerRadius != cornerRadius
```

颜色改变，因此：

```text
drawChanged == true
```

接着：

```kotlin
invalidateDraw()
```

日志应该出现类似：

```text
Element.update() -> color=新颜色, debugVersion=0
影响绘制的参数改变 -> invalidateDraw()
Node.draw() -> Node@xxxx, debugVersion=0
```

这个流程与 `Sec05B` 最终效果完全一样：

```text
颜色变化
→ update Node
→ Draw invalidation
→ draw()
```

区别只是：

```text
Sec05B
自动 invalidation

Sec05C
我们自己判断
→ invalidateDraw()
```

所以 `invalidateDraw()` 才是 `update()` 与下一次 `draw()` 之间真正的桥梁；只不过普通 Node 默认由 Compose 帮你走了这一步。

------

#### 7. 第二次实验：只改变 `debugVersion`

现在点击：

```text
只改 debugVersion
```

`debugVersion` 也是 `ControlledBorderElement` 的构造参数，因此 `data class equals()` 会认为 Element 发生变化：

```text
旧：
debugVersion = 0
新：
debugVersion = 1
↓
equals == false
↓
update(existing Node)
```

所以你仍然会看到：

```text
Element.update()
```

这一点正好回答上一阶段的 TODO。但是进入 Node 后：

```kotlin
val drawChanged =
    this.color != color ||
        this.width != width ||
        this.cornerRadius != cornerRadius
```

三个真正影响绘制的参数都没变：

```text
drawChanged == false
```

因此：

```text
Element.update()
只有非绘制参数改变 -> 不 invalidateDraw()
```

随后**不应该因为这次 Node 更新而出现新的 `Node.draw()`**。这说明三个概念必须严格区分：

```text
Element 改变
≠ Node 必须替换

Node 被 update
≠ Draw 必须重新执行

Node 中影响 Draw 的数据改变
→ 才需要 Draw invalidation
```

如果这里保持默认的 `shouldAutoInvalidate = true`，`debugVersion` 改变虽然不影响 Border，`update()` 之后仍会自动触发 Node 的绘制失效。这就是手动 invalidation 能优化掉的工作。

------

#### 8. 那为什么默认还要自动 invalidation？

因为默认行为更安全。考虑第一阶段最普通的：

```kotlin
override fun update(node: BorderNode) {
    node.color = color
    node.width = width
    node.cornerRadius = cornerRadius
}
```

如果 Compose 要求所有开发者每次都另外写：

```kotlin
invalidateDraw()
```

很容易出现：

```text
Node.color 已经变了
但是忘记 invalidateDraw()
↓
内部数据是新的
屏幕却还是旧的
```

因此默认策略是：`update()` 发生了，我宁可替这个 Node 自动使相关阶段失效。只有当 Modifier 足够复杂，你明确知道哪些属性影响 Draw、哪些影响 Layout、哪些完全不需要刷新时，才值得：

```kotlin
shouldAutoInvalidate = false
```

然后精确控制。例如一个 Node 同时实现：

```kotlin
LayoutModifierNode
DrawModifierNode
```

如果只有：

```text
color
```

改变，只需要：

```kotlin
invalidateDraw()
```

如果只有影响尺寸的数据改变，则应该使 Layout 对应阶段失效，而不必无脑让所有能力一起工作。官方给出的手动 invalidation 使用场景正是这种多能力 Node。[Android Developers](https://developer.android.com/develop/ui/compose/custom-modifiers?authuser=8&utm_source=chatgpt.com)

所以对我们当前这个纯 `DrawModifierNode` 来说，**第一阶段那种默认自动 invalidation 才是日常首选**。`Sec05C` 的价值主要是让你理解机制，以及以后面对复杂 Node 时知道为什么存在手动控制。

------

#### 9. 现在把 Recomposition 和 Draw invalidation 分成两套东西

到这里可以把 Compose 中两种完全不同的“失效”正式分开。当 Composition 中读取的 State 改变：

```text
Composition Scope invalidated
        ↓
Recomposition
```

当 Drawing 阶段所依赖的数据改变：

```text
Draw invalidated
        ↓
重新执行 draw()
```

它们针对的是不同阶段。`Sec05B` 的路径比较绕：

```text
State
↓
Composition invalidation
↓
Recomposition
↓
new Element
↓
update Node
↓
Draw invalidation
↓
draw()
```

这就自然产生一个问题：如果一个状态仅仅影响绘制，为什么一定要先经过 Composition？答案是：**不一定。**

#### 11. 这个例子最关键的一行不是按钮，而是 `colorState.value`

看：

```kotlin
override fun ContentDrawScope.draw() {
    val color = colorState.value
```

`State<Color>` 对象本身是在 Composition 时传给 Node 的：

```
.stateBorder(
    colorState = borderColorState,
    ...
)
```

但是 Composition **没有读取**：

```
borderColorState.value
```

真正读取 `.value` 的位置是：

```
ContentDrawScope.draw()
```

Compose 会跟踪 Drawing Scope 中的 Snapshot State 读取。当 `draw()` 读取的 State 后来改变时，会直接使相应 Draw Scope 失效并重新执行绘制。[Android Developers](https://developer.android.com/develop/ui/compose/custom-modifiers?authuser=8&utm_source=chatgpt.com) 所以第一次运行：

```
Composition 完成
create() -> Node@123
Node.draw() -> Node@123, color=蓝色
```

然后点击：

```
改变 State
```

重点观察。理想情况下你会看到：

```
Node.draw() -> Node@123, color=绿色
```

但不会因为这次颜色变化看到：

```
Composition 完成
Element.update()
```

流程已经从 `Sec05B` 的：

```
State
→ Recomposition
→ Element
→ update
→ Draw
```

缩短成：

```
State
→ Draw invalidation
→ draw()
```

这就是**状态读取阶段决定哪个阶段需要重新执行**的实际表现。

#### 12. 为什么改变 State，却没有让 Composable 重组？

Compose 并不是看到任何 `MutableState` 改变就把整个 UI 重组。关键是：**谁读取了这个 State。**如果在 Composition 中：

```kotlin
val color = borderColorState.value
```

那么 Composition 建立了对它的观察，值变化后对应 Composition Scope 会失效。而我们的代码没有在 Composition 读取 `.value`。Composition 只持有：

```
borderColorState
```

这个 `State<Color>` 对象本身。真正的 `.value` 读取发生在：

```
ContentDrawScope.draw()
```

因此依赖关系建立在 Draw 阶段：

```
borderColorState.value
        ↑
     draw() 读取
```

值变化以后，Compose 知道需要重新工作的正是 Drawing，而不是 Composition。Compose 的阶段优化本身就是基于“状态在哪个阶段被读取”来限制重新执行范围；`DrawModifierNode` 对应 Drawing 阶段。[Android Developers ](https://developer.android.com/develop/ui/compose/performance/modifier-phases?utm_source=chatgpt.com) 这和你以前学 State 时的模型并不冲突，而是把那个模型补完整了。以前更常见的是：

```
State 在 Composition 被读取
→ 重组
```

现在增加：

```
State 在 Draw 被读取
→ 重绘
```

以后第 7 章还会看到 State 在 Layout 阶段读取时的相应行为。

------

#### 13. `Element.update()` 和 Draw 中读取 State，是两条完全不同的更新路径

现在可以把 6.5 到目前为止最重要的两条路径并排看。普通值作为 Modifier 参数：

```
.myBorder(
    color = colorState.value
)
```

`.value` 在 Composition 中被读取：

```
State 改变
↓
Recomposition
↓
新的 Element
↓
update(Node)
↓
Draw invalidation
↓
draw()
```

而把 `State` 对象交给 Node，并在 `draw()` 中读取：

```
.stateBorder(
    colorState = colorState
)
```

则是：

```
State 改变
↓
Draw Scope 失效
↓
draw()
```

第二种少经过了：

```
Composition
Element update
```

这正是高频视觉变化时“延迟读取状态”的核心价值。但这里不要得出一个新的机械规则：“以后颜色都应该传 `State<Color>`。” 完全不是。普通页面中：

```
Modifier.xxx(color = uiState.color)
```

简单、清晰、足够好，优先这样写。

只有当数据**变化频繁，而且确实只影响 Drawing**，跳过 Composition 和 Layout 能带来明确价值时，才值得设计成 Drawing 阶段读取状态。官方的阶段优化建议也是尽可能把高频变化延迟到实际需要它的阶段，而不是把所有状态强行往后推。[Android Developers](https://developer.android.com/develop/ui/compose/performance/modifier-phases?utm_source=chatgpt.com)

#### 14. 手动 `invalidateDraw()` 与 Draw Scope 自动观察 State，不是一回事

这两个机制很容易因为最终结果一样而混起来。`Sec05C`：

```
普通 Kotlin 属性变化
        ↓
我们主动调用 invalidateDraw()
        ↓
draw()
```

这里：

```
color
```

只是 Node 的普通字段。Compose 不会因为：

```kotlin
this.color = color
```

自动观察这个 Kotlin `var`。而 `Sec05D`：

```
draw() 读取 Snapshot State
        ↓
Compose 建立 Draw 阶段观察关系
        ↓
State 改变
        ↓
自动使 Draw Scope 失效
        ↓
draw()
```

这里依赖的是 Compose Snapshot State 的观察机制。所以有三种来源都可能最终走到 `draw()`：

```
Element.update()
→ Node 默认 auto invalidation

手动判断
→ invalidateDraw()

Draw 中读取 Snapshot State
→ State 改变后自动 Draw invalidation
```

**最终目标相同，触发来源不同。**把这三条区分开，6.5 后面遇到复杂 Node 时就不会混乱。

------

#### 15. 什么时候应该关闭自动 invalidation

这一点不用背复杂规则，只抓一个判断标准：**默认保留自动 invalidation；只有当“Element 更新”明显不等于“这个 Node 的所有能力都需要重新执行”时，再考虑手动控制。**我们的第一阶段 Border：

```
color
width
cornerRadius
```

三个参数全部影响 Draw。因此默认机制非常合适：

```
shouldAutoInvalidate == true
```

而 `Sec05C` 故意加入：

```
debugVersion
```

制造了：

```
Element 需要 update
但是 Draw 不需要重做
```

这时精细 invalidation 才开始有价值。真正的业务价值通常会在一个 Node 同时承担：

```
Layout
Draw
Pointer Input
Semantics
...
```

等多个能力时明显增加。那时候一个参数变化到底应该 invalidate 哪个阶段，就值得精确控制。当前 6.5 不继续展开其它 Node 类型。

#### 16. 第三阶段最终模型

这一阶段最重要的不是记住 `shouldAutoInvalidate` 这个属性，而是把“数据变化 → 屏幕更新”拆成不同层次。

普通自定义 Draw Modifier 最常见的路径：

```
State 在 Composition 中改变
        ↓
Recomposition
        ↓
Element 改变
        ↓
update(existing Node)
        ↓
Node 默认自动 Draw invalidation
        ↓
draw()
```

精确控制：

```
Element 改变
        ↓
update(existing Node)
        ↓
shouldAutoInvalidate = false
        ↓
判断真正影响了什么
        ↓
invalidateDraw()
        ↓
draw()
```

高频且只影响绘制的 State：

```
State 在 draw() 中被读取
        ↓
State 改变
        ↓
Draw Scope 直接 invalidated
        ↓
draw()

不经过 Recomposition
不经过 Element.update()
```

到这里，`DrawModifierNode` 的运行模型已经基本闭环：

```
声明
→ Element
→ Node
→ update
→ invalidation
→ draw
```

下一阶段可以真正从“机制实验”回到“怎么写一个合格的实际 Modifier”：参数 API 应该怎么设计、哪些东西应该保存在 Node、Modifier 顺序怎样继续影响自定义 Node、`draw()` 中哪些操作不适合每帧执行，以及什么时候这种底层 Node 写法值得用于真实项目。

### 第四阶段：把 DrawModifierNode 写成真正可复用的 Modifier

前三个阶段解决的是运行机制：`Element` 为什么存在、Node 为什么能够复用、`update()` 怎样同步参数，以及 Draw invalidation 怎样把新的运行时数据送进下一次 `draw()`。这一阶段开始回到实际开发：**一个自定义 `DrawModifierNode` 应该怎样设计，才能像 Compose 官方 Modifier 一样被正常复用，而不是只能跑通的实验代码。**

本阶段新建独立文件：`Sec05E_StatusIndicatorModifier.kt`

案例做一个很常见的视觉能力：在任意组件四角绘制一个状态圆点。这个圆点本身没有业务含义，可以代表在线状态、同步状态、未读状态、日历事件状态等。案例重点是参数设计、`Dp → px`、当前绘制空间、Modifier 顺序以及业务状态与绘制实现的职责边界。

```kotlin
    var color: Color,

        if (!visible) {
            return

                if (layoutDirection == LayoutDirection.Ltr) {
                    startX
                } else {
                    endX
                }

                    endX

                    startX
                }
            }

            StatusIndicatorCorner.TopStart,
            StatusIndicatorCorner.TopEnd -> topY

            StatusIndicatorCorner.BottomStart,
            StatusIndicatorCorner.BottomEnd -> bottomY
        }

        drawCircle(
            color = color,
            radius = radiusPx,
            center = Offset(x, y)
        )
    }
```

#### 2. 一个好的 Modifier API 应该描述“视觉能力”，而不是暴露实现细节

现在对外 API 是：

```kotlin
fun Modifier.statusIndicator(
    visible: Boolean,
    color: Color,
    radius: Dp = 6.dp,
    edgePadding: Dp = 6.dp,
    corner: StatusIndicatorCorner = StatusIndicatorCorner.TopEnd
): Modifier
```

从调用者角度，只需要思考：

```text
显示吗？
什么颜色？
多大？
离边缘多远？
在哪个角？
```

调用者完全不需要知道：

```text
ModifierNodeElement
DrawModifierNode
invalidateDraw
ContentDrawScope
Node 如何复用
```

这就是底层实现和公共 API 应该有的边界。所以自定义 Modifier 的目标不是让使用它的人写出：

```kotlin
Modifier.someModifier(
    nodeConfig = ...,
    drawScopeConfig = ...,
    invalidateMode = ...
)
```

而应该尽可能接近官方 Modifier：

```kotlin
Modifier.padding(16.dp)

Modifier.background(Color.Red)

Modifier.statusIndicator(
    visible = true,
    color = Color.Green
)
```

**Node 是实现手段，不应该泄漏成调用者的负担。**

---

#### 3. 为什么公开参数使用 `Dp`，Node 到 `draw()` 才转换成 px

我们的 API 接收：

```kotlin
radius: Dp
edgePadding: Dp
```

但真正绘制的时候：

```kotlin
val radiusPx = radius.toPx()
val edgePaddingPx = edgePadding.toPx()
```

原因很直接：对 UI API 来说：

```text
6.dp
8.dp
```

是合理的设备无关尺寸，而 Canvas 最终工作在像素坐标中：

```text
x = 42.5 px
radius = 21 px
```

`ContentDrawScope` 本身提供了当前绘制环境的 `Density`，所以 `Dp.toPx()` 可以在这里直接使用。这也是一个很实用的设计原则：**公共 Modifier API 尽量使用 Compose UI 层自然的单位；进入具体绘制阶段以后，再转换成 DrawScope 所需要的像素值。**不要把对外 API 做成：

```kotlin
fun Modifier.statusIndicator(
    radiusPx: Float,
    edgePaddingPx: Float
)
```

否则调用者还要自己处理设备密度，这相当于把绘制实现细节泄漏出去了。

---

#### 4. Node 使用的 `size` 是“它当前所在位置的绘制空间”

这里：

```kotlin
size.width
size.height
```

不是整个屏幕尺寸，也不是固定等于 `Box.size(220.dp, 120.dp)` 的某个全局属性。它表示：**当前这个 DrawModifierNode 在 Modifier 链当前位置拥有的绘制空间。**因此：

```kotlin
val endX = size.width - edgePaddingPx - radiusPx
```

实际表达的是：从当前 Draw Node 的右边缘往回退 `edgePadding + radius`。这也是为什么一个 Modifier 可以被放到：

```kotlin
Text
Box
Row
Image
```

上复用。Node 不需要知道外面是什么 Composable，它只面对：

```text
当前绘制空间有多大？
当前 LayoutDirection 是什么？
我要在这个空间里画什么？
```

这个思想和 6.2 学 `Canvas / DrawScope` 时其实完全一致。

---

#### 5. 为什么这里使用 Start / End，而不是 Left / Right

我们定义：

```kotlin
TopStart
TopEnd
BottomStart
BottomEnd
```

而没有定义：

```text
TopLeft
TopRight
```

因为 Compose UI 通常应该尊重：

```kotlin
layoutDirection
```

对于 LTR：

```text
Start = Left
End   = Right
```

对于 RTL：

```text
Start = Right
End   = Left
```

所以：

```kotlin
if (layoutDirection == LayoutDirection.Ltr) startX else endX
```

本质上是在做逻辑方向到实际坐标的映射。这里体现了一个比较重要的 Modifier API 设计原则：**对外描述 UI 意图时尽量使用逻辑语义；真正进入绘制阶段时，再根据当前环境计算物理坐标。**这也是为什么 Node 很适合保存：

```text
corner = TopEnd
```

而不是提前保存：

```text
x = 193.5f
y = 15.5f
```

后者过早把环境相关的结果固定死了。

---

#### 6. `drawContent()` 的位置本身就是这个 Modifier 的语义

我们的代码：

```kotlin
override fun ContentDrawScope.draw() {
    drawContent()
    
    if (!visible) return
    
    drawCircle(...)
}
```

因此顺序是：

```text
组件原本内容
    ↓
状态圆点
```

圆点覆盖在内容之上。如果改成：

```kotlin
drawCircle(...)
drawContent()
```

语义就变成：

```text
先画状态圆点
    ↓
再画组件内容
```

组件自己的内容可能把圆点盖住。如果完全删除：

```kotlin
drawContent()
```

这个 Modifier 就不再继续绘制它包裹的内容。这些行为你在 6.3 已经实验过，现在真正需要补的是：**当我们封装公共 Modifier 时，`drawContent()` 放在哪里不是实现细节，而是这个 Modifier 对外行为的一部分。**比如：

```text
background 类 Modifier
→ 通常先画自己的东西，再 drawContent()

overlay / badge / indicator
→ 通常先 drawContent()，再画自己的东西
```

我们这个 `statusIndicator` 明确属于后者。

---

#### 7. `drawContent()` 也不要求“一定正好调用一次”

常见 Modifier 通常调用一次：

```kotlin
drawContent()
```

但 `ContentDrawScope` 并没有规定必须如此。零次：

```kotlin
override fun ContentDrawScope.draw() {
    drawRect(Color.Black)
}
```

原内容不再绘制。一次：

```kotlin
drawContent()
drawCircle(...)
```

正常叠加效果。理论上多次：

```kotlin
drawContent()
translate(...) {
    drawContent()
}
```

就会把内容绘制多次。所以 `drawContent()` 更准确的理解不是：“这里必须写的一行模板代码。” 而是：**继续执行被当前 Draw Modifier 包裹的下一层绘制内容。**只是绝大多数普通视觉 Modifier 都只需要调用一次。

---

#### 8. Modifier 顺序对自定义 Draw Node 仍然有效

自定义 Node 并不会脱离 Modifier 链。例如：

```kotlin
Modifier
    .statusIndicator(...)
    .padding(24.dp)
```

和：

```kotlin
Modifier
    .padding(24.dp)
    .statusIndicator(...)
```

不是同一个东西。`padding` 改变了后续内容所处的布局空间，因此 `statusIndicator` 放在不同位置时：

```kotlin
size
```

可能不同，最终：

```kotlin
endX
bottomY
```

自然也可能不同。同理：

```text
clip
background
padding
graphicsLayer
statusIndicator
```

顺序交换以后，都可能改变最终结果。现在先掌握应用层结论：**自定义 `DrawModifierNode` 和官方 Modifier 完全一样，仍然遵守 Modifier 链的顺序语义。**

至于为什么 Modifier A 包着 Modifier B 时，Layout 与 Draw 会形成怎样的嵌套层级，我们已经约定放到 **7.9** 正式展开。现在没必要从 `NodeCoordinator` 等内部结构往下钻。

---

#### 9. `draw()` 运行频率可能很高，不要把它当普通业务函数

Drawing 阶段可能频繁发生，特别是动画、拖拽、滚动以及高频 State 更新过程中。所以：

```kotlin
override fun ContentDrawScope.draw()
```

应该主要承担：

```text
读取当前绘制参数
计算必要坐标
执行绘制
```

像当前代码：

```kotlin
val radiusPx = radius.toPx()
val edgePaddingPx = edgePadding.toPx()

val startX = ...
val endX = ...

drawCircle(...)
```

这种简单数值计算没有问题。真正需要警惕的是每一帧反复进行：

```text
创建复杂 Path
构建大型集合
解析字符串
执行数据库查询
访问 Repository
创建昂贵 Shader / Brush
做复杂业务计算
```

特别是：

```kotlin
override fun ContentDrawScope.draw() {
    repository.loadSomething()
}
```

从职责上就已经彻底错位了。Draw 阶段应该拿到**已经准备好的 UI 绘制数据**，然后快速完成这一帧。

前面 6.3 学过 `drawWithCache`，就是因为某些绘制对象没必要每一帧重建。将来真正碰到复杂 Node 时，同样要思考哪些结果可以缓存；但当前案例只有几个坐标和一个圆，所以刻意加缓存反而属于过度设计。

---

#### 10. Node 里应该保存什么，不应该保存什么

当前 Node 保存：

```kotlin
var visible: Boolean
var color: Color
var radius: Dp
var edgePadding: Dp
var corner: StatusIndicatorCorner
```

这些都是：**完成当前 Modifier 行为所需要的 UI 参数。**这是合理的。但是假设以后你在记账 App 里有：

```kotlin
data class Transaction(
    val id: Long,
    val amount: BigDecimal,
    val category: Category,
    val syncStatus: SyncStatus,
    ...
)
```

不建议设计成：

```kotlin
Modifier.statusIndicator(
    transaction = transaction
)
```

然后让 Node 自己判断：

```text
Transaction 是否同步
应该显示什么颜色
业务状态是不是失败
```

更合理的是在 UI 层先完成业务状态到视觉状态的映射：

```kotlin
Modifier.statusIndicator(
    visible = transaction.syncStatus != SyncStatus.Synced,
    color = indicatorColor
)
```

也就是：

```text
业务含义
    ↓
Composable / UI State 做转换
    ↓
纯视觉参数
    ↓
DrawModifierNode
```

Node 不需要认识：

```text
ViewModel
Repository
UseCase
Database Entity
Domain Model
```

它只需要知道：

```text
画不画
什么颜色
画多大
画在哪里
```

这也是自定义 Modifier 能保持高度复用的重要原因。

---

#### 11. `State<T>` 要不要直接传进 Node，不应该形成机械规则

上一阶段的 `Sec05D` 我们故意写过：

```kotlin
colorState: State<Color>
```

然后在：

```kotlin
draw()
```

里读取：

```kotlin
colorState.value
```

那是为了学习：

```text
State 在 Draw 阶段读取
→ 可以直接使 Draw 失效
→ 跳过 Recomposition
```

但普通 Modifier API 不应该因此全部改成：

```kotlin
fun Modifier.statusIndicator(
    visibleState: State<Boolean>,
    colorState: State<Color>,
    radiusState: State<Dp>
)
```

这会让公共 API 非常难用。默认仍然应该优先：

```kotlin
visible: Boolean
color: Color
radius: Dp
```

因为它表达清晰，调用自然，而且绝大多数 UI 根本不需要为了少一次 Composition 而把 `State<T>` 整个传进 Node。只有满足类似条件时，才值得考虑像 `Sec05D` 那样延迟读取：

```text
数据变化非常频繁
+
变化只影响 Drawing
+
确实希望避免 Composition / Layout 工作
```

所以 `Sec05D` 是一种**性能与阶段控制技术**，不是自定义 Modifier 的默认模板。

---

#### 12. 一个 Modifier 应该只负责一个清晰能力

假设现在继续往 `StatusIndicatorNode` 塞东西：

```text
圆点
边框
阴影
点击
动画
业务状态转换
埋点
Repository
```

最后虽然技术上可能还能运行，但这个 Modifier 会越来越难复用、难测试、难理解。更合理的是让：

```kotlin
Modifier.statusIndicator(...)
```

只表达：在当前组件上绘制一个状态指示器。如果以后还需要：

```kotlin
Modifier.selectionBorder(...)
```

就让它成为另一条 Modifier。调用者自己组合：

```kotlin
Modifier
    .selectionBorder(...)
    .statusIndicator(...)
```

Compose 的 Modifier 链本身就是为了支持这种小能力组合。因此写底层 Node 时不要因为“我已经拿到底层能力了”，就试图造一个万能 Node。

---

#### 13. 什么时候值得专门写 `DrawModifierNode`

目前我们已经付出了明显更多代码：

```text
Modifier factory
Element
create()
update()
Node
draw()
```

所以不能因为它更“底层”，就认为它比：

```kotlin
drawBehind
drawWithContent
drawWithCache
```

更高级、更应该使用。`DrawModifierNode` 真正有价值的典型情况是：

```text
这个绘制行为需要被项目大量复用
        +
希望拥有正式独立的 Modifier API
        +
需要长期存在的运行时 Node
        +
可能还需要精细更新、状态观察或性能控制
```

像今天：

```kotlin
Modifier.statusIndicator(...)
```

如果它真的是整个 App 都会使用的基础视觉能力，Node 实现很合理。但一个页面里只出现一次：

```text
在标题下面画一条线
```

专门写：

```text
XxxElement
XxxNode
```

通常就是过度设计。完整的：

```text
Canvas
drawBehind
drawWithContent
drawWithCache
DrawModifierNode
```

选择边界，我们下一阶段再统一整理。

---

#### 14. 第四阶段最终应该建立的设计模型

写一个真实的 `DrawModifierNode`，可以按这条顺序思考：

```text
第一步：这个 Modifier 对外提供什么视觉能力？
        ↓
设计简单、稳定的 Modifier API

第二步：哪些参数真正描述当前视觉配置？
        ↓
放进 ModifierNodeElement

第三步：运行中的 Node 需要保存哪些参数？
        ↓
由 create / update 同步进去

第四步：哪些数据必须到 Draw 阶段才能确定？
        ↓
size
Density
LayoutDirection
当前绘制坐标

第五步：drawContent() 应该在什么位置？
        ↓
确定这个 Modifier 是背景、覆盖层还是替代内容

第六步：draw() 中只留下必要的绘制工作
        ↓
避免业务逻辑和昂贵重复计算
```

现在你已经不只是能够写：

```kotlin
Modifier.Node(), DrawModifierNode
```

而是可以开始判断一个 Draw Modifier 应该怎样设计。

6.5 剩下最重要的一步，就是把已经学过的所有绘制入口摆到同一张地图上：**什么时候直接用 `Canvas`，什么时候 `drawBehind`，什么时候必须 `drawWithContent`，什么时候需要 `drawWithCache`，什么时候才值得真正实现 `DrawModifierNode`。** 下一阶段会专门解决这个选择问题，不再继续增加新的 Node 运行机制。

对，阶段四确实偏水了：真正的新知识密度明显低于前三阶段，却维持了同样的篇幅，而且提前侵入了本该放在收尾阶段的“什么时候用 Node”。这次直接把原来的第五、六阶段合并，**本阶段就是 6.5 最后一阶段**，只留下真正值得收尾的内容。

### 第五阶段：6.5 收尾——绘制 API 选择地图与核心边界

#### 1. 先把第 6 章重新压缩成一张地图

学完 6.1～6.5以后，不应该记住几十个零散 API，而应该形成下面这条主线：

```text
我需要一个特殊形状
→ Shape / Outline / Path                 [6.1]

我需要自己画一块 UI
→ Canvas + DrawScope                     [6.2]

我需要给已有 Composable 增加绘制
→ drawBehind / drawWithContent
→ drawWithCache                          [6.3]

我需要控制绘制结果怎样进入图层、怎样合成
→ graphicsLayer / Offscreen
→ CompositingStrategy                    [6.4]

我需要真正实现一条底层 Modifier 绘制能力
→ ModifierNodeElement
→ Modifier.Node
→ DrawModifierNode                       [6.5]
```

这就是第六章真正值得长期保留的骨架。具体参数忘掉很正常，只要以后遇到需求能够知道应该往哪一层找。

---

#### 2. `Canvas`、三个 Draw Modifier、`DrawModifierNode` 到底怎么选

| API | 最核心的定位 | 典型情况 |
|---|---|---|
| `Canvas` | **这个 Composable 的主体就是自己绘制出来的** | 图表、日历网格、自定义仪表盘、大面积自绘 UI |
| `drawBehind` | 给已有内容增加**固定在后面的绘制** | 自定义背景、底线、背景装饰 |
| `drawWithContent` | 需要自己决定**原内容什么时候画** | 前景遮罩、覆盖层、改变绘制顺序、隐藏内容 |
| `drawWithCache` | 绘制前存在**值得缓存的昂贵准备结果** | `Path`、`Brush`、复杂几何结果 |
| `DrawModifierNode` | 真正实现具有**长期运行 Node、update/invalidation 等能力**的底层 Modifier | 基础设施级 Modifier、复杂可复用行为、以后还可能结合其他 Node 能力 |

这里最需要纠正一个容易产生的错觉：

```text
Canvas
→ drawBehind
→ drawWithContent
→ drawWithCache
→ DrawModifierNode
```

**不是“越来越高级”的升级路线。**比如一个非常复杂的图表，可能最适合的仍然是 `Canvas`；一个只画一条线的效果，即使项目里复用十次，也完全可以：

```kotlin
fun Modifier.bottomLine(color: Color): Modifier =
    drawBehind {
        drawLine(
            color = color,
            start = Offset(0f, size.height),
            end = Offset(size.width, size.height)
        )
    }
```

没有任何理由为了显得底层，再造 `Element + Node`。

---

#### 3. `drawBehind` 和 `drawWithContent` 的选择其实最简单

只问一个问题：**我要不要控制原 Composable 内容的绘制时机？**不需要：

```text
我只想画在它后面
→ drawBehind
```

需要：

```text
我要画在前面
我要先画一层，再画内容
我要画完内容以后覆盖
甚至不想让内容出现

→ drawWithContent
```

因此：

```kotlin
drawWithContent {
    drawContent()
    drawRect(...)
}
```

和：

```kotlin
drawWithContent {
    drawRect(...)
    drawContent()
}
```

并不是实现细节上的小差异，而是在定义这个 Modifier 的实际行为。`drawContent()` 也不是必须存在的模板代码。它真正表达的是：**继续绘制被当前 Draw Modifier 包裹的内容。**不调用，就不继续绘制那部分内容。

---

#### 4. `drawWithCache` 只在真的有东西值得缓存时使用

这一点值得专门卡死，因为它非常容易被滥用。像：

```kotlin
val radius = 8.dp.toPx()
drawCircle(...)
```

这种计算根本没必要为了“优化”而上 `drawWithCache`。真正值得考虑缓存的是：

```text
复杂 Path
Brush / Shader
大量几何预计算
不需要每次 draw() 都重新构造的对象
```

所以判断标准不是：

```text
绘制代码复杂
→ drawWithCache
```

而是：

```text
Draw 之前存在昂贵、可以复用的准备结果
→ drawWithCache
```

这也是你以后回忆 6.3 时最值得留下的区别。

---

#### 5. `DrawModifierNode` 真正比普通 Drawing Modifier 多出来什么

这一节前三阶段真正学习的东西，可以浓缩成这一条链：

```text
Modifier factory
      ↓
ModifierNodeElement
      ↓
create / update
      ↓
长期存在的 Modifier.Node
      ↓
DrawModifierNode
      ↓
Draw invalidation
      ↓
ContentDrawScope.draw()
```

其中 `Element` 和 `Node` 的分离是核心。`Element` 表示：

```text
这一轮声明出来的 Modifier 配置
```

例如：

```text
Blue / 6.dp / 20.dp
```

下一次重组可以重新产生一个新的 Element。而 `Node` 是：

```text
真正挂在 UI 运行时结构里工作的对象
```

所以 Compose 可以做到：

```text
Element 完全相等
→ REUSE
→ Node 不动

Element 参数变化，但还是同一种 Element
→ UPDATE
→ 同一个 Node
→ update(node)

Element 类型改变
→ REPLACE
```

这就是为什么我们不能简单理解成：

```text
重组
→ Modifier 全部重建
→ Node 全部重建
```

声明式描述可以反复产生，而真正工作的运行对象可以继续复用。

---

#### 6. `update(node)` 后为什么会重新 `draw()`，这是 6.5 最重要的闭环之一

普通情况下：

```kotlin
override fun update(node: BorderNode) {
    node.color = color
}
```

只是修改了一个 Kotlin 属性。真正让新颜色最终出现在屏幕上的过程是：

```text
Element 发生变化
        ↓
update(existing Node)
        ↓
Node 中影响 Draw 的数据改变
        ↓
Modifier.Node 默认自动 invalidation
        ↓
Draw invalidated
        ↓
draw()
        ↓
读取新参数
        ↓
新的像素
```

这里的 **invalidation** 不表示 Node 坏掉了，也不是销毁 Node，而是：**此前这个阶段计算出来的结果已经过期，需要重新执行。**这条概念以后到了 Layout 仍然会反复出现。

---

#### 7. `Element.update()` 与 Draw 中直接读取 State，是两条不同路线

这是第三阶段最值得长期记住的地方。

第一种：

```kotlin
Modifier.xxx(
    color = colorState.value
)
```

`.value` 在 Composition 中读取：

```text
State change
→ Composition invalidation
→ Recomposition
→ new Element
→ update(Node)
→ Draw invalidation
→ draw()
```

第二种：

```kotlin
Modifier.xxx(
    colorState = colorState
)
```

然后：

```kotlin
override fun ContentDrawScope.draw() {
    val color = colorState.value
}
```

`.value` 在 Drawing 阶段读取：

```text
State change
→ Draw invalidation
→ draw()
```

中间不需要：

```text
Recomposition
Element.update()
```

所以 Compose 更完整的状态模型不是简单一句：

```text
State 改变 → 重组
```

而是：**State 在哪个阶段被读取，变化以后就可能使那个阶段失效。**目前你已经认识两个：

```text
Composition 中读取
→ Recomposition

Drawing 中读取
→ Redraw
```

以后学 Layout 时这张图还会再补一块。

---

#### 8. 自动 invalidation 与手动 `invalidateDraw()` 的边界

默认：

```kotlin
shouldAutoInvalidate == true
```

对于普通 `DrawModifierNode`，这是首选。例如：

```text
color
width
cornerRadius
```

全部都会影响绘制，那么 Element 发生变化后直接自动 invalidate Draw，非常合理。只有出现这种情况：

```text
Element 确实需要 update

但是：
某些参数影响 Draw
某些参数不影响 Draw
或者这个 Node 同时具有多个不同能力
```

才值得考虑：

```kotlin
override val shouldAutoInvalidate = false
```

然后自己：

```kotlin
if (drawChanged) {
    invalidateDraw()
}
```

因此不要看到手动 invalidation 更“精细”，以后就全部关掉自动机制。日常默认仍然应该让 Compose 管。

---

#### 9. 上一阶段那个 Element `equals()` 问题，最终结论也可以固定下来

假设 Element 有：

```kotlin
data class MyElement(
    val color: Color,
    val debugTag: String
)
```

而 Node 根本不使用 `debugTag`。只改变：

```text
debugTag
```

那么：

```text
旧 Element != 新 Element
→ UPDATE
→ 同一个 Node
→ update(node)
```

不会走真正的 `REUSE`。所以：

```text
REUSE
= Element.equals() == true
= 不 update

UPDATE
= equals() == false
  但 Element 类型相同
= 同一个 Node
= 调用 update
```

如果某个字段完全不影响 Modifier 行为，却又进入了 `equals()`，就可能产生不必要的 update，配合默认 auto invalidation 甚至产生没有必要的重新绘制。这也是为什么 `ModifierNodeElement.equals()/hashCode()` 并不是无关紧要的样板代码。

#### 10. `State<T>` 直接传进 Node 是技术手段，不是默认设计

`Sec05D` 为了验证 Drawing 阶段直接观察 State，故意写成：

```kotlin
colorState: State<Color>
```

这是一个非常好的机制实验。但真实 API 默认仍然优先：

```kotlin
color: Color
visible: Boolean
radius: Dp
```

只有：

```text
状态变化非常频繁
+
它真的只影响 Drawing
+
跳过 Composition 有实际价值
```

才值得考虑把状态读取推迟到 Drawing 阶段。不要学到性能技巧以后，把所有：

```text
T
```

机械改成：

```text
State<T>
```

那会让普通 Modifier API 反而变难用。

#### 11. 还有一个现在知道存在、但不继续下钻的黑盒

我们已经验证：

```kotlin
this then StateBorderElement(...)
```

执行的时候，只是在建立 Modifier / Element 描述。它并不会在 `then()` 这一瞬间直接调用：

```kotlin
Element.create()
```

Compose 后续还需要把新的 Modifier 描述协调到真实运行时结构，再决定：

```text
REUSE
UPDATE
REPLACE
create Node
```

我们在 `Sec05D` 里还观察到了 `SideEffect`、Node `create()` 等日志顺序上的现象。**现在到这里停止。**因为再继续解释：

```text
LayoutNode
attach
NodeChain
Coordinator
Element diff
Node attach / detach
```

就已经进入第 11 章的 Modifier Node 内部体系，而且还依赖第 7 章即将学习的 Layout 心智模型。当前只留下这条边界：

```text
Composition 产生描述
        ↓
Compose 把 Modifier 描述应用到运行时 UI 结构
        ↓
Element 与 Node 被协调
        ↓
DrawModifierNode 最终参与 Drawing
```

以后知识够了，再回来把中间黑盒逐层打开。

#### 12. 最后用几个真实场景验收 6.5

|---|---|

#### 13. 6.5 到这里正式结束

这一节真正需要长期保留的不是 `ModifierNodeElement` 每一行怎么写，而是四个结论：

```text
Element = 声明式 Modifier 描述
Node = 可长期复用的运行时对象

create()
= 第一次建立对应 Node

update(node)
= 把新的 Element 配置同步进已有 Node

invalidation
= 某个阶段此前的结果过期，需要重新执行
```

再加上一条选择原则：**能用更简单的 `Canvas` / Drawing Modifier 清晰解决，就停在那里；真正需要 Node 的运行时能力时，再下降到 `DrawModifierNode`。**

至此 **6.1～6.5「图形与绘制完全掌握」结束**。下一章进入第 7 章以后，重点会从“像素怎么画出来”切换到另一套核心机制：**尺寸怎样被测量、位置怎样被确定，以及如何真正自定义 Layout。**
