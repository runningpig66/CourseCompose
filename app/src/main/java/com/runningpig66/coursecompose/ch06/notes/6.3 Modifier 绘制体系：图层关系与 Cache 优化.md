### 第一阶段：从 `Canvas` 走向 `Modifier.drawBehind()`

你刚学完 6.2，所以这一阶段最重要的不是再学一遍 `DrawScope`，而是完成一个思维转换：

> **6.2 的 `Canvas`：我专门拿出一块区域来画。**  
> **6.3 的 `drawBehind`：我给一个本来就有内容的 Composable，再附加一层自定义绘制。**

这就是 `Modifier` 绘制体系真正开始有开发价值的地方。

官方文档甚至直接指出：`Canvas` Composable 本身就是围绕 `Modifier.drawBehind` 提供的便利封装。也就是说，你在 6.2 学过的 `drawCircle()`、`drawLine()`、`drawPath()`、`size`、`Offset`、`dp.toPx()` 等知识，现在全部可以直接搬过来，并不是重新学习另一套绘图 API。

#### 1. 为什么已经有 `Canvas`，还需要 `drawBehind()`？

假设你要画一张完全自定义的折线图，整个区域基本都是自己绘制的，那么 `Canvas` 非常自然：

```kotlin
Canvas(
    modifier = Modifier.size(300.dp)
) {
    drawLine(...)
    drawCircle(...)
}
```

但真实 UI 经常不是这样。比如你已经有一个 `Text`、`Box`、`Row`，里面有正常的 Compose 内容，现在只是想给它增加：

- 自定义背景；
- 一条装饰线；
- 一个圆形状态标记；
- 根据组件尺寸变化的特殊背景；
- 后面更复杂的渐变、Path 等。

如果为了这些东西再单独塞一个 `Canvas`，你还得考虑 Canvas 与文字如何叠放、尺寸如何同步、谁负责布局。`drawBehind()` 的思路更直接：

```text
这个 Box 正常布局、正常显示内容
        +
在它自己的绘制区域后面，再执行我的 DrawScope 绘制
```

这正是它解决的问题。官方对它的定义也非常直接：**在被 Modifier 修饰的内容后方进行 Canvas 绘制。**

#### 2. 教学示例：`Sec03A_DrawBehindIntro.kt`

这份代码你可以直接建文件运行。先不要急着分析 Modifier 顺序，本阶段只观察 `drawBehind` 最核心的行为。

```kotlin
@Composable
fun Sec03A_DrawBehindIntro() {

    var expanded by remember {
        mutableStateOf(false)
    }

    Column(
        modifier = Modifier
            .fillMaxSize()
            .padding(24.dp),
        verticalArrangement = Arrangement.spacedBy(20.dp)
    ) {

        Text(
            text = "Modifier.drawBehind()",
            style = MaterialTheme.typography.headlineSmall
        )

        Button(
            onClick = {
                expanded = !expanded
            }
        ) {
            Text("切换 Box 宽度")
        }

        Box(
            modifier = Modifier
                .width(
                    if (expanded) 320.dp else 220.dp
                )
                .height(140.dp)
                .drawBehind {

                    Log.d(
                        "Sec03A",
                        "drawBehind: width=${size.width}, height=${size.height}"
                    )

                    // 整个 Box 的自定义背景
                    drawRoundRect(
                        color = Color(0xFFE8EAF6),
                        cornerRadius = CornerRadius(
                            24.dp.toPx()
                        )
                    )

                    // 右上角装饰圆
                    drawCircle(
                        color = Color(0xFF5C6BC0),
                        radius = 18.dp.toPx(),
                        center = Offset(
                            x = size.width - 34.dp.toPx(),
                            y = 34.dp.toPx()
                        )
                    )

                    // 底部装饰线
                    drawLine(
                        color = Color(0xFF5C6BC0),
                        start = Offset(
                            x = 20.dp.toPx(),
                            y = size.height - 18.dp.toPx()
                        ),
                        end = Offset(
                            x = size.width - 20.dp.toPx(),
                            y = size.height - 18.dp.toPx()
                        ),
                        strokeWidth = 3.dp.toPx()
                    )
                }
        ) {

            Column(
                modifier = Modifier
                    .fillMaxSize()
                    .padding(20.dp),
                verticalArrangement = Arrangement.spacedBy(8.dp)
            ) {

                Text(
                    text = "我是 Box 的正常内容",
                    style = MaterialTheme.typography.titleMedium
                )

                Text(
                    text = "背景和装饰来自 drawBehind()"
                )
            }
        }
    }
}
```

#### 3. 运行以后重点观察什么？

第一件事，**文字仍然是普通 `Box` 的内容。**我们没有在 `DrawScope` 里面调用任何 `drawText()`，也没有让 Canvas 接管整个组件。`Box` 该怎么组合、布局、显示文字，仍然怎么工作。但是在它背后，多出了一层你自己画出来的东西：

```text
圆角矩形
圆形
装饰线
────────────
Box 自己的 Text 内容
```

这里“背后”非常关键。你会发现右上角的紫色圆如果和文字区域发生重叠，**文字依然会绘制在它上面**。这就是 `drawBehind` 这个名字的字面含义：

```text
先画 drawBehind 的东西
再画 Composable 自己的内容
```

现在只需要形成这个结论。到第二阶段学习 `drawWithContent()` 时，我们再真正控制“原始内容到底在哪一步画”。

#### 4. 你其实仍然处于熟悉的 `DrawScope`

看这一段：

```kotlin
.drawBehind {
    drawCircle(...)
    drawLine(...)
}
```

这里 lambda 的接收者就是：

```kotlin
DrawScope
```

所以 6.2 学过的东西全部还在。你仍然拥有：

```kotlin
size
center
drawLine()
drawRect()
drawRoundRect()
drawCircle()
drawPath()
dp.toPx()
```

因此可以把关系理解成：

```text
Canvas
   ↓
提供一块专门用于绘制的 Composable

drawBehind
   ↓
把 DrawScope 绘制能力附着到现有 Composable 上
```

不是两套绘制系统，而是**同一套 `DrawScope` 能力的两种使用入口**。这也是为什么 6.2 必须放在 6.3 前面：现在看到 `drawBehind {}`，里面的绘图部分对你而言应该已经完全陌生感为零。

#### 5. `size` 现在是谁的尺寸？

这个变化非常重要。以前写：

```kotlin
Canvas(
    modifier = Modifier.size(300.dp)
) {
    println(size)
}
```

`size` 是 Canvas 最终获得的绘制区域。现在：

```kotlin
Box(
    modifier = Modifier
        .width(220.dp)
        .height(140.dp)
        .drawBehind {
            println(size)
        }
)
```

`size` 是 **`drawBehind` 当前拥有的绘制区域大小**。第一次运行，你应该在 Logcat 看到类似：

```text
drawBehind: width=660.0, height=420.0
```

具体 px 数值取决于设备 density，所以不一定和这里一样。然后点击：

```text
切换 Box 宽度
```

Box 从：

```kotlin
220.dp
```

变成：

```kotlin
320.dp
```

重新 Layout 以后，`drawBehind` 下一次绘制拿到的 `size.width` 也会变大。于是这句：

```kotlin
x = size.width - 34.dp.toPx()
```

自动把圆保持在新的右上角；这句：

```kotlin
x = size.width - 20.dp.toPx()
```

也会自动延长底部横线。这正是自定义绘制非常典型的写法：**不要提前假设组件最终是多少像素，而是在真正绘制时，根据当前 `DrawScope.size` 计算几何位置。**

#### 6. 一个非常重要的边界：`drawBehind()` 不负责布局

这里很容易产生一个潜在误解。假如你这样写：

```kotlin
Box(
    modifier = Modifier
        .size(100.dp)
        .drawBehind {
            drawCircle(
                radius = 300.dp.toPx()
            )
        }
)
```

你画了一个巨大圆，并不会因此告诉 Compose：“我的组件现在需要 600dp × 600dp。” 不会。`drawBehind()` 属于 **Draw 阶段**。组件多大，原则上在它进入绘制之前，布局阶段已经确定好了。官方当前的 Compose phase 文档也明确把 `drawBehind` 放在 Drawing phase 中。所以要区分两个问题：

```text
这个 Composable 占多大的布局空间？
        ↓
Layout 决定

这块已经确定的区域里要画什么？
        ↓
drawBehind / DrawScope 决定
```

这是从 6.2 走进整个绘制 Modifier 体系之后，需要牢牢记住的一条边界。至于“画出边界的东西到底会不会看得到、什么时候被裁切”，我们后面结合 `clip` 和图层关系再处理，现在不要提前展开。

#### 第一阶段收束

现阶段你只需要形成下面这个心智模型：

```text
Composable
├── Layout 已经决定它有多大
├── drawBehind {
│       // this = DrawScope
│       // 使用当前绘制区域的 size
│       // 先画自定义图形
│   }
└── 再绘制 Composable 自己的内容
```

因此，**`Canvas` 更适合“这块区域本身主要就是我要画的东西”；`drawBehind()` 更适合“我已经有正常 Composable，只想在它背后增加自定义绘制”。**

第一阶段先停在这里。下一阶段我们会进入本节真正关键的第二个 API：`drawWithContent()`，到时候直接通过代码改变 `drawContent()` 的位置，看清楚为什么 `drawBehind()` 永远只能负责“后面”，而 `drawWithContent()` 能真正控制内容的绘制顺序。

### 第二阶段：`drawWithContent()` —— 用 `drawContent()` 控制绘制顺序

第一阶段的 `drawBehind()` 有一个已经固定好的规则：**先执行你的自定义绘制，再绘制 Composable 自己的内容。**第二阶段要把这件事拆开。`drawWithContent()` 给你的不再只是普通 `DrawScope`，而是 `ContentDrawScope`。你仍然拥有 6.2 学过的所有绘图能力，但额外得到一个非常关键的函数：

```kotlin
drawContent()
```

它的意义可以直接理解成：**“现在，把这个 Modifier 后面的原始内容画出来。”**

因此 `drawWithContent()` 真正重要的并不是又多了一个绘图 API，而是：**原来 Compose 自动帮你决定的内容绘制时机，现在交给你控制。**官方当前也把 `drawWithContent` 定义为三个主要 Drawing Modifier 中最基础的一个，并明确说明它可以控制自定义绘制发生在 Composable 内容之前还是之后。

#### 1. 先直接跑三个结果：`Sec03B_DrawWithContentOrder.kt`

这一阶段最适合一次把三种情况摆在屏幕上。你运行以后不用先分析代码，只看三个 Box 的区别。

```kotlin
@Composable
fun Sec03B_DrawWithContentOrder() {

    Column(
        modifier = Modifier
            .fillMaxSize()
            .padding(24.dp),
        verticalArrangement = Arrangement.spacedBy(24.dp)
    ) {

        Text(
            text = "drawWithContent 绘制顺序",
            style = MaterialTheme.typography.headlineSmall
        )

        DrawOrderCard(
            title = "A：先自定义绘制，再 drawContent()",
            mode = DrawOrderMode.Behind
        )

        DrawOrderCard(
            title = "B：先 drawContent()，再自定义绘制",
            mode = DrawOrderMode.Front
        )

        DrawOrderCard(
            title = "C：完全不调用 drawContent()",
            mode = DrawOrderMode.HideContent
        )
    }
}

private enum class DrawOrderMode {
    Behind,
    Front,
    HideContent
}

@Composable
private fun DrawOrderCard(
    title: String,
    mode: DrawOrderMode
) {

    Box(
        modifier = Modifier
            .fillMaxWidth()
            .height(110.dp)
            .drawWithContent {

                when (mode) {

                    DrawOrderMode.Behind -> {
                        drawCircle(
                            color = Color(0xFF5C6BC0),
                            radius = 52.dp.toPx(),
                            center = center
                        )

                        drawContent()
                    }

                    DrawOrderMode.Front -> {
                        drawContent()

                        drawCircle(
                            color = Color(0x995C6BC0),
                            radius = 52.dp.toPx(),
                            center = center
                        )
                    }

                    DrawOrderMode.HideContent -> {
                        drawCircle(
                            color = Color(0xFF5C6BC0),
                            radius = 52.dp.toPx(),
                            center = center
                        )

                        // 故意不调用 drawContent()
                    }
                }
            }
            .border(
                width = 1.dp,
                color = Color.Gray
            ),
        contentAlignment = Alignment.Center
    ) {

        Text(
            text = title,
            style = MaterialTheme.typography.bodyLarge
        )
    }
}
```

这里我故意让圆和文字发生重叠，否则绘制顺序虽然不同，视觉上却不明显。

#### 2. 第一组：自定义绘制 → `drawContent()`

先看：

```kotlin
DrawOrderMode.Behind -> {
    drawCircle(...)
    drawContent()
}
```

实际顺序就是：

```text
① drawCircle()
② drawContent()
```

所以先把紫色圆画到 Canvas 上，然后才把 `Box` 原本拥有的内容画出来。这里所谓的“原本内容”，在我们的例子里主要就是：

```kotlin
Text(
    text = title
)
```

所以最后视觉效果是：

```text
Text
──────────
紫色圆
```

这里不是说它们真的存在两个独立 Android View 图层，而是描述**最终的绘制覆盖关系**：后画的内容盖在先画的内容上。你已经可以发现：

```kotlin
.drawWithContent {
    drawCircle(...)
    drawContent()
}
```

和第一阶段：

```kotlin
.drawBehind {
    drawCircle(...)
}
```

在这个例子里的结果基本一样。这不是巧合。官方文档明确说明，`drawBehind` 本质上就是针对这种固定顺序提供的便利 API：你只负责写“后面的自定义绘制”，内容的绘制顺序已经替你安排好了。所以平时如果需求只是：“我要在内容背后画点东西。” 那么没有必要为了显得高级而写 `drawWithContent()`。直接：

```kotlin
drawBehind { }
```

更能表达意图。

---

#### 3. 第二组：`drawContent()` → 自定义绘制

真正体现 `drawWithContent()` 价值的是第二组：

```kotlin
DrawOrderMode.Front -> {
    drawContent()
    drawCircle(
        color = Color(0x995C6BC0),
        ...
    )
}
```

这一次顺序完全反过来了：

```text
① drawContent()
② drawCircle()
```

所以 Compose 先把 `Box` 的文字画出来，然后我们再画一个半透明紫色圆。最终：

```text
半透明紫色圆
────────────
Text
```

圆覆盖在文字上。之所以我这里把颜色设置成：

```kotlin
Color(0x995C6BC0)
```

而不是完全不透明，是为了让你仍然能看到下面的文字，从而非常明显地观察到：**圆不是背景，它真的是后来覆盖上去的前景绘制。**这就是 `drawWithContent()` 和 `drawBehind()` 最核心的能力差异。

`drawBehind()`：

```text
自定义绘制
↓
原始内容
```

而 `drawWithContent()`：

```text
你决定
↓
drawContent() 到底插在哪里
```

官方给出的典型案例也是这个思路，例如先 `drawContent()`，再在已经绘制好的 UI 上增加渐变遮罩。

---

#### 4. 第三组：不调用 `drawContent()` 会发生什么？

第三组是整个阶段最重要的小实验：

```kotlin
DrawOrderMode.HideContent -> {
    drawCircle(...)
    // 没有 drawContent()
}
```

运行以后，你应该会看到：

- Box 还在；
- Modifier 的尺寸还在；
- 紫色圆还正常绘制；
- **但是 Box 里面的 Text 消失了。**

这里很容易第一次产生一个误解：“是不是 Text 没有 Composition？” “是不是 Text 没有 Layout？” 都不是。`drawWithContent()` 属于 Draw 阶段。Compose 的 Composition、Measurement、Placement 等工作此前仍然可以正常发生；只是到了这个节点的绘制阶段，你没有执行：

```kotlin
drawContent()
```

于是原本应该继续绘制的内容没有被画出来。官方文档也特别提醒：如果不调用 `drawContent()`，实际 Composable 内容就不会被渲染出来。所以一定不要把：

```kotlin
drawContent()
```

理解成：“调用子 Composable。” 也不要理解成：“触发子组件重组。” 它只是**绘制阶段中的内容绘制操作**。我们前面学 Compose 状态的时候一直区分：

```text
Composition
Layout
Draw
```

这里正在操作的是最后的 **Draw**。官方当前的 Modifier phase 文档也将 `drawWithContent` 明确列在 Drawing phase，并指出其中可以利用 `drawContent()` 控制绘制顺序。

#### 5. `ContentDrawScope` 到底比 `DrawScope` 多解决了什么？

第一阶段：

```kotlin
.drawBehind {
    // this = DrawScope
}
```

你关注的是：“我能画什么？” 所以你使用：

```kotlin
drawCircle()
drawRect()
drawPath()
size
center
```

第二阶段：

```kotlin
.drawWithContent {
    // this = ContentDrawScope
}
```

这些东西仍然都能用。但是现在多出来一个核心能力：

```kotlin
drawContent()
```

所以你的问题从：“我能画什么？” 升级成：“我的东西和原始内容应该以什么顺序画？” 可以把两者的心智模型记成：

```text
DrawScope
├── size
├── center
├── drawCircle()
├── drawRect()
├── drawPath()
└── ...

ContentDrawScope
├── 上面的绘图能力
└── drawContent()
```

这就是为什么 API 叫：

```kotlin
drawWithContent
```

而不是类似 `drawForeground`。因为它并没有固定要求你画前景。**它真正给你的能力是把“content”也纳入自己的绘制流程。**

---

#### 6. 于是你现在已经能推导 `drawBehind()` 了

第一阶段我们只是告诉你：

```kotlin
drawBehind {
    drawCircle(...)
}
```

会先画圆，再画内容。现在你已经可以从机制上理解它为什么能够这么工作。从使用心智模型上，可以把它近似理解成：

```kotlin
drawWithContent {
    // 你的 drawBehind 代码
    drawCircle(...)
    // Compose 随后绘制内容
    drawContent()
}
```

所以：

```kotlin
drawBehind { ... }
```

本质上是在表达一个已经固定好的策略：**“我的自定义内容永远在原始内容后面。”** 而：

```kotlin
drawWithContent { ... }
```

则把这个策略取消掉：**“顺序我自己定。”** 这也是官方为什么把 `drawWithContent` 称为基础 drawing modifier，而把 `drawBehind` 描述成更方便的封装。

---

#### 7. 真正开发时什么时候需要 `drawWithContent()`？

不要因为它能力更强，就所有地方都用它。如果你只是画：

```text
自定义背景
装饰底纹
背景网格
背景 Path
底部装饰线
```

而它们永远位于内容下面，那么：

```kotlin
drawBehind
```

更合适。真正应该想到 `drawWithContent()` 的，是这种需求：

```text
原始 UI
     ↓
再覆盖我画的东西
```

例如：

- 图片上的渐变遮罩；
- UI 上方的高亮区域；
- 内容边缘的渐隐效果；
- 自定义前景蒙层；
- 某些 Spotlight / Flashlight 效果；
- 需要同时“先画一点 → 内容 → 再画一点”的复杂绘制。

甚至完全可以：

```kotlin
.drawWithContent {
    // 背景
    drawRect(...)
    // 原始内容
    drawContent()
    // 前景
    drawCircle(...)
}
```

这样一个 Modifier 就拥有三层关系：

```text
最后画：前景自定义绘制
────────────────────
中间画：drawContent()
────────────────────
最先画：背景自定义绘制
```

这才是 `drawWithContent()` 最完整的价值。

#### 8 你这个偶然加出的边框，正好验证了 `drawContent()` 到底画了什么

你的核心判断是对的，而且这个实验非常值钱。现在这条 Modifier 链是：

```kotlin
Modifier
    .drawWithContent { ... }
    .border(1.dp, Color.Red)
```

这里的 `border()` 位于 `drawWithContent()` **后面，也就是它内部的后续 Modifier 链的一部分**。因此在 `drawWithContent` 看来，`drawContent()` 并不只是把 `Box` 里面那个 `Text` 画出来，而是会继续绘制后面的 Modifier 和最终内容。可以先建立这个模型：

```text
drawWithContent
    │
    └── drawContent()
            ↓
        border()
            ↓
        Box / Text 内容
```

所以第三个 Case 不调用 `drawContent()` 时，**Text 和红色 `border` 一起消失**，正好证明这一点。你自己写在 `drawWithContent` 内部的灰色 `drawRoundRect()` 却还存在，因为它是当前这个 Draw Modifier 自己直接执行的绘制，与 `drawContent()` 无关。

A 的顺序确实是：

```text
灰色边框
→ 紫色圆
→ drawContent()
    → 红色 border
    → Text
```

所以红色边框后画，压在灰色边框上。B 则是：

```text
灰色边框
→ drawContent()
    → 红色 border
    → Text
→ 紫色圆
```

这里有一个小修正：**B 中紫色圆在绘制顺序上确实位于红色 border 上方。** 现在之所以看起来红色边框完全没被覆盖，只是因为这个圆在中间，根本没有碰到四周的 border。如果你把最后的圆换成：

```kotlin
drawRect(
    color = Color.Black.copy(alpha = 0.5f)
)
```

铺满整个区域，那么 B 中的红色 `border` 和 Text 都会一起被这层前景压住。所以你这次实验实际上提前摸到了第三阶段最核心的一条规律：**`drawContent()` 绘制的并不只是 Composable 的子内容，还包括当前 Draw Modifier 后面的 Modifier 绘制链。**这也是为什么第三阶段我们必须专门研究 **Modifier 顺序和嵌套层级**。你这个例子到那里可以直接继续用。

#### 第二阶段收束

这一阶段真正需要留下来的不是 API 语法，而是下面这个模型：

```text
drawBehind {
    A
}

≈

drawWithContent {
    A
    drawContent()
}
```

而 `drawWithContent()` 可以进一步变成：

```text
drawWithContent {
    A                 // 内容下面
    drawContent()     // 原始 Composable 内容
    B                 // 内容上面
}
```

最关键的一句话就是：**`drawContent()` 不是“获取内容”，而是在当前绘制流程中真正把内容画出来；它所在的位置，决定了原始内容和你的自定义绘制之间的覆盖顺序。**

把 `Sec03B_DrawWithContentOrder.kt` 三种效果亲手跑一遍以后，下一阶段我们就可以进入 6.3 最容易把人绕晕、但也最值得真正搞懂的部分：**多个 Modifier 连起来以后，这些 draw 到底怎么嵌套，为什么交换 Modifier 顺序会直接改变最终图层关系。**

### 第三阶段：Modifier 绘制链的嵌套关系——顺序为什么会改变最终结果

你刚才偶然加出来的 `border` 现象，确实已经碰到了这一阶段的核心。第二阶段我们只说了 `drawContent()` 会绘制“后续内容”，现在要把这个说法精确化：**对于一个 Draw Modifier，`drawContent()` 会继续向 Modifier 链的内部执行后续绘制节点，最终才到达 Composable 自己的内容。**

这一阶段不要把 Modifier 想成一串简单的“从上往下执行的函数”。更准确的心智模型是：**Modifier 链形成了一层套一层的包装关系。** 对绘制阶段而言，外层 Draw Modifier 调用 `drawContent()` 才会进入下一层；下一层完成后，控制权又会返回外层，因此可以形成“进去一次、出来一次”的绘制顺序。

#### 3.1 先建立一个最重要的 Modifier 链模型

假设有这样的结构：

```kotlin
Modifier
    .drawWithContent { /* A */ }
    .drawWithContent { /* B */ }
```

后面的 Composable 是 `Box`，里面还有一个 `Text`。绘制阶段可以先把它想成：

```text
A
└── B
    └── Box / Text
```

A 是外层 Draw Modifier，B 是它后面的内层 Draw Modifier。于是如果 A 调用：

```kotlin
drawContent()
```

它不是直接跳到 `Text`，而是首先进入 B。B 再调用自己的 `drawContent()`，才会继续进入真正的 Box 内容。所以：

```kotlin
.drawWithContent {
    // A before
    drawContent()
    // A after
}
.drawWithContent {
    // B before
    drawContent()
    // B after
}
```

最终真正的执行顺序应该是：

```text
A before
    B before
        Box / Text
    B after
A after
```

这个模型非常关键。**Modifier 写在前面并不等于它所有代码都一定先执行完；它可能先执行一半，通过 `drawContent()` 进入内部，等内部全部返回以后，再继续执行剩下的一半。**这和普通函数调用栈其实非常像。

#### 3.3 实验一：真正理解“进入内部，再返回外部”

运行以后，先看 Logcat。你应该反复看到这样的顺序：

```text
1. Outer BEFORE
2. Inner BEFORE
3. Inner AFTER
4. Outer AFTER
```

中间那个 `Box / Text` 没有打日志，但它实际上发生在：

```text
2. Inner BEFORE
    Box / Text 绘制
3. Inner AFTER
```

为什么会这样？从外层开始：

```kotlin
Log.d("Outer BEFORE")
drawContent()
Log.d("Outer AFTER")
```

执行到外层的 `drawContent()` 时，Compose 开始继续绘制**它后面的 Modifier 链**，因此进入第二个 `drawWithContent`：

```kotlin
Log.d("Inner BEFORE")
drawContent()
Log.d("Inner AFTER")
```

内层再调用 `drawContent()`，这一次后面已经没有其他 Draw Modifier，于是继续绘制真正的 `Box` 内容。Box 内容完成以后返回内层，因此执行 `Inner AFTER`；内层全部结束以后，再返回外层，最终执行 `Outer AFTER`。因此绘制关系实际是：

```text
Outer BEFORE
Inner BEFORE
真正的 Content
Inner AFTER
Outer AFTER
```

这就是 Modifier 绘制链最值得掌握的模型。视觉上你也可以验证这一点。外层最后画的蓝色边框一定处于最上面，因为它是整个调用链最后执行的绘制；内层的红色边框虽然也是在自己的 `drawContent()` 之后绘制，但完成以后还必须返回外层，所以最后仍然会被 `Outer AFTER` 的绘制压在下面。

#### 3.4 `drawContent()` 到底在调用谁？——理解整个 Draw Modifier 链的关键

先把最容易误导人的说法删掉：**`drawContent()` 不是“本来准备直接画 Text，然后检查前面还有没有其他绘制 Modifier”。** 更准确的理解是：

> `drawContent()` 的职责是：**继续执行当前 Draw Modifier 内侧的绘制链。**  
> 如果内侧还有另一个 Draw Modifier，就进入那个 Draw Modifier；如果已经没有 Draw Modifier，最终才会绘制真正的 Composable 内容。

例如：

```kotlin
Modifier
    .drawWithContent { /* Outer */ }
    .drawWithContent { /* Inner */ }
```

它们的嵌套关系是：

```text
Outer
└── Inner
    └── Box / Text
```

当 `Outer` 调用：

```kotlin
drawContent()
```

这一次调用的完整工作其实是：

```text
进入 Inner
Inner 自己执行代码
如果 Inner 调用 drawContent()
继续进入 Box / Text
Text 绘制完成
返回 Inner
Inner 执行 drawContent() 后面的代码
Inner 结束
返回 Outer
```

所以不存在“Inner 已经偷偷把 Text 画掉了，Outer 回来以后发现 Text 画过了，因此不再画”这种机制。**Outer 的那一次 `drawContent()` 本身就包含了整个 Inner → Content 的调用过程。** 当这个调用返回时，Outer 只是继续执行自己 `drawContent()` 后面的代码，没有第二次自动绘制 Text 的步骤。

这就解释了 `03C` 为什么是：

```text
Outer BEFORE
Outer.drawContent()
        Inner BEFORE
        Inner.drawContent()
                Text
        Inner AFTER
    ← Outer.drawContent() 返回
Outer AFTER
```

它本质上就是一层普通的嵌套调用。

---

现在回到 `03B`，你原来的 Modifier 是：

```kotlin
Modifier
    .drawWithContent { ... }
    .border(
        width = 1.dp,
        color = Color.Red
    )
```

这里可以理解为：

```text
你的 drawWithContent
└── border
    └── Text
```

而 `border` 本身也是参与绘制链的 Modifier。对于我们现在的应用层心智模型，可以把它近似理解成：

```kotlin
drawWithContent {
    drawContent()
    drawBorder()
}
```

也就是说，**`border` 并不是先画红框再画 Text，而是先继续绘制自己的内部内容，然后回来把 border 画在上面。** 这一点正好解释了你看到的红框总是在内容上方。

于是 03B 的 A，真正顺序是：

```text
你手写的灰色圆角边框
→ 蓝色圆
→ 外层 drawContent()
    → 进入 border
        → border 的 drawContent()
            → Text
        → 红色 border
→ 返回外层
```

也就是：

```text
灰色边框
蓝色圆
Text
红色 border
```

B 则是：

```text
灰色边框
→ 外层 drawContent()
    → Text
    → 红色 border
→ 蓝色圆
```

所以真正顺序是：

```text
灰色边框
Text
红色 border
蓝色圆
```

你之前判断“最后那个蓝色圆属于最上层”是完全正确的。截图中红色 border 看起来没有被它盖住，只是因为圆在中间，没有碰到四周的 border；如果最后画一个铺满整个区域的半透明 `drawRect()`，红色 border 也会被覆盖。

C 则最简单：

```text
灰色边框
→ 蓝色圆
→ 不调用 drawContent()
→ 当前 drawWithContent 结束
```

因为没有调用 `drawContent()`，绘制流程根本没有进入：

```text
border
└── Text
```

所以**后面的红色 `border` 和 Text 都完全不会执行。**

---

最关键的实验就是你说的另一种情况：

```kotlin
Modifier
    .border(
        width = 1.dp,
        color = Color.Red
    )
    .drawWithContent {
        ...
        // C 中不调用 drawContent()
    }
```

现在嵌套关系反过来了：

```text
border
└── 你的 drawWithContent
    └── Text
```

C 为什么即使不调用 `drawContent()`，红色 border 仍然出现，而且还是最后出现？

因为真正的过程是：

```text
先进入外层 border
    ↓
border 调用自己的 drawContent()
    ↓
进入你的 drawWithContent
    ↓
画灰色圆角边框
    ↓
画蓝色圆
    ↓
你没有调用 drawContent()
所以 Text 被截断
    ↓
你的 drawWithContent 返回
    ↓
border 的 drawContent() 返回
    ↓
border 继续执行自己的剩余绘制
    ↓
最后画红色 border
```

所以最终：

```text
灰色边框
蓝色圆
红色 border
```

这就是你觉得最反直觉的地方：**`border` 写在前面，并不意味着它的“红色线条”一定先画。**

它写在前面意味着它是**外层 Modifier**。外层 Modifier 可以先进入，然后把内部整套绘制执行完，最后回来再画自己的东西。`border` 恰好就是这种行为，所以它虽然是最先进入的 Modifier，却可以是最后真正把边框像素画到画布上的那个。

到这里可以把整个第三阶段最核心的一句话改成：

> **Modifier 的书写顺序首先决定“谁包着谁”，而不是简单决定“谁的像素先画”。真正的像素绘制顺序，还取决于每个 Draw Modifier 在调用 `drawContent()` 之前画什么、之后又画什么。**

因此，看到：

```kotlin
A
    .B()
    .C()
```

不要简单理解成：

```text
先画 B
再画 C
```

而应该先想：

```text
B
└── C
    └── Content
```

然后再根据 B、C 各自的 `drawContent()` 在什么位置，推导最终绘制顺序。

#### 3.6 为什么 `padding` 的顺序甚至会改变 `DrawScope.size`

绘制顺序只是 Modifier 顺序影响的一部分。第二个实验更加接近日常 Compose 开发，因为它把 Draw Modifier 和 Layout Modifier 混在了一起。

第一种：

```kotlin
Modifier
    .size(240.dp, 110.dp)
    .drawBehind { ... }
    .padding(20.dp)
```

可以理解成：

```text
240 × 110 的区域
└── drawBehind
    └── padding 20dp
        └── Content
```

所以 `drawBehind` 位于 `padding` 外层。它看到的是 padding 发生之前的整个区域，因此蓝色背景会覆盖完整的 `240dp × 110dp`。

第二种：

```kotlin
Modifier
    .size(240.dp, 110.dp)
    .padding(20.dp)
    .drawBehind { ... }
```

变成：

```text
240 × 110 的区域
└── padding 20dp
    └── drawBehind
        └── Content
```

`drawBehind` 已经进入 padding 内部，所以它获得的是被四周 20dp 压缩后的内部区域。你会直接看到第二块蓝色区域明显更小，Logcat 中 B 的 `size.width` 和 `size.height` 也会小于 A。

这里特别重要的一点是：**Modifier 顺序改变的不只是“谁覆盖谁”，它还可能改变某个 Draw Modifier 实际拥有的坐标空间和尺寸。**

所以你以前已经知道：

```kotlin
padding()
size()
width()
```

顺序不同会影响布局结果；现在只是在这个已有经验上继续往前一步：**布局 Modifier 还会进一步影响它内侧 Draw Modifier 所看到的 `DrawScope.size`。**

#### 3.7 不要把 Modifier 链理解成简单的 Z 轴列表

学到这里以后，很容易把 Modifier 链粗暴理解成：

```text
第一个 Modifier = 最外层
第二个 Modifier = 第二层
第三个 Modifier = 第三层
```

这个说法作为入门直觉有帮助，但还不够精确。真正重要的是：**不同 Modifier 会参与不同阶段。**例如：

```kotlin
padding()
```

主要参与 Layout；

```kotlin
drawBehind()
drawWithContent()
border()
```

会参与 Draw；而同一个 Modifier 链在不同阶段会按照各自规则工作。

所以现阶段不要试图总结成一句“所有 Modifier 永远按照某个固定方向执行”。我们只需要牢牢掌握这一节真正有用的规则：

> 对 Draw Modifier 来说，`drawContent()` 就像一扇进入内部 Modifier 链的门；调用它，就继续绘制后面的 Draw Modifier 和最终 Composable 内容；不调用它，当前节点之后的绘制链就不会继续。

而如果 `drawContent()` 之后还有代码，那么等内部绘制完成后，控制权会返回当前 Modifier，再继续执行后面的绘制操作。

#### 3.8 第三阶段收束

这一阶段最终需要留下两个模型。第一个是纯 Draw Modifier 嵌套：

```text
Outer BEFORE
    Inner BEFORE
        Content
    Inner AFTER
Outer AFTER
```

第二个是 Layout Modifier 和 Draw Modifier 混合以后：

```text
Modifier 的位置
    ↓
决定它处于哪个内外层
    ↓
可能改变绘制顺序
也可能改变 DrawScope 实际获得的尺寸和坐标空间
```

你第二阶段无意间加进去的 `border`，其实正好提前证明了第一条：**`drawContent()` 所代表的“content”不是单纯那个 `Text`，而是当前 Draw Modifier 后面的整段绘制链，最终才到真正的 Composable 内容。**

这一阶段把 `Sec03C_ModifierDrawingLayers.kt` 跑通，尤其亲眼确认 `Outer BEFORE → Inner BEFORE → Inner AFTER → Outer AFTER` 的日志顺序以后，这套模型就算真正建立起来了。下一阶段才进入另一个完全不同的问题：`drawWithCache()` 到底缓存什么，以及它为什么不是“把 Canvas 画面缓存起来”。

### 第四阶段：`drawWithCache()` —— 把“构建绘制资源”和“真正执行绘制”彻底分开

前三个阶段解决的是**绘制顺序和 Modifier 绘制链**。从这一阶段开始，问题发生变化：假设我们已经知道什么时候画、画在谁前面，但某些绘制资源本身创建成本不低，例如 `Path`、`Brush`、Shader、文字测量结果。如果把这些对象直接创建在 `drawBehind {}` 或 `drawWithContent {}` 中，那么每次该节点重新绘制时，都可能重新执行对象创建。

`drawWithCache()` 的核心价值不是“换一种方式画东西”，而是把一次绘制拆成两个生命周期完全不同的部分：

```text
Cache Build
    │
    │  创建、计算可以复用的绘制资源
    │  Path / Brush / 几何计算结果……
    │
    ▼
得到一个 DrawResult
    │
    │  缓存仍有效时，不再重复 Build
    │
    ▼
Draw
    │
    │  每次真正需要重新绘制时执行
    ▼
把缓存资源真正画到 Canvas 上
```

官方当前文档对这个边界说得很明确：`drawWithCache` 外层构建块负责缓存绘制对象；只要绘制区域尺寸不变、它读取的状态没有变化，这些对象就可以跨多次 draw 复用，而 `onDrawBehind` / `onDrawWithContent` 中的真正绘制代码仍然会在需要绘制时执行。([Android Developers][1])

这一阶段真正需要搞懂三个问题：**什么被缓存、什么时候重新 Build、状态到底应该读在外层还是内层。**

---

#### 4.1 先看 `drawWithCache` 的结构：外层根本不是普通的“每帧绘制 lambda”

先看最典型的结构：

```kotlin
Modifier.drawWithCache {

    val path = Path()
    val brush = Brush.linearGradient(...)

    onDrawBehind {
        drawPath(
            path = path,
            brush = brush
        )
    }
}
```

第一眼很容易把它理解成：

```text
drawWithCache {
    创建 Path
    创建 Brush
    画 Path
}
```

但这恰恰是最应该避免的错误心智模型。实际上存在两个不同的执行层级：

```kotlin
Modifier.drawWithCache {
    // 第一层：Cache Build
    val path = Path()
    val brush = Brush.linearGradient(...)

    onDrawBehind {
        // 第二层：真正的 Draw
        drawPath(
            path = path,
            brush = brush
        )
    }
}
```

第一次需要绘制时，可以近似理解为：

```text
① 执行 Cache Build
   创建 path
   创建 brush

② Cache Build 产生 DrawResult

③ 执行 DrawResult
   drawPath(path, brush)
```

第二次发生 redraw，而缓存仍然有效时：

```text
① 不再执行 Cache Build

② 直接使用之前保存的 DrawResult

③ drawPath(之前那个 path, 之前那个 brush)
```

所以 `drawWithCache()` **绝对不是“不再重新绘制”**。它优化的是某些绘制资源的重复构建，而不是把最终像素截图保存起来。这是这一节第一条最重要的边界。

---

#### 4.2 它缓存的不是 Canvas 结果，而是 Draw 阶段要反复使用的资源

假设你原来这么写：

```kotlin
Modifier.drawBehind {
    
    val brush = Brush.linearGradient(
        colors = listOf(
            Color.Blue,
            Color.Cyan
        ),
        end = Offset(
            x = size.width,
            y = size.height
        )
    )

    drawRect(
        brush = brush
    )
}
```

只要这个 Draw Modifier 被要求重新绘制，这整个 lambda 都会再次执行。所以 `Brush.linearGradient(...)` 也位于 Draw 执行路径上。而：

```kotlin
Modifier.drawWithCache {

    val brush = Brush.linearGradient(
        colors = listOf(
            Color.Blue,
            Color.Cyan
        ),
        end = Offset(
            x = size.width,
            y = size.height
        )
    )

    onDrawBehind {
        drawRect(
            brush = brush
        )
    }
}
```

现在 `Brush` 创建发生在 Cache Build，而真正的：

```kotlin
drawRect(...)
```

发生在 Draw。因此最准确的说法不是：`drawWithCache` 缓存绘制。而是：**`drawWithCache` 允许你把能够跨多次 Draw 复用的计算结果和对象，从高频 Draw 路径中提出来。**

像下面这些东西才是典型的缓存对象：

```text
Path
Brush
Shader 相关对象
复杂几何计算结果
TextLayoutResult
与当前 size 绑定的绘制辅助对象
```

反过来，如果里面只是：

```kotlin
drawCircle(
    color = Color.Red,
    radius = 20.dp.toPx()
)
```

根本没有值得保存的对象或昂贵计算，那么为了“优化”强行改成 `drawWithCache()` 并没有意义。官方也明确提醒：没有需要缓存的对象时使用 `drawWithCache`，反而会产生不必要的 lambda 等开销。([Android Developers][1])

---

#### 4.3 可运行示例：`Sec03D_DrawWithCacheLifecycle.kt`

这次示例重点不是画漂亮 UI，而是**把 Cache Build 和 Draw 的生命周期直接用 Logcat 撕开给你看**。而且三个按钮分别验证三个不同问题：

1. 只改变 Draw 阶段读取的状态；
2. 改变 Cache Build 阶段读取的状态；
3. 改变绘制区域尺寸。

```kotlin
private class DrawCacheDebugCounter {
    var buildCount = 0
    var drawCount = 0
}

@Composable
fun Sec03D_DrawWithCacheLifecycle() {

    // 只在真正 Draw 时读取
    val circlePosition = remember {
        mutableFloatStateOf(0.25f)
    }

    // 在 Cache Build 中读取
    val gradientVariant = remember {
        mutableIntStateOf(0)
    }

    // 用于改变组件尺寸
    var expanded by remember {
        mutableStateOf(false)
    }

    // 普通 Kotlin 对象，只用来记录日志次数，
    // 故意不用 Compose State，避免它自己参与失效机制
    val counter = remember {
        DrawCacheDebugCounter()
    }

    Scaffold { innerPadding ->

        Column(
            modifier = Modifier
                .fillMaxSize()
                .padding(innerPadding)
                .padding(24.dp),
            verticalArrangement = Arrangement.spacedBy(16.dp)
        ) {

            Text(
                text = "drawWithCache 生命周期",
                style = MaterialTheme.typography.headlineSmall
            )

            Button(
                onClick = {
                    circlePosition.floatValue =
                        if (circlePosition.floatValue < 0.5f) {
                            0.75f
                        } else {
                            0.25f
                        }
                }
            ) {
                Text("1. 移动圆：只触发 Draw")
            }

            Button(
                onClick = {
                    gradientVariant.intValue =
                        if (gradientVariant.intValue == 0) 1 else 0
                }
            ) {
                Text("2. 切换渐变：使 Cache 失效")
            }

            Button(
                onClick = {
                    expanded = !expanded
                }
            ) {
                Text("3. 改变尺寸")
            }

            Box(
                modifier = Modifier
                    .width(
                        if (expanded) 320.dp else 240.dp
                    )
                    .height(180.dp)
                    .drawWithCache {

                        counter.buildCount++

                        /*
                         * 关键：
                         * gradientVariant 在 Cache Build 中读取。
                         */
                        val variant = gradientVariant.intValue

                        val gradientBrush =
                            if (variant == 0) {
                                Brush.linearGradient(
                                    colors = listOf(
                                        Color(0xFF7986CB),
                                        Color(0xFF80CBC4)
                                    ),
                                    start = Offset.Zero,
                                    end = Offset(
                                        x = size.width,
                                        y = size.height
                                    )
                                )
                            } else {
                                Brush.linearGradient(
                                    colors = listOf(
                                        Color(0xFFEF9A9A),
                                        Color(0xFFFFCC80)
                                    ),
                                    start = Offset.Zero,
                                    end = Offset(
                                        x = size.width,
                                        y = size.height
                                    )
                                )
                            }

                        /*
                         * Path 同样只在 Cache Build 时创建，
                         * 而且它依赖当前 size。
                         */
                        val decorationPath = Path().apply {
                            moveTo(
                                x = 0f,
                                y = size.height * 0.72f
                            )

                            quadraticBezierTo(
                                x1 = size.width * 0.5f,
                                y1 = size.height * 0.42f,
                                x2 = size.width,
                                y2 = size.height * 0.72f
                            )

                            lineTo(
                                x = size.width,
                                y = size.height
                            )

                            lineTo(
                                x = 0f,
                                y = size.height
                            )

                            close()
                        }

                        Log.d(
                            "Sec03D",
                            "CACHE BUILD #${counter.buildCount}, " +
                                "variant=$variant, size=$size"
                        )

                        onDrawWithContent {
                            counter.drawCount++

                            /*
                             * 注意：
                             * circlePosition 到这里才读取。
                             */
                            val position =
                                circlePosition.floatValue

                            Log.d(
                                "Sec03D",
                                "DRAW #${counter.drawCount}, " +
                                    "circlePosition=$position"
                            )

                            drawRect(
                                brush = gradientBrush
                            )

                            drawPath(
                                path = decorationPath,
                                color = Color.White.copy(
                                    alpha = 0.22f
                                )
                            )

                            drawContent()

                            drawCircle(
                                color = Color.White,
                                radius = 14.dp.toPx(),
                                center = Offset(
                                    x = size.width * position,
                                    y = size.height * 0.28f
                                )
                            )
                        }
                    },
                contentAlignment = Alignment.Center
            ) {

                Text(
                    text = "Cached Drawing",
                    color = Color.White,
                    style = MaterialTheme.typography.titleMedium
                )
            }
        }
    }
}
```

第一次打开页面时，先不要点按钮。Logcat 过滤：

```text
Sec03D
```

核心现象应该类似：

```text

DRAW #1, circlePosition=0.25
```

系统实际环境可能产生额外 Draw，所以不要死记具体 `DRAW #几`；我们要观察的是**哪一类日志增加**。

#### 4.4 第一个实验最关键：改变 Draw 状态，为什么不用重新构建 Cache？

点击：

```text
1. 移动圆：只触发 Draw
```

你会看到圆从左边移动到右边。关键看 Logcat，理想的核心现象是：

```text
DRAW #2, circlePosition=0.75
```

而不会因为这个状态变化重新出现：

```text
CACHE BUILD #2
```

为什么？因为：

```kotlin
val position = circlePosition.floatValue
```

发生在：

```kotlin
onDrawWithContent {
    ...
}
```

里面。也就是说 `circlePosition` 是 **Draw 阶段依赖**：

```text
circlePosition 改变
        ↓
当前绘制结果已经过期
        ↓
重新 Draw
        ↓
继续复用 gradientBrush
继续复用 decorationPath
```

这里特别值得和你以前学的 Compose 状态机制连接起来。状态读取发生在哪个阶段，会决定这个状态变化需要让 Compose 从哪个阶段重新开始。官方当前性能文档明确指出，在 Drawing Modifier 的绘制 lambda 中读取状态，可以跳过 Composition 和 Layout，只重新执行 Drawing。([Android Developers][2])

因此我们的第一个按钮不是单纯为了让圆移动，而是在证明：**一个状态可以参与每次绘制，却完全没有必要成为 Cache 的失效条件。**

这在以后做动画、自定义手势绘制时非常重要。比如一个圆的位置每帧都变化，但复杂背景 `Path` 完全没变化。你绝对不希望“圆移动一下 → 整个 Path 重新构建”。

---

#### 4.5 第二个实验：状态读在 Cache Build 中，意义完全不同

现在点击：

```text
2. 切换渐变：使 Cache 失效
```

这次 `gradientVariant` 发生变化，而它是在外层读取的：

```kotlin
.drawWithCache {
    val variant = gradientVariant.intValue
    ...
}
```

所以它不是普通 Draw 依赖，而是 **Cache Build 的依赖**。这次你应该看到类似：

```text
CACHE BUILD #2, variant=1, size=...
DRAW #3, circlePosition=...
```

为什么既 Build 又 Draw？因为以前缓存的资源是：

```text
gradientVariant = 0
    ↓
gradientBrush A
```

现在状态已经变成：

```text
gradientVariant = 1
```

如果继续使用旧 `gradientBrush`，画面显然是错的。因此 Compose 发现 Cache Build 中读取过的 Snapshot State 发生变化，会把当前 Draw Cache 标记为失效。下一次需要绘制时，首先重新执行 Cache Build：

```text
旧 Cache 失效
      ↓
重新执行 drawWithCache 外层 block
      ↓
得到新的 Brush / Path / DrawResult
      ↓
执行新的 DrawResult
```

官方 API 文档对这一点的定义就是：**只要绘制区域尺寸保持不变，并且构建缓存时读取的状态没有变化，缓存内容就能够跨 draw calls 保存；读取状态发生改变后，会重新建立用于绘制的对象。**([Android Developers][3])

这里出现了一个非常重要的规则：

```text
状态在哪里读
不是代码风格问题
而是在声明：“这个状态变化应该使什么东西失效？”
```

读在 Cache Build：

```kotlin
drawWithCache {
    val value = state.value
    ...
}
```

意味着：value 一旦变化，我之前构建的缓存资源可能已经不正确，请重新 Build。读在真正 Draw：

```kotlin
drawWithCache {
    val cachedObject = ...
    onDrawBehind {
        val value = state.value
        ...
    }
}
```

意味着：缓存资源本身仍然有效，只需要使用新的 value 再画一次。这是 `drawWithCache` 最重要、也是最容易被一句“它可以缓存 Brush”掩盖掉的机制。

---

#### 4.6 一个非常典型的错误：把高频动画状态读错地方

假设以后你有：

```kotlin
val progress: Float
```

它每帧从：

```text
0.00
0.01
0.02
...
1.00
```

不断变化。如果写成：

```kotlin
Modifier.drawWithCache {
    val currentProgress = progressState.floatValue
    val path = buildExpensivePath(size)

    onDrawBehind {
        drawPath(
            path = path,
            color = Color.Blue
        )

        drawCircle(
            center = Offset(
                x = size.width * currentProgress,
                y = center.y
            ),
            radius = 10.dp.toPx(),
            color = Color.White
        )
    }
}
```

虽然 `path` 本身完全没有变化，但由于 `progressState` 在 **Cache Build** 中读取：

```text
progress 改变
Cache 失效
重新 buildExpensivePath()
Draw
```

如果是 60 FPS 动画，理论上你刚刚想缓存掉的昂贵构建工作，又可能跟着动画不断重建。正确思路是：

```kotlin
Modifier.drawWithCache {
    val path = buildExpensivePath(size)

    onDrawBehind {
        val currentProgress = progressState.floatValue

        drawPath(
            path = path,
            color = Color.Blue
        )

        drawCircle(
            center = Offset(
                x = size.width * currentProgress,
                y = center.y
            ),
            radius = 10.dp.toPx(),
            color = Color.White
        )
    }
}
```

现在关系变成：

```text
size 改变
Path 已经不适用于新尺寸
重新 Build Path
```

但：

```text
progress 改变
Path 完全还能用
只重新 Draw
```

这一点以后对 Canvas 动画、图表、拖拽、进度效果非常实用。**`drawWithCache` 真正的优化能力来自正确划分“稳定资源”和“每次 Draw 才变化的数据”。**

#### 4.7 第三个实验：为什么 `size` 天然就是 Cache 的边界？

再点击：

```text
3. 改变尺寸
```

Box 从：

```kotlin
240.dp
```

变成：

```kotlin
320.dp
```

你会重新看到 Cache Build 日志。这是必须发生的，因为我们缓存的东西明显依赖：

```kotlin
size
```

例如：

```kotlin
end = Offset(
    x = size.width,
    y = size.height
)
```

以及：

```kotlin
quadraticBezierTo(
    x1 = size.width * 0.5f,
    ...
)
```

假如组件从 240dp 变成 320dp，还继续拿旧 Path 和旧渐变范围绘制，那么缓存本身已经失去正确性。

因此 `drawWithCache` 会把绘制区域的尺寸作为 Cache 生命周期的重要边界。官方 API 直接规定：绘**制区域大小变化时，会重新调用缓存构建逻辑。**([Android Developers][3])

所以你可以把目前的 Cache key 心智模型先建立成：

```text
Cache 是否还能用？

        ┌── size 是否仍然相同？
        │
        ├── Cache Build 中读取的 State 是否仍然相同？
        │
        └── 当前 Modifier cache 本身是否仍然有效？
                    ↓
              是 → 继续复用
              否 → 重新 Build
```

最后一项涉及 Modifier Node 本身的缓存失效机制，我们 6.3 不需要立刻下钻源码；应用开发层最应该主动控制和理解的是前两项。

---

#### 4.8 `onDrawBehind` 和 `onDrawWithContent` 到底是什么？

这里千万不要把它们理解成“另外两个缓存 API”。它们首先负责给 Cache Build 返回一个 **DrawResult**，也就是：“缓存构建完了，以后真正 Draw 的时候，请执行这一段绘制逻辑。” 因此：

```kotlin
drawWithCache {
    val path = ...

    onDrawBehind {
        drawPath(path, ...)
    }
}
```

可以理解为：

```text
Build：
    创建 path
    创建未来要执行的绘制逻辑

以后每次 Draw：
    drawPath(path)
    然后正常绘制 content
```

它的绘制顺序语义对应你已经学过的 `drawBehind()`。如果需要控制内容前后关系，则使用：

```kotlin
drawWithCache {
    val path = ...

    onDrawWithContent {
        drawContent()
        drawPath(
            path = path,
            color = Color.Red
        )
    }
}
```

这里的心智模型直接继承第三阶段：

```text
Cache Build
    ↓
缓存 path
    ↓
得到 onDrawWithContent 的 DrawResult


真正 Draw
    ↓
drawContent()
    ↓
进入内侧 Modifier 绘制链
    ↓
返回
    ↓
drawPath()
```

所以第三阶段关于 `drawContent()`、Draw Modifier 嵌套链的知识没有作废。`drawWithCache` 只是在外面再增加了一层“**DrawResult 构建与复用机制**”。可以把三个 API 的关系逐渐统一起来：

```text
drawBehind
    └── 直接进行 behind 绘制

drawWithContent
    └── 直接进行 Draw 并自己控制 drawContent()

drawWithCache
    ├── 先构建/缓存绘制资源
    │
    └── DrawResult
        ├── onDrawBehind
        └── onDrawWithContent
```

因此 `drawWithCache` 并不是替代前两个 API，而是在**需要缓存绘制资源**的时候，把同样的绘制顺序能力放进 Cache 机制里。官方目前也是按照这个关系介绍三者的。([Android Developers][1])

---

#### 4.9 `drawWithCache` 与 `remember` 最容易混淆的地方

你已经学过 `remember`，所以这里必须把边界提前讲清楚，但不需要展开成兄弟 API 大比较。理论上可以：

```kotlin
val path = remember {
    Path()
}
```

然后：

```kotlin
Modifier.drawBehind {
    ...
}
```

所以问题自然来了：那我为什么不能全部 `remember`，非要 `drawWithCache`？

核心差别之一就是：**很多绘制资源依赖最终的 DrawScope 信息，而这些信息直到布局/绘制环境建立以后才真正合适使用。**例如：

```kotlin
size.width
size.height
```

是绘制区域尺寸。这样的资源：

```kotlin
val path = Path().apply {
    lineTo(size.width, ...)
}
```

天然适合：

```kotlin
drawWithCache {
    val path = ...
}
```

因为 `CacheDrawScope` 就提供了当前绘制尺寸，并且尺寸变化时自动让缓存失效。如果自己用 `remember` 管：

```kotlin
remember(width, height) {
    ...
}
```

首先你需要提前把绘制尺寸传回 Composition；其次还得自己设计依赖 key。对于**纯粹服务于绘制阶段的资源**，这往往是在把 Draw 层的问题强行搬回 Composition。

所以现在可以先记住这个边界：**业务/UI 状态和跨 Composition 保存的普通对象仍然是 `remember` 的领域；与当前绘制尺寸、绘制环境强绑定，只为 Draw 服务的昂贵对象，优先考虑 `drawWithCache`。**

第五阶段我们还会专门处理“哪些东西值得缓存、哪些东西不值得缓存”，这里先不要扩大。

---

#### 4.10 第四阶段最终运行模型

这一阶段最值得长期留下来的不是 `drawWithCache` 的语法，而是下面这个模型：

```text
第一次需要 Draw
        ↓
Cache 是否有效？
        ↓
       否
        ↓
执行 Cache Build
        │
        ├── 读取 size
        ├── 读取 Cache 依赖 State
        ├── 创建 Path / Brush / ...
        │
        └── 创建 DrawResult
                ↓
             执行 Draw


下一次需要 Draw
        ↓
Cache 是否有效？
        ↓
       是
        ↓
跳过 Cache Build
        ↓
直接复用原来的 DrawResult
        ↓
执行 Draw
```

而一旦：

```text
size 改变
```

或者：

```text
Cache Build 中读取的 State 改变
```

那么：

```text
Cache 失效
    ↓
重新 Build
    ↓
得到新的缓存资源
    ↓
再 Draw
```

与之相反，如果状态只在：

```kotlin
onDrawBehind { }
```

或：

```kotlin
onDrawWithContent { }
```

中读取，那么它首先是 **Draw 依赖**：状态变化需要重新绘制，但不必因此重新创建缓存资源。

所以这一阶段最核心的一句话可以定成：

> **`drawWithCache` 的本质不是“缓存画面”，而是把低频的绘制资源构建和高频的真正 Draw 分离；把状态读在哪一层，就是在决定这个状态变化只需要 Redraw，还是必须连 Cache 一起重建。**

`Sec03D_DrawWithCacheLifecycle.kt` 最值得你认真观察的是前两个按钮。只要你能在 Logcat 中亲自确认“移动圆只有 `DRAW`，切换渐变出现 `CACHE BUILD + DRAW`”，这一阶段最核心的运行机制就真正落地了。

### 第五阶段：Cache 优化的正确边界——什么该缓存，什么绝对不该塞进 Cache

上一阶段解决的是 `drawWithCache()` 的运行机制：外层是 Cache Build，`onDrawBehind` / `onDrawWithContent` 是真正的 Draw；尺寸变化或者 Cache Build 中读取的状态变化，会使缓存重新构建。这一阶段不再重复这个机制，而是解决更实际也更难的问题：**知道机制以后，怎么判断一段数据究竟应该放在 Cache Build，还是应该留在每次 Draw 中？**

这里最容易犯的错误不是“忘了用缓存”，而是**缓存边界划错了**。一个高频变化的状态只要被读进 Cache Build，就可能导致整块 Cache 跟着高频失效；反过来，如果某个昂贵几何结果本来只依赖尺寸和低频数据，却每次 Draw 都重新创建，也是在浪费性能。官方对 `drawWithCache` 的定位非常明确：它主要是为了复用 `Brush`、`Shader`、`Path` 等绘制对象，而且只有在确实存在需要缓存的对象时才值得使用。([Android Developers][1])

#### 5.1 Cache 的真正设计问题：不是“这个值会不会变化”，而是“它变化时，哪些东西真的必须重建”

先看一个非常典型的真实场景：你有一张折线图，图形本身根据组件尺寸计算出完整 `Path`，然后播放一段“从左到右逐渐显示”的动画。

这里同时存在两类数据。完整折线 `Path` 只依赖绘制区域 `size`，只要尺寸没变，它完全可以一直复用；而动画 `progress` 可能在 1.5 秒内从 `0f` 连续变化到 `1f`，属于典型的高频 Draw 数据。

正确的依赖关系应该是：

```text
size / 图表数据
        ↓
   构建完整 Path
        ↓
      Cache


progress
   ↓
每一帧 Draw
   ↓
决定现在显示 Path 的哪一部分
```

如果把 `progress` 错误地读进 Cache Build，问题就出现了：虽然 `Path` 根本没有因为 progress 改变而发生本质变化，但整个 Cache Build 都会被判定为失效，于是连 `Path` 也跟着重新创建。

而且这里有一个比上一阶段更重要的细节：**`drawWithCache` 并不会聪明到逐个分析外层 block 里的每一个 `val`，然后只重建依赖变化状态的那个变量。外层 Cache Build 一旦失效，这个 block 就会重新执行。**

所以一个放错位置的高频状态，会把同一个 Cache Build 中本来完全稳定的昂贵对象一起拖下水。下面直接用代码验证这个问题。

#### 5.2 可运行示例：`Sec03E_DrawCacheInvalidation.kt`

这个例子同时画两张完全相同的折线图。上面的 BAD 写法故意把动画状态读进 Cache Build；下面的 GOOD 写法缓存完整 `Path`，而只在真正 Draw 时读取动画进度。UI 效果基本相同，但 Logcat 中的 Cache Build 次数会完全不同。

                x = 0f,

                x = size.width,
                y = y
            )
        }
    }
}

#### 5.3 BAD 为什么危险：一个高频状态让整个 Cache Build 失去意义

BAD 的关键代码只有这一句：

```kotlin
.drawWithCache {
    val progress = progressState.value
    val gridPath = buildGridPath(size)
    val chartPath = buildChartPath(size)
    ...
}
```

动画运行以后，`progress` 会连续变化：

```text
0.00
0.03
0.07
0.11
...
1.00
```

由于 `progressState.value` 是在 Cache Build 中被读取的，每次这个状态发生变化，当前 Cache 都不再有效。于是 Logcat 会出现大量类似：

```text
BAD CACHE BUILD #2, progress=0.03
BAD CACHE BUILD #3, progress=0.07
BAD CACHE BUILD #4, progress=0.11
...
```

关键问题并不是计算：

```kotlin
size.width * progress
```

有多昂贵，这个乘法几乎不值得讨论。真正的问题是，因为这一行状态读取发生在 Cache Build，下面这些东西：

```kotlin
buildGridPath(size)
buildChartPath(size)
```

也跟着一遍遍执行。也就是说：

```text
progress 改变
    ↓
Cache Build 整体失效
    ↓
重新创建 gridPath
重新创建 chartPath
重新计算 revealRight
    ↓
Draw
```

而事实上 `progress` 根本没有改变 `gridPath` 和 `chartPath` 的几何结构。这就是缓存边界划错以后最典型的问题：**真正昂贵而稳定的资源，被一个廉价但高频变化的变量拖着一起重建。**

---

#### 5.4 GOOD 的核心不是“少读一次状态”，而是把依赖关系设计正确

GOOD 写法中：

```kotlin
.drawWithCache {
    val gridPath = buildGridPath(size)
    val chartPath = buildChartPath(size)
    onDrawBehind {
        val progress = progressState.value
        val revealRight = size.width * progress
        ...
    }
}
```

这里实际上做了一次非常重要的数据分类。`gridPath` 与 `chartPath` 的依赖是：

```text
size
 ↓
Path
```

因此只要 `size` 不变，它们完全可以复用。而 `revealRight` 的依赖是：

```text
size + progress
       ↓
一个简单 Float
```

它非常便宜，而且 progress 每帧都变化，所以没有任何必要缓存。动画期间，GOOD 的运行模型因此变成：

```text
第一次：
Build Path
   ↓
Draw progress = 0.00

下一帧：
复用 Path
   ↓
Draw progress = 0.03

下一帧：
复用 Path
   ↓
Draw progress = 0.07

下一帧：
复用 Path
   ↓
Draw progress = 0.11
```

你应该看到 GOOD 的 Cache Build 日志在动画过程中基本不会跟着每帧增长，而绘制本身当然仍然会不断发生。这和 Compose 的阶段优化也是一致的：状态在 Drawing 阶段读取时，状态变化可以只重新执行绘制，而不要求重新经历 Composition 和 Layout。([Android Developers][2])

这里比“Cache 性能更好”更值得记住的原则是：**让状态尽可能在真正需要它的最晚阶段读取。**如果它只影响最终几个像素怎么画，就不要让它提前参与 Composition；如果它只影响每次 Draw，就不要让它进入 Cache Build；如果它确实决定缓存资源本身，那么才应该成为 Cache Build 的依赖。

---

#### 5.5 但不要走到另一个极端：Cache 重建不等于写错了

这一点非常重要。学完前面的例子，很容易产生一个新的错误观念：“只要 Cache Build 重新执行，就是性能问题。” 不是。假设折线图的数据真的发生变化：

```text
[10, 20, 15, 40]
        ↓
[10, 35, 28, 60]
```

那么 `chartPath` 本身已经不再正确。此时新的图表数据就应该在 Cache Build 中成为依赖：

```kotlin
.drawWithCache {
    val data = chartDataState.value

    val chartPath =
        buildChartPath(
            size = size,
            data = data
        )

    onDrawBehind {
        drawPath(
            path = chartPath,
            ...
        )
    }
}
```

数据发生变化以后：

```text
chartData 改变
      ↓
旧 Path 已经错误
      ↓
Cache 失效
      ↓
重新 buildChartPath()
```

这是**正确失效**，不是性能问题。所以判断一个状态应该放在哪一层，最核心的问题其实只有一个：**如果这个状态改变，当前缓存出来的对象本身还正确吗？**如果答案是“不正确”，那么 Cache 应该失效。如果答案是“缓存对象依然完全正确，只是画它的方式有点变化”，那么这个状态通常就应该推迟到 Draw。在刚才的例子中：

```text
size 改变
→ Path 不正确
→ 应该重新 Build

图表数据改变
→ Path 不正确
→ 应该重新 Build

动画 progress 改变
→ 完整 Path 仍然正确
→ 不应该重新 Build
→ 只重新 Draw
```

这比死记“动画状态不要写外面”更可靠，因为以后遇到任何新场景，你都可以自己推导。

---

#### 5.6 有时候高频状态真的会改变几何结构：这时 `drawWithCache` 也救不了你

再深入一步。假设你的动画不是“显示已经存在的完整 Path”，而是每一帧真的要求产生不同的复杂几何：

```text
progress = 0.31 → Path A
progress = 0.32 → Path B
progress = 0.33 → Path C
```

并且这些 Path 无法通过裁切、变换、透明度或其他廉价方式从同一个稳定 Path 得到。那么你不能为了维持 Cache 命中，错误地把 progress 移到 Draw 里面，然后继续使用已经过期的 Path。**正确性永远优先于缓存命中率。**

这种情况下有两个选择。要么接受每帧重新构建几何，因为需求本身就是如此；要么重新设计绘制表达方式，把真正稳定的部分提取出来。例如我们这个例子没有为每个 progress 创建一个“只画到 37% 的 Path”，而是缓存完整 Path：

```text
完整 Path
```

然后每帧只改变：

```kotlin
clipRect(
    right = size.width * progress
)
```

于是把：

```text
高频重建 Path
```

转换成：

```text
低频缓存完整 Path
+
高频改变裁切区域
```

这种思路比单纯学习一个 `drawWithCache()` API 更有价值。真正的性能优化经常不是“再加一个 cache”，而是**重新划分稳定部分和动态部分**。

---

#### 5.7 到底什么值得缓存？不要把 `drawWithCache` 当成微优化垃圾桶

官方给出的典型对象是 `Brush`、`Shader`、`Path` 等，因为它们可能存在对象创建、几何计算或底层资源构造成本。([Android Developers][1]) 像我们刚才的：

```kotlin
val gridPath = buildGridPath(size)
val chartPath = buildChartPath(size)
```

非常适合作为 Cache 候选，因为它们既有对象创建，又有多次几何操作，而且可以跨很多次 Draw 复用。但这种东西：

```kotlin
val x = size.width * progress
```

完全没有必要为了“缓存”而塞进 Cache Build。同样，如果你只是：

```kotlin
drawCircle(
    color = Color.Red,
    radius = 20.dp.toPx()
)
```

没有昂贵对象，也没有复杂预计算，直接 `drawBehind` 很可能就是最清楚的实现。官方甚至专门提醒：没有需要缓存的绘制对象却使用 `drawWithCache`，自身会产生额外的 lambda 分配，没有必要。([Android Developers][1]) 因此不要形成：

```text
drawWithCache
=
drawBehind 的性能加强版
```

这样的错误模型。它们的关系应该是：

```text
只需要直接画
→ drawBehind / drawWithContent

存在真正值得跨 Draw 保存的绘制资源
→ drawWithCache
```

---

#### 5.8 `remember` 和 `drawWithCache`：不要只从“它们都能缓存”出发比较

这一点上一阶段已经碰过，但现在可以把边界真正定下来。`remember` 属于 Composition：

```kotlin
val something = remember {
    ...
}
```

它适合保存由 Composition 管理、与 Composable 生命周期相关的对象和状态。`drawWithCache` 则天然处于绘制 Modifier 的环境中，可以直接使用：

```kotlin
size
density
layoutDirection
```

等绘制环境信息，而且绘制尺寸发生变化时，缓存机制本身就知道这些绘制资源可能需要重建。官方文档也明确指出：如果对象只是为了绘制而存在，`drawWithCache` 往往比把这套缓存搬回 Composition 更合适。([Android Developers][1]) 例如：

```kotlin
val path = remember {
    Path()
}
```

本身当然可以保存一个 `Path` 对象，但假如这个 Path 的几何结构依赖：

```kotlin
size.width
size.height
```

那么 Composition 中根本天然没有当前 DrawScope 的这个最终尺寸。你还得通过其他机制把尺寸拿回来、设计 key、在尺寸变化时重建 Path。这就开始变成：

```text
为了缓存一个纯绘制对象
↓
把绘制阶段的问题搬回 Composition
↓
自己维护尺寸依赖和缓存失效
```

这种情况下 `drawWithCache` 更符合职责。反过来，一个 Repository、业务模型、UI 状态容器、网络结果当然不应该因为“需要缓存”就塞进 `drawWithCache`。`drawWithCache` 管的是**绘制资源缓存**，不是通用缓存系统。

---

#### 5.9 最后一个容易踩的坑：缓存的是可变对象时，不要每帧继续往里面堆数据

`Path` 本身是可变对象，所以还有一种很隐蔽的问题。例如：

```kotlin
.drawWithCache {
    val path = Path()

    onDrawBehind {
        path.lineTo(
            x = ...,
            y = ...
        )

        drawPath(
            path = path,
            color = Color.Blue
        )
    }
}
```

如果 Draw 执行很多次，而你每次都继续向同一个缓存 `Path` 添加命令，那么之前的内容不会因为“下一帧到了”自动消失。你缓存的恰恰就是**同一个 Path 对象**，于是数据可能不断累积。

所以对于 `Path` 这类 mutable resource，最安全也最清楚的缓存模式通常是：

```kotlin
.drawWithCache {

    val path = Path().apply {
        // 在 Build 中完整建立稳定几何
    }

    onDrawBehind {
        // Draw 阶段只读取 path
        drawPath(
            path = path,
            ...
        )
    }
}
```

也就是：**Build 阶段构造完成，Draw 阶段只消费。**如果业务确实要求每次 Draw 都修改同一个 Path，那么你必须明确管理它的清空和重建，例如正确使用 `reset()`，而不能把“被缓存”误解成“Compose 每帧会帮我恢复对象原状”。

---

#### 5.10 第五阶段收束：以后判断 Cache 边界，只问三个问题

以后遇到自定义绘制，不需要机械背 API，可以按下面这个判断链自己推导：

```text
这个东西创建或计算成本值得缓存吗？
        │
        ├── 否
        │    → 直接在 Draw 中计算 / 绘制
        │
        └── 是
             ↓
它是否可以跨多次 Draw 继续保持正确？
             │
             ├── 是
             │    → 放进 Cache Build
             │
             └── 否
                  ↓
是什么导致它失效？
                  │
                  ├── size / 数据真的改变对象本身
                  │    → 让 Cache 正常失效并重建
                  │
                  └── 只是动画位置、alpha、clip 等
                       → 尽量缓存稳定资源
                       → 动态值留在 Draw
```

第五阶段真正应该留下来的结论不是“`Path` 要缓存”这么简单，而是：

> **Cache Build 应该只包含那些“昂贵、稳定，并且其依赖变化时确实必须重新构建”的东西；高频变化但只影响最终绘制方式的数据，应尽可能留在真正的 Draw 阶段。**

这样设计以后，`drawWithCache` 才真正是在减少重复工作，而不是一个名字里带着 Cache、实际却每帧都在重新 Build 的壳子。下一阶段我们再把 `drawBehind`、`drawWithContent`、`drawWithCache` 放进同一个真实 UI 场景中完成最终选择边界和 6.3 收尾。

[2]: https://developer.android.com/develop/ui/compose/performance/modifier-phases?utm_source=chatgpt.com "Modifier breakdown by phase  |  Jetpack Compose  |  Android Developers"

### 第六阶段：真实场景整合与 API 选择边界

这一阶段不再引入新的绘制 API，只做一件事：把 `drawBehind`、`drawWithContent`、`drawWithCache` 放进一个真实组件里，判断每段绘制逻辑到底应该属于谁。重点不是“一个组件把三个 API 全用上就很高级”，而是**每种需求都放到职责最合适的位置**。

#### 6.1 实战场景：日历时间轴中的日程卡片

假设以后你的日历 App 时间轴里有一张日程卡片。它包含正常的 Compose 文本内容，同时还有三种绘制需求：

1. 左侧有一条简单的分类色条，它只是在内容后面画一个矩形，没有复杂资源；
2. 卡片右下角有一块根据组件尺寸生成的曲线装饰，需要构造 `Path`，尺寸不变时可以复用；
3. 用户选中日程后，需要在**整个已有 UI 上面**覆盖一层轻微高亮。

这三个需求恰好应该分别落到：

```text
简单背景装饰        → drawBehind
尺寸相关 Path       → drawWithCache
内容上方覆盖效果    → drawWithContent
```

我们用独立的最终示例，不修改之前任何练习文件。

#### 6.2 `Sec03F_RealDrawingModifier.kt`

#### 6.3 为什么这里三个 API 各自合理

先看：

```kotlin
.drawBehind {
    drawRoundRect(...)
    drawRect(...)
}
```

背景和左侧色条非常简单，没有创建需要复用的复杂绘制资源。这里使用 `drawWithCache` 没有什么收益，反而会让代码的意图变差。所以即使 `drawWithCache` 功能更强，也不应该机械替代 `drawBehind`。

右下角装饰则不同：

```kotlin
.drawWithCache {
    val decorationPath = Path().apply {
        ...
    }

    onDrawBehind {
        drawPath(decorationPath, ...)
    }
}
```

这个 `Path` 的几何形状明显依赖：

```kotlin
size.width
size.height
```

但只要组件尺寸没有变化，同一个 `Path` 就能够持续复用。这里才真正满足 `drawWithCache` 的使用条件：**存在一个构建成本高于简单数值计算、生命周期又比单次 Draw 更长的绘制资源。**

最后的选中效果：

```kotlin
.drawWithContent {
    drawContent()

    if (selected) {
        ...
    }
}
```

需求本身已经告诉我们它必须位于 content 上方。因此这里的关键不是缓存，而是控制：

```text
已有整张卡片
→ 选中遮罩
→ 选中描边
```

所以 `drawWithContent` 才是正确工具。**注意 `selected` 直接在 Draw lambda 中读取。**在这个示例里它只决定“这一帧要不要画覆盖层”，不会改变前面的 `decorationPath`，因此不应该为了 selected 去重新 Build Path。

---

#### 6.4 这里还有一个很重要的现实判断：能用普通 Modifier，就不要为了练习 Canvas 强行自己画

比如卡片背景如果只是：

```text
一个普通圆角纯色背景
```

真实项目中其实完全可以直接写：

```kotlin
.background(
    color = Color(0xFF20232D),
    shape = RoundedCornerShape(20.dp)
)
```

普通边框也完全可以：

```kotlin
.border(...)
```

这往往比自己写：

```kotlin
drawRoundRect(...)
```

更清晰。这次代码故意把背景放进 `drawBehind`，是为了让最终练习同时出现三种 Drawing Modifier。但真正开发时，选择顺序应该是：

| 需求                            | 首选                               |
| ----------------------------- | -------------------------------- |
| 普通背景、圆角、边框、裁切                 | `background` / `border` / `clip` |
| 简单自定义图形，只需要画在内容下面             | `drawBehind`                     |
| 需要控制内容之前、之后的绘制                | `drawWithContent`                |
| 存在值得复用的 `Path`、`Brush`、复杂计算结果 | `drawWithCache`                  |
| 整块区域主要就是自定义绘图                 | `Canvas`                         |

所以不要从“我今天学了哪个 API”出发，而要从需求出发。

#### 6.5 三个 Drawing Modifier 最终选择边界

现在可以把 6.3 真正压缩成三个判断问题。

第一问：**我要不要控制原始 Content 的绘制位置？**

不需要，只需要在后面画：

```kotlin
drawBehind
```

需要自己决定：

```text
背景
→ Content
→ 前景
```

那么：

```kotlin
drawWithContent
```

第二问：**有没有值得跨多次 Draw 保存的绘制资源？**

如果有：

```text
Path
Brush
Shader
复杂几何结果
TextLayoutResult
```

再考虑：

```kotlin
drawWithCache
```

如果只是几个：

```kotlin
Offset
Float
简单乘法
drawCircle()
drawRect()
```

通常没有必要为了 Cache 而 Cache。

第三问：**这个状态变化以后，缓存对象本身还正确吗？**例如：

```text
size 改变
图表数据改变
```

导致旧 Path 已经错误，那么 Cache 应该失效。但：

```text
progress 改变
alpha 改变
selection 改变
简单位置改变
```

如果稳定资源本身仍然正确，就尽量只在 Draw 中读取这些动态值。这三个问题已经足够覆盖大多数真实 App 绘制场景。

---

#### 6.6 UI、ViewModel 和 Repository 的职责边界

绘制代码没有理由进入 ViewModel。例如真实项目中 ViewModel 可以提供：

```kotlin
data class CalendarEventUiState(
    val title: String,
    val time: String,
    val isSelected: Boolean
)
```

Composable 收到：

```kotlin
selected = uiState.isSelected
```

之后，至于 `isSelected == true` 时到底：

```text
画多粗的边框
使用什么 alpha
画在 Content 前面还是后面
用什么 Path
```

这些全部属于 UI 绘制实现。ViewModel 应该知道：这个日程当前是否被选中。但不应该知道：Compose 应该调用 `drawWithContent()`，然后画一个 2dp Stroke。Repository 更不应该知道这些东西。这一点对于以后做复杂日历、自定义时间轴非常重要：**业务层提供“是什么状态”，UI 层决定“这个状态怎样被画出来”。**

---

#### 6.7 6.3 最终心智模型

这一节真正应该带走的是这一套完整关系：

```text
Composable 已经完成布局
        ↓
进入 Draw Modifier 链
        ↓
每个 Draw Modifier 都可能：

    drawContent() 之前画
            ↓
       进入内层链
            ↓
       Content 绘制
            ↓
         返回
            ↓
    drawContent() 之后继续画
```

而 `drawWithCache` 只是在这个 Draw 系统之外增加了一层：

```text
需要时 Build 绘制资源
        ↓
缓存 DrawResult
        ↓
真正进入 Draw Modifier 链
```

所以三个 API 并不是三个互相独立的零散知识，而是同一个绘制系统里的不同控制能力：

```text
drawBehind
→ 固定在 Content 前画

drawWithContent
→ 自己控制 Content 在绘制流程中的位置

drawWithCache
→ 在上述绘制能力之外，再管理可复用绘制资源
```

到这里，**6.3 可以正式结束，不需要再继续下钻源码。** 以应用层 Android 开发而言，目前已经足够理解 Drawing Modifier 的绘制链、`drawContent()`、Modifier 顺序和 Cache 失效边界。再往下研究 `DrawModifierNode` / `CacheDrawModifierNode`，收益已经明显下降，而且 6.5 本身就是更底层的自定义绘制 Modifier。

下一节 **6.4 图层合成与离屏缓冲** 才会进入一个新的问题：现在我们已经知道“谁先画、谁后画”，但当透明度、裁切、BlendMode、`graphicsLayer` 等开始参与以后，**这些东西到底是在同一个 Canvas 上直接画，还是先画进一个离屏 Layer，再整体合成回来？** 这会直接影响最终像素结果和性能。
