### 6.1 阶段一：第一次真正写一个 Custom Shape

你当前新课目录把第六章的路线安排为 `Shape / Outline / Path → Canvas / DrawScope → Modifier 绘制体系 → 图层合成 → 自定义绘制 Modifier`，所以 6.1 的职责非常明确：**先学会描述“一个组件的几何边界长什么样”，之后 6.2 才学习“主动往画布上画什么”。**

阶段一我们只解决一个核心问题：**Compose 里的 `Shape` 到底是什么？一个自定义 `Shape` 是怎样最终变成屏幕上的形状的？**这一阶段结束以后，你至少应该形成下面这条稳定心智模型：

```text
组件先完成布局，拥有具体 Size
            ↓
Shape.createOutline(size, layoutDirection, density)
            ↓
生成这个尺寸下的 Outline
            ↓
Surface / background / clip / shadow 等使用这个边界
```

注意，这里最值得先记住的一句话不是某个函数名，而是：**`Shape` 不是一个已经画好的图形。`Shape` 更像一份“根据实际尺寸生成图形边界的规则”。**这句话是今天阶段一的中心。

---

#### 一、我们以前其实已经使用 Shape 很久了

比如你一定写过这种代码：

```kotlin
Surface(
    shape = RoundedCornerShape(24.dp)
) {
    Text("Hello")
}
```

或者：

```kotlin
Modifier.background(
    color = Color.Blue,
    shape = RoundedCornerShape(24.dp)
)
```

以前我们可以把 `RoundedCornerShape(24.dp)` 暂时理解成：“给我弄个 24dp 圆角。” 对于普通 UI 开发，这完全够用。但现在开始学习自定义图形，这层抽象就不够了。因为接下来我们会遇到：

```text
切掉右上角的卡片
聊天气泡
票券缺口
特殊标签
日历选中背景
时间轴上的特殊事件块
任意不规则轮廓
```

这些东西不一定有现成的 `RoundedCornerShape()` 可以调用。所以我们需要知道 Compose 背后的统一接口：

```kotlin
interface Shape {
    fun createOutline(
        size: Size,
        layoutDirection: LayoutDirection,
        density: Density
    ): Outline
}
```

当前 Compose 官方 API 仍然就是这个模型：`Shape.createOutline()` 接收实际 `Size`、当前 `LayoutDirection` 和 `Density`，并返回对应尺寸的 `Outline`。([Android Developers][1]) 这里先不要急着研究 `Outline` 的三个子类。今天只把调用关系跑通。

#### 二、第一份完整实验：`Sec01A_ShapeOutlineIntro.kt`

在你的：`Chapter06` 包下面建立：`Sec01A_ShapeOutlineIntro.kt`，下面这部分可以直接作为完整练习文件主体。

```kotlin
private const val TAG_SEC01A = "Sec01A"

/**
 * 一个简单的自定义 Shape：
 *
 * 把矩形的右上角切掉一块。
 *
 * 注意：
 * Path 的具体原理会在后续阶段正式学习。
 * 当前只需要把它看成“描述边界路线的工具”。
 */
private class CutTopRightShape(
    private val cutSize: Dp
) : Shape {

    override fun createOutline(
        size: Size,
        layoutDirection: LayoutDirection,
        density: Density
    ): Outline {

        val cutSizePx = with(density) {
            cutSize.toPx()
        }.coerceIn(
            minimumValue = 0f,
            maximumValue = minOf(size.width, size.height)
        )

        println(
            "$TAG_SEC01A createOutline() " +
                "size=$size, " +
                "cutSizePx=$cutSizePx, " +
                "layoutDirection=$layoutDirection"
        )

        val path = Path().apply {
            // 左上角
            moveTo(0f, 0f)

            // 沿顶部向右走，但在右上角之前停下
            lineTo(size.width - cutSizePx, 0f)

            // 斜着切到右边
            lineTo(size.width, cutSizePx)

            // 右下角
            lineTo(size.width, size.height)

            // 左下角
            lineTo(0f, size.height)

            // 回到起点，形成闭合区域
            close()
        }

        return Outline.Generic(path)
    }
}

@Composable
fun Sec01A_ShapeOutlineIntro(
    modifier: Modifier = Modifier
) {
    /*
     * 这是同一个 Shape 对象。
     *
     * 后面它会被不同尺寸的组件使用。
     */
    val cutShape = remember {
        CutTopRightShape(cutSize = 32.dp)
    }

    Surface(
        modifier = modifier.fillMaxSize(),
        color = MaterialTheme.colorScheme.background
    ) {
        Column(
            modifier = Modifier
                .fillMaxSize()
                .padding(24.dp),
            verticalArrangement = Arrangement.spacedBy(20.dp)
        ) {
            Text(
                text = "6.1A Shape / Outline",
                style = MaterialTheme.typography.headlineSmall
            )

            Text(
                text = "① 先看我们熟悉的内置 Shape",
                style = MaterialTheme.typography.titleMedium
            )

            Surface(
                modifier = Modifier
                    .fillMaxWidth()
                    .height(100.dp),
                shape = RoundedCornerShape(28.dp),
                color = MaterialTheme.colorScheme.secondaryContainer
            ) {
                Box(
                    modifier = Modifier
                        .fillMaxSize()
                        .padding(16.dp),
                    contentAlignment = Alignment.CenterStart
                ) {
                    Text("RoundedCornerShape(28.dp)")
                }
            }

            Text(
                text = "② 再看我们自己实现的 Shape",
                style = MaterialTheme.typography.titleMedium
            )

            Surface(
                modifier = Modifier
                    .fillMaxWidth()
                    .height(110.dp),
                shape = cutShape,
                color = MaterialTheme.colorScheme.primaryContainer
            ) {
                Box(
                    modifier = Modifier
                        .fillMaxSize()
                        .padding(16.dp),
                    contentAlignment = Alignment.CenterStart
                ) {
                    Text(
                        text = "CutTopRightShape\n" +
                            "右上角由我们自己定义"

                            color = MaterialTheme.colorScheme.tertiaryContainer,

                }

                Box(

                }
            }

            Text(
```

#### 三、运行以后，第一件事不要研究 Path，而是观察 Size

你应该在日志中看到类似：

```text
Sec01A createOutline() size=Size(936.0, 330.0), cutSizePx=96.0, layoutDirection=Ltr
Sec01A createOutline() size=Size(528.0, 300.0), cutSizePx=96.0, layoutDirection=Ltr
Sec01A createOutline() size=Size(360.0, 300.0), cutSizePx=96.0, layoutDirection=Ltr
```

具体数字肯定依设备而异，所以**不要拿我的数字和你的数字对答案**。真正观察的是：

```text
同一个 cutShape
       ↓
被宽卡片使用
       ↓
createOutline(size = 宽卡片自己的尺寸)

同一个 cutShape
       ↓
被窄 Box 使用
       ↓
createOutline(size = 窄 Box 自己的尺寸)
```

这件事情非常重要。很多人第一次学习 `Shape` 会在脑中形成错误模型：

```text
CutTopRightShape
        ↓
创建了一张固定大小的形状
        ↓
塞给组件
```

**不是。**真正的模型是：

```text
CutTopRightShape
        ↓
只保存“怎么生成边界”的规则
        ↓
某个具体组件需要它
        ↓
组件已经拥有实际 Size
        ↓
Shape 根据这个 Size 生成 Outline
```

官方文档对 `size` 的定义就是“shape boundary 的 size”，即 Compose 要你针对这个实际尺寸生成对应的边界。([Android Developers][1]) 所以从今天开始，我希望你把 `Shape` 暂时理解成：**Shape = Size → Outline 的几何规则。**严格来说它还依赖 `LayoutDirection` 和 `Density`，所以完整版是：

```text
(size, layoutDirection, density)
                ↓
              Shape
                ↓
             Outline
```

但第一阶段先抓住 `Size → Outline` 这一条最核心关系。

#### 四、为什么 `Shape` 自己不需要知道组件宽度是多少？

看看我们的构造函数：

```kotlin
private class CutTopRightShape(
    private val cutSize: Dp
) : Shape
```

这里只传了：

```kotlin
32.dp
```

我们完全没有传：

```kotlin
width
height
```

可是在 `createOutline()` 里面：

```kotlin
size.width
size.height
```

已经有了。这就是 Compose 这个 API 设计非常漂亮的地方。如果 `Shape` 创建时就必须写：

```kotlin
CutTopRightShape(
    width = 300.dp,
    height = 100.dp,
    cutSize = 32.dp
)
```

那这个 Shape 几乎没法复用。现在却可以：

```kotlin
val cutShape = CutTopRightShape(32.dp)
```

然后：

```kotlin
Surface(
    modifier = Modifier
        .fillMaxWidth()
        .height(110.dp),
    shape = cutShape
)
```

也可以：

```kotlin
Box(
    modifier = Modifier
        .width(120.dp)
        .height(100.dp)
        .background(
            color = Color.Blue,
            shape = cutShape
        )
)
```

**尺寸是组件布局出来的，Shape 不负责决定尺寸。**这是阶段一必须钉死的边界：

```text
Layout / Modifier
负责：
“我多大？”

Shape
负责：
“在你已经这么大的前提下，
你的边界长什么样？”
```

这两个职责千万不要混。以后学自定义 `Layout()`，你会发现这一点更加重要。

#### 五、现在正式拆 `createOutline()` 的三个参数

我们的代码：

```kotlin
override fun createOutline(
    size: Size,
    layoutDirection: LayoutDirection,
    density: Density
): Outline
```

三个参数都不是随便塞进来的。Compose 当前正式 API 就要求这三个上下文。([Android Developers][1])

##### `size: Size` 这是本次需要生成边界的实际尺寸。里面最重要的是：

```kotlin
size.width
size.height
```

这里已经进入 Compose 图形坐标空间，值是 `Float`。所以你看到的可能是：

```text
936.0
330.0
```

而不是：

```text
312.dp
110.dp
```

这一点以后进入 Canvas 会天天碰到：**布局 API 很多时候使用 `Dp`；真正进入绘制与几何计算以后，我们会越来越多地面对像素坐标和 `Float`。**今天先认识这个变化即可。

---

##### `density: Density` 我们的 Shape API 对外非常舒服：

```kotlin
CutTopRightShape(32.dp)
```

但实际 Path 坐标不能直接拿：

```kotlin
32.dp
```

和：

```kotlin
size.width
```

做运算。所以需要：

```kotlin
val cutSizePx = with(density) {
    cutSize.toPx()
}
```

假如某个设备密度导致：

```text
32.dp → 96px
```

最终真正参加几何计算的是：

```kotlin
96f
```

于是：

```kotlin
size.width - cutSizePx
```

单位统一以后才有意义。这也是为什么 `Shape.createOutline()` 主动把 `Density` 给你，而不是逼你从 Composable 环境里自己找密度。官方接口也明确把该参数定义为当前屏幕 Density。([Android Developers][1])

---

##### `layoutDirection: LayoutDirection`

你的设备现在大概率打印：

```text
Ltr
```

也就是 Left To Right。今天**我们故意没有使用它进行几何计算**：

```kotlin
layoutDirection=Ltr
```

只是打印出来。因为我们现在做的是：

```text
CutTopRightShape
```

物理意义就是：永远切右上角。以后如果我们做的是：

```text
CutTopEndShape
```

那么：

```text
LTR → End 在右边
RTL → End 在左边
```

这时候 `layoutDirection` 就必须参与生成 Outline。这个问题放在阶段四正式做，今天只要知道：Shape 不仅能知道自己有多大，也知道当前界面的布局方向。不要现在展开 RTL。

---

#### 六、终于轮到今天最重要的返回值：`Outline`

我们的最后一句是：

```kotlin
return Outline.Generic(path)
```

这里第一次正式出现 `Outline`。官方当前定义得非常清楚：`Outline` 是描述图形区域边界的 sealed class，可以被用来定义背景区域、阴影区域以及裁切区域；它目前有 `Rectangle`、`Rounded` 和 `Generic` 三种直接表示。([Android Developers][2])

但我们今天不要急着背三种类型。先把 `Outline` 理解成：**Shape 最终交给 Compose 的“这次具体边界结果”。**于是：

```text
Shape
```

和：

```text
Outline
```

已经能严格区分了。

`Shape` 是：

```text
规则 / 配方
```

而 `Outline` 是：

```text
在一个具体 Size 下，
按照这份规则算出来的实际边界结果
```

比如：

```text
CutTopRightShape(32.dp)
```

本身不知道自己最终有：

```text
936 × 330 px
```

还是：

```text
360 × 300 px
```

当某个组件真正需要边界时：

```kotlin
createOutline(
    size = ...
)
```

才产生这一次具体的：

```kotlin
Outline
```

所以以后看到名字不要把两个东西混成“都是 Shape”。我推荐你脑中固定成：

```text
Shape = 模板
Outline = 模板针对当前尺寸算出的结果
```

这已经非常接近正确的工程心智模型。

---

#### 七、那为什么我们突然用了 `Path`？

这里先只看四句话：

```kotlin
val path = Path().apply {
    moveTo(0f, 0f)
    lineTo(...)
    lineTo(...)
    close()
}
```

**这一阶段不要求你学会 Path。**你现在只需要把 `Path` 想成：“我沿着哪些坐标点走一圈，从而描述一个复杂边界。” 我们从：

```text
左上角
```

开始：

```kotlin
moveTo(0f, 0f)
```

走到：

```text
顶部、靠近右上角
```

```kotlin
lineTo(size.width - cutSizePx, 0f)
```

再斜着走到：

```text
右边
```

```kotlin
lineTo(size.width, cutSizePx)
```

然后沿着矩形剩余边缘走完，最后：

```kotlin
close()
```

闭合。于是得到：

```text
┌──────────────────────╲
│                       ╲
│                        │
│                        │
└────────────────────────┘
```

然后：

```kotlin
Outline.Generic(path)
```

意思可以暂时读成：**“这是个无法简单用普通矩形表示的 Outline，我拿 Path 把它描述出来了。”**

`GenericShape` 这个 Compose 现成类的官方定义本身也是“通过在 `Path` 上执行 builder 来创建 Shape”，所以 `Shape → Path → Outline.Generic` 本来就是 Compose 正式支持的不规则边界路线。([Android Developers][3])

阶段三我们会停下来把：

```kotlin
moveTo()
lineTo()
close()
```

以及坐标系、多个 contour、贝塞尔曲线全部认真学。今天不要抢课。

#### 八、现在可以解释为什么同一个 Shape 能给 Surface 和 background 使用了

你看我们只创建了一次：

```kotlin
val cutShape = remember {
    CutTopRightShape(32.dp)
}
```

第一次：

```kotlin
Surface(
    shape = cutShape
)
```

第二次：

```kotlin
Modifier.background(
    color = ...,
    shape = cutShape
)
```

这就是 `Shape` 这个抽象真正强的地方。`CutTopRightShape` 并不知道：“我是给 Surface 用的。” 也不知道：“我是给 background 用的。” 它只会一件事：

```text
你给我当前尺寸
↓
我给你边界 Outline
```

至于拿这个边界干什么，是消费者自己的事情。官方 `Outline` 文档也正是把它描述成供背景、阴影、裁切等图形区域使用的边界抽象。([Android Developers][2]) 这是一种很经典、很值得学习的 API 分层：

```text
几何定义
    ↓
Shape / Outline

具体用途
    ↓
background
clip
shadow
Surface
...
```

**定义形状的人不需要知道最终用它来干嘛。**这也是为什么一个 `RoundedCornerShape()` 可以到处出现，却不属于 `Surface`、`Box` 或 `background` 中的任何一个。

#### 九、再回头看一次整个运行过程

现在把整个代码压缩成真正的核心：

```kotlin
val shape = CutTopRightShape(32.dp)

Surface(
    shape = shape
)
```

你代码里虽然只写了这么一点，但概念上发生的是：

```text
Surface / Modifier
    │
    │ 需要知道自己的图形边界
    ↓
CutTopRightShape
    │
    │ createOutline(
    │     size,
    │     layoutDirection,
    │     density
    │ )
    ↓
Path
    │
    │ 描述不规则轮廓
    ↓
Outline.Generic
    │
    ↓
具体图形边界
```

这里我特意没有写：

```text
Composable → Shape
```

因为 `Shape` 本身并不是一个 Composable。你不能：

```kotlin
@Composable
fun CutTopRightShape() { ... }
```

然后期待它变成 UI。`Shape` 属于：

```kotlin
androidx.compose.ui.graphics
```

它是图形模型，而不是 UI 节点。这个区别以后非常重要。

#### 十、一个容易产生的误解：Shape 负责“绘制”吗？

严格说，**不要这样理解。**我们的：

```kotlin
CutTopRightShape
```

并没有：

```kotlin
drawRect()
drawPath()
drawLine()
```

也没有颜色。它只是：

```kotlin
return Outline.Generic(path)
```

所以：**Shape 的核心职责是描述边界，而不是主动绘制内容。**比如：

```kotlin
CutTopRightShape(32.dp)
```

里面根本没有：

```text
蓝色
红色
阴影
渐变
文字
```

颜色来自：

```kotlin
Surface(
    color = ...
)
```

或者：

```kotlin
Modifier.background(
    color = ...
)
```

这也是我们为什么一定要先学 6.1，再学 6.2。到了 6.2：

```kotlin
Canvas {
    drawLine(...)
    drawCircle(...)
    drawPath(...)
}
```

才进入：**“我要主动绘制什么。” **现在的 6.1 是：**“我的几何边界是什么。”** 这两个概念如果现在混了，后面 Canvas 会越学越乱。

#### 十一、为什么这里用了 `remember`？

这里：

```kotlin
val cutShape = remember {
    CutTopRightShape(32.dp)
}
```

不是因为：“Shape 必须 remember。” 不是。我们只是因为这个 Shape 参数完全不变，所以没必要每次重组时：

```kotlin
CutTopRightShape(32.dp)
```

重新创建一个对象。你已经学过 `remember`，这里不重新上状态课。只记：

```text
这是普通对象复用问题
不是 Shape 特有规则
```

即可。

#### 十二、还有一个小细节：为什么要 `coerceIn()`？

我们没有直接：

```kotlin
val cutSizePx = with(density) {
    cutSize.toPx()
}
```

而是：

```kotlin
.coerceIn(
    minimumValue = 0f,
    maximumValue = minOf(size.width, size.height)
)
```

因为一个可复用 Shape 不能假设组件永远足够大。假设：

```text
cutSize = 100.dp
```

可是组件最终只有：

```text
50 × 30px
```

如果完全不做限制：

```kotlin
size.width - cutSizePx
```

甚至可能出现负坐标。这个边界 Case 今天不继续深入，但我要从第一份代码就让你养成一个习惯：**自定义图形代码必须考虑实际 Size，而不是默认设计稿尺寸永远成立。**这会一直延续到 Canvas、自定义 Layout 和手势坐标。

#### 阶段一最重要的知识模型

今天如果其他细节都忘了，下面这一段不能忘：

```text
Layout 决定：
组件有多大

        ↓

Shape.createOutline()
拿到实际 Size

        ↓

Shape 根据当前尺寸
计算几何边界

        ↓

Outline 表示这一次
真正计算出来的边界

        ↓

background / Surface /
clip / shadow 等使用这个边界
```

所以一句话总结：**`Shape` 是边界生成规则，`Outline` 是规则针对当前具体尺寸生成出的边界结果。**而 `Path` 目前只需要知道：**复杂 Outline 的一种几何描述工具。**

**`Path()` 不是创建 `Shape` 对象时执行的，而是 `createOutline()` 已经被调用、实际 `size` 已经传进来以后才执行。`Shape` 不决定多大，只决定“这么大时长什么样”。`createOutline()` 真正执行以后，返回的 `Outline` 已经是针对这一轮实际尺寸计算完成的边界。**这就是阶段一正确的学习深度。

### 6.1 阶段二：把 `Outline` 拆开——Rectangle、Rounded、Generic

老哥，继续。按照最初的大纲，这一阶段就是把阶段一留下的那个黑盒：

```kotlin
Shape.createOutline(...) -> Outline
```

正式拆开。新课目录里 6.1 本来就是 `Shape、Outline 和 Path`，所以今天我们还没有进入“系统学 Path”，而是先回答：**为什么 Compose 的 `Outline` 要专门分成三种？** 

官方当前定义非常直接：`Outline` 是一个 `sealed class`，只有三个直接子类型：`Outline.Rectangle`、`Outline.Rounded`、`Outline.Generic`；它们分别表示矩形区域、圆角矩形区域和由 `Path` 定义的区域。`Outline` 还统一暴露一个 `bounds: Rect`，表示这个轮廓的外接边界。([Android Developers][1])

这一阶段我希望你最后形成的不是“三个类名”，而是下面这个判断模型：

```text
我要描述一个边界
      │
      ├─ 普通矩形可以完整表达
      │      ↓
      │  Outline.Rectangle(Rect)
      │
      ├─ 圆角矩形可以完整表达
      │      ↓
      │  Outline.Rounded(RoundRect)
      │
      └─ 上面两个都表达不了
             ↓
        Outline.Generic(Path)
```

这才是今天真正要学的东西。

#### 二、先看最简单的 `Outline.Rectangle`

核心实际上只有这几行：

```kotlin
val rect = Rect(
    left = 0f,
    top = 0f,
    right = size.width,
    bottom = size.height
)

return Outline.Rectangle(rect)
```

这里第一次需要认真认识：

```kotlin
Rect
```

`Rect` 不是 UI，也不是 Shape，更不是绘制命令。它只是一个**二维几何数据结构**：

```text
left
top
right
bottom
```

我们的局部坐标系是：

```text
(0, 0)
  ┌───────────────────────→ x
  │
  │
  │
  ↓
  y
```

所以：

```kotlin
Rect(
    left = 0f,
    top = 0f,
    right = size.width,
    bottom = size.height
)
```

意思其实非常朴素：从当前组件局部坐标的 `(0, 0)` 开始，一直延伸到 `(size.width, size.height)`。也就是：

```text
(0, 0)
   ┌────────────────────┐
   │                    │
   │                    │
   └────────────────────┘
                (width, height)
```

这里值得注意一个以后会反复出现的词：**局部坐标（local coordinates）**。我们现在写：

```kotlin
0f
size.width
size.height
```

不是在说：“屏幕左上角是多少？” 而是在说：**“当前这个图形自己的坐标空间。”** 因此不管这个 Box 最后摆在屏幕顶部、中间还是底部，Shape 一般都不需要知道它在整个手机屏幕上的绝对位置。这个概念到 `Canvas`、手势、自定义 Layout 都会回来。

---

#### 三、这里出现了第一层几何抽象

现在把这三个名字分开：

```text
Shape
Rect
Outline.Rectangle
```

它们不是同一个东西。`Rect` 是纯粹的：**矩形几何数据。**它保存：

```text
left
top
right
bottom
```

而：

```kotlin
Outline.Rectangle(rect)
```

表达的是：**“我要把这个 Rect 当成一个 Compose 图形边界。”** 于是阶段一那个模型现在可以展开一级：

```text
Shape
  │
  │ createOutline(size...)
  ↓
Rect
  │
  │ 包装为矩形轮廓
  ↓
Outline.Rectangle
```

这里的“包装”不是说 `Outline.Rectangle` 没意义，而是职责不同。`Rect` 的职责是：几何学上这是一个矩形。`Outline.Rectangle` 的职责是：**这个矩形现在作为 Shape 系统中的一个轮廓结果。** 这就是 Compose 图形 API 里很常见的一种分层。

#### 四、为什么不直接让 `Shape.createOutline()` 返回 `Rect`？

因为 Shape 显然不可能只支持矩形。那能不能干脆：

```kotlin
fun createOutline(...): Path
```

所有形状全部 Path 化？当然理论上可以设计出这样的 API，但 Compose 没这么设计。它保留了三种不同层级：

```text
Rectangle → Rect
Rounded   → RoundRect
Generic   → Path
```

官方 API 就是这样明确区分三类区域的。([Android Developers][1]) 这样做最重要的价值，不需要现在扯底层渲染优化，光从**数据表达能力**就已经能看出来：一个普通矩形只需要：

```text
left
top
right
bottom
```

就能完整描述。你没必要为了说：“我就是个矩形。” 却硬写：

```kotlin
moveTo(...)
lineTo(...)
lineTo(...)
lineTo(...)
close()
```

那等于把一个高度结构化的信息：

```text
我是矩形
```

主动降级成：

```text
我是一串任意路径命令，
碰巧最后长得像矩形。
```

这就是今天一个很重要的设计思想：**能用更具体、更有语义的几何类型完整表达，就不要无意义地退化成最通用的 `Path`。**

#### 五、第二层：`Outline.Rounded`

现在来看：

```kotlin
val roundRect = RoundRect(...)
return Outline.Rounded(roundRect)
```

`Outline.Rounded` 官方定义就是**具有圆角的矩形区域**，其构造函数直接接收 `RoundRect`。([Android Developers][2]) 因此：

```text
Outline.Rectangle
      │
      └── Rect

Outline.Rounded
      │
      └── RoundRect
```

这两个结构非常对称。那 `RoundRect` 又是什么？官方当前的 `RoundRect` 是一个不可变的圆角矩形几何对象，它不只是保存矩形的 `left/top/right/bottom`，还可以分别保存四个角自己的 `CornerRadius`。([Android Developers][3]) 我们的代码：

```kotlin
val roundRect = RoundRect(
    left = 0f,
    top = 0f,
    right = size.width,
    bottom = size.height,
    topLeftCornerRadius = cornerRadius,
    topRightCornerRadius = cornerRadius,
    bottomRightCornerRadius = cornerRadius,
    bottomLeftCornerRadius = cornerRadius
)
```

如果四个角都相同：

```text
╭────────────────────╮
│                    │
│                    │
╰────────────────────╯
```

但实际上完全可以：

```kotlin
RoundRect(
    left = 0f,
    top = 0f,
    right = size.width,
    bottom = size.height,
    topLeftCornerRadius = CornerRadius(80f, 80f),
    topRightCornerRadius = CornerRadius(20f, 20f),
    bottomRightCornerRadius = CornerRadius(0f, 0f),
    bottomLeftCornerRadius = CornerRadius(40f, 40f)
)
```

所以 `RoundRect` 本身已经具有相当强的表达能力。

#### 六、`CornerRadius` 为什么有 `x` 和 `y` 两个值？

我们写的是：

```kotlin
CornerRadius(
    x = radiusPx,
    y = radiusPx
)
```

这里很多人第一次看到会产生疑问：圆角半径不是一个数吗？为什么有 x 和 y？因为它不一定非得是正圆的一部分。官方对 `CornerRadius` 的定义是：它可以表示圆形或者椭圆形角的半径，也就是说有横向半径和纵向半径。([Android Developers][4]) 当：

```text
x == y
```

就是普通圆弧：

```text
    ○
```

当：

```text
x != y
```

其实更接近：

```text
    椭圆
```

所以：

```kotlin
CornerRadius(
    x = 80f,
    y = 30f
)
```

得到的角会在水平方向拉得更长。**这一点知道即可，不需要现在深入曲线数学。**

#### 七、`RoundedCornerShape(28.dp)` 和我们刚写的东西是什么关系？

现在你应该开始有感觉了。以前：

```kotlin
RoundedCornerShape(28.dp)
```

看起来像一个“神奇的系统 Shape”。但从我们今天学到的抽象上，它最终仍然必须完成：

```text
RoundedCornerShape
        ↓
createOutline(...)
        ↓
Outline
```

官方当前 `RoundedCornerShape` API 本身也仍然通过 `createOutline(...)` 创建给定尺寸的 `Outline`。([Android Developers][5]) 所以我们今天手写：

```kotlin
RoundedOutlineShape(28.dp)
```

绝不是为了以后让你放弃：

```kotlin
RoundedCornerShape(28.dp)
```

恰恰相反。我们的目的是让你以后再看到：

```kotlin
RoundedCornerShape(28.dp)
```

脑子里已经知道：“哦，它不是魔法。它也是一个 `Shape`，最后要根据实际 `Size` 生成对应的 Outline。” **真实项目当然优先用现成的 `RoundedCornerShape`。** 这堂课是在扒开抽象，而不是教你重复造轮子。

#### 八、第三层：`Outline.Generic`

现在终于来到：

```kotlin
Outline.Generic(path)
```

官方定义简单得不能再简单：`Outline.Generic` 表示一个由 `Path` 定义的区域。([Android Developers][6]) 我们今天用一个三角形：

```kotlin
val path = Path().apply {
    moveTo(
        x = size.width / 2f,
        y = 0f
    )

    lineTo(
        x = size.width,
        y = size.height
    )

    lineTo(
        x = 0f,
        y = size.height
    )

    close()
}
```

不要急着背这些 Path API。只观察为什么这里突然不得不用 `Path`。我们的图形：

```text
               (w/2, 0)
                   ▲
                  / \
                 /   \
                /     \
               /       \
              /_________\
       (0,h)             (w,h)
```

你现在问 Compose：“请给我一个描述这个三角形的 `Rect`。” 做不到。因为 `Rect` 只能告诉你：

```text
┌────────────────────┐
│                    │
│         ▲          │
│        / \         │
│       /___\        │
└────────────────────┘
```

它最多只能描述三角形的**外接矩形**，却不能描述真正的三角形区域。那：

```text
RoundRect
```

当然也做不到。所以这时候才升级到：

```text
Path
```

这就是 `Generic` 存在的真正原因。

#### 九、这里必须区分“真正的轮廓”和 `bounds`

这是本阶段一个我认为非常值得额外插入的知识。所有 `Outline` 都有：

```kotlin
outline.bounds
```

官方定义就是：返回 Outline 的 bounds。([Android Developers][1]) 对于 Rectangle：

```text
真实区域：
┌─────────────┐
│             │
└─────────────┘

bounds：
┌─────────────┐
│             │
└─────────────┘
```

完全一样。对于 Rounded：

```text
真实区域：
╭─────────────╮
│             │
╰─────────────╯

bounds：
┌─────────────┐
│             │
└─────────────┘
```

已经不完全一样。而对于我们的三角形：

```text
真实区域：

       /\
      /  \
     /    \
    /______\


bounds：

┌────────────┐
│     /\     │
│    /  \    │
│   /____\   │
└────────────┘
```

这就是计算机图形里很常见的 **bounding rectangle / bounding box（外接矩形）**。所以：

```kotlin
outline.bounds
```

**不代表“真实轮廓就是这个矩形”。**它只是在说：“至少有这样一个矩形，可以把整个轮廓包起来。”

这个区别以后非常重要，尤其到了：

* 碰撞判断；
* 手势命中；
* Path 测量；
* 自定义 Layout；
* 图形变换。

我们现在只先埋下这个概念。

#### 十、回头解决上一阶段你和我争论的那个问题

现在应该可以非常精确地区分 `Shape` 和 `Outline` 了。例如：

```kotlin
private object TriangleOutlineShape : Shape
```

这是一个长期存在的规则对象。它里面写着：

```kotlin
size.width / 2f
size.width
size.height
```

这些确实是**算法表达式**。但只有当 Compose 调用：

```kotlin
createOutline(
    size = Size(900f, 300f),
    ...
)
```

以后，这次执行中的 Path 才真正得到：

```text
moveTo(450, 0)
lineTo(900, 300)
lineTo(0, 300)
close
```

然后产生：

```kotlin
Outline.Generic(path)
```

所以这里有三个层级，最好彻底分开：

```text
第一层：Shape 对象
TriangleOutlineShape

    ↓ 持有算法规则


第二层：createOutline() 执行
拿到了本次真实 Size
开始计算实际坐标

    ↓


第三层：Outline 对象
Outline.Generic(path)

其中的 Path 已经包含
本次计算出来的几何路径
```

你上次说“源码里面仍然写的是 `size.width`，怎么看都像规则”，这个观察本身没有错；错的是把**函数源码**和**函数执行后的对象内容**放到了同一个时间点来看。这次实验之后，这个问题基本就可以彻底结束了。

#### 十一、三种 Outline 为什么不是“高级程度递增”？

这里也很容易产生一个错误观念：

```text
Rectangle = 初级
Rounded = 中级
Generic = 高级
```

**不要这么理解。**正确理解是：它们是三种不同的几何表达工具，选择的是“最适合当前形状的表达”，不是“越复杂越高级”。普通矩形：

```kotlin
Outline.Rectangle(...)
```

就是最佳表达。圆角矩形：

```kotlin
Outline.Rounded(...)
```

就是最佳表达。三角形、星形、波浪、聊天气泡尾巴、不规则缺口：

```kotlin
Outline.Generic(path)
```

才是合适表达。这跟数据结构选择很像。你不会因为 `HashMap` 比一个 `Int` 复杂，就认为任何整数都应该用 `HashMap` 保存。**表达能力越强，不意味着任何时候越好。**

### 6.1 阶段三：Path——真正建立二维路径的心智模型

老哥，这一阶段是 **6.1 最核心的一段**。阶段一、二其实都是在给它搭桥：我们先知道 `Shape` 最终生成 `Outline`，然后知道复杂边界会进入 `Outline.Generic(Path)`；现在终于可以把 `Path` 本身拆开。

而且先更新一个很重要的 API 细节：**在你现在这代 Compose API 里，二次贝塞尔应该优先使用 `quadraticTo()`。旧的 `quadraticBezierTo()` 已经被标记为 Deprecated；当前 API 同时提供 `quadraticTo()`、`cubicTo()`、`arcTo()`、`addRect()`、`addOval()`、`Path.combine()` 等。** ([Android Git Repositories][1])

这一阶段我们要真正吃透五件事：Path 的“当前点”、`moveTo / lineTo / close`、一个 Path 中的多个 contour、二次/三次贝塞尔、圆弧与组合操作。`PathOperation` 我也会讲到，但不会把它升级成一门计算几何课。

---

#### 一、先把 Path 从“形状”这个词里解放出来

前两阶段为了方便，我们一直说：Path 用来描述复杂形状。这句话没错，但不够精确。更准确的理解是：**`Path` 是一组有顺序的二维几何路径指令。**

官方 Compose 绘制文档也是这样定位它的：Path 是一系列数学指令，之后可以交给 `drawPath()` 真正绘制。我们现在还没进入 `Canvas / DrawScope`，所以暂时把它包装进 `Outline.Generic` 给 Shape 使用；到了 6.2，同一个 `Path` 会直接成为绘制对象。([Android Developers][2]) 也就是说，你不要脑补成：

```text
Path = 一张已经画好的图
```

而应该想成：

```text
Path
=
从这里开始
→ 走直线到这里
→ 再沿曲线走到这里
→ 再走……
→ 最后闭合
```

最核心的概念其实不是 API，而是：**Path 内部存在“当前点”。**后面绝大多数 API 都是在回答：从当前点开始，下一步怎么走？

```kotlin
private enum class PathDemoType {
    Polygon,
    Quadratic,
    Cubic,
    Arc,
    MultiContour,
    TicketCutout
}

/**
 * 6.1 阶段三：
 *
 * 使用不同 Path 构造方式生成 Outline.Generic，
 * 重点观察 Path 本身的几何行为。
 */
private class PathDemoShape(
    private val type: PathDemoType
) : Shape {

    override fun createOutline(
        size: Size,
        layoutDirection: LayoutDirection,
        density: Density
    ): Outline {
        val path = when (type) {
            PathDemoType.Polygon -> createPolygonPath(size)
            PathDemoType.Quadratic -> createQuadraticPath(size)
            PathDemoType.Cubic -> createCubicPath(size)
            PathDemoType.Arc -> createArcPath(size)
            PathDemoType.MultiContour -> createMultiContourPath(size)
            PathDemoType.TicketCutout -> createTicketPath(size)
        }

        return Outline.Generic(path)
    }
}

/**
 * 直线构成的五边形。
 * 用于观察：moveTo -> lineTo -> close
 */
private fun createPolygonPath(size: Size): Path {
    val w = size.width
    val h = size.height

    return Path().apply {
        moveTo(x = w * 0.5f, y = 0f)
        lineTo(x = w, y = h * 0.38f)
        lineTo(x = w * 0.8f, y = h)
        lineTo(x = w * 0.2f, y = h)
        lineTo(x = 0f, y = h * 0.38f)
        close()
    }
}

/**
 * 顶边是一条二次贝塞尔曲线。
 * 当前点 P0：(0, h * 0.72)
 * 控制点 P1：(w / 2, 0)
 * 终点 P2：(w, h * 0.72)
 */
private fun createQuadraticPath(size: Size): Path {
    val w = size.width
    val h = size.height

    return Path().apply {
        moveTo(x = 0f, y = h)
        lineTo(x = 0f, y = h * 0.72f)
        quadraticTo(x1 = w * 0.5f, y1 = 0f, x2 = w, y2 = h * 0.72f)
        lineTo(x = w, y = h)
        close()
    }
}

/**
 * 顶边是一条三次贝塞尔曲线。
 * 当前点 P0：(0, h * 0.55)
 * 控制点 P1：(w * 0.25, 0)
 * 控制点 P2：(w * 0.75, h)
 * 终点 P3：(w, h * 0.45)
 */
private fun createCubicPath(size: Size): Path {
    val w = size.width
    val h = size.height

    return Path().apply {
        moveTo(x = 0f, y = h)
        lineTo(x = 0f, y = h * 0.55f)
        cubicTo(x1 = w * 0.25f, y1 = 0f, x2 = w * 0.75f, y2 = h, x3 = w, y3 = h * 0.45f)
        lineTo(x = w, y = h)
        close()
    }
}

/**
 * 顶部使用半个椭圆弧。
 */
private fun createArcPath(size: Size): Path {
    val w = size.width
    val h = size.height

    val ovalBounds = Rect(
        left = 0f,
        top = 0f,
        right = w,
        bottom = h
    )

    return Path().apply {
        moveTo(x = 0f, y = h)
        lineTo(x = 0f, y = h * 0.5f)
        arcTo(rect = ovalBounds, startAngleDegrees = 180f, sweepAngleDegrees = 180f, forceMoveTo = false)
        lineTo(x = w, y = h)
        close()
    }
}

/**
 * 一个 Path 中放入两个彼此分离的 contour。
 */
private fun createMultiContourPath(size: Size): Path {
    val w = size.width
    val h = size.height

    return Path().apply {
        addRect(
            Rect(
                left = 0f,
                top = h * 0.15f,
                right = w * 0.40f,
                bottom = h * 0.85f
            )
        )

        addOval(
            Rect(
                left = w * 0.60f,
                top = h * 0.15f,
                right = w,
                bottom = h * 0.85f
            )
        )
    }
}

/**
 * 真实一点的例子：
 *
 * 一个矩形主体减去左右两个圆形区域，
 * 得到票券式缺口。
 */
private fun createTicketPath(size: Size): Path {
    val w = size.width
    val h = size.height

    val outerPath = Path().apply {
        addRect(
            Rect(
                left = 0f,
                top = 0f,
                right = w,
                bottom = h
            )
        )
    }

    val radius = h * 0.18f

    val cutoutPath = Path().apply {
        addOval(
            Rect(
                left = -radius,
                top = h / 2f - radius,
                right = radius,
                bottom = h / 2f + radius
            )
        )

        addOval(
            Rect(
                left = w - radius,
                top = h / 2f - radius,
                right = w + radius,
                bottom = h / 2f + radius
            )
        )
    }

    return Path.combine(
        operation = PathOperation.Difference,
        path1 = outerPath,
        path2 = cutoutPath
    )
}
```

#### 三、`moveTo()`：只移动“笔尖”，不产生线段

第一段：

```kotlin
moveTo(
    x = w * 0.5f,
    y = 0f
)
```

执行之前可以把 Path 想象成还没有真正开始走。`moveTo()` 的意思不是：从 `(0, 0)` 画到这里。而是：**把当前点移动到这里，并把这里作为当前 contour 的起点。**所以：

```kotlin
moveTo(100f, 50f)
```

本身没有：

```text
(0,0) ───────── (100,50)
```

这条线。它只是把“笔尖”拿起来，放到 `(100, 50)`。这个“笔尖模型”虽然不是 API 的严格内部实现，但作为 Path 的学习心智模型非常好用，因为接下来 `lineTo()`、贝塞尔、`arcTo()` 都跟**当前点**有关。Compose 当前 Path API 中 `moveTo()`、`lineTo()`、曲线和相对版本都仍然存在。([Android Git Repositories][1])

---

#### 四、`lineTo()`：从当前点画到新点，同时更新当前点

例如：

```kotlin
moveTo(
    x = w * 0.5f,
    y = 0f
)

lineTo(
    x = w,
    y = h * 0.38f
)
```

第一次 `moveTo()` 后：

```text
当前点
P0 = (w / 2, 0)
```

随后：

```kotlin
lineTo(w, h * 0.38f)
```

做的是：

```text
P0 ─────────→ P1
```

然后：

```text
当前点 = P1
```

再执行：

```kotlin
lineTo(
    x = w * 0.8f,
    y = h
)
```

就不是从最开始的 P0 过去，而是：

```text
P1 ─────────→ P2
```

所以真正正确的 Path 心智模型应该是：

```text
当前点
   ↓
执行一条路径命令
   ↓
产生新的几何段
   ↓
终点成为新的当前点
   ↓
下一条命令继续
```

这也是为什么 Path 是“有顺序的命令”，不是一堆互不相关的坐标点。

---

#### 五、`close()` 不是“结束 Path”

这是一个非常值得认真区分的地方。我们的五边形最后：

```kotlin
close()
```

意思不是：Path 到此永久结束，再也不能添加东西。而是：**把当前 contour 的终点与这个 contour 的起点连接起来，使它闭合。**例如：

```text
P0
 / \
/   \
P4   P1
|     |
P3───P2
```

执行到最后：

```text
当前点 = P4
起点 = P0
```

`close()` 会把：

```text
P4 → P0
```

这一条缺失边补上。之后这个 `Path` 仍然可以继续加入新的 contour。所以：`close()` 关闭的是**当前 contour**，不是销毁或冻结整个 Path。这马上就引出了今天第二个很重要的概念。

---

#### 六、一个 Path 并不等于“一个轮廓”：contour

这次代码里专门放了：

```kotlin
private fun createMultiContourPath(size: Size): Path {
    return Path().apply {
        addRect(...)
        addOval(...)
    }
}
```

你运行后应该看到：

```text
┌──────────┐               ╭────────╮
│          │               │        │
│          │               │        │
└──────────┘               ╰────────╯
```

中间完全没有连接。但它们仍然属于：

```kotlin
同一个 Path
```

这就是 **contour**。可以把：

```text
Path
```

理解成一本路径集合，而：

```text
contour
```

是里面一条连续的路径。例如：

```text
Path

Contour 1:
A → B → C → A

Contour 2:
D → 曲线 → E → D

Contour 3:
一个圆
```

三条彼此完全不相连，但都属于同一个 Path。这在以后非常实用。例如一个图标可能由多个互不连接的部分组成；一个字形也完全可能包含多个独立区域。

---

#### 七、第二次 `moveTo()` 为什么非常重要？

你甚至可以不用 `addRect()` / `addOval()`，纯手写多个 contour：

```kotlin
Path().apply {
    moveTo(0f, 0f)
    lineTo(100f, 0f)
    lineTo(100f, 100f)
    close()

    moveTo(200f, 0f)
    lineTo(300f, 0f)
    lineTo(300f, 100f)
    close()
}
```

第二次：

```kotlin
moveTo(200f, 0f)
```

不是从上一个形状拉一根线过去。它相当于：把笔抬起来，到另一个地方重新开始一条 contour。因此可以用一个非常直观的模型：

```text
lineTo
= 笔贴着纸移动

moveTo
= 抬笔换位置
```

以后你看到 SVG、VectorDrawable 的 PathData，这套直觉同样会继续有用。

---

#### 八、二次贝塞尔：`quadraticTo()`

现在正式进入曲线。当前 Compose API 中应该优先写：

```kotlin
quadraticTo(
    x1 = ...,
    y1 = ...,
    x2 = ...,
    y2 = ...
)
```

老代码里经常能看到的：

```kotlin
quadraticBezierTo(...)
```

在当前 API 已经被标记为 Deprecated，并由 `quadraticTo()` 取代，所以我们的新课直接采用新 API。([Android Git Repositories][1]) 二次贝塞尔只需要理解三个点：

```text
P0 = 起点
P1 = 控制点
P2 = 终点
```

但注意一个非常关键的事情：**P0 不写在 `quadraticTo()` 参数里。**为什么？因为：

```text
P0 就是 Path 当前点。
```

我们的代码：

```kotlin
lineTo(
    x = 0f,
    y = h * 0.72f
)

quadraticTo(
    x1 = w * 0.5f,
    y1 = 0f,
    x2 = w,
    y2 = h * 0.72f
)
```

执行 `quadraticTo()` 时：

```text
P0 = (0, h × 0.72)
P1 = (w × 0.5, 0)
P2 = (w, h × 0.72)
```

几何直觉大概是：

```text
                P1
                ●
              /   \
            /       \
P0 ●──────╯           ╰──────● P2
```

但我要强调：**曲线通常并不会经过控制点 P1。**P1 不是：“中间必须经过的点。”而是：**把曲线向自己这个方向拉扯的控制点。**这就是“控制点”真正的直觉。

---

#### 九、请你一定亲手移动二次贝塞尔的控制点

原代码：

```kotlin
quadraticTo(
    x1 = w * 0.5f,
    y1 = 0f,
    x2 = w,
    y2 = h * 0.72f
)
```

先改成：

```kotlin
quadraticTo(
    x1 = w * 0.5f,
    y1 = h * 0.60f,
    x2 = w,
    y2 = h * 0.72f
)
```

你会看到顶边明显变平。再改：

```kotlin
quadraticTo(
    x1 = w * 0.15f,
    y1 = 0f,
    x2 = w,
    y2 = h * 0.72f
)
```

曲线最高、最明显的“拉扯”会偏向左边。这比背任何公式都有效。二次贝塞尔真正需要的直觉就是：**起点和终点确定“从哪儿到哪儿”；控制点决定“中间怎么弯”。**目前没有必要学习贝塞尔参数方程。

---

#### 十、三次贝塞尔：`cubicTo()`

三次贝塞尔比二次贝塞尔多一个控制点：

```text
P0 = 起点
P1 = 第一个控制点
P2 = 第二个控制点
P3 = 终点
```

同样：

```text
P0 不写
```

因为 P0 已经是当前点。代码：

```kotlin
cubicTo(
    x1 = w * 0.25f,
    y1 = 0f,
    x2 = w * 0.75f,
    y2 = h,
    x3 = w,
    y3 = h * 0.45f
)
```

实际是：

```text
P0 = (0, h × 0.55)
P1 = (w × 0.25, 0)
P2 = (w × 0.75, h)
P3 = (w, h × 0.45)
```

两个控制点分别可以更精细地控制曲线两端的运动趋势，所以三次贝塞尔特别适合这种：

```text
~~~~~~~ 波浪
```

以及复杂的图标、Vector Path、圆角平滑连接、自由曲线等。官方当前 Compose Shapes 文档在解释多边形平滑圆角时，也明确提到内部会使用多段 cubic curves 来完成平滑过渡。([Android Developers][3])

---

#### 十一、二次和三次到底什么时候选？

不要死记：

```text
简单曲线 → quadratic
复杂曲线 → cubic
```

更准确一点：**二次贝塞尔只有一个控制点，所以适合只需要一次整体弯曲趋势的曲线；三次贝塞尔有两个控制点，因此可以分别控制曲线离开起点和接近终点时的趋势，表达能力明显更强。**例如这种简单拱顶：

```text
    ______
  /        \
```

`quadraticTo()` 就很好。而这种：

```text
   ╭────
───╯
       ╭────
───────╯
```

明显更适合 cubic。实际 App 开发中你不需要有一种执念：能 cubic 就绝不用 quadratic。哪个自然就用哪个。

#### 十二、`arcTo()`：贝塞尔不是画圆弧的唯一办法

现在看：

```kotlin
arcTo(
    rect = ovalBounds,
    startAngleDegrees = 180f,
    sweepAngleDegrees = 180f,
    forceMoveTo = false
)
```

这个 API 的理解重点不在“arc = 圆”。它实际上是在说：**先定义一个椭圆所在的矩形，然后取这个椭圆周长上的一段弧。**所以：

```kotlin
val ovalBounds = Rect(
    left = 0f,
    top = 0f,
    right = w,
    bottom = h
)
```

这里定义的是：

```text
┌─────────────────────────┐
│        ╭─────╮          │
│     ╭──╯     ╰──╮       │
│    │    哈哈     │      │
│     ╰──╮     ╭──╯       │
│        ╰─────╯          │
└─────────────────────────┘
```

这个 `Rect` 是椭圆的 bounding rectangle。然后：

```kotlin
startAngleDegrees = 180f
sweepAngleDegrees = 180f
```

取其中半圈。Compose 当前 `Path` API 的 `arcTo()` 参数仍然正是：

```text
Rect
startAngleDegrees
sweepAngleDegrees
forceMoveTo
```

([Android Git Repositories][1])

---

#### 十三、`forceMoveTo` 是什么？

这是 `arcTo()` 最容易让人蒙的一项。我们现在写：

```kotlin
forceMoveTo = false
```

可以先把它理解为：**这条圆弧属于当前 contour，继续当前路径。**也就是前面的：

```kotlin
lineTo(
    x = 0f,
    y = h * 0.5f
)
```

走到圆弧起点附近以后，接着沿圆弧继续走。而如果你的目标是：这段圆弧自己开始一条新的 contour，不和之前的当前路径连起来，才更接近 `forceMoveTo = true` 的用途。目前把这一层掌握即可，阶段三不值得围绕这个 Boolean 钻半小时。

---

#### 十四、`addRect()` / `addOval()` 和 `lineTo()` 是什么关系？

阶段二你已经理解：

```kotlin
Rect
RoundRect
Path
```

是不同的几何表达。现在 Path 自己又提供：

```kotlin
addRect(...)
addOval(...)
addRoundRect(...)
```

当前 API 也确实提供这些方法。([Android Git Repositories][1]) 为什么？因为你当然可以手写一个矩形：

```kotlin
moveTo(0f, 0f)
lineTo(w, 0f)
lineTo(w, h)
lineTo(0f, h)
close()
```

但是如果你的真实意思就是：往这个 Path 里加入一个完整矩形 contour。那么：

```kotlin
addRect(
    Rect(
        left = 0f,
        top = 0f,
        right = w,
        bottom = h
    )
)
```

语义明显更直接。所以这类 API 可以理解成：**快速往 Path 中加入已知几何轮廓。**不是新的图形体系。

---

#### 十五、`addOval()` 为什么也很好理解？

例如：

```kotlin
addOval(
    Rect(
        left = w * 0.60f,
        top = h * 0.15f,
        right = w,
        bottom = h * 0.85f
    )
)
```

这个 `Rect` 不是你最终要画出来的矩形。而是在说：这个椭圆必须被完整包在这个 Rect 里面。例如：

```text
Rect
┌────────────────────┐
│    ╭────────╮      │
│  ╭─╯        ╰─╮    │
│  ╰─╮        ╭─╯    │
│    ╰────────╯      │
└────────────────────┘
```

因此你会发现 `Rect` 在图形编程里非常重要。它不一定代表：我要画矩形。它经常只是：**某个图形的几何边界框。**`arcTo()`、`addOval()` 都体现了这个模型。

---

#### 十六、真正很实用的高级能力：`PathOperation`

现在来到票券：

```text
┌──────────────────────────────┐
│                              │
 )                            (
│                              │
└──────────────────────────────┘
```

我们没有一点一点手算这个缺口曲线。而是先：

```kotlin
val outerPath = Path().apply {
    addRect(...)
}
```

得到 A：

```text
████████████████████████
████████████████████████
████████████████████████
```

再创建 B：

```kotlin
val cutoutPath = Path().apply {
    addOval(...)
    addOval(...)
}
```

然后：

```kotlin
Path.combine(
    operation = PathOperation.Difference,
    path1 = outerPath,
    path2 = cutoutPath
)
```

意思非常直接：

```text
A - B
```

也就是：**从 path1 中减去 path2。**

Compose 当前 `PathOperation` 官方定义了 `Difference`、`Intersect`、`ReverseDifference`、`Union`、`Xor` 五种组合策略，而 `Path.combine()` 就是利用这些操作把两个 Path 组合成新的 Path。([Android Developers][4])

---

#### 十七、PathOperation 不需要现在全部练一遍

你现在只需要形成这张图：

```text
Difference
A - B
从 A 挖掉 B

Intersect
A ∩ B
只留下两者重叠

Union
A ∪ B
把两者合并

Xor
只保留“不重叠”的部分

ReverseDifference
B - A
```

官方当前 API 对这些操作就是这个定义。([Android Developers][4]) 真实业务最容易遇到的就是：

```kotlin
PathOperation.Difference
```

因为：

```text
卡片挖洞
票券缺口
圆环
镂空区域
蒙版
```

都非常自然。所以我们今天实际跑 `Difference`，其他四种知道存在即可。

---

#### 十八、一个非常关键的区别：contour 和 PathOperation 不是一回事

这个地方如果不讲，很容易以后混掉。我们这里：

```kotlin
val cutoutPath = Path().apply {
    addOval(leftCircle)
    addOval(rightCircle)
}
```

已经是：

```text
一个 Path
两个 contour
```

但是：

```text
两个 contour
≠
自动执行减法
```

它们只是都被放进了这个 Path。真正执行：

```text
outer - cutouts
```

的是：

```kotlin
Path.combine(
    PathOperation.Difference,
    outerPath,
    cutoutPath
)
```

因此：**Contour 解决“一个 Path 内包含哪些连续路径”；PathOperation 解决“两个 Path 的区域怎么做集合运算”。**这两个层次必须分开。

---

#### 十九、为什么代码里尽量用 `size.width * 比例`？

你应该已经注意到，我们这次很少写：

```kotlin
lineTo(300f, 100f)
```

更多写：

```kotlin
lineTo(
    x = w * 0.8f,
    y = h
)
```

这是刻意的。因为 Shape 的核心优势正是：

```text
同一套规则
+
不同 Size
=
不同尺寸下正确生成轮廓
```

如果你大量写：

```kotlin
100f
200f
300f
```

那么一个在：

```text
300 × 100
```

上正常的 Shape，换成：

```text
900 × 300
```

可能直接比例崩坏。所以以后做**随组件尺寸缩放的图形**，最常见的方式就是：

```kotlin
val w = size.width
val h = size.height

w * 0.25f
h * 0.5f
w * 0.8f
```

而如果某个尺寸是产品设计明确规定的固定视觉尺寸，例如：

```text
缺口半径 = 12.dp
```

那才是：

```kotlin
with(density) {
    12.dp.toPx()
}
```

这两种坐标来源以后会经常混用：

```text
比例坐标
+
dp → px 的固定视觉尺寸
```

这就是比较真实的 Custom Shape。

#### 二十一、现在把 Path 的完整心智模型拼起来

到这里，我希望你脑中不再是：


而应该是：

```text
Path
│
```

### 6.1 阶段四：从 Path 实验到真正可复用的 `Shape`

前面三阶段我们已经分别解决了：`Shape → Outline` 的职责关系、三种 `Outline` 的表达层级，以及 `Path` 如何用直线、贝塞尔、圆弧、多个 contour 和布尔运算构造复杂几何。按照最初大纲，这一阶段要把这些东西真正合起来：**写一个不是“只在某个固定尺寸上碰巧能跑”的 Shape，而是能够适应组件尺寸、屏幕密度和 LTR/RTL 的业务 Shape。**这正好也是 6.1 从 API 学习走向实际开发的关键一步。

我们继续使用官方 `Shape` 给我们的三个运行时参数：`size` 是当前 Shape 边界的实际尺寸，`layoutDirection` 是当前布局方向，`density` 是当前屏幕密度。也就是说，一个真正具有适应能力的 Shape，其实已经天然拿到了完成适配最需要的信息。([Android Developers][1])

这一阶段建立：`Sec01C_AdaptiveBubbleShape.kt`

案例是一个**聊天气泡 Shape**。它具有四个真实业务性质：

1. 圆角、尾巴宽度和高度由 `Dp` 配置；
2. 实际几何计算发生时转换成 px；
3. 气泡可以指定尾巴位于逻辑 `Start` 或 `End`；
4. 同一个 Shape 在 LTR / RTL 下自动镜像，而且组件尺寸过小时不会让路径坐标失控。

#### 一、先看完整运行代码

```kotlin
private const val TAG_SEC01C = "Sec01C"

private enum class BubbleTailSide {
    Start,
    End
}

/**
 * 一个可以真正复用的聊天气泡 Shape。
 *
 * cornerRadius / tailWidth / tailHeight：
 * 表示设计层面的固定视觉尺寸，因此使用 Dp。
 *
 * tailSide：
 * 使用 Start / End，而不是 Left / Right，
 * 因此可以跟随 LayoutDirection 自动镜像。
 */
private class AdaptiveBubbleShape(
    private val tailSide: BubbleTailSide,
    private val cornerRadius: Dp = 20.dp,
    private val tailWidth: Dp = 18.dp,
    private val tailHeight: Dp = 28.dp
) : Shape {

    override fun createOutline(
        size: Size,
        layoutDirection: LayoutDirection,
        density: Density
    ): Outline {
        val requestedRadiusPx = with(density) {
            cornerRadius.toPx()
        }.coerceAtLeast(0f)

        val requestedTailWidthPx = with(density) {
            tailWidth.toPx()
        }.coerceAtLeast(0f)

        val requestedTailHeightPx = with(density) {
            tailHeight.toPx()
        }.coerceAtLeast(0f)

        /*
         * Start / End 是逻辑方向。
         */
        val tailOnLeft = when (tailSide) {
            BubbleTailSide.Start ->
                layoutDirection == LayoutDirection.Ltr

            BubbleTailSide.End ->
                layoutDirection == LayoutDirection.Rtl
        }

        /*
         * 防止极小组件中：
         * tailWidth 比整个 Shape 都宽。
         *
         * 这里把尾巴最多限制为总宽度的 28%。
         * 28% 不是 Compose 规则，而是这个 Shape 自己的设计策略。
         */
        val actualTailWidth = requestedTailWidthPx.coerceIn(
            minimumValue = 0f,
            maximumValue = size.width * 0.28f
        )

        /*
         * 尾巴会占用一部分横向空间。
         *
         * 如果尾巴在左：
         *
         *      body
         *      ↓
         *    ┌─────────────┐
         *   <              │
         *    └─────────────┘
         *
         * bodyLeft = tailWidth
         *
         * 如果尾巴在右则反过来。
         */
        val bodyLeft = if (tailOnLeft) {
            actualTailWidth
        } else {
            0f
        }

        val bodyRight = if (tailOnLeft) {
            size.width
        } else {
            size.width - actualTailWidth
        }

        val bodyWidth = (bodyRight - bodyLeft)
            .coerceAtLeast(0f)

        /*
         * 圆角半径不能大到超过：
         *
         * bodyWidth / 2
         * height / 2
         *
         * 否则小组件上的几何关系会失控。
         */
        val actualRadius = requestedRadiusPx.coerceIn(
            minimumValue = 0f,
            maximumValue = minOf(
                bodyWidth / 2f,
                size.height / 2f
            )
        )

        /*
         * 圆角占用了上下两端以后，
         * 中间剩下的直线区域才适合放尾巴。
         */
        val availableSideHeight =
            (size.height - actualRadius * 2f)
                .coerceAtLeast(0f)

        val actualTailHeight = requestedTailHeightPx.coerceIn(
            minimumValue = 0f,
            maximumValue = availableSideHeight
        )

        /*
         * 把尾巴垂直居中。
         *
         * 因为 actualTailHeight 已经受 availableSideHeight 限制，
         * 所以不会侵入上下圆角。
         */
        val tailTop =
            (size.height - actualTailHeight) / 2f

        val tailBottom =
            tailTop + actualTailHeight

        val tailTipY =
            (tailTop + tailBottom) / 2f

        println(
            "$TAG_SEC01C " +
                "size=$size, " +
                "direction=$layoutDirection, " +
                "tailSide=$tailSide, " +
                "tailOnLeft=$tailOnLeft, " +
                "radius=$actualRadius, " +
                "tailWidth=$actualTailWidth, " +
                "tailHeight=$actualTailHeight"
        )

        val path = if (tailOnLeft) {
            createLeftTailPath(
                size = size,
                bodyLeft = bodyLeft,
                bodyRight = bodyRight,
                radius = actualRadius,
                tailTop = tailTop,
                tailBottom = tailBottom,
                tailTipY = tailTipY
            )
        } else {
            createRightTailPath(
                size = size,
                bodyLeft = bodyLeft,
                bodyRight = bodyRight,
                radius = actualRadius,
                tailTop = tailTop,
                tailBottom = tailBottom,
                tailTipY = tailTipY
            )
        }

        return Outline.Generic(path)
    }

    private fun createLeftTailPath(
        size: Size,
        bodyLeft: Float,
        bodyRight: Float,
        radius: Float,
        tailTop: Float,
        tailBottom: Float,
        tailTipY: Float
    ): Path {
        return Path().apply {

            /*
             * 从左上圆角结束位置开始，
             * 顺时针绕完整个气泡。
             */
            moveTo(
                x = bodyLeft + radius,
                y = 0f
            )

            // 顶边
            lineTo(
                x = bodyRight - radius,
                y = 0f
            )

            // 右上圆角
            quadraticTo(
                x1 = bodyRight,
                y1 = 0f,
                x2 = bodyRight,
                y2 = radius
            )

            // 右边
            lineTo(
                x = bodyRight,
                y = size.height - radius
            )

            // 右下圆角
            quadraticTo(
                x1 = bodyRight,
                y1 = size.height,
                x2 = bodyRight - radius,
                y2 = size.height
            )

            // 底边
            lineTo(
                x = bodyLeft + radius,
                y = size.height
            )

            // 左下圆角
            quadraticTo(
                x1 = bodyLeft,
                y1 = size.height,
                x2 = bodyLeft,
                y2 = size.height - radius
            )

            // 左侧向上走到尾巴下沿
            lineTo(
                x = bodyLeft,
                y = tailBottom
            )

            // 尾巴尖端
            lineTo(
                x = 0f,
                y = tailTipY
            )

            // 回到气泡主体
            lineTo(
                x = bodyLeft,
                y = tailTop
            )

            // 继续向左上角
            lineTo(
                x = bodyLeft,
                y = radius
            )

            // 左上圆角
            quadraticTo(
                x1 = bodyLeft,
                y1 = 0f,
                x2 = bodyLeft + radius,
                y2 = 0f
            )

            close()
        }
    }

    private fun createRightTailPath(
        size: Size,
        bodyLeft: Float,
        bodyRight: Float,
        radius: Float,
        tailTop: Float,
        tailBottom: Float,
        tailTipY: Float
    ): Path {
        return Path().apply {

            moveTo(
                x = bodyLeft + radius,
                y = 0f
            )

            // 顶边
            lineTo(
                x = bodyRight - radius,
                y = 0f
            )

            // 右上圆角
            quadraticTo(
                x1 = bodyRight,
                y1 = 0f,
                x2 = bodyRight,
                y2 = radius
            )

            // 右边走到尾巴上沿
            lineTo(
                x = bodyRight,
                y = tailTop
            )

            // 尾巴尖端
            lineTo(
                x = size.width,
                y = tailTipY
            )

            // 回到气泡主体
            lineTo(
                x = bodyRight,
                y = tailBottom
            )

            // 继续向右下角
            lineTo(
                x = bodyRight,
                y = size.height - radius
            )

            // 右下圆角
            quadraticTo(
                x1 = bodyRight,
                y1 = size.height,
                x2 = bodyRight - radius,
                y2 = size.height
            )

            // 底边
            lineTo(
                x = bodyLeft + radius,
                y = size.height
            )

            // 左下圆角
            quadraticTo(
                x1 = bodyLeft,
                y1 = size.height,
                x2 = bodyLeft,
                y2 = size.height - radius
            )

            // 左边
            lineTo(
                x = bodyLeft,
                y = radius
            )

            // 左上圆角
            quadraticTo(
                x1 = bodyLeft,
                y1 = 0f,
                x2 = bodyLeft + radius,
                y2 = 0f
            )

            close()
        }
    }
}
```

#### 二、这个案例和阶段一最大的区别：参数开始分成两类

阶段一我们写：

```kotlin
CutTopRightShape(
    cutSize = 32.dp
)
```

几何非常简单，所以你可能还不会特别注意参数来源。现在这个 Shape 中其实出现了两种性质完全不同的尺寸。第一种是设计尺寸：

```kotlin
cornerRadius = 20.dp
tailWidth = 18.dp
tailHeight = 30.dp
```

产品设计表达的意思通常就是：圆角视觉上保持约 20dp，不管组件最终宽 200dp 还是 400dp。这种量很适合使用 `Dp`。但是到了：

```kotlin
createOutline(...)
```

真正进行 Path 几何运算时，我们面对的是：

```kotlin
size.width
size.height
```

这些已经是当前图形空间中的 `Float` 像素值。因此才转换：

```kotlin
val requestedRadiusPx = with(density) {
    cornerRadius.toPx()
}
```

`density` 正是 `Shape.createOutline()` 官方提供的当前屏幕密度参数，所以 Shape 可以在这里完成这种设计尺寸到实际几何坐标的转换。([Android Developers][1]) 另一种则是**相对尺寸**。例如上一阶段：

```kotlin
x = size.width * 0.5f
```

表达的不是固定视觉距离，而是：不管多宽，我永远取中间。所以以后写 Custom Shape 时，经常要混合两套思路：

```text
固定视觉要求
20.dp、12.dp、8.dp
        ↓ Density
     实际 px


相对几何要求
宽度的 50%
高度的 30%
        ↓
size.width * 0.5f
size.height * 0.3f
```

这是第一个真正值得带进实际项目的能力。

#### 三、`Start / End` 和 `Left / Right` 必须正式分开

这个案例最核心的一段之一是：

```kotlin
val tailOnLeft = when (tailSide) {
    BubbleTailSide.Start ->
        layoutDirection == LayoutDirection.Ltr

    BubbleTailSide.End ->
        layoutDirection == LayoutDirection.Rtl
}
```

为什么不干脆定义：

```kotlin
enum class BubbleTailSide {
    Left,
    Right
}
```

因为这是两套完全不同的产品语义。如果产品说：尾巴永远出现在屏幕物理左侧。那确实应该是：

```text
Left
```

LTR / RTL 都不应该改变它。但是聊天界面更常见的逻辑很可能是：尾巴位于消息的 Start 或 End。此时 Start / End 是**逻辑方向**。Compose 当前的 `LayoutDirection` 就明确区分 `Ltr` 和 `Rtl`：LTR 水平方向从左到右，RTL 则从右到左。([Android Developers][2]) 所以四种组合是：

```text
             LTR             RTL

Start        Left            Right

End          Right           Left
```

这张关系你不需要死背，理解 Start / End 的含义自然就能推出来。

#### 四、为什么绝对不要把 `layoutDirection` 自己塞进构造函数？

我们没有这么写：

```kotlin
AdaptiveBubbleShape(
    tailSide = Start,
    layoutDirection = LayoutDirection.Ltr
)
```

这是故意的。因为 `Shape` 接口本身已经规定：

```kotlin
createOutline(
    size,
    layoutDirection,
    density
)
```

由调用时的当前环境把 `LayoutDirection` 交给 Shape。([Android Developers][1]) 所以我们的对象只保存：

```kotlin
BubbleTailSide.Start
```

也就是：**这个 Shape 自身稳定的设计规则。**至于这一次到底运行在：

```text
LTR
```

还是：

```text
RTL
```

属于：**这次生成 Outline 的运行环境。**这一点其实和阶段一讲 `Size` 是一个完全相同的设计思想。不要创建：

```kotlin
BubbleShape(
    width = 300,
    height = 100
)
```

因为 `Size` 会传进来。同样也没必要创建：

```kotlin
BubbleShape(
    layoutDirection = Ltr
)
```

因为 `LayoutDirection` 也会传进来。因此现在 `Shape` 的完整模型就真的可以写成：

```text
            Shape 自己保存
       稳定的“形状设计参数”
               │
               │
               ↓
createOutline(
    size,               ← 当前组件尺寸
    layoutDirection,    ← 当前布局方向
    density             ← 当前屏幕密度
)
               │
               ↓
        计算本次几何坐标
               │
               ↓
             Path
               │
               ↓
       Outline.Generic
```

到阶段四，这张模型已经可以作为你长期使用 `Shape` 的正式心智模型了。

---

#### 五、现在看真正业务代码里最容易被初学者漏掉的东西：边缘 Case

假设设计稿告诉你：

```kotlin
cornerRadius = 20.dp
```

如果组件本身：

```text
高度 = 100dp
```

毫无问题。但是某天这个 Shape 被复用到了：

```text
高度 = 24dp
```

还能硬使用 20dp 半径吗？不能只想着：产品写的是 20dp，我就永远转换成 20dp。因为图形算法面对的是**实际运行尺寸**。所以代码做了：

```kotlin
val actualRadius = requestedRadiusPx.coerceIn(
    minimumValue = 0f,
    maximumValue = minOf(
        bodyWidth / 2f,
        size.height / 2f
    )
)
```

如果高度只有：

```text
40px
```

那么半径最大：

```text
20px
```

不是因为 Compose 要求你必须这么写，而是因为：一个半径如果已经超过自身短边的一半，我们原本设计的“圆角矩形主体”几何模型就开始失去意义。这就是**设计参数**和**实际几何参数**之间的区别。代码里：

```kotlin
requestedRadiusPx
```

表达：我希望是多少。而：

```kotlin
actualRadius
```

表达：在这一次实际 Size 下，最终允许是多少。这种命名也很值得借鉴。

---

#### 六、尾巴为什么同样不能直接相信传进来的 `18.dp`

我们做：

```kotlin
val actualTailWidth =
    requestedTailWidthPx.coerceIn(
        0f,
        size.width * 0.28f
    )
```

假设：

```text
组件宽度 = 40px
尾巴要求 = 50px
```

如果照单全收，主体甚至可能：

```text
bodyWidth < 0
```

然后接下来：

```kotlin
bodyRight - radius
bodyLeft + radius
```

都会开始产生完全违反原始几何假设的坐标。所以真正可复用的 Shape 必须不断问：**这个参数在当前 Size 下还合法吗？**这其实和你以后写自定义 Layout 非常像。设计要求是设计要求，运行约束是运行约束。我们这里规定：

```text
尾巴最多占整体宽度的 28%
```

这 **28% 是我给这个教学 Shape 制定的业务规则，不是什么 Compose 官方规定。**这一点很重要。不要以后看到：

```kotlin
size.width * 0.28f
```

误以为 Compose 有什么 28% 规则。没有。如果你的真实 App 视觉设计认为：

```text
最大 20%
最大固定 24dp
或者最少留下 60dp 主体
```

完全可以采用其他策略。

#### 七、尾巴高度为什么还要依赖圆角？

这部分：

```kotlin
val availableSideHeight =
    (size.height - actualRadius * 2f)
        .coerceAtLeast(0f)
```

其实体现了真正 Custom Shape 中非常重要的一种思维：**不同几何特征之间不是彼此独立的。**我们的左边：

```text
         圆角区
           ↓
      ╭────────────
      │
      │   可放尾巴
    < │
      │
      │
      ╰────────────
           ↑
         圆角区
```

如果：

```text
圆角越来越大
```

那么中间能够安全放尾巴的区域自然越来越小。所以：

```kotlin
actualTailHeight
```

不能只看：

```text
用户要求 tailHeight = 30.dp
```

还必须看：

```text
当前 height
当前 radius
```

这就是为什么到了真实 Shape，几何计算开始明显比阶段三“画一个五边形”复杂。不是 Path API 突然难了，而是：**真正困难的开始变成几何约束之间的关系。**这个认识非常重要。

#### 八、现在真正读懂左尾巴 Path

前面我们学 Path 时，一个一个 API 看。现在第一次应该尝试**整体追踪一条真实轮廓**。左尾巴气泡：

```text
       P0
       ↓
       ╭────────────────────╮
       │                    │
       │                    │
 tip ←<                     │
       │                    │
       │                    │
       ╰────────────────────╯
```

代码从：

```kotlin
moveTo(
    x = bodyLeft + radius,
    y = 0f
)
```

开始，也就是左上圆角已经结束、正式进入顶部直线的位置。

然后整个 Path **顺时针**：

```text
顶部
↓
右上角
↓
右边
↓
右下角
↓
底部
↓
左下角
↓
左侧
↓
尾巴下沿
↓
尾巴尖端
↓
尾巴上沿
↓
左侧
↓
左上角
↓
close()
```

所以你现在已经不能只是看：

```kotlin
lineTo(...)
quadraticTo(...)
```

而应该学会：“我现在在这个封闭轮廓的哪一条边上？”这就是阶段三“当前点”模型到了真实业务代码中的用途。

#### 九、我们的圆角严格来说不是数学上的标准圆弧

这里：

```kotlin
quadraticTo(
    x1 = bodyRight,
    y1 = 0f,
    x2 = bodyRight,
    y2 = radius
)
```

是在用二次贝塞尔从：

```text
(bodyRight - radius, 0)
```

弯到：

```text
(bodyRight, radius)
```

控制点放在：

```text
(bodyRight, 0)
```

这样会得到一个视觉上很自然的圆角过渡，但**它不是严格意义上的四分之一圆**。这不是 bug，是我们这次教学案例刻意选择的近似方式：它能把上一阶段的 `quadraticTo()` 真正用于业务形状，而且代码简单。

如果真实设计明确要求精确圆弧，我们可以改用合适的 arc 几何，或者在更适合的场景利用 `RoundRect` / 其他 Shape 能力。这里没有必要为了数学上完美的圆角，让“自适应 Shape”这堂课变成曲线逼近课程。

---

#### 十、为什么左右 Path 我故意写成两个函数，而没有疯狂抽象？

你可能已经看出来：

```kotlin
createLeftTailPath()
createRightTailPath()
```

里面大量代码几乎对称。理论上当然可以把坐标全部抽象，通过：

```text
mirrorX
directionMultiplier
transform
```

最后把两份代码压成一份。但是**我现在故意没这么做**。因为现阶段教学目标是让你看懂：当尾巴换边以后，Path 到底哪里改变了？如果现在为了“高级”把所有坐标都抽进一套镜像数学变换：

```kotlin
physicalX(...)
logicalX(...)
mirror(...)
```

代码可能少了二十行，但学习成本反而更高。真实项目什么时候值得抽？当这个 Shape：

* 已经经过测试；
* 几何行为稳定；
* 左右实现确认完全对称；
* 重复代码开始产生维护问题；

那时候再做镜像抽象。这是代码设计里的一个实际原则：**先把几何逻辑写清楚，再抽象；不要为了 DRY 把几何意图藏起来。**

---

#### 十一、观察 `CompositionLocalProvider` 这个实验

页面里我们写：

```kotlin
CompositionLocalProvider(
    LocalLayoutDirection provides layoutDirection
) {
    ...
}
```

它只是为了**人为切换当前这块 UI 的布局方向**，方便实验。你点：

```text
切换 LTR / RTL
```

当：

```text
tailSide = Start
```

时应该看到：

```text
LTR：
尾巴左边


RTL：
尾巴右边
```

然后把：

```text
tailSide = End
```

再测试：

```text
LTR：
尾巴右边


RTL：
尾巴左边
```

当前 Compose 官方定义的 `LayoutDirection` 就是 `Ltr` 与 `Rtl` 两种水平方向，所以这个实验实际上是在验证我们的 Start / End 映射是否正确。([Android Developers][2]) 与此同时看日志：

```text
Sec01C size=...
direction=Ltr
tailSide=Start
tailOnLeft=true
...

Sec01C size=...
direction=Rtl
tailSide=Start
tailOnLeft=false
...
```

你要重点看到：**同一个业务语义 `Start` 没有变，但物理坐标方向发生了变化。**

这个理解以后不仅用于 Shape，还会贯穿 Compose 的 padding、alignment、布局等大量 API。

---

#### 十二、为什么文字 padding 也用了 `start / end`

这里还有一个很有价值的小细节：

```kotlin
.padding(
    start = if (
        tailSide == BubbleTailSide.Start
    ) {
        34.dp
    } else {
        18.dp
    },
    end = if (
        tailSide == BubbleTailSide.End
    ) {
        34.dp
    } else {
        18.dp
    }
)
```

气泡尾巴占用了 Start 空间时：

```text
Start padding 更大
```

如果切成 RTL：

```text
Start 又自然变成物理右侧
```

于是：

```text
Shape 的 Tail Start
```

和：

```text
Content 的 Padding Start
```

使用的是**同一套逻辑方向语义**。这才是真正可国际化、可复用的组件设计。如果 Shape 写的是：

```text
Start
```

而内容却硬写：

```text
left padding = 34.dp
```

两套坐标语义就打架了。

#### 十三、现在看三个尺寸，你会看到什么？

第一个：

```kotlin
.fillMaxWidth()
.height(110.dp)
```

空间充足，基本会完整使用：

```text
20.dp radius
18.dp tailWidth
30.dp tailHeight
```

第二个：

```kotlin
.width(220.dp)
.height(82.dp)
```

还是比较正常，Shape 根据新的 `Size` 重新计算 Path。官方 `Shape.createOutline()` 的职责本身就是为“given size”创建 Outline。([Android Developers][1]) 第三个故意压成：

```kotlin
.width(90.dp)
.height(44.dp)
```

这里最值得看。设计参数完全没变：

```text
cornerRadius = 20.dp
tailWidth = 18.dp
tailHeight = 30.dp
```

但是实际：

```text
actualRadius
actualTailWidth
actualTailHeight
```

可能被压缩。这正是这节课最核心的业务能力：**Shape 参数描述“想要什么”；`createOutline()` 根据本次真实运行环境决定“最终能画成什么”。**

---

#### 十四、这里还有一个非常重要的职责边界

假设气泡太小。我们现在的 Shape 做的是：

```text
把圆角缩小
把尾巴缩小
继续生成一个合法轮廓
```

但是还有另一种选择：让布局层根本不给它这么小。例如未来真实聊天气泡组件可能本身就：

```kotlin
Modifier
    .widthIn(min = 80.dp)
    .heightIn(min = 48.dp)
```

这两种方案不是互相替代，而是不同职责。布局层保证：**这个组件原则上至少应该多大。**Shape 的防御性计算保证：**即使某次真的拿到了极端尺寸，我也尽量不要生成荒谬坐标。**

这是一种很成熟的组件设计思路。不能因为 Layout 有最小尺寸，就让 Shape 完全相信外界永远正确；也不能因为 Shape 会自行压缩，就让 Layout 随便把组件压成 3×3。

---

#### 十五、我们现在终于可以重新完整解释 `Outline.Generic`

最终仍然只是：

```kotlin
return Outline.Generic(path)
```

官方当前对 `Outline.Generic` 的定义非常简单，就是“由 Path 定义的区域”。([Android Developers][3]) 但是你现在再看这一句话，与阶段一看到它的时候已经完全不是一个层级了。阶段一：

```text
Path 是个黑盒
↓
Outline.Generic(path)
```

阶段四：

```text
Dp 设计参数
       ↓
Density 转 px
       ↓
实际 Size
       ↓
LayoutDirection
       ↓
边缘 Case 限制
       ↓
计算 bodyLeft / bodyRight
       ↓
计算 radius
       ↓
计算 tailTop / tailBottom
       ↓
根据 Start / End + LTR / RTL
选择实际左右路径
       ↓
逐段构造 Path
       ↓
Outline.Generic(path)
```

所以 Custom Shape 真正的难点，从来不只是：

```kotlin
Path().apply { ... }
```

真正的能力是：**把业务视觉规则转换成一套能够适应运行环境的几何规则。**这才是这一节比“我会画三角形”高一个层级的地方。

如何变化，然后对照代码解释为什么。

**实验三：暂时删除 `actualRadius` 的 clamp，直接写：**

```kotlin
val actualRadius = requestedRadiusPx
```

然后继续测试那个：

```kotlin
90.dp × 44.dp
```

看看几何结果是否开始异常。看完恢复代码。

**实验四：把：**

#### 阶段四验收

这一阶段我只留四个问题，而且全部贴着真实代码：

### 6.1 阶段五：选择边界、必要源码与最终验收

老哥，6.1 最后一阶段不再继续堆 Path API。现在真正重要的是：**面对一个 UI 需求，你能不能快速判断应该用现成 `Shape`、`GenericShape`、自定义 `Shape`、单独的 `Path`，还是直接等到 Canvas。**新课目录下一节就是 6.2 `Canvas 与 DrawScope`，所以我们今天把这条边界彻底划清，6.1 就结束。

---

#### 一、先建立最终的选择顺序

以后拿到一个图形需求，不要第一反应就是：

```kotlin
Path().apply { ... }
```

正确顺序应该是先问：**我要的是“组件边界”，还是“主动绘制内容”？**如果是组件边界，继续判断：

```text
组件边界
   │
   ├─ 普通矩形
   │     → RectangleShape
   │
   ├─ 圆角矩形
   │     → RoundedCornerShape
   │
   ├─ 切角矩形
   │     → CutCornerShape
   │
   └─ 现成 Shape 表达不了
         ↓
       Path
         ↓
   GenericShape / 自定义 Shape
```

如果需求本身是：

```text
画刻度
画折线
画圆点
画时间轴
画走势图
画多层图形
画动态绘制内容
```

那么这往往根本不是 Shape 的主要职责，而应该进入下一节：

```text
Canvas / DrawScope
```

官方目前同样把 `Shape` 用于 clipping 等“区域边界”，而复杂主动绘制则通过 DrawScope 的 `drawPath()` 等完成。([Android Developers][1]) 这是 6.1 最重要的选择边界。

---

#### 二、`RoundedCornerShape`、`CutCornerShape`：能用现成的绝不造轮子

例如：

```kotlin
RoundedCornerShape(
    topStart = 16.dp,
    topEnd = 32.dp,
    bottomEnd = 8.dp,
    bottomStart = 0.dp
)
```

已经能够描述四个角不同的圆角。类似：

```kotlin
CutCornerShape(
    topStart = 20.dp,
    topEnd = 0.dp,
    bottomEnd = 0.dp,
    bottomStart = 20.dp
)
```

可以表达切角。当前 Compose API 依然保留这套 `CornerBasedShape` 体系。([Android Git Repositories][2]) 所以不要因为学完 Path，就出现这种“学会锤子以后什么都是钉子”的倾向。比如产品说：右上角切掉 16dp。优先：

```kotlin
CutCornerShape(
    topEnd = 16.dp
)
```

而不是自己写：

```kotlin
Path().apply {
    ...
}
```

**Custom Shape 的价值在于表达现成 Shape 表达不了的规则，而不是替代现成 Shape。**

---

#### 三、`GenericShape`：简单自定义轮廓的快捷方式

我们这几阶段一直自己：

```kotlin
class XxxShape : Shape {
    override fun createOutline(...): Outline {
        val path = Path().apply { ... }
        return Outline.Generic(path)
    }
}
```

Compose 其实提供：

```kotlin
GenericShape { size, layoutDirection ->
    moveTo(...)
    lineTo(...)
    close()
}
```

当前公开 API 中，`GenericShape` 的 builder 就以 `Path` 为 receiver，同时拿到 `Size` 和 `LayoutDirection`；它自己实现了 `Shape.createOutline()`。([Android Git Repositories][3]) 比如一个非常简单的三角形：

```kotlin
val triangleShape = GenericShape { size, _ ->
    moveTo(size.width / 2f, 0f)
    lineTo(size.width, size.height)
    lineTo(0f, size.height)
}
```

这时候它比：

```kotlin
private class TriangleShape : Shape
```

少很多样板代码。所以：**简单、无状态、只依赖 Size / LayoutDirection 的 Path Shape，可以优先考虑 `GenericShape`。**

---

#### 四、那为什么我们的 Bubble 还值得自己实现 `Shape`？

因为 Bubble 已经明显超过了：

```text
给我 Size
→ 随手画一个 Path
```

它需要：

```text
Dp 参数
↓
Density → px

LayoutDirection
↓
Start / End 映射

极端 Size
↓
clamp

多个设计参数
↓
真实几何参数

最后
↓
Path
```

这里有一个很实际的区别：当前 `GenericShape` 的 builder 公开参数是 `Size` 和 `LayoutDirection`，**并不会直接把 `Density` 暴露给 builder**；而自己实现 `Shape.createOutline()` 时，你直接拥有 `Density`。([Android Git Repositories][3]) 所以像：

```kotlin
cornerRadius: Dp
tailWidth: Dp
```

这种设计，直接实现 `Shape` 更自然。可以把选择压成一句：`GenericShape` 适合轻量 Path Shape；需要 Density、复杂参数约束、辅助函数和完整可维护逻辑时，正式实现 `Shape`。不是硬规则，但工程上很好用。

---

#### 五、`Shape` 和 `Path` 不是竞争关系

这一点必须彻底结束。比如：

```kotlin
val path = Path()
```

本身只是几何路径。它可以被：

```kotlin
Outline.Generic(path)
```

用于定义 Shape 边界。也可以到了下一章直接：

```kotlin
drawPath(
    path = path,
    color = Color.Red
)
```

拿去绘制。所以：

```text
Path
=
通用二维几何描述
```

而：

```text
Shape
=
“组件边界”这个用途上的抽象
```

这两个根本不是：“Shape 和 Path 到底选哪个？”而是：**我是否需要把这个 Path 提升成一个可供组件消费的 Shape？**这是非常关键的层次关系。

---

#### 六、`Modifier.clip(shape)` 也不是 Shape 的替代品

这一点我们前面已经碰过，现在正式收尾。

```kotlin
Modifier.clip(bubbleShape)
```

意思不是：`clip()` 自己产生 Bubble 形状。而是：

```text
bubbleShape
↓
提供边界

clip()
↓
使用这个边界裁掉区域外的内容
```

官方当前示例也是：

```kotlin
Modifier.clip(CircleShape)
```

或者自定义 `Shape` 后：

```kotlin
Modifier.clip(customShape)
```

来裁切内容。([Android Developers][1]) 同一个 Shape 还能交给：

```kotlin
Surface(shape = bubbleShape)
```

或者：

```kotlin
Modifier.background(
    color = ...,
    shape = bubbleShape
)
```

所以 Shape 是**几何信息提供者**，`clip/background/Surface` 是不同消费者。

---

#### 七、什么时候应该直接 Canvas，而不是 Shape？

这个判断对你以后写日历 App 尤其重要。假设做一天时间轴。需求是：

```text
08:00 ─────────────
09:00 ─────────────
10:00 ─────────────
11:00 ─────────────
```

这里不是在问：“这个组件的外边界是什么形状？” 而是在问：“我要在组件内部画很多线和文字。” 所以 Shape 不合适。再比如走势图：

```text
        ╭──╮
──╮    ╭╯  ╰──
  ╰────╯
```

虽然会使用：

```kotlin
Path
```

但很可能不需要：

```kotlin
Shape
```

直接：

```kotlin
Canvas {
    drawPath(...)
}
```

才符合职责。而聊天气泡：

```text
  ╭──────────╮
< │ message  │
  ╰──────────╯
```

如果你需要：

```text
Surface
背景
裁切
阴影
border
```

都共享这个边界，那么把几何封装成：

```kotlin
BubbleShape
```

就非常合理。所以最终判断是：**Shape 面向“边界复用”；Canvas 面向“绘制过程”。**这一句进入 6.2 前一定要留住。

---

#### 八、必要源码：我们只看到这里就停止

`Shape` 当前源码核心仍然只有这一件事：

```kotlin
interface Shape {
    fun createOutline(
        size: Size,
        layoutDirection: LayoutDirection,
        density: Density
    ): Outline
}
```

官方 AndroidX 主干源码也是如此。([Android Git Repositories][4]) 这其实已经验证了我们整节课的模型：

```text
Shape
不是 View
不是 Composable
不是绘制器
不是 Layout

它只是：

当前运行环境
(Size / LayoutDirection / Density)

        ↓

Outline
```

`GenericShape` 也只是对“通过 Path 构建 Outline”这个常见模式做快捷封装；当前公开 API 依然表明它最终实现同一个 `Shape.createOutline()`。([Android Git Repositories][3])

**源码看到这里就停。**我们现在完全没有必要继续追：

```text
background 内部怎么消费 Outline
clip 怎么生成 layer
Outline.Generic 最终怎么进 Skia
Path 怎么落到 native
GPU 怎么 rasterize
```

这些不会提升你当前写 App 的能力。以后 6.3、6.4 讲绘制 Modifier、图层合成时，需要哪一层再下钻哪一层。

---

#### 九、还有一个现代 API，你现在只需要知道存在

Compose 当前还有：

```text
androidx.graphics.shapes
```

里面有 `RoundedPolygon` 等能力，尤其适合：

* 多边形；
* 圆角多边形；
* shape morph 动画。

官方现在明确说，这套 graphics-shapes **不是任意 Shape 的通用替代方案**，主要解决圆角多边形以及它们之间的 morph；其他任意形状仍然可以直接使用 `Path`。([Android Developers][5]) 所以现在知道存在即可。不要插课学习。等以后真有：

```text
六边形
星形平滑圆角
形状 Morph 动画
```

的需求，再定向补。

#### 十、6.1 最终业务判断题

这次不考术语定义。你直接判断方案。

##### 场景 1

头像必须显示成圆形。

最优先：

```text
CircleShape
+
Modifier.clip()
```

不用 Path。

---

##### 场景 2

一个 Card 四个角分别：

```text
8dp / 16dp / 24dp / 0dp
```

优先：

```text
RoundedCornerShape
```

不用自定义 Shape。

---

##### 场景 3

聊天消息需要：

```text
圆角主体
+
Start / End 尾巴
+
RTL
+
Surface、background、clip 都可能复用
```

非常适合：

```text
自定义 Shape
→ Path
→ Outline.Generic
```

这就是我们的 `AdaptiveBubbleShape`。

---

##### 场景 4

绘制股票走势图。核心：

```text
Path
+
Canvas / DrawScope
```

通常**不需要 Shape**。

---

##### 场景 5

日历里画当前时间：

```text
─────── ● 14:32 ───────
```

这是绘制内容：

```text
Canvas / DrawScope
```

不是 Shape。这将会是你后面日历 App 很现实的场景。

##### 场景 6

一个图片要裁成自定义五角星。这里几何可以：

```text
Path
↓
Shape
↓
Modifier.clip(shape)
```

因为最终需求就是：用这个几何边界裁切现有内容。

---

##### 场景 7

你只是想在 Box 中画一个五角星图标，并不要求这个五角星成为 Box 的边界。

那就：

```text
Path
+
Canvas
```

而不是为了 Path 强行造 Shape。这一组如果你能够自然判断，6.1 就真正学完了。

#### 6.1 最终知识地图

现在你可以把整节压缩成这一张：

```text
                        Shape
                          │
         createOutline(size, direction, density)
                          │
                          ↓
                       Outline
                 ┌────────┼────────┐
                 ↓        ↓        ↓
             Rectangle  Rounded  Generic
                 │        │        │
                Rect   RoundRect   Path
                                   │
                 ┌─────────────────┼───────────────┐
                 │                 │               │
              line/curve        contour       operation
                 │
       moveTo / lineTo
       quadraticTo / cubicTo
       arcTo / close


Shape 的用途：
定义可复用的组件边界

消费者：
Surface / background / clip / shadow / border ...

Path 的用途更广：
既可以服务 Shape，
也可以直接交给 Canvas / DrawScope 绘制
```

* 正确处理 `Dp → px`；

* 对极端 Size 做几何防御；
* 判断现成 Shape、`GenericShape`、自定义 Shape、Path 和 Canvas 的职责边界。
