### 第一阶段：第一次真正观察“合成策略会改变绘制结果”

按我们的课程顺序，6.3 刚刚解决的是 `drawBehind`、`drawWithContent`、`drawWithCache` 这些**绘制 Modifier 如何参与绘制，以及绘制顺序和缓存**；6.4 紧接着开始研究：这些绘制命令执行之后，最终产生的像素究竟怎样作为一个图层与页面上已有内容合成。这个衔接和新课目录本身是一致的。

这一阶段先不深入离屏缓冲的内部模型。我们先跑一个实验，你会直接看到一个很关键的现象：**完全相同的两个矩形，完全相同的 `alpha = 0.5f`，仅仅换一个 `CompositingStrategy`，重叠区域的颜色就会变化。**这就是 6.4 最好的入口。

#### 1. 我们这次到底要观察什么

以前我们写：

```kotlin
Canvas {
    drawRect(...)
    drawRect(...)
}
```

你的第一反应应该很清楚：第二个矩形是在第一个矩形之后绘制的，所以在两个矩形的重叠区域中，第二个矩形会覆盖第一个矩形。现在我们在整个 Canvas 外再加：

```kotlin
.graphicsLayer {
    alpha = 0.5f
}
```

问题就来了：**这个 `0.5f` 究竟是作用在“两个矩形画完以后的整体结果”上，还是分别作用在每一条 `drawRect()` 指令上？**这两种做法听起来只差一句话，但只要两个图形发生重叠，结果就不一样。我们现在直接验证。

---

#### 2. 教学示例：`Sec04A_CompositingStrategyDemo.kt`

这个文件可以直接作为这一节的第一份练习。没有架构、ViewModel、状态流这些无关内容，只保留一个交互按钮和三个对照实验。

```kotlin
@Composable
fun Sec04A_CompositingStrategyDemo() {
    var layerAlpha by remember { mutableFloatStateOf(0.5f) }

    Scaffold { innerPadding ->
        Column(
            modifier = Modifier
                .fillMaxSize()
                .padding(innerPadding)
                .verticalScroll(rememberScrollState())
                .padding(24.dp),
            verticalArrangement = Arrangement.spacedBy(20.dp)
        ) {
            Text(
                text = "CompositingStrategy",
                style = MaterialTheme.typography.headlineSmall
            )

            Text(text = "当前图层 Alpha：$layerAlpha")

            Button(
                onClick = {
                    layerAlpha = if (layerAlpha == 1f) 0.5f else 1f
                }
            ) {
                Text(text = if (layerAlpha == 1f) "切换到 0.5" else "切换到 1.0")
            }

            StrategyExample(
                title = "Auto",
                description = "默认合成策略",
                layerAlpha = layerAlpha,
                strategy = CompositingStrategy.Auto
            )

            StrategyExample(
                title = "Offscreen",
                description = "强制使用离屏缓冲",
                layerAlpha = layerAlpha,
                strategy = CompositingStrategy.Offscreen
            )

            StrategyExample(
                title = "ModulateAlpha",
                description = "把 Alpha 调制到每条绘制指令",
                layerAlpha = layerAlpha,
                strategy = CompositingStrategy.ModulateAlpha
            )
        }
    }
}

@Composable
private fun StrategyExample(
    title: String,
    description: String,
    layerAlpha: Float,
    strategy: CompositingStrategy
) {
    Column(
        verticalArrangement = Arrangement.spacedBy(8.dp)
    ) {
        Text(
            text = title,
            style = MaterialTheme.typography.titleMedium
        )

        Text(
            text = description,
            style = MaterialTheme.typography.bodySmall
        )

        Box(
            modifier = Modifier
                .fillMaxWidth()
                .height(130.dp)
                .background(Color(0xFFF1F1F1))
        ) {
            Canvas(
                modifier = Modifier
                    .fillMaxSize()
                    .graphicsLayer {
                        alpha = layerAlpha
                        compositingStrategy = strategy
                    }
            ) {
                val horizontalPadding = 24.dp.toPx()
                val top = 20.dp.toPx()
                val rectHeight = size.height - 40.dp.toPx()
                val rectWidth = size.width * 0.6f

                drawRect(
                    color = Color.Red,
                    topLeft = Offset(
                        x = horizontalPadding,
                        y = top
                    ),
                    size = Size(
                        width = rectWidth,
                        height = rectHeight
                    )
                )

                drawRect(
                    color = Color.Blue,
                    topLeft = Offset(
                        x = size.width - horizontalPadding - rectWidth,
                        y = top
                    ),
                    size = Size(
                        width = rectWidth,
                        height = rectHeight
                    )
                )
            }
        }
    }
}
```

这里故意使用两个**完全不透明**的 `Color.Red` 和 `Color.Blue`，而不是直接给矩形设置透明色。这样实验中唯一控制透明度的东西就是：

```kotlin
.graphicsLayer {
    alpha = layerAlpha
    compositingStrategy = strategy
}
```

所以结果不会被别的 alpha 干扰。

#### 3. 第一次运行：先切到 `alpha = 1f`

先把按钮切换成：

```text
当前图层 Alpha：1.0
```

此时重点看三个区域中的两个矩形。你应该看到完全相同的三组结果：

| 策略              | 红色区域 | 蓝色区域 | 红蓝重叠区域 |
| --------------- | ---- | ---- | ------ |
| `Auto`          | 红    | 蓝    | 蓝      |
| `Offscreen`     | 红    | 蓝    | 蓝      |
| `ModulateAlpha` | 红    | 蓝    | 蓝      |

重叠区域为什么是蓝色，这里没有任何新知识：

```kotlin
drawRect(Color.Red)
drawRect(Color.Blue)
```

先画红，再画蓝，所以蓝色覆盖红色。这个状态只是我们的**基准组**。

---

#### 4. 第二次运行：切换到 `alpha = 0.5f`

现在真正有意思的地方来了。点击按钮：

```text
当前图层 Alpha：0.5
```

这时候仔细比较三个 Canvas 的**重叠区域**。你应该看到：**`Auto` 和 `Offscreen` 的结果完全相同；`ModulateAlpha` 的重叠区域却变成了另外一种颜色。**尤其不要只看红色和蓝色各自不重叠的地方。真正有价值的是中央：

```text
红色矩形 ∩ 蓝色矩形
```

不同合成策略造成的差异会直接体现在这里。

---

#### 5. 为什么会这样？先解释到第一层

我们先只建立这一阶段需要的模型。对于 `Auto`，当 `graphicsLayer` 的 `alpha < 1f` 时，Compose 默认会先把这个图层的内容绘制到一个离屏缓冲区，然后再把**整个结果**以指定 alpha 合成到最终目标上。`Offscreen` 则明确要求内容先光栅化到离屏纹理或位图，因此在这个实验里，两者会得到相同的视觉结果。([Android Developers][1]) 可以暂时把它想成：

```text
先画红色
再画蓝色
    ↓
形成一张完整结果
整张结果 × 0.5 alpha
    ↓
放到页面
```

注意红蓝重叠区域：因为蓝色是在红色之后画的，所以**在这个中间结果里，那块已经是蓝色了**。然后整个结果统一变成 50% 透明。因此这里不存在“半透明红色和半透明蓝色互相叠加”。

---

`ModulateAlpha` 的处理方式不同。当 `alpha < 1f` 时，**它不会为了处理这个透明度而创建离屏缓冲**，而是把 `graphicsLayer` 设置的 alpha 分别应用到其中记录的**每一条绘制指令**上。因此，当图层内部存在相互重叠的绘制内容时，最终结果会与 `Auto` 和 `Offscreen` 不同。 ([Android Developers][1]) 所以我们的代码原来是：

```kotlin
drawRect(
    color = Color.Red
)

drawRect(
    color = Color.Blue
)
```

使用：

```kotlin
alpha = 0.5f
compositingStrategy = CompositingStrategy.ModulateAlpha
```

你现阶段可以近似理解成：

```text
先画一个 50% alpha 的红色

然后

再画一个 50% alpha 的蓝色
```

于是重叠区域发生的是：

```text
页面背景
   ↑
半透明红色
   ↑
半透明蓝色
```

在 `ModulateAlpha` 下，红色矩形和蓝色矩形都会分别以 `0.5f` 的 alpha 参与绘制。先画出的半透明红色已经与背景发生混合，随后半透明蓝色又绘制在它上面，因此中央会出现一种红蓝共同参与的颜色。

---

#### 6. `Auto`、`Offscreen`、`ModulateAlpha` 现在先记到什么程度

这一阶段不要急着背完整规则，我们后面还要专门拆机制。现在只需要把三个策略记到这个程度：

| 策略              | 第一阶段先建立的认识                         |
| --------------- | ---------------------------------- |
| `Auto`          | 默认策略；这个实验中 `alpha < 1f` 会使用离屏合成    |
| `Offscreen`     | 明确要求内容先画到离屏缓冲，再把结果合成回来             |
| `ModulateAlpha` | 把 alpha 作用到各条绘制指令；重叠内容可能因此产生不同视觉结果 |

这三个示例中，`graphicsLayer` 设置的 alpha 都是 `0.5f`，数值完全相同。不同之处在于这个 `0.5f` 作用在绘制流程的哪个阶段：`Auto` 和 `Offscreen` 是先完成图层内部的绘制，再把整个图层结果以 `0.5f` 的 alpha 合成到目标画面上；`ModulateAlpha` 则把 `0.5f` 分别应用到图层内部的每一条绘制指令上。正是这个处理阶段的不同，导致了重叠区域最终颜色的不同。

#### 7. 和 6.3 的边界现在已经可以看出来了

假如我们现在问：为什么重叠区域是蓝色，不是红色？这是 6.2 / 6.3 已经掌握的问题：

```text
红先画
蓝后画
→ 蓝覆盖红
```

但如果问：为什么整个 `graphicsLayer` 都是 `alpha = 0.5f`，`Auto` 和 `ModulateAlpha` 的重叠区域却不同？这就不是“谁先画谁后画”能回答的了。因为现在讨论的是：

```text
这些 draw 指令产生的结果
        ↓
在哪个阶段应用 alpha
        ↓
是否先形成独立中间结果
        ↓
最后怎样和目标像素合成
```

这就是 **6.4 图层合成与离屏缓冲真正新增的知识层级**。

你把 `Sec04A_CompositingStrategyDemo.kt` 实际跑起来之后，重点只验证两个现象：**alpha=1 时三组基本一致；alpha=0.5 时 `Auto` / `Offscreen` 与 `ModulateAlpha` 的重叠区域出现明显差别。** 下一阶段我们就直接拿这个现象拆开 `graphicsLayer`、Layer 和 Offscreen Buffer 三个最容易混成一团的概念。

### 第二阶段：建立核心心智模型——Draw Layer、Rasterization 与 Offscreen Buffer

第一阶段已经通过红、蓝两个矩形观察到了一个现象：同样把 `graphicsLayer` 的 `alpha` 设置为 `0.5f`，`Auto / Offscreen` 与 `ModulateAlpha` 在重叠区域可能得到不同结果。第二阶段要解决的不是继续记三种策略的规则，而是建立一套能够解释这些现象的运行模型。这一阶段最需要分清四个东西：

```text
graphicsLayer
      ↓
Draw Layer
      ↓  （必要时 rasterize）
Offscreen Buffer
      ↓
destination
```

其中最重要的边界是：**Draw Layer 不等于 Offscreen Buffer。**

#### 1. `graphicsLayer` 到底创建了什么

当我们写：

```kotlin
Canvas(
    modifier = Modifier
        .graphicsLayer {
            alpha = 0.5f
        }
) {
    drawRect(Color.Red)
    drawRect(Color.Blue)
}
```

`graphicsLayer` 会让这个 Composable 的绘制内容进入一个独立的 **draw layer**。官方对它的描述很明确：Layer 可以隔离其中的 drawing instructions，使渲染系统能够独立管理这组绘制指令，并统一对它们应用平移、缩放、旋转、alpha 等图形属性。([Android Developers][1])

因此这里首先发生的事情可以理解为：

```text
Draw Layer
│
├── drawRect(Red)
└── drawRect(Blue)
```

这里的 `drawRect()` 可以先理解为 Layer 中记录的 **drawing instructions（绘制指令）**。Layer 建立的是一个绘制边界：这一组指令属于同一个 Layer，后续可以作为整体进行图形处理。所以：

```text
graphicsLayer
        ↓
建立一个独立的 Draw Layer
```

到这里为止，还不能继续推出：

```text
已经生成了一张 Bitmap
```

更不能推出：

```text
已经创建了 Offscreen Buffer
```

官方文档专门强调：`graphicsLayer` 本身可以只是用于隔离绘制指令，并不意味着一定会分配并光栅化一个独立的离屏图层。([Android Developers][1])

---

#### 2. Draw Layer 为什么要记录绘制指令

假设 Layer 中有：

```kotlin
drawRect(Color.Red)
drawRect(Color.Blue)
```

随后我们修改：

```kotlin
graphicsLayer {
    rotationZ = 30f
}
```

旋转的是整个 Layer，而不是要求我们重新计算红色矩形和蓝色矩形每一个点的新坐标。Layer 把内部绘制内容隔离起来以后，渲染系统可以统一对这一组内容应用变换。可以把关系理解为：

```text
Draw Layer
┌──────────────────────┐
│ drawRect(Red)        │
│ drawRect(Blue)       │
└──────────────────────┘
            │
            │ rotationZ = 30°
            ▼
      整个 Layer 旋转
```

Layer 的价值并不局限于旋转。`translationX`、`scaleX`、`alpha` 等属性，本质上都可以针对这个 Layer 进行处理。

这里还涉及一个性能上的重要特点：Layer 中已经记录的绘制指令可以被渲染管线再次使用，而不一定需要重新执行应用层的绘制代码。这个能力以后理解图形变换和绘制性能时很有用，但 6.4 不需要继续下钻它的底层实现。([Android Developers][1])

---

#### 3. Rasterization：从“绘制指令”变成“像素结果”

现在进入第二个核心概念：**rasterization（光栅化）**。前面的：

```text
drawRect(Red)
drawRect(Blue)
```

描述的是“要怎么画”。而经过光栅化之后，我们关心的已经不是这两条命令本身，而是它们执行后产生的实际像素。可以粗略理解成：

```text
Drawing Instructions
│
│ drawRect(Red)
│ drawRect(Blue)
│
        ↓ 执行这些绘制指令
   Rasterization
        ↓
实际的像素结果
```

如果这个 Layer 需要进行**离屏光栅化**，这些像素不会直接写入最终绘制目标，而会先写入一块独立的 Offscreen Buffer。官方对此的描述是：当 Layer 被 rasterize 时，其中的 drawing instructions 会执行，执行结果会被捕获到一个 offscreen buffer 中。([Android Developers][1])

于是整个过程变成：

```text
Draw Layer
│
├── drawRect(Red)
└── drawRect(Blue)
        │
        │ rasterize
        ▼
┌─────────────────────┐
│  Offscreen Buffer   │
│                     │
│   已经生成的像素结果  │
└─────────────────────┘
```

因此 Draw Layer 和 Offscreen Buffer 最大的区别可以这样记：**Draw Layer 管的是一组绘制内容及绘制指令；Offscreen Buffer 保存的是这些指令执行之后产生的中间像素结果。**

---

#### 4. “Offscreen”究竟离开了什么屏幕

`Offscreen Buffer` 翻译成“离屏缓冲区”，很容易让人误以为它是某种完全脱离当前界面的后台画布。其实这里的“离屏”主要表示：**这一轮绘制结果暂时没有直接写入最终的 destination，而是先写进另一个中间绘制目标。**

这里顺便把 `destination` 讲准确。在图形合成语境中，destination 可以理解成：**当前这一层最终准备把结果绘制到的目标。**在最简单的页面中，它最终可能对应窗口的渲染目标；但如果还有父级 Offscreen Layer，那么当前 Layer 的 destination 也可能是**父级的 Offscreen Buffer**。所以不能简单把 destination 永远翻译成“屏幕”。我们现在的教学示例可以简化成：

```text
Draw Layer
     │
     │ rasterize
     ▼
Offscreen Buffer
     │
     │ composite
     ▼
 destination
```

`composite` 就是“合成”：把这个已经得到的像素结果再放到 destination 上，并按照 alpha、BlendMode 等规则与 destination 中原有的像素组合。这就是 **compositing** 这个词在本节真正指向的事情。

---

#### 5. `Auto + alpha = 0.5f`：先画完整内容，再对整个结果应用 alpha

现在重新解释第一阶段的红蓝矩形，但这次使用完整模型。我们有：

```kotlin
graphicsLayer {
    alpha = 0.5f
    compositingStrategy = CompositingStrategy.Auto
}
```

当 `alpha < 1f` 时，默认的 `Auto` 会为整个 Layer 创建离屏中间结果：先把 Layer 内部的内容绘制到 Offscreen Buffer，然后再使用这个 Layer 的 alpha 把整个缓冲结果绘制到 destination。([Android Developers][1])

完整过程是：

```text
Draw Layer

drawRect(Red)
drawRect(Blue)
        │
        │ rasterize
        ▼
┌──────────────────────┐
│  Offscreen Buffer    │
│                      │
│ 红色先画              │
│ 蓝色后画              │
│ 重叠位置最终已经是蓝色 │
└──────────────────────┘
        │
        │ 整个 Buffer × 0.5 alpha
        ▼
    destination
```

注意 `0.5f` 出现的位置。它并没有分别改变红色和蓝色两条 `drawRect()` 的绘制过程，而是在 Layer 内部已经得到完整像素结果之后，作用于**整个 Layer 的结果**。所以我们把这种方式称为：**整层 alpha（layer alpha）。**

红色和蓝色在 Offscreen Buffer 内首先按照正常的不透明绘制完成。蓝色后画，因此重叠处在中间结果中已经只剩蓝色；随后这一整张中间结果再以 `0.5f` 的 alpha 与 destination 合成。

---

#### 6. `Offscreen`：明确要求先产生这张中间像素结果

换成：

```kotlin
graphicsLayer {
    alpha = 0.5f
    compositingStrategy = CompositingStrategy.Offscreen
}
```

这一次不是由 `Auto` 根据属性决定，而是我们明确要求：这个 Layer 的内容先 rasterize 到 Offscreen Buffer，再把这个中间结果绘制到 destination。官方定义就是：`Offscreen` 会始终把 Composable 的内容先光栅化到离屏纹理或位图，然后再渲染到 destination。([Android Developers][1])

因此在第一阶段那个示例里：

```text
Auto + alpha 0.5
```

和：

```text
Offscreen + alpha 0.5
```

都经历了：

```text
内部绘制
   ↓
形成完整 Offscreen 像素结果
   ↓
整个结果应用 0.5 alpha
   ↓
合成到 destination
```

所以最终看到的是相同结果。但两者的**决策方式**不同：`Auto` 是因为当前属性需要离屏合成而自动这样做，`Offscreen` 则是开发者明确要求这个 Layer 使用离屏中间结果。

---

#### 7. `ModulateAlpha`：改变的不是“重叠规则”，而是 alpha 介入的位置

现在看真正容易混淆的：

```kotlin
graphicsLayer {
    alpha = 0.5f
    compositingStrategy = CompositingStrategy.ModulateAlpha
}
```

对于这个 alpha，`ModulateAlpha` 不先生成一个完整的 Offscreen Buffer，然后再给整个结果乘 `0.5f`。它会把 Layer 的 alpha **调制到 Layer 中记录的每一条 drawing instruction 上**。官方对这一行为的定义非常明确。([Android Developers][1])

所以第一阶段的两条指令可以近似理解为：

```text
原来：
drawRect(Red)
drawRect(Blue)

ModulateAlpha：
drawRect(Red × 0.5 alpha)
drawRect(Blue × 0.5 alpha)
```

流程变成：

```text
draw Red × 0.5
        ↓
   destination

draw Blue × 0.5
        ↓
与 destination 中已经存在的结果继续合成
```

这里没有为了这个 `alpha = 0.5f` 先制作一张“红色 + 蓝色的完整中间图”，所以两个矩形的 alpha 会分别参与合成。这就是**逐条 alpha（per-drawing-instruction alpha）**与前面的**整层 alpha（layer alpha）**最本质的区别。

---

#### 8. 内容重叠影响的是“结果是否一样”，不是“要不要创建 Offscreen Buffer”

现在可以准确解释第一阶段为什么特意画两个发生重叠的矩形。如果两个绘制内容完全不重叠：

```text
┌──── Red ────┐      ┌──── Blue ────┐
└─────────────┘      └──────────────┘
```

对于每一个像素位置，都只有一条绘制指令参与。因此：

```text
先画完整 Layer，再整体 × 0.5
```

与：

```text
每条绘制指令分别 × 0.5
```

最终通常可以得到相同的像素结果。正因为如此，官方指出：如果事先知道内容不会重叠，`ModulateAlpha` 可以避免仅仅为了 alpha 建立 Offscreen Buffer，从而可能比 `Auto` 更高效。([Android Developers][1]) 如果两个内容发生重叠：

```text
Red
 ┌───────────┐
 │        ┌──┼────────┐
 │        │  │        │
 └────────┼──┘        │
          └──── Blue ─┘
```

`Auto / Offscreen` 是：

```text
先得到完整绘制结果
        ↓
整体 × 0.5
```

而 `ModulateAlpha` 是：

```text
Red × 0.5
        ↓
Blue × 0.5 再画上去
```

同一个像素位置发生了两次半透明绘制，因此最终颜色不同。

这里必须把因果关系保持清楚：**内容是否重叠，不负责决定 `ModulateAlpha` 是否创建 Offscreen Buffer；它决定的是“逐条应用 alpha”和“对整个 Layer 应用 alpha”最终能不能得到相同的视觉结果。**

对于 `ModulateAlpha`，只要讨论的是 `alpha < 1f` 这个条件本身，它不会因为内容重叠而突然改成 Offscreen。官方明确写的是：它不会为了小于 `1f` 的 alpha 创建 Offscreen Buffer；重叠内容只是可能让最终结果与其他策略不同。([Android Developers][1])

#### 9. 用一张图把三种策略收起来

以第一阶段同一个：

```kotlin
alpha = 0.5f
```

为例：

```text
                    Draw Layer
                Red       Blue
                  \       /
                   \     /
                    \   /
					V

Auto
alpha < 1f
    │
    ▼
Rasterize 整个 Layer
    │
    ▼
Offscreen Buffer
    │
    │ 整体 × 0.5
    ▼
destination


Offscreen
    │
    ▼
强制 Rasterize 整个 Layer
    │
    ▼
Offscreen Buffer
    │
    │ 整体 × 0.5
    ▼
destination


ModulateAlpha
    │
    ├── Red  × 0.5 ──────► destination
    │
    └── Blue × 0.5 ──────► destination
```

因此三种策略的区别不能简单记成“谁有 Buffer，谁没 Buffer”，更准确的理解是：

| 策略              | 对本例 `alpha = 0.5f` 的处理                                              |
| --------------- | ------------------------------------------------------------------- |
| `Auto`          | 自动把 Layer rasterize 到 Offscreen Buffer，再对整个结果应用 alpha               |
| `Offscreen`     | 明确强制把 Layer rasterize 到 Offscreen Buffer，再对整个结果应用 alpha             |
| `ModulateAlpha` | 不为了这个 alpha 创建完整 Offscreen 中间结果，而是把 alpha 调制到各条 drawing instruction |

还有一个边界现在知道即可：`RenderEffect`、overscroll 等其他条件本身也可能要求 Offscreen 渲染，因此不能把 `ModulateAlpha` 理解为“永远不会出现 Offscreen Buffer”。这里讨论的是：**它不会仅仅因为 Layer 的 alpha 小于 `1f` 而创建 Offscreen Buffer。** ([Android Developers][1])

#### 10. 本阶段真正需要留下的模型

最后只保留下面这一条链：

```text
graphicsLayer
    ↓
建立 Draw Layer，隔离和记录 drawing instructions
    ↓
必要时进行 rasterization
    ↓
得到 Offscreen Buffer 中的中间像素结果
    ↓
把结果 composite 到 destination
```

`Auto / Offscreen` 在第一阶段的 `alpha = 0.5f` 示例里，都是**先得到整个 Layer 的像素结果，再应用整层 alpha**；`ModulateAlpha` 则把这个 alpha **提前分配到每一条 drawing instruction 上**。内容是否重叠决定这两种处理方式的视觉结果是否一致，而不是决定 `ModulateAlpha` 是否离屏。

#### Addition 0: 上一段话更详细的分析是这样的

`graphicsLayer` 首先建立的是一个 Draw Layer，这个 Layer 可以把其中的 drawing instructions 隔离并记录起来。例如第一阶段的 `drawRect(Color.Red)` 和 `drawRect(Color.Blue)`，在这一层仍然可以理解为“要画什么”的绘制指令，而不是一张已经生成好的图片。要真正得到这些绘制指令对应的像素结果，需要执行 rasterization（光栅化）：也就是执行这些 drawing instructions，把它们转换成某个绘制目标中的实际像素。这个绘制目标不一定是 Offscreen Buffer；是否需要额外的离屏中间结果，要看当前采用的合成策略以及 Layer 的其他属性。`graphicsLayer` 本身只是提供 Draw Layer，并不等于一定创建 Offscreen Buffer。

在第一阶段 `alpha = 0.5f` 的例子中，`Auto` 会因为整个 Layer 的 alpha 小于 `1f` 而创建 Offscreen Buffer，`Offscreen` 则是明确要求始终创建这样的离屏中间结果。因此这两种策略都会先执行 Layer 中的红色、蓝色两条绘制指令，把整个 Layer 光栅化到 Offscreen Buffer 中。此时 Layer 内部的绘制已经全部完成：红色先画，蓝色后画，所以重叠区域在这张中间像素结果里已经只剩后画的蓝色。随后才把这个完整的 Offscreen Buffer 作为一个整体，以 Layer 设置的 `alpha = 0.5f` 与 destination 进行合成。这里的 destination 表示“当前结果最终要画到的目标”，它可能是窗口的绘制目标，也可能是更外层 Layer 的 Offscreen Buffer，因此不应该简单等同于物理屏幕。

因此，对 `Auto / Offscreen + alpha < 1f` 可以形成这样的抽象模型：**Draw Layer 保存绘制指令 → 对整个 Layer 进行 rasterization → 得到 Offscreen Buffer 中的完整像素结果 → 对这个完整结果应用整层 alpha → composite 到 destination。** 这里的关键是，alpha 介入时，Layer 内部的绘制已经完成了，所以它操作的是整个 Layer 的结果，而不是分别改变每一条 `drawRect()` 的透明度。

`ModulateAlpha` 的流程不同。它仍然有 Draw Layer，里面仍然记录着相同的 drawing instructions，也仍然必须执行这些绘制指令才能产生最终像素；区别在于，它不会仅仅为了 `alpha < 1f` 先建立一个完整 Layer 的 Offscreen Buffer。Layer 上的 `alpha = 0.5f` 会被分别调制到每一条 drawing instruction 上，所以可以把第一阶段的代码近似理解成“以 `0.5f` alpha 绘制红色矩形，再以 `0.5f` alpha 绘制蓝色矩形”。这些绘制指令最终直接参与当前 destination 的绘制与合成，而不是先组成一张完整的红蓝中间图，再统一乘一次 `0.5f`。

因此，`Auto / Offscreen` 与 `ModulateAlpha` 真正的区别不是“有没有执行光栅化”——最终都必须把 drawing instructions 转换成像素——而是**是否先把整个 Layer 光栅化成一个独立的 Offscreen 中间结果，以及 Layer alpha 是作用于这个完整结果，还是分别作用于 Layer 内的 drawing instructions。** 当绘制内容不重叠时，这两种 alpha 处理方式通常可以得到相同的视觉结果；当内容发生重叠时，同一像素会在 `ModulateAlpha` 下参与多次半透明绘制，因此结果就可能不同。内容是否重叠影响的是最终视觉结果是否一致，而不是决定 `ModulateAlpha` 是否因为 alpha 创建 Offscreen Buffer。

到这里，第二阶段的核心模型就完整了。下一阶段再进入 `BlendMode.Clear`，在那里 Offscreen Buffer 不再只是为了演示 alpha 的差异，而会真正承担**把 BlendMode 的作用范围限制在当前 Layer 内部**的职责。

[1]: https://developer.android.com/develop/ui/compose/graphics/draw/modifiers?authuser=0000&utm_source=chatgpt.com "Graphics modifiers  |  Jetpack Compose  |  Android Developers"

### 第三阶段：`BlendMode.Clear`——为什么有些绘制效果必须先进入 Offscreen Buffer

第二阶段建立的模型到这里开始真正发挥作用。我们已经知道：Draw Layer 保存 drawing instructions；需要离屏合成时，这些指令先经过 rasterization，在 Offscreen Buffer 中形成完整的中间像素结果，再把这个结果 composite 到 destination。第三阶段不再用 `alpha` 观察“结果为什么不同”，而是换一个更有实际意义的问题：

**如果一条绘制指令本身要修改、甚至删除已经存在的像素，它到底能修改哪些像素？**答案取决于它当前面对的 **destination 是谁**。`BlendMode.Clear` 正好可以把这个问题非常直观地暴露出来。

#### 1. 先认识这一阶段唯一需要的 `BlendMode`

这一阶段不系统学习整个 `BlendMode` 家族，只使用：

```kotlin
BlendMode.Clear
```

BlendMode 描述的是：**当前正在绘制的内容，怎样与 destination 中已经存在的像素进行合成。**在图形系统里通常会出现两个词：

```text
Source       当前这一次准备画进去的内容
Destination  当前绘制目标中已经存在的像素
```

例如普通的：

```kotlin
drawCircle(Color.Red)
```

可以粗略理解为：红色圆形是 source，当前绘制目标中原来存在的像素是 destination，然后按照默认的合成规则把红色圆画上去。但：

```kotlin
drawCircle(
    color = Color.Black,
    blendMode = BlendMode.Clear
)
```

意思完全不同。`Clear` 关注的是这个圆覆盖的范围，它会把这个范围内 destination 已有的像素清除掉。这里传入什么颜色并不重要，我们使用 `Color.Black` 只是给 API 提供一个 source color。因此真正值得问的是：**Clear 清除的是哪里的 destination？**第二阶段刚刚学过的 Offscreen Buffer，就是答案的关键。

---

#### 2. 示例：给头像状态点“挖出”一圈间隔

这一阶段使用第二份代码：`Sec04B_OffscreenBlendMode.kt`

我们做一个很常见的 UI 效果：头像右下角有一个绿色在线状态点。为了让状态点和头像之间有明显间隔，我们先用一个稍大的 `BlendMode.Clear` 圆把头像挖掉一块，再在中间画一个稍小的绿色圆。代码本身会同时展示 `Auto` 和 `Offscreen`，方便直接比较。

```kotlin
@Composable
fun Sec04B_OffscreenBlendMode() {
    Scaffold { innerPadding ->
        Column(
            modifier = Modifier
                .fillMaxSize()
                .padding(innerPadding)
                .verticalScroll(rememberScrollState())
                .padding(24.dp),
            verticalArrangement = Arrangement.spacedBy(24.dp)
        ) {
            Text(
                text = "BlendMode.Clear",
                style = MaterialTheme.typography.headlineSmall
            )

            StatusAvatarExample(
                title = "Auto",
                description = "alpha = 1f，不主动创建 Offscreen Buffer",
                strategy = CompositingStrategy.Auto
            )

            StatusAvatarExample(
                title = "Offscreen",
                description = "先把当前 Layer 绘制到 Offscreen Buffer",
                strategy = CompositingStrategy.Offscreen
            )
        }
    }
}

@Composable
private fun StatusAvatarExample(
    title: String,
    description: String,
    strategy: CompositingStrategy
) {
    Column(
        verticalArrangement = Arrangement.spacedBy(8.dp)
    ) {
        Text(
            text = title,
            style = MaterialTheme.typography.titleMedium
        )

        Text(
            text = description,
            style = MaterialTheme.typography.bodySmall
        )

        Box(
            modifier = Modifier
                .fillMaxWidth()
                .height(190.dp)
                .background(Color(0xFFFFF1B8))
        ) {
            Box(
                modifier = Modifier
                    .size(150.dp)
                    .align(Alignment.Center)
                    .graphicsLayer {
                        compositingStrategy = strategy
                    }
                    .drawWithContent {
                        val avatarRadius = size.minDimension * 0.42f

                        val statusCenter = Offset(
                            x = center.x + avatarRadius * 0.72f,
                            y = center.y + avatarRadius * 0.72f
                        )

                        val cutoutRadius = 20.dp.toPx()
                        val statusRadius = 14.dp.toPx()

                        // 1. 头像主体
                        drawCircle(
                            color = Color(0xFF536DFE),
                            radius = avatarRadius,
                            center = center
                        )

                        // 2. 绘制 Box 中真正的内容：中间的字母 A
                        drawContent()

                        // 3. 先挖出一个较大的圆形区域
                        drawCircle(
                            color = Color.Black,
                            radius = cutoutRadius,
                            center = statusCenter,
                            blendMode = BlendMode.Clear
                        )

                        // 4. 再画一个更小的在线状态点
                        drawCircle(
                            color = Color(0xFF00C853),
                            radius = statusRadius,
                            center = statusCenter
                        )
                    },
                contentAlignment = Alignment.Center
            ) {
                Text(
                    text = "A",
                    color = Color.White,
                    style = MaterialTheme.typography.headlineLarge
                )
            }
        }
    }
}
```

这里故意继续使用 6.3 学过的 `drawWithContent`。顺序非常简单：先画头像圆形，再 `drawContent()` 把字母画出来，然后用 `Clear` 挖一个大圆，最后在圆洞中间画一个较小的绿色状态点。绿色圆比 Clear 圆小：

```text
Clear 圆：   radius = 20dp
绿色状态点： radius = 14dp
```

所以理论上绿色状态点外围应该留下大约 `6dp` 的“空隙”。真正的问题是：**这 6dp 到底会露出什么？**

#### 3. 运行时重点观察哪里

这一阶段不需要观察整个页面，只看绿色状态点外围那一圈被 `Clear` 清掉的区域。`Offscreen` 那一组应该很容易理解：头像被挖掉一圈以后，会露出外层 `Box` 的浅黄色背景，因此得到：

```text
蓝色头像
      \
       浅黄色间隔
          \
           绿色状态点
```

这就是我们真正想要的效果。

而没有强制离屏的 `Auto`，这一圈可能继续把当前 destination 中已经绘制好的背景像素清除掉。对于普通不透明窗口，最终经常会看到黑色或窗口更底层的内容，而不是我们想保留的浅黄色背景。官方文档专门用 `BlendMode.Clear` 展示了这个现象：没有 Offscreen Buffer 时，`Clear` 会作用于 destination 中已经存在的背景内容；使用 `Offscreen` 后，BlendMode 的作用范围才被限制在当前 Composable 的离屏内容中。([Android Developers][1])

因此不要把重点放在“它到底是不是黑色”。真正稳定的观察标准是：**Offscreen 下，外层背景保持完整；没有离屏隔离时，`Clear` 可以继续清除当前 destination 中原本不属于头像的像素。**

---

#### 4. `Offscreen` 为什么能把 Clear 限制在当前组件内部

现在用第二阶段的完整模型重新走一次。使用：

```kotlin
graphicsLayer {
    compositingStrategy = CompositingStrategy.Offscreen
}
```

之后，头像所在的 Draw Layer 会先 rasterize 到自己的 Offscreen Buffer。一开始：

```text
Offscreen Buffer

┌─────────────────────────┐
│                         │
│       蓝色头像           │
│          A              │
│                         │
└─────────────────────────┘
```

然后执行：

```kotlin
drawCircle(
    blendMode = BlendMode.Clear
)
```

此时 `Clear` 面对的 destination 是谁？就是：

```text
这个 Layer 自己的 Offscreen Buffer
```

所以它只能清除这块 Buffer 中已经存在的像素：

```text
Offscreen Buffer

┌─────────────────────────┐
│                         │
│       蓝色头像           │
│          A       ○      │
│                 ↑       │
│             被清成透明    │
└─────────────────────────┘
```

随后再画绿色状态点：

```text
Offscreen Buffer

┌─────────────────────────┐
│                         │
│       蓝色头像           │
│          A      ◉       │
│                ↑ ↑      │
│              空隙 绿点    │
└─────────────────────────┘
```

到这里 Offscreen Buffer 本身已经完成了。最后才把整个 Buffer composite 到真正的外层 destination：

```text
外层 destination 已经有浅黄色背景
              +
头像 Offscreen Buffer
              ↓
          最终结果
```

因为 Clear 只是把头像 Buffer 的那部分像素变成透明，而**没有碰外层 destination 的浅黄色像素**，所以合成时，透明区域自然会露出下面原本存在的浅黄色背景。这就是所谓的：**Offscreen Buffer 为 BlendMode 建立了一个局部的像素操作范围。**

官方文档对这个用途说得非常直接：**`Offscreen` 可以让 `BlendMode` 只作用于当前 Composable 的内容，而不影响已经绘制在其后的背景内容。**([Android Developers][2])

---

#### 5. 不使用 Offscreen 时，到底发生了什么

现在看：

```kotlin
graphicsLayer {
    compositingStrategy = CompositingStrategy.Auto
}
```

我们这里没有设置 `alpha < 1f`，也没有 `RenderEffect` 等需要离屏渲染的条件，所以单纯这个 `Auto` 不会因为当前代码主动生成 Offscreen Buffer。([Android Developers][1])

Draw Layer 中依然有这些 drawing instructions：

```text
画蓝色头像
画字母 A
Clear 圆形
画绿色状态点
```

但它们没有先被限制在一张属于头像自己的 Offscreen Buffer 中。于是执行：

```text
BlendMode.Clear
```

时，它所操作的 destination 已经包含此前绘制进去的内容，包括更外层已经存在的背景。可以抽象成：

```text
当前 destination

┌───────────────────────────────┐
│        浅黄色背景              │
│                               │
│            蓝色头像           │
│               A               │
│                               │
└───────────────────────────────┘
```

执行 Clear：

```text
                    ○
                    ↑
          Clear 直接修改 destination
```

于是圆形范围内并不是只删除“头像自己的蓝色像素”，而是**把 destination 在这个位置已有的像素一起清除**。这时候第二阶段学过的 `destination` 就不再是一个抽象名词了。

Clear 根本不知道：这个像素是“头像自己的”，那个像素是“父组件的背景”。它只知道：**我现在正在向这个 render target 绘制，而 `BlendMode.Clear` 要把这里已有的 destination pixels 清掉。**

如果你希望它只能碰头像自己的像素，就必须先给头像建立一个独立的 render target——也就是 Offscreen Buffer。

---

#### 6. 为什么第一阶段的 alpha 只是“结果不同”，这里却可能直接“画错”

这两个案例放在一起，正好可以看到 Offscreen 的两种不同意义。

第一阶段：

```text
Auto / Offscreen
vs
ModulateAlpha
```

讨论的是：alpha 应该作用于整个 Layer 的中间结果，还是分别作用于每一条 drawing instruction？即使选择 `ModulateAlpha`，绘制仍然可以正常完成，只是重叠内容得到的颜色可能不同。

而这一阶段：

```text
BlendMode.Clear
```

讨论的是：**Clear 到底有权修改哪一块 destination？**如果我们真正想表达的是：

```text
只删除头像自己的像素
```

那么当前 Composable 就必须拥有一个可以独立操作的中间像素结果。因此：

```text
Offscreen Buffer
```

在这里不仅仅改变视觉算法，而是在建立一个**像素操作边界**。

这也是为什么在复杂遮罩、擦除、镂空等效果中，`Offscreen` 经常不是一个“可有可无的性能选项”，而是保证 BlendMode 作用范围正确的重要工具。官方也把 masking content 明确列为 `CompositingStrategy.Offscreen` 的典型使用场景。([Android Developers][1])

---

#### 7. 一个非常值得亲手验证的小实验：把 Auto 的 alpha 改成 `0.99f`

现在暂时修改第一组：

```kotlin
.graphicsLayer {
    alpha = 0.99f
    compositingStrategy = CompositingStrategy.Auto
}
```

其他代码完全不动。按照第二阶段建立的模型，你现在应该能够在运行之前预测结果。因为：

```text
Auto
+
alpha < 1f
```

会让 Compose 为这个 Layer 创建 Offscreen Buffer。([Android Developers][1]) 于是虽然我们没有写：

```kotlin
CompositingStrategy.Offscreen
```

真正的流程却已经变成：

```text
Draw Layer
    ↓
Rasterization
    ↓
Offscreen Buffer
    ↓
BlendMode.Clear 只修改这个 Buffer
    ↓
整个 Buffer × 0.99
    ↓
destination
```

因此，原本 `Auto` 下那个越界清除背景的现象应该消失，Clear 会被限制到这个离屏中间结果中。这个实验很重要，因为它证明了一件事情：**`BlendMode.Clear` 本身没有“是否隔离”的属性；真正决定它能碰到哪些像素的，是它执行时面对的 destination。**

而 `CompositingStrategy`、`alpha` 等条件，会影响这个 destination 前面是否多出一层 Offscreen Buffer。验证完以后把 `alpha = 0.99f` 删除，恢复原代码即可。

#### 8. 再把 Source、Destination 和 Offscreen 串成一条完整链

到现在可以把这一阶段压缩成一个完整例子。执行：

```kotlin
drawCircle(
    color = Color.Black,
    blendMode = BlendMode.Clear
)
```

这个圆形就是当前 drawing operation 的 source 范围。如果有 Offscreen：

```text
Source
Clear 圆
   │
   ▼
Destination
当前 Layer 的 Offscreen Buffer
   │
   │ Clear
   ▼
Buffer 中出现透明洞
   │
   │ composite
   ▼
更外层 destination
```

如果没有 Offscreen：

```text
Source
Clear 圆
   │
   ▼
Destination
当前真正正在绘制的外层 render target
   │
   │ Clear
   ▼
已有背景像素也可能被一起删除
```

所以同一句：

```kotlin
blendMode = BlendMode.Clear
```

代码完全没变，最终效果却可能完全不同。不是 `Clear` 的算法发生了改变，而是：**它正在操作的 destination 变了。**

这一点把第二阶段的 `destination`、rasterization、Offscreen Buffer 和第三阶段的 BlendMode 真正连成了一条完整逻辑。

---

#### 9. 这一阶段暂时不要把 Offscreen 理解成万能遮罩开关

看到这里很容易产生另一个极端：以后用了 BlendMode，我直接全部 `Offscreen`。暂时不要形成这个习惯。

`Offscreen` 会创建与当前绘制区域相对应的离屏纹理或位图，先进行一次离屏光栅化，再把结果合成回来，因此确实存在额外成本。官方同时指出，离屏纹理的大小与绘制区域有关，并且使用 `Offscreen` 时，绘制默认会被限制在该区域内。这个边界行为正是我们下一阶段要专门验证的内容。([Android Developers][1])

所以这一阶段真正应该留下的判断不是：

```text
BlendMode → 一律 Offscreen
```

而是：

```text
如果 BlendMode 应该只操作当前组件自己的像素，
就必须确认它拥有正确的局部 destination。

CompositingStrategy.Offscreen
是显式建立这种局部离屏结果的方式。
```

#### 本阶段收尾

前两个阶段到现在已经形成了一条完整链路：

```text
graphicsLayer
    ↓
Draw Layer
    ↓
drawing instructions
    ↓
必要时 rasterization
    ↓
Offscreen Buffer
    ↓
BlendMode / 整层 alpha 等操作
    ↓
composite
    ↓
destination
```

第一阶段用 alpha 让我们看到不同 compositing strategy 的视觉差异；第二阶段解释了 Draw Layer、rasterization、Offscreen Buffer 和 destination；这一阶段则第一次真正利用这个模型解决一个实际问题：**通过改变 BlendMode 执行时面对的 destination，把像素清除操作限制在当前 Layer 内。**

下一阶段会继续沿着 Offscreen Buffer 本身往下走，但重点换成另一个很容易在自定义绘制里踩坑的性质：**Offscreen Buffer 有自己的尺寸边界，因此原本能够画出 Composable bounds 之外的内容，在强制离屏之后可能直接被裁掉。**

[2]: https://developer.android.com/develop/ui/compose/graphics/draw/modifiers?authuser=0000&utm_source=chatgpt.com "Graphics modifiers  |  Jetpack Compose  |  Android Developers"

#### Addition 1: `BlendMode.Clear` 的核心是：**把 source 覆盖到的 destination 像素清成 0**

`BlendMode.Clear` 的核心不是“画一个什么颜色的圆”，而是：**把 source 覆盖到的 destination 像素清成 0。** 官方定义就是 destination 中被 source 覆盖的像素会被清除，输出颜色和 alpha 都变成 0。([Android Developers](https://developer.android.com/reference/android/graphics/BlendMode?utm_source=chatgpt.com)) 所以你这里：

```kotlin
// 3. 先挖出一个较大的圆形区域
drawCircle(
    // BlendMode.Clear 会清除当前 destination 中被 source 圆覆盖的像素。
    // 这里的 color 不决定最终显示颜色，但 drawCircle() 的 API 仍要求传入 color。
    color = Color.White,
    radius = cutoutRadius,
    center = statusCenter,
    blendMode = BlendMode.Clear
)
```

在这个例子里，`Color.White`、`Color.Black`、`Color.Red` 都不会决定那个圆洞最后显示什么颜色。`BlendMode.Clear` 不是“画一种颜色”，而是“清除当前 destination 中 source 覆盖范围内的像素”；是否使用 Offscreen，决定的是这个 destination 到底是哪一层。真正决定你看到什么的是：**Clear 把当前 destination 那一块清掉以后，下面还能透出什么。**

你截图里 `Auto` 出现黑色圆环，也不是因为之前写过 `Color.Black`。而是没有 Offscreen 隔离时，`Clear` 一路清到了当前 destination，最后露出了窗口 rendering buffer；官方文档甚至直接说明，这种情况下可能会看到黑色的 window rendering buffer。([Android Developers](https://developer.android.com/develop/ui/compose/graphics/draw/modifiers?authuser=0000&utm_source=chatgpt.com))

而 `Offscreen` 那组之所以看到浅黄色圆环，是因为 Clear 清掉的是头像自己那张 Offscreen Buffer 里的像素，得到透明区域以后，再把整张 Buffer 合成到外层浅黄色背景上，所以浅黄色自然透了出来。

### 第四阶段：Offscreen Buffer 的尺寸边界——为什么强制离屏后，画出去的内容会被裁掉

第三阶段我们利用 Offscreen Buffer 给 `BlendMode.Clear` 建立了一个局部 destination。现在继续沿着同一个模型往前走，会出现一个很自然的问题：既然 Offscreen Buffer 是一块真实存在的中间绘制目标，那么这块 Buffer 有多大？

答案非常重要：**默认情况下，它的大小就是当前 Layer 的绘制区域。** 因此，一旦内容先被 rasterize 到 Offscreen Buffer，超出这块 Buffer 边界的像素就没有地方保存，最终会被裁掉。官方文档也专门用 `Auto` 与 `Offscreen` 对比这个行为：普通 `graphicsLayer` 可以让绘制内容超出布局边界，而 `Offscreen` 会创建与绘制区域对应的离屏纹理，并默认把绘制限制在这个区域内。([Android Developers][1])

这一阶段使用第三个示例：`Sec04C_OffscreenBounds.kt`

#### 1. 先从一个反直觉现象开始

假设一个 `Canvas` 的尺寸只有：

```kotlin
.size(120.dp)
```

但我们偏偏在里面画：

```kotlin
drawRect(
    size = Size(
        width = 200.dp.toPx(),
        height = 200.dp.toPx()
    )
)
```

这里要唤醒一个已经学过的 Compose 概念：**布局尺寸和绘制范围不是一回事。**

`size(120.dp)` 决定这个 Composable 在 Layout 阶段占多大空间，但普通绘制并不会因为这个尺寸自动获得一个裁剪框。`graphicsLayer` 本身也不会改变测量尺寸和摆放位置；如果内容经过变换或绘制后超出布局边界，它有可能继续绘制到外面。([Android Developers][1])

因此，没有离屏光栅化时：

```text
Canvas 布局范围
┌──────────────┐
│              │
│              │
│              │──────────────┐
└──────────────┘              │
                              │
   实际绘制的 200dp Rect       │
                              │
               └──────────────┘
```

`Canvas` 只有 120dp，不代表右边和下面多出来的绘制内容一定会消失。但一旦强制 `Offscreen`，结果会发生明显变化。

为了避免“到底哪里是 Canvas 自己的范围”看不清楚，这次我专门用一个独立的描边框标出 120dp 的布局边界。外层区域故意做得更大，让超出去的图形有空间显示。

#### 3. `Auto`：120dp 的布局范围，不等于 120dp 的裁剪范围

第一组：

```kotlin
graphicsLayer {
    compositingStrategy = CompositingStrategy.Auto
}
```

这里没有：

```kotlin
alpha < 1f
```

也没有 `RenderEffect` 等会使这个 Layer 进入 Offscreen Buffer 的条件，所以当前示例不会仅仅因为存在 `graphicsLayer` 就建立一张离屏纹理。([Android Developers][1])

于是 Layer 中虽然记录着：

```text
Canvas layout size = 120 × 120
```

但 drawing instruction 是：

```text
drawRect = 200 × 200
```

这条绘制指令仍然可以把像素画到 120dp 布局边界之外。运行结果应该类似：

```text
┌──────────── 220dp 外层区域 ────────────┐
│                                       │
│ ┌──── Canvas 120dp ────┐              │
│ │██████████████████████│██████████    │
│ │██████████████████████│██████████    │
│ │██████████████████████│██████████    │
│ └──────────────────────┘██████████    │
│  █████████████████████████████████    │
│  █████████████████████████████████    │
│                                       │
└───────────────────────────────────────┘
```

黑框标出的仍然只有 120dp，那是它真正参与 Layout 的范围；紫色区域却可以继续延伸到外面。这也是理解 Compose Drawing 时非常重要的一个边界：**Layout 决定“你占多大地方”，Drawing 决定“你实际往哪里画”；前者不会天然成为后者的 clip。**

#### 4. `Offscreen`：为什么 200dp 的 Rect 突然只剩 120dp

第二组唯一改变的是：

```kotlin
graphicsLayer {
    compositingStrategy = CompositingStrategy.Offscreen
}
```

现在整个 Draw Layer 要先 rasterize 到 Offscreen Buffer。而这个示例里的 Layer 尺寸是：

```text
120dp × 120dp
```

所以可以抽象成：

```text
Draw Layer
120 × 120

里面有一条 instruction：

drawRect(200 × 200)
          │
          │ rasterize
          ▼
┌────────────────────┐
│ Offscreen Buffer   │
│ 120 × 120          │
│                    │
│ ██████████████████ │
│ ██████████████████ │
│ ██████████████████ │
└────────────────────┘
```

绘制指令仍然说：我要画一个 200 × 200 的矩形。问题是这次它正在往一个 **120 × 120 的 Offscreen Buffer** 中写像素。右边额外的 80dp：

```text
x = 120dp ... 200dp
```

以及下面额外的 80dp：

```text
y = 120dp ... 200dp
```

根本不属于这张 Buffer 可以保存的区域，因此不会成为这张离屏中间结果的一部分。最终再把 Buffer composite 回 destination 时，能够拿回来当然也只有这 120 × 120 的像素。所以结果变成：

```text
┌──────────── 220dp 外层区域 ────────────┐
│                                       │
│ ┌──── Canvas 120dp ────┐              │
│ │██████████████████████│              │
│ │██████████████████████│              │
│ │██████████████████████│              │
│ └──────────────────────┘              │
│                                       │
│                                       │
└───────────────────────────────────────┘
```

官方文档给出的结论也是如此：**`CompositingStrategy.Offscreen` 会创建与绘制区域对应的离屏纹理，并且绘制命令默认会被裁剪到这个区域。**([Android Developers][1])

#### 5. 这里的“裁剪”和 `Modifier.clip()` 不是一回事

这个地方很容易把两个概念混起来。我们没有写：

```kotlin
Modifier.clip(...)
```

也没有：

```kotlin
graphicsLayer {
    clip = true
}
```

但是 Offscreen 仍然产生了边界限制。原因不是我们主动增加了一个 `clip()` 操作，而是：**Offscreen Buffer 本身只有这么大。**可以把两件事分开：

```text
Modifier.clip(...)
```

表达的是：我主动定义一个裁剪规则，只允许某个 Shape 范围内的内容显示。而现在的：

```text
CompositingStrategy.Offscreen
```

产生的是：Layer 先被画进一张有限尺寸的离屏纹理；超出这张纹理范围的像素没有进入中间结果。最终视觉上都表现成“外面的东西不见了”，但背后的原因不同。

---

#### 6. 这和第三阶段其实是同一套机制

上一阶段我们说 Offscreen 很有用，因为：

```text
BlendMode.Clear
        ↓
只能修改自己的 Offscreen Buffer
```

于是它不会继续清除父层的背景。现在我们又发现：

```text
超出 Layer bounds 的绘制
        ↓
也无法写到自己的 Offscreen Buffer 外
```

这两个现象其实来自**完全相同的原因**：**Offscreen Buffer 给当前 Layer 建立了一块有限大小、独立的像素空间。**这个“独立”带来了第三阶段的好处：

```text
BlendMode 不再误伤外层 destination
```

而这个“有限大小”又带来了这一阶段的副作用：

```text
超出 Buffer bounds 的绘制无法保留下来
```

所以 Offscreen 不是一个抽象的“开启高级图形效果”开关。它真正改变的是：

```text
原来：
drawing instructions
       ↓
直接参与外部 destination

现在：
drawing instructions
       ↓
有限大小的独立 Offscreen Buffer
       ↓
再 composite 到外部 destination
```

一旦这个中间 render target 出现，**像素隔离和尺寸边界会同时出现。**这也是为什么前面把 Offscreen Buffer 真正理解成“一块中间像素结果”，比单独背 `CompositingStrategy.Offscreen` 的 API 规则重要得多。

#### 7. `Auto` 也可能出现同样的裁剪

现在做一个非常值得验证的小实验。把第一组 `Auto` 改成：

```kotlin
.graphicsLayer {
    alpha = 0.5f
    compositingStrategy = CompositingStrategy.Auto
}
```

按照我们第二阶段建立的模型，现在应该能直接预测结果。

`Auto + alpha < 1f`：

```text
Auto
  +
alpha = 0.5
  ↓
需要整层 alpha
  ↓
创建 Offscreen Buffer
```

于是原本：

```text
200dp Rect
超出 120dp Canvas 的部分仍然可见
```

会变成：

```text
200dp Rect
只留下 Offscreen Buffer 范围内的 120dp
```

也就是说：**真正导致这个边界行为的根本原因不是枚举值叫 `Offscreen`，而是当前 Layer 是否真的被 rasterize 到有限大小的 Offscreen Buffer。**`CompositingStrategy.Offscreen` 是明确强制它发生；`Auto` 在满足相应条件时也可能发生。官方文档正是用 `alpha` 导致离屏光栅化来说明这种隐式裁剪行为。([Android Developers][1])

#### 8. 一个真实开发中很容易出现的问题

假设以后做日历 App，你画一个选中日期：

```text
┌─────────────┐
│      15     │
│             │
└─────────────┘
```

然后为了强调选中状态，你画一个稍微超过 Cell 边界的光晕：

```text
      ╭────────╮
   ╭──┼────────┼──╮
   │  │   15   │  │
   ╰──┼────────┼──╯
      ╰────────╯
```

普通绘制下，这种效果完全可能正常显示。后来你又为了做：

```text
alpha
BlendMode
RenderEffect
Offscreen
```

而让这个 Layer 进入离屏缓冲。结果突然发现：为什么我的光晕被整整齐齐切掉了？如果没有今天这个模型，很容易开始乱查：

```text
是不是 Canvas bug？
是不是 drawCircle 算错半径？
是不是 Modifier 顺序有问题？
是不是 parent clip 了？
```

其实根因可能只是：

```text
以前
drawing 可以超过 layout bounds

后来
Layer 被 rasterize 到与自身绘制区域对应的 Offscreen Buffer

因此
超出的像素无法进入这个 Buffer
```

这就是这一阶段真正有开发价值的地方。

#### 9. 那超出 Layer 的内容就永远不能和 Offscreen 共存吗？

不是。当前 Compose 的 `graphicsLayer` API 还提供了 **Layer Outsets** 这一类能力，用来扩展被提升为 Offscreen Buffer 时的视觉边界，官方 API 示例就是为了解决“`alpha < 1f` 导致离屏后，原本画出布局区域之外的内容被裁掉”这个问题。([Android Developers][2])

不过这个 API 现在**不展开学习**。原因很简单：我们这一节真正需要掌握的是 Offscreen Buffer 的运行模型，而不是继续增加一个边缘 API。以后真实项目确实出现“必须离屏，同时又必须保留 bounds 外绘制”的需求，再回来定向学习 `LayerOutsets` 更合理。现在只需要知道：**Offscreen 默认有边界；确实存在扩展这个视觉边界的办法。**这样心智模型既不会错误，也不用把课程拖进低频 API。

---

#### 10. Offscreen 的性能成本现在也可以理解，而不需要死记

讲到这里，“Offscreen 有成本”已经不用背结论了。没有离屏中间结果时，可以粗略理解成：

```text
drawing instructions
        ↓
destination
```

使用 Offscreen 后多了一层：

```text
drawing instructions
        ↓
rasterize
        ↓
Offscreen Buffer
        ↓
composite
        ↓
destination
```

这里多出的不是一个抽象概念，而是真正需要一块中间绘制目标来保存像素结果。Offscreen Buffer 的尺寸越大，需要处理和保存的像素自然也越多。所以：

```kotlin
CompositingStrategy.Offscreen
```

不应该成为“我不知道选什么，所以开最强模式”的保险开关。在需要：

```text
BlendMode 隔离
Mask
明确的整层中间像素结果
```

这类效果时使用它，有明确意义。如果只是普通绘制，没有任何需要离屏结果的理由，那就没有必要主动增加这一层。这里理解到应用层就够了，不需要继续深入 GPU framebuffer、显存分配或者 RenderNode 实现。

#### 11. 把第三阶段和第四阶段合起来看

现在 Offscreen Buffer 已经不再只是一个模糊的“中间层”。它有两个非常具体的性质：

```text
                Offscreen Buffer
                       │
             ┌─────────┴─────────┐
             │                   │
          独立性                有限尺寸
             │                   │
             ▼                   ▼
BlendMode 只能操作        超出 Buffer bounds
当前 Buffer 中的像素       的像素无法保存
```

第三阶段利用的是左边：**独立性。**第四阶段观察到的是右边：**尺寸边界。**而它们实际上是同一件事情的两个侧面：**当前 Layer 获得了一块属于自己的、有限大小的中间像素空间。**

#### 本阶段收尾

到这里，6.4 已经可以形成一条相当完整的运行链：

```text
graphicsLayer
        ↓
Draw Layer
记录并隔离 drawing instructions
        ↓
根据当前属性和 CompositingStrategy
决定是否需要离屏光栅化
        ↓
        ├── 不需要 Offscreen
        │       ↓
        │   直接参与当前 destination 的绘制
        │
        └── 需要 Offscreen
                ↓
          rasterization
                ↓
       有限大小的 Offscreen Buffer
                ↓
       在其中完成 BlendMode /
       整层 alpha 等像素处理
                ↓
            composite
                ↓
           destination
```

第三阶段告诉我们为什么有时候**必须**拥有这块独立 Buffer；这一阶段则告诉我们，拥有它以后也不是没有代价——除了额外的离屏绘制和合成，它还会引入明确的像素边界。

下一阶段就可以从机制学习转向选择问题：**`Auto`、`Offscreen`、`ModulateAlpha` 在真实 App 中到底怎么选，哪些情况应该保持默认，哪些情况必须显式 Offscreen，哪些情况才值得用 `ModulateAlpha`。**

[2]: https://developer.android.com/reference/kotlin/androidx/compose/ui/Modifier?utm_source=chatgpt.com "Modifier  |  API reference  |  Android Developers"

### 第五阶段：三种 `CompositingStrategy` 的选择边界与真实 App 使用判断

前四个阶段已经把机制铺完整了，现在这一阶段不再继续往底层钻，而是解决真正开发时最重要的问题：**什么时候什么都不用管，保持 `Auto`；什么时候必须显式 `Offscreen`；什么时候才值得主动使用 `ModulateAlpha`？**

这三个策略不是“性能从低到高”或者“功能从弱到强”的关系，而是在回答不同的问题。最实用的选择顺序其实很简单：**先保持 `Auto`，只有明确需要像素隔离时才用 `Offscreen`，只有明确知道内容不会重叠并且想避免 alpha 引起的离屏时，才考虑 `ModulateAlpha`。**

这一阶段使用最后一个综合示例：`Sec04D_RealCompositingCase.kt`

---

#### 1. 第一种场景：普通组件整体变透明——保持 `Auto`

先看真实 App 中最常见的需求：一个组件进入 disabled 状态，希望它整体变淡。比如一个“餐饮”分类卡片：

```text
┌──────────────────────┐
│   🍜    餐饮         │
│         ¥ 128        │
└──────────────────────┘
```

里面可能同时有：背景、Icon、Text、Badge、阴影、其他绘制内容。这时候我们真正表达的设计意图是：**把整个组件已经画好的最终结果一起变成 50% 透明。**这就是非常典型的整层 alpha。

```kotlin
@Composable
private fun DisabledCategoryCard() {
    Box(
        modifier = Modifier
            .size(
                width = 220.dp,
                height = 90.dp
            )
            .graphicsLayer {
                alpha = 0.5f
                compositingStrategy = CompositingStrategy.Auto
            }
            .background(
                color = Color(0xFF536DFE),
                shape = RoundedCornerShape(18.dp)
            ),
        contentAlignment = Alignment.Center
    ) {
        Column(
            horizontalAlignment = Alignment.CenterHorizontally
        ) {
            Text(
                text = "餐饮",
                color = Color.White,
                style = MaterialTheme.typography.titleMedium
            )

            Text(
                text = "¥ 128",
                color = Color.White,
                style = MaterialTheme.typography.bodyMedium
            )
        }
    }
}
```

这里没有任何理由手动写：

```kotlin
CompositingStrategy.Offscreen
```

因为：

```text
Auto
+
alpha < 1f
```

已经能够完成我们需要的整层 alpha。流程就是我们前面已经建立好的：

```text
整个 Card 的 drawing instructions
               ↓
        rasterization
               ↓
        Offscreen Buffer
               ↓
         整层 alpha = 0.5
               ↓
          destination
```

因此普通 App 开发中，**大多数时候根本不需要主动选择合成策略**。`Auto` 就是默认答案。这也是为什么不应该学完 `Offscreen` 以后开始到处显式写：

```kotlin
compositingStrategy = CompositingStrategy.Offscreen
```

如果 `Auto` 已经能够根据当前图层属性正确处理，就没有必要替它强制做决定。

---

#### 2. 为什么这里通常不应该换成 `ModulateAlpha`

这个 Card 内部存在明显的绘制重叠：

```text
蓝色背景
    ↑
白色文字
```

从 drawing instruction 的角度看，大致存在：

```text
绘制背景
绘制文字
```

文字所在的位置本来就覆盖在背景之上。如果使用：

```kotlin
graphicsLayer {
    alpha = 0.5f
    compositingStrategy = CompositingStrategy.ModulateAlpha
}
```

就不再是：

```text
背景 + 文字
     ↓
形成完整 Card
     ↓
整体 × 0.5
```

而会更接近：

```text
背景 × 0.5
       ↓
文字 × 0.5 再绘制上去
```

由于这些内容发生重叠，结果可能不再等价。所以真实业务组件只要内部结构稍微复杂一点，通常就不要为了“可能省掉一次 Offscreen”随手改成 `ModulateAlpha`。这就是一个非常实用的判断：**如果你根本无法确定组件内部所有 drawing instructions 是否存在重叠，就保持 `Auto`。**

---

#### 3. 第二种场景：需要像素隔离——明确使用 `Offscreen`

现在换成我们已经真正遇到过的需求：

```kotlin
BlendMode.Clear
```

假设要做头像状态点：

```text
头像
  ↓
挖一个透明洞
  ↓
再画绿色状态点
```

这里的设计意图不是简单的透明度，而是：`Clear` 只能清除头像自己的像素，不能继续清除外层 destination。这时候：

```kotlin
CompositingStrategy.Offscreen
```

就是明确的业务要求。因为我们真正需要的是：

```text
当前组件
    ↓
先生成自己的 Offscreen Buffer
    ↓
Clear 只修改这个 Buffer
    ↓
整个结果再 composite 到外层
```

换句话说：**`Offscreen` 最值得主动使用的场景，不是“我想优化”，而是“我明确需要一个独立的中间像素结果”。**典型需求包括：

```text
BlendMode
Mask
Clear / DstIn / DstOut 等像素混合
局部擦除
局部镂空
必须隔离的图形效果
```

这些场景真正关心的是：**当前绘制操作的 destination 必须限定在自己的 Layer 内。**因此 `Offscreen` 是一个**正确性工具**，而不仅仅是性能策略。

---

#### 4. 第三种场景：内容明确不重叠——`ModulateAlpha` 才有意义

现在来看 `ModulateAlpha` 真正适合什么东西。假设我们自己绘制一个简单的状态指示器：

```text
▮   ▮   ▮   ▮
```

四根柱子之间完全没有重叠。我们希望整个图标显示成 40% 透明。

```kotlin
@Composable
private fun SignalIndicator(
    alpha: Float
) {
    Canvas(
        modifier = Modifier
            .size(
                width = 120.dp,
                height = 48.dp
            )
            .graphicsLayer {
                this.alpha = alpha
                compositingStrategy =
                    CompositingStrategy.ModulateAlpha
            }
    ) {
        val barWidth = 18.dp.toPx()
        val gap = 12.dp.toPx()

        repeat(4) { index ->
            val heightRatio = (index + 1) / 4f
            val barHeight = size.height * heightRatio

            drawRect(
                color = Color(0xFF536DFE),
                topLeft = Offset(
                    x = index * (barWidth + gap),
                    y = size.height - barHeight
                ),
                size = Size(
                    width = barWidth,
                    height = barHeight
                )
            )
        }
    }
}
```

这里我们能够非常明确地证明：

```text
柱 1
柱 2
柱 3
柱 4
```

互相没有重叠。所以：

```text
先把四根柱子画好，再整体 × 0.4
```

和：

```text
每根柱子分别 × 0.4
```

视觉结果相同。此时 `ModulateAlpha` 才真正发挥它的价值：

```text
不需要为了 alpha 创建完整 Offscreen Buffer
而是：每条 drawing instruction 直接使用对应 alpha 绘制
```

因此它可能减少一次离屏光栅化和后续合成。这里的关键不是：`ModulateAlpha` 比 `Auto` 高级。而是：**我们明确知道逐条 alpha 和整层 alpha 在这个组件中是等价的。**只有在这个前提成立时，这个优化才有意义。

#### 6. 现在正式建立选择顺序

```kotlin
graphicsLayer {
    alpha = ...
}
```

```text
第一步：
默认 Auto 能不能满足需求？
```

绝大多数情况答案都是：

```text
能
```

到这里结束。只有出现：

```text
BlendMode
Mask
Clear
必须限定像素作用范围
```

才继续问：

```text
我是不是明确需要自己的
Offscreen Buffer？
```

如果是：

```text
Offscreen
```

再有一种比较特殊的情况：

```text
我只是要给整个 Layer 设置 alpha
+
我明确知道 Layer 内的绘制内容不会重叠
+
这里确实值得避免 alpha 带来的 Offscreen
```

才考虑：

```text
ModulateAlpha
```

因此实际选择关系可以压缩成：

```text
                     默认
                      │
                      ▼
                    Auto
                      │
          ┌───────────┴───────────┐
          │                       │
  需要独立像素结果？        只是 alpha？
          │                       │
         是                 内容确定不重叠？
          │                       │
          ▼                       ▼
      Offscreen             ModulateAlpha
```

这比背三个 API 的定义更有实际价值。

#### 7. 一个很重要的反例：不要把 `ModulateAlpha` 当成“性能版 Auto”

这是这一节最容易留下错误印象的地方。看到：

```text
Auto
→ alpha < 1
→ 可能创建 Offscreen Buffer

ModulateAlpha
→ 不因为 alpha 创建 Offscreen Buffer
```

很容易自然推导：那以后只要用了 alpha，我尽量用 `ModulateAlpha`，不是更快吗？这个结论不成立。因为 `ModulateAlpha` 是用**改变合成方式**换取避免离屏。只有：

```text
逐条应用 alpha
```

与：

```text
整个 Layer 应用 alpha
```

在当前组件中视觉等价，这个优化才成立。如果绘制内容有重叠，你已经不是单纯做性能优化，而是在改变最终像素结果。所以正确关系是：

```text
视觉语义正确
      ↓
再谈性能
```

不能反过来。

---

#### 8. `Offscreen` 也不是“画得最正确”的模式

另一边也一样。看到：

```text
Offscreen
→ 独立 Buffer
→ BlendMode 更安全
```

不能推导成：那我所有 `graphicsLayer` 都写 Offscreen，肯定最准确。因为 `Offscreen` 会明确增加一个中间 render target：

```text
drawing instructions
        ↓
Offscreen Buffer
        ↓
composite
        ↓
destination
```

同时我们上一阶段刚刚验证过：这块 Buffer 还有自己的尺寸边界，可能导致原本超出 Layer bounds 的绘制被裁掉。所以它不是“更高级的 Auto”，而是：**当业务效果明确需要中间像素结果时，主动要求创建这个结果。**

---

#### 9. 关于你以前对 `graphicsLayer` 的理解

你前面提到以前照着代码写过 `graphicsLayer`，当时大概理解为“避免 Recomposition，在 GUI 层处理变化”。这个直觉不能说完全错，但需要稍微校准。`graphicsLayer` 确实可以让：

```text
alpha
scale
translation
rotation
```

这类 Layer 属性变化只更新图形 Layer，而不一定重新执行 Composable 内容本身的绘制逻辑，因此动画和频繁图形变换中很有价值。但不要把：

```text
graphicsLayer
```

定义成：避免 Recomposition 的 Modifier。它真正提供的是：**把绘制内容放入一个可以独立管理的 Graphics Layer，并在这个 Layer 上应用图形属性。**

至于“某些变化因此可以跳过 Composition / Layout / 重新执行绘制代码”，那是建立在这个 Layer 模型上的性能收益，而不是 `graphicsLayer` 存在的唯一目的。这样以后再看到以前写过的：

```kotlin
.graphicsLayer {
    translationX = ...
    scaleX = ...
    scaleY = ...
}
```

就不会只知道“这是优化写法”，而会知道为什么它能够这样工作。

---

#### 10. 到这里，6.4 的三个策略可以压缩成三句话

现在已经不需要再背长定义了。

**`Auto`：**默认选择。让 Compose 根据 Layer 属性决定是否需要 Offscreen；普通整体透明、图形变换等场景优先保持它。

**`Offscreen`：**我明确需要当前 Layer 先拥有一份独立的中间像素结果，例如要限制 BlendMode / Mask 的作用范围。

**`ModulateAlpha`：**我明确知道 Layer 内绘制内容不会发生会改变结果的重叠，并希望让 alpha 分别作用于 drawing instructions，从而避免仅因 alpha 创建 Offscreen Buffer。

再把前三阶段的机制接上：

```text
Auto
  ↓
系统决定是否需要中间像素结果

Offscreen
  ↓
我明确要求中间像素结果

ModulateAlpha
  ↓
对于 alpha，不先形成完整中间结果
而是提前作用到 drawing instructions
```

这就是这一节真正应该带进项目里的选择模型。

#### 本阶段收尾

6.4 到这里，核心机制实际上已经全部闭环了：

```text
drawing instructions
        ↓
Draw Layer
        ↓
CompositingStrategy
        ↓
是否需要 rasterization 到 Offscreen Buffer
        ↓
整层 alpha / BlendMode / 像素隔离
        ↓
composite 到 destination
```

你现在不只是知道三个枚举值分别“干什么”，而是可以从需求反推为什么需要它们：**普通情况交给 `Auto`；需要独立像素空间时显式 `Offscreen`；只有明确知道逐条 alpha 与整层 alpha 等价时，才考虑 `ModulateAlpha`。**

下一阶段就是 6.4 的最后收尾，不再增加新的核心 API，也不继续挖渲染源码。重点是把 6.1～6.4 的 Drawing 心智模型串成一条线，再用几个场景题检查这些知识是否已经能够真正用于开发。

#### Addition 2: graphicsLayer 的位置意义

你这个 TODO 非常值得问，而且**这里的顺序确实有影响**。你现在写的是：

```kotlin
.size(...)
.background(...)
.graphicsLayer { alpha = 0.5f }
```

Compose 的 Modifier 是有嵌套顺序的，前面的 Modifier 包在后面的外面。官方也明确说明 Modifier 的顺序会影响最终行为。:chatgpt-content-reference{index="0"}

因此你现在这个顺序里，`background` 在 `graphicsLayer` 外面。可以粗略理解成：

```text
size
└── background
    └── graphicsLayer
        └── Box content
```

所以 `graphicsLayer` 的 `alpha = 0.5f` **不会把前面的 background 一起包进这个 Layer**；它主要影响后面的内容。对于我们这个“整个卡片一起变透明”的例子，更合理的是：

```kotlin
Modifier
    .size(
        width = 220.dp,
        height = 90.dp
    )
    .graphicsLayer {
        alpha = 0.5f
        compositingStrategy = CompositingStrategy.Auto
    }
    .background(
        color = Color(0xFF536DFE),
        shape = RoundedCornerShape(18.dp)
    )
```

这样关系才是：

```text
size
└── graphicsLayer
    ├── background
    └── Box content
```

也就是**背景和文字都属于这个 Layer，整个卡片统一应用 alpha**。

所以不是“`graphicsLayer` 通常约定俗成写在末尾”。相反，**它写在哪里，本质上是在决定这个 Layer 包住 Modifier 链中的哪些绘制内容。** 这个问题其实和 6.3 学过的 Modifier 绘制嵌套关系是直接连上的。`graphicsLayer` 会把它所包含的内容绘制进独立 draw layer；它不是一个无所谓放哪儿的配置项。:chatgpt-content-reference{index="1"}

你这个 TODO 可以改成：

```kotlin
// graphicsLayer 的位置有意义：它只把后续绘制内容包含进当前 Layer。
// 如果希望背景、内容一起应用 alpha，应把 graphicsLayer 放在 background 前面。
```

### 第六阶段：6.4 收尾——把图层合成真正收进心智模型

这一阶段不再增加 API，也不重新讲一遍前三个阶段。6.4 到现在真正应该留下来的，是一条能够在以后遇到绘制问题时拿出来推导的运行链：

```text
drawing instructions
        ↓
Draw Layer
        ↓
是否需要离屏光栅化
        ↓
 ┌───────────────┬────────────────┐
 │               │                │
不需要         需要
 │               │
直接参与         rasterization
destination      ↓
               Offscreen Buffer
                    ↓
             整层 alpha / BlendMode
                    ↓
                 composite
                    ↓
                destination
```

`graphicsLayer` 首先给我们的是一个独立管理绘制内容的 Draw Layer，而不是天然生成一张离屏图片。只有当前的合成需求要求这么做时，这个 Layer 才会进一步 rasterize 成 Offscreen Buffer。这个 Buffer 保存的是已经执行 drawing instructions 后得到的中间像素结果，因此它同时带来了两个重要性质：**像素操作具有独立性，同时又受到自身尺寸边界的限制。**

`Auto`、`Offscreen`、`ModulateAlpha` 也不需要再背长定义。开发时只要记住选择方向即可：普通情况保持 `Auto`；明确需要一份独立的中间像素结果，例如限制 `BlendMode.Clear`、Mask 等操作范围时，使用 `Offscreen`；如果只是处理 Layer alpha，并且能够确认内部绘制内容不会因为逐条应用 alpha 而改变视觉结果，才有理由考虑 `ModulateAlpha`。

#### 1. 用几个场景检查是否真的理解

**场景一：一个复杂的 Card 需要整体变成 50% 透明。**

Card 内有背景、文字、图标，而且彼此存在覆盖关系。这里使用默认 `Auto` 即可。因为我们的需求就是“整个 Card 最终结果一起变透明”，没有必要主动改成 `ModulateAlpha`，也没有必要手动强制 `Offscreen`。

**场景二：Canvas 中画了几个互不重叠的小圆，只想让整体显示成 30% 透明。**

`Auto` 仍然完全正确。如果这个组件绘制频繁，而且你能够确认所有 drawing instructions 不会发生影响结果的重叠，那么可以考虑 `ModulateAlpha`，因为逐条应用 `0.3f` 与整层应用 `0.3f` 在这个场景中可以得到相同结果，同时避免仅仅为了 alpha 创建 Offscreen Buffer。

这里的判断顺序永远是：**先保证视觉语义一致，再谈是否值得优化。**

**场景三：使用 `BlendMode.Clear` 给头像挖一个洞，但不希望把头像下面的父组件背景也清掉。**

这里需要独立的像素操作空间，所以显式使用 `Offscreen` 是合理的。Clear 执行时面对的 destination 会变成当前 Layer 自己的 Offscreen Buffer，它只能清除这个 Buffer 中的像素。最后整个 Buffer 再与外层 destination 合成，透明洞的位置自然露出父级背景。

这里真正起作用的不是“Offscreen 对 Clear 有特殊处理”，而是 **destination 发生了变化**。

**场景四：Canvas 本身只有 120dp，但故意画一个 200dp 的图形到布局区域之外。后来增加 `Offscreen`，发现超出去的部分消失了。**

这是符合模型的。Offscreen Buffer 是有限大小的中间绘制目标，超出它范围的像素不会进入这份中间结果，所以最终 composite 回去时也不存在这些像素。这个现象与 `Modifier.clip()` 虽然视觉上都像“被裁掉”，但原因不同。

**场景五：`ModulateAlpha` 下两个半透明图形发生重叠，结果和 `Auto` 不一样。是不是因为发生重叠后 Compose 自动切换到了 Offscreen？**

不是。内容是否重叠主要决定**逐条 alpha 与整层 alpha 的视觉结果是否一致**，并不会因为发生了重叠，就让 `ModulateAlpha` 自动改成为了 alpha 创建完整的 Offscreen Buffer。这一点是 6.4 最容易混淆、也最值得长期保留的边界。

#### 2. 6.3 和 6.4 现在可以彻底分开了

学完这一节以后，这两个章节的职责已经非常清楚。

6.3 主要回答：**绘制 Modifier 怎样参与绘制，谁先画、谁后画，以及怎样缓存绘制相关的数据。**

6.4 主要回答：**这些 drawing instructions 最终在哪个 Layer 中执行，是否先形成 Offscreen 中间像素结果，以及这些像素怎样与 destination 合成。**

所以以后看到问题：“为什么这个东西盖住了那个东西？” 首先想到绘制顺序。看到：“为什么相同的 alpha 在重叠区域颜色不一样？” 想到 compositing strategy。看到：“为什么 `Clear` 把父背景也清掉了？” 想到 destination 与 Offscreen 隔离。看到：“为什么加了 Offscreen 后，原来画出 bounds 外面的效果消失了？” 想到 Offscreen Buffer 的尺寸边界。这就是把知识真正变成排查问题的工具。

#### Addition 3: `Modifier.alpha()` 与 `graphicsLayer { alpha = ... }`  

对，这个小问题现在顺手补掉很合适，而且有一个关键点需要纠正：**`Modifier.alpha()` 本身实际上也会建立 graphics layer 来实现透明度，并不是另一套完全不同的透明度机制。** 官方文档明确写了，`Modifier.alpha(alpha)` 会把该 Composable 的内容渲染到单独的 graphics layer；当 `alpha < 1f` 时，会产生用于整层透明度的中间合成层。它可以看成“只想设置透明度时的便捷 API”。:chatgpt-content-reference{index="0"}

不过两者用途还是有区别：如果只是静态地把整个组件设成 `0.5f`，直接写 `Modifier.alpha(0.5f)` 完全可以；如果需要控制 `CompositingStrategy`、旋转、缩放、位移、`RenderEffect` 等 Layer 属性，就必须使用 `graphicsLayer`。另外如果 alpha 会频繁变化或做动画，官方推荐 `graphicsLayer { alpha = state }`，因为状态可以直接更新 Layer 属性，不必因为 `Modifier.alpha(state)` 的参数变化而重新组合。:chatgpt-content-reference{index="1"}

你可以把下面这段作为 addition：

> `Modifier.alpha()` 不是另一套透明度实现，它本身也会通过 graphics layer 对内容应用透明度。对于简单、静态的整体透明效果，直接使用 `Modifier.alpha()` 更简洁；而 `graphicsLayer` 除了 alpha 之外，还能控制 `CompositingStrategy`、缩放、旋转、位移等 Layer 属性，并且更适合频繁变化或动画中的 alpha。两者在 Modifier 链中的位置同样有意义，只会影响它所包裹的后续绘制内容。:chatgpt-content-reference{index="2"}

还有你这段代码里一个值得马上注意的小地方：

```kotlin
.graphicsLayer { alpha = 0.5f }
.background(...)
.alpha(0.1f)
```

最后这个 `.alpha(0.1f)` **并不会重新把前面的 `background` 包进去**，因为它写在 `background` 后面；它主要作用于后续内容。如果想用 `Modifier.alpha()` 让**背景和文字整个 Card 一起透明**，应该和前面的 `graphicsLayer` 一样放在 `background` 前：

```kotlin
.size(...)
.alpha(0.1f)
.background(...)
```

所以这里正好再次验证了我们刚才那个结论：**Layer Modifier 写在哪里，不是格式习惯，而是在决定它包住哪些绘制内容。**
