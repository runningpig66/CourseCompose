### 阶段一：先让完整链路真正跑起来——第一个 `ViewModel + StateFlow` 页面

#### 1. 这一阶段到底要解决什么问题

这一阶段先刻意不讲 ViewModel 的生命周期细节、不讲 `stateIn()`、不讲 Repository，也不讨论复杂架构。我们只建立一个最重要的第一手经验：

> **Compose 页面可以不自己保存屏幕业务状态，而是把用户操作交给 ViewModel；ViewModel 启动协程、修改 `StateFlow`，Compose 观察这份状态并自动刷新 UI。**

Android 官方目前把 `ViewModel` 定位为**屏幕级 state holder 的实现方式**，并建议 Android Compose UI 使用 `collectAsStateWithLifecycle()` 来收集 Flow。`viewModelScope` 则是绑定到 ViewModel 的协程作用域。([Android Developers][1])

我们今天先把这一条完整链路跑通：

```text
用户点击按钮
    ↓
Composable 调用 ViewModel.loadData()
    ↓
viewModelScope.launch { ... }
    ↓
ViewModel 修改 MutableStateFlow
    ↓
StateFlow 发出新的 UI State
    ↓
collectAsStateWithLifecycle()
    ↓
Compose State 改变
    ↓
读取这份状态的 UI 重组
```

你现在先不要试图把这张图里的每一个箭头都解释到底。**阶段一的任务是先亲眼看到它工作。**

#### 2. 准备依赖

我们这一节需要 Lifecycle 对 Compose 的两个集成库。当前 Lifecycle 稳定版为 `2.11.0`；官方文档分别把 `lifecycle-viewmodel-compose` 用于 Compose 中的 ViewModel 工具，把 `lifecycle-runtime-compose` 用于包括 `collectAsStateWithLifecycle()` 在内的 Lifecycle Compose API。([Android Developers][2])

如果你的练习项目还没有，就加入：

```kotlin
dependencies {
    implementation("androidx.lifecycle:lifecycle-viewmodel-compose:2.11.0")
    implementation("androidx.lifecycle:lifecycle-runtime-compose:2.11.0")
}
```

如果你使用 `libs.versions.toml`，当然也可以放进 version catalog。**这一节不值得为了依赖管理再开支线，能正常 import 就行。**

#### 3. 第一个完整教学案例

新建：

```text
Sec05A_ViewModelStateFlowBasics.kt
```

这个案例模拟一个很常见的真实页面行为：

> 用户点击“加载数据” → 页面立即进入 Loading → ViewModel 模拟执行 1.5 秒异步任务 → 加载成功 → 页面展示结果。

这里的 `delay()` 暂时代替网络请求、数据库操作等真正的异步任务。这样我们可以把所有注意力放在 ViewModel、协程和状态传递本身。

完整代码如下：

```kotlin
package your.package.name

import android.util.Log
import androidx.compose.foundation.layout.Arrangement
import androidx.compose.foundation.layout.Column
import androidx.compose.foundation.layout.fillMaxSize
import androidx.compose.foundation.layout.padding
import androidx.compose.material3.Button
import androidx.compose.material3.CircularProgressIndicator
import androidx.compose.material3.MaterialTheme
import androidx.compose.material3.Text
import androidx.compose.runtime.Composable
import androidx.compose.runtime.getValue
import androidx.compose.ui.Alignment
import androidx.compose.ui.Modifier
import androidx.compose.ui.unit.dp
import androidx.lifecycle.ViewModel
import androidx.lifecycle.compose.collectAsStateWithLifecycle
import androidx.lifecycle.viewModelScope
import androidx.lifecycle.viewmodel.compose.viewModel
import kotlinx.coroutines.delay
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.launch

private const val TAG = "Sec05A"

data class LoadUiState(
    val isLoading: Boolean = false,
    val message: String = "还没有加载数据",
    val loadCount: Int = 0
)

class LoadViewModel : ViewModel() {

    private val _uiState = MutableStateFlow(LoadUiState())

    val uiState: StateFlow<LoadUiState> = _uiState.asStateFlow()

    init {
        Log.d(TAG, "ViewModel 创建：${this.hashCode()}")
    }

    fun loadData() {
        if (_uiState.value.isLoading) return

        Log.d(TAG, "收到 UI 的 loadData() 事件")

        viewModelScope.launch {
            Log.d(TAG, "协程开始执行")

            _uiState.value = _uiState.value.copy(
                isLoading = true,
                message = "正在加载..."
            )

            Log.d(TAG, "StateFlow -> Loading")

            delay(1500)

            val newCount = _uiState.value.loadCount + 1

            _uiState.value = LoadUiState(
                isLoading = false,
                message = "第 $newCount 次加载成功",
                loadCount = newCount
            )

            Log.d(TAG, "StateFlow -> Success，第 $newCount 次")
        }
    }
}

@Composable
fun ViewModelStateFlowBasicsRoute(
    viewModel: LoadViewModel = viewModel()
) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()

    ViewModelStateFlowBasicsScreen(
        uiState = uiState,
        onLoadClick = viewModel::loadData
    )
}

@Composable
private fun ViewModelStateFlowBasicsScreen(
    uiState: LoadUiState,
    onLoadClick: () -> Unit
) {
    Column(
        modifier = Modifier
            .fillMaxSize()
            .padding(32.dp),
        horizontalAlignment = Alignment.CenterHorizontally,
        verticalArrangement = Arrangement.spacedBy(
            space = 24.dp,
            alignment = Alignment.CenterVertically
        )
    ) {
        Text(
            text = uiState.message,
            style = MaterialTheme.typography.headlineSmall
        )

        Text(
            text = "成功加载次数：${uiState.loadCount}"
        )

        if (uiState.isLoading) {
            CircularProgressIndicator()
        }

        Button(
            onClick = onLoadClick,
            enabled = !uiState.isLoading
        ) {
            Text(
                if (uiState.isLoading) {
                    "加载中"
                } else {
                    "加载数据"
                }
            )
        }
    }
}
```

然后在你的 `setContent` 中把它作为当前页面运行：

```kotlin
setContent {
    MaterialTheme {
        ViewModelStateFlowBasicsRoute()
    }
}
```

#### 5. 现在重新沿着代码走一遍

刚才最重要的地方，其实不是某一个 API，而是**职责已经第一次被拆开了**。

Composable 这一侧没有：

```kotlin
var message by remember { ... }
var isLoading by remember { ... }
var count by remember { ... }
```

也没有：

```kotlin
CoroutineScope(...)
```

更没有：

```kotlin
delay(1500)
```

Composable 做的事情非常克制：

```kotlin
val uiState by viewModel.uiState.collectAsStateWithLifecycle()
```

然后：

```kotlin
ViewModelStateFlowBasicsScreen(
    uiState = uiState,
    onLoadClick = viewModel::loadData
)
```

也就是说，它主要干两件事：

**第一，读取状态。**

**第二，把用户事件交出去。**

而真正决定“点击以后应该做什么”的，是：

```kotlin
fun loadData()
```

它属于 `LoadViewModel`。

这已经出现了现代 Android UI 架构里最重要的一条分界线：**UI 描述当前状态长什么样；ViewModel 持有并生产这个屏幕需要的状态。** Android 官方也明确建议 ViewModel 作为 screen-level state holder 使用，而不是把它当成任意小组件的状态容器。([Android Developers][1])

#### 6. 第一个主角：`MutableStateFlow`

ViewModel 里面有两行非常经典的代码：

```kotlin
private val _uiState = MutableStateFlow(LoadUiState())

val uiState: StateFlow<LoadUiState> = _uiState.asStateFlow()
```

今天先只建立最浅的一层理解。

`MutableStateFlow` 里面**始终有一个当前值**。创建它的时候就必须给一个初始状态：

```kotlin
LoadUiState()
```

因此页面第一次出现时，并不需要等数据库、网络或者其他东西先发射一个值，UI 马上就有：

```kotlin
isLoading = false
message = "还没有加载数据"
loadCount = 0
```

之后 ViewModel 可以修改：

```kotlin
_uiState.value = ...
```

而外部看到的是：

```kotlin
StateFlow<LoadUiState>
```

也就是页面能够观察状态，但不能通过这个公开接口随便修改状态。

`MutableStateFlow` 可以通过 `.value` 更新当前状态，而 `asStateFlow()` 会把可变的 StateFlow 暴露成只读的 `StateFlow`。这是 Kotlin Coroutines 官方 API 本身提供的能力。([Kotlin][3])

至于为什么它一定要有初始值、为什么它叫 **State**Flow、重复设置相同值会怎样、新 collector 会拿到什么——**全部留到阶段三实验。**

现在不要吃撑。

---

#### 7. 第二个主角：`viewModelScope`

点击按钮以后：

```kotlin
fun loadData() {
    viewModelScope.launch {
        ...
        delay(1500)
        ...
    }
}
```

这里你应该非常熟悉 `launch` 和协程了。真正的新东西只有：

```kotlin
viewModelScope
```

你之前学习 `LaunchedEffect` 和 `rememberCoroutineScope` 时，已经知道一个核心原则：

> **协程不能凭空存在，它一定属于某个 CoroutineScope，而 scope 决定这项工作的生命周期。**

现在只是多了一种非常重要的 scope：

```kotlin
viewModelScope
```

它属于这个 `ViewModel`。官方定义是：每个 ViewModel 都有对应的 `viewModelScope`，其中启动的协程会在 ViewModel 被 clear 时自动取消。([Android Developers][4])

阶段一我们只记一句：

> **这是“属于 ViewModel 的工作”的协程作用域。**

至于什么叫 ViewModel 被 clear、旋转屏幕为什么不一定 clear、退出页面什么时候 clear，我们阶段二会直接拿这个 Demo 做实验。现在先不要提前展开。

---

#### 8. 第三个主角：`collectAsStateWithLifecycle()`

ViewModel 现在对外给我们的东西是：

```kotlin
StateFlow<LoadUiState>
```

但是你已经非常熟悉 Compose 的那一套东西了。Compose 真正能够追踪读取并驱动重组的核心，是：

```kotlin
State<T>
```

因此这里发生了一次非常关键的“接头”：

```kotlin
val uiState by viewModel.uiState.collectAsStateWithLifecycle()
```

可以暂时把它理解成：

```text
StateFlow<LoadUiState>
          ↓
collectAsStateWithLifecycle()
          ↓
State<LoadUiState>
          ↓
Compose 读取
          ↓
重组
```

Android 官方目前推荐 Android 应用使用 `collectAsStateWithLifecycle()` 收集 Flow；它会生命周期感知地收集 Flow，并把最新值表示为 Compose `State`。([Android Developers][5])

这里其实已经和你刚学完的 `produceState()` 产生了一点熟悉感：

> **外部世界的状态 → Compose 能读取的 `State<T>`。**

但现在先不比较内部实现，更不重新讲 `produceState`。阶段四我们再把这条桥彻底拆开。

---

#### 9. 最值得你现在盯住的一次状态变化

我们只追踪这句：

```kotlin
_uiState.value = _uiState.value.copy(
    isLoading = true,
    message = "正在加载..."
)
```

它执行以后，发生的是：

```text
MutableStateFlow 的当前值改变
        ↓
StateFlow 的观察者收到新状态
        ↓
collectAsStateWithLifecycle() 得到新值
        ↓
它所代表的 Compose State 改变
        ↓
ViewModelStateFlowBasicsRoute 读到了新的 uiState
        ↓
下层 Screen 得到新的参数
        ↓
Text / CircularProgressIndicator / Button
根据新 uiState 描述新的 UI
```

所以页面从：

```text
还没有加载数据
```

变成：

```text
正在加载...
```

并不是因为 ViewModel 跑过去找到一个 `TextView`：

```kotlin
textView.text = "正在加载"
```

ViewModel甚至根本不知道页面有没有 `Text`。

它只做了一件事情：

```kotlin
旧状态
↓
新状态
```

UI 再根据新状态重新描述自己。

这和你以前学习声明式 UI、状态提升、单向数据流时的知识终于开始接到**真正的 App 架构**上了。

#### 10. 为什么这里专门定义 `LoadUiState`

我们完全可以写成三个独立 StateFlow：

```kotlin
val message: StateFlow<String>
val isLoading: StateFlow<Boolean>
val count: StateFlow<Int>
```

但是这个页面实际上在某一个时刻存在的是**一整个页面状态**：

```kotlin
LoadUiState(
    isLoading = true,
    message = "正在加载...",
    loadCount = 1
)
```

所以我们先用了：

```kotlin
data class LoadUiState(...)
```

来表达：

> **“当前这个屏幕是什么状态？”**

这还不是阶段六真正要讲的完整 `UiState` 架构。今天你只需要先感受到：**ViewModel 并不是给 UI 塞零碎变量，它可以对外提供整个屏幕当前状态的一张快照。**

这也是为什么以后你的真实 App 里面会大量出现：

```kotlin
HomeUiState
CalendarUiState
StatisticsUiState
SettingsUiState
```

之类的类型。

#### 11. 为什么我把 Composable 拆成 Route 和 Screen

你可能注意到了，我没有直接写：

```kotlin
@Composable
fun Screen(
    viewModel: LoadViewModel = viewModel()
) {
    // 所有 UI 全塞这里
}
```

而是：

```kotlin
@Composable
fun ViewModelStateFlowBasicsRoute(
    viewModel: LoadViewModel = viewModel()
) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()

    ViewModelStateFlowBasicsScreen(
        uiState = uiState,
        onLoadClick = viewModel::loadData
    )
}
```

再配：

```kotlin
@Composable
private fun ViewModelStateFlowBasicsScreen(
    uiState: LoadUiState,
    onLoadClick: () -> Unit
)
```

这是故意的，但目前只需要理解一个很简单的理由：

`Route` 是**连接 ViewModel 和 Compose UI 的地方**；

`Screen` 只知道：

```kotlin
状态是什么
用户点击以后调用哪个 lambda
```

所以 Screen 根本不需要知道：

```kotlin
ViewModel
StateFlow
viewModelScope
```

你以前已经学过状态提升，因此这个结构本质上不是新知识，只是把以前的经验正式连接到了 ViewModel。

后面进入 UDF 时，这个结构会越来越有价值。

#### 12. 现在最重要的一张图

阶段一真正希望你留下的，不是一堆 API 定义，而是下面这张图：

```text
┌──────────────────────────── Compose ────────────────────────────┐
│                                                                │
│  ViewModelStateFlowBasicsScreen                                │
│                                                                │
│       显示 uiState                    用户点击按钮               │
│            ↑                              │                     │
│            │                              ↓                     │
│  collectAsStateWithLifecycle()      onLoadClick()              │
│            ↑                              │                     │
└────────────│──────────────────────────────│─────────────────────┘
             │                              │
             │ StateFlow                    │ loadData()
             │                              ↓
┌────────────│──────────────────── ViewModel ─────────────────────┐
│            │                                                   │
│        uiState                                         │
│            ↑                                                   │
│      MutableStateFlow                                          │
│            ↑                                                   │
│      修改 _uiState.value                                      │
│            ↑                                                   │
│      viewModelScope.launch                                     │
│            │                                                   │
│      异步业务工作                                               │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

方向非常重要。

**状态向下走：**

```text
ViewModel
→ StateFlow
→ Compose
→ UI
```

**事件向上走：**

```text
用户
→ UI
→ ViewModel
```

这就是我们后面越来越完整的单向数据流的雏形。

#### 13. 阶段一先不要得出的几个错误结论

第一，不要理解成：

> “以后所有 `remember` 都应该换成 ViewModel。”

不是。什么状态属于 ViewModel、什么状态应该留在 Compose，我们后面专门划边界。

第二，不要理解成：

> “ViewModel 就是为了保存旋转屏幕的数据。”

这只是它生命周期特性的一个结果，并不是理解 ViewModel 的最佳起点。官方现在更强调它作为**屏幕级状态持有者以及业务逻辑访问点**的职责。([Android Developers][1])

第三，也不要理解成：

> “StateFlow 是 Compose 专用状态。”

不是。`StateFlow` 来自 Kotlin Coroutines，而 Compose 只是通过 `collectAsStateWithLifecycle()` 把它接入 Compose `State` 世界。([Kotlin][6])

第四，不要觉得：

> “这不就是 `mutableStateOf` 换个名字？”

后面你会发现这两个东西处在**不同层次和生态位置**。现在只需要知道，它们最终都可以驱动 UI，但工作模型并不相同。

### 阶段二：ViewModel 生命周期与 `viewModelScope`——它到底活多久，协程又跟谁走

阶段一我们已经跑通了：

```text
UI Event
→ ViewModel
→ viewModelScope
→ StateFlow
→ Compose State
→ UI
```

但里面其实留下了两个很大的黑盒：

```kotlin
viewModel: LoadViewModel = viewModel()
```

和：

```kotlin
viewModelScope.launch { ... }
```

这一阶段我们就专门拆这两个黑盒，而且继续使用你刚刚实际敲好的 **`Sec05A_ViewModelStateFlowBasics.kt`**。不新增业务，不换案例。

这一阶段最终要建立的核心心智模型是：

> **ViewModel 的寿命不由某次 Composable 调用决定，而由它所归属的 `ViewModelStoreOwner` 决定；`viewModelScope` 又跟着 ViewModel 的寿命走。**

官方的准确描述也是：ViewModel 会一直存在，直到它所属的 `ViewModelStoreOwner` 永久消失；`viewModelScope` 中启动的协程则在 ViewModel 被 clear 时自动取消。([Android Developers][1])

---

#### 1. 先解决一个最容易形成错误直觉的问题：`viewModel()` 不是“创建 ViewModel”

我们代码里写了：

```kotlin
@Composable
fun ViewModelStateFlowBasicsRoute(
    viewModel: LoadViewModel = viewModel()
)
```

第一次看到很容易产生这样的直觉：

```text
Composable 执行
↓
viewModel()
↓
new LoadViewModel()
```

如果真是这样，那麻烦就大了。

因为 Compose 可以不断重组：

```text
第一次组合
→ 创建 ViewModel A

状态改变
→ 重组
→ 创建 ViewModel B

再改变
→ 重组
→ 创建 ViewModel C
```

那 ViewModel 根本不可能保存任何东西。

实际上，`viewModel()` 更应该理解为：

> **向当前作用域对应的 ViewModel 存储区请求一个 `LoadViewModel`。如果已经有对应实例，就拿已有实例；没有时才创建。**

而这个“当前作用域”背后的关键角色就是：

```kotlin
ViewModelStoreOwner
```

当前 Compose 的 `viewModel()` 默认会从最近的 `LocalViewModelStoreOwner` 获取 owner。在普通没有 Navigation 包裹干预的 Activity Compose 页面中，通常就是宿主 `Activity`；使用 Navigation Compose 后，通常会是当前 `NavBackStackEntry`。([Android Developers][2])

所以先把阶段一的错误想象：

```text
Composable
   │
   └── 创建 ViewModel
```

改成：

```text
Composable
   │
   │ viewModel()
   ↓
找到当前 ViewModelStoreOwner
   ↓
找到它的 ViewModelStore
   ↓
有没有这个 LoadViewModel？
   │
   ├── 有 → 返回原来的
   │
   └── 没有 → 创建并保存
```

这一下，很多东西就开始通了。

#### 2. 第一个实验：重组会不会创建新的 ViewModel？

你现在已经有：

```kotlin
init {
    log("$TAG05A ViewModel 创建：${this.hashCode()}")
}
```

很好，我们再暂时给 `Route` 加一个你已经学过的 `SideEffect`：

```kotlin
@Composable
fun ViewModelStateFlowBasicsRoute(
    viewModel: LoadViewModel = viewModel()
) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()

    SideEffect {
        log("$TAG05A Route 完成一次组合，ViewModel=${viewModel.hashCode()}")
    }

    ViewModelStateFlowBasicsScreen(
        uiState = uiState,
        onLoadClick = viewModel::loadData
    )
}
```

这里故意使用 `SideEffect`，而不是直接：

```kotlin
log(...)
```

写在 Composable 函数体里。

你刚学过原因：Composable 函数体不是执行副作用的可靠位置，而 `SideEffect` 会在一次成功的 Composition 完成后执行。

现在重新运行。

第一次进入：

```text
Sec05A ViewModel 创建：12345678
Sec05A Route 完成一次组合，ViewModel=12345678
```

点击“加载数据”。

`StateFlow` 变成 Loading，Compose 状态变化，因此相关 UI 会发生重组。随后你可能看到：

```text
Sec05A Route 完成一次组合，ViewModel=12345678
```

1.5 秒以后 Success：

```text
Sec05A Route 完成一次组合，ViewModel=12345678
```

但你不会因为这些正常重组不断看到：

```text
ViewModel 创建
ViewModel 创建
ViewModel 创建
```

最关键的是 hash：

```text
12345678
12345678
12345678
```

还是同一个。

于是第一个结论出现了：

> **Composable 重组 ≠ ViewModel 重建。**

`viewModel()` 写在 Composable 里面，并不意味着每次 Composable 重组就重新实例化 ViewModel。

这也是为什么：

```kotlin
viewModel: LoadViewModel = viewModel()
```

可以非常自然地写在 Route 里。

#### 3. 所以 ViewModel 到底归谁？

这就必须正式认识：

```kotlin
ViewModelStoreOwner
```

名字其实非常直白：

```text
ViewModelStoreOwner

拥有
    ↓
ViewModelStore

里面保存
    ↓
ViewModel
```

可以先理解成：

```text
Activity / NavBackStackEntry / 某些其他 Owner
                │
                ↓
        ViewModelStore
                │
                ↓
          LoadViewModel
```

ViewModel 真正的生命周期问题因此不应该问：

> “这个 Composable 活多久？”

而应该问：

> **“这个 ViewModel 当前被 scope 到哪个 ViewModelStoreOwner？”**

官方目前明确列出的常见 owner 包括 Activity、Navigation destination / graph 等；ViewModel 的存在时间跟着它所属的 owner，而不是跟着某次 Composable 函数执行。([Android Developers][1])

这也是我上一阶段为什么纠正你一句话：

> “`viewModelScope` 生命周期比页面大。”

这个说法**有时候现象上成立，但不能作为定义**。

真正准确的是：

```text
ViewModelStoreOwner 决定
        ↓
ViewModel 的生命周期
        ↓
viewModelScope 的生命周期
```

这是最值得记住的因果链。

#### 4. 第二个实验：旋转屏幕到底发生了什么？

现在开始第一个真正有 Android 味道的实验。

为了看得非常清楚，我们临时给 `MainActivity` 加日志：

```kotlin
class MainActivity : ComponentActivity() {

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        log("$TAG05A Activity onCreate：${this.hashCode()}")

        setContent {
            CourseComposeTheme {
                ViewModelStateFlowBasicsRoute()
            }
        }

    override fun onDestroy() {
        log(
            "$TAG05A Activity onDestroy：" +
                "${this.hashCode()}，" +
                "isChangingConfigurations=$isChangingConfigurations"
        )

        super.onDestroy()
    }
}
```

同时给 ViewModel 增加：

```kotlin
override fun onCleared() {
    log("$TAG05A ViewModel onCleared：${this.hashCode()}")
    super.onCleared()
}
```

现在按这个顺序操作：

```text
1. 启动 App
2. 点击加载两次
3. 确认 loadCount = 2
4. 旋转手机
```

假设第一次 Activity 是：

```text

```

你很可能看到：

```text

ViewModel 创建：999
```

旋转以后：

```text

Activity onCreate：222
```

注意：

```text
Activity
111 → 222
```

**Activity 真换了。**

但是你应该没有看到：

```text
ViewModel onCleared：999
ViewModel 创建：888
```

而页面仍然显示：

```text
成功加载次数：2
```

ViewModel 还是：

```text
999
```

于是我们终于可以把“ViewModel 能抗旋转”说准确了。

#### 5. ViewModel 不是因为“Activity 没销毁”才保住的

这是非常重要的一刀。

初学时经常会产生一种模糊理解：

> “ViewModel 能保存旋转数据，因为旋转的时候 Activity 好像没真正死。”

错。

**Activity 对象真的被销毁，然后创建了新的 Activity 对象。**

你刚才的 hash 已经亲眼看到了：

```text
Activity 111
    ↓ destroy

Activity 222
    ↓ create
```

真正特殊的是：

> 配置变更时，Activity 所对应的 `ViewModelStore` 会被保留下来，让新的 Activity 继续使用原来的 ViewModel 实例。

Android 的 `ViewModelStore` 就是专门设计成在配置变更期间被保留的；只有当 owner 真正永久结束时，store 才应该被清理。([Android Developers][3])

所以实际模型更接近：

```text
第一次 Activity #111
        │
        ↓
 ViewModelStore
        │
        ↓
 LoadViewModel #999


发生旋转


Activity #111 销毁
        X

ViewModelStore 保留
        │
        ↓
 LoadViewModel #999
        │
        ↓
新的 Activity #222 继续使用
```

这就比一句：

> “ViewModel 生命周期比 Activity 长。”

准确得多。

因为它并不是无条件比 Activity 长。

**它只是针对配置变更具有保留机制。**

---

#### 6. 这里重新理解你之前说的“ViewModel 比页面寿命长”

现在你应该可以把它改成一句非常准确的话：

> **一次 Composable 的存在、一次 Composition、甚至一次因配置变更而创建出来的 Activity 实例，都不一定等于 ViewModel 的生命周期边界。ViewModel 的边界由它所属的 `ViewModelStoreOwner` 决定。**

比如我们的当前实验中，可以近似画成：

```text
Activity #1
|---------|

              配置变更

             Activity #2
             |---------|

ViewModel
|----------------------------------|
```

所以 Activity **实例**换掉了。

ViewModel 没换。

官方文档也明确指出，配置变更期间 ViewModel 中的异步工作能够继续执行，这正是它状态与工作的 persistence 特性之一。([Android Developers][1])

#### 7. 第三个实验：协程运行到一半旋转，会发生什么？

这才是这一阶段最有价值的实验。

我们把：

```kotlin
delay(1500.milliseconds)
```

**临时改成：**

```kotlin
delay(8.seconds)
```

然后操作：

```text
点击“加载数据”
↓
看到“正在加载”
↓
等 2 秒
↓
旋转手机
↓
继续等待
```

你的第一反应可能会有两个候选答案。

可能 A：

```text
旧 Activity 被销毁
↓
页面没了
↓
协程取消
```

也可能 B：

```text
ViewModel 没销毁
↓
viewModelScope 没取消
↓
协程继续跑
```

正确的是 **B**。

官方明确说明：`viewModelScope` 是每个 ViewModel 对应的 CoroutineScope，其中启动的协程会在 **ViewModel 被 clear** 时自动取消，而不是因为 Activity 发生普通配置变更就取消。([Android Developers][4])

所以你会看到：

```text
点击
↓
协程开始

2 秒后旋转

旧 Activity destroy
↓
新 Activity create
↓
同一个 ViewModel
↓
同一个 viewModelScope 中的协程继续运行
↓
8 秒总时间到达
↓
StateFlow → Success
↓
新页面显示加载成功
```

也就是说：

```text
旧 UI：没了
ViewModel：还在
协程：还在
状态：还在
新 UI：重新接回来
```

这个现象非常重要。

---

#### 8. 这就是 `viewModelScope` 真正解决的问题

假设你不用 ViewModel，而把这个 8 秒任务绑在某次 UI Composition 上，例如：

```kotlin
LaunchedEffect(...) {
    delay(8.seconds)
    ...
}
```

你之前已经学过：

> `LaunchedEffect` 的协程属于 Composition。

当对应 Composable 离开 Composition 时，协程会取消；key 改变时，也会取消旧协程并重新启动。([Android Developers][4])

而现在：

```kotlin
viewModelScope.launch {
    delay(8.seconds)
}
```

表达的是另一件事：

> **这个工作不是“这一次 Composable 存在期间的 UI 副作用”，而是“这个 ViewModel 活着期间需要完成的工作”。**

因此两者不是：

```text
LaunchedEffect = 老写法
viewModelScope = 新写法
```

更不是二选一。

而是**生命周期所有权不同**。

```text
LaunchedEffect
    ↓
属于 Composition

viewModelScope
    ↓
属于 ViewModel
```

这其实和你学习协程以后一直建立的原则完全一致：

> **谁负责这项工作，谁提供它的 CoroutineScope。**

#### 9. 用真实 App 场景感受一下这两个 Scope

比如用户打开“账单详情”。

页面第一次出现时，我们需要驱动一个 UI 动画：

```text
页面出现
→ 开始动画
页面消失
→ 动画没有继续存在的意义
```

这非常像：

```kotlin
LaunchedEffect
```

因为工作属于 **Composition**。

但假设用户点击：

```text
刷新本月账单
```

然后 Repository 开始请求 / 查询数据：

```text
用户点击
→ ViewModel 接收事件
→ 加载数据
→ 得到新的 UiState
```

如果只是因为旋转了一下屏幕，就：

```text
取消查询
→ 新页面进来
→ 再请求一次
```

通常并不是我们想要的。

这种工作更自然地属于：

```kotlin
viewModelScope
```

这也是 Android 官方把 ViewModel 描述为既持有 UI state、又负责处理 UI 层业务逻辑与相关操作的原因。([Android Developers][1])

#### 10. 那到底什么时候 `viewModelScope` 才真的取消？

现在就要看：

```kotlin
onCleared()
```

我们刚刚添加了：

```kotlin
override fun onCleared() {
    log("$TAG05A ViewModel onCleared：${this.hashCode()}")
    super.onCleared()
}
```

旋转时：

```text
Activity onDestroy
```

出现了。

但是：

```text
ViewModel onCleared
```

没有出现。

这意味着：

```text
Activity 对象销毁
≠
ViewModel clear
```

什么时候会 clear？

对于一个 **Activity-scoped ViewModel**，最典型的是 Activity 真正 `finish`；对于 Navigation destination scoped ViewModel，则通常是对应 navigation entry 从 back stack 被永久移除。([Android Developers][1])

所以现在不要背：

```text
onDestroy → onCleared
```

这个关系是错的。

应该记：

```text
ViewModelStoreOwner 永久结束
          ↓
ViewModelStore clear
          ↓
ViewModel onCleared()
          ↓
viewModelScope cancel
```

这条关系非常重要。

#### 11. 第四个实验：真正结束 Activity

现在重新打开 App。

启动一个长任务：

```kotlin
delay(8.seconds)
```

然后在任务完成之前，**按返回键真正退出当前 Activity**。

这次你应该看到类似：

```text
Activity onDestroy：xxx，isChangingConfigurations=false
ViewModel onCleared：yyy
```

这里终于和旋转不同了。

旋转：

```text
Activity destroy
ViewModel 不 clear
```

真正 finish：

```text
Activity destroy
ViewModel clear
```

于是现在的模型已经很清晰：

```text
              Activity destroy
                     │
          ┌──────────┴──────────┐
          │                     │
    配置变更导致             永久结束
          │                     │
          ↓                     ↓
ViewModelStore 保留       ViewModelStore clear
          │                     │
          ↓                     ↓
ViewModel 保留           ViewModel onCleared()
                                │
                                ↓
                       viewModelScope cancel
```

这才是 ViewModel 生命周期真正应该掌握的深度。

#### 12. 我们再把“协程取消”亲眼看出来

现在给 `loadData()` 临时加一个 `try/finally`，专门用于实验：

```kotlin
fun loadData() {
    if (_uiState.value.isLoading) return

    log("$TAG05A 收到 UI 的 loadData() 事件")

    viewModelScope.launch {
        log("$TAG05A 协程开始执行")

        try {
            _uiState.value = _uiState.value.copy(
                isLoading = true,
                message = "正在加载..."
            )

            log("$TAG05A StateFlow -> Loading")

            delay(8.seconds)

            val newCount = _uiState.value.loadCount + 1

            _uiState.value = LoadUiState(
                isLoading = false,
                message = "第 $newCount 次加载成功",
                loadCount = newCount
            )

            log("$TAG05A StateFlow -> Success，第 $newCount 次")
        } finally {
            log("$TAG05A loadData 协程 finally")
        }
    }
}
```

再执行两组实验。

**实验 A：加载中旋转**

你应该最终看到：

```text
协程开始执行
Activity onDestroy：changingConfig=true
Activity onCreate
StateFlow -> Success
loadData 协程 finally
```

也就是说旋转**没有把这个协程取消**。

**实验 B：加载中真正退出 Activity**

你应该看到：

```text
协程开始执行
Activity onDestroy...
ViewModel onCleared
loadData 协程 finally
```

而：

```text
StateFlow -> Success
```

不会出现。

为什么？

因为 `delay()` 是可取消的挂起函数。ViewModel clear 后，其 `viewModelScope` 被取消，正在 `delay()` 的子协程收到取消，后面的 Success 代码不会继续正常执行；`finally` 则仍会进入。`viewModelScope` 随 ViewModel clear 自动取消这一生命周期关系，是 Lifecycle 提供它的核心语义。([Android Developers][4])

这个实验比背十遍：

> “viewModelScope 会自动取消。”

价值大得多。

#### 13. 一个很重要的细节：进入后台 ≠ ViewModel 被销毁

这里很容易跟我们下一阶段涉及到的 Lifecycle-aware collection 混起来。

你按：

```text
Home
```

把 App 放到后台，通常不要认为：

```text
页面不可见
→ ViewModel clear
→ viewModelScope cancel
```

不是这套关系。

`viewModelScope` 的取消点是：

```text
ViewModel clear
```

而不是简单的：

```text
Activity STOPPED
```

所以一个已经运行中的 `viewModelScope` 协程，**不会仅仅因为页面进入后台就自动停止**。官方 UI-state production 文档也明确指出，ViewModel 中的协程通常会继续运行，即使 UI 当前不可见，除非协程被显式取消或 ViewModel 被 clear。([Android Developers][5])

这和：

```kotlin
collectAsStateWithLifecycle()
```

形成了一个非常漂亮的区别。

默认情况下，`collectAsStateWithLifecycle()` 会在 Lifecycle 至少达到 `STARTED` 时收集，在低于该状态时停止收集。([Android Developers][4])

所以以后你会看到这种情况：

```text
ViewModel
viewModelScope 工作仍然可以继续
StateFlow 当前状态继续存在

          ↑

UI 进入后台
collectAsStateWithLifecycle 暂停收集

          ↓

UI 再回来
重新开始收集
拿到 StateFlow 当前状态
```

不过**这一层我们阶段四再正式实验**。

这里先知道它跟 ViewModel 生命周期不是一回事。

#### 14. 现在回头看 `viewModelScope`，它其实一点都神秘

你系统学过协程，所以这里没有必要把它包装成 Android 魔法。

本质仍然是：

```kotlin
CoroutineScope
```

只是 Android Lifecycle 为 ViewModel 提供了一个合适的作用域：

```kotlin
viewModelScope
```

其生命周期契约是：

```text
ViewModel 存活
        │
        ↓
viewModelScope 可以承载工作

ViewModel clear
        │
        ↓
viewModelScope cancel
        │
        ↓
其中正在运行的子协程被取消
```

因此真正重要的不是记：

```kotlin
viewModelScope.launch
```

这几个字。

而是看到这句代码时，你脑子里自动出现：

> **“这项工作的 owner 是 ViewModel。”**

这才算真正理解它。

#### 15. 那为什么不用自己创建一个 `CoroutineScope`？

比如我们完全可以：

```kotlin
class LoadViewModel : ViewModel() {

    private val scope = CoroutineScope(...)

    fun loadData() {
        scope.launch {
            ...
        }
    }
}
```

但这样一来：

> **谁负责在 ViewModel 不用了以后取消它？**

你自己。

于是又得写清理逻辑。

而 `viewModelScope` 本身已经把：

```text
ViewModel 生命周期
+
CoroutineScope 生命周期
```

绑定好了，所以普通 ViewModel 业务任务直接使用它即可。官方也把自定义 scope 主要留给需要特殊配置、测试控制等更进阶的情况。([Android Developers][4])

因此真实项目里看到：

```kotlin
viewModelScope.launch {
    repository.doSomething()
}
```

它并不是“Android 样板代码”。

它实际上表达了架构含义：

> **这项操作属于这个 ViewModel，并且不应该比这个 ViewModel 活得更久。**

#### 16. 和你已经学过的三个协程入口正式对齐一次

现在我们已经有三个非常熟悉的东西：

```kotlin
LaunchedEffect
rememberCoroutineScope
viewModelScope
```

这一阶段不做完整“兄弟 API 大辨析”，只做必要定位。

`LaunchedEffect` 表达：

> **Composable 进入 Composition 后，由状态/key 驱动的一项 Composition 生命周期工作。**

`rememberCoroutineScope()` 表达：

> **需要从 UI callback 手动启动，但这项工作仍属于当前 Composition。**

`viewModelScope` 表达：

> **这项工作属于 ViewModel，而不是某一次 Composition。**

所以：

```text
LaunchedEffect
        │
        ├── 谁触发？Composition / key
        └── 谁拥有？Composition

rememberCoroutineScope
        │
        ├── 谁触发？UI callback
        └── 谁拥有？Composition

viewModelScope
        │
        ├── 谁触发？通常 ViewModel 方法
        └── 谁拥有？ViewModel
```

这里最值得防止的一种错误理解就是：

> “用户点击 Button，因此一定应该用 `rememberCoroutineScope()`。”

不对。

**触发位置不是唯一判断标准，真正重要的是这项工作属于谁。**

比如：

```text
点击按钮
→ 展开 Snackbar
```

如果它纯粹属于当前 UI，可能是 Compose scope。

而：

```text
点击按钮
→ 保存一笔账单
→ Repository 写数据库
→ 更新页面业务状态
```

这项工作通常应该进入 ViewModel，由 ViewModel 管理，而不是因为“事件来自 Button”就绑死在当前 Composable 上。

#### 17. 一个必须提前堵住的误区：ViewModel ≠ 永久存储

旋转之后：

```text
loadCount = 2
```

还在。

这很容易让人兴奋地得出：

> “太好了，把状态放 ViewModel 就不会丢了。”

这句话必须马上切掉。

ViewModel解决的是**在它自己的生命周期范围内保留状态与工作**，尤其能跨越配置变更。

但是：

```text
系统杀掉整个 App 进程
```

以后，内存里的：

```text
LoadViewModel 对象
MutableStateFlow 对象
LoadUiState 对象
```

还能存在吗？

当然不能。

**整个进程内存都没了。**

官方因此专门区分配置变更和 system-initiated process death；需要跨进程死亡恢复的轻量 UI 状态，可以使用 `SavedStateHandle`，而更大的持久数据应该依赖真正的持久化数据层。([Android Developers][6])

所以：

```text
remember
    ↓
Composition 生命周期

rememberSaveable
    ↓
可借助 saved instance state 跨重建/部分进程恢复

ViewModel
    ↓
ViewModelStoreOwner 生命周期
    ↓
天然跨配置变更

SavedStateHandle
    ↓
给 ViewModel 中需要恢复的轻量状态提供 saved-state 备份

Room / DataStore / 文件 / 服务端
    ↓
真正持久化数据
```

这里先只定位 `SavedStateHandle`，**这一节不展开它。**

你已经学过 `rememberSaveable`，因此只需要知道：

> ViewModel 解决“我的 screen state 和工作不应该因为一次旋转就全部重来”。

它不等于数据库，也不等于永久保存。

### 阶段三：真正学懂 `StateFlow`——它为什么特别适合表示 UI State

前两个阶段里，我们一直在使用下面两行代码：


Kotlin 官方对它的定义非常值得抓住：`StateFlow` 是一个可观察的状态持有者，始终拥有一个当前值；它是 hot flow，并且状态更新存在 equality-based conflation。换句话说，它首先代表的是“**此时此刻状态是什么**”，然后才具有 Flow 的收集能力。([Kotlin][1])

#### 1. 先看完整实验：让 StateFlow 的几个特性一次全部暴露出来

这个例子依然保留 `ViewModel + Route + Screen`，因为我们学习的是 Android App 中真正使用 StateFlow 的方式，而不是在一个控制台程序里孤立测试 Flow。

你可以直接新建 `Sec05B_StateFlowBehavior.kt`：

```kotlin
private const val TAG05B = "Sec05B"

data class StateFlowLabUiState(
    val count: Int = 0,
    val message: String = "初始状态"
)

class StateFlowLabViewModel : ViewModel() {

    private val _uiState = MutableStateFlow(
        StateFlowLabUiState()
    )

    val uiState: StateFlow<StateFlowLabUiState> =
        _uiState.asStateFlow()

    private var lateCollectorJob: Job? = null

    init {
        log("$TAG05B ViewModel 创建")

        // 注意：现在还没有启动下面两个 collector。
        // StateFlow 已经拥有自己的当前值。
        log("$TAG05B collector 启动前 value = ${_uiState.value}")

        // Collector A：快速 collector
        viewModelScope.launch {
            uiState.collect { state ->
                log(
                    "$TAG05B Collector A 收到：" +
                            "count=${state.count}, message=${state.message}"
                )
            }
        }

        // Collector B：故意设计成慢 collector
        viewModelScope.launch {
            uiState.collect { state ->
                log(
                    "$TAG05B Collector B 开始处理：" +
                            "count=${state.count}"
                )

                delay(1200)

                log(
                    "$TAG05B Collector B 处理完成：" +
                            "count=${state.count}"
                )
            }
        }
    }

    fun increment() {
        _uiState.update { oldState ->
            oldState.copy(
                count = oldState.count + 1,
                message = "普通 +1"
            )
        }
    }

    fun setEqualValue() {
        val oldState = _uiState.value
        val newState = oldState.copy()

        log(
            "$TAG05B 准备设置相等对象：" +
                    "old == new → ${oldState == newState}"
        )

        _uiState.value = newState
    }

    fun burstUpdate() {
        viewModelScope.launch {
            repeat(5) { index ->
                _uiState.update { oldState ->
                    oldState.copy(
                        count = oldState.count + 1,
                        message = "连续更新 ${index + 1}/5"
                    )
                }

                log(
                    "$TAG05B Producer 写入：" +
                            "count=${_uiState.value.count}"
                )

                // 给快速 collector 一个运行机会，
                // 后面专门观察慢 collector 会发生什么。
                yield()
            }
        }
    }

    fun startLateCollector() {
        if (lateCollectorJob != null) {
            log("$TAG05B Collector C 已经启动过")
            return
        }

        log(
            "$TAG05B 即将启动 Collector C，" +
                    "当前 value=${_uiState.value}"
        )

        lateCollectorJob = viewModelScope.launch {
            uiState.collect { state ->
                log(
                    "$TAG05B Collector C 收到：" +
                            "count=${state.count}, message=${state.message}"
                )
            }
        }
    }

    fun printCurrentValue() {
        log("$TAG05B 直接读取 value：${_uiState.value}")
    }

    override fun onCleared() {
        log("$TAG05B ViewModel onCleared")
        super.onCleared()
    }
}
```

#### 2. 实验 A：没有 collector 之前，StateFlow 就已经有值

重新进入页面，你应该首先看到类似：

```text
Sec05B ViewModel 创建
Sec05B collector 启动前 value = StateFlowLabUiState(count=0, message=初始状态)
Sec05B Collector A 收到：count=0, message=初始状态
Sec05B Collector B 开始处理：count=0
```

最值得注意的是这两件事情的执行顺序：

```kotlin
private val _uiState =
    MutableStateFlow(StateFlowLabUiState())
```

执行以后，我们甚至还没有调用：

```kotlin
uiState.collect { ... }
```

就已经可以：

```kotlin
_uiState.value
```

并且得到：

```text
StateFlowLabUiState(count=0, message=初始状态)
```

这正是 `StateFlow` 与普通 Flow 建立心智差异的第一个地方：**StateFlow 必须始终拥有一个当前值，因此创建 `MutableStateFlow` 时必须给初始值，而且任何时候都可以通过 `value` 同步读取这个当前值。** Kotlin 官方明确指出，`StateFlow` 不存在“还没有值”的状态，也不存在创建一个没有初始值的 StateFlow 的方式。([Kotlin][1])

所以：

```kotlin
MutableStateFlow(StateFlowLabUiState())
```

不是单纯在说：“以后我要发送很多 `StateFlowLabUiState`。” 它首先是在说：**“从现在这一刻开始，这个状态容器的当前状态就是 `StateFlowLabUiState()`。”** 这就是名字里的 **State**。

#### 3. `value` 不是“最后一次 event”，而是“现在是什么状态”

阶段一里面，我们一直写：

```kotlin
_uiState.value = ...
```

你很容易把 `value` 理解成：“Flow 最近发送的一条数据。” 这不算完全错误，但不够准确。对于 StateFlow，更好的理解应该是：**`value` 就是这份状态现在的值。**

例如：

```kotlin
_uiState.value
```

现在可能是：

```kotlin
StateFlowLabUiState(
    count = 7,
    message = "普通 +1"
)
```

那么不管此刻有没有 Compose 页面正在收集它，不管有没有 collector，这个 StateFlow **现在就是这个状态**。

Android 官方也把 `StateFlow` 描述为 state-holder observable flow：它既向 collectors 提供当前和后续状态，也可以直接通过 `value` 读取当前状态。([Android Developers][2])

这也是为什么真实 ViewModel 里经常可以写：

```kotlin
if (_uiState.value.isLoading) return
```

你阶段一已经这么写过：

```kotlin
fun loadData() {
    if (_uiState.value.isLoading) return
    ...
}
```

这里根本不需要：

```kotlin
_uiState.first()
```

也不需要启动：

```kotlin
_uiState.collect { ... }
```

因为 StateFlow 本来就有**当前状态**，直接读取即可。

#### 4. 实验 B：为什么两个 collector 一启动，马上都收到 `0`

刚才第一次进入页面时：

```text
Collector A 收到：count=0
Collector B 开始处理：count=0
```

注意，我们并没有先做：

```kotlin
_uiState.value = ...
```

两个 collector 却立即拿到了 `0`。

这就是 StateFlow 的第二个非常重要的行为：

> **新 collector 开始收集 StateFlow 时，会立即得到当前状态，然后再继续接收未来的状态变化。**

StateFlow 会向新 collector 提供当前值；它不是从“订阅之后发生的下一次更新”才开始工作。([Kotlin][1])

我们可以画成：

```text
StateFlow 当前值：

          0
          │
          │
Collector A 开始 collect
          ↓
          立即得到 0


后来状态：

          0 → 1 → 2 → 3


这时候 Collector C 才加入
                    ↓
                  立即得到 3
```

这个行为对于 UI State 非常重要。假设你的 ViewModel 已经加载完数据：

```text
StateFlow 当前状态 = Success(data)
```

此时由于配置变化，一个新的 UI 开始重新收集。你希望它怎么办？

绝对不是：“不好意思，你错过之前的 Success 了，请等下一条。”

而应该是：**“你刚来？现在状态就是 Success(data)，直接拿去渲染。”**

这就是 StateFlow 特别适合“状态”的一个核心原因。

#### 5. 实验 C：故意晚一点启动 Collector C

先点击三次：

```text
普通 +1
普通 +1
普通 +1
```

页面显示：

```text
count = 3
```

然后再点击：

```text
启动新的 Collector C
```

预计日志类似：

```text
Sec05B 即将启动 Collector C，当前 value=StateFlowLabUiState(count=3, ...)
Sec05B Collector C 收到：count=3, message=普通 +1
```

注意，Collector C 并没有经历：

```text
0
1
2
3
```

它是在 `3` 的时候才出现，所以一开始拿到的就是：

```text
3
```

以后如果状态继续变成：

```text
4
5
6
```

它再继续接收新的状态。

因此 StateFlow 更接近：

```text
                 ┌───────────────┐
                 │ 当前状态 = 3  │
                 └───────────────┘
                   ↑     ↑     ↑
                   │     │     │
                   A     B     C
```

而不是：

```text
历史消息队列：

0 → 1 → 2 → 3
```

**它不会因为 Collector C 来晚了，就把整个历史从头重放一遍。**

StateFlow 重点保存的是“当前状态”，而不是完整状态历史。官方 API 也指出，StateFlow 始终保留一个最新值供新 collector 获取。([Kotlin][1])

#### 6. 现在终于正式理解：什么叫 Hot Flow

你之前系统学协程 Flow 的时候应该碰过 cold / hot 的概念，这里只唤醒必要的部分。

一个普通的：

```kotlin
val numbers = flow {
    emit(1)
    emit(2)
    emit(3)
}
```

通常可以理解为一份**冷的数据生产流程描述**。collector 来 collect，它才执行；另一个 collector 来，又可以有自己的一次执行。

StateFlow 不一样。当：

```kotlin
private val _uiState = MutableStateFlow(StateFlowLabUiState())
```

这一句执行完成之后，这个 StateFlow 实例本身已经存在，并已经有：

```text
当前值 = StateFlowLabUiState()
```

有没有 collector，不决定这份状态是否存在。因此 Kotlin 官方把 `StateFlow` 定义为 **hot flow**：其 active instance 独立于 collectors 是否存在。([Kotlin][1])

结合你阶段二自己做的 Navigation 实验，其实你已经亲眼见过这个现象了。当你离开 `PracticeDemo` 页面时，UI 不再显示，Compose collector 可能已经不存在，但只要那个 ViewModel 还在：

```text
MutableStateFlow
+
它的当前 value
```

仍然存在。所以：

```text
有没有 collector？
```

和：

```text
StateFlow 有没有当前状态？
```

是两件事情。这就是“hot”在这里真正有用的应用层含义。

---

#### 7. 多个 collector 收集的是同一份状态，不是每人复制一个 StateFlow

现在我们的 ViewModel 至少有：

```text
Collector A
Collector B
```

Compose 这里还有：

```kotlin
collectAsStateWithLifecycle()
```

如果你再点按钮启动 Collector C，就有：

```text
Collector A
Collector B
Collector C
Compose collector
```

它们观察的是**同一个 `uiState`**：

```text
                    StateFlow
                  当前状态 = 5
                /      |      \
               /       |       \
              ↓        ↓        ↓
        Collector A Collector B Collector C

                 ↓
           Compose Collector
```

这就是 StateFlow 天然支持多个 collector 的意义。你没有因为多一个 collector 就复制一份 `_uiState`；大家观察的是同一个状态源。`StateFlow` 本身就是面向多个 subscriber / collector 的共享 hot flow。([Kotlin][1])

真实 App 里面，这意味着 ViewModel 可以对外公开：

```kotlin
val uiState: StateFlow<UiState>
```

不同消费者在需要的时候观察同一份状态，而 ViewModel 仍然保持单一状态源。

#### 8. 实验 D：给 StateFlow 设置“相等的新对象”会怎么样？

现在点：

```text
设置相等状态
```

我们的代码是：

```kotlin
fun setEqualValue() {
    val oldState = _uiState.value
    val newState = oldState.copy()

    log(
        "$TAG05B 准备设置相等对象：" +
                "old == new → ${oldState == newState}"
    )

    _uiState.value = newState
}
```

假设当前：

```kotlin
oldState = StateFlowLabUiState(
    count = 3,
    message = "普通 +1"
)
```

然后：

```kotlin
val newState = oldState.copy()
```

这是一个新的对象实例，但因为 `data class` 的所有属性完全相同：

```kotlin
oldState == newState
```

结果：

```text
true
```

你会看到：

```text
Sec05B 准备设置相等对象：old == new → true
```

但是应该**不会**看到 Collector A / B / C 因此再次收到相同状态。

这就是 StateFlow 一个特别重要的机制：**它根据 `Any.equals()` 判断新值与当前值是否相等；如果相等，就抑制这次状态更新对 collector 的发射。** Kotlin 官方把这一行为称为 strong equality-based conflation，并明确类比 `distinctUntilChanged` 的相等性语义。([Kotlin][1])

所以：

```kotlin
_uiState.value = oldState.copy()
```

即使：

```text
对象引用不同
```

只要：

```text
oldState == newState
```

StateFlow 就认为：**状态没有变化，没有必要再次通知 collectors。**

#### 9. 这和 Compose 里的“状态等价策略”很像，但不要直接当成同一套机制

你已经学过 Compose State，所以这里很容易产生联想：“哦，是不是跟 Compose `mutableStateOf()` 判断新旧值类似？”

在应用层直觉上确实有相似之处：**都是状态容器，不希望毫无意义地重复通知同样的状态。**

但不要因此认为：

```text
StateFlow == Compose Snapshot State
```

它们不是同一个状态系统。

`MutableStateFlow` 属于：

```text
kotlinx.coroutines
```

Compose Snapshot State 属于：

```text
Compose Runtime / Snapshot System
```

这一阶段只需要记：

```text
StateFlow
使用 equals 判断状态更新是否真的不同
```

到了阶段四：

```text
StateFlow
↓
collectAsStateWithLifecycle()
↓
Compose State
```

我们再研究两个状态世界是怎么接起来的。

#### 10. “相等值不发射”为什么对 UI State 非常合理？

假设当前状态：

```kotlin
UiState(
    isLoading = false,
    count = 5
)
```

你又写入：

```kotlin
UiState(
    isLoading = false,
    count = 5
)
```

从“状态”的角度看：

```text
以前是什么？
false, 5

现在是什么？
false, 5
```

什么都没有变。

所以 StateFlow 不把它当作一次有意义的新状态，这非常符合状态容器的语义。

但这个特性也立即告诉我们：**StateFlow 天生不是一个“每调用一次 emit，我都要求 collector 精确收到一次”的事件队列。**

如果你的需求是：

```text
用户点击一次 → event #1
用户又点击一次 → event #2
用户又点击一次 → event #3
```

即使三个 event 内容完全一样，你仍然要求三个都不能丢，那么它和 StateFlow 的“当前状态”模型之间已经出现语义冲突。

这里我们只认识边界。`SharedFlow`、Channel、以及现代 Android 对 UI event 的处理方式，会在后面的选型阶段再讨论；现在不抢 StateFlow 主线。

#### 11. 实验 E：最重要的一个——慢 collector 会不会收到每一个中间值？

现在终于点击：

```text
连续快速更新 5 次
```

我们的 producer 会：

```kotlin
repeat(5) {
    _uiState.update { ... }
    yield()
}
```

假设开始时：

```text
count = 0
```

producer 很快写入：

```text
1
2
3
4
5
```

Collector A 没有额外延迟，所以在这个特意加入 `yield()` 的实验里，它通常有机会观察到非常多、甚至全部中间状态：

```text
Collector A 收到：1
Collector A 收到：2
Collector A 收到：3
Collector A 收到：4
Collector A 收到：5
```

但 Collector B 每拿到一个值以后，都故意：

```kotlin
delay(1200)
```

因此很可能出现这样的日志：

```text
Collector B 开始处理：1

Producer 写入：1
Producer 写入：2
Producer 写入：3
Producer 写入：4
Producer 写入：5

...1200ms 后...

Collector B 处理完成：1
Collector B 开始处理：5
```

它很可能没有按照：

```text
1
2
3
4
5
```

一个一个补课。而是直接追到：

```text
5
```

这正是 StateFlow 的另一个核心行为：**当状态变化速度快于 collector 的处理速度时，慢 collector 可以跳过中间状态，但它会得到最新状态。** Kotlin 官方明确说明，StateFlow 更新是 conflated 的，慢 collector 会跳过快速发生的中间更新，同时始终能够看到最近的值。([Kotlin][1])

注意，由于协程调度存在实际时序差异，你本机具体看到：

```text
0 → 3 → 5
```

还是：

```text
0 → 2 → 5
```

并不重要。真正要观察的是：

> **Collector B 不保证逐条消费 1、2、3、4、5，却最终追上最新状态。**

#### 12. 现在终于可以准确解释 `conflation`

这是 StateFlow 最容易被背成术语、却没有真正理解的部分。

对于我们这一节，StateFlow 的 conflation 至少要从两个现象去理解。

第一种：

```text
当前状态 = A
写入状态 = A

A == A
↓
没有新的状态需要发送
```

这是 **equality-based conflation**。

第二种：

```text
状态快速变化：

A → B → C → D → E

慢 collector 还在处理 A
↓
没有必要要求它把 B、C、D 全部补处理
↓
醒来以后直接看到最新 E
```

这是 StateFlow 作为**最新状态容器**的 conflated 行为。官方 `StateFlow` 文档把这两者放在同一套状态语义下描述：`value` 的快速更新会被合并，而新旧值的相等性判断基于 `Any.equals()`。([Kotlin][1])

所以以后看到：

```text
conflated
```

不要只背：“合流。”

应该想到：**我关心的是最新状态，不保证每个瞬间的中间状态都被每个 collector 逐条处理。**

这就是 StateFlow 的灵魂。

#### 13. 为什么这种“会跳过中间值”的东西反而特别适合 UI？

乍一听很容易觉得：“丢数据不是 bug 吗？”

对于**事件历史**，可能是。但对于**当前状态**，通常恰恰正确。

假设一个下载页面极短时间内经历：

```text
Progress 10%
Progress 11%
Progress 12%
...
Progress 78%
```

UI collector 一时处理不过来。两秒之后，你真正希望它做的是：

```text
从 10% 开始，
把 11、12、13、14……
一个一个全部补画？
```

还是：

```text
现在已经 78% 了，
直接显示 78%？
```

通常当然是后者。再比如：

```text
搜索框当前文本
当前选中的日期
当前账单列表
当前 Loading 状态
当前排序条件
当前用户资料
```

UI 真正需要问的是：**“现在是什么？”**

而不是：“这份状态过去的每一个历史版本是什么？”

因此 Android 官方也推荐在 UDF 的 UI 层，把不断产生的 UiState 通过类似 `StateFlow` 这样的 observable state holder 暴露给 UI，让 UI 对**当前状态变化**做响应。([Android Developers][3])

#### 14. StateFlow 不是事件队列，这句话现在应该真正有感觉了

我们可以把两种需求放在一起。

**状态问题：**

```text
“现在登录了吗？”
“当前余额是多少？”
“现在 Loading 吗？”
“当前选中哪一天？”
“当前页面应该显示什么？”
```

这里最重要的是：

```text
当前值
```

所以 StateFlow 非常自然。

而另一类问题可能是：

```text
“刚刚发生过几次独立事件？”
“每一个事件是不是都必须消费？”
```

如果你要求：

```text
A
A
A
```

三次完全相同的信息都必须被当成三次独立发生的事情，并且慢消费者也不能把它们简单合成“最新 A”，那就已经不是 StateFlow 最擅长表达的语义了。

因此以后看到：

```kotlin
StateFlow<UiState>
```

脑子里要出现的是：**“屏幕现在是什么状态？”**

而不是：“这是一个消息传送管道。”

这一区分在真实项目里非常重要。

#### 15. `value = ...` 和 `update { ... }`：为什么这个例子开始改用 `update`

阶段一我们写的是：

```kotlin
_uiState.value = _uiState.value.copy(
    isLoading = true
)
```

这一阶段我在 `increment()` 里故意换成：

```kotlin
_uiState.update { oldState ->
    oldState.copy(
        count = oldState.count + 1,
        message = "普通 +1"
    )
}
```

两种写法在简单单协程场景里都完全能工作。但是，只要你的新状态依赖**旧状态**：

```text
old count
↓
+1
↓
new count
```

`update {}` 是更稳妥的标准写法，因为它对“读取旧值并计算新值”这个整体执行原子更新。Kotlin 官方 API 明确说明，`update()` 会原子地根据当前 `MutableStateFlow.value` 计算并设置新值。([Kotlin][4])

为什么这件事重要？考虑两个协程几乎同时执行：

```kotlin
_uiState.value =
    _uiState.value.copy(count = _uiState.value.count + 1)
```

假设初始：

```text
count = 10
```

两个协程可能都先读到：

```text
10
```

然后分别计算：

```text
11
11
```

最终：

```text
count = 11
```

明明加了两次，却只增加了 1。

而：

```kotlin
_uiState.update {
    it.copy(count = it.count + 1)
}
```

就是为这种“基于当前状态原子更新”的需求准备的。([Kotlin][4])

所以以后对于典型 UI State：

```kotlin
_uiState.update {
    it.copy(isLoading = true)
}
```

通常是非常自然的写法。

---

#### 16. 但是 `update {}` 的 lambda 里面不要偷偷做副作用

`update()` 还有一个特别值得现在就记住的小边界。官方 API 明确提醒：如果存在并发更新，传给 `update()` 的函数可能被执行多次。([Kotlin][4])

**update {} 的 lambda 在 CAS 竞争下可能因为失败而重试、执行多次，所以里面如果放埋点、数据库写入之类副作用，就可能重复执行；因此最安全的原则就是：lambda 只负责“旧状态 → 新状态”的纯计算，副作用放到 update 外面。**

因此下面这种写法不要养成：

```kotlin
_uiState.update {
    saveToDatabase() // 不要这样
    sendAnalytics()  // 不要这样

    it.copy(count = it.count + 1)
}
```

因为 `update {}` 里面最适合放的是：

```text
旧状态
↓
纯计算
↓
新状态
```

也就是：

```kotlin
_uiState.update { oldState ->
    oldState.copy(
        count = oldState.count + 1
    )
}
```

数据库保存、网络请求、埋点等副作用应该在外面做。这一点以后进入真正 ViewModel 业务代码时会非常重要。

#### 17. `_uiState` 为什么 private，而 `uiState` 为什么只读

现在再回头看：

```kotlin
private val _uiState =
    MutableStateFlow(StateFlowLabUiState())

val uiState: StateFlow<StateFlowLabUiState> =
    _uiState.asStateFlow()
```

这已经不应该再被理解为“Android 喜欢下划线的样板代码”。

真正表达的是：

```text
ViewModel 内部：

MutableStateFlow
↓
可以修改状态


ViewModel 外部：

StateFlow
↓
只能观察 / 读取状态
```

`asStateFlow()` 官方语义就是把 `MutableStateFlow` 暴露成只读 `StateFlow` 接口。([Kotlin][5])

如果我们直接写：

```kotlin
val uiState = MutableStateFlow(...)
```

然后公开出去，那么 Composable 就可以干：

```kotlin
viewModel.uiState.value = ...
```

于是：

```text
ViewModel 可以修改
Composable 也可以修改
其他对象也可以修改
```

谁才是状态源？开始乱了。所以：

```kotlin
private val _uiState: MutableStateFlow<UiState>
val uiState: StateFlow<UiState>
```

表达的不只是 encapsulation。它实际上在维护我们之前一直说的：**单一信息源与单向数据流。**

外部：

```text
只能观察 state
```

如果想改变状态：

```text
发 event 给 ViewModel
```

然后：

```text
ViewModel 决定如何产生新 state
```

这和阶段一已经跑起来的结构完全接上了。

#### 18. 一个很细但非常重要的理解：`StateFlow.collect()` 正常情况下不会自己结束

我们的 Collector C：

```kotlin
lateCollectorJob = viewModelScope.launch {
    uiState.collect { state ->
        log(...)
    }
}
```

点一次以后，这个 Job 会一直处在收集状态，直到对应协程被取消，例如阶段二学过的 ViewModel 被 clear。

这是因为 StateFlow 代表持续存在的 hot state stream；官方 API 明确指出，StateFlow collection 正常不会自行完成。([Kotlin][1])

这也很符合状态语义。你的页面状态不会说：

```text
Loading
Success

好了，
这辈子再也没有状态了，
StateFlow 永久结束。
```

真实页面可能继续：

```text
Success
↓
用户刷新
↓
Loading
↓
Success
↓
用户修改数据
↓
新的 Success
↓
发生错误
↓
Error
```

只要 ViewModel 还活着，这份屏幕状态就有继续变化的可能。

#### 19. 现在回头看阶段一的代码，意义已经完全不一样

阶段一：

```kotlin
private val _uiState = MutableStateFlow(LoadUiState())

val uiState: StateFlow<LoadUiState> = _uiState.asStateFlow()
```

当时你可能理解成：“创建一个可变 StateFlow，然后暴露成不可变。”

现在应该能读出更多东西了：

```text
MutableStateFlow(LoadUiState())
```

意味着：**第一，状态从创建的那一刻就有初始值。**

```text
_uiState.value
```

意味着：**第二，任何时候都可以同步读取当前状态。**

```text
StateFlow<LoadUiState>
```

意味着：**第三，多个 collector 可以观察同一份 hot state。**

新的 collector 加入意味着：**第四，它立即得到当前状态，而不是等待下次更新。**

```kotlin
_uiState.value = equalState
```

意味着：**第五，如果 equals 判断相等，不会产生一次新的状态通知。**

状态快速变化意味着：**第六，慢 collector 不保证消费每个中间值，而是追踪最新状态。**

```kotlin
_uiState.update { ... }
```

意味着：**第七，当新状态依赖旧状态时，可以进行原子的 read-modify-write。**

到了这里，这两行已经不再应该是模板代码。

#### 20. StateFlow 的完整应用层心智模型

这一阶段真正应该保存下来的模型，可以压缩成下面这一张图：

```text
                    MutableStateFlow
                 ┌────────────────────┐
                 │                    │
                 │ 当前值 = State S3 │
                 │                    │
                 └────────────────────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
              ↓            ↓            ↓
         Collector A  Collector B  Collector C
          快速读取       慢速读取       后来加入
              │            │            │
              │            │            └─→ 一加入先拿 S3
              │            │
              │            └─→ 可以跳过中间状态，
              │                追上最新状态
              │
              └─→ 持续观察最新状态


ViewModel 内部：
MutableStateFlow<UiState>
        │
        │ value / update
        ↓
修改当前状态


ViewModel 外部：
StateFlow<UiState>
        │
        ↓
只能观察状态
```

一句话总结：**StateFlow 是一份“始终存在当前值、可以被多个消费者持续观察、以最新状态为核心语义”的 hot state holder；它不是要求完整保存并逐条交付历史消息的事件队列。**

这就是为什么它和 ViewModel 的 `UiState` 天生非常合拍。([Kotlin][1])

#### 22. 阶段三验收

这一阶段最建议你亲手跑的是三个实验：先把 `count` 加到 3 再启动 Collector C；在状态没有变化时点击“设置相等状态”；最后点击“连续快速更新 5 次”，重点对比 Collector A 和故意 `delay(1200)` 的 Collector B。

跑完以后，你应该能自己解释下面六个问题：

1. 为什么还没有任何 collector 时，`MutableStateFlow` 就已经可以读取 `.value`？
2. 为什么一个晚加入的 collector 不需要等待下一次更新，而是立即得到当前状态？
3. 为什么给 `_uiState.value` 设置一个新的 `data class` 对象，但所有属性都一样时，collectors 不会再次收到它？
4. 为什么慢 Collector B 可能只看到 `1 → 5`，而不是保证依次看到 `1 → 2 → 3 → 4 → 5`？
5. 根据前两个实验，为什么说 StateFlow 更像“当前状态容器”，而不是“历史事件队列”？
6. 为什么当新状态依赖旧状态时，真实 ViewModel 代码通常更适合写：

```kotlin
_uiState.update {
    it.copy(...)
}
```

而不是到处写：

```kotlin
_uiState.value = _uiState.value.copy(...)
```

如果这六个问题能够结合你自己的 Logcat 现象解释清楚，那么 **StateFlow 最核心的应用层心智模型已经建立完成**。

### 阶段四：`collectAsStateWithLifecycle()`——StateFlow 怎样真正接入 Compose 与 Android Lifecycle

前三个阶段其实已经把链路拆开了一大半。阶段二解决了“`ViewModel` 和 `viewModelScope` 活多久”，阶段三解决了“`StateFlow` 自己到底是什么”。现在只剩中间最关键的一座桥：

```kotlin
val uiState by viewModel.uiState.collectAsStateWithLifecycle()
```

这行代码虽然短，却同时连接了三个完全不同的世界：Kotlin Coroutines 的 `StateFlow`、Android 的 `Lifecycle`、Compose Runtime 的 `State<T>`。Android 官方把它作为 Android Compose 中收集 Flow 的推荐方式：它会生命周期感知地收集 Flow，并把最新值表示成 Compose `State<T>`；默认只有 Lifecycle 至少达到 `STARTED` 时才进行收集。([Android Developers][1])

这一阶段继续使用：

```text
Sec05B_StateFlowBehavior.kt
```

我们不会重新造一个陌生案例，而是在阶段三的 StateFlow 实验上增加一个“持续生产状态”的测试。这样可以亲眼看到：**ViewModel 还在工作、StateFlow 还在更新，但是 Compose 已经停止收集；页面回来以后，又立即追上 StateFlow 的最新状态。**

#### 1. 先明确我们究竟要验证什么

阶段三已经证明：

```text
StateFlow
    ↓
无论有没有 collector
    ↓
都拥有当前 value
```

阶段二又证明：

```text
App 暂时进入后台
≠
ViewModel 被 clear
≠
viewModelScope 自动取消
```

于是马上出现一个非常现实的问题：假设 ViewModel 每秒钟产生一次新状态，用户按 Home 键把 App 放到后台，那么 UI 还有必要继续每秒 collect 吗？

通常没有必要。用户现在根本看不到这个页面，Compose 没必要继续消费这一串 UI 更新。因此我们真正想要的是：

```text
ViewModel / StateFlow
可以继续存在

        ↓

UI 可见、Lifecycle >= STARTED
        ↓
开始 collect

UI 进入后台、Lifecycle < STARTED
        ↓
停止 collect

UI 再回来
        ↓
重新 collect
        ↓
立刻得到 StateFlow 当前最新值
```

这正是 `collectAsStateWithLifecycle()` 的核心契约。官方 API 文档明确写明：Lifecycle 达到 `minActiveState` 时收集，低于它时停止收集，再次达到时重新开始；默认的 `minActiveState` 是 `Lifecycle.State.STARTED`。([Android Developers][2])

这里先特别校准一个术语：以后我们可以口语上说“后台时暂停 collect”，但技术上更准确的是**停止这次 collection，Lifecycle 再次满足条件后重新开始一次 collection**，不是把同一个 `collect` 调用冻结在某一行然后继续。

#### 2. 给阶段三的 ViewModel 增加一个持续运行的状态生产器

保留你上一阶段的 `StateFlowLabViewModel`，在里面增加下面这一部分即可：

```kotlin
private var lifecycleTickerJob: Job? = null

fun startLifecycleTicker() {
    if (lifecycleTickerJob?.isActive == true) return

    lifecycleTickerJob = viewModelScope.launch {
        log("$TAG05B LifecycleTicker 开始")

        while (isActive) {
            delay(1.seconds)

            _uiState.update { oldState ->
                val newCount = oldState.count + 1

                oldState.copy(
                    count = newCount,
                    message = "ViewModel 持续生产：$newCount"
                )
            }

            log(
                "$TAG05B Producer 写入 StateFlow：" +
                        "count=${_uiState.value.count}"
            )
        }
    }
}

fun stopLifecycleTicker() {
    lifecycleTickerJob?.cancel()
    lifecycleTickerJob = null

    log("$TAG05B LifecycleTicker 停止")
}
```

这个实验非常单纯：点击开始以后，`viewModelScope` 每秒更新一次 `_uiState`。这里仍然使用阶段三刚学过的：

```kotlin
_uiState.update { ... }
```

因为新状态依赖旧的 `count`。`update {}` 内部也只有纯粹的“旧状态 → 新状态”计算，没有副作用；日志放在 `update` 外面，这正好延续你刚才补上的 CAS / retry 心智模型。

然后给 `Screen` 增加两个事件：

```kotlin

                text = "count = ${uiState.count}",

                text = uiState.message
```

#### 3. 给 Compose 这一侧装一个“窃听器”

我们平常直接写：

```kotlin
val uiState by viewModel.uiState.collectAsStateWithLifecycle()
```

当然能够运行，但 Logcat 看不到“Compose 这边到底什么时候正在 collect”。为了做实验，我们临时给 StateFlow 接一个 `onEach`：

```kotlin
@Composable
fun StateFlowBehaviorRoute(
    viewModel: StateFlowLabViewModel = viewModel()
) {
    val observedUiStateFlow = remember(viewModel) {
        viewModel.uiState.onEach { state ->
            log(
                "$TAG05B Route collector 真正收到：" +
                        "count=${state.count}"
            )
        }
    }

    val uiState by observedUiStateFlow.collectAsStateWithLifecycle(
        initialValue = viewModel.uiState.value
    )

    SideEffect {
        log(
            "$TAG05B Compose 完成一次组合：" +
                    "count=${uiState.count}"
        )
    }

    StateFlowBehaviorScreen(
        uiState = uiState,
        onIncrement = viewModel::increment,
        onSetEqualValue = viewModel::setEqualValue,
        onBurstUpdate = viewModel::burstUpdate,
        onStartLateCollector = viewModel::startLateCollector,
        onPrintCurrentValue = viewModel::printCurrentValue,
        onStartLifecycleTicker = viewModel::startLifecycleTicker,
        onStopLifecycleTicker = viewModel::stopLifecycleTicker
    )
}
```

这里的 `onEach` **只是教学探针，不是正式项目应该增加的一层架构**。它本身不会主动做任何事情；只有下游真正 collect 这条 Flow 时，`onEach` 才会运行，因此这条日志能够告诉我们 `collectAsStateWithLifecycle()` 此刻到底有没有在收集。

这里出现了一个小变化：

```kotlin
viewModel.uiState
```

原本类型是：

```kotlin
StateFlow<StateFlowLabUiState>
```

接了：

```kotlin
.onEach { ... }
```

之后对外类型变成了普通：

```kotlin
Flow<StateFlowLabUiState>
```

所以此时调用的是 `Flow.collectAsStateWithLifecycle(initialValue = ...)` 重载，需要我们自己提供初始值。普通生产代码直接针对 `StateFlow` 调用时不需要写 `initialValue`，因为专门的 `StateFlow` 重载会直接使用 `StateFlow.value` 作为返回 Compose State 的初始值。这个区别是 API 明确规定的。([Android Developers][2])

#### 5. 实验 A：页面可见时，一切正常串起来

进入 `PracticeDemo`，点击：

```text
开始 Lifecycle 测试
```

假设当前是 `count = 0`，你会逐渐看到类似：

```text
Sec05B LifecycleTicker 开始

Sec05B Producer 写入 StateFlow：count=1
Sec05B Route collector 真正收到：count=1
Sec05B Compose 完成一次组合：count=1

Sec05B Producer 写入 StateFlow：count=2
Sec05B Route collector 真正收到：count=2
Sec05B Compose 完成一次组合：count=2

Sec05B Producer 写入 StateFlow：count=3
Sec05B Route collector 真正收到：count=3
Sec05B Compose 完成一次组合：count=3
```

这里实际上有三件完全不同的事情。

第一层是：

```text
Producer 写入 StateFlow
```

这是 ViewModel 世界。

第二层是：

```text
Route collector 真正收到
```

这是 Flow → Compose 的桥。

第三层是：

```text
Compose 完成一次组合
```

这是 Compose Runtime 根据 `State<T>` 的变化重新执行相关 UI。

因此现在完整链路已经第一次被日志拆开：

```text
viewModelScope
     ↓
MutableStateFlow.update()
     ↓
StateFlow 发出当前新状态
     ↓
collectAsStateWithLifecycle()
     ↓
Compose State<T>.value 更新
     ↓
读取该 State 的 Composition 失效
     ↓
重新组合
     ↓
Screen 收到新的 uiState
```

Compose 本身不能因为你修改了一个普通 `StateFlow.value` 就自动知道该重组；官方文档明确指出，Compose 读取其他 observable 类型之前，需要先把它们转换为 Compose `State<T>`。对于 Android Flow，官方推荐的转换入口就是 `collectAsStateWithLifecycle()`。([Android Developers][3])

现在保持 ticker 运行，在比如：

```text

```

的时候按 Home。

你应该看到：

```text
Sec05B Activity onStop
```

接下来最关键的日志现象出现了：

```text
Sec05B Producer 写入 StateFlow：count=6
Sec05B Producer 写入 StateFlow：count=7
Sec05B Producer 写入 StateFlow：count=8
Sec05B Producer 写入 StateFlow：count=9
Sec05B Producer 写入 StateFlow：count=10
```

但是应该不再继续出现：

```text

Sec05B Compose 完成一次组合：count=6
Sec05B Route collector 真正收到：count=7
Sec05B Compose 完成一次组合：count=7

```

这就是阶段四最重要的实验结果之一。

**`collectAsStateWithLifecycle()` 停止的是 UI 这一侧的 Flow collection，它没有取消 `viewModelScope`，也没有把 `StateFlow` 冻结，更没有停止 ViewModel 生产数据。** 官方 API 的契约就是 Lifecycle 低于 `STARTED` 时停止 collection；而你阶段二已经证明，`viewModelScope` 的取消边界是 ViewModel clear，不是简单的 Activity `onStop()`。([Android Developers][2])

```text
App 后台

ViewModel
   │
   ├── viewModelScope 继续运行
   │
   ↓
StateFlow
   │
   └── 当前 value 继续变：
       6 → 7 → 8 → 9 → 10

Compose collector
   X
当前没有继续收集
```

这和阶段三的知识严丝合缝：**StateFlow 不依赖 collector 才能存在，它本身就是 hot state holder。**

#### 7. 最精彩的一步：5 秒后重新回到 App

假设离开页面时 UI 最后显示：

```text
count = 5
```

后台期间 ViewModel 已经把 StateFlow 更新到了：

```text
count = 10
```

现在重新打开 App。

你不会看到页面疯狂补演：

```text
6
7
8
9
10
```

而是很快看到：

```text
Sec05B Activity onStart
Sec05B Route collector 真正收到：count=10
Sec05B Compose 完成一次组合：count=10
```

页面直接来到：

```text
count = 10
```

这里其实同时用到了阶段三的两个知识。

首先，Lifecycle 再次达到 `STARTED`，`collectAsStateWithLifecycle()` **重新开始 collection**。其次，被收集的对象是 `StateFlow`，而阶段三已经证明：**新的 collector 一加入，立即拿到 StateFlow 当前最新值。** 因此 UI 并不需要自己维护“后台期间漏了哪些数字”的历史，它重新接上以后问的只是：“现在是什么状态？”

所以这一整个现象可以压缩成：

```text
前台
UI 收到 1 → 2 → 3 → 4 → 5

进入后台
UI collection 停止
             │
ViewModel： 6 → 7 → 8 → 9 → 10

重新前台
UI 开始新的 collection
             ↓
StateFlow 当前值 = 10
             ↓
UI 直接显示 10
```

这正是 **StateFlow 的“当前状态语义”与 `collectAsStateWithLifecycle()` 的 Lifecycle-aware collection 完美配合的地方。**

#### 8. 所以 `collectAsStateWithLifecycle()` 到底干了两件什么事？

到这里，可以把这个长名字拆成两个职责。

第一部分是：

```text
collectAsState
```

也就是：

```text
Flow / StateFlow
        ↓
    收集数据
        ↓
Compose State<T>
```

官方 API 返回类型就是：

```kotlin
State<T>
```

每当活动生命周期期间 Flow 有新值，返回的 `State.value` 被更新；读取这个 `State.value` 的 Compose 代码随后能够发生重组。([Android Developers][2])

第二部分是：

```text
WithLifecycle
```

它解决：

```text
现在 UI 的 Lifecycle
值得不值得继续 collect？
```

默认规则是：

```kotlin
minActiveState = Lifecycle.State.STARTED
```

Lifecycle 达到或超过 `STARTED`：

```text
collect
```

低于 `STARTED`：

```text
停止 collect
```

再次回来：

```text
重新 collect
```

官方还允许把门槛指定成比如：

```kotlin
minActiveState = Lifecycle.State.RESUMED
```

不过普通屏幕 UI State 基本使用默认的 `STARTED` 即可，不需要习惯性改成 `RESUMED`。([Android Developers][1])

#### 9. 终于精确解释我们用了三阶段的这一行

原始代码：

```kotlin
val uiState by viewModel.uiState.collectAsStateWithLifecycle()
```

实际上如果把 Kotlin 属性委托先拿掉，可以想象成：

```kotlin
val uiStateState: State<StateFlowLabUiState> =
    viewModel.uiState.collectAsStateWithLifecycle()
```

那么：

```kotlin
uiStateState.value
```

才是真正的：

```kotlin
StateFlowLabUiState
```

而 `by` 只是利用 Compose `State<T>` 的属性委托，让：

```kotlin
val uiState by ...
```

以后直接写：

```kotlin
uiState.count
```

而不用每次：

```kotlin
uiStateState.value.count
```

所以不要把：

```kotlin
collectAsStateWithLifecycle()
```

理解成：“把 StateFlow 类型永久转换成了另一个对象。” 更适合的理解是：**Composable 建立了一个生命周期感知的收集过程，并用一个 Compose `State<T>` 保存目前已经收集到的最新值。**原来的：

```kotlin
viewModel.uiState
```

仍然是：

```kotlin
StateFlow<UiState>
```

它没有被改造成 Compose State。

Compose 只是另外建立了一座桥：

```text
ViewModel                     Compose

StateFlow<UiState>
        │
        │ collect
        ↓
                          State<UiState>
                                │
                                ↓
                         Composition 读取
```

#### 10. 一个很值得亲手试的反例：为什么不能直接 `.value`

现在把 Route 临时改成：

```kotlin
@Composable
fun StateFlowBehaviorRoute(
    viewModel: StateFlowLabViewModel = viewModel()
) {
    val uiState = viewModel.uiState.value

    StateFlowBehaviorScreen(
        uiState = uiState,
        ...
    )
}
```

乍一看非常合理，因为阶段三刚刚说过：

```kotlin
StateFlow.value
```

就是当前状态。那么为什么还需要麻烦地写：

```kotlin
collectAsStateWithLifecycle()
```

呢？运行以后你会发现，ViewModel 可以继续：

```text
count = 1
count = 2
count = 3
```

但是 UI **不会可靠地随着 StateFlow 改变自动重组**。如果某个无关原因碰巧让这个 Composable 后来重组，它当然可能重新执行 `.value` 并读到新数字，但 StateFlow 的变化本身没有给 Compose Runtime 建立可观察的 Snapshot State 读取关系。原因现在应该非常清楚：

```text
StateFlow.value
```

只是普通 Kotlin 属性读取。而：

```kotlin
val uiState by collectAsStateWithLifecycle()
```

得到的是 Compose：

```kotlin
State<UiState>
```

Compose Runtime 能够跟踪 `State.value` 的读取，并在它改变以后调度相应重组。官方文档也明确说明：对于 Flow 这样的其他 observable 类型，在 Compose 中读取前需要转换成 `State<T>`。([Android Developers][3])

这个反例非常值得跑一次，因为它能彻底消灭一种以后很容易写出来的代码：

```kotlin
val uiState = viewModel.uiState.value
```

**“能读到当前值”不等于“Compose 正在观察这份状态”。**

#### 11. `collectAsState()` 和它是什么关系？

现在主 API 已经真正跑过，我们才有资格看兄弟 API。

Compose Runtime 自己提供：

```kotlin
collectAsState()
```

它同样能够：

```text
Flow
↓
collect
↓
Compose State<T>
```

所以它解决的是“Flow 怎样进入 Compose State”这一半问题，但它没有 Android Lifecycle 这一层语义。Android 官方因此推荐 Android App 使用 `collectAsStateWithLifecycle()`；`collectAsState()` 更适合平台无关的 Compose 代码。([Android Developers][3])

因此不要背成：

```text
collectAsState = 错
collectAsStateWithLifecycle = 对
```

真正的区别是：

```text
collectAsState()
      ↓
Composition-aware

collectAsStateWithLifecycle()
      ↓
Composition-aware + Android Lifecycle-aware
```

在一个普通 Android Screen 中，我们通常选择后者，因为页面虽然还可能留在 Composition 或整个 App 进程里，却已经进入后台，不需要继续消费本来只用于显示的 UI State。官方当前也把 `collectAsStateWithLifecycle()` 作为 Compose 中安全收集 Flow 的推荐方式。([Android Developers][1])

#### 12. 这里和阶段二有一个非常容易混淆的地方

现在我们同时有：

```kotlin
viewModelScope
```

和：

```kotlin
collectAsStateWithLifecycle()
```

它们的 Lifecycle 策略完全不同。

`viewModelScope`：

```text
ViewModel 活着
↓
协程可以继续

ViewModel clear
↓
scope cancel
```

而 UI collection：

```text
Lifecycle >= STARTED
↓
collect

Lifecycle < STARTED
↓
停止 collect
```

所以阶段二你亲眼看到：

```text
页面暂时不显示
但 ViewModel 协程继续计算
```

阶段四又亲眼看到：

```text
ViewModel 继续计算、StateFlow 继续更新
但 UI collector 已经停掉
```

两者没有冲突，因为它们根本由不同 owner、不同生命周期规则控制。([Android Developers][1])

把这两条线分开，是 ViewModel + Flow 架构里面非常重要的一步：

```text
             ViewModel 生命周期
                    │
                    ↓
             viewModelScope
                    │
                    ↓
                StateFlow
                    │
              生命周期边界 ①
                    │
────────────────────┼────────────────────
                    │
          collectAsStateWithLifecycle
                    │
              生命周期边界 ②
                    │
                    ↓
             Compose State
                    │
                    ↓
                   UI
```

#### 13. 一个非常关键的边界：停止 collect ≠ 停止上游生产

你刚才的实验尤其要防止形成一个错误结论：“`collectAsStateWithLifecycle()` 进入后台以后，会把 Flow 上面的任务停下来。” **这句话不能泛化。** 对于我们当前：

```kotlin
viewModelScope.launch {
    while (...) {
        _uiState.update { ... }
    }
}
```

生产者属于 `viewModelScope`，所以 UI 停止 collect 根本不会取消它。`StateFlow` 仍然一路更新。

以后我们会遇到：

```kotlin
repository.someFlow
    .stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(...),
        ...
    )
```

这时候“有没有 subscriber”又可能反过来决定某些上游工作是否保持活跃。**那是阶段五 `stateIn()` 的主题。**

所以现在只记住当前层次：**`collectAsStateWithLifecycle()` 管的是这个 UI collector 什么时候存在，不等于它无条件控制整个上游的数据生产。**

这条边界非常重要，否则下一阶段学 `WhileSubscribed` 时很容易全部搅在一起。

#### 14. 为什么 StateFlow 版本不需要 `initialValue`

现在再看最标准的真实项目代码：

```kotlin
val uiState by viewModel.uiState.collectAsStateWithLifecycle()
```

你可能已经习惯到不会问这个问题：“Compose 的 `State<T>` 一创建就需要有个 value，那这个初始 value 从哪来？”

阶段三已经给出了答案：

```text
StateFlow 永远有当前 value
```

所以专门针对 `StateFlow<T>` 的重载可以直接：

```text
StateFlow.value
      ↓
作为 Compose State 初始值
```

官方 API 文档就是这样规定的。相反，如果你手上只是：

```kotlin
Flow<T>
```

普通 Flow 并不保证天然存在一个“当前 value”，所以对应重载要求：

```kotlin
collectAsStateWithLifecycle(
    initialValue = ...
)
```

([Android Developers][2])

这又一次说明：

```text
StateFlow
```

不是“普通 Flow 换个名字”。

它的“永远存在当前状态”这一特征，从 ViewModel 一直影响到了 Compose API 的设计。

#### 15. 只看一次高价值实现骨架：你刚学完的 `produceState()` 原来就在这里

这一部分不作为源码课继续下钻，但因为你刚刚系统学完 `produceState()`，这里看一眼 AndroidX 当初引入 `collectAsStateWithLifecycle()` 时的核心实现思路非常值。它的结构可以概括成：

```kotlin
produceState(initialValue = ...) {
    lifecycle.repeatOnLifecycle(minActiveState) {
        flow.collect { newValue ->
            value = newValue
        }
    }
}
```

AndroidX 的实现中确实使用了 `produceState` 和 `repeatOnLifecycle` 来完成这座桥：`produceState` 负责把外部异步数据转成 Compose `State<T>`，`repeatOnLifecycle` 负责决定 Flow collection 在什么 Lifecycle 状态启动和停止。([Android Git Repositories][4])

这一下你刚刚学过的 4.13 就不是孤岛了。你已经知道：

```text
produceState
```

擅长：

```text
非 Compose 异步状态
        ↓
Compose State
```

现在：

```text
collectAsStateWithLifecycle
```

可以理解成 AndroidX 已经替你封装好的一个**针对 Flow + Android Lifecycle 的专业版本**：

```text
Flow / StateFlow
      │
      │ 生命周期控制
      ↓
produce Compose State
      ↓
UI
```

所以真实项目里当然不应该自己每次写：

```kotlin
produceState {
    repeatOnLifecycle {
        collect(...)
    }
}
```

直接使用专用 API：

```kotlin
collectAsStateWithLifecycle()
```

即可。

这就是源码在这里真正有价值的地方：不是为了记实现，而是证明你之前学过的几个机制最终真的被组合到了一个真实 Android API 里。到这里立即停止源码下钻。

#### 18. 阶段四最终心智模型

```text

                    │

                    │
```

### 阶段五：`stateIn()`——当上游本来就是 Flow，ViewModel 为什么还要再变成 StateFlow

前四个阶段里，我们使用的都是这一种模式：

```kotlin
private val _uiState = MutableStateFlow(UiState())
val uiState: StateFlow<UiState> = _uiState.asStateFlow()
```

然后 ViewModel 自己在某个时刻：

```kotlin
_uiState.update { ... }
```

这非常适合这样的业务：用户点击按钮，ViewModel 执行一个动作，然后主动修改屏幕状态。但真实 App 还有另一种极其常见的情况：**数据层本身已经持续给你一个 `Flow`。**

例如以后 Room DAO 很可能天然给你：

```kotlin
Flow<List<Transaction>>
```

DataStore 也会暴露 Flow，Repository 也可能组合多个数据源以后返回 Flow。Android 官方当前的架构建议正是：如果数据从下层以流的形式到达 ViewModel，可以在 ViewModel 中用 `stateIn()` 把它转换为 `StateFlow`；简单的、没有下层数据流参与的情况，则可以继续使用 `MutableStateFlow`。([Android Developers][1])

所以阶段五真正解决的问题是：**如果 Repository 已经给了我 `Flow<T>`，我还需要自己创建 `MutableStateFlow`，再启动一个协程把每个值手动搬进去吗？**

通常不需要。`stateIn()` 就是解决这个问题的核心 API。

#### 1. 先看那个“能工作，但明显有点笨”的版本

假设 Repository 已经提供：

```kotlin
fun observeData(): Flow<Int>
```

我们完全可以这样写：

```kotlin
class ExampleViewModel : ViewModel() {

    private val _uiState = MutableStateFlow(0)
    val uiState: StateFlow<Int> = _uiState.asStateFlow()

    init {
        viewModelScope.launch {
            repository.observeData().collect { value ->
                _uiState.value = value
            }
        }
    }
}
```

这段代码并没有错。Android 官方自己的文档里也展示过类似模式，只是当需求仅仅是“把下层 Flow 持续暴露成 ViewModel 的 StateFlow”时，这个手动 `collect → MutableStateFlow` 的中转过程通常可以直接由 `stateIn()` 完成。([Android Developers][2])

我们现在写的代码实际上只是在做：

```text
Repository Flow
      ↓
手动 collect
      ↓
拿到一个 value
      ↓
手动写 MutableStateFlow
      ↓
暴露 StateFlow
```

而 `stateIn()` 可以把它压缩成：

```text
Repository Flow
      ↓
stateIn(...)
      ↓
StateFlow
```

但注意：**`stateIn()` 远远不只是少写几行代码。**它还解决了 “谁来启动上游 Flow” “多个 collector 是否共享同一次上游执行” “没人订阅以后是否还继续消耗资源” 等问题。Kotlin 官方定义中，`stateIn()` 会把 cold `Flow` 转换为一个 hot `StateFlow`，并把单个上游执行实例产生的最新值共享给多个下游 subscriber。([Kotlin][3])

所以这阶段必须跑实验。

#### 2. 新案例：`Sec05C_StateInRepositoryFlow.kt`

这次我们第一次正式加入一个假的 Repository，但它只做一件事：提供一个 cold Flow。没有 Room，没有数据库，没有 DI，不让辅助概念抢走主线。

完整核心代码可以这样写：

```kotlin
private const val TAG05C = "Sec05C"

data class RepositoryTick(
    val session: Int,
    val tick: Int
)

class FakeCounterRepository {

    private var sessionCount = 0

    fun observeTicks(): Flow<RepositoryTick> = flow {
        val session = ++sessionCount

        log("$TAG05C Repository 上游 START，session=$session")

        try {
            var tick = 0

            while (currentCoroutineContext().isActive) {
                delay(1.seconds)

                tick++

                log(
                    "$TAG05C Repository emit：" +
                            "session=$session, tick=$tick"
                )

                emit(
                    RepositoryTick(
                        session = session,
                        tick = tick
                    )
                )
            }
        } finally {
            log(
                "$TAG05C Repository 上游 STOP，session=$session"
            )
        }
    }
}
```

这里最值得注意的是：

```kotlin
fun observeTicks(): Flow<RepositoryTick> = flow { ... }
```

它返回的是普通 cold Flow。调用 `observeTicks()` 得到 Flow 对象本身，并不会立刻执行里面的循环；真正有人开始 collect 时，`flow {}` 内部才开始运行。普通 Flow 默认是 cold stream，每一次收集都会运行对应的数据生产逻辑。([Android Developers][4])

我专门加了：

```text
session=1
session=2
...
```

因为稍后只要上游被停止并重新启动，你就能从日志明确看到：

```text
Repository 上游 START，session=2
```

而不是靠猜。

#### 6. `stateIn()` 到底做了什么

现在正式拆：

```kotlin
.stateIn(
    scope = viewModelScope,
    started = SharingStarted.WhileSubscribed(5_000),
    initialValue = StateInUiState()
)
```

它最重要的结果是：

```text
Flow<StateInUiState>
        ↓
stateIn(...)
        ↓
StateFlow<StateInUiState>
```

但内部心智模型应该比“类型转换”再深一层。原来的：

```text
Repository cold Flow
```

只是一套“有人 collect 时如何生产数据”的流程。`stateIn()` 则创建了一份真正持续存在的：

```text
StateFlow
```

并启动一个**共享协程**，负责在适当时机 collect 上游，把上游最新结果保存成 StateFlow 当前值，再让所有 StateFlow subscribers 共享这一个上游 collection。Kotlin 官方就是这样描述 `stateIn()`：把 cold Flow 转换成 hot StateFlow，并从单个运行中的 upstream instance 共享最新值。([Kotlin][3])

所以更完整的模型是：

```text
             Repository cold Flow
                     │
                     │ 只有一份 upstream collection
                     ↓
              sharing coroutine
                     │
                     ↓
                 StateFlow
              当前值 = 最新数据
               /           \
              /             \
     Compose collector    其他 collector
```

这个“**共享一个上游执行**”非常重要。

---

#### 7. 如果不用 `stateIn()`，两个 collector 可能意味着两次上游执行

假设你直接把 Repository cold Flow 暴露出去：

```kotlin
val data: Flow<RepositoryTick> = repository.observeTicks()
```

然后有两个地方分别：

```kotlin
data.collect { ... }
```

对于 cold Flow，它们通常会分别执行 `flow {}` 的生产逻辑，也就是说你可能看到：

```text
Repository START session=1
Repository START session=2
```

如果这里是真实网络监听、传感器监听或某种昂贵数据源，就意味着可能建立了两套上游工作。

而经过：

```kotlin
stateIn(...)
```

以后，多个下游 subscriber 观察的是同一个 hot `StateFlow`，它们共享 `stateIn` 管理的那一次上游 collection。([Kotlin][3])

这就是为什么名字里有：

```text
state + In
```

可以从应用层理解为：**把这条 Flow 在某个 scope 中“状态化、共享化”。**

---

#### 8. 第一个参数：`scope = viewModelScope`

现在我们终于能看懂为什么 `stateIn()` 必须要一个 `CoroutineScope`。

因为 cold Flow 原来根本没有一个独立持续运行的“拥有者”。`stateIn()` 要建立一个共享 upstream collector，就必须知道：**这个共享工作应该活多久？**

我们写：

```kotlin
scope = viewModelScope
```

表达的就是：**这份 StateFlow 的共享生产工作属于 ViewModel。**

因此如果 `StateInViewModel` 真正被 clear，`viewModelScope` 取消，`stateIn()` 创建的 sharing coroutine 也会结束，上游 Flow collection 随之停止。Kotlin 文档明确说明，`stateIn()` 创建的 hot flow 使用传入的 scope 运行 sharing coroutine；取消这个 scope 会停止相应上游 collection。([Kotlin][8])

这一下你阶段二的知识直接接回来了：

```text
ViewModel
   ↓
viewModelScope
   ↓
stateIn sharing coroutine
   ↓
Repository Flow collection
```

所以：

```kotlin
scope = viewModelScope
```

绝对不是三个参数中随便填的“标准模板”。它是在声明这条状态生产管线的生命周期 owner。

---

#### 9. 第二个参数才是这一阶段最难的：`SharingStarted.WhileSubscribed(5_000)`

这句话如果只翻译成：“有订阅的时候启动。” 还远远不够。它真正控制的是：

```text
stateIn 创建的 sharing coroutine
到底什么时候开始 collect upstream，
什么时候停止 collect upstream。
```

`SharingStarted.WhileSubscribed()` 的默认语义是：第一个 subscriber 出现时开始 sharing，最后一个 subscriber 消失后停止；它还允许通过 `stopTimeoutMillis` 延迟停止。([Kotlin][9])

我们写：

```kotlin
SharingStarted.WhileSubscribed(5_000)
```

意味着：

```text
subscriber 从 0 → 1
        ↓
立即启动上游

subscriber 从 1 → 0
        ↓
不要马上停
        ↓
再等 5 秒
        ↓
5 秒内没人回来
        ↓
停止上游
```

Android 官方目前的架构推荐也经常采用 `WhileSubscribed(5000)`；Lifecycle 文档明确解释，这 5 秒能让订阅在 UI 短暂消失时继续保持，从而处理配置变化等短暂的 collector 丢失。([Android Developers][10])

这正好和阶段四形成接力。

#### 10. 实验 A：Back 回主页，但 3 秒内立刻回来

这里我们反而可以利用你现有练习项目的结构。

你前面已经实际验证过：在目前这套练习工程中，从 `PracticeDemo` Back 回主页时，这个练习 ViewModel 并没有立即 clear。所以这个实验非常干净，不需要按 Home 把进程送到后台。

进入 `PracticeDemo`：

```text
session=1
tick=1
tick=2
tick=3
```

然后按 Back 回到按钮主页。这时候 `StateInRepositoryRoute` 离开 Composition，它原来的：

```kotlin
collectAsStateWithLifecycle()
```

也随之不再成为这个 StateFlow 的 subscriber。

但是由于我们使用：

```kotlin
WhileSubscribed(5_000)
```

你应该还会短暂看到：

```text
Repository emit：tick=4
Repository emit：tick=5
Repository emit：tick=6
```

如果在 **5 秒之内**重新点进 `PracticeDemo`，你应该看到它继续处于：

```text
session=1
```

而不是：

```text
session=2
```

上游没有重新启动。原因就是：

```text
最后一个 subscriber 离开
        ↓
启动 5 秒停止倒计时
        ↓
3 秒后 subscriber 又回来了
        ↓
取消这次停止
        ↓
原来的 upstream 继续
```

这就是 `5_000` 最直观的实际意义。

#### 11. 实验 B：Back 回主页，等超过 5 秒

这次重新进入：

```text
session=1
```

然后 Back，**至少等六七秒**。你应该看到：

```text
Sec05C Repository 上游 STOP，session=1
```

注意这里发生了非常重要的事情：**ViewModel 并没有 clear，`viewModelScope` 也没有 cancel，但是 stateIn 主动停止了 Repository upstream collection。** 为什么？因为：

```text
ViewModel 还活着
```

只决定这条 sharing coroutine **最多可以活多久**。而：

```text
SharingStarted.WhileSubscribed
```

决定的是它在 ViewModel 活着期间**什么时候值得真正 collect upstream**。

所以现在终于有了两层控制：

```text
外层生命周期上限：
viewModelScope
    ↓
ViewModel clear 后，一切结束


内层资源策略：
WhileSubscribed
    ↓
没有 subscriber 一段时间
    ↓
暂时停止 upstream
```

Android 的 UI-state production 指南也明确推荐：如果这条状态生产 pipeline 只在 UI 可见并正在收集时才值得保持活跃，可以选择 `SharingStarted.WhileSubscribed`。([Android Developers][11])

这和阶段四那个“`collectAsStateWithLifecycle()` 只控制 UI collector，不一定停止上游”的结论终于接上了：**它自己确实不直接控制上游，但当下游 subscriber 的消失被 `stateIn(WhileSubscribed)` 感知以后，`stateIn` 可以据此停止自己的上游 collection。**

#### 12. 超过 5 秒以后重新进入：为什么会出现 `session=2`

现在重新点进 `PracticeDemo`。

新的 Compose collector 出现：

```text
subscriber 0 → 1
```

`WhileSubscribed` 于是重新启动 upstream：

```text
Sec05C Repository 上游 START，session=2
```

接下来：

```text
session=2, tick=1
session=2, tick=2
...
```

这说明之前的：

```text
session=1
```

并不是被“暂停后继续执行”。而是真的：

```text
old upstream collection
        ↓
STOP

new subscriber
        ↓
new upstream collection
        ↓
START session=2
```

这个区别非常重要。

---

#### 13. 但是 StateFlow 自己并没有因此消失

这里会出现一个很有意思的现象。假设停止上游之前最后状态是：

```text
session=1
tick=8
```

上游 STOP 以后，`uiState` 这个 `StateFlow` 对象依然存在，因为 ViewModel 还活着。它的：

```kotlin
uiState.value
```

默认仍然保留：

```text
session=1
tick=8
```

`WhileSubscribed()` 默认会保留 replay cache；`replayExpiration` 默认是无限，因此停止上游并不等于把 StateFlow 当前缓存值自动抹掉。([Kotlin][12])

所以重新进入的一瞬间，你可能先看到旧的：

```text
session=1, tick=8
```

紧接着新的 upstream：

```text
START session=2
```

发出：

```text
session=2, tick=1
```

页面再更新到新值。这又一次说明要把两件事分开：

```text
StateFlow 本身存在吗？
```

和：

```text
StateFlow 当前有没有正在 collect upstream？
```

不是同一个问题。

#### 14. 第三个参数：`initialValue`

再看：

```kotlin
initialValue = StateInUiState()
```

为什么 `stateIn()` 必须要这个值？

阶段三已经学过：

```text
StateFlow 必须随时有 current value
```

但是原来的：

```kotlin
repository.observeTicks()
```

只是普通 cold Flow。在第一个 subscriber 出现之前，它甚至都没开始运行，当然还没有真正从 Repository 收到任何值。

于是 `stateIn()` 创建 StateFlow 的那个瞬间必须回答：“现在 StateFlow 的值是什么？”

所以我们提供：

```kotlin
StateInUiState(
    session = 0,
    tick = 0,
    message = "等待 UI 订阅"
)
```

然后：

```text
stateIn 创建完成
↓
StateFlow 当前值 = initialValue

upstream 第一次 emit
↓
StateFlow 当前值 = Repository 真数据
```

Kotlin 官方 `stateIn(scope, started, initialValue)` 的契约就是如此：用这个初始值建立 StateFlow，在 upstream 产生新值之后再更新其当前状态。([Kotlin][3])

所以这个参数也不是为了“API 非要你填一个默认值”。它来自 StateFlow 最根本的语义要求：**StateFlow 在任何时刻都必须有当前状态。**

---

#### 15. `WhileSubscribed(5_000)` 和阶段四到底是什么关系

现在可以把前两个阶段合起来了。阶段四：

```kotlin
collectAsStateWithLifecycle()
```

负责的是：

```text
UI Lifecycle >= STARTED
↓
UI subscriber 存在

UI Lifecycle < STARTED
↓
UI subscriber 消失
```

阶段五：

```kotlin
stateIn(
    started = SharingStarted.WhileSubscribed(5_000)
)
```

负责的是：

```text
subscriber 存在
↓
需要 upstream

subscriber 消失超过 5 秒
↓
停止 upstream
```

因此完整关系终于成为：

```text
              Repository cold Flow
                       ↑
                       │
             stateIn sharing coroutine
                       ↑
                       │
          WhileSubscribed(5_000)
                       ↑
                       │
                 subscriber 数量
                       ↑
                       │
       collectAsStateWithLifecycle()
                       ↑
                       │
                Android Lifecycle
                       ↑
                       │
                    Compose
```

Android 官方甚至专门建议把这两者配合使用：UI 生命周期感知地 collect，而 ViewModel 的状态生产 pipeline 如果只有 UI 可见时才有必要运行，可以使用 `WhileSubscribed`。([Android Developers][11])

这就是阶段五最核心的一张图。

#### 16. 为什么不总是直接让 `viewModelScope.launch { collect(...) }`？

现在回头比较。手动模式：

```kotlin
private val _uiState = MutableStateFlow(UiState())

init {
    viewModelScope.launch {
        repository.observeData()
            .collect { data ->
                _uiState.value = ...
            }
    }
}
```

这种写法的直接结果通常是：

```text
ViewModel 创建
↓
立刻开始 collect Repository
↓
只要 ViewModel 还活着
↓
上游通常一直执行
```

而：

```kotlin
repository.observeData()
    .stateIn(
        viewModelScope,
        SharingStarted.WhileSubscribed(5_000),
        initialValue
    )
```

可以让这条纯状态流管线具备：

```text
StateFlow 当前值
+
多个 subscriber 共享 upstream
+
订阅驱动的启动 / 停止策略
+
ViewModel 生命周期上限
```

所以 Android 当前架构建议中，如果 UI state 来自数据层的 stream，优先使用 `stateIn()`；如果状态主要由 ViewModel 自己的同步用户事件和简单逻辑驱动，则 `MutableStateFlow` 仍然完全合理。([Android Developers][1])

这不是：

```text
MutableStateFlow = 落后
stateIn = 高级
```

而是**状态的来源不同，生产方式不同。**

---

#### 17. `Eagerly`、`Lazily`、`WhileSubscribed` 现在可以简单定位了

主 API 已经跑过，现在再看另外两个策略就不会喧宾夺主。

`SharingStarted.` 表示 sharing coroutine 会立即启动，不等待 subscriber；`Lazily` 是第一个 subscriber 出现以后启动，之后通常继续保持 sharing；`WhileSubscribed` 则会根据 subscriber 是否存在启动和停止。`SharingStarted` 官方提供的内建策略包括这三类。([Kotlin][7])

应用层可以暂时这样理解：

```text
Eagerly
ViewModel 一有这份 stateIn
就尽早启动 upstream

Lazily
第一次有人要以后才启动
但启动后继续保持

WhileSubscribed
有人要才启动
没人要一段时间后停止
```

Android 官方 state-production 指南给出的选择思路也很实用：如果 pipeline 只在 UI 正在显示并收集时有价值，使用 `WhileSubscribed`；如果 UI 可能在 back stack 或其他 tab 上暂时不可见，但你仍希望生产管线继续活跃，可以考虑 `Lazily`。([Android Developers][11])

对于我们接下来普通 ViewModel UI State，大多数时候你会频繁见到：

```kotlin
SharingStarted.WhileSubscribed(5_000)
```

但以后不要把 `5_000` 当成神秘标准常量。它只是一个常见策略值，代表我们愿意为短暂订阅断开保留一小段缓冲时间。Android 官方示例当前也使用这个值来应对类似配置变更的短暂 UI 消失。([Android Developers][10])

#### 18. 一个特别重要的边界：`stateIn()` 不会自动替你做业务状态建模

例如 Repository 给你：

```kotlin
Flow<List<Transaction>>
```

你完全可以：

```kotlin
val transactions =
    repository.observeTransactions()
        .stateIn(
            viewModelScope,
            SharingStarted.WhileSubscribed(5_000),
            emptyList()
        )
```

得到：

```kotlin
StateFlow<List<Transaction>>
```

但真实屏幕往往不只需要一份 List，还可能有：

```text
loading
error
selectedDate
searchQuery
filter
summary
```

那么最终更常见的目标不是单纯：

```kotlin
StateFlow<List<Transaction>>
```

而是：

```kotlin
StateFlow<CalendarUiState>
```

例如：

```text
Repository Flow
      +
用户选择状态
      +
筛选状态
      ↓
map / combine / ...
      ↓
UiState
      ↓
stateIn
      ↓
StateFlow<UiState>
```

这就是我们阶段六要做的事情。所以这一阶段不要急着认为“会 `stateIn()` 就等于会组织完整 UiState”。

今天只把**从下层 stream 到 ViewModel StateFlow**这一条桥学扎实。

#### 19. 顺手建立一个以后看 Room 代码会非常舒服的心智模型

以后你很可能在 DAO 看到：

```kotlin
fun observeTransactions(): Flow<List<Transaction>>
```

Repository：

```kotlin
fun observeTransactions(): Flow<List<Transaction>> =
    dao.observeTransactions()
```

ViewModel：

```kotlin
val uiState: StateFlow<UiState> =
    repository
        .observeTransactions()
        .map { transactions ->
            UiState(
                transactions = transactions
            )
        }
        .stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5_000),
            initialValue = UiState()
        )
```

Compose：

```kotlin
val uiState by viewModel.uiState.collectAsStateWithLifecycle()
```

然后你脑子里不应该再是：“哦，这几行是官方固定模板。” 而应该清楚看到：

```text
Room / Repository
提供 cold Flow
        ↓
ViewModel 用 map 等操作
生产屏幕状态
        ↓
stateIn
把这条状态生产管线
变成 ViewModel 范围内共享的 StateFlow
        ↓
WhileSubscribed
决定有没有 UI subscriber 时
是否值得维持 upstream
        ↓
collectAsStateWithLifecycle
根据 UI Lifecycle
创建 / 取消 subscriber
        ↓
Compose State
        ↓
UI
```

这就是你两个月前看到 `stateIn()` 时可能只能照抄，而现在应该逐渐能解释清楚的那套东西。

#### 20. 阶段五最终心智模型

这一阶段最重要的结论可以压缩成一句：

> **`stateIn()` 把一条普通 Flow 放进指定 CoroutineScope 中，通过一个受 `SharingStarted` 控制的共享 collection，把它转换成具有当前值、可被多个 subscriber 共享的 `StateFlow`。** ([Kotlin][3])

而我们的标准 Android ViewModel 写法：

```kotlin
repositoryFlow
    .map { ... }
    .stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5_000),
        initialValue = UiState()
    )
```

实际上在表达四件事：

```text
map
→ 下层数据如何变成 UI 状态

viewModelScope
→ 这条共享状态生产管线最多活多久

WhileSubscribed(5_000)
→ 在 ViewModel 活着期间，
  什么时候值得真正运行 upstream

initialValue
→ upstream 第一条数据到来之前，
  StateFlow 当前状态是什么
```

这四件事理解以后，`stateIn()` 基本就不再是样板代码了。

#### 21. 阶段五验收

这一阶段建议你一定亲手做两轮 Back 实验：第一轮离开 `PracticeDemo` 不到 5 秒就回来，观察 `session` 是否仍然是 `1`；第二轮离开超过 5 秒，观察 `Repository 上游 STOP session=1`，然后重新进入时是否出现 `START session=2`。

跑完以后，你应该能解释下面六个问题：

1. 如果 Repository 已经返回 `Flow<T>`，为什么很多情况下没必要再手写 `viewModelScope.launch { flow.collect { _uiState.value = ... } }`？
2. `stateIn()` 为什么必须接收一个 `CoroutineScope`，而我们为什么通常传 `viewModelScope`？
3. `SharingStarted.WhileSubscribed(5_000)` 中的“subscriber”到底是谁？为什么 Compose 离开页面会影响它？
4. ViewModel 明明还活着，为什么 Repository upstream 却可以因为 5 秒没人订阅而停止？
5. upstream 停止以后，为什么 `StateFlow` 对象本身和它最后的当前值仍然可以存在？
6. 当新的 subscriber 出现以后，为什么 upstream 可以重新启动一个新的 `session`？

如果这六个问题能结合 Logcat 顺下来，那么你已经真正跨过了 ViewModel 这一课里面很关键的一道坎：**不再只是会创建 `MutableStateFlow`，而是开始理解真实 App 中“数据层 Flow → ViewModel StateFlow”的状态生产管线。**

下一阶段我们会继续升级这条管线，不再只有 Repository 的一个数字。阶段六会进入真正的 **Screen `UiState`**：把 Repository 数据、用户选择、Loading / Error 等页面需要的状态组织成一个屏幕级状态，并开始使用 `combine()`、`map()`、`stateIn()` 把多个状态来源收束成一个稳定的 `StateFlow<UiState>`。

### 阶段六：从几个状态来源，生产真正的 Screen `UiState`

前五个阶段解决的是几个相对独立的问题：ViewModel 活多久、`StateFlow` 是什么、Compose 怎么收集它、Repository 已经给出 `Flow` 时怎样通过 `stateIn()` 变成 ViewModel 范围内共享的 `StateFlow`。到了阶段六，我们开始碰到**真正写 App 时 ViewModel 最核心的工作之一：状态生产（state production）**。

真实页面通常不只有一条 Repository Flow。一个账单页面可能同时依赖数据库里的账单数据、用户输入的搜索词、当前筛选条件，甚至还有 Loading、Error 等状态。最终 UI 并不希望分别理解这些来源，它真正需要的是一句话：“**当前整个屏幕应该长什么样？**” Android 官方的 UI Layer 指南也把 UI state production 描述为把应用数据以及用户交互产生的状态转换成 UI 可以直接呈现的状态；多个 Flow 可以组合后，再通过 `stateIn()` 暴露成一个 `StateFlow`。([Android Developers][1])

这一阶段我们新建：

```text
Sec05D_ScreenUiState.kt
```

这一次的核心结构会升级成：

```text
Repository 数据
        │
        │
用户搜索词 ─────┐
                ├── combine ──→ LedgerUiState ──→ stateIn ──→ StateFlow<LedgerUiState>
用户筛选条件 ───┘                                          │
                                                          ↓
                                            collectAsStateWithLifecycle()
                                                          ↓
                                                      Compose UI
```

这里的重点不是记住 `combine()` 的函数签名，而是理解：**一个 Screen `UiState` 往往不是某个地方直接“存”出来的，而是由若干真正的状态源持续推导出来的。**

#### 1. 先建立这一阶段最重要的区别：Source State 与 Derived State

假设页面依赖三样东西：

```text
Repository 当前账单数据
用户当前搜索词
用户当前筛选条件
```

这三个可以称为我们的**源状态**。它们各自拥有自己的事实来源。

最终：

```kotlin
LedgerUiState
```

则是从它们计算出来的**派生屏幕状态**。

可以用一个非常值得长期记住的表达来理解：

```text
UiState = f(
    repositoryState,
    query,
    filter
)
```

例如 Repository 当前有 6 条账单，`query = "午餐"`，`filter = EXPENSE`，那么屏幕当前真正应该显示哪些 Item、显示几个、合计金额是多少，都可以由这三个输入确定。

这意味着一个非常重要的设计原则：**不要无缘无故再创建第四份可变事实。**

例如不要同时维护：

```kotlin
private val _query = MutableStateFlow("")
private val _filter = MutableStateFlow(...)
private val _repositoryData = ...
private val _uiState = MutableStateFlow(...)
```

然后每当前三者变化，都靠程序员手工记得同步修改 `_uiState`。那会出现两个层次的“真相”：源状态已经变了，但 `_uiState` 忘记同步，页面立刻不一致。

如果 `uiState` 本质可以从源状态确定，那么更自然的模型就是：

```text
源状态变化
    ↓
自动重新推导
    ↓
新的 UiState
```

`combine()` 正是实现这种模型的重要 Flow operator。Kotlin 官方对 `combine` 的定义是：使用**每个上游 Flow 最近一次发出的值**生成新的结果。([Kotlin][2])

#### 2. 先把完整案例跑起来

这个例子模拟以后记账 App 中很常见的一类页面：Repository 持续提供账单列表；用户可以输入搜索词，并选择“全部 / 支出 / 收入”；ViewModel 根据三者计算最终页面状态。

这里我们同时把 Loading 和 Error 放进模型，不过暂时不研究异常处理机制。Repository 会把 Loading / Error 当成普通状态数据发出来，真正的异常捕获放到阶段七再讲。

完整的核心代码如下。沿用你项目里的 `log()`、`@PhonePreviews` 和 `CourseComposeTheme` 即可，imports 让 Android Studio 自动补全。

```kotlin
private const val TAG05D = "Sec05D"

enum class EntryType {
    EXPENSE,
    INCOME
}

enum class LedgerFilter {
    ALL,
    EXPENSE,
    INCOME
}

data class LedgerEntry(
    val id: Int,
    val title: String,
    val amount: Int,
    val type: EntryType
)

sealed interface RepositoryEntriesState {

    data object Loading : RepositoryEntriesState

    data class Data(
        val entries: List<LedgerEntry>
    ) : RepositoryEntriesState

    data class Error(
        val message: String
    ) : RepositoryEntriesState
}

sealed interface LedgerContent {

    data object Loading : LedgerContent

    data class Data(
        val entries: List<LedgerEntry>,
        val signedTotal: Int
    ) : LedgerContent

    data class Error(
        val message: String
    ) : LedgerContent
}

data class LedgerUiState(
    val query: String = "",
    val filter: LedgerFilter = LedgerFilter.ALL,
    val content: LedgerContent = LedgerContent.Loading
)
```

这里先停一下看状态模型。`query` 和 `filter` 无论页面是在 Loading、Data 还是 Error，都可以存在；但 Loading / Data / Error 三者本身互斥，所以我没有写成：

```kotlin
data class LedgerUiState(
    val isLoading: Boolean,
    val items: List<LedgerEntry>,
    val errorMessage: String?
)
```

因为这种模型理论上可以构造出：

```text
isLoading = true
errorMessage = "加载失败"
items = 一堆数据
```

到底页面是什么状态，需要额外制定规则。这里用内部的 `LedgerContent` sealed interface，类型本身就保证某一时刻只能是 Loading、Data、Error 之一。

这不是说以后所有 `UiState` 都必须用 sealed interface。**彼此正交、可以同时存在的状态适合普通字段；互斥状态用 sealed hierarchy 往往更容易维持状态不变量。**

#### 3. Fake Repository：继续保留真实的 cold Flow 行为

Repository 如下：

```kotlin
class FakeLedgerRepository(
    private val shouldFail: Boolean = false
) {

    fun observeEntries(): Flow<RepositoryEntriesState> = flow {
        log("$TAG05D Repository START")

        try {
            emit(RepositoryEntriesState.Loading)

            delay(1200.milliseconds)

            if (shouldFail) {
                emit(
                    RepositoryEntriesState.Error(
                        message = "模拟 Repository 加载失败"
                    )
                )

                return@flow
            }

            val initialEntries = listOf(
                LedgerEntry(
                    id = 1,
                    title = "午餐",
                    amount = 28,
                    type = EntryType.EXPENSE
                ),
                LedgerEntry(
                    id = 2,
                    title = "工资",
                    amount = 12000,
                    type = EntryType.INCOME
                ),
                LedgerEntry(
                    id = 3,
                    title = "地铁",
                    amount = 6,
                    type = EntryType.EXPENSE
                ),
                LedgerEntry(
                    id = 4,
                    title = "咖啡",
                    amount = 18,
                    type = EntryType.EXPENSE
                ),
                LedgerEntry(
                    id = 5,
                    title = "退款",
                    amount = 50,
                    type = EntryType.INCOME
                )
            )

            emit(
                RepositoryEntriesState.Data(
                    entries = initialEntries
                )
            )

            // 模拟数据库稍后又发生了一次变化。
            delay(5.seconds)

            emit(
                RepositoryEntriesState.Data(
                    entries = initialEntries +
                            LedgerEntry(
                                id = 6,
                                title = "晚餐",
                                amount = 42,
                                type = EntryType.EXPENSE
                            )
                )
            )
        } finally {
            log("$TAG05D Repository STOP")
        }
    }
}
```

这仍然是一条 cold Flow。真正有人 collect 时，`flow {}` 才执行；以后如果 collection 被取消并重新开始，这套生产逻辑又会重新执行。普通 Flow 默认就是 cold，并且 Flow operator 默认形成一条顺序的数据处理链。([Kotlin][3])

这一次故意在 5 秒后增加一条“晚餐”，是为了让你看到：**`combine()` 不仅会响应用户输入，也会响应 Repository 自己的数据变化。**

#### 4. ViewModel：这一阶段真正的主角出现了

ViewModel：

```kotlin
class LedgerViewModel : ViewModel() {

    private val repository = FakeLedgerRepository(
        shouldFail = false
    )

    private val _query = MutableStateFlow("")

    private val _filter = MutableStateFlow(
        LedgerFilter.ALL
    )

    val uiState: StateFlow<LedgerUiState> =
        combine(
            repository.observeEntries(),
            _query,
            _filter
        ) { repositoryState, query, filter ->

            log(
                "$TAG05D combine 执行：" +
                        "query=$query, filter=$filter"
            )

            when (repositoryState) {

                is RepositoryEntriesState.Loading -> {
                    LedgerUiState(
                        query = query,
                        filter = filter,
                        content = LedgerContent.Loading
                    )
                }

                is RepositoryEntriesState.Error -> {
                    LedgerUiState(
                        query = query,
                        filter = filter,
                        content = LedgerContent.Error(
                            message = repositoryState.message
                        )
                    )
                }

                is RepositoryEntriesState.Data -> {
                    val normalizedQuery = query.trim()

                    val visibleEntries =
                        repositoryState.entries.filter { entry ->

                            val matchesFilter =
                                when (filter) {
                                    LedgerFilter.ALL -> true

                                    LedgerFilter.EXPENSE ->
                                        entry.type == EntryType.EXPENSE

                                    LedgerFilter.INCOME ->
                                        entry.type == EntryType.INCOME
                                }

                            val matchesQuery =
                                normalizedQuery.isBlank() ||
                                        entry.title.contains(
                                            other = normalizedQuery,
                                            ignoreCase = true
                                        )

                            matchesFilter && matchesQuery
                        }

                    val signedTotal =
                        visibleEntries.sumOf { entry ->
                            when (entry.type) {
                                EntryType.INCOME -> entry.amount
                                EntryType.EXPENSE -> -entry.amount
                            }
                        }

                    LedgerUiState(
                        query = query,
                        filter = filter,
                        content = LedgerContent.Data(
                            entries = visibleEntries,
                            signedTotal = signedTotal
                        )
                    )
                }
            }
        }
        .stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5_000),
            initialValue = LedgerUiState()
        )

    init {
        log("$TAG05D ViewModel 创建：${hashCode()}")
    }

    fun onQueryChange(newQuery: String) {
        log("$TAG05D onQueryChange：$newQuery")

        _query.value = newQuery
    }

    fun onFilterChange(newFilter: LedgerFilter) {
        log("$TAG05D onFilterChange：$newFilter")

        _filter.value = newFilter
    }

    override fun onCleared() {
        log("$TAG05D ViewModel onCleared")
        super.onCleared()
    }
}
```

这一段就是阶段六需要认真啃的核心代码。

你会发现这里再次**没有 `_uiState`**。

`uiState` 完全由：

```text
Repository Flow
_query
_filter
```

推导出来：

```kotlin
combine(...)
    .stateIn(...)
```

也就是说，ViewModel 不是每收到一个事件就开始人工维护整个 `LedgerUiState`，而是只修改真正的**源状态**。

用户改搜索词：

```kotlin
_query.value = newQuery
```

用户改筛选：

```kotlin
_filter.value = newFilter
```

Repository 自己负责数据库数据。而最终页面应该长什么样，则由 `combine()` 自动重新计算。

```kotlin
                horizontalArrangement =
                    Arrangement.spacedBy(8.dp)

                    FilterChip(
                        selected = uiState.filter == filter,
                        onClick = {
                            onFilterChange(filter)
                        },

                                when (filter) {
                                    LedgerFilter.ALL -> "全部"
                                    LedgerFilter.EXPENSE -> "支出"
                                    LedgerFilter.INCOME -> "收入"
                                }
                            )
                        }
                    )
                }
            }

            when (val content = uiState.content) {

                LedgerContent.Loading -> {
                    Box(
                        modifier = Modifier
                            .fillMaxWidth()
                            .weight(1f),
                        contentAlignment = Alignment.Center
                    ) {
                        CircularProgressIndicator()
                    }
                }

                is LedgerContent.Error -> {
                    Box(
                        modifier = Modifier
                            .fillMaxWidth()
                            .weight(1f),
                        contentAlignment = Alignment.Center
                    ) {
                        Text(
                            text = content.message
                        )
                    }

                is LedgerContent.Data -> {

                        LazyColumn(
                            modifier = Modifier.weight(1f),
                            verticalArrangement =
                                Arrangement.spacedBy(8.dp)

                                items = content.entries,

                                        .fillMaxWidth(),

                                        Arrangement.SpaceBetween

                                    Text(
                                        text = when (entry.type) {
                                            EntryType.INCOME ->
                                                "+${entry.amount} 元"

                                            EntryType.EXPENSE ->
                                                "-${entry.amount} 元"
                                        }
                                    )
                                }
                            }
                        }
                    }
                }
            }
        }
    }
}
```

#### 6. 第一次运行：先观察整个屏幕状态是怎么“生成”的

重新进入页面时，首先有一件非常重要的事情发生：

```kotlin
.stateIn(
    ...
    initialValue = LedgerUiState()
)
```

已经创建了一个 StateFlow，所以 Compose **不需要等待 Repository 完成第一次加载**，立即就能拿到：

```text
query = ""
filter = ALL
content = Loading
```

因此你首先能看到 Loading UI。随后 `stateIn()` 根据 `WhileSubscribed` 启动共享 collection，Repository cold Flow 开始执行。`stateIn()` 产出的 StateFlow 在 upstream 第一条真正数据到来以前就必须存在一个当前值，这就是 `initialValue` 的意义。([Kotlin][4])

Logcat 大致会出现：

```text
0 [main] Sec05D ViewModel 创建：85398962
13 [main] Sec05D Compose：query=, filter=ALL, content=Loading
416 [main @coroutine#91] Sec05D Repository START
418 [main @coroutine#90] Sec05D combine 执行：query=, filter=ALL
1659 [main @coroutine#90] Sec05D combine 执行：query=, filter=ALL
1670 [main] Sec05D Compose：query=, filter=ALL, content=Data
6725 [main @coroutine#90] Sec05D combine 执行：query=, filter=ALL
6727 [main @coroutine#91] Sec05D Repository STOP
6736 [main] Sec05D Compose：query=, filter=ALL, content=Data
```

这里有一个你阶段五已经发现过的细节：Repository 第一条也发了 `Loading`，而 `stateIn(initialValue)` 本身已经是完全相等的 `LedgerUiState()`。因此即便 `combine()` 确实执行了一次并得到相同的 Loading，最终 StateFlow 也可能因为 equality-based conflation 而不产生一次新的 Compose 更新。这正是阶段三已经验证过的 StateFlow 相等值行为。([Kotlin][5])

#### 7. `combine()` 到底做了什么：这里需要真正建立运行模型

这是阶段六最核心的 API。当前代码：

```kotlin
combine(
    repository.observeEntries(),
    _query,
    _filter
) { repositoryState, query, filter ->
    ...
}
```

不要把它理解成“把三个 Flow 拼起来”。

更准确的运行模型是：**当这条 combined Flow 被 collect 后，`combine` 会同时收集这些 upstream，并分别保存每一条 Flow 最近一次发出的值。等所有 upstream 至少提供过一个值以后，只要其中任意一个 upstream 再发生变化，transform 就会拿“所有来源此刻最新的值”重新执行一次。**这正是 Kotlin 官方 `combine` 的语义。([Kotlin][2])

假设当前：

```text
Repository = [午餐, 工资, 地铁, 咖啡, 退款]
query      = ""
filter     = ALL
```

那么：

```text
combine
   ↓
计算全部 5 条
```

现在用户输入：

```text
query = "午餐"
```

Repository **没有重新 emit**，filter 也没变，但 `_query` 发出新值，于是：

```text
Repository 最近值 = 原来的 5 条
query 最新值       = "午餐"
filter 最近值      = ALL
                  ↓
               combine
                  ↓
           重新计算 UiState
```

这就是 `combine` 最大的价值。

它关注的不是：“三条 Flow 在同一时刻是不是各 emit 了一条？”

而是：**“任何一个输入发生变化时，我都使用其余输入最近一次的状态重新求结果。”**

---

#### 8. 这里顺便解释：为什么 `combine` 要等所有 Flow 至少 emit 一次

假设你有：

```text
A Flow
B Flow
C Flow
```

`combine` 要计算：

```text
f(A, B, C)
```

但如果 C 从来没有提供过任何值，它连：

```text
C 当前是什么？
```

都不知道，自然没有办法调用 transform。

因此 `combine` 的第一个输出要等到所有输入都至少拥有一个最新值。([Kotlin][2])

我们的例子很舒服，因为：

```kotlin
_query = MutableStateFlow("")
_filter = MutableStateFlow(LedgerFilter.ALL)
```

这两个 `StateFlow` **天生已有初始值**。阶段三已经学过，新 collector 一 collect，它们马上就能提供当前值。真正需要等待的只剩 Repository Flow。而 Repository 一开始就：

```kotlin
emit(RepositoryEntriesState.Loading)
```

因此三份输入很快就齐了。

这几个阶段到这里已经真正接在了一起：

```text
MutableStateFlow 有当前值
        +
Repository emit Loading
        ↓
combine 三份输入全部就绪
        ↓
产生第一个 Derived UiState
```

```text
62596 [main @coroutine#196] Sec05D onQueryChange：咖
62597 [main @coroutine#90] Sec05D combine 执行：query=咖, filter=ALL
62633 [main] Sec05D Compose：query=咖, filter=ALL, content=Data
```

继续输入：

```text
咖啡
```

又会出现：

```text
98647 [main @coroutine#208] Sec05D onQueryChange：咖啡
98647 [main @coroutine#90] Sec05D combine 执行：query=咖啡, filter=ALL
98666 [main] Sec05D Compose：query=咖啡, filter=ALL, content=Data
```

但非常重要的是，你不会重新看到：

```text

```

也不需要 Repository 再发一次列表。

因为 Repository 的最新值已经被 `combine` 保存着。发生变化的是 `_query`，所以 `combine` 使用：

```text
上一次 Repository 数据
+
新的 query
+
上一次 filter
```

重新计算即可。这就是**响应式状态派生**，而不是命令式地写：

```text
query 改了
→ 手动去问 repository 当前数据
→ 手动 filter
→ 再手动 setUiState()
```

#### 10. 实验 B：点击“支出”，再次观察同一套机制

假设现在搜索词清空，点击

```text
支出
```

代码只执行：

```kotlin
_filter.value = LedgerFilter.EXPENSE
```

然后：

```text
_filter emit EXPENSE
        ↓
combine
        ↓
拿 Repository 最新列表
拿 query 最新值 ""
拿 filter 最新值 EXPENSE
        ↓
生成新的 LedgerUiState
        ↓
stateIn 当前值改变
        ↓
Compose 更新
```

这次你会看到午餐、地铁、咖啡，而工资、退款被过滤掉。

这里特别值得注意：`onFilterChange()` 中我们没有使用：

```kotlin
_filter.update { ... }
```

而只是：

```kotlin
_filter.value = newFilter
```

这是完全合理的，因为新值根本不依赖旧值。阶段三讲 `update` 时不要反过来形成另一个机械习惯：**只有 read-modify-write 需要原子更新语义时，`update {}` 才特别有价值；如果就是明确把状态设置成某个新值，直接赋 `value` 很自然。**

#### 11. 实验 C：5 秒以后 Repository 自己变化

如果你什么都不操作，Repository 在第二次 Data 后还会等待 5 秒，然后增加一条：

```text
晚餐 -42
```

这一次变化方向反过来了：

```text
Repository emit 新列表
        ↓
combine
```

`_query` 和 `_filter` 都没有 emit，但 combine 仍然会拿：

```text
新的 Repository 数据
+
当前 query
+
当前 filter
```

重新计算。如果你此时 filter 是：

```text
EXPENSE
```

那么新来的“晚餐”自动出现在列表里。如果 query 此时是：

```text
咖啡
```

那么虽然 Repository 多了一条“晚餐”，最终 UI 仍然只有“咖啡”。这就是为什么：

```text
UiState = f(repositoryData, query, filter)
```

这个心智模型非常强。**谁变化并不重要。任何输入变化，最终状态都会重新由同一套规则推导。**

#### 12. `combine()` 本身仍然是 cold Flow，这一点非常重要

现在来看整条代码：

```kotlin
combine(
    repository.observeEntries(),
    _query,
    _filter
) {
    ...
}
.stateIn(...)
```

`combine(...)` 返回的仍然只是：

```kotlin
Flow<LedgerUiState>
```

它本身并没有因为我们写下这段声明，就永远在后台执行过滤逻辑。真正把它变成：

```kotlin
StateFlow<LedgerUiState>
```

并让一条 sharing coroutine 去 collect 这条 derived Flow 的，还是：

```kotlin
stateIn(...)
```

所以整条结构应该这样理解：

```text
Repository Flow ───────┐
                       │
_query StateFlow ──────┼── combine ──→ Flow<LedgerUiState>
                       │
_filter StateFlow ─────┘
                                      │
                                      ↓
                                  stateIn
                                      │
                                      ↓
                           StateFlow<LedgerUiState>
```

这也是为什么我之前使用“状态生产管线”这个词。它不是某个神秘 Android 概念，只是指这一串：

```text
源数据
→ Flow operators
→ 派生状态
→ StateFlow
```

整个连续的数据处理链。

---

#### 13. 把阶段五的 `WhileSubscribed` 再接回来，会出现一个很漂亮的行为

假设当前 ViewModel 还活着，但是 Compose subscriber 消失超过 5 秒。阶段五已经学过：

```text
stateIn
    ↓
WhileSubscribed
    ↓
停止当前 sharing 对 upstream 的 collection
```

这里的 upstream 已经不只是 Repository 本身，而是：

```text
combine(...)
```

这一整条 Flow。因此 collection 停止以后，`combine` 对三个 upstream 的 collection 也随之停止。但是：

```kotlin
_query
_filter
```

本身都是 `MutableStateFlow`，所以它们依然活着、依然保留自己的当前值。

`uiState` 这个由 `stateIn()` 创建的 StateFlow 也仍然保存上一次最新的 `LedgerUiState`。`WhileSubscribed` 默认保留 replay cache；重新有 subscriber 后 sharing 可以再次启动。([Kotlin][6])

以后重新 collect 时：

```text
combine 重新开始

_query
→ 立即提供当前 query

_filter
→ 立即提供当前 filter

Repository cold Flow
→ 重新开始一次 collection
→ 重新 emit Loading / Data
```

而直到新的一轮派生状态出来以前，`stateIn` 自己仍然持有之前最后的 `UiState`。

现在你应该能看到，前五阶段并不是一个个孤立 API，而是在组成完整架构。

---

#### 14. 为什么最终通常希望公开一个 Screen `UiState`

我们当然可以对 Compose 暴露：

```kotlin
val entries: StateFlow<List<LedgerEntry>>
val query: StateFlow<String>
val filter: StateFlow<LedgerFilter>
val loading: StateFlow<Boolean>
val error: StateFlow<String?>
```

然后 Screen 自己 collect 五次。技术上当然能写。问题不是“collect 五次性能一定不行”，而是职责变得含糊：**到底谁负责定义“这些东西组合起来意味着当前屏幕是什么状态”？**

如果 Screen 自己开始：

```text
收 entries
收 filter
收 query
然后自己做业务筛选
自己计算 total
自己推断 loading/error
```

那 ViewModel 就逐渐退化成“给 UI 发原材料的盒子”，真正的 screen state production 跑回 Composable 里了。

Android 官方建议 ViewModel 作为 screen-level state holder，在业务逻辑参与时把状态提升到 ViewModel，并向 UI 暴露不可变状态以及修改状态的事件。([Android Developers][7])

所以我们现在更希望：

```kotlin
val uiState: StateFlow<LedgerUiState>
```

Compose 一看就知道：**这是这个屏幕现在的完整可渲染状态。**

这对于以后测试也极其舒服：给定某组源状态，只检查最终 `LedgerUiState` 是否正确。

---

#### 15. 但是不要把 ViewModel 变成“全宇宙状态垃圾桶”

这里必须立即画边界。我们这个案例把：

```kotlin
query
filter
```

放进 ViewModel，是有理由的：它们真正参与了**屏幕数据的业务派生**。例如：

```text
query
    ↓
决定当前显示哪些账单

filter
    ↓
决定当前显示哪些账单
```

所以它们已经超出了某个 `TextField` 或某个 Chip 单纯的视觉细节。但下面这些东西通常没有必要塞进去：

```text
某个 TextField 是否 Focus
LazyColumn 当前像素滚动位置
按钮是否正在被按压
Ripple 状态
某个动画当前执行到第几帧
```

这些往往属于 UI element state，应该尽量留在真正消费它们的 UI 附近。Compose 官方的状态提升原则也不是“所有东西全部提升到 ViewModel”，而是把状态提升到**所有读写方的最低公共祖先**；当业务逻辑需要它时，这个 owner 才可能是 ViewModel。([Android Developers][7])

所以：**ViewModel 是 Screen State Holder，不是 UI 每一个细枝末节的垃圾箱。**

---

#### 16. `map()` 和 `combine()` 到这里终于可以准确区分

阶段五：

```kotlin
repository.observeTicks()
    .map { tick ->
        UiState(...)
    }
```

只有一个状态来源：

```text
Repository emission
        ↓
转换
        ↓
UiState
```

所以 `map()` 很自然。

阶段六：

```text
Repository
query
filter
```

三个来源都可能独立变化，而最终状态依赖三者，所以：

```kotlin
combine(...)
```

更自然。Kotlin 的 `combine` 使用每个 Flow 最新的值；相比之下，`zip` 更像“一条 A 配一条 B”的逐对组合，所以 `zip` 通常不是这种状态派生场景的选择。([Kotlin][2])

可以暂时记成：

```text
map
一个输入发生变化
→ 计算一个输出


combine
多个状态输入中的任意一个发生变化
→ 使用所有输入的最新值
→ 重新计算一个输出
```

这就够了。

---

#### 17. `combine` 的 transform 也应该尽量保持“纯”

这部分和阶段三 `update {}` 有一点相似，但**原因不同，不要混为一谈**。

`MutableStateFlow.update {}` 不应该放副作用，是因为 CAS 竞争下 lambda 可能 retry、执行多次。

而 `combine {}` 不应该随便放：

```kotlin
sendAnalytics()
database.insert(...)
showNotification()
```

主要原因是另一套：**每个 upstream 的变化都可能重新调用 transform。** 例如用户连续输入：

```text
咖
咖啡
```

transform 就可能执行两次。Repository 又更新：

```text
Data #2
```

transform 再执行。filter 变化：

```text
ALL → EXPENSE
```

又执行。所以 `combine` 最舒服的职责同样是：

```text
输入状态
↓
纯计算
↓
UiState
```

而不是：

```text
“每次重新计算 UiState 时顺便做一次不可逆业务动作”
```

这不是因为 CAS retry，而是因为**状态派生天然可以被重新求值很多次**。这个区分很重要。

---

#### 18. 这其实已经是 UDF 的核心轮廓了

虽然完整 UDF 要到 4.18 专门学，但现在已经第一次形成一个非常完整的闭环：

```text
                       ┌──────────── UI State ────────────┐
                       │                                  ↓
Repository → combine → StateFlow<LedgerUiState> → Compose Screen
                  ↑                                 │
                  │                                 │
             _query / _filter                      │
                  ↑                                 │
                  └──────── User Event ─────────────┘
```

用户输入：

```text
onQueryChange("咖啡")
```

不是 UI 自己修改过滤后的列表，而是：

```text
UI event
↓
ViewModel 修改 source state
↓
combine 重新推导
↓
新的 UiState
↓
UI 根据新状态重新描述
```

这就是阶段一那句：

```text
State 向下
Event 向上
```

在真实 ViewModel 状态生产中的完整版。

#### 19. 如果想验证 Error，只需要改一个地方

为了不把异常处理抢进阶段六，我们的 Fake Repository 把 Error 当成正常状态发射。临时改成：

```kotlin
private val repository = FakeLedgerRepository(
    shouldFail = true
)
```

重新运行。页面首先仍然立即获得：

```text
LedgerUiState(
    content = Loading
)
```

之后 Repository 发：

```text
Error
```

`combine` 仍然同时拿着：

```text
Repository Error
+
当前 query
+
当前 filter
```

于是生成：

```kotlin
LedgerUiState(
    query = query,
    filter = filter,
    content = LedgerContent.Error(...)
)
```

因此即使内容区加载失败，搜索词与筛选条件仍然是屏幕状态的一部分，没有凭空丢掉。

这也体现了为什么我们没有简单粗暴地把整个 `LedgerUiState` 写成：

```text
Loading | Success | Error
```

因为 `query`、`filter` 和 Loading / Data / Error **并不是互斥关系；我们只把真正互斥的“内容状态”放进 sealed interface。**

#### 20. 到这里回头看：ViewModel 真正难的不是 `viewModelScope.launch`

你前面说 ViewModel 是靠近 UI 的整个架构里最重要的一块，这一阶段已经开始看到原因了。

真实 ViewModel 最有价值的部分往往不是：

```kotlin
class XxxViewModel : ViewModel()
```

也不是：

```kotlin
viewModelScope.launch
```

这几个固定 API。真正需要设计能力的是：

> **我的 screen state 到底由哪些真实状态源决定？谁是 source of truth？哪些只是 derived state？哪些状态应该合并？哪些应该保留在 UI？用户事件修改的是哪个 source？最终应该向 Screen 暴露什么样的不可变 `UiState`？**

API 往往只有：

```kotlin
MutableStateFlow
combine
map
stateIn
```

几样。难的是你如何把业务问题表达成这一条稳定的数据流。

这也是为什么 Android 官方把 UI layer 描述成一条把 application data 转成 UI 可以呈现的信息、再由 UI 渲染的 pipeline。([Android Developers][8])

---

#### 阶段六最终心智模型

这一阶段最值得留下的是下面这张图：

```text
               ┌──────── Source State ────────┐
               │                              │
Repository Flow│                              │
       │       │                              │
       ├───────┤                              │
       │       │                              ↓
_query StateFlow ───────→  combine  ───→ Flow<UiState>
       │                       ↑                   │
_filter StateFlow ─────────────┘                   │
                                                   ↓
                                                stateIn
                                                   │
                                                   ↓
                                        StateFlow<UiState>
                                                   │
                                        collectAsStateWithLifecycle
                                                   │
                                                   ↓
                                                Screen
                                                   │
                                                   │ User Event
                                                   ↓
                                          修改真正的 Source State
```

而一句话总结就是：

> **Screen `UiState` 应该尽可能成为“真实状态源经过业务规则计算后的当前屏幕快照”；当它依赖多个会独立变化的 Flow 时，可以用 `combine()` 持续使用每个来源的最新状态重新推导，再通过 `stateIn()` 把这条派生 Flow 转成 ViewModel 范围内稳定、共享、有当前值的 `StateFlow<UiState>`。** ([Android Developers][1])

#### 阶段六验收

这一阶段建议你一定实际跑三件事：加载完成以后输入搜索词；切换 `ALL / EXPENSE / INCOME`；保持某个 query/filter 等待 Repository 5 秒后的第二次数据更新。然后回答下面六个问题。

1. `_query`、`_filter` 和 `uiState` 中，哪些是真正的 source state，哪个是 derived state？为什么我们没有再创建一个 `_uiState` 手动维护？
2. `combine()` 第一次为什么必须等所有 upstream 至少提供过一个值？之后任意一个 upstream 变化时，它又使用什么值调用 transform？
3. 用户只修改 `_filter.value`，Repository 没有重新 emit，为什么最终账单列表仍然能够立即变化？
4. 为什么这里的 `combine(...)` 返回的仍然是 cold `Flow<LedgerUiState>`，而末尾还需要 `stateIn()`？
5. 为什么 `query` 在这个案例中适合进入 ViewModel，而 `TextField` 的 Focus、光标、动画状态通常不应该因此一起塞进 ViewModel？
6. 为什么 `combine {}` 里也不适合写数据库修改、埋点等副作用？这个原因和 `MutableStateFlow.update {}` 中不能随便写副作用的 **CAS/retry 原因有什么不同**？

如果这六个问题能结合你跑出来的日志回答清楚，那么阶段六真正学到的就不是一个新的 Flow API，而是开始掌握 **ViewModel 最核心的 Screen State Production 能力**。下一阶段我们会专门拿这些已经能工作的结构去制造错误，处理 `StateFlow` / ViewModel 最容易踩的边缘 Case：状态原地修改、重复状态、错误的协程位置、异常以及“什么东西根本不应该进入 ViewModel”。

### 阶段七：关键边缘 Case 与错误写法实验——“代码能跑”不等于状态模型正确

阶段六已经把一条相当完整的链路跑起来了：

```text
Repository Flow
    +
ViewModel Source State
    ↓
combine / map
    ↓
Flow<UiState>
    ↓
stateIn
    ↓
StateFlow<UiState>
    ↓
Compose
```

到了阶段七，我们不再继续增加新的主 API，而是专门**破坏这套结构**。这一阶段非常重要，因为真实项目里的 ViewModel Bug 很多并不是“不会写 `stateIn()`”，而是状态可变性、协程归属、异常、事件语义这些边缘地方写得似乎合理，运行几分钟也没问题，最后却出现“偶尔不刷新”“返回页面突然跳一下”“Loading 永远不结束”这种很恶心的 Bug。

这一阶段使用：

```text
Sec05E_ViewModelStateFlowPitfalls.kt
```

我们先用一个可运行实验解决最危险的一类问题：**StateFlow 外壳是响应式的，但你塞进去的对象内部却偷偷原地修改。**

#### 1. 实验 A：最阴险的 Bug——StateFlow 里面放了可变对象，然后原地修改

先写一个明显不推荐的状态：

```kotlin
private const val TAG05E = "Sec05E"

data class BadMutableListState(
    val items: MutableList<String> = mutableListOf()
)

data class GoodImmutableListState(
    val items: List<String> = emptyList()
)
```

然后写 ViewModel：

```kotlin
class PitfallViewModel : ViewModel() {

    private val _badListState =
        MutableStateFlow(BadMutableListState())

    val badListState =
        _badListState.asStateFlow()


    private val _goodListState =
        MutableStateFlow(GoodImmutableListState())

    val goodListState =
        _goodListState.asStateFlow()


    private val _unrelatedTick =
        MutableStateFlow(0)

    val unrelatedTick =
        _unrelatedTick.asStateFlow()


    fun addBadItem() {
        val state = _badListState.value

        state.items.add(
            "Bad Item ${state.items.size + 1}"
        )

        log(
            "$TAG05E BAD 内部已经修改：" +
                    "size=${state.items.size}"
        )

        // 即使这样重新赋回去也救不了。
        // 还是同一个对象，而且 equals 仍然相等。
        _badListState.value = state
    }


    fun addGoodItem() {
        _goodListState.update { oldState ->
            oldState.copy(
                items = oldState.items +
                        "Good Item ${oldState.items.size + 1}"
            )
        }

        log(
            "$TAG05E GOOD 更新：" +
                    "size=${_goodListState.value.items.size}"
        )
    }


    fun forceUnrelatedChange() {
        _unrelatedTick.update { it + 1 }

        log(
            "$TAG05E 制造无关状态变化：" +
                    "tick=${_unrelatedTick.value}"
        )
    }
}
```

Compose：

```kotlin

        viewModel.badListState.collectAsStateWithLifecycle()
```

#### 2. 先跑最反直觉的现象

进入以后你应该看到：

```text
错误 MutableList 数量：0
正确不可变 List 数量：0
无关状态：0
```

连续点击两次：

```text
错误：原地修改 MutableList
```

Logcat 很可能已经是：

```text
BAD 内部已经修改：size=1
BAD 内部已经修改：size=2
```

但是屏幕仍然：

```text
错误 MutableList 数量：0
```

这时候不要再点 Bad，改点：

```text
制造一次无关重组
```

然后非常有意思的现象可能出现：

```text
错误 MutableList 数量：2
```

它突然“补上来了”。

这就是一种非常危险的状态 Bug：**修改的时候 UI 不刷新，后来某个毫不相关的状态触发了一次重组，之前偷偷修改的数据突然出现在 UI 上。**

---

#### 3. 为什么会这样？这里需要把机制讲精确

问题出在：

```kotlin
val state = _badListState.value
state.items.add(...)
```

你没有产生一个新的屏幕状态，而是直接进入旧 State 对象内部，把它持有的 `MutableList` 改掉了。此时：

```text
StateFlow 当前持有的对象
        │
        └── items
              ↓
        同一个 MutableList
```

你只是把那个 List 的内部内容从：

```text
[]
```

变成：

```text
[Bad Item 1]
```

StateFlow 并不知道“这个对象里面的一块内存被你偷偷改过”。随后你又：

```kotlin
_badListState.value = state
```

但 `state` 本身就是原来那个对象。`StateFlow` 的新旧值发射判断基于 `Any.equals()`；相等的新值会被 suppress，因此不会产生新的 StateFlow emission。([Kotlin][1])

也就是说：

```text
StateFlow 当前对象 A
        ↓
偷偷修改 A.items
        ↓
仍然把 A 赋回去
        ↓
old == new
        ↓
没有 emission
```

于是 `collectAsStateWithLifecycle()` 没收到新 StateFlow 值，Compose 那座桥也没有新的状态更新，自然没有因此安排重组。

但是注意：Compose 这一侧之前保存的也是**这个对象 A 的引用**。A 内部的 MutableList 已经真的被改了。所以后来 `unrelatedTick` 引起 Screen 再执行一次时，它重新求：

```kotlin
badState.items.size
```

突然发现：

```text
原来已经变成 2 了
```

于是 UI 一口气跳到 2。

这就是为什么**屏幕状态最好表现为不可变快照，而不是一个外表叫 State、内部却到处都是 MutableList / MutableMap 的可变对象图。**

#### 4. `MutableStateFlow` 线程安全，不等于你塞进去的对象线程安全

这个点对你尤其值得说清，因为你有 Java 并发基础。

Kotlin 官方保证的是 `StateFlow` / `MutableStateFlow` 自己的方法是 thread-safe。([Kotlin][1])

比如：

```kotlin
_state.value = newValue
_state.update { ... }
```

StateFlow 自己负责并发安全。但如果你塞进去：

```kotlin
MutableList
HashMap
某个自己写的可变对象
```

并不会神奇地获得 StateFlow 的线程安全保障。可以把它想成：

```text
MutableStateFlow
    └── 安全地管理“引用 / value”

value 里面的 MutableList
    └── 是另一回事
```

所以这种代码：

```kotlin
_state.update { state ->
    state.items.add("A")
    state
}
```

**同样是错误方向。**别因为用了 `update {}` 就觉得安全了。

你虽然通过 CAS/retry 安全地更新 StateFlow，但 lambda 里面仍然在修改旧对象本身，而且由于 `update` lambda 在竞争时可能重试，这种副作用式修改甚至会更加危险。正确的模式还是：

```kotlin
_state.update { oldState ->
    oldState.copy(
        items = oldState.items + newItem
    )
}
```

这里：

```text
旧 List
→ 不动

oldState
→ 不动

产生新 List
→ 产生新 State
→ 原子提交
```

这就是“不可变状态快照”真正的价值。

#### 5. 实验 B：为什么 ViewModel 不应该把 `MutableStateFlow` 直接暴露出去

我们前面一直写：

```kotlin
private val _uiState = MutableStateFlow(...)

val uiState = _uiState.asStateFlow()
```

阶段三已经解释过封装，这一阶段再从“真实 Bug”角度看一次。下面这种写法虽然能编译：

```kotlin
class BadViewModel : ViewModel() {

    val uiState = MutableStateFlow(MyUiState())
}
```

那么 UI 甚至可以：

```kotlin
viewModel.uiState.value = MyUiState(...)
```

于是状态关系会变成：

```text
ViewModel 可以修改
UI 也可以修改
别的对象也能修改
```

那你在排查：“为什么现在是 Loading？” 的时候，可能根本不知道是谁写进去的。

Android 的状态提升建议本身就是：**状态 owner 对外暴露不可变状态，并暴露 event 让外部请求修改。** ([Android Developers][2]) Kotlin 官方给 `StateFlow` 的标准示例也是 private `MutableStateFlow` + public read-only `StateFlow`。([Kotlin][1]) 所以：

```text
外部：
我要修改筛选条件
        ↓
onFilterChange(EXPENSE)

ViewModel：
收到 event
        ↓
决定修改哪个 source state
        ↓
重新生产 UiState
```

而不是：

```text
UI：
我自己进去把 StateFlow.value 改了
```

这不是“多写一个下划线比较规范”，而是在保护 **single writer / state ownership**。

#### 6. 实验 C：业务协程启动在 Composable，为什么经常是职责错误

下面这段代码本身完全合法：

```kotlin
@Composable
fun BadSaveScreen(
    repository: LedgerRepository
) {
    val scope = rememberCoroutineScope()

    Button(
        onClick = {
            scope.launch {
                repository.saveLedger()
            }
        }
    ) {
        Text("保存账单")
    }
}
```

问题并不是：`rememberCoroutineScope()` 不能启动协程。

当然能，而且你已经系统学过它。问题是这里做的是：

```text
保存账单
```

这是业务操作。它的生命周期和职责不应该由某一次 Composition 来决定。Android 官方的协程最佳实践也建议，让 ViewModel 创建处理业务操作的协程；这样工作可以跨配置变化继续，而且业务逻辑更容易测试。([Android Developers][3])

更自然的是：

```kotlin
@Composable
fun SaveScreen(
    onSave: () -> Unit
) {
    Button(
        onClick = onSave
    ) {
        Text("保存账单")
    }
}
```

Route：

```kotlin
SaveScreen(
    onSave = viewModel::saveLedger
)
```

ViewModel：

```kotlin
fun saveLedger() {
    viewModelScope.launch {
        repository.saveLedger()
    }
}
```

这里再次回到阶段二的根原则：**不是“Button 点击应该用哪个 Scope”，而是“这项工作属于谁”。**如果工作是：

```text
滚动列表
显示 Snackbar
控制动画
```

往往属于 UI。如果工作是：

```text
提交账单
刷新业务数据
修改数据库
执行登录
```

通常应该由 ViewModel 接收用户事件并协调业务层。Android 官方也区分了 UI behavior logic 与 business logic，并建议业务事件由 ViewModel 处理。([Android Developers][4])

#### 7. 异常是阶段六那套 `stateIn()` 管线里必须补上的一环

阶段六我们写：

```kotlin
repository.observeEntries()
    .combine(...)
    .stateIn(...)
```

但是如果 Repository 的 upstream **真的 throw exception**，而不是像教学 Fake Repository 那样：

```kotlin
emit(RepositoryEntriesState.Error(...))
```

会怎样？`StateFlow` 本身并不能表达“我失败了”或者“我关闭了”；Kotlin 官方明确规定，StateFlow 不能用 failure/completion signal 表示失败，需要你自己把这些结果**materialize 成状态数据**。([Kotlin][1])

而 `stateIn()` 的 upstream 如果抛出异常，sharing coroutine 会终止；如果希望自定义错误恢复，应当在 `stateIn()` **之前**使用 `catch` / `retry`。([Kotlin][5]) 所以这才是更真实的：

```kotlin
val uiState: StateFlow<LedgerUiState> =
    repository
        .observeEntries()
        .map<List<LedgerEntry>, LedgerUiState> { entries ->
            LedgerUiState(
                content = LedgerContent.Data(
                    entries = entries,
                    signedTotal = ...
                )
            )
        }
        .catch { cause ->
            if (cause is IOException) {
                emit(
                    LedgerUiState(
                        content = LedgerContent.Error(
                            message = "数据加载失败"
                        )
                    )
                )
            } else {
                throw cause
            }
        }
        .stateIn(
            scope = viewModelScope,
            started =
                SharingStarted.WhileSubscribed(5_000),
            initialValue = LedgerUiState()
        )
```

这里的运行模型是：

```text
Repository Flow
    ↓
Data
    ↓
Data
    ↓
throw IOException
    ↓
catch
    ↓
把“异常”翻译成
LedgerUiState(Error)
    ↓
stateIn 保存 Error 状态
    ↓
UI 渲染 Error
```

`catch` 捕获的是它上游的异常，而且可以 `emit()` 一个 fallback value；它不会把 cancellation 当普通失败吞掉。([Kotlin][6])

---

#### 8. 为什么我在 `catch` 中没有直接吞掉所有 `Throwable`

注意刚才故意写的是：

```kotlin
.catch { cause ->
    if (cause is IOException) {
        emit(...)
    } else {
        throw cause
    }
}
```

而不是：

```kotlin
.catch {
    emit(Error("失败"))
}
```

因为“数据库暂时打不开”“网络 IOException”属于你预期可能出现的业务失败，但：

```text
NullPointerException
IllegalStateException
某个你自己的逻辑 Bug
```

未必应该被偷偷伪装成一句：

```text
加载失败
```

Kotlin 官方 Flow 文档同样建议：对于预期的、可恢复异常进行处理；无法处理的异常重新抛出。([Kotlin][7])

否则有一天你写错：

```kotlin
something!!
```

程序本来应该通过 Crash / 日志迅速告诉你：这里有 Bug。结果你自己：

```text
catch Throwable
↓
显示“网络异常”
```

然后排查两天。这叫把 bug 吃掉了。

#### 9. 手写 `try/catch` 时还要特别警惕 `CancellationException`

假设不是 Flow pipeline，而是：

```kotlin
fun save() {
    viewModelScope.launch {
        try {
            repository.save()
        } catch (e: Throwable) {
            ...
        }
    }
}
```

这里的 `Throwable` 范围很大，协程取消本身使用的 `CancellationException` 也属于异常体系。Kotlin 协程的取消就是通过 `CancellationException` 协作完成的。([Kotlin][8]) 所以真实业务代码更推荐：

```kotlin
catch (e: IOException) {
    // 处理真正预期的 IO 失败
}
```

而不是习惯性：

```kotlin
catch (e: Throwable) {
    // 什么都吃掉
}
```

如果确实有理由 catch 很宽，就必须清楚 cancellation 的传播问题，而不是把 ViewModel clear 导致的正常协程取消误当成“保存失败”。这一点以后排查协程取消 Bug 非常重要。

#### 10. 一个常见误区：StateFlow 是状态，不应该机械地拿来模拟“每次发生一次的事件计数器”

阶段三已经证明：

```text
StateFlow
→ 当前状态
→ equality conflation
→ 慢 collector 可以跳过中间状态
```

所以这种设计很可疑：

```kotlin
private val _showToast = MutableStateFlow(Unit)
```

然后期待：

```text
emit Unit
emit Unit
emit Unit

UI 必须精确收到三次
```

StateFlow 的语义根本不是“一个都不能少的事件队列”。相等值会被 conflated，它保存的核心又是“最新状态”。([Kotlin][1])

不过这里有一个很重要的现代 Android 架构边界：**不要因此机械记成“瞬时 UI 事件就一律 SharedFlow / Channel”。**

Android 官方现在更倾向于问：这件事情是不是其实应该建模成 UI state？例如：

```kotlin
data class UiState(
    val userMessage: String? = null
)
```

ViewModel：

```text
业务失败
↓
userMessage = "保存失败"
```

UI 显示 Snackbar 以后再回调：

```text
userMessageShown()
↓
userMessage = null
```

这样即使配置变化，那个还没消费的用户消息仍然存在于状态中。Android 官方 UI Events 指南就是用这种方式建模 transient message，并明确强调 ViewModel 发起的 UI action 应尽量转化为 UI state update。([Android Developers][4])

`SharedFlow` / `Channel` 到阶段十我们再正式定位，现在这里只建立边界：

> **不要因为“我需要从 ViewModel 通知 UI 一下”就下意识创建 `MutableStateFlow<Unit>`。先判断它究竟是状态，还是具有严格交付语义的事件。**

#### 11. 重复状态不发射不是 Bug，真正的 Bug 经常是你的 State 建模不对

阶段三已经实验过：

```kotlin
_uiState.value = oldState.copy()
```

如果：

```text
oldState == newState
```

StateFlow 不重新通知 collector，这是设计行为，不是 bug。([Kotlin][1])

所以有时候开发中看到：“我明明 setValue 了，为什么 UI 没刷新？”

第一反应不要写什么：

```text
forceRefresh = Random.nextInt()
timestamp = System.nanoTime()
```

硬逼 StateFlow 变成“不相等”。

应该先问：**UI 真正的状态有没有变化？**

如果 UI 真正需要表达：

```text
第 2 次刷新
第 3 次刷新
```

那么“刷新次数 / 当前 refresh operation”可能本身就是状态的一部分。

如果你只是想：

```text
同一个 Toast 再弹一次
```

那它本来就未必应该被建模成普通 StateFlow current state。

**不要和 StateFlow 的 equality 机制打架，应该修正状态模型。**

#### 12. 最后再划一次 ViewModel 边界：什么东西根本不应该进去

阶段六你已经答得不错，所以这里只做最后一次强化。

Android 官方建议把状态提升到所有读写者的最低公共祖先，并保持状态靠近实际消费位置；业务逻辑需要参与时，ViewModel 可以作为 screen-level state holder。([Android Developers][2])

所以例如：

```text
当前账单数据
搜索 query
筛选 filter
提交状态
业务错误
```

通常非常适合 ViewModel，因为它们影响 screen state 或业务规则。而：

```text
按钮 ripple
动画播放进度
某个局部区域展开 / 收起
LazyListState
FocusRequester / 焦点状态
DrawerState
```

不要因为“ViewModel 很重要”就全部扔进去。很多 UI element state 就应该留在 Composition 或 plain UI state holder 中。官方也明确把 screen UI state 和 UI element state 分开讨论。([Android Developers][2])

可以先使用这个非常实用的判断问题：**如果明天这个页面从手机 Compose UI 换成平板双栏 UI，这个状态仍然是业务意义上必须存在的吗？** 如果答案明显是：“不是，它只是当前这个 UI 怎么画、怎么滚、怎么展开。” 那它往往不属于 ViewModel。

#### 阶段七最终排雷图

到了这里，你写 ViewModel 时可以进行一次快速检查：

```text
                 Screen ViewModel
                       │
       ┌───────────────┼────────────────┐
       │               │                │
       ↓               ↓                ↓
  Source State    Repository Flow    User Event
       │               │                │
       └───────────────┼────────────────┘
                       ↓
                  状态生产逻辑
                       ↓
                immutable UiState
                       ↓
               StateFlow<UiState>
                       ↓
                     UI
```

需要重点避免的是：

```text
❌ UiState 内部偷偷 MutableList 原地改
❌ 把 MutableStateFlow 直接暴露给 UI
❌ Composable 自己启动本属于业务层的协程
❌ upstream exception 没有转换成明确 UiState
❌ catch(Throwable) 把真正的程序 Bug / cancellation 全吞掉
❌ 把“严格发生几次的事件”硬塞进 StateFlow current-state 模型
❌ 所有 UI 零碎状态一股脑塞进 ViewModel
```

这里真正贯穿所有问题的其实只有一句：

> **ViewModel 的职责不是“存很多变量”，而是拥有明确的状态源和业务事件，把它们稳定地生产成不可变、可解释的 Screen UiState。**

#### 18. `addRecord()` 本身也有可以继续收紧的地方

现在校验错误是这样：

```kotlin

    _formState.update { ... }
}

if (amount invalid) {
    _formState.update { ... }
}
```

如果两个字段都错，就产生两次 StateFlow 更新。技术上完全没问题。

但你现在经过阶段三以后应该知道，可以先算出：

```text
nameError
amountError
```

然后一次：

```kotlin
_formState.update {
    it.copy(
        nameError = ...,
        amountError = ...
    )
}
```

这样一次就提交完整的新表单快照。这不是性能问题，而是：**一个业务动作最好尽量产生一个一致、完整的新 State。**阶段九如果改代码，这也是很合适的一刀。

### 阶段十：4.5 ViewModel 最终收尾——以后真正写项目时，到底该选什么

阶段九已经延期，因此这一阶段不再造新 Demo，也不再重复前面九个阶段。我们只做一件事：**把这一大课最终压缩成开发时可以直接拿来决策的模型。**

Android 当前仍把 `ViewModel` 定位为 **screen-level state holder / business logic holder**：它向 UI 暴露状态、处理来自 UI 的业务事件，但真正的数据获取通常继续委托给 Repository 等下层组件。([Android Developers][1])

---

#### 1. 以后看到一个状态，先不要问“用哪个 API”，先问“谁拥有它”

这是整节课最重要的最终原则。假设出现一个状态：

```text
当前筛选条件
当前账单列表
输入框焦点
保存账单是否成功
当前 Snackbar
LazyColumn 滚动位置
数据库中的账单
```

第一步永远不是：用 `MutableStateFlow` 还是 `mutableStateOf()`？而是：**谁是这个状态真正的 owner？**

如果它只是某个 Composable 的 UI element state，例如焦点、展开状态、局部动画状态，它通常留在 UI 附近。如果它参与屏幕业务逻辑、需要由多个 UI 部分共享，或者决定整个 screen state，那么 ViewModel 往往是合理 owner。Compose 官方仍然建议状态提升到所有读写者的最低公共祖先，只有业务逻辑需要参与时才自然提升到 ViewModel。([Android Developers][2])

所以不要形成：

```text
状态
↓
一律 ViewModel
```

而应该是：

```text
状态
↓
确定 owner
↓
再选择 State API
```

---

#### 2. ViewModel 自己拥有、自己修改的 Source State：`MutableStateFlow`

最典型：

```kotlin
private val _query = MutableStateFlow("")
private val _filter = MutableStateFlow(Filter.ALL)
```

如果新状态基于旧状态：

```kotlin
_state.update { old ->
    old.copy(count = old.count + 1)
}
```

这里记住阶段三那个真正重要的机制：`update {}` 是原子的 read-modify-write，并可能在竞争时重新计算 lambda，因此 lambda 应尽量是纯函数，不要把数据库写入、埋点之类副作用塞进去。

而公开边界通常保持：

```kotlin
private val _state = MutableStateFlow(...)
val state: StateFlow<State> = _state.asStateFlow()
```

也就是：

```text
ViewModel
拥有写权限

UI
只有读权限 + Event API
```

这正符合官方推荐的“owner 暴露 immutable state + events”的模型。([Android Developers][2])

---

#### 3. Repository 已经给你 `Flow`：优先考虑 `stateIn()`

例如：

```kotlin
repository.observeRecords()
    .map { records ->
        RecordUiState(...)
    }
    .stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5_000),
        initialValue = RecordUiState()
    )
```

这时不要机械再造：

```kotlin
private val _uiState = MutableStateFlow(...)

init {
    viewModelScope.launch {
        repository.observeRecords().collect {
            _uiState.value = ...
        }
    }
}
```

手写当然可以，但如果目的只是：

```text
cold Flow
→ 转换
→ ViewModel 中共享的当前状态
```

`stateIn()` 正是为它服务的。它会在传入的 `CoroutineScope` 中运行 sharing coroutine，把 cold Flow 转换成 hot `StateFlow`；`SharingStarted` 决定这个 sharing 工作什么时候启动、停止。([Kotlin][3])

你现在对这一行应该已经能真正读出来：

```kotlin
.stateIn(
    scope = viewModelScope,
    started = SharingStarted.WhileSubscribed(5_000),
    initialValue = UiState()
)
```

不是模板，而是：

```text
viewModelScope
→ 整条共享工作的生命周期上限

WhileSubscribed(5000)
→ subscriber 消失后，何时停止 upstream collection

initialValue
→ upstream 第一条数据到来前，StateFlow 当前值是什么
```

并且 `WhileSubscribed` 默认会保留 replay cache，因此 upstream 停止并不意味着 `StateFlow` 自己和最后的当前值消失；之后重新订阅时 upstream 可以重新启动。([Kotlin][4])

---

#### 4. 一个来源用 `map`，多个独立来源共同决定结果用 `combine`

这一点阶段六已经真正跑过。一个来源：

```text
Repository Records
        ↓
      map
        ↓
     UiState
```

多个来源：

```text
Repository
query
filter
   ↓
combine
   ↓
UiState
```

`combine()` 的关键语义不是“等三个 Flow 同时发送”，而是等每个 upstream 至少有过一个值以后，任意一个 upstream 再更新，就拿**所有 upstream 的最新值**重新执行 transform。([Android Developers][5])

所以真正需要设计的是：

```text
哪些是 Source State？
哪些只是 Derived State？
```

如果：

```text
UiState = f(records, query, filter)
```

那么尽量让它真的通过这三个 source 推导出来，而不是同时维护第四份 `_uiState`，然后靠程序员手工保证四份状态永远同步。

---

#### 5. `viewModelScope`：最终只记“任务归属”，不要记“耗时任务”

这一块我们前面来回讨论过，现在封口。

不要记成：耗时任务所以放 `viewModelScope`。正确问题是：**这项异步工作属于谁？**

保存账单：

```kotlin
fun saveRecord() {
    viewModelScope.launch {
        repository.save(...)
    }
}
```

这是 screen/business work，因此属于 ViewModel。Android 官方也建议 ViewModel 创建业务操作所需的协程，这能让工作不因为普通配置变化而随 UI Composition 消失。([Android Developers][6])

但：

```text
Snackbar
滚动列表
动画
焦点操作
```

这些通常属于 UI。反过来，如果某项工作要求：用户离开这个 Screen、甚至 App 进入后台以后也必须可靠完成。

那 `viewModelScope` 又可能太短。此时需要根据任务性质考虑 Repository/application scope 或 WorkManager 等，而不是强行把 ViewModel 当成后台任务中心。([Android Developers][6])

所以 Scope 的判断逻辑是：

```text
谁应该拥有这个任务？
↓
任务应该活多久？
↓
选择 CoroutineScope
```

而不是：

```text
耗时
↓
随便找个 Scope.launch
```

---

#### 6. Compose 收 ViewModel 状态：Android 页面默认想到 `collectAsStateWithLifecycle()`

标准入口：

```kotlin
val uiState by viewModel.uiState.collectAsStateWithLifecycle()
```

它完成：

```text
StateFlow / Flow
        ↓
Lifecycle-aware collection
        ↓
Compose State
        ↓
Recomposition
```

Android 官方当前仍推荐 Compose UI 使用 `collectAsStateWithLifecycle()` 进行 lifecycle-aware state collection。([Android Developers][7])

这里再次分清两个生命周期：

```text
viewModelScope
→ ViewModel 工作生命周期

collectAsStateWithLifecycle
→ UI collector 生命周期
```

UI 停止收集，不等于 ViewModel 自动停止；有没有进一步停止 upstream，要继续看 `stateIn` 的 `SharingStarted` 等上游策略。

---

#### 7. StateFlow 是 State，不是“消息管道”

这是以后特别容易写歪的地方。State 的核心问题是：**此刻是什么？**例如：

```text
当前列表
当前筛选条件
当前保存状态
当前错误状态
当前用户消息
```

Event 的核心问题则是：**发生了什么？**

Android 当前的 UI architecture 也明确区分 events 与 state：event 是 state production 的输入，而 state 是生产后的结果，并始终存在。([Android Developers][8])

所以不要看到：“我要通知 UI 一次。” 就条件反射：

```kotlin
MutableStateFlow<Unit>
```

StateFlow 有 equality conflation、最新状态语义，它不是严格事件队列。

另一方面，也不要反过来形成：

```text
一次性效果
→ 一律 SharedFlow
```

很多事情其实可以转化成 state。例如：

```kotlin
data class UiState(
    val userMessage: String? = null
)
```

UI 显示后通知 ViewModel 消费。

**到底用 State 还是 Event，是业务语义判断；SharedFlow / Channel 只是后面的工具选择。** Android 官方目前也强调 ViewModel 产生的 UI action 应尽量落实为 UI state update。([Android Developers][8])

阶段十不用继续展开 SharedFlow，我们到真正遇到场景再决定。

---

#### 8. ViewModel 解决不了进程死亡

这一点不能因为“旋转以后 ViewModel 没死”就忘掉。

ViewModel 能很好地跨 configuration change 保持，但不是磁盘持久化方案；进程真正被系统杀掉，原来的 ViewModel 和其中内存状态都会消失。([Android Developers][9])

因此以后判断：

```text
旋转屏幕需要保留
→ ViewModel 通常足够

进程死亡还需要恢复少量 screen state
→ SavedStateHandle / rememberSaveable 等

真正业务数据
→ Room / DataStore / 服务端等持久数据源
```

不要把：

```text
ViewModel
```

误理解成：

```text
“可靠数据保存区”
```

它只是一个有明确生命周期的 screen-level state holder。

---

#### 9. 最终标准结构：以后看到 ViewModel，大部分项目都可以先从这里思考

不是要求照抄，只是形成基准线：

```kotlin
class XxxViewModel(
    private val repository: XxxRepository
) : ViewModel() {

    private val _query = MutableStateFlow("")
    private val _filter = MutableStateFlow(Filter.ALL)

    val uiState: StateFlow<XxxUiState> =
        combine(
            repository.observeData(),
            _query,
            _filter
        ) { data, query, filter ->

            XxxUiState(
                ...
            )
        }
        .stateIn(
            scope = viewModelScope,
            started =
                SharingStarted.WhileSubscribed(5_000),
            initialValue =
                XxxUiState.Loading
        )

    fun onQueryChange(query: String) {
        _query.value = query
    }

    fun onSave() {
        viewModelScope.launch {
            repository.save(...)
        }
    }
}
```

UI：

```kotlin
@Composable
fun XxxRoute(
    viewModel: XxxViewModel = viewModel()
) {
    val uiState by
        viewModel.uiState.collectAsStateWithLifecycle()

    XxxScreen(
        uiState = uiState,
        onQueryChange = viewModel::onQueryChange,
        onSave = viewModel::onSave
    )
}
```

然后纯 Screen：

```kotlin
@Composable
fun XxxScreen(
    uiState: XxxUiState,
    onQueryChange: (String) -> Unit,
    onSave: () -> Unit
) {
    ...
}
```

这已经非常接近 Android 当前强调的 UDF：**state 向 UI 流动，event 向 state holder 流动，ViewModel 处理业务事件并生产新的 UI state。** ([Android Developers][10])

以后真正项目当然会比它复杂，但复杂是在这个骨架上增长，不应该一上来变成 Activity / Composable 到处直接碰 Repository。

#### 10. 最终选择边界

把整节 4.5 真正压缩以后，大概只需要记住这些判断：

| 场景                              | 首先考虑                            |
| ------------------------------- | ------------------------------- |
| ViewModel 自己拥有、会修改的状态           | `MutableStateFlow`              |
| 下层已经提供 `Flow`，ViewModel 要暴露当前状态 | `stateIn()`                     |
| 一个 Flow 转成 UiState              | `map()`                         |
| 多个独立状态源共同决定 UiState             | `combine()`                     |
| 基于旧 StateFlow 状态原子地产生新状态        | `update {}`                     |
| Compose Android 页面观察 StateFlow  | `collectAsStateWithLifecycle()` |
| Screen/business coroutine       | `viewModelScope`                |
| 纯 UI 瞬时工作                       | Compose/UI scope                |
| UI element state                | 优先留在 UI 附近                      |
| Screen/business state           | 考虑 ViewModel                    |
| 真正持久业务数据                        | Room/DataStore/服务器，而非 ViewModel |

这个表如果以后能自然使用，4.5 就已经达到实际开发要求了。

#### 阶段十最终验收

最后不再问 API 定义，给你六个真实场景。你下一条可以直接按 `1～6` 回答。

**1.** Room DAO 返回：

```kotlin
Flow<List<RecordEntity>>
```

Repository 已转换成：

```kotlin
Flow<List<Record>>
```

页面只是展示它。你在 ViewModel 里会优先选择手写 `_uiState + collect`，还是 `map + stateIn`？为什么？

**2.** 页面同时存在：

```text
Room Records Flow
搜索 query
当前月份 selectedMonth
```

三者共同决定最终页面。你会怎样组织 source state 和 derived `UiState`？

**3.** 用户点击“保存”，Repository 的 `suspend fun insert()` 大约需要 200ms。这个操作应该由 `rememberCoroutineScope` 还是 `viewModelScope` 启动？判断依据是什么？注意不要回答“因为耗时”。

**4.** 一个 Dialog 的展开状态只决定这个页面现在是不是显示弹窗，不参与业务。它应该默认放 ViewModel 还是 Compose？如果以后“是否显示这个 Dialog”本身变成业务流程的一部分，你的判断会不会变化？

**5.** `stateIn(WhileSubscribed(5_000))` 的 UI subscriber 消失超过 5 秒以后，分别回答三个东西是否仍然存在：

```text
ViewModel
StateFlow 和最后的 value
当前 upstream collection
```

然后 UI subscriber 回来以后又分别发生什么？

**6.** 最后一题也是最重要的一题。请你不用 API 名称，用自己的语言描述：

> **在现代 Compose App 中，一个 screen-level ViewModel 到底是干什么的？**
