### 阶段一：从当前工程出发——无参数 Route 到带参数 Route

这一阶段我们先不急着写 `Sec06A_TypeSafeRouteArguments.kt`。你现在其实已经把 Navigation 3 的“骨架”搭出来了，所以最合适的起点不是重新介绍 Navigation，而是直接拿你正在运行的 `MainActivity.kt`，看它**目前究竟能表达什么，以及到了 Calendar Note 为什么马上就不够用了**。

#### 1.1 先把你现在已经会的东西压缩成一张心智地图

你现在的 Navigation 3 核心代码大致是这条链：

```text
Route
  ↓
rememberNavBackStack(Route.Home)
  ↓
用户点击
  ↓
backStack.add(route)
  ↓
NavDisplay 观察 backStack
  ↓
entryProvider 根据 Route 找到对应页面
  ↓
显示 Composable
```

这不是我重新给你讲 Navigation 3，而是确认一下我们接下来建立新知识的位置。

你当前定义了：

```kotlin
@Serializable
sealed interface Route : NavKey
```

下面全部都是类似：

```kotlin
data object Home : Route
data object PracticeDemo : Route
data object TweenDemo : Route
```

然后首页的按钮最终做的事情就是：

```kotlin
backStack.add(route)
```

而 `NavDisplay` 中：

```kotlin
entry<Route.PracticeDemo> {
    ViewModelPitfallsRoute()
}
```

负责把这个 Key 解析成真正显示的 Composable。你当前工程确实就是这个结构。

Navigation 3 官方现在描述的核心模型也正是如此：**back stack 本身不保存页面内容，它保存的是用于标识内容的 key；`NavDisplay` 观察 back stack，再通过 entry provider 把 key 解析成 `NavEntry` / 页面内容。** 而且这个 back stack 是应用自己持有和修改的。([Android Developers][1])

这句话非常重要，因为 **4.6 整节课其实就是在这个模型上再走一步。**

---

#### 1.2 你现在的 Route 到底表达了什么？

比如：

```kotlin
Route.TweenDemo
```

它表达的是：“我要去 TweenDemo 页面。” `Route.PracticeDemo` 表达：“我要去 PracticeDemo 页面。” 它们都是 `data object`。为什么用 `object` 很自然？因为对于你这些动画练习来说，**仅仅知道目标页面是什么，就已经足够了。**进入 `TweenDemo`，不需要再问：哪一个 TweenDemo？进入 `SpringDemo`，也不需要问：SpringDemo 的第 37 号数据是什么？这个页面本身就是完整身份。所以你现在实际上已经实现了第一层类型安全：

```text
不是：
"practice"
"tween"
"spring"

而是：
Route.PracticeDemo
Route.TweenDemo
Route.SpringDemo
```

也就是说，Navigation 状态里已经不是随便写的字符串，而是真正的 Kotlin 类型。这一点我们不再展开，因为你已经实际用了很长一段时间。

---

#### 1.3 真正的问题出现在 Calendar Note

现在把场景换回你接下来准备正式开发的 Calendar Note。假设首页显示一个日历。你点：`2026 年 8 月 14 日` 要进入这一天的详情页。如果我们照搬你现在的写法，很容易定义：

```kotlin
data object DayDetail : Route
```

然后：

```text
Calendar
    ↓ 点击 8 月 14 日
DayDetail
```

问题马上来了。`DayDetail` 页面知道：“我是 DayDetail 页面。” 但是它完全不知道：**“我是哪个 DayDetail？”** 是：

```text
2026-08-14？
```

还是：

```text
2026-08-15？
```

还是：

```text
2027-01-01？
```

`data object DayDetail` 全世界只有这么一个值。于是开发者很容易开始想一些补丁：

```text
先把 clickedDate 写进某个全局状态
        ↓
再导航到 DayDetail
        ↓
DayDetail 自己去那个状态里拿日期
```

或者：

```text
先调用 ViewModel.setSelectedDate(...)
        ↓
再导航
```

甚至：

```text
Singleton.currentDate = ...
```

这些办法可能都能把 Demo 跑起来，但它们会让一个非常简单的问题变得模糊：**“我现在导航到的这个页面，到底是谁？”** 因为答案被拆成了两块：

```text
Route.DayDetail
+
某个藏在别处的 selectedDate
```

Navigation 状态本身已经不能完整描述当前导航位置了。这正是 4.6 要解决的核心问题。

---

#### 1.4 Route 不只是“页面名称”，它可以描述“一次具体导航”

我们现在把 Route 的认识升级一级。以前你的心智模型可以暂时认为：

```text
Route = 页面
```

从今天开始，更准确地说：

```text
Route / NavKey
=
能够标识某个导航内容的一份数据
```

官方文档甚至直接用了很适合我们这一课的示例：

```kotlin
data object ProductList
data class ProductDetail(val id: String)
```

也就是说：

```text
ProductList
```

只需要知道：我在商品列表。所以它可以是一个单例。而：

```text
ProductDetail(id = "A")
ProductDetail(id = "B")
```

虽然它们属于**同一种 Route 类型**，却代表两个不同的导航 Key。官方也明确说明，Navigation 3 的 back stack 保存的是这些 key，它们通常就是简单、可序列化的数据对象。([Android Developers][1]) 因此 Calendar Note 将来真正需要表达的是类似这种概念：

```text
DayDetail(2026-08-14)

而不是：

DayDetail
+
“日期请去别处找”
```

这就是所谓的**类型安全路由参数**最核心的一层含义。现在先不要关心具体字段写成什么，也不要关心怎么从 `entry` 里把它取出来。阶段二我们会真的写。这一阶段只先把模型立住。

---

#### 1.5 一个非常重要的变化：Back Stack 里面的东西也随之升级了

你以前看到：

```kotlin
backStack.add(Route.PracticeDemo)
```

脑子里可能比较自然地理解成：“让 Navigation 去 PracticeDemo。” 从 Navigation 3 的模型来说，更精确的理解应该是：**“向我的导航状态列表末尾增加一个 `Route.PracticeDemo` Key。”** 

官方明确把 Navigation 3 的 forward / back 模型描述成：向 back stack 的末尾增加 key，或者从末尾删除 key；`NavDisplay` 观察这个导航状态并反映到 UI。([Android Developers][1]) 到了带参数以后，这件事就非常有意思了。概念上以后可能出现：

```text
Back Stack

Home
DayDetail(A)
DayDetail(B)
DayDetail(C)
```

这里后三个不是：

```text
三个不同页面类型
```

而是：

```text
同一个 Route 类型
三个不同 Route 实例
三份不同导航状态
```

这件事是下一阶段实验 B 最终要验证的核心，但我现在先给你埋这个钩子。因为一旦这个模型建立起来，你后面就会发现 Navigation 3 的参数传递其实不像某些旧式导航框架那样：“导航的时候另外附带一包 arguments。” 而更接近：**“参数本身就是这个 Navigation Key 的组成部分。”** 这是 Navigation 3 非常值得吃透的地方。

#### 1.6 为什么这和你刚学完的 ViewModel 特别容易混淆？

因为我们上一节刚刚连续学了十个阶段的 ViewModel + StateFlow，你现在脑子里已经形成了一套非常强的：

```text
数据
↓
ViewModel
↓
StateFlow
↓
UI
```

模型。这很好，但也正因为如此，第一次做 Navigation 参数时特别容易产生一个冲动：“那日期也塞 ViewModel 不就完了吗？” 以后当然会有日期进入 ViewModel。但我们必须先分清两个问题。

```text
Navigation 回答：
“我要看谁？”

ViewModel 回答：
“这个对象对应的页面现在是什么业务状态？”
```

比如：

```text
NoteDetail(noteId = 123)
```

Navigation 首先告诉页面：我要打开 **123 号 Note**。然后 ViewModel 才可能根据 `123`：

```text
读取 Room
↓
加载 Note
↓
生成 UiState
↓
StateFlow
↓
Compose
```

所以 4.5 和 4.6 不是两套互相竞争的方案。它们以后会接成一条链。

```text
用户点击某条记录
        ↓
Navigation Key
“我要打开 noteId = 123”
        ↓
目标页面
        ↓
ViewModel
        ↓
Repository / Room
        ↓
UiState
        ↓
Compose
```

这正是阶段四 `Sec06C_RouteArgumentsWithViewModel.kt` 才会正式解决的问题。今天暂时不要往下面钻。

#### 1.8 今天这一阶段真正需要留下来的结论

这一阶段其实只需要把下面四句话真正吃进去：

1. **Navigation 3 的 back stack 保存的是 Key，不是 Composable 页面本身。** `NavDisplay` 再通过 `entryProvider` 把 Key 解析成要显示的内容。([Android Developers][1])
2. 你当前 `data object PracticeDemo` 这种 Route 只能表达“去哪个页面”，对于动画 Demo 已经足够。
3. 真实 App 中很多目的地还必须表达“这个页面对应的是谁”，例如某一天、某条 Note、某个账户。
4. 因此带参数 Route 最重要的心智模型不是“给页面额外传几个参数”，而是：**这些数据参与构成这个具体的 Navigation Key。**

下一阶段我们就不再空讲了。会正式建立：`Sec06A_TypeSafeRouteArguments.kt`

让你亲手点击多个条目，观察 UI 和 Logcat，然后第一次看到**同一种 Route 类型，不同参数实例，是怎样进入 Back Stack 并解析成目标页面的**。

[1]: https://developer.android.com/guide/navigation/navigation-3/basics?utm_source=chatgpt.com "Understand and implement the basics | App architecture"

另外先把你刚才的 Navigation 心智模型校正两个小地方。`back stack` 官方中文文档叫**“返回堆栈”**，我们日常直接叫“返回栈”就行；不是“幕后栈”，这里的 `back` 是“用户按返回时能够回到哪里”的意思。你的“后进先出”直觉在我们当前这种单窗格线性导航里完全够用，不过 Navigation 3 从 API 本质上把它建模成应用自己持有的一份可观察列表：前进就是往末尾加 Key，返回就是从末尾移除 Key。([Android Developers][1])

第二个小修正更重要：不要把“返回时 `NavDisplay` 自动把 Key 删除”作为最终心智模型。Navigation 3 的根原则是**应用拥有导航状态，`NavDisplay` 负责观察并呈现它**；官方基础示例明确把返回写成 `onBack = { backStack.removeLastOrNull() }`。你当前工程没有显式写 `onBack` 也能工作，是你当前使用的 API 组合提供了相应默认行为，但以后做正式架构时，我们还是要把“谁修改返回栈”这件事想成自己的导航状态逻辑，而不是 `NavDisplay` 神秘地管理了一个内部栈。([Android Developers][1]) 你现在的总体认识已经够进入阶段二了：`NavKey` 是内容标识，`backStack` 保存这些 Key，`entryProvider` 把 Key 解析成 `NavEntry`，`NavDisplay` 显示当前应该出现的内容。官方文档对这条数据流也是这样定义的。([Android Developers][2])

至于你说的 4.19，方向理解得差不多：那一节真正要处理的是**顶层导航结构**，例如 Bottom Navigation、可能的多返回栈，以及如何把这些东西和强类型 Route 组织成正式 App 导航框架；至于底部那根 Bar 长什么样，完全可以是 Material 组件，也完全可以以后自己画。**导航状态模型和导航条的视觉实现不是一回事。** 所以现在不碰它很合适。

### 阶段二：教学引入示例 A——第一次真正跑通类型安全参数导航

这一阶段我们要完成一件非常具体的事情：不再只是“知道 `data class` 可以当 Route”，而是亲手看到一个带参数的 `NavKey` **被创建 → 压入返回栈 → 被 `entryProvider` 按类型匹配 → 整个 Key 对象交给目标页面 → 参数真正显示在 UI 上**。

这次我会故意先不用 ViewModel、Room、Hilt，也不传什么复杂 Note 对象。我们选一个和 Calendar Note 高度相关、又不会引入其他知识的场景：**日历首页有三个日期，点某一天进入该日期详情页。**

最终你会亲眼看到类似：

```text
Calendar
↓ 点击 2026-08-14
DayDetail(year=2026, month=8, day=14)
```

这个例子对应我们大纲里的：`Sec06A_TypeSafeRouteArguments.kt`

#### 2.1 先确定这次实验到底验证什么

我们定义两种 Key。第一个是日历首页，它没有任何身份参数，因此依然适合 `data object`；第二个是某一天的详情，它必须回答“哪一天”，所以用 `data class`：

```kotlin
@Serializable
private sealed interface Sec06ARoute : NavKey {

    @Serializable
    data object Calendar : Sec06ARoute

    @Serializable
    data class DayDetail(
        val year: Int,
        val month: Int,
        val day: Int,
    ) : Sec06ARoute
}
```

先盯着这一小段，不要急着往下看。这里最重要的变化根本不是“`object` 换成了 `data class`”，而是以前只有一个可能的值：

```kotlin
Sec06ARoute.Calendar
```

现在同一个 `DayDetail` 类型可以创建很多不同的 Key：

```kotlin
Sec06ARoute.DayDetail(2026, 8, 14)
Sec06ARoute.DayDetail(2026, 8, 15)
Sec06ARoute.DayDetail(2026, 9, 1)
```

这三个对象的 Kotlin 类型全部都是 `Sec06ARoute.DayDetail`，但对象里的数据不同，所以它们代表三份不同的导航身份。Navigation 3 官方自己的基础示例也是同一个模型：无参数内容使用 `data object ProductList`，需要标识具体商品的内容使用 `data class ProductDetail(val id: String)`。([Android Developers][2])

这里你刚才说的那句话就真正落到代码上了：**从语法上看，它确实很像普通构造函数传参；从 Navigation 语义上看，我们不是在“调用 DayDetail 页面并给页面塞三个参数”，而是在构造一个完整的 Navigation Key。**

#### 2.2 完整教学示例：`Sec06A_TypeSafeRouteArguments.kt`

这次文件我给你写成可以直接放进现在工程里的独立实验页。你现有 `MainActivity` 已经把 `Route.PracticeDemo` 当作当前练习入口，所以只需要把那里原来的 Composable 页面换成这个 `TypeSafeRouteArgumentsDemo()` 即可。你现在的入口确实正是这种结构。

```kotlin
package com.runningpig66.coursecompose.ch04_state.sec06

private const val TAG06A = "Sec06A"

@Serializable
private sealed interface Sec06ARoute : NavKey {

    @Serializable
    data object Calendar : Sec06ARoute

    @Serializable
    data class DayDetail(
        val year: Int,
        val month: Int,
        val day: Int,
    ) : Sec06ARoute
}

private data class DemoDay(
    val year: Int,
    val month: Int,
    val day: Int,
    val noteCount: Int,
)

private val demoDays = listOf(
    DemoDay(year = 2026, month = 8, day = 14, noteCount = 3),
    DemoDay(year = 2026, month = 8, day = 15, noteCount = 1),
    DemoDay(year = 2026, month = 9, day = 1, noteCount = 5),
)

@Composable
fun TypeSafeRouteArgumentsDemo() {
    val backStack = rememberNavBackStack(Sec06ARoute.Calendar)

    Scaffold { innerPadding ->
        NavDisplay(
            modifier = Modifier.padding(innerPadding),
            backStack = backStack,
            onBack = {
                val removedKey = backStack.removeLastOrNull()

                Log.d(
                    TAG06A,
                    "POP -> $removedKey | backStack = ${backStack.joinToString(" -> ")}"
                )
            },
            entryProvider = entryProvider {

                entry<Sec06ARoute.Calendar> {
                    CalendarScreen(
                        backStackText = backStack.joinToString(" -> "),
                        onDayClick = { day ->
                            val key = Sec06ARoute.DayDetail(
                                year = day.year,
                                month = day.month,
                                day = day.day,
                            )

                            backStack.add(key)

                            Log.d(
                                TAG06A,
                                "PUSH -> $key | backStack = ${backStack.joinToString(" -> ")}"
                            )
                        }
                    )
                }

                entry<Sec06ARoute.DayDetail> { key ->
                    DayDetailScreen(
                        key = key,
                        backStackText = backStack.joinToString(" -> "),
                        onBack = {
                            val removedKey = backStack.removeLastOrNull()

                            Log.d(
                                TAG06A,
                                "UI POP -> $removedKey | " +
                                        "backStack = ${backStack.joinToString(" -> ")}"
                            )
                        }
                    )
                }
            }
        )
    }
}

@Composable
private fun CalendarScreen(
    backStackText: String,
    onDayClick: (DemoDay) -> Unit,
) {
    Column(
        modifier = Modifier
            .fillMaxSize()
            .padding(24.dp),
        verticalArrangement = Arrangement.spacedBy(16.dp),
    ) {
        Text("Calendar")

        Text(
            text = "当前返回栈：\n$backStackText"
        )

        HorizontalDivider()

        demoDays.forEach { day ->
            Button(
                onClick = {
                    onDayClick(day)
                },
                modifier = Modifier.fillMaxWidth(),
            ) {
                Text(
                    text = "${day.year}-${day.month}-${day.day}  " +
                            "(${day.noteCount} 条记录)"
                )
            }
        }
    }
}

@Composable
private fun DayDetailScreen(
    key: Sec06ARoute.DayDetail,
    backStackText: String,
    onBack: () -> Unit,
) {
    Column(
        modifier = Modifier
            .fillMaxSize()
            .padding(24.dp),
        verticalArrangement = Arrangement.spacedBy(16.dp),
    ) {
        Text("Day Detail")

        Text(
            text = "收到的 NavKey：\n$key"
        )

        Text(
            text = "year = ${key.year}\n" +
                    "month = ${key.month}\n" +
                    "day = ${key.day}"
        )

        HorizontalDivider()

        Text(
            text = "当前返回栈：\n$backStackText"
        )

        Button(
            onClick = onBack,
        ) {
            Text("返回 Calendar")
        }
    }
}
```

然后你现在的 `MainActivity.kt` 只改当前实验入口：

```kotlin
entry<Route.PracticeDemo> {
    TypeSafeRouteArgumentsDemo()
}
```

注意，我们这里为了不破坏你整个课程工程，把 Sec06A 做成了一个**自包含的教学导航容器**，挂在现有 `PracticeDemo` 里面。正式 Calendar Note 不会套两层这种课程实验结构；到最后实战阶段，我们会把真正的 Route 放到 App 级导航框架里。这一点现在知道即可，不展开。

#### 2.4 现在开始拆最关键的一行：`backStack.add(key)`

点击日期时，我们先做了普通 Kotlin 对象创建：

```kotlin
val key = Sec06ARoute.DayDetail(
    year = day.year,
    month = day.month,
    day = day.day,
)
```

到这里为止 Navigation 3 **什么都没发生**。我们只是创建出了一个普通 Kotlin 对象，例如：

```text
DayDetail(year=2026, month=8, day=14)
```

真正发生导航的是：

```kotlin
backStack.add(key)
```

这句话不是：“NavController，请导航到某个 destination，并顺便携带 arguments。” 而是非常字面意义的：“我的导航状态现在多了一个 Key。” 于是返回栈从：

```text
Calendar
```

变成：

```text
Calendar → DayDetail(year=2026, month=8, day=14)
```

官方文档明确强调 Navigation 3 的一个核心设计就是 **you own the back stack**；所谓 push / pop，本质就是对列表末尾添加或移除元素。([Android Developers][2]) 这也是为什么你昨天学完 `StateFlow` 再来看 Nav3，其实会觉得它非常 Compose：**导航首先是一份状态；UI 是这个状态的结果。**

---

#### 2.5 第二个关键点：`entry<DayDetail> { key -> }` 到底做了什么？

现在来看：

```kotlin
entry<Sec06ARoute.DayDetail> { key ->
    DayDetailScreen(
        key = key,
        ...
    )
}
```

这里是今天整节课最值得你亲手点进 IDE 看类型推导的地方。`entry<Sec06ARoute.DayDetail>` 的泛型已经告诉 Entry Provider：“如果你需要解析的 Key 是 `Sec06ARoute.DayDetail` 类型，这一项负责它。” 因此 lambda 里的：

```kotlin
key
```

就不是一个 `String`，不是一个 `Bundle`，不是一个 `Map<String, Any>`，也不是你再根据 `"year"` 这种名称去手动取参数。它本身就是：

```kotlin
Sec06ARoute.DayDetail
```

所以直接：

```kotlin
key.year
key.month
key.day
```

即可。官方 `entryProvider` DSL 的参数化示例也是：

```kotlin
entry<ProductDetail> { key ->
    Text("Product ${key.id}")
}
```

也就是说，**Key 的类型匹配和 Key 内部参数的访问是一条完整的 Kotlin 类型链。** ([Android Developers][2]) 这才是“类型安全路由参数”在代码层面最直观的价值。以前如果你是这种思想：

```text
route = "day_detail/2026/8/14"
```

你脑子里还要额外维护：

```text
第一个位置是 year
第二个位置是 month
第三个位置是 day
```

而现在：

```kotlin
Sec06ARoute.DayDetail(
    year = 2026,
    month = 8,
    day = 14,
)
```

编译器已经知道三者分别是什么。今天先不要把这扩展成 Navigation 2 对比，我们只是借这个反例理解为什么现在这套代码舒服。

---

#### 2.6 为什么 `DayDetailScreen()` 仍然只是普通 Composable？

这里还有一个架构细节我希望你从一开始就养成正确习惯。我们没有写：

```kotlin
@Composable
fun DayDetailScreen(
    backStack: NavBackStack<...>
)
```

而是写：

```kotlin
@Composable
private fun DayDetailScreen(
    key: Sec06ARoute.DayDetail,
    backStackText: String,
    onBack: () -> Unit,
)
```

也就是说，真正知道 Navigation 3 存在的是外面的：

```kotlin
TypeSafeRouteArgumentsDemo()
```

而 `DayDetailScreen()` 自己只知道：“有人给了我一个 DayDetail 数据，以及一个返回事件。” 这和你上一节刚刚建立起来的 UDF / ViewModel 边界其实是一致的：**尽量不要让纯 UI 页面到处直接操作导航基础设施。**

今天我们暂时把整个 `key` 传进去，是为了让你清清楚楚观察 NavKey；到了正式 App，我们还会继续讨论到底应该让 Screen 收整个 Route，还是只拿它真正需要的数据。这个问题先留到后面的架构阶段。

---

#### 2.7 `@Serializable` 这次先认识用途，但不下钻

你会发现：

```kotlin
@Serializable
data class DayDetail(...)
```

这里不只是因为“这是个 data class，所以顺手序列化一下”。你现在使用的是：

```kotlin
rememberNavBackStack(...)
```

Navigation 3 要让这份返回栈能够跨配置变化，乃至保存恢复导航状态，就必须能够保存里面的 Key。官方明确要求 `rememberNavBackStack()` 使用的导航 Key 可序列化；Navigation 3 当前的标准 `NavBackStack` 也是围绕 `NavKey` 构建的。([Android Developers][3]) 不过**今天不讲它怎么序列化，也不做进程死亡实验**。那是阶段三。你现在只需要建立：

```text
NavKey 是导航身份
+
NavKey 需要能够被保存
+
所以我们定义成 @Serializable
```

这就够了。

#### 2.8 今天最容易产生的一个误解

你刚才说：“这里传的参数仅仅是为了最终组成 NavKey 的一个整体。” 这句话我给你判 **基本正确，但“仅仅”两个字以后要小心。**比如：

```kotlin
DayDetail(
    year = 2026,
    month = 8,
    day = 14,
)
```

这三个值首先确实共同构成这个具体 Navigation Key 的身份；但因为 Entry Provider 拿到的是**整个 Key 对象**，这些字段同时也是目标 destination 可以消费的数据。所以不要形成两个极端：

```text
错误理解 A：
参数只是普通函数参数，
NavKey 身份不重要。

错误理解 B：
参数只负责唯一标识，
页面本身不能使用这些数据。
```

更准确的是：**Route 的字段首先描述“这一次导航到底指向什么内容”，而这个完整 Key 在解析 destination 时也会作为类型安全的数据提供给目标内容。**官方文档甚至直接把 Navigation 3 的 Key 定义成“对内容的引用”，通常就是简单、可序列化的数据类。([Android Developers][2])

#### 2.9 阶段二跑完后，你应该形成的完整模型

到这里，我们终于可以把第一阶段那个朦胧模型升级成真正能写代码的模型：

```text
用户点击 2026-08-14
        ↓
构造普通 Kotlin 对象
DayDetail(2026, 8, 14)
        ↓
backStack.add(key)
        ↓
返回栈状态发生变化
        ↓
NavDisplay 观察到顶部 Key 改变
        ↓
entryProvider 按 Key 的类型匹配
entry<DayDetail>
        ↓
lambda 收到完整 DayDetail 对象
        ↓
key.year / key.month / key.day
        ↓
DayDetailScreen 显示对应日期
```

这里面**没有“参数包”这个额外概念**。你的参数就在 `NavKey` 里面，你压栈的就是这个完整对象，Entry Provider 最后拿到的也是这个完整对象。这就是阶段二真正要建立的第一手直觉。([Android Developers][1])

### 阶段三：示例 B——参数 Route 的运行模型、返回栈与状态恢复

这一阶段我们不再学习新的导航语法，重点是把阶段二已经跑通的那条链真正吃透：**同一种 Route 类型为什么可以在返回栈里出现很多次、参数究竟怎样参与 Key 的身份、返回栈保存的究竟是什么、页面来源状态变化会不会反过来修改已经入栈的 Key，以及旋转屏幕以后为什么还能留在原来的详情页。**

这几个问题如果不搞清楚，类型安全 Route 很容易最后被理解成“比字符串导航方便一点的数据类”，那就太浅了。Navigation 3 真正重要的变化，是**导航历史本身就是由一串业务可解释的 Key 数据构成的状态**。官方当前文档也是这样定义的：返回栈本质上是 snapshot-state-backed 的列表，push / pop 就是向列表末尾增加或删除 Key；`NavDisplay` 观察这份列表并把它反映到 UI。([Android Developers][1])

这一阶段继续用独立文件：`Sec06B_RouteBackStackExperiment.kt`

#### 3.1 先把今天最重要的问题摆出来：同一个 `DayDetail` 到底有几个页面？

阶段二我们写过：

```kotlin
@Serializable
data class DayDetail(
    val year: Int,
    val month: Int,
    val day: Int,
) : Sec06ARoute
```

于是我们可以创建：

```kotlin
DayDetail(2026, 8, 14)
DayDetail(2026, 8, 15)
DayDetail(2026, 9, 1)
```

这三个对象的**类型完全一样**，都是 `DayDetail`。所以 `entryProvider` 根本不需要为三天注册三个 Entry：

```kotlin
entry<Sec06BRoute.DayDetail> { key ->
    ...
}
```

这一份规则就能处理所有 `DayDetail`。但与此同时，这三个对象又不是同一个 Key，因为 `data class` 的相等性由属性值参与决定：

```kotlin
DayDetail(2026, 8, 14) == DayDetail(2026, 8, 14) // true
DayDetail(2026, 8, 14) == DayDetail(2026, 8, 15) // false
```

所以这里要把两个概念彻底分开：**Route 的类型决定“由哪一类 Entry 负责解析我”；Route 实例中的数据决定“我这一份具体导航内容是谁”。**比如：

```text
DayDetail(2026, 8, 14)
DayDetail(2026, 8, 15)
```

它们会命中同一个：

```kotlin
entry<DayDetail>
```

却可以同时存在于返回栈中：

```text
[0] Calendar
[1] DayDetail(2026, 8, 14)
[2] DayDetail(2026, 8, 15)
```

默认单窗格 `NavDisplay` 只显示最顶部的 Entry，因此此时屏幕显示 8 月 15 日；Back 删除 `[2]` 后，8 月 14 日重新成为顶部，于是显示 8 月 14 日。官方基础文档明确说明，默认 `NavDisplay` 显示返回栈最顶部的 `NavEntry`。([Android Developers][1]) 这也是今天第一个实验要亲手验证的东西。

#### 3.2 完整示例 B


#### 3.3 第一组实验：同一种 Route 类型，可以形成完整的导航历史

先进入 `2026-08-14`，然后在详情页连续点两次“继续进入下一个 DayDetail”。你应该得到：

```text
[0] Calendar
[1] DayDetail(year=2026, month=8, day=14)
[2] DayDetail(year=2026, month=8, day=15)
[3] DayDetail(year=2026, month=9, day=1)
```

注意，这里三个 Detail 全部由这一条负责：

```kotlin
entry<Sec06BRoute.DayDetail> { key ->
    ...
}
```

`entryProvider` 并不是在注册：

```text
8 月 14 日页面
8 月 15 日页面
9 月 1 日页面
```

它注册的是：**凡是 `Sec06BRoute.DayDetail` 类型的 Key，都由这一套 Entry 内容负责。**真正决定当前 Detail 展示哪一天的是 lambda 收到的那个 `key` 实例。现在连续 Back 三次。返回栈应该严格按相反顺序变成：

```text
Calendar
→ 8/14
→ 8/15
→ 9/1

Back

Calendar
→ 8/14
→ 8/15

Back

Calendar
→ 8/14

Back

Calendar
```

所以这里“栈”的价值终于真正体现出来了。参数不是只在“进入详情页的那一瞬间”有用，它已经成为**导航历史的一部分**。官方对 Navigation 3 的定义非常直接：返回栈里保存的是 Key，而不是页面内容；push / pop 的底层模型就是对这份列表末尾做增加与删除。([Android Developers][1]) 这和这样一种模型完全不同：

```text
currentScreen = DayDetail
selectedDate = ...
```

后者只能告诉你“现在在哪”，但不能天然描述：

```text
我之前经过了 8/14
然后进入 8/15
然后进入 9/1
```

而返回栈天然保存的就是这段历史。

---

#### 3.4 一个特别重要的区分：Key 的“类型”与 Key 的“值”

假设当前返回栈是：

```text
DayDetail(2026, 8, 14)
DayDetail(2026, 8, 15)
```

两者满足：

```kotlin
first::class == second::class
```

但是：

```kotlin
first == second
```

是 `false`。这就是为什么我上一阶段说“参数参与构成 Key”非常重要。`DayDetail` 这个类只是导航内容的**类别**；`DayDetail(2026, 8, 14)` 才是一份具体导航 Key。可以把它类比成：

```kotlin
data class UserId(val value: Long)
```

`UserId` 是一种 ID 类型，而：

```text
UserId(100)
UserId(101)
```

才是两个具体身份。所以以后看到：

```kotlin
entry<NoteDetail> { key -> ... }
```

不要理解成：“系统注册了一个 NoteDetail 页面。” 更准确是：“我声明了所有 `NoteDetail` 类型 Key 应该怎样解析成内容。” 然后：

```kotlin
NoteDetail(noteId = 100)
NoteDetail(noteId = 101)
```

才是实际进入返回栈的导航状态。

#### 3.5 第二组实验：改变来源页面状态，已经入栈的 Key 会不会变化？

这就是为什么代码里故意加了：

```kotlin
var calendarRevision by remember {
    mutableIntStateOf(0)
}
```

这个变量不属于 Route。它只是我们 Navigation 容器附近的一份普通 Compose 状态。先进入：

```text
DayDetail(2026, 8, 14)
```

然后连续点几次：修改 Calendar 的普通状态 +1，比如变成：

```text
calendarRevision = 3
```

你会看到 Detail 页面上的 `Calendar revision` 立即变成 3，因为这个页面也读取了它。但返回栈仍然是：

```text
[0] Calendar
[1] DayDetail(year=2026, month=8, day=14)
```

`DayDetail` 完全没变。然后 Back 回 Calendar，你会看到：

```text
Calendar 普通状态 revision = 3
```

这说明两件事情。第一，下面那个 Calendar 并没有因为你导航到 Detail，就从逻辑世界中彻底消失；Navigation 返回以后重新显示它时，外层那份状态仍然可以继续喂给它。第二，更关键的是：**已经压入返回栈的 Route 是一份独立导航状态，并不会因为来源页面旁边的其他状态变化而自动“跟着更新”。**

当时执行：

```kotlin
val key = DayDetail(
    year = 2026,
    month = 8,
    day = 14,
)

backStack.add(key)
```

你压进去的是一个具体的数据对象。后面：

```kotlin
calendarRevision++
```

和这个对象没有任何关系。这也是为什么 Route 最适合设计成简单、不可变、可序列化的数据对象。官方当前文档同样建议 Key 通常使用简单、可序列化的数据类。([Android Developers][1])

以后如果你把某个巨大的、内部还会不断突变的业务对象整个塞进 Route，这种干净的边界马上就会被破坏。所以阶段五我们会专门讨论：

```text
NoteDetail(noteId = 123)
```

为什么通常优于：

```text
NoteDetail(note = 整个Room实体)
```

今天先不提前展开。

#### 3.6 第三组实验：完全相同的 Key 再压一次，会发生什么？

这个实验比看起来重要得多。进入：

```text
DayDetail(2026, 8, 14)
```

然后点：`实验：再次压入完全相同的 Key`，代码执行的是：

```kotlin
val duplicateKey = key.copy()
backStack.add(duplicateKey)
```

Logcat 会看到类似：

```text
old == new = true
old === new = false
```

这里正好复习 Kotlin 最基础但非常关键的两个概念。

```kotlin
key == duplicateKey
```

是结构相等。因为 `DayDetail` 是 `data class`，三个属性完全相同，所以结果为 `true`。而：

```kotlin
key === duplicateKey
```

是引用相同。`copy()` 创建了另一个对象，所以为 `false`。返回栈从纯粹的列表角度，可以出现：

```text
[0] Calendar
[1] DayDetail(2026, 8, 14)
[2] DayDetail(2026, 8, 14)
```

于是这里出现一个很漂亮的问题：两个 Kotlin 对象明明不是同一个引用，为什么 Navigation 层面却可能不应该把它们当成两个独立页面身份？

因为 Navigation 3 除了你看到的 `NavKey` 之外，`NavEntry` 自己还有一个用于 Entry 状态身份的 `contentKey`。你现在使用的 Navigation 3 `1.1.6` 刚刚在这一块改过实现：默认 `contentKey` 由 `key.toString()` 与 `key::class.toString()` 的组合构成。([Android Developers][2])

那么两个：

```kotlin
DayDetail(2026, 8, 14)
```

既有相同 class，又有相同 `toString()`，所以按照当前默认规则推导出来，**它们的默认 `contentKey` 也相同**。这是根据官方 1.1.6 默认规则可以直接得出的结论。([Android Developers][2])

所以这里必须形成一个重要的工程边界：**“列表允许我 add 两个相等的 Key”不等于“我就应该把两个完全相等的 Key 当成两个独立导航 Entry 来设计”。**

你运行这个按钮后，最值得观察的是返回栈长度确实增加了，但页面内容看起来完全一样；Back 一次以后，你甚至还是看到同样的 `DayDetail(8/14)`，因为下面那个也是同样的数据。从用户角度，这种导航历史通常就已经很可疑了。

正式 App 中，如果用户已经处在：

```text
NoteDetail(noteId = 123)
```

你通常不会毫无理由再 push：

```text
NoteDetail(noteId = 123)
```

形成两个完全等价页面。

如果业务真的存在“同一业务对象需要两个独立 Entry 实例”的特殊需求，那就必须认真考虑 Entry identity，而不是无脑重复 push 完全相同的 Key。Navigation 3 的发布历史也一直在修复与 `contentKey`、状态保存、key reuse 有关的边界问题；1.1.6 本身就修复了 rapid pop 时 key reuse 与 `SaveableStateHolder` 的冲突。([Android Developers][2])

这一块**知道边界即可，不继续钻 `contentKey` 源码**。你现在真实 Calendar Note 大概率根本不需要主动制造完全相同的 Entry。

#### 3.7 第四组实验：旋转屏幕——这才是 `rememberNavBackStack()` 与普通 `remember` 真正分家的地方

这一组是今天最重要的实验之一。先导航成：

```text
[0] Calendar
[1] DayDetail(2026, 8, 14)
[2] DayDetail(2026, 8, 15)
```

然后在 Detail 页面把：

```text
calendarRevision
```

点到比如 `5`。此时直接旋转屏幕。按照我们代码的设计，你应该重点观察两个结果：

```text
返回栈：
仍然停留在 DayDetail(2026, 8, 15)
并且之前的 Calendar、8/14 仍然存在。

calendarRevision：
重新变回 0。
```

如果你的实际运行正是这样，那么这个实验一次性验证了两个完全不同的保存机制。我们的普通状态用了：

```kotlin
remember {
    mutableIntStateOf(0)
}
```

Activity 因配置变更被重建以后，这个普通 `remember` 没有跨 Activity 保存能力，因此重新初始化成 0。这个你在以前课程里已经学过，我们不重新讲。但返回栈用的是：

```kotlin
rememberNavBackStack(
    Sec06BRoute.Calendar
)
```

它不是普通的 `remember`。官方当前 API 文档明确说明，`rememberNavBackStack()` 会自动让 `NavBackStack` 跨**配置变更和进程死亡**恢复；它底层使用 `NavBackStackSerializer`，并通过 `rememberSerializable` 保存与恢复整份 back stack。([Android Developers][3]) 因此旋转前：

```text
Calendar
DayDetail(8/14)
DayDetail(8/15)
```

并不是旋转以后重新“推导”出来的。而是：

```text
旧 Activity
    ↓
NavBackStack 被保存
    ↓
Activity 因旋转销毁
    ↓
新 Activity / 新 Composition
    ↓
rememberNavBackStack 恢复之前保存的数据
    ↓
NavDisplay 看见恢复后的顶部 Key
    ↓
仍显示 DayDetail(8/15)
```

官方的 Basic Saveable Recipe 也是专门用 `rememberNavBackStack()` 来让返回栈跨屏幕旋转保持，并要求 Route 可序列化。([Android Developers][4]) 这里一定不要形成一种错误印象：“旋转以后 Navigation 3 没有被销毁。” 不是。

Activity 还是可以正常销毁和重建，Compose 也重新建立；**被保存并恢复的是导航状态数据。**

这和你刚学完 ViewModel 时的实验非常值得对照。ViewModel 跨配置变更主要靠 `ViewModelStore` 的 retained 机制继续使用原来的 ViewModel 实例；而 `rememberNavBackStack()` 这里走的是**保存 / 序列化 / 恢复导航状态**这条路线。它们得到的表面效果都可能是“旋转以后还在”，但机制完全不是一回事。

#### 3.8 那为什么我们的 Route 必须 `@Serializable`？

现在终于不是机械背注解了。返回栈里面可能是：

```text
Calendar
DayDetail(2026, 8, 14)
DayDetail(2026, 8, 15)
```

如果新 Activity 甚至新进程要把这份导航历史重新构造出来，系统不可能靠 JVM 对象引用恢复，因为原对象可能早就没了。它必须能表达：

```text
这里原来是 Calendar
这里原来是 DayDetail
year = 2026
month = 8
day = 14
...
```

然后重新反序列化出新的 Key 对象。所以：

```kotlin
@Serializable
data class DayDetail(...)
```

的意义不是：“Navigation 参数需要转成字符串。” 也不是：“为了传参方便。” 

而是：**这份 Key 本身属于需要持久保存并重新构造的导航状态。**你当前 Android-only 使用的：

```kotlin
rememberNavBackStack(...)
```

简单重载会在 Android 上使用反射支持 NavKey 的多态序列化；官方 API 明确要求放入 back stack 的每一个元素都必须 `@Serializable`。([Android Developers][3]) 所以现在可以把：

```text
NavKey
@Serializable
rememberNavBackStack
```

这三个东西连成一条逻辑链了，而不是三个彼此独立的 API。

#### 3.9 配置变更之后，还是“原来的那个 Key 对象”吗？

这是一个很容易被忽略、但非常适合你现在深度的问题。假设旋转前 JVM 内存里有：

```kotlin
val key = DayDetail(2026, 8, 15)
```

如果真的经历保存 → Activity 销毁 → 恢复，那么我们关心的是它的**值能不能恢复**：

```text
year = 2026
month = 8
day = 15
```

而不是要求：

```kotlin
oldKey === restoredKey
```

必须成立。事实上从序列化恢复模型看，我们应该把它理解成：

```text
旧对象
    ↓ serialize
一份数据表示
    ↓ deserialize
新对象
```

因此 Navigation 身份依赖的是稳定、可恢复的数据语义，而不是某一个 JVM 引用的生命长度。`rememberNavBackStack` 的 API 文档明确说明恢复过程依赖 `NavBackStackSerializer` 和序列化。([Android Developers][3])

这也是为什么 `data class` 在这里如此自然。我们关心：

```kotlin
restoredKey == oldKey
```

在值语义上仍然表达同一个导航内容，而不是：

```kotlin
restoredKey === oldKey
```

仍然是同一个内存对象。所以我在 Demo 里专门把：

```kotlin
System.identityHashCode(...)
```

也打印出来了。你可以顺便观察，但**不要把 `identityHashCode` 的具体数值当 API 契约**；它只是教学探针，用来提醒我们“对象引用”和“导航值身份”不是同一件事。

#### 3.10 进程死亡需要掌握到什么程度？

这里不值得像 `rememberSaveable()` 那一课一样重新上一整节保存状态课，但必须知道边界。

官方现在对 `rememberNavBackStack()` 的 API 契约说得很明确：在 Android 上，它返回的 `NavBackStack` 可以跨配置变更与进程死亡恢复。([Android Developers][3]) 所以：

```text
Calendar
→ NoteDetail(123)
→ EditNote(123)
```

这样的导航结构，在正常系统状态保存条件成立时，可以恢复到原来的导航位置。但这不意味着：“Route 里面随便放什么业务数据都自动永久保存。” 保存的是**可序列化的 Navigation Key**。比如以后：

```kotlin
NoteDetail(noteId = 123)
```

恢复以后你重新得到的是：

```text
noteId = 123
```

然后 ViewModel / Repository 再拿这个 ID 去 Room 重新读取业务数据。这就是一个非常漂亮的职责组合：

```text
Navigation：
恢复“用户当时正在看 123 号 Note”

Room：
恢复“123 号 Note 的真正持久业务内容”

ViewModel：
重新建立这个页面当前需要的 UiState
```

而不是 Navigation 把整个数据库实体、列表、图片、网络结果全部塞进返回栈。阶段四我们把这三层正式接起来。

#### 3.11 我建议你按这个顺序实际跑一遍

这次实验比较多，但不用一次乱点。按下面顺序，你能很清楚地把每个现象对应到一个机制：

1. `Calendar → 8/14 → 8/15 → 9/1`，观察返回栈里三个同类型 `DayDetail` 同时存在，然后逐级 Back，验证参数已经成为导航历史的一部分。
2. 进入 `8/14` 后执行“重复压入完全相同 Key”，观察 `== true`、`=== false` 和返回栈里出现两个值相同的元素；再 Back 一次，观察页面视觉上仍然还是同一天，从而体会“列表元素增加”和“形成一个有意义的新页面身份”不是同一件事。
3. 进入某个 Detail，把 `calendarRevision` 改成 3，再 Back，确认 Calendar 能看到 3，同时 Detail 的 Route 参数没有被修改。
4. 再进入 `8/14 → 8/15`，把 `calendarRevision` 改成 5，然后旋转屏幕。重点确认：**返回栈仍在 8/15，而普通 `remember` 状态回到 0。**
5. 旋转后再连续 Back，确认恢复出来的历史仍然按照 `8/15 → 8/14 → Calendar` 正常出栈。

如果第 4 步在你现在这种“外层课程 Navigation + 内层 Sec06B Navigation”的嵌套实验架构里出现和预期不同的恢复结果，你直接把实际 UI 和日志发给我。我们会以真实运行结果分析，因为那里会涉及父 Entry 的 Saveable State 环境，不能强行套结论。

#### 3.12 阶段三最终要留下来的心智模型

到这里，我希望“带参数 Route”在你脑子里已经不再只是：

```text
data class 可以传参数
```

而是下面这一套完整模型：

```text
Route 类型
决定这一类 Key 由哪个 Entry 规则解析

Route 的字段值
参与描述一个具体导航内容

多个不同参数的同类型 Route
可以同时组成一段返回历史

backStack
保存的是这些 Key 的有序导航状态

NavDisplay
根据返回栈状态决定当前显示什么

rememberNavBackStack
负责让这份可序列化导航状态跨配置变更，
并支持进程死亡后的恢复

业务/UI 的其他状态
不会因为 Navigation 被保存就自动一起获得同样生命周期
```

最后再压缩成一句以后写正式 App 最有用的话：

> **Navigation 3 的 Route 参数不是“临时传给下一个 Composable 的 arguments”，而是可进入返回栈、参与导航身份、并能够随导航状态一起保存和恢复的数据。**

这就是阶段三真正应该掌握的深度。源码目前依然没有必要继续钻；官方 API 对 `NavBackStack`、`rememberNavBackStack()`、序列化和 `NavDisplay` 的契约已经足够解释我们这一阶段所有开发层行为。下一步阶段四，我们再把这套 Key 真正交给刚学完的 ViewModel，让 `noteId / date` 从 Navigation 进入业务数据链。

#### 补充：你对 `NavKey` 的重新理解，比我前面那个“唯一身份”说法更准确

官方自己的定义其实非常接近你刚才说的：**back stack 里并不存页面，而是存“对内容的引用（references to content），这些引用被称为 keys”**；它还明确说 back stack 是一个 List，所谓 push / pop，本质就是在列表尾部 add/remove。官方没有说“每个 Key 值必须全局唯一”。([Android Developers][1])

因此：

```kotlin
backStack.add(
    DayDetail(2026, 8, 14)
)

backStack.add(
    DayDetail(2026, 8, 14)
)
```

从**返回栈数据结构**的角度完全成立：

```text
[0] Calendar
[1] DayDetail(2026, 8, 14)
[2] DayDetail(2026, 8, 14)
```

`NavBackStack` 的 API 本身就是 `MutableList` 语义，并不会因为两个元素 `equals()` 相等就拒绝第二次 `add()`。AndroidX 的 API 定义也直接显示 `NavBackStack` 实现了 `KMutableList/List`。([Android源代码][2])

所以你拿旧时代 Activity 举例非常合适。可以把：

```text
MainActivity
→ DetailActivity(id=14)
→ DetailActivity(id=14)
→ DetailActivity(id=14)
```

类比成：

```text
Calendar
→ DayDetail(14)
→ DayDetail(14)
→ DayDetail(14)
```

虽然底层完全不是 Activity，但在“**同一种 destination 可以被重复 push 成多个返回历史位置**”这件事情上，直觉是一样的。Navigation 3 默认并没有替你实施 `singleTop` 或“相等 Route 自动去重”的业务政策。

甚至 `data object` 也一样。单纯从 List 角度：

```kotlin
backStack.add(Route.Settings)
backStack.add(Route.Settings)
backStack.add(Route.Settings)
```

同一个 singleton 引用完全可以在一个 List 里出现三次。每 Back 一次，就删掉列表末尾的一次 occurrence。**所以 `NavKey` 的 Key 绝对不能理解成数据库 Primary Key 那种“必须唯一”。**这点我前面的表述需要正式纠正。

##### 那 `data class DayDetail(...)` 到底是什么？你现在这套理解已经非常接近正确答案

我们现在可以把以前那句“不是为了传参数”也修正得更准确一点：**它当然是在传参数。只不过这些参数不是独立于 Route 的一次性 arguments，而是直接成为这个 Route/Key 对象的一部分，并随它一起进入返回栈。**官方例子就是：

```kotlin
data class ProductDetail(val id: String)
```

然后：

```kotlin
entry<ProductDetail> { key ->
    Text("Product ${key.id}")
}
```

所以从开发者的角度说：

```text
ProductDetail.id
就是类型安全的导航参数
```

一点毛病都没有。官方自己的代码也是拿 `key.id` 给目标内容使用。([Android Developers][1]) 你现在可以把 Navigation 3 分成几个非常干净的角色，但不用把它们想成“唯一 ID”：

```text
Route 类型
DayDetail
    ↓
决定这是哪一种 Destination
    ↓
entry<DayDetail> 负责创建这一类内容

Route 数据
year / month / day
    ↓
是这一次导航携带的类型安全参数
    ↓
目标内容可以直接读取

BackStack 中的位置
[1]、[2]、[3]
    ↓
代表发生了几次 push
    ↓
即使里面的 Key 值完全相等，也可以有多个位置
```

这个模型比我之前的：“Route 实例唯一标识一个页面” 准确得多。而且官方 `entryProvider` 的说明也正好支持你的理解：Entry Provider 接受一个 Key，并把它解析成 `NavEntry`；使用 DSL 时，`entry<ProductDetail>` 根据 Key 类型声明这一类内容，然后 lambda 收到具体 Key。([Android Developers][1])

你说：“密封子类型决定进入哪个 Entry；有参数就用 data class，没有参数可以用 data object。” **作为我们现在这一层应用开发心智模型，我赞成。**

只补充一点：`sealed interface` 是我们自己为了让 Route 集合封闭、类型安全而采用的设计，并不是 Navigation 3 强制要求必须 sealed。Navigation 3 真正要求的是 Key 能满足它的 back stack / serialization 契约。

##### 你日志里还有一个 Kotlin 小细节需要纠正

你说两个对象：“hashCode 不一样，所以对象不一样。” 其实你这份日志恰恰显示：

```text
old hashCode = 1947248
new hashCode = 1947248
```

**普通 `hashCode()` 是相同的。**因为它们是 `data class`：

```kotlin
old == new // true
```

按照 Kotlin/Java 的基本契约，相等对象必须拥有相同 `hashCode()`，所以这个结果完全正常。不同的是：

```text
identity=176477249
identity=9477060
```

这个来自：

```kotlin
System.identityHashCode()
```

以及最关键的：

```kotlin
old === new // false
```

真正能够确定“不是同一个引用”的是 `=== false`。`identityHashCode()` 适合拿来做实验辅助观察，但它也**不是一个绝对唯一 ID**，理论上不同对象仍可能碰撞，所以以后不要把它叫“唯一 hashCode”。

##### 还有最后一层，我们现在终于可以把“Key”和“Entry 身份”分开

你的实验实际上暴露出了 Navigation 3 一个比我们现在课程主题稍微底一层的概念：**back stack 中的 Key 值，和 NavEntry 自己用于保存 UI 状态等用途的 identity，不完全是同一件事。**

AndroidX 后来专门引入了 `NavEntry.contentKey`，官方 release notes 直接说 NavEntry 及其相关状态由 `contentKey` 进行标识；Navigation 3 的这些版本也持续修改过默认 `contentKey` 和相同 Key 重用时的状态处理。([Android Developers][3]) 所以：

```text
NavKey.equals()
```

绝对不能简单翻译成：

```text
“是不是同一个返回栈页面实例”
```

你刚才用实验已经证明这一点了。如果未来真的有一种业务：我就是要连续打开三个 `DayDetail(8/14)`，而且要求它们内部各自的 `rememberSaveable` / ViewModel 等 Entry 级状态完全独立，

那时候我们才需要认真设计**每次 Entry 的身份**，例如**额外的 instance ID 或定制 content key**。现在不用展开，这属于更深的 Navigation 3 Entry 状态管理，不是这一阶段的主线。

---

最后，你对于 `@Serializable` 的理解也基本到位。`rememberNavBackStack()` 保存的是导航 Key 列表，因此 Key 必须能被序列化；旋转或进程恢复之后，再根据恢复出来的 Key 重新解析对应内容。官方 Basic Saveable Recipe 明确就是 `RouteB(id)` → 序列化 back stack → 恢复后仍拿到这个 `id`。([Android Developers][4])

所以如果现在让我重新给阶段三定一句最准确的结论，我会改成：

> **`NavKey` 不是“每个页面实例唯一的 ID”。它是返回栈中用于描述“要解析成什么内容、并携带哪些导航参数”的值；每次 push 都是在返回栈中增加一次导航记录，即使两个 Key 的值完全相等也可以重复存在。`entryProvider` 再依据 Key 把这条记录解析成 `NavEntry`。**

而你说的“详情 Route 通常只携带一个稳定索引，例如 `noteId`，页面再拿它去 ViewModel / Repository / Room 查询真实数据”，就是我们正式 App 中非常典型的用法。参数不必永远只是 ID，也可以是一些小而稳定的导航输入，但**把它理解成‘类型安全、可恢复的导航参数’比我之前反复强调‘唯一页面身份’准确得多。**

### 阶段四：示例 C——Navigation 参数进入 ViewModel，建立真正的页面业务链

阶段三解决的是“返回栈到底保存什么”；阶段四开始进入真实 App 最常见的一条链：

```text
用户点击某条 Note
→ backStack.add(NoteDetail(noteId = 101))
→ entry<NoteDetail> 拿到 key
→ 用 noteId 创建当前 NavEntry 专属的 ViewModel
→ ViewModel 根据 noteId 请求 Repository
→ Repository 返回业务数据
→ ViewModel 暴露 StateFlow<UiState>
→ Compose 收集并显示
```

这一阶段有两个真正的新知识点。第一，**Route 参数进入 ViewModel 的职责边界**：Navigation 最好携带能够重新定位业务对象的小而稳定的数据，例如 `noteId`，真正的 Note 内容由 ViewModel 通过 Repository 获取。第二，**Navigation 3 中 ViewModel 应该如何作用域到某一个 `NavEntry`**。第二个问题尤其重要，因为如果只是把上一课学过的 `viewModel()` 原样塞进 `entry<NoteDetail>`，很容易把几个不同详情页错误地共享成同一个 ViewModel。官方 Navigation 3 专门提供了 `rememberViewModelStoreNavEntryDecorator()` 来解决这个问题：它为每一个 `NavEntry` 建立自己的 `ViewModelStore`，并在这个 Entry 被真正 pop 后清理对应 Store。([Android Developers][1])

本阶段使用：`Sec06C_RouteArgumentsWithViewModel.kt`

#### 4.1 为什么这一次只传 `noteId`，不把整个 Note 塞进 Route？

先定一个以后 Calendar Note 很可能真的会出现的 Route：

```kotlin
@Serializable
private sealed interface Sec06CRoute : NavKey {

    @Serializable
    data object NoteList : Sec06CRoute

    @Serializable
    data class NoteDetail(
        val noteId: Long,
    ) : Sec06CRoute
}
```

假设列表里有这样一个业务对象：

```kotlin
data class NoteRecord(
    val id: Long,
    val title: String,
    val content: String,
)
```

点击它时，我们不做：

```kotlin
NoteDetail(
    note = 整个 NoteRecord
)
```

而是：

```kotlin
NoteDetail(
    noteId = note.id
)
```

这不是因为 Navigation 3 技术上只能传基本类型；我们的 Route 本来就是可序列化对象，能表达比一个 `Long` 丰富得多的数据。这里真正考虑的是**数据所有权和恢复语义**：`noteId = 101` 表达“我要查看 101 号 Note”，而 101 号 Note 当前标题、正文、修改时间是什么，应当由真正的数据源决定。进程恢复以后 Navigation 只需要恢复“用户当时正在看 101”，ViewModel 再根据 `101` 从 Room/Repository 重建页面数据即可。Android 官方在 Saved State 指南里也把“详情对象的 ID”列为典型的可保存导航状态，而不是要求把完整业务数据复制进 saved state。([Android Developers][2])

于是职责会很干净：

```text
Navigation
保存：noteId = 101

ViewModel
知道：当前业务目标是 101

Repository / Room
负责：101 号 Note 现在真实的数据

UiState
负责：这一刻页面应该显示什么
```

这就是我们今天整个例子的架构主轴。

```kotlin
private class NoteDetailViewModel(

        loadNote()
    }

    fun reload() {
        if (_uiState.value.isLoading) return
        loadNote()
    }

    private fun loadNote() {
        viewModelScope.launch {
            val nextLoadCount = _uiState.value.loadCount + 1
            _uiState.update {
                it.copy(
                    isLoading = true,
                    errorMessage = null
                )
            }
            log(TAG06C, "LOAD START | noteId=$noteId | vm=$instanceId | count=$nextLoadCount")

            if (note != null) {
                _uiState.update {
                    it.copy(
                        isLoading = false,
                        note = note,
                        loadCount = nextLoadCount
                    )
                }
                log(TAG06C, "LOAD SUCCESS | noteId=$noteId | vm=$instanceId | count=$nextLoadCount")
            } else {
                _uiState.update {
                    it.copy(
                        isLoading = false,
                        loadCount = nextLoadCount,
                        errorMessage = "找不到 noteId=$noteId"
                    )
                }
            }
        }
    }

    override fun onCleared() {
        log(TAG06C, "ViewModel CLEARED | noteId=$noteId | vm=$instanceId")
    }

    class Factory(
        private val noteId: Long,
        private val repository: NoteRepository
    ) : ViewModelProvider.Factory {
        @Suppress("UNCHECKED_CAST")
        override fun <T : ViewModel> create(modelClass: Class<T>): T {
            return NoteDetailViewModel(
                noteId = noteId,
                repository = repository
            ) as T
        }
    }
}
```

#### 4.3 先看最关键的新代码：为什么突然多了两个 `entryDecorators`？

阶段二、三我们可以直接：

```kotlin
NavDisplay(
    backStack = backStack,
    entryProvider = ...
)
```

今天却加了：

```kotlin
entryDecorators = listOf(
    rememberSaveableStateHolderNavEntryDecorator(),
    rememberViewModelStoreNavEntryDecorator(),
)
```

这不是为了传 `noteId`。**参数传递本身在 `entry<NoteDetail> { key -> }` 时已经完成了。**它解决的是另外一个问题：`entry<NoteDetail>` 里面调用 `viewModel()` 时，这个 ViewModel 到底属于谁？你在 4.5 已经学过：

```kotlin
viewModel()
```

不会凭空制造某种“页面级生命周期”，它会寻找当前 Composition 中最近的 `ViewModelStoreOwner`，然后从那个 Owner 的 `ViewModelStore` 中获取或创建 ViewModel。如果 Navigation 3 不做额外处理，`entry<NoteDetail>` 里的 `viewModel()` 很可能继续找到外面的 Activity Owner。于是下面两次导航：

```text
NoteDetail(101)
NoteDetail(102)
```

虽然是两个返回栈 Entry，但两边都请求：

```text
NoteDetailViewModel
```

在同一个 Activity 的 `ViewModelStore` 里，默认 ViewModel key 又是同一个类型，那么第二个页面可能直接拿到第一个已经存在的 ViewModel。你明明进入 `noteId=102`，却继续得到持有 `noteId=101` 的 ViewModel。Navigation 3 官方给出的解决方式就是：

```kotlin
rememberViewModelStoreNavEntryDecorator()
```

它为每个 `NavEntry` 提供自己的 `ViewModelStoreOwner` / Store，从而让 `viewModel()` 自动作用域到**当前 Entry**；Entry 被 pop 后，对应 Store 会被清理。官方的 Navigation 3 “Passing Arguments to ViewModels” 示例也是完全相同的组合，并特别强调：如果希望每一个新的导航 Key/Entry 拥有自己的 ViewModel，就需要这个 decorator。([Android Developers][3])

前面的：

```kotlin
rememberSaveableStateHolderNavEntryDecorator()
```

则是 Navigation 3 默认的 saveable-state decorator。官方要求，当我们自己提供 decorator 列表时，通常应把它放在前面，让每个 Entry 内部的 `rememberSaveable` 等状态能够正确保存恢复。([Android Developers][1])

现在暂时不学怎么自己实现 `NavEntryDecorator`。应用开发层只需要理解：

```text
SaveableStateHolderNavEntryDecorator
→ 给每个 Entry 管 saveable Compose 状态

ViewModelStoreNavEntryDecorator
→ 给每个 Entry 管 ViewModelStore
```

后一个就是今天的核心。

#### 4.4 这次 `entry<NoteDetail>` 其实是一个非常重要的架构边界

重点看：

```kotlin
entry<Sec06CRoute.NoteDetail> { key ->

        noteId = key.noteId,
        repository = repository,
```

再进入：

```kotlin
@Composable

    noteId: Long,
    repository: NoteRepository,
    ...

        factory = NoteDetailViewModel.Factory(
            noteId = noteId,
            repository = repository,

    val uiState by viewModel.uiState.collectAsStateWithLifecycle()
```

这里我**故意没有**让 `NoteDetailViewModel` 构造函数接收：

```kotlin
Sec06CRoute.NoteDetail
```

而是只接收：

```kotlin
noteId: Long
```

原因不是 Navigation 3 不允许这么做。Google 官方 Nav3 示例事实上就直接把整个 `RouteB` Key 交给 ViewModel；自定义 Factory、Hilt assisted injection、Koin 三种官方方案都可以这么干。([Android Developers][3]) 我这里选择把：

```text
Navigation Key
        ↓
key.noteId
        ↓
ViewModel
```

转换发生在 `NoteDetailRoute()` 附近，是为了建立更清楚的职责边界：`Sec06CRoute.NoteDetail` 属于 UI/Navigation 层的导航模型，而 ViewModel 真正需要的业务输入只是“我要管理 101 号 Note”。这样以后就算你重构 Navigation Route 的组织方式，ViewModel 也不一定需要跟着知道 Navigation 3 的具体类型。所以这里可以把 `NoteDetailRoute()` 看成一层很薄的**胶水层 / Route 层**：

```text
Navigation 世界
key.noteId
      ↓
NoteDetailRoute
      ↓
ViewModel 世界
noteId
      ↓
Repository
```

而真正负责画页面的：

```kotlin
NoteDetailScreen(
    uiState = ...,
    onReload = ...,
    onBack = ...
)
```

完全不知道 `NavKey`、`NavDisplay`、ViewModel、Repository 的存在。这个结构以后做 Preview 也特别舒服。

#### 4.6 第二组实验：Back 后哪个 ViewModel 会死，哪个会回来？

在 Note 102 页面把“加载次数”也点到 2，然后 Back。返回栈：

```text
NoteList
NoteDetail(101)
NoteDetail(102)
```

变为：

```text
NoteList
NoteDetail(101)
```

这次应该重点找：

```text
ViewModel CLEARED | noteId=102 | vm=789012
```

因为 102 对应的 NavEntry 已经真正被 pop。然后 101 页面重新出现，你应该看到：

```text
noteId = 101
ViewModel = 123456
加载次数 = 3
```

而不是创建一个新的 101 ViewModel。这就是 `ViewModelStoreNavEntryDecorator` 真正有价值的运行模型：

```text
push 101
→ 创建 Store101
→ 创建 VM101

push 102
→ Store101 保留
→ 创建 Store102
→ 创建 VM102

pop 102
→ 清理 Store102
→ VM102.onCleared()

101 再次成为顶部
→ 继续使用 Store101
→ 继续使用原来的 VM101
```

所以从今天开始，“一个详情页面有一个 ViewModel”这句话还不够精确。更准确应该是：**一个返回栈 Entry 可以拥有自己作用域内的 ViewModel。**这意味着两个同类型页面：

```text
NoteDetail(101)
NoteDetail(102)
```

完全可以各自维护独立的业务状态。

#### 4.7 一个非常值得做的反例：暂时删除 ViewModel decorator

这个实验我强烈建议你做一次，因为只看正确代码，很难体会这行 API 为什么存在。暂时把：

```kotlin
entryDecorators = listOf(
    rememberSaveableStateHolderNavEntryDecorator(),
    rememberViewModelStoreNavEntryDecorator(),
)
```

改成：

```kotlin
entryDecorators = listOf(
    rememberSaveableStateHolderNavEntryDecorator(),
)
```

然后重新运行：

```text
NoteList
→ Note 101
→ 从 101 再打开 Note 102
```

观察第二个页面拿到的 ViewModel。按照 `viewModel()` 的 Owner 查找规则，如果没有 Navigation 3 给当前 Entry 提供独立 `ViewModelStoreOwner`，它会向外寻找最近的 Owner；在我们这个教学工程里很可能最终落到更外层 Owner，因此两个 `NoteDetailRoute()` 对同一个 ViewModel 类型的请求可能命中同一个 Store 中的同一个实例。Google 官方 Nav3 示例正是因此强调：需要给 `NavDisplay` 加 `rememberViewModelStoreNavEntryDecorator()`，才能让每个新导航 Entry 得到独立 ViewModel。([Android Developers][3]) 如果你实际跑出来：

```text
Note 101
vm=123456

进入 Note 102
仍然 vm=123456
甚至页面继续显示 101 的数据
```

那这不是 Factory 没执行对，而是 **Factory 根本没有机会再次创建 ViewModel**：`viewModel()` 先在当前 Owner 的 Store 中查到了已有实例，所以直接返回它。然后把 decorator 恢复。这个实验一旦跑过，以后你基本不可能忘：

```kotlin
rememberViewModelStoreNavEntryDecorator()
```

到底解决什么。如果你当前嵌套的课程 Navigation 环境导致实验结果和上述预期不同，把实际日志发我，我们按真实 Owner 链分析，不强行套理论。

#### 4.8 Factory 到底起什么作用？不要把两个机制混在一起

这里有两个很容易混淆的组件：

```kotlin
rememberViewModelStoreNavEntryDecorator()
```

和：

```kotlin
NoteDetailViewModel.Factory(
    noteId = noteId,
    repository = repository,
)
```

它们解决的问题完全不同。

Decorator 解决：**这个 ViewModel 存在哪里、属于哪个 NavEntry、什么时候清理。**

Factory 解决：**第一次确实需要创建这个 ViewModel 时，构造函数需要的 `noteId` 和 Repository 从哪里来。**

所以调用：

```kotlin
viewModel(
    factory = NoteDetailViewModel.Factory(
        noteId = 102,
        repository = repository,
    )
)
```

绝不是每次重组都会创建一个新 VM。`viewModel()` 仍然先去当前 `ViewModelStore` 查询；只有 Store 中不存在对应实例时，Factory 才参与创建。这正好连接你 4.5 已经掌握的模型，只是现在：

```text
ViewModelStoreOwner
```

从原来主要观察的 Activity，进一步细化到了 Navigation 3 的 `NavEntry`。

#### 4.9 为什么这里不用 `SavedStateHandle.toRoute()`？

这个地方我提前帮你挡一个很容易踩的坑。如果你网上搜索“Compose 类型安全 Navigation 参数进 ViewModel”，经常会看到：

```kotlin
class MyViewModel(
    savedStateHandle: SavedStateHandle
) : ViewModel() {
    val route = savedStateHandle.toRoute<MyRoute>()
}
```

这个写法是 **Navigation 2 / Navigation Compose 类型安全 Route** 的官方方案之一。Navigation 3 当前官方“Passing Arguments to ViewModels” Recipe 则采用另一条明确链路：`entry` 已经拿到 Navigation Key，然后通过自定义 `ViewModelProvider.Factory`、Hilt assisted injection 或 Koin 参数把 Key 传给 ViewModel。([Android Developers][3])

所以我们当前不要机械搬：

```text
Nav2 的 SavedStateHandle.toRoute()
```

到 Nav3。Navigation 3 的模型反而很直观：

```text
entry<NoteDetail> { key ->
    我现在手里已经有 key
}
```

接下来就是决定**怎样把这份创建参数交给 ViewModel**。

#### 4.10 旋转屏幕和进程死亡时，这条链会发生什么？

这个实验可以顺便做，但不需要重新上一遍 4.5。假设当前：

```text
NoteList
→ NoteDetail(101)
→ NoteDetail(102)
```

102 的 ViewModel 已经加载完成。**旋转屏幕时**，NavEntry 仍然存在，Navigation 3 的 ViewModel integration 会让 Entry 作用域的 ViewModelStore 跨配置变更保持，因此 ViewModel 本身应继续存活；这正是 `lifecycle-viewmodel-navigation3` 提供的 Entry-scoped ViewModel integration。([Android Developers][4]) 你可以观察 `vm` identity：正常情况下旋转前后应该仍然是同一个 102 ViewModel，也不会重新执行 `init`。

**真正的进程死亡则不同。** ViewModel 对象本身不会跨进程死亡继续活着。Navigation 的 back stack 可以通过可序列化的 `NoteDetail(noteId=102)` 恢复；然后新的 Entry 根据恢复出来的 `noteId=102` 再创建新的 ViewModel，这个 ViewModel 再从 Repository / Room 重建业务状态。Saved State 官方也明确区分了 ViewModel 跨配置变化的存活能力与 system-initiated process death 后的状态恢复。([Android Developers][2]) 所以最终形成：

```text
配置变更：
Route 保持
Entry 保持
ViewModel 保持
业务状态继续

进程死亡后恢复：
Route 被反序列化恢复
↓
noteId = 102 重新得到
↓
创建新的 ViewModel
↓
Repository / Room 重新取得真实业务数据
```

这也是为什么只在 Route 里保存 `noteId` 已经足够有价值。

#### 4.11 到正式 Calendar Note + Hilt 时怎么变？

我们这个教学 Demo 用 Factory 是为了不让 Hilt 抢走 Navigation 主线。你正式 Calendar Note 已经有 Hilt，那么未来基本结构不会变：

```text
entry<NoteDetail> 拿到 key
        ↓
noteId
        ↓
Hilt assisted injection
        ↓
NoteDetailViewModel
        ↓
Repository
        ↓
Room
```

Google 当前 Navigation 3 官方 Recipe 对 Hilt 的方案就是 `@HiltViewModel` + assisted injection：Navigation Key 是运行时导航参数，通过 `creationCallback` 交给 assisted factory；同时仍然需要 `rememberViewModelStoreNavEntryDecorator()` 保证 ViewModel 作用域属于对应 NavEntry。([Android Developers][3])

这一阶段不把 Hilt 完整代码再写一套，因为那会变成“同一件事换 DI 框架重写一次”。等最后 Calendar Note 实战，我们直接在那里用你真正的 Hilt 工程做一次。

#### 4.12 阶段四真正需要留下来的东西

这一阶段最重要的已经不是 `data class NoteDetail(val noteId: Long)` 了，而是三条边界。

第一条是导航与业务数据边界：

```text
Route：
“打开 noteId=101”

ViewModel + Repository：
“101 号 Note 当前是什么”
```

第二条是 `NavEntry` 与 ViewModel 生命周期边界：

```text
NoteDetail(101) Entry
→ VM101

NoteDetail(102) Entry
→ VM102

102 pop
→ VM102 onCleared

101 仍在 back stack
→ VM101 继续存在
```

第三条是两个 API 的职责不要混：

```text
rememberViewModelStoreNavEntryDecorator()
→ 决定 ViewModel 属于哪个 Entry

Factory / Hilt Assisted
→ 决定创建 ViewModel 时怎样得到 noteId、Repository 等构造参数
```

如果这三条通过实际实验验证清楚，那么 4.5 的 ViewModel / StateFlow 和 4.6 的 Navigation 3 就第一次真正接上了。**下一阶段才适合讨论“Route 到底该放哪些参数、哪些绝对不该放”，以及各种容易写出能运行但架构很差的 Navigation 参数设计。**

### 阶段五：参数设计的易错点与选择边界——Route 到底应该携带什么？

这一阶段不再新建 `Sec06D`。原大纲里的 `Sec06D_CalendarNoteNavigation.kt` 留给阶段六正式 Calendar Note 实战；今天主要解决设计判断，所以只用少量代码片段验证边界，不再生成一大份重复工程代码。以后需要完整案例时我也不再生成 import，把篇幅留给真正的逻辑。

经过前四个阶段，现在可以把我们之前争论过的那个问题定得更准确一些：**Route 参数当然就是导航参数。** `NoteDetail(noteId = 101)` 里的 `noteId` 会随着 Key 进入返回栈，并最终被目标内容读取。它和传统意义上“额外附加一包 arguments”的区别在于，Navigation 3 直接把这些参数建模进 Key 对象本身；官方对 Key 的定义就是 back stack 中“对内容的引用”，通常使用简单、可序列化的数据类。([Android Developers][1])

所以今天真正的问题不是“Route 能不能传数据”，而是：**能传很多东西，但真实项目中到底应该传什么？**

---

#### 5.1 第一原则：Route 应该描述“我要去哪里”，而不是复制“那个页面现在有什么”

还是拿 Note 举例。下面这种设计非常自然：

```kotlin
@Serializable
data class NoteDetail(
    val noteId: Long,
) : AppRoute
```

`NoteDetail(101)` 的语义非常稳定：打开 ID 为 101 的 Note。无论 101 的标题后来从“学习 Navigation”改成“学习 Navigation 3”，无论正文增加多少，无论数据库重新查询多少次，Route 的导航含义都没有变化。反过来，如果写成：

```kotlin
@Serializable
data class NoteDetail(
    val id: Long,
    val title: String,
    val content: String,
    val createdAt: Long,
    val updatedAt: Long,
) : AppRoute
```

代码当然可能跑得通，但问题已经出现了：**Route 里开始保存业务数据的一个副本。**假设列表页读取：

```text
id = 101
title = "Navigation"
```

然后进入详情页，用户把标题改成：

```text
"Navigation 3"
```

Room 里的真数据已经变了，可返回栈里的 Key 可能仍然保存：

```text
NoteDetail(
    id = 101,
    title = "Navigation"
)
```

于是你无缘无故制造了两个数据源：

```text
Room：Navigation 3
Route：Navigation
```

以后你开始纠结“应该相信谁”，架构就已经歪了。因此对于**数据库中本来就具有稳定身份的实体**，最典型的写法仍然是：

```kotlin
NoteDetail(noteId = 101)
AccountDetail(accountId = 8)
TransactionDetail(transactionId = 9527)
```

Route 保存定位信息，Repository 保存事实数据，ViewModel 根据定位信息构建当前业务状态。这也和 Android 官方关于状态恢复的建议一致：保存重新定位数据所需要的最小信息，再从数据层重新获取复杂业务数据，而不是把复杂 screen data 塞进 saved state。([Android Developers][2])

---

#### 5.2 但“Route 只能传 ID”也是错误规则

这里不要从一个极端走到另一个极端。比如你的 Calendar Note 中：

```kotlin
@Serializable
data class DayDetail(
    val year: Int,
    val month: Int,
    val day: Int,
) : AppRoute
```

完全合理。我们没有必要为了贯彻“只能传 ID”，先人工制造一个：

```text
dateId = 20260814
```

再去解析它。因为：

```text
2026 / 8 / 14
```

本身就是描述这次导航目标所需要的小型、稳定、可序列化值，而且它不会产生另一个复杂业务数据副本。类似地：

```kotlin
@Serializable
data class SearchResult(
    val query: String,
) : AppRoute
```

也可能合理。如果“搜索 Kotlin”本身就是这个 destination 的导航含义，那么 `query` 就是非常自然的 Route 参数。所以更准确的规则不是：Route 只能放数据库 ID。而是：**Route 应优先保存能够重新描述 / 定位目标内容的最小、稳定、可序列化输入。**官方 Navigation 3 也只是说 Key **通常**是简单、可序列化的数据类，并没有规定只能有一个 ID。([Android Developers][1])

---

#### 5.3 哪些东西基本不应该放进 Route？

这几个以后看到就应该立刻警觉：

```kotlin
data class BadRoute(
    val repository: NoteRepository,
    val viewModel: NoteViewModel,
    val uiState: StateFlow<NoteUiState>,
    val context: Context,
    val bitmap: Bitmap,
    val onClick: () -> Unit,
)
```

这里的问题不只是“序列化不了”。更根本的是这些东西根本不是导航状态。`Repository` 是依赖，应该由 DI 提供；`ViewModel` 是有生命周期的状态持有者；`StateFlow` 是运行中的状态流；`Context` 属于 Android 运行环境；lambda 是行为；Bitmap 这种大型运行时对象属于内容数据。把它们塞进 Route，相当于让“我要去哪个页面”承担对象图、生命周期、业务状态和 UI 行为，职责全部混在一起。

而且 `rememberNavBackStack()` 的保存恢复要求 Key 可序列化；官方明确把可序列化 Key 与配置变化、进程死亡后的 back stack 恢复联系在一起。([Android Developers][3]) 所以看到一个 Route 字段时，可以问一句很实用的问题：**如果 App 进程现在死掉，明天只恢复这个字段，它还有清晰的导航意义吗？**

`noteId = 101`：有。

`date = 2026-08-14`：有。

`searchQuery = "Compose"`：有。

`repository = XXXRepository@1234`：没有。

`viewModel = NoteViewModel@5678`：没有。

这个问题很好用。

---

#### 5.4 Route 参数和 `UiState` 最容易混在哪里？

阶段四我们有：

```kotlin
NoteDetail(noteId = 101)
```

进入 ViewModel 后得到：

```kotlin
NoteDetailUiState(
    noteId = 101,
    isLoading = false,
    note = ...,
    loadCount = 3,
    errorMessage = null,
)
```

你一眼就能看到，有些信息似乎重叠了，例如两边都有 `noteId`。但两者承担的职责不同。Route 中：

```text
noteId = 101
```

回答的是：用户导航到了谁？UiState 中：

```text
note
isLoading
errorMessage
loadCount
```

回答的是：这个页面现在呈现什么？因此：

```kotlin
NoteDetail(
    noteId = 101,
    isLoading = true,
    errorMessage = "网络失败",
)
```

就明显不对。`isLoading`、`errorMessage` 是页面运行过程中不断变化的状态，不应该为了 UI 更新不断修改返回栈里的 Route。正常流向应该是单向的：

```text
NoteDetail(noteId=101)
        ↓
ViewModel(101)
        ↓
Repository
        ↓
UiState
        ↓
Screen
```

而不是：

```text
UiState 变化
↓
不停重写 NoteDetail Route
```

Navigation 和页面业务状态是两条不同层级的状态系统。

---

#### 5.5 Route 参数和 Screen 普通参数也不是一回事

这也是阶段四那个 `NoteDetailRoute()` 非常值得保留的原因。可以这样写：

```kotlin
entry<AppRoute.NoteDetail> { key ->
    NoteDetailRoute(
        noteId = key.noteId,
        onBack = { backStack.removeLastOrNull() }
    )
}
```

然后：

```kotlin
@Composable
fun NoteDetailRoute(
    noteId: Long,
    onBack: () -> Unit,
) {
    // 创建 / 获取 ViewModel
    // 收集 UiState

    NoteDetailScreen(
        uiState = uiState,
        onReload = ...,
        onBack = onBack,
    )
}
```

这里存在三层完全不同的参数：

```text
Navigation Key
NoteDetail(noteId)
        ↓
Route Composable 参数
noteId / onBack
        ↓
Screen 参数
uiState / callbacks
```

`noteId` 起源于 Navigation，但 `onBack` 不是导航参数，它只是一个函数依赖；`uiState` 更不是导航参数，而是 Screen 的渲染输入。所以以后千万不要因为某个值最终进入了 Composable 参数列表，就统统称为“Navigation 参数”。

#### 5.6 一个真实项目里非常容易写歪的设计：`CreateOrEditNote(noteId: Long?)`

例如：

```kotlin
@Serializable
data class NoteEditor(
    val noteId: Long?,
) : AppRoute
```

约定：

```text
noteId == null
→ 新建

noteId != null
→ 编辑
```

这并不是错误代码。如果创建和编辑确实就是同一个业务流程、同一个 Screen、同一个 ViewModel 状态机，那么这种建模完全可以接受。但如果两者业务意义已经明显不同，我反而更倾向：

```kotlin
@Serializable
data object CreateNote : AppRoute

@Serializable
data class EditNote(
    val noteId: Long,
) : AppRoute
```

为什么？因为第二种设计让非法状态更难产生。看到：

```kotlin
EditNote(noteId = 101)
```

无需知道任何约定。而：

```kotlin
NoteEditor(noteId = null)
```

你必须额外记住：null 在这里不是“数据缺失”，而是“创建模式”。这不是 Navigation 3 特有问题，而是普通 Kotlin 数据建模问题：**能用类型表达业务区别时，通常比靠特殊值表达更清楚。**不过我不会给你定成教条。未来 Calendar Note 如果创建/编辑真的共享 95% 流程，`noteId: Long?` 也可能是非常务实的选择。要看真实业务。

#### 5.7 “列表页已经有完整 Note，为什么详情页还要重新从 Repository 查？不是浪费吗？”

这个问题实际开发一定会遇到。假设列表已经拿到了：

```kotlin
NoteRecord(
    id = 101,
    title = "...",
    content = "...",
)
```

于是你可能觉得：我都已经有完整对象了，为什么只传 101，然后详情页又查一次 Room？这里要区分**数据正确性设计**与**性能优化**。架构上以：

```kotlin
NoteDetail(noteId = 101)
```

作为 destination identity 很干净。但这不意味着详情页必须无条件执行一次昂贵的网络请求。Repository 完全可以有缓存，Room 查询本身也可能非常便宜，甚至详情 ViewModel 订阅：

```kotlin
observeNote(101)
```

获得持续更新的数据流。也就是说：

```text
Route 只传 ID
```

并不等价于：

```text
每次进入都必须重新下载所有东西
```

导航层解决“定位谁”，数据层负责决定“怎样最高效地拿到谁”。别为了避免一次数据库查询，就把整个业务对象永久塞进导航状态。优化应该发生在 Repository / cache / database 这一层。

---

#### 5.8 返回结果，不要硬塞成“反向导航参数”

假设我们现在是：

```text
NoteDetail(101)
→ EditNote(101)
```

Edit 页面保存成功以后，NoteDetail 要显示新标题。最自然的情况根本不需要：

```text
EditNote
Back(
    result = 更新后的完整 Note
)
```

如果两个页面都依赖同一个 Repository / Room，那么 Edit 更新数据库后，Detail 的 ViewModel 订阅数据源，自然得到新数据。这是业务事实发生了变化，应当由数据层传播。但还有另一类真正的“返回结果”，比如：

```text
选择颜色
→ 返回用户刚选的 color
```

或者：

```text
联系人选择器
→ 返回选中的 contactId
```

这种结果并不是“下一个 destination 的身份参数”，而是**子页面完成后返回给调用者的结果**。Navigation 3 当前官方也单独提供 state-based returning result 的 Recipe，说明“向前传导航参数”和“向前一个页面返回结果”本来就是两个问题。([Android Developers][4]) 所以不要设计成某种奇怪的：

```kotlin
PreviousScreen(
    returnedColor = ...
)
```

然后为了返回结果把旧 Key pop 掉、重建一个新 Key。那是在拿 Route 当 UiState 用。这一块今天知道边界即可，不展开 Result API。

---

#### 5.9 Deep Link 也进一步说明了为什么 Route 应该“轻”

以后外部链接可能打开：

```text
myapp://note/101
```

外部 URL 很容易转成：

```kotlin
NoteDetail(noteId = 101)
```

这非常自然。Navigation 3 官方 Deep Link Recipe 也是先解析外部 `Intent` / URL，再把它转换成 Navigation Key，随后按普通导航状态处理。([Android Developers][5]) 这其实是检验 Route 设计质量的另一个好办法：如果这个 destination 有一天要被 Deep Link 直接打开，我现在的 Key 能不能从一个简单外部请求重新构造？

`NoteDetail(101)` 很容易。“必须先从某个列表页拿到完整的 `NoteRecord` 对象才能进入详情页”就很脆弱。这不代表所有页面必须支持 Deep Link，而是这种思考方式可以帮助我们判断导航目标是否真正自洽。

---

#### 5.10 最容易产生误解的“Key”再收一次尾

经过阶段三的实验，现在绝不能再说：`NoteDetail(101)` 是返回栈中唯一的页面 ID。因为：

```kotlin
backStack.add(NoteDetail(101))
backStack.add(NoteDetail(101))
backStack.add(NoteDetail(101))
```

完全可以产生三个返回栈位置。所以今天讲“稳定导航身份”时，准确含义是：**Key 的数据描述这个 destination 指向什么内容，而不是保证返回栈里只能存在一份这个值。**`NoteDetail(101)` 三次都描述“101 号 Note”，但它们可以是三次导航记录。至于业务层要不要防止：

```text
101 → 101 → 101
```

那属于导航政策，例如防重复点击、single-top 类行为、手动检查栈顶等。**不要把这种业务政策误以为 `data class.equals()` 会自动替你完成。**你自己的阶段三实验已经证明这一点了。

还不写正式代码，只判断参数。Calendar 首页很可能没有必要携带参数：

```kotlin

```




```text

RecordRepository
Flow<List<Record>>
是否正在加载
错误提示
当前列表滚动位置
Composable lambda
```

注意我这里用了“原则上”。例如非常小的不可变展示参数，有时业务上确实适合直接跟随 Route；架构不是看到两个字段就判刑。真正判断标准仍然是：**它是不是描述这次导航所需要的稳定输入？还是目标页面运行以后产生的业务/UI 状态？**只要把这句话守住，大多数 Navigation 参数设计都不会离谱。

#### 5.12 阶段五验收：以后看到一个 Route 字段，依次问四个问题

这四问我建议你以后真正在项目里拿来用，而不是背某个“只能传 ID”的规则。

1. **这个值是在描述“我要打开谁 / 什么内容”，还是页面运行后的状态？** 后者通常不进 Route。
2. **它是不是已有业务数据的一份巨大副本？** 如果有稳定 ID 能重新找到事实数据，优先传 ID。
3. **进程死亡以后只恢复这个值，它是否仍然有意义？** 如果没有，它很可能不是导航状态。
4. **目标页面能不能只凭这个 Key 加上自己的 ViewModel / Repository 独立重建？** 如果必须依赖上一个页面偷偷塞过来的运行时对象，Route 设计通常还不够自洽。

这四问比“Route 必须只能放基本类型”“只能放 ID”“所有参数越少越好”这些死规则实用得多。

```text
Calendar
→ DayDetail(2026-08-14)
→ EditRecord(recordId = 101)
```

这里真正新增的知识只有一个：**“向前导航的参数”与“子页面返回的结果”是两套不同的数据通道。**

#### 6.1 先建立 Result API 的整体位置

Navigation 3 1.2 现在官方提供的是 `ResultEventBus`。`rememberResultEventBusNavEntryDecorator()` 把 Result 能力接入 `NavEntry`，并通过 `LocalResultEventBus` 提供给 Entry 内容；产生结果的页面调用 `sendResult()`，接收页面则有两种主要方式：用 `ResultEffect<T>` 把结果当作一次性事件处理，或者用 `conflateAsState<T>()` 把“最新结果”当作 Compose `State` 观察。官方分别提供了 Event-Based 和 State-Based 两份 recipe。([Android Developers][2])

因此可以先形成这个模型：

```text
向前：

EditRecord
    ↓ backStack.add(...)
ColorPicker(initialColor = BLUE)


向后：

ColorPicker
    ↓ resultBus.sendResult(RED)
ResultEventBus
    ↓
EditRecord 的 ResultEffect<...>
    ↓
ViewModel.onColorSelected(RED)

同时：
ColorPicker 被 pop
```

注意 Result **不是 Back Stack 里的一个新 Key，也不是去修改旧的 `EditRecord` Key**。它是独立的 Entry 间通信机制。

---

#### 6.2 为什么这个场景选择 `ResultEffect`，而不是 `conflateAsState`

颜色选择器返回 RED 后，我们真正想做的是：“收到一次 RED → 通知 EditRecordViewModel → ViewModel 把自己的 UiState 更新成 RED。” 这是非常标准的**一次性结果事件**。官方也明确把 `ResultEffect` 定位为接收某种结果类型的一次性事件方式；State-Based Recipe 则适合“我只关心最新一次 Result，并希望直接把它当 State 观察”的场景。([Android Developers][2]) 因此今天主案例采用：

```kotlin
ResultEffect<ColorPickerResult> { result ->
    viewModel.onColorSelected(result.color)
}
```

而不是：

```kotlin
val resultState = LocalResultEventBus.current
        .conflateAsState<ColorPickerResult?>(null)
```

后面我会专门把这两个 API 的边界讲清楚。

---

#### 6.3 Route 和 Result 是两种不同的数据类型

先定义导航 Key：

```kotlin
private const val TAG06D = "Sec06D"

@Serializable
private sealed interface Sec06DRoute : NavKey {

    @Serializable
    data object Calendar : Sec06DRoute

    @Serializable
    data class DayDetail(
        val year: Int,
        val month: Int,
        val day: Int,
    ) : Sec06DRoute

    @Serializable
    data class EditRecord(
        val recordId: Long,
    ) : Sec06DRoute

    @Serializable
    data class ColorPicker(
        val recordId: Long,
        val initialColor: RecordColor,
    ) : Sec06DRoute
}

@Serializable
private enum class RecordColor {
    RED,
    GREEN,
    BLUE,
    YELLOW,
}
```

然后单独定义 ColorPicker 的返回结果：

```kotlin
private data class ColorPickerResult(
    val color: RecordColor,
)
```

这里有一个非常重要的设计细节。`ColorPicker(initialColor = BLUE)` 里的 BLUE 是**进入目标页面之前就已经存在的导航输入**：颜色选择器打开时应该默认选中什么，所以它属于 Route。用户进入页面之后点击 RED，RED 是**运行以后产生的结果**，所以它属于 `ColorPickerResult`。两者看起来都是 `RecordColor`，但职责完全不同：

```text
initialColor = BLUE
→ 向前传
→ “ColorPicker 启动时需要知道什么？”

ColorPickerResult(RED)
→ 向后返回
→ “ColorPicker 执行完以后产生了什么？”
```

这就是阶段五“不要把 Route 当 UiState”在真实代码里的落地。

#### 6.5 先把“向前”和“向后”两条数据链彻底分开

从 EditRecord 打开 ColorPicker 时：

```kotlin
val pickerKey =
    Sec06DRoute.ColorPicker(
        recordId = key.recordId,
        initialColor = currentColor,
    )

backStack.add(pickerKey)
```

这是标准前向 Navigation。假设编辑页当前状态：

```text
EditRecordUiState(
    recordId = 101,
    color = BLUE
)
```

那么 Back Stack 从：

```text
Calendar
→ DayDetail(2026,8,14)
→ EditRecord(101)
```

变成：

```text
Calendar
→ DayDetail(2026,8,14)
→ EditRecord(101)
→ ColorPicker(101, BLUE)
```

BLUE 被放进 Route，是因为目标 ColorPicker **启动时就需要它**。用户进入 ColorPicker 后选择 RED，发生的却不是：

```kotlin
EditRecord(
    recordId = 101,
    color = RED
)
```

更不是找到 Back Stack 里的旧 `EditRecord(101)` 去修改它。我们创建的是另外一种对象：

```kotlin
ColorPickerResult(
    color = RED
)
```

然后：

```kotlin
resultBus.sendResult<ColorPickerResult>(
    result = result
)
```

官方 Event-Based Recipe 就是这个模式：子 Entry 从 `LocalResultEventBus.current` 得到 EventBus，调用 `sendResult()`，然后把自己从 back stack 移除；父 Entry 使用 `ResultEffect<T>` 接收。([Android Developers][2]) 于是：

```text
Route：
ColorPicker(recordId=101, initialColor=BLUE)

Result：
ColorPickerResult(color=RED)
```

不是两个不同写法表达同一个东西，而是两个方向完全不同的数据。

#### 6.6 `ResultEventBus` 到底替我们做了什么？

如果没有这个 API，我们之前想象的办法可能是把：

```text
selectedColor
```

提升到 Navigation 容器上层，然后 ColorPicker 写进去，EditRecord 再观察；或者自己造一个 Map / SharedFlow / EventBus。现在 Navigation 3 正式提供了一块专门用于 **NavEntry → NavEntry Result 通信**的基础设施。`ResultEventBusNavEntryDecorator` 把 EventBus 提供到 Entry 的 Composition 中，因此发送页面可以通过 `LocalResultEventBus.current` 获取它，而接收页面通过 `ResultEffect` 或 `conflateAsState()` 消费结果。([Android Developers][2])

所以你会发现我们根本没有：

```kotlin
var returnedColor by remember { ... }
```

也没有：

```kotlin
MutableSharedFlow<Color>()
```

更没有：

```kotlin
EditRecord(
    recordId = 101,
    returnedColor = RED
)
```

Result 基础设施已经独立出来了。

---

#### 6.7 `sendResult()` 为什么紧接着 `pop`？

代码：

```kotlin
resultBus.sendResult<ColorPickerResult>(
    result = result
)

backStack.removeLastOrNull()
```

我们严格按照官方 Recipe 的写法：**先发送 Result，再 pop 当前页面。** 官方 Event-Based 与 State-Based 示例都是这个顺序。([Android Developers][2]) 概念上也很好理解。选择 RED 是 ColorPicker 完成业务动作，产生结果；pop 是 ColorPicker 完成以后离开导航历史。于是一个按钮点击里发生两件不同的事情：

```text
业务通信：
sendResult(RED)

导航：
pop ColorPicker
```

如果用户只是点击“取消”，代码则只有：

```kotlin
backStack.removeLastOrNull()
```

没有 `sendResult()`。因此：

```text
取消
= 只返回

选择 RED
= 产生 Result + 返回
```

这两个动作一定要在脑子里分开。

---

#### 6.8 最关键的新 API：`ResultEffect<T>`

父页面：

```kotlin
ResultEffect<ColorPickerResult> { result ->
    viewModel.onColorSelected(
        color = result.color
    )
}
```

`ResultEffect<ColorPickerResult>` 表示：当前这个 NavEntry 对 `ColorPickerResult` 类型的一次性 Result 感兴趣。ColorPicker 发出：

```kotlin
ColorPickerResult(
    color = RED
)
```

ResultEffect 收到以后调用：

```kotlin
viewModel.onColorSelected(RED)
```

然后真正稳定存在于 Edit 页面里的数据变成：

```kotlin
EditRecordUiState(
    recordId = 101,
    color = RED,
)
```

这里的职责非常漂亮：

```text
ResultEventBus
只负责“送到”

ResultEffect
负责“收到时执行什么”

ViewModel
负责“收到后业务状态怎样变化”

StateFlow
负责“新业务状态送给 UI”

Screen
负责“显示 RED”
```

所以 Result 本身不是 UiState。它只是把 RED 从子页面运回父页面的一次运输。官方明确把 `ResultEffect` 定义为处理 transient / one-time result 的方式。([Android Developers][2])

---

#### 6.9 为什么我专门定义 `ColorPickerResult`，不直接发送 `RecordColor`

技术上我们完全可以：

```kotlin
resultBus.sendResult<RecordColor>(
    result = RecordColor.RED
)
```

接收：

```kotlin
ResultEffect<RecordColor> { color ->
    ...
}
```

但我这里故意多包了一层：

```kotlin
data class ColorPickerResult(
    val color: RecordColor
)
```

因为 Result 的**类型本身也是通信协议的一部分**。以后你的 Edit 页面可能同时打开：

```text
ColorPicker
AccountPicker
CategoryPicker
DatePicker
```

如果所有地方都随手返回 `Long`、`String`、`Int`，代码虽然短，但“这个 String 到底是什么结果”很快就会变得模糊。因此：

```kotlin
ColorPickerResult
AccountPickerResult
CategoryPickerResult
```

比：

```kotlin
String
Long
Long
```

更有业务语义。这不是 Navigation 3 强制规则，而是我们主动利用 Kotlin 类型系统让 Result 协议更明确。

---

#### 6.10 为什么 EditRecord 的 ViewModel 还是原来的那个对象？

假设：

```text
EditRecord(101)
vm = 123456
```

然后：

```text
EditRecord(101)
→ ColorPicker
→ RED
→ Back
```

在 ColorPicker 存在的时候，`EditRecord(101)` 仍然留在 Back Stack：

```text
[0] Calendar
[1] DayDetail(...)
[2] EditRecord(101)
[3] ColorPicker(...)
```

因此 EditRecord 对应的 Entry 没有被 pop，它的 Entry-scoped ViewModelStore 也没有被清理。ColorPicker pop 以后，原来的 EditRecord Entry 又成为当前页面，`ResultEffect` 最终把 RED 交给**同一个 EditRecordViewModel**。Navigation 3 的 ViewModel decorator 官方契约就是：ViewModel 作用域属于对应 NavEntry，并在 Entry 真正从 Back Stack 移除后才清理。([Android Developers][3]) 因此你应该观察到：

```text
打开 EditRecord：

EditViewModel CREATE
recordId=101
vm=123456


进入 ColorPicker：
不会 CLEARED


选择 RED 返回：

RESULT EFFECT
vm=123456

ViewModel RECEIVE COLOR
vm=123456
color=RED
```

直到你把：

```text
EditRecord(101)
```

本身 pop 掉，才应该看到：

```text
EditViewModel CLEARED
```

这和“编辑页面 → 分类选择器 → 返回编辑页面”“编辑页面 → 账户选择器 → 返回编辑页面”这类真实业务非常契合。

---

#### 6.11 `ResultEffect` 和你以前学过的 `rememberUpdatedState` 居然接上了

这一点非常值得讲，但不需要读源码。Navigation 3 `1.2.0-alpha07` 的 release notes 有一个非常具体的修复：`ResultEffect` 现在使用 `rememberUpdatedState` 捕获最新的 `onResult` lambda。([Android Developers][1])

这正好就是你前面正式学过的 4.10。假设：

```kotlin
ResultEffect<ColorPickerResult> { result ->
    someObject.handle(result)
}
```

Composition 后来更新了，`someObject` 或这整个回调逻辑已经换成最新版本，但负责监听 Result 的 Effect 本身又不应该因为 callback 更新就反复取消、重启监听。这正是：

```text
Effect 长生命周期工作继续运行
+
callback 永远使用最新值
```

这种典型 `rememberUpdatedState` 场景。所以 `alpha07` 这个 bug fix 不是一句无聊的 release note，它恰好是你以前学过的机制在真正 AndroidX API 内部出现的一个高价值实例。我们知道这一层就够了，不继续看源码。

---

#### 6.12 那 `conflateAsState()` 又是什么？

如果父页面不是想：“收到一次 Result，执行一次操作。” 而是想：“我只关心目前最新的 Result 值，并希望 UI 直接观察它。” 就可以：

```kotlin
val colorResultState =
    LocalResultEventBus.current
        .conflateAsState<ColorPickerResult?>(
            null
        )

val colorResult = colorResultState.value
```

于是 Result 本身成为 Compose State：

```text
没有结果：
null

第一次：
ColorPickerResult(RED)

下一次：
ColorPickerResult(GREEN)
```

UI 读取 `colorResultState.value` 后，结果变化会直接触发相应 Compose 更新。官方把这种方式叫 **State-Based Result**，并说明它适用于只需要最新结果的情况。([Android Developers][4]) 所以可以这样选择：

```text
ResultEffect<T>

“每来一条结果，我要处理一次”
例如：
选完颜色 → 更新 ViewModel
拍完照片 → 通知 ViewModel
选完联系人 → 提交 contactId


conflateAsState<T>()

“我想持续观察最新结果”
例如：
页面 UI 本身直接根据最近一次 picker result 显示内容
```

对于我们当前：

```text
ColorPicker
→ RED
→ ViewModel.onColorSelected(RED)
```

`ResultEffect` 更自然，因为真正的持久页面状态已经由 ViewModel 接管了。

---

#### 6.13 一个非常容易忽视的生命周期边界

官方明确说明，普通 `conflateAsState()` 所保存的 Result State **不会跨配置变更或进程死亡保留**。官方因此另外提供了一份 Serializable State Recipe，用 `rememberSerializable` + `ResultEffect` 自己组合出 `conflateAsSerializableState()`；注意这个 `conflateAsSerializableState()` 是官方 Recipe 中提供的**自定义扩展函数**，不是 `alpha07` 核心库直接附带的 API。([Android Developers][4]) 

这条边界很重要，但不要因此产生：“那 ResultEventBus 不可靠，不能用。” 对于今天这种流程：

```text
ColorPicker
→ RED
→ ResultEffect
→ EditRecordViewModel.color = RED
```

Result 的使命在 `ResultEffect` 成功处理以后就结束了。之后 RED 已经进入 ViewModel 的 UiState，页面状态生命周期由 ViewModel 管。只有当你的业务真的要求：“Result 本身即使尚未来得及被消费，经历配置变更甚至进程死亡以后仍必须恢复。” 才需要考虑官方 Serializable Result Recipe，或者进一步把关键业务事实持久化到数据层。

这种需求我们以后真实遇到再学，不在这里为了“完整”再造一套保存机制。

---

#### 6.14 `rememberResultEventBus()` 为什么这次没有用？

`alpha05` 新增：

```kotlin
rememberResultEventBus()
```

它允许你把 `ResultEventBus` 从 `ResultEventBusNavEntryDecorator` 内部提升出来，然后再把同一个 Bus 传给 decorator。官方 release notes 对这个 API 的定位就是“允许 ResultEventBus hoist 到 decorator 外部”。([Android Developers][1]) 我们当前完全不需要这么做。因为发送端：

```kotlin
entry<ColorPicker> {
    val resultBus = LocalResultEventBus.current
}
```

就在 NavEntry 的 Composition 内部，官方最简单的 Recipe 已经足够。所以这节课先掌握：

```kotlin
rememberResultEventBusNavEntryDecorator()

LocalResultEventBus.current

sendResult()

ResultEffect<T>

conflateAsState<T>()
```

`rememberResultEventBus()` 只需要知道：“如果未来确实需要在 decorator 外部持有同一个 Bus，现在官方已经允许这么做。” 不要为了使用新 API 而强行使用它。

#### 6.15 这份代码真正应该怎么跑

这次建议严格按一个顺序实验：

1. `Calendar → 2026-08-14 → Edit Record 101`，记住 ViewModel 的 `instanceId` 和当前 `BLUE`。
2. 点击“选择颜色”，确认 Back Stack 新增 `ColorPicker(recordId=101, initialColor=BLUE)`。
3. 点击 RED，重点观察日志中的 `SEND RESULT`、ColorPicker pop、`RESULT EFFECT`、`ViewModel RECEIVE COLOR`，并确认页面回到 EditRecord 后颜色变成 RED。
4. 再次进入 ColorPicker，这次应该看到 `initialColor=RED`，因为向前导航时取的是当前 ViewModel UiState。
5. 点击“取消，不返回结果”，确认 EditRecord 仍然保持 RED，并且日志里没有 `RESULT EFFECT`。
6. 再选择 GREEN，确认同一个 EditRecordViewModel 从 RED 更新为 GREEN。
7. 最后 pop EditRecord，确认这时才出现 `EditViewModel CLEARED`。

这里不要求日志的毫秒级先后顺序和我描述完全一致，因为 `NavDisplay` 有转场和 Composition 时机；我们真正检查的是**因果关系**。

#### 6.16 最后把整个阶段压缩成一张心智图

现在 Navigation 3 的页面通信已经不再只有一种“传参数”：

```text
一、向前导航输入

EditRecord(101)
→ ColorPicker(
      recordId = 101,
      initialColor = BLUE
  )

工具：
NavKey
backStack.add()


二、子页面向父页面返回结果

ColorPicker
→ ColorPickerResult(RED)
→ EditRecord

工具：
ResultEventBus
sendResult()
ResultEffect / conflateAsState()


三、页面自己的长期运行状态

EditRecordUiState(
    recordId = 101,
    color = RED
)

工具：
ViewModel
StateFlow
```

这三个层次以后千万不要混：

> **Route 参数描述“我要带着什么输入去下一个页面”；Result 描述“下一个页面执行完成后带回了什么”；ViewModel UiState 描述“当前页面现在是什么状态”。**

而对于你现在这条 Calendar Note 原型：

```text
EditRecord(101)
```

从 BLUE 变 RED 的整个过程中，它的 Navigation Key 根本不需要变化。变化的是 ColorPicker 返回的一次 Result，最终被父 Entry 的 ViewModel 吸收成新的 UiState。

这就是 Navigation 3 `1.2.0-alpha07` 下，目前官方 Result API 最值得真正掌握的心智模型。([Android Developers][2])

### 阶段七：从教学 Demo 到正式 App——Hilt Assisted、NavEntry ViewModel 与大型 Navigation 组织

这一阶段不做“4.6 知识点复读”，而是解决两个你马上开发时一定会碰到的问题：**Navigation 传来的运行时参数怎样进入正式的 Hilt ViewModel；几十个甚至上百个 Destination 怎么组织，而不是把所有 `entry {}` 堆在一个几千行文件里。** Deep Link、多 Back Stack、Bottom Navigation / NavigationRail、Dialog / Overlay 今天都不扩张；前两者以后有明确课程和项目需求再学，后两者等真正涉及 Scene / 顶层导航时再补。

如果你想把这一阶段保存在 CourseCompose，文件可以叫 `Sec06E_ProductionNavigationBridge.kt`；但下面我会故意按**真实项目的文件职责**来展示，而不是假装生产项目也应该所有东西塞进一个 kt 文件。

---

#### 7.1 先看最终形态：正式项目不是“Navigation 创建 Repository”

阶段四的教学 Demo 曾经有这种结构：

```kotlin
NoteDetailRoute(
    noteId = key.noteId,
    repository = repository,
)
```

然后 Route 再手动构造：

```kotlin
viewModel(
    factory = NoteDetailViewModel.Factory(
        noteId = noteId,
        repository = repository,
    )
)
```

作为无 DI 教学代码没问题，但正式 Hilt 项目不应该长这样。正式版本应该变成：

```text
Navigation
    ↓
recordId = 101
    ↓
RecordDetailRoute
    ↓
hiltViewModel()
    ↓
RecordDetailViewModel

其中：

recordId
→ Navigation 运行时产生
→ Hilt 事先不知道
→ Assisted 参数

ObserveRecordUseCase / Repository
→ Hilt 对象图已经知道
→ Hilt 正常注入
```

这正是 **Hilt Assisted Injection（辅助注入）**解决的问题：动态运行时参数由调用者补充，而 Repository、UseCase 等正常依赖继续由 Hilt 提供。Navigation 3 官方现在专门有一份 Hilt Recipe，使用 `@HiltViewModel`、`@AssistedInject`、`@AssistedFactory` 和 `hiltViewModel(... creationCallback = ...)` 完成这条链。([Android Developers][1])

这意味着你之前 Calendar Note 中那种：

```kotlin
@HiltViewModel
class RecordViewModel @Inject constructor(
    private val xxxUseCase: XxxUseCase,
    private val yyyUseCase: YyyUseCase,
) : ViewModel()
```

本身完全不用推翻。只是当 ViewModel 又需要一个 **Hilt 无法预先知道的 `recordId`** 时，把这一项变成 `@Assisted`。

---

#### 7.2 一份接近正式项目的 Data / Domain 层

我们仍然用 Fake 数据，避免这一阶段又变成 Room 课，但对象依赖关系按照正式 Hilt 项目设计。

```kotlin
data class Record(
    val id: Long,
    val title: String,
    val amount: Long,
)

interface RecordRepository {
    fun observeRecord(recordId: Long): Flow<Record?>
}

@Singleton
class FakeRecordRepository @Inject constructor() : RecordRepository {

    private val records = MutableStateFlow(
        mapOf(
            101L to Record(
                id = 101L,
                title = "午餐",
                amount = 1800L,
            ),
            102L to Record(
                id = 102L,
                title = "交通",
                amount = 420L,
            ),
        )
    )

    override fun observeRecord(
        recordId: Long
    ): Flow<Record?> {
        return records.map { map ->
            map[recordId]
        }
    }
}

class ObserveRecordUseCase @Inject constructor(
    private val repository: RecordRepository,
) {
    operator fun invoke(
        recordId: Long
    ): Flow<Record?> {
        return repository.observeRecord(recordId)
    }
}
```

如果 Repository 是接口，正式项目通常再通过 Hilt Module 把实现绑定进去：

```kotlin
@Module
@InstallIn(SingletonComponent::class)
abstract class RecordDataModule {

    @Binds
    @Singleton
    abstract fun bindRecordRepository(
        impl: FakeRecordRepository
    ): RecordRepository
}
```

这里 Navigation 完全不存在。`RecordRepository` 不知道 `NavKey`，UseCase 也不知道 `NavDisplay`。以后把 `FakeRecordRepository` 换成 Room 实现，上面的 Navigation 层不需要跟着改变。

#### 7.3 正式关键代码：Hilt Assisted ViewModel

Route 只传一个最小业务索引：

```kotlin
@Serializable
data class RecordDetailKey(
    val recordId: Long,
) : NavKey
```

然后 ViewModel：

```kotlin
@HiltViewModel(
    assistedFactory = RecordDetailViewModel.Factory::class
)
class RecordDetailViewModel @AssistedInject constructor(

    @Assisted
    private val recordId: Long,

    private val observeRecord:
        ObserveRecordUseCase,

) : ViewModel() {

    val instanceId =
        System.identityHashCode(this)

    val uiState: StateFlow<RecordDetailUiState> =
        observeRecord(recordId)
            .map { record ->
                if (record == null) {
                    RecordDetailUiState.NotFound(
                        recordId = recordId
                    )
                } else {
                    RecordDetailUiState.Success(
                        record = record
                    )
                }
            }
            .stateIn(
                scope = viewModelScope,
                started = SharingStarted.WhileSubscribed(5_000),
                initialValue =
                    RecordDetailUiState.Loading(
                        recordId = recordId
                    ),
            )

    init {
        log(
            "RecordVM",
            "CREATE | recordId=$recordId | vm=$instanceId"
        )
    }

    override fun onCleared() {
        log(
            "RecordVM",
            "CLEARED | recordId=$recordId | vm=$instanceId"
        )
    }

    @AssistedFactory
    interface Factory {
        fun create(
            recordId: Long
        ): RecordDetailViewModel
    }
}
```

UiState 保持普通 UDF：

```kotlin
sealed interface RecordDetailUiState {

    data class Loading(
        val recordId: Long,
    ) : RecordDetailUiState

    data class Success(
        val record: Record,
    ) : RecordDetailUiState

    data class NotFound(
        val recordId: Long,
    ) : RecordDetailUiState
}
```

这里最值得看的是构造函数的“不对称”：

```kotlin
@Assisted
private val recordId: Long
```

和：

```kotlin
private val observeRecord: ObserveRecordUseCase
```

`recordId` 是用户刚刚点了哪条记录以后才产生的，因此 Hilt 在编译期不可能知道它；`ObserveRecordUseCase` 属于依赖图，Hilt 知道怎么创建。所以 Factory 只需要：

```kotlin
fun create(recordId: Long): RecordDetailViewModel
```

**你绝对不需要把 Repository、UseCase 再作为 Factory 参数手工传进去。** `Factory` 补的是 Assisted 参数，不是在重新手写一个 DI 容器。Hilt 官方对 ViewModel assisted injection 的定义正是“动态运行时参数 + Hilt 管理依赖”共同创建 ViewModel。([Android Developers][2])

---

#### 7.4 Navigation Key 怎样真正进入这个 ViewModel？

现在来看 Route 层：

```kotlin
@Composable
private fun RecordDetailRoute(
    recordId: Long,
    onEdit: () -> Unit,
    onBack: () -> Unit,
) {
    val viewModel =
        hiltViewModel<
            RecordDetailViewModel,
            RecordDetailViewModel.Factory
        >(
            creationCallback = { factory ->
                factory.create(
                    recordId = recordId
                )
            }
        )

    val uiState by
        viewModel.uiState.collectAsStateWithLifecycle()

    RecordDetailScreen(
        uiState = uiState,
        onEdit = onEdit,
        onBack = onBack,
    )
}
```

这几行就是阶段四那个手写 `ViewModelProvider.Factory` 的**正式 Hilt 替代品**。运行链非常值得一次看透：

```text
entry<RecordDetailKey>
拿到：
RecordDetailKey(recordId=101)

        ↓

RecordDetailRoute(
    recordId = 101
)

        ↓

hiltViewModel<VM, Factory>()

        ↓

先询问当前 NavEntry 的 ViewModelStore：
“这里已经有 RecordDetailViewModel 吗？”

        ↓

没有

        ↓

Hilt 得到 creationCallback

        ↓

factory.create(101)

        ↓

Hilt 创建：

RecordDetailViewModel(
    recordId = 101,              ← Assisted
    observeRecord = xxxUseCase   ← Hilt
)

        ↓

存进当前 NavEntry 的 ViewModelStore
```

Navigation 3 官方的 Hilt Recipe 就是在 `entry<RouteB> { key -> ... }` 中调用带 `creationCallback` 的 `hiltViewModel()`，并配合 `rememberViewModelStoreNavEntryDecorator()`，使 ViewModel 作用域属于对应 `NavEntry`。([Android Developers][1]) 这同时解释了为什么阶段四那个 decorator 绝对不能忘：

```kotlin
entryDecorators = listOf(
    rememberSaveableStateHolderNavEntryDecorator(),
    rememberViewModelStoreNavEntryDecorator(),
    rememberResultEventBusNavEntryDecorator(),
)
```

没有 ViewModel decorator，`hiltViewModel()` 虽然依旧会帮你 DI，但**Owner 错了还是错了**。Hilt 解决“VM 怎么造”；NavEntry decorator 解决“VM 属于谁”。官方当前文档也是把这两个职责分开的。([Android Developers][3])

#### 7.5 Assisted 参数经过进程死亡怎么办？

这里有一个非常容易误会的地方。Dagger/Hilt 明确说明：**Assisted 参数自己不会被 Hilt 持久化到磁盘。** ViewModel 真正因为进程死亡消失以后，原来的 assisted 参数也跟着没了。([Dagger][4]) 但是我们的 `recordId` 还有另一份来源：

```text
RecordDetailKey(
    recordId = 101
)
```

这个 Key 在 `rememberNavBackStack()` 中，是 Navigation 的可序列化导航状态。Navigation 3 可以恢复 back stack；新的 Entry 重建以后，`entry<RecordDetailKey>` 又重新得到 `recordId=101`，随后新的 `creationCallback` 再把 101 交给新的 ViewModel。Navigation 3 官方就是依靠 saveable / serializable Key 恢复导航状态。([Android Developers][3]) 所以：

```text
旋转屏幕：

NavEntry 保留
→ ViewModel 保留
→ Factory 不重新创建 VM


进程死亡：

旧 VM 消失
→ Navigation 恢复 RecordDetailKey(101)
→ 创建新的 NavEntry
→ creationCallback 再得到 101
→ Hilt 创建新的 VM
→ Repository / Room 重建业务状态
```

这条链非常适合真实详情页。

#### 7.6 然后解决你最担心的问题：100 个页面难道真写 100 个 `entry`？

**逻辑上，是的：100 个真正独立的导航 Destination，最终就必须有把这些 Key 解析成内容的规则。** 某种东西总得告诉系统：

```text
CalendarKey      → CalendarRoute
DayDetailKey     → DayDetailRoute
RecordDetailKey  → RecordDetailRoute
SettingsKey      → SettingsRoute
...
```

框架不可能凭空猜出来。但是生产项目绝对不是：

```kotlin
entryProvider {
    // 第 1 个
    // 第 2 个
    // ...
    // 第 100 个
}
```

全部塞进 `MainActivity.kt`。Navigation 3 官方现在已经专门发布了 **Modularize navigation code** 指南，推荐把相关 Key 和 Entry 按 feature 拆开；其中最基础的方案就是在 `EntryProviderScope` 上写 extension function，也就是官方称呼的 **entry builder**。([Android Developers][5]) 例如 Record feature 自己管理 Record 的导航：

```kotlin
fun EntryProviderScope<NavKey>.recordEntries(
    navigator: AppNavigator,
) {
    entry<RecordDetailKey> { key ->
        RecordDetailRoute(
            recordId = key.recordId,

            onEdit = {
                navigator.navigate(
                    EditRecordKey(
                        recordId = key.recordId
                    )
                )
            },

            onBack = navigator::back,
        )
    }

    entry<EditRecordKey> { key ->
        EditRecordRoute(
            recordId = key.recordId,
            onBack = navigator::back,
        )
    }

    entry<RecordCategoryKey> { key ->
        RecordCategoryRoute(
            categoryId = key.categoryId,
            onBack = navigator::back,
        )
    }
}
```

Calendar feature 自己管理 Calendar：

```kotlin
fun EntryProviderScope<NavKey>.calendarEntries(
    navigator: AppNavigator,
) {
    entry<CalendarKey> {
        CalendarRoute(
            onOpenDay = { date ->
                navigator.navigate(
                    DayDetailKey(
                        year = date.year,
                        month = date.month,
                        day = date.dayOfMonth,
                    )
                )
            }
        )
    }

    entry<DayDetailKey> { key ->
        DayDetailRoute(
            year = key.year,
            month = key.month,
            day = key.day,

            onOpenRecord = { recordId ->
                navigator.navigate(
                    RecordDetailKey(recordId)
                )
            },

            onBack = navigator::back,
        )
    }
}
```

Settings feature 又有自己的：

```kotlin
fun EntryProviderScope<NavKey>.settingsEntries(
    navigator: AppNavigator,
) {
    entry<SettingsKey> {
        SettingsRoute(...)
    }

    entry<ThemeSettingsKey> {
        ThemeSettingsRoute(...)
    }

    entry<BackupSettingsKey> {
        BackupSettingsRoute(...)
    }
}
```

最后 App 根节点里只剩：

```kotlin
entryProvider = entryProvider {
    calendarEntries(navigator)
    recordEntries(navigator)
    statisticsEntries(navigator)
    settingsEntries(navigator)
}
```

于是：

```text
100 个 Destination

不是：

AppNavigation.kt
    └── 100 个 entry，3000 行


而是：

calendar/
    CalendarRoutes.kt
    CalendarEntries.kt
    CalendarRoute.kt

record/
    RecordRoutes.kt
    RecordEntries.kt
    RecordDetailRoute.kt
    EditRecordRoute.kt

statistics/
    StatisticsRoutes.kt
    StatisticsEntries.kt

settings/
    SettingsRoutes.kt
    SettingsEntries.kt
```

根 Navigation 只负责**组装 feature**。这不是我们自己发明的模式；官方 Navigation 3 modularization 文档现在直接推荐 `EntryProviderScope<NavKey>.featureXEntryBuilder()` 这种拆法。([Android Developers][5])

#### 7.7 我甚至建议正式 App 不要让所有 Screen 直接摸 `backStack`

到现在教学代码一直写：

```kotlin
backStack.add(...)
backStack.removeLastOrNull()
```

这是为了让你学习 Navigation 3 的真实模型。正式项目页面一多，如果到处直接传：

```kotlin
backStack
```

最后 Navigation 状态修改会散满整个项目。我们可以放一个非常薄的导航状态操作对象：

```kotlin
class AppNavigator(
    private val navigateAction: (NavKey) -> Unit,
    private val backAction: () -> Unit,
) {
    fun navigate(
        key: NavKey
    ) {
        navigateAction(key)
    }

    fun back() {
        backAction()
    }
}
```

Host 创建：

```kotlin
val backStack = rememberNavBackStack(CalendarKey)

val navigator = remember(backStack) {
    AppNavigator(
        navigateAction = { key ->
            backStack.add(key)
        },
        backAction = {
            backStack.removeLastOrNull()
        }
    )
}
```

然后 feature navigation 只知道：

```kotlin
navigator.navigate(
    RecordDetailKey(101)
)

navigator.back()
```

这不是为了重新造一个 `NavController`。`AppNavigator` 不保存另一份导航状态，它只是把：

```kotlin
backStack.add()
backStack.removeLastOrNull()
```

集中成一个操作边界。这样以后如果你要增加：

```text
防重复导航
日志
Analytics
singleTop 类政策
统一 pop 规则
```

不必在 80 个 Screen 里到处改。Navigation 3 官方模块化指南也明确提到：如果各 feature 的 Entry 需要导航，可以向 entry builder 提供一个**能够修改应用导航状态的对象**。([Android Developers][5])

#### 7.8 最终 AppNavigationHost 已经会非常干净

现在把前面的东西拼起来：

```kotlin
@Composable
fun AppNavigationHost() {
    val backStack = rememberNavBackStack(CalendarKey)

    val navigator =
        remember(backStack) {
            AppNavigator(
                navigateAction = backStack::add,
                backAction = {
                    backStack.removeLastOrNull()
                }
            )
        }

    NavDisplay(
        backStack = backStack,
        onBack = navigator::back,
        entryDecorators = listOf(
            rememberSaveableStateHolderNavEntryDecorator(),
            rememberViewModelStoreNavEntryDecorator(),
            rememberResultEventBusNavEntryDecorator(),
        ),

        entryProvider = entryProvider {
            calendarEntries(navigator)
            recordEntries(navigator)
            statisticsEntries(navigator)
            settingsEntries(navigator)
        }
    )
}
```

看这个 Host，现在你已经很难从代码长度判断 App 到底是 10 个页面还是 100 个页面。它只关心四件事情：

```text
1. 返回栈在哪里
2. 谁修改返回栈
3. 每个 Entry 需要哪些横切能力
4. App 有哪些 feature 的 Entry
```

**具体某个页面如何创建 Hilt ViewModel、需要什么 Key、点击按钮去哪，都回到自己的 feature 里。**这才是从我们现在的教学 Demo 向生产代码迈出的真正一步。

#### 7.9 单模块个人 App，需要现在就拆 `api / impl` Gradle Module 吗？

这里我建议你千万别从“以前太简单”突然跳到“企业级过度架构”。Google 当前 Navigation 3 官方模块化方案更进一步：对于真正的多模块大型项目，可以让每个 feature 拆成：

```text
feature:record:api
feature:record:impl
```

其中：

```text
api
→ 对外暴露 NavKey

impl
→ Route / Screen
→ ViewModel
→ Entry builder
```

这样别的 feature 想导航到 Record，只需要依赖：

```text
feature:record:api
```

不需要依赖整个 Record UI 实现。官方目前明确推荐导航 Key 放 `api` 模块，`entryProvider` 和可导航内容放 `impl` 模块。([Android Developers][5]) 但对于你接下来自己的 Calendar Note，我**不会建议一开工就创建二三十个 Gradle Module**。现在更适合：

```text
app/

feature/
    calendar/
        navigation/
        CalendarRoute.kt
        CalendarScreen.kt
        CalendarViewModel.kt

    record/
        navigation/
        RecordRoute.kt
        RecordScreen.kt
        RecordViewModel.kt

    statistics/
        ...

    settings/
        ...

data/
domain/
navigation/
```

也就是**先按 package / feature 做逻辑模块化**。如果以后项目真的长到几十个 feature、多人协作、编译隔离和依赖边界开始成为现实问题，再把这些 package 迁成真正 Gradle modules。今天学习官方 `api / impl` 模型，是为了知道大型 App 怎么走，不是让你的个人 App 第一天就照搬 Google 自己的大型工程规模。

#### 7.10 真正到非常大的 App，连四五十个 feature builder 都不想手动注册怎么办？

Navigation 3 官方也考虑到了。如果：

```kotlin
entryProvider {
    accountEntries()
    calendarEntries()
    recordEntries()
    statisticsEntries()
    searchEntries()
    settingsEntries()
    ...
}
```

随着 feature module 极多仍然开始膨胀，官方模块化文档进一步给出了 **Dagger multibindings + `@IntoSet`** 的方案：每个 feature 自己把 entry builder 贡献进一个 `Set`，App 根模块注入这个集合，然后循环注册。([Android Developers][5])

概念上会变成：

```text
Calendar feature
        \
Record feature
         \
Settings feature  → Hilt/Dagger Set<EntryBuilder>
         /
Search feature
        /
Statistics feature

             ↓

AppNavigationHost

entryProvider {
    builders.forEach {
        注册这个 feature 的 entries
    }
}
```

也就是说，一个新 feature 加入项目以后，可以做到：feature 自己声明“我提供这些 Navigation Entry”，App 根 Host 不必再人工增加一行。官方示例就是用 `@IntoSet` 将 `EntryProviderScope<NavKey>.() -> Unit` 注入 Activity，再统一调用。([Android Developers][5]) 但是这一层我建议你**现在只理解，不实装**。你个人 Calendar Note 用：

```kotlin
calendarEntries()
recordEntries()
statisticsEntries()
settingsEntries()
```

已经非常干净。等哪一天你真的面对一个五六十个 feature module 的商业工程，再用 DI 自动收集 Entry Builder，不迟。

#### 7.11 一个容易忽视的问题：大型模块化以后，还要不要一个全局 `sealed interface AppRoute`？

你现在教学工程一直是：

```kotlin
@Serializable
sealed interface Sec06Route : NavKey
```

在**单 module**里非常舒服，因为所有 Route 可以集中封闭管理。但如果未来真的按照官方方案：

```text
feature:calendar:api
feature:record:api
feature:statistics:api
```

分别定义 Key，那么强行要求所有 feature 都成为一个跨 Module 的 `sealed interface AppRoute` 子类反而不自然。Kotlin 的 sealed 层级本身对直接子类所在 module/package 有约束。大型多模块项目完全可以直接：

```kotlin
@Serializable
data object CalendarKey : NavKey

@Serializable
data class DayDetailKey(
    ...
) : NavKey

@Serializable
data class RecordDetailKey(
    val recordId: Long
) : NavKey
```

然后统一使用：

```kotlin
EntryProviderScope<NavKey>
```

官方模块化示例本身也是围绕 `NavKey` 和不同 feature 的 Key 来组织，而不是要求整个大型 App 必须有一个总 `sealed AppRoute`。([Android Developers][5]) 所以这里不要把我们的：

```kotlin
sealed interface Sec06CRoute
```

误认为 Navigation 3 的强制架构。它只是**小型 / 单模块项目特别好用的一种 Kotlin 建模方式**。

#### 7.12 把 Hilt、Navigation、UDF 三条链最终合起来

现在一个正式的 Record Detail 页面，完整调用链已经是：

```text
用户在 DayDetail 点击 Record 101
                ↓
AppNavigator.navigate(
    RecordDetailKey(101)
)
                ↓
backStack 新增 Key
                ↓
recordEntries() 中：
entry<RecordDetailKey>
                ↓
RecordDetailRoute(
    recordId = 101
)
                ↓
hiltViewModel(
    creationCallback = {
        factory.create(101)
    }
)
                ↓
NavEntry VM Store
        +
Hilt Assisted
                ↓
RecordDetailViewModel(
    recordId = 101,
    observeRecordUseCase = Hilt提供
)
                ↓
UseCase
                ↓
Repository
                ↓
Room / Network
                ↓
StateFlow<UiState>
                ↓
collectAsStateWithLifecycle()
                ↓
RecordDetailScreen(
    uiState,
    callbacks
)
```

请注意每一层现在都只知道自己该知道的东西：**`RecordDetailKey`** 知道“去看 101”；**Navigation** 知道如何找到 `RecordDetailRoute`；**Route Composable** 是 Navigation、Hilt ViewModel 与纯 UI 之间的胶水层；**ViewModel** 知道 `recordId` 和业务 UseCase，但不需要知道 `backStack`；**Repository** 根本不知道页面和 Navigation；**Screen** 只认识 `UiState` 和事件。这就是我认为你正式 Calendar Note 可以采用的骨架。

#### 7.13 哪些 Navigation 3 知识现在明确不继续钻？

4.6 到这里，已经跨过“只会 Demo”的门槛了。Navigation 3 当前官方能力还包括 Scene、自适应多 Pane、Deep Link、metadata、Overlay、复杂返回行为、多 Back Stack 等等；Navigation 3 本身也明确支持自适应布局和同时展示多个 Destination。([Android Developers][6])

但按照你当前开发目标，我会这样排：

**现在已经必须会的**：Key、back stack、`NavDisplay`、`entryProvider`、参数、Entry-scoped ViewModel、Hilt Assisted、Result、feature entry builders。我们已经覆盖。

**4.19 再正式学的**：Bottom Navigation / NavigationRail、多个顶层 Destination、多 Back Stack、手机与大屏导航框架。

**开发遇到时定向补的**：Deep Link、Dialog / Overlay、特殊 pop 策略、复杂 Result 保存。

**现在只知道存在即可的**：自定义 Scene、metadata、高级 NavigationEvent / Predictive Back 定制等。官方当前确实还有 Scene 与 metadata 等更底层扩展能力，但它们并不阻塞你开始一个普通 Calendar Note App。([Android Developers][7])

所以这一次我不再给你安排“阶段八继续深挖 Navigation 3”。**4.6 到阶段七可以正式结束。**

而且现在的结束点比原大纲那个“做几道场景题然后总结”有价值很多：你已经知道从一个 `data class NavKey`，一路走到 Hilt ViewModel，再走到几十个页面的 feature 级 Navigation 组织应该是什么样子。

接下来按照当前知识路线，更合理的是离开 Navigation 3，继续补下一个真正会阻塞正式 App 开发的核心主题；等到 4.19，再回来把今天这套纵向页面导航升级成完整的 App 顶层导航框架。
