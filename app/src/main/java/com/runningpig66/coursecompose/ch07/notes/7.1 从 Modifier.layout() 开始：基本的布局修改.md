### 第一阶段：第一次进入 Compose 布局系统 —— 从 `Modifier.layout()` 看完整布局流程

你前面 6.1～6.5 学的是绘制。到了 `DrawScope` 里，我们一直默认一个事实：**当前组件已经拥有确定的 `size`，你只负责在这块区域里画东西。**从 7.1 开始，我们往前追一步：**这块区域为什么这么大？它的位置是谁决定的？**这就是布局系统负责的事情。

Compose 官方对一个布局节点的过程概括得很直接：**测量子项 → 决定自己的尺寸 → 放置子项**。`Modifier.layout()` 则允许我们插入这个过程，修改一个组件“怎样被测量、最终占多大空间、内部内容放在哪里”。[Android Developers](https://developer.android.com/develop/ui/compose/layouts/custom?authuser=4&utm_source=chatgpt.com) 这一阶段先不研究复杂的 Constraints 传播，也不研究 Modifier 链嵌套。我们只把一次完整布局真正跑通。

#### 1. 先建立最基本的问题：为什么“绘制”之前必须有“布局”

假设现在有一个：

```kotlin
Text("Hello")
```

最终屏幕当然需要知道两件事：

```
它有多大？
它放在哪里？
```

否则后面的绘制根本没有坐标系可用。所以可以先把目前的整体关系理解成：

```
Composition
    ↓
Layout
    ├─ Measure：多大？
    └─ Placement：放哪？
    ↓
Draw：在已经确定的区域中画什么？
```

你在 6.x 里学到的：

```kotlin
drawBehind {
    println(size)
}
```

这里的 `size` 并不是绘制阶段自己算出来的。**布局阶段已经把尺寸确定好了，绘制阶段只是拿来使用。**现在 7.x 要研究的，正是这个 `size` 从哪里来的。

------

#### 2. 第一次看 `Modifier.layout()` 的形状

它最基本的写法是：

```
Modifier.layout { measurable, constraints ->

}
```

目前只认识两个角色，不需要一次吃透。`constraints` 是**外面传进来的尺寸限制**。父布局并不总是直接告诉你“你必须是 300 × 100”，更常见的是告诉你：

```
宽度最少多少、最多多少
高度最少多少、最多多少
```

也就是一个允许范围。概念上可以先看成：

```
Constraints(
    minWidth,
    maxWidth,
    minHeight,
    maxHeight
)
```

这一阶段只需要知道：**Constraints 是上游交给当前组件的尺寸规则。**下一阶段我们会专门把它拆开实验。另一个参数：

```
measurable
```

可以先理解为：**“一个还没有测量过的东西。”** 因此它现在没有一个你可以直接使用的最终宽高。你需要主动：

```
val placeable = measurable.measure(constraints)
```

意思就是：按照这份 `constraints`，把里面这个东西测量一次。测量之后得到：

```
Placeable
```

此时：

```
placeable.width
placeable.height
```

才是测量得到的宽高。官方 API 对这个关系的定义也是：`Measurable.measure(constraints)` 会按照指定 Constraints 测量，并返回拥有测量尺寸的 `Placeable`。[Android Developers](https://developer.android.com/reference/kotlin/androidx/compose/ui/layout/Measurable?utm_source=chatgpt.com) 所以先记住这个非常自然的状态变化：

```
Measurable
还没测
    ↓ measure(constraints)
Placeable
测完了，知道 width / height，也可以被摆放
```

这两个名字以后会反复出现。

#### 3. 第一个完整实验：人为给一个 Text 增加布局空间

创建：`Sec01A_BasicLayoutModifier.kt`

```kotlin
private const val Sec0701A = "Sec0701A"

@Composable
fun Sec01A_BasicLayoutModifier() {
    Column(
        modifier = Modifier
            .fillMaxSize()
            .padding(24.dp),
        verticalArrangement = Arrangement.spacedBy(20.dp)
    ) {
        Text(
            text = "Modifier.layout() 第一次实验",
            style = MaterialTheme.typography.titleMedium
        )

        Text(
            text = "橙色：layout Modifier 对外占据的区域\n" +
                    "蓝色：真正被测量的内部内容"
        )

        Box(
            modifier = Modifier
                .background(Color(0xFFFFE0B2))
                .border(2.dp, Color(0xFFF57C00))
        ) {
            Text(
                text = "MEASURED CHILD",
                color = Color.Black,
                modifier = Modifier
                    .layout { measurable, constraints ->
                        Log.d(
                            TAG,
                            "① incoming constraints = $constraints"
                        )

                        val placeable = measurable.measure(constraints)

                        Log.d(
                            TAG,
                            "② measured child = " +
                                    "${placeable.width} x ${placeable.height}"
                        )

                        val extraWidth = 80.dp.roundToPx()
                        val extraHeight = 56.dp.roundToPx()

                        val layoutWidth = constraints.constrainWidth(
                            placeable.width + extraWidth
                        )

                        val layoutHeight = constraints.constrainHeight(
                            placeable.height + extraHeight
                        )

                        Log.d(
                            TAG,
                            "③ report layout size = " +
                                    "$layoutWidth x $layoutHeight"
                        )

                        layout(
                            width = layoutWidth,
                            height = layoutHeight
                        ) {
                            val x = (layoutWidth - placeable.width) / 2
                            val y = (layoutHeight - placeable.height) / 2

                            Log.d(
                                TAG,
                                "④ place child at x=$x, y=$y"
                            )

                            placeable.placeRelative(x, y)
                        }
                    }
                    .background(Color(0xFFBBDEFB))
                    .border(2.dp, Color(0xFF1976D2))
                    .padding(
                        horizontal = 16.dp,
                        vertical = 12.dp
                    )
            )
        }
    }
}

@Preview(showBackground = true)
@Composable
private fun Sec01A_BasicLayoutModifierPreview() {
    MaterialTheme {
        Sec01A_BasicLayoutModifier()
    }
}
```

这里故意不用什么真实业务。第一份代码只服务一个目标：**把布局过程看见。**

#### 4. 先运行，不要急着读每一行

运行之后，重点看 UI。你应该看到一个**比较大的橙色区域**，而蓝色的 `MEASURED CHILD` 位于橙色区域中央。视觉上大致是：

```
┌──────────────────────────────┐
│          橙色区域             │
│                              │
│     ┌──────────────────┐     │
│     │  MEASURED CHILD  │     │
│     └──────────────────┘     │
│                              │
└──────────────────────────────┘
```

这里第一次出现了一个非常值得注意的现象：**蓝色内容本身明明没有那么大，但是整个东西在父布局眼中却占据了更大的橙色区域。**先把这个现象记住。然后打开 Logcat，过滤：

```
Sec0701A
```

会看到类似：

```
① incoming constraints = Constraints(...)
② measured child = 178 x 83
③ report layout size = 418 x 251
④ place child at x=120, y=84
```

你的具体数字会因为屏幕密度、字体等不同而变化，**不要对照具体数字**。布局系统这里使用的是像素值，所以我们写的 `80.dp` 最终也通过：

```
80.dp.roundToPx()
```

变成了 px。真正需要观察的是四个步骤的关系。

------

#### 5. 第一步：父级先给我们 `constraints`

代码进入：

```
.layout { measurable, constraints ->
```

此时发生的第一件事不是“Text 多大”。事实上，此刻我们**还不知道里面 Text 最终多大**。我们现在首先拥有的是：

```
constraints
```

它来自外层布局。在这个例子中，外层最终是 `Box`、`Column` 等布局结构。它们经过布局过程以后，把一组允许的尺寸范围传进来。所以整个过程首先是从外往里的：

```
外层布局
    ↓
Constraints
    ↓
当前 layout Modifier
```

这和绘制阶段很不一样。绘制时你经常拿到的是一个已经确定的：

```
Size(width, height)
```

布局阶段拿到的首先却是：

```
Constraints
```

也就是：**“你最终可以多大。”**而不是：“你已经这么大了。” 这是从绘制进入布局之后，第一个真正重要的心智转换。

------

#### 6. 第二步：我们拿着 Constraints 去测里面的内容

接下来：

```
val placeable = measurable.measure(constraints)
```

可以暂时把这句话翻译成：“里面那个组件，你按照父级给我的这些尺寸限制，测一下你自己需要多大。” 于是：

```
Constraints
      ↓
Measurable.measure()
      ↓
Placeable
```

现在得到：

```
placeable.width
placeable.height
```

日志：

```
② measured child = ...
```

就是这个结果。这个 `placeable` 可以理解成：**里面那个内容已经完成测量之后的布局对象。**它现在已经有尺寸了，但注意：**它还没有被我们决定放在哪里。**也就是说：

```
Measure 完成
≠
Placement 完成
```

Compose 故意把这两步分开。官方自定义布局文档也是按照“测量子项 → 决定自身尺寸 → 放置子项”描述整个过程的。[Android Developers](https://developer.android.com/develop/ui/compose/layouts/custom?authuser=4&utm_source=chatgpt.com)

------

#### 7. 第三步：我们决定“当前这一层”自己有多大

这里是第一次接触 `Modifier.layout()` 最容易让人惊讶的地方。child 测出来可能只有：

```
178 × 83
```

但我们没有直接：

```
layout(
    placeable.width,
    placeable.height
)
```

而是人为增加：

```
val extraWidth = 80.dp.roundToPx()
val extraHeight = 56.dp.roundToPx()
```

最后：

```
layoutWidth = placeable.width + extraWidth
layoutHeight = placeable.height + extraHeight
```

于是出现了：

```
child 实际测量尺寸
178 × 83
↓
当前 layout Modifier 对外尺寸
418 × 251
```

数字只是示意。这里先建立一个极其重要的概念：**里面的 child 有多大，和当前这一层 layout 最终向外表现为多大，不要求完全相同。**所以我们第一次看到了两个尺寸：

```
Placeable size
    ↓
里面被测量内容的尺寸

Layout size
    ↓
当前 layout Modifier 自己最终占据的尺寸
```

第二阶段会专门把这个区别狠狠干透。这一阶段先观察到它确实存在就够了。代码里的：

```
constraints.constrainWidth(...)
constraints.constrainHeight(...)
```

暂时可以理解为：“我虽然想要这么大，但最后仍然遵守父级传进来的 Constraints。” 具体为什么必须这样，以及违反 Constraints 会发生什么，下一阶段再实验。

------

#### 8. 注意这里有两个长得一样的 `layout`

这段代码第一次看非常容易混：

```
Modifier.layout { measurable, constraints ->

    ...

    layout(width, height) {

    }
}
```

它们虽然都叫 `layout`，但角色完全不同。外面的：

```
Modifier.layout { measurable, constraints -> ... }
```

是在说：**给这个组件安装一个自定义的布局 Modifier。**而里面的：

```
layout(width, height) {
    ...
}
```

是在当前测量过程中说：**“我这一层最终决定自己的尺寸是 width × height。” ** 然后它返回一个 `MeasureResult`。`Modifier.layout` 当前的官方签名也是：

```
fun Modifier.layout(
    measure: MeasureScope.(
        Measurable,
        Constraints
    ) -> MeasureResult
): Modifier
```

也就是说，我们整个 lambda 最终必须产生一次测量结果。[Android Developers](https://developer.android.com/reference/kotlin/androidx/compose/ui/Modifier?authuser=002&utm_source=chatgpt.com) 现阶段不需要背这个签名，只要别把两个 `layout` 当成同一件事情。

------

#### 9. 第四步：有了自己的区域，再决定 child 放在哪里

现在我们的 layout 已经决定：

```
我有这么宽
我有这么高
```

但里面蓝色 child 只有较小的一块。那它放左上角？还是右下角？还是中间？这就是 Placement。代码计算：

```kotlin
val x = (layoutWidth - placeable.width) / 2
val y = (layoutHeight - placeable.height) / 2
```

然后：

```kotlin
placeable.placeRelative(x, y)
```

意思就是：**把刚才已经测好的 Placeable 放到当前 Layout 区域中的 `(x, y)`。**坐标仍然遵循你在 Canvas 中已经很熟悉的概念：

```
(0, 0)
┌────────────────────────────→ x
│
│
│
↓
y
```

于是整个过程终于完整：

```
① 收到 Constraints
        ↓
② measurable.measure(constraints)
        ↓
   得到 Placeable
   知道 child 多大
        ↓
③ layout(width, height)
   决定当前这一层自己多大
        ↓
④ placeable.placeRelative(x, y)
   决定 child 放在哪里
```

这就是你现在要建立的 **Compose Layout 第一张核心地图**。

------

#### 10. 为什么 `layout {}` 里面还套着一个 placement block

再仔细看：

```
layout(
    width = layoutWidth,
    height = layoutHeight
) {
    placeable.placeRelative(x, y)
}
```

这里其实已经把两个阶段在代码结构上分出来了。`layout(width, height)` **之前**：

```
val placeable = measurable.measure(constraints)
```

主要是在做测量以及决定自己的尺寸。而：

```
layout(width, height) {
    ...
}
```

内部的 block 负责 placement。官方目前也把 `Modifier.layout` 明确区分为 Measurement 和 Placement 两部分：`layout(w, h)` 之前的代码运行在测量阶段，而 `layout { ... }` 中对子项执行 `place` 的代码属于 placement 阶段。[Android Developers](https://developer.android.com/develop/ui/compose/performance/modifier-phases?utm_source=chatgpt.com) 所以代码结构其实已经在提示你：

```
Measure
------------------------
measure(...)
计算自己的 width/height

        ↓

Placement
------------------------
layout(...) {
    place(...)
}
```

以后学习布局动画和性能时，这个区分还会重新出现。但现在只需要认识它。

------

#### 11. `Measurable` 和 `Placeable` 不要背定义，用流程记

这两个名字第一次出现很容易绕。直接这样记：

```
Measurable
“你可以测我”
      ↓
   measure()
      ↓
Placeable
“我已经测完了，现在可以摆我”
```

所以代码天然就是：

```
val placeable = measurable.measure(constraints)
```

然后：

```
placeable.width
placeable.height

placeable.placeRelative(...)
```

这个命名其实非常贴切。

`Measurable` 强调 **measure 能力**。
`Placeable` 强调测量完成后进入 **place 能力**。

------

#### 12. 一个现在就要知道的规则：同一个 child 不要反复 measure

你可能很自然会想：

```
val a = measurable.measure(constraints1)
val b = measurable.measure(constraints2)
```

“我先试一次，不满意再换一种尺寸测一次不就行了吗？”

普通 Compose 自定义布局不是这么工作的。Compose 的布局模型要求一个子项在一次测量过程中不能为了尝试不同配置而反复测量；官方文档明确说明 Compose UI 不允许这种 multi-pass measurement。[Android Developers](https://developer.android.com/develop/ui/compose/layouts/custom?authuser=4&utm_source=chatgpt.com)

所以我们现在的基本习惯就是：

```
val placeable = measurable.measure(...)
```

**一次测好，再根据结果决定自己的布局。**为什么 Compose 做这种限制，以及遇到“必须先知道结果再决定组合内容”的需求怎么办，现在不要展开。后面的 `SubcomposeLayout()` 会解决另一类更复杂的问题。

#### 13. 回到屏幕上的橙色和蓝色，现在应该能解释了

运行结果：

```
┌──────────────────────────────┐
│            orange            │
│                              │
│      ┌────────────────┐      │
│      │      blue      │      │
│      └────────────────┘      │
│                              │
└──────────────────────────────┘
```

蓝色区域对应的是：

```
val placeable = measurable.measure(constraints)
```

之后得到的内部内容尺寸。橙色区域之所以比它大，是因为我们后来主动：

```
layout(
    width = placeable.width + extraWidth,
    height = placeable.height + extraHeight
)
```

让当前这一层向外占据了更大的空间。然后蓝色内容能待在中央，是因为：

```
placeable.placeRelative(x, y)
```

把它移动到了当前 layout 区域中央。所以今天这个实验真正证明的是：

```
Constraints
    ↓
measure child
    ↓
Placeable
    ↓
decide my size
    ↓
layout(width, height)
    ↓
place child
    ↓
最终位置确定
    ↓
Draw
```

这条链路一旦建立起来，你后面学习所有自定义布局，基本都不会再从零开始。

#### 14. 最后连接一下你刚学完的绘制体系

现在可以把 6.x 和 7.x 第一次真正接起来。前面写：

```
Modifier.drawBehind {
    drawRect(...)
}
```

你进入 `DrawScope` 后，已经拥有：

```
size
```

而今天我们第一次知道，在绘制开始以前，布局系统已经经历：

```
父级 Constraints
        ↓
Measure
        ↓
决定当前尺寸
        ↓
Placement
        ↓
得到最终布局区域
        ↓
DrawScope.size
        ↓
开始绘制
```

所以你以后看到：

```
size.width
size.height
```

脑子里不应该再把它理解成“组件天生就有这么大”。它是**前面的布局过程产生的结果**。这就是第一阶段真正需要留下来的心智模型。

你实际运行 `Sec01A_BasicLayoutModifier.kt` 时，重点只检查三件事：**橙色是否明显大于蓝色；蓝色是否被放在橙色区域中央；Logcat 中是否能看到 Constraints → measured child → reported size → placement 这四组信息。**如果实际 UI 或日志和这里描述的不一致，直接把结果发给我，我们以你的真实运行结果为准，再进入第二阶段。

### 第二阶段：把 Measure 拆开——Constraints、Measurable、Placeable 与“我自己多大”

第一阶段已经跑通了完整流程：

```text
收到 Constraints
→ measure()
→ 得到 Placeable
→ layout(width, height)
→ placeRelative()
```

这一阶段不增加底层概念，而是把这条链中最容易混淆的三件事彻底分开：

1. **父级允许当前布局多大；**
2. **当前 `layout` Modifier 把内侧内容测成多大；**
3. **当前这一层最终向外报告自己多大。**

你上一阶段重新加入 `padding` 后得到：

```text
无 padding：
measured child = 366 x 63

有 padding：
measured child = 450 x 127
```

这个现象正好给第二阶段提供了入口。

---

#### 1. 先把 `measurable` 的身份说准确

第一阶段为了入门，我们把 `measurable` 暂时解释成：一个还没有测量过的东西。现在需要把它升级成准确版本：**`measurable` 代表当前这个 `Modifier.layout` 内侧、等待当前层去测量的内容。**

这里最重要的是“**内侧**”。例如：

```kotlin
Text(
    text = "MEASURED CHILD",
    modifier = Modifier
        .layout { measurable, constraints ->
            ...
        }
        .background(...)
        .border(...)
        .padding(16.dp)
)
```

当前 `layout` 并不是直接拿到了一个“裸的 `Text`”。从当前 `layout` 的视角来看，它内侧还有：

```text
background
→ border
→ padding
→ Text
```

其中 `background`、`border` 本身不会改变测量尺寸，但 `padding` 会参与布局。所以当这里执行：

```kotlin
val placeable = measurable.measure(constraints)
```

它测量的是**当前 `layout` Modifier 内侧那整层内容**。于是你得到：

```text
无 padding：366 × 63
有 padding：450 × 127
```

完全合理。这也是为什么以后不要把：

```kotlin
measurable
```

简单记成：当前 Text。更好的长期理解是：**当前 Layout Modifier 需要负责测量的“下一层内容”。**完整的 Modifier 链如何一层套一层，我们放到第三阶段。这里先把 `measurable` 的身份固定下来。

---

#### 2. `Constraints` 不是组件尺寸，而是一份允许范围

第一阶段你的日志是：

```text
Constraints(
    minWidth = 0,
    maxWidth = 954,
    minHeight = 0,
    maxHeight = 1784
)
```

这绝不是说：

```text
当前组件宽 = 954
当前组件高 = 1784
```

它的意思更接近：

```text
宽度：允许 0 ～ 954 px
高度：允许 0 ～ 1784 px
```

也就是说，父级交给当前层的是一个**合法区间**。可以把 `Constraints` 看成：

```text
            父级
              │
              │  你最终必须遵守这些限制
              ▼
┌───────────────────────────┐
│ minWidth  ≤ width  ≤ maxWidth
│ minHeight ≤ height ≤ maxHeight
└───────────────────────────┘
              │
              ▼
       当前布局节点
```

所以：

```kotlin
measurable.measure(constraints)
```

不是在告诉 child：你必须是 `954 × 1784`。而是在告诉它：**你可以在这组限制中选择一个合法尺寸。**像 `Text` 这种组件通常会根据自己的文字内容，在 Constraints 允许的范围内得到一个适合自己的尺寸。因此第一阶段才出现：

```text
父级最大允许宽度 = 954
实际 measured child 宽度 = 366
```

没有任何矛盾。

---

#### 3. 一个非常重要的方向：Constraints 向内传，尺寸向外返回

现在可以第一次建立 Layout 最有价值的方向模型。父布局开始测量当前组件：

```text
父
│
│ Constraints
▼
当前层
│
│ Constraints
▼
child
```

这是**向内**。child 测完以后：

```text
child
│
│ Placeable(width, height)
▼
当前层
│
│ 自己的 width / height
▼
父
```

尺寸结果则是**向外返回**。所以布局测量不是一句：“父组件决定子组件多大。” 更准确的是一轮协商：

```text
父级：
“这是我允许你的范围。”

        ↓（Constraints 向内传）

当前层：
“我拿这份规则去测里面的内容。”

        ↓（Constraints 向内传）

child：
“在这份规则下，我测出来是这么大。”

        ↑（测量结果向外返回）

当前层：
“根据 child 的结果，我决定自己最终这么大。”

        ↑（当前层的测量结果再向外返回）

父级获得当前层的测量结果
```

这张图后面学习 `Layout()` 时还会原样使用。

```text
      ↓
```

```text
      ↓
当前 Layout Modifier

```

#### 9. `layout(width, height)` 到底属于 Measure 还是 Placement？

这是你上一次提出的那个非常好的问题，现在正好正式解决。代码是：

```kotlin
layout(
    width = layoutWidth,
    height = layoutHeight
) {
    placeable.placeRelative(x, y)
}
```

这里不要把整个：

```kotlin
layout() { ... }
```

统称为 placement。更准确地拆开：

```kotlin
layout(
    width = layoutWidth,
    height = layoutHeight
)
```

**这个调用发生在 Measure 阶段。**它在声明：当前这一层测量完成，我最终的尺寸就是这么大。而它里面的：

```kotlin
{
    placeable.placeRelative(x, y)
}
```

这个 block 是 **Placement 阶段真正执行的内容**。因此：

```text
Measure 阶段
────────────────

val placeable = measurable.measure(...)

计算 layoutWidth / layoutHeight

layout(
    width,
    height
) {
    // 这里先定义 placement 逻辑
}


之后


Placement 阶段
────────────────

执行 layout { } 中保存的 block

placeable.placeRelative(...)
```

这能修正你之前那个已经非常接近正确答案的直觉：不是：`layout()` 整体属于 placement。而是：**`layout(width, height)` 用来结束当前测量并返回测量结果；它提供的 placement block 会在后面的 Placement 阶段执行。**这个区分后面非常重要。

#### 10. 为什么要把 Measure 和 Placement 分开？

现在先从应用层理解即可。假设当前区域已经确定：

```text
600 × 300
```

里面 child：

```text
400 × 100
```

child 的**尺寸没有任何变化**，但我们可以把它：

```text
放左边
放中间
放右边
```

例如：

```text
┌──────────────────────────────┐
│ child                        │
└──────────────────────────────┘
```

或者：

```text
┌──────────────────────────────┐
│        child                 │
└──────────────────────────────┘
```

或者：

```text
┌──────────────────────────────┐
│                  child       │
└──────────────────────────────┘
```

这些操作根本没有必要重新测量 child。所以 Compose 把：

```text
多大？
```

和：

```text
放哪？
```

明确分成两个阶段。以后某些状态只影响位置时，Compose 甚至可能只重新执行 placement，而不重新走完整 measurement。这个性能机制以后再展开，现在知道这个设计为什么合理就够了。

#### 11. 现在重新看 `constraints.constrainWidth()`

第一阶段我们写：

```kotlin
val layoutWidth = constraints.constrainWidth(placeable.width + extraWidth)
```

当时只说：我想这么大，但必须遵守父级 Constraints。现在可以具体理解了。假设：

```text
constraints:
minWidth = 0
maxWidth = 500
```

我们计算：

```text
placeable.width = 450
extraWidth = 100

期望：550
```

但：

```text
550 > maxWidth 500
```

所以：

```kotlin
constraints.constrainWidth(550)
```

最后只能得到：

```text
500
```

也就是：

```text
我期望多大
    ↓
放进父级允许区间
    ↓
得到合法尺寸
```

同理：

```kotlin
constraints.constrainHeight(...)
```

处理高度。所以这两个 API 的作用非常朴素：**把你计算出来的尺寸夹进 Constraints 的合法范围里。**它不是新的布局阶段，只是帮助你遵守当前测量协议。

```kotlin
Text(
```

站在 Composable 结构角度，我们很容易说：Text 是 child。
但站在当前 `layout` Modifier 的测量角度：

代表的是当前 Modifier **内侧的整个待测量部分**。所以以后课程里如果说：“测量 child” 它通常是为了语言简洁。你脑子里的准确版本应该是：**测量当前布局节点 / Layout Modifier 所负责的内侧 measurable。**这一点会让你第三阶段理解 Modifier 顺序轻松很多。

#### 本阶段应留下的模型

到这里，你应该已经可以把一次测量描述为：

```text
父级
 │
 │  Constraints
 ▼
当前 Layout Modifier
 │
 │  自己决定传什么 Constraints
 ▼
measurable.measure(...)
 │
 ▼
Placeable
(child 测量结果)
 │
 ▼
当前 Layout Modifier
根据 child 结果计算自己的尺寸
 │
 ▼
layout(width, height)
向父级报告自己的测量结果


随后进入 Placement


layout { ... }
 │
 ▼
placeable.placeRelative(...)
```

其中三个尺寸概念必须彻底分开：

```text
Constraints
= 父级允许的尺寸范围

Placeable.width / height
= 内侧内容在指定 Constraints 下测出的尺寸

layout(width, height)
= 当前这一层最终向外报告的尺寸
```

而：


这就是 7.1 最核心的 Measure 心智模型。下一阶段我们不再重复这些概念，而是利用它们进入你上一阶段已经主动发现的问题：**两个 Layout Modifier、`padding`、`background` 等 Modifier 串起来以后，Constraints 和尺寸究竟怎样穿过整条 Modifier 链。**

### 第三阶段：Modifier 链中的布局嵌套——到底是谁在测谁，为什么会出现橙色和蓝色两层

前两个阶段已经建立了单个 `Modifier.layout()` 的基本模型：

```text
Constraints
→ measurable.measure()
→ Placeable
→ layout(width, height)
→ placeRelative()
```

这一阶段开始解决 Modifier 链本身。重点不是再学习一次 `measure()`，而是理解：

```kotlin
Modifier
    .layout { ... }
    .background(...)
    .border(...)
    .padding(...)
```

这些 Modifier 串在一起之后，**谁位于谁的外层、Constraints 怎样向内传播、尺寸怎样向外返回，以及绘制区域为什么会随着 Modifier 顺序发生变化。**这一部分理解之后，前面一直模糊的 `measurable` 和 “child 到底是谁” 也会自然清楚。

---

#### 1. Modifier 链首先要理解成“一层包一层”

看上一阶段的代码：

```kotlin
Text(
    text = "MEASURED CHILD",
    modifier = Modifier
        .layout { measurable, constraints ->
            // ...
        }
        .background(Color(0xFFBBDEFB))
        .border(2.dp, Color(0xFF1976D2))
        .padding(
            horizontal = 16.dp,
            vertical = 12.dp
        )
)
```

不要把它理解成：

```text
先把 layout 完整执行完
→ 再执行 background
→ 再执行 border
→ 再执行 padding
→ 最后执行 Text
```

这种“函数调用流水线”模型对于 Modifier 是不够准确的。更合适的心智模型是：

```text
Layout
└── Background
    └── Border
        └── Padding
            └── Text
```

也就是：**写在前面的 Modifier 位于更外层，写在后面的 Modifier 位于更内层。**概念上可以想象成：

```text
Layout(
    Background(
        Border(
            Padding(
                Text
            )
        )
    )
)
```

这里不是在描述 Compose 内部真实创建了这样的 Kotlin 对象，而是在描述它们之间的**包裹关系**。这个包裹关系比“谁先执行”更重要。

---

#### 2. 现在可以准确解释 `measurable` 了

对于：

```kotlin
Modifier.layout { measurable, constraints ->
    // ...
}
```

`measurable` 不是简单等同于：

```text
Text
```

更准确地说：**它代表当前这个 Layout Modifier 向内所包裹的、等待当前层测量的内容。**在当前代码里，从这个 `layout` 往内看是：

```text
Background
└── Border
    └── Padding
        └── Text
```

因此：

```kotlin
val placeable = measurable.measure(constraints)
```

可以理解为：“让我里面的内容按照这份 Constraints 完成一次测量，然后把测量结果交给我。”

不过这里有一个很重要的精确区别。`background` 和 `border` 虽然位于 Modifier 链中，但它们主要参与 **Draw**，不会像 `padding` 一样改变测量尺寸。因此不要想象成：

```text
Background measure 一次
→ Border measure 一次
→ Padding measure 一次
→ Text measure 一次
```

真正会修改 Measurement 行为的是布局相关 Modifier，例如这里的 `padding`。所以从布局角度可以简化成：

```text
当前 Layout Modifier
        │
        │ measure(...)
        ▼
     Padding
        │
        ▼
       Text
```

`background` 和 `border` 仍然位于这段内侧 Modifier 链中，只是它们不会改变 Constraints 或测量结果。

---

#### 3. Constraints 向内走，测量结果向外回来

现在来看一次完整 Measurement。假设父级传给当前 custom layout：

```text
Constraints(
    minWidth = 0,
    maxWidth = 954,
    minHeight = 0,
    maxHeight = 1784
)
```

当前 Layout Modifier 执行：

```kotlin
val placeable = measurable.measure(constraints)
```

首先发生的是 **Constraints 向内传播**：

```text
Custom Layout
     ↓
   Padding
     ↓
    Text
```

`padding` 收到 Constraints 后，会为自己预留 padding 所需要的空间，再给里面的 `Text` 一份更小的可用范围。例如概念上：

```text
外层最大宽度：954 px

Padding：左右各占一部分空间
↓
Text 可以使用的最大宽度会比 954 px 更小
```

然后 Text 根据收到的 Constraints 测出自己的尺寸。接下来是 **尺寸结果向外返回**：

```text
Text 的测量尺寸
        ↓
Padding 加回左右、上下空间
        ↓
Custom Layout 获得 Placeable
```

因此 Measurement 可以记成两个方向：

```text
Constraints：
外 → 内

Measured Size：
内 → 外
```

这个方向模型后面进入 `Layout()` 时还会继续使用。

---

#### 4. 你的 padding 实验正好证明了这个过程

上一阶段你实际得到：

```text
没有 padding：
measured child = 366 x 63
```

加入：

```kotlin
.padding(
    horizontal = 16.dp,
    vertical = 12.dp
)
```

之后：

```text
measured child = 450 x 127
```

差值为：

```text
宽度：450 - 366 = 84 px
高度：127 - 63 = 64 px
```

而代码中的 padding 是：

```text
水平方向：16dp + 16dp
垂直方向：12dp + 12dp
```

经过当前设备 density （例如典型密度：2.625）转成 px 后，与这个差值吻合。这说明：

```kotlin
val placeable = measurable.measure(constraints)
```

得到的 `placeable` 已经包含了**当前 custom layout 内侧的 padding 所贡献的空间**。所以现在可以把：

```text
measured child
```

理解得更精确一点：它不是“裸 Text 字符串本身的尺寸”，而是当前 Layout Modifier 所测量到的**内侧可测量内容的最终尺寸**。

---

#### 5. custom layout 又在这个结果外面增加了一层空间

假设加入 padding 后：

```text
Placeable = 450 × 127
```

custom layout 又执行：

```kotlin
val extraWidth = 80.dp.roundToPx()
val extraHeight = 56.dp.roundToPx()
```

最终得到：

```text
layout size = 660 × 274
```

此时已经存在两个不同的矩形。第一个：

```text
450 × 127
```

是：

```kotlin
placeable
```

也就是当前 custom layout **内侧内容的测量结果**。第二个：

```text
660 × 274
```

是：

```kotlin
layout(
    width = layoutWidth,
    height = layoutHeight
)
```

决定的当前 custom layout **自己最终向外报告的尺寸**。因此结构已经变成：

```text
Custom Layout：660 × 274

┌────────────────────────────────────┐
│                                    │
│          Placeable                 │
│          450 × 127                 │
│                                    │
└────────────────────────────────────┘
```

然后：

```kotlin
placeable.placeRelative(x, y)
```

把较小的 `Placeable` 放到了较大的 Layout 区域中央。

#### 6. 橙色到底是什么？

现在来看外面的代码：

```kotlin
Box(
    modifier = Modifier
        .background(Color(0xFFFFE0B2))
        .border(2.dp, Color(0xFFF57C00))
) {
    Text(...)
}
```

橙色并不是：

```kotlin
Modifier.layout()
```

画出来的。`Modifier.layout()` 本身不负责画颜色。真正负责橙色的是：

```kotlin
Box.background(...)
```

我们只是故意利用这个 Box，把 **Text 最终向父级报告的整个布局尺寸**显示出来。假设 Text 最外层的 custom layout 最终报告：

```text
660 × 274
```

Box 测量自己的 child 时，就会得到这个尺寸。因此 Box 最终大致也是：

```text
660 × 274
```

于是：

```kotlin
.background(orange)
```

就会把整块区域涂成橙色。所以以后看到这个实验，可以把橙色理解成：**外层父布局对当前 Text 整体占用空间的可视化。**

---

#### 7. 为什么蓝色只出现在中间？

蓝色 Modifier 的位置是：

```kotlin
.layout { ... }
.background(Color(0xFFBBDEFB))
.border(...)
.padding(...)
```

它的层级是：

```text
Custom Layout
└── Background
    └── Border
        └── Padding
            └── Text
```

关键在于：**蓝色 Background 位于 custom Layout 的内侧。**因此 custom layout 执行：

```kotlin
val placeable = measurable.measure(constraints)
```

时，得到的 `placeable` 对应的正是它内侧这部分内容。假设：

```text
Placeable = 450 × 127
```

蓝色 Background 所拥有的布局区域也就是这部分内侧区域。然后 custom layout 自己向外扩大为：

```text
660 × 274
```

于是：

```text
┌───────────────────────────────┐
│          橙色区域              │
│                               │
│      ┌─────────────────┐      │
│      │    蓝色区域      │      │
│      │    Text         │      │
│      └─────────────────┘      │
│                               │
└───────────────────────────────┘
```

外圈新增空间里没有蓝色 Background，所以透出了父 Box 的橙色。这就是你之前截图中两层颜色真正产生的原因。

---

#### 8. 为什么 padding 也属于蓝色区域？

当前顺序是：

```kotlin
.background(blue)
.border(...)
.padding(...)
```

对应：

```text
Background
└── Border
    └── Padding
        └── Text
```

Background 位于 Padding 外面。Padding 测量 Text，然后把：

```text
左 padding
+ Text
+ 右 padding
```

以及：

```text
上 padding
+ Text
+ 下 padding
```

共同组成自己的测量尺寸，再向外返回。Background 位于它外面，因此 Background 得到的区域包含整个：

```text
Padding + Text
```

所以你看到的是：

```text
┌────────────────────────┐
│ 蓝色                    │
│                        │
│    MEASURED CHILD      │
│                        │
└────────────────────────┘
```

padding 留出来的空间本身也是蓝色。这不是因为 padding 自己会画蓝色，而是因为：**Background 位于 Padding 外层，因此 Background 的绘制区域包含了 Padding 所贡献的空间。**

```kotlin
private fun Modifier.extraSpaceLayout(
    label: String
): Modifier {
    return layout { measurable, constraints ->
        log(
            TAG,
            "[$label] incoming = $constraints"
        )

        val placeable = measurable.measure(constraints)

        log(
            TAG,
            "[$label] wrapped content = " +
                    "${placeable.width} x ${placeable.height}"
        )

        val layoutWidth =
            constraints.constrainWidth(
                placeable.width + 80.dp.roundToPx()
            )

        val layoutHeight =
            constraints.constrainHeight(
                placeable.height + 56.dp.roundToPx()
            )

        log(
            TAG,
            "[$label] layout = " +
                    "$layoutWidth x $layoutHeight"
        )

        layout(
            width = layoutWidth,
            height = layoutHeight
        ) {
            val x =
                (layoutWidth - placeable.width) / 2

            val y =
                (layoutHeight - placeable.height) / 2

            placeable.placeRelative(x, y)
        }
    }
}
```

#### 12. C：把 Padding 放到 Background 外面

```kotlin
.border(...)
```

层级：

```text
Custom Layout
└── Padding
    └── Background
        └── Border
            └── Text
```

和 A 对比：

```text
A：

Background
└── Padding
    └── Text
```

而 C：

```text
└── Background
```


的总体尺寸相同，因为它们都存在相同的 padding。但是最终视觉结果不同。这证明：**Modifier 顺序不一定非要改变测量尺寸才能产生差异。即使最终 Layout Size 一样，只要 Draw Modifier 所处的层级不同，视觉结果也可能完全不同。**

#### 13. 为什么不能再用“从左到右执行”解释 Modifier？

现在已经可以正式舍弃：

```text
先执行 layout
→ 再执行 background
→ 再执行 padding
```

这种模型。原因是 Modifier 链会参与不同阶段。对于当前课程最重要的是三类：

```text
Measure
Placement
Draw
```

它们访问同一条 Modifier 链，但处理的事情完全不同。Measurement 中：

```text
Constraints
外 → 内

Measured Size
内 → 外
```

Placement 中：

```text
外层布局
决定内层 Placeable 放在哪里
```

Draw 又处理：

```text
背景
边框
内容
前景
```

等绘制关系。所以以后分析一个 Modifier 顺序问题，第一反应应该是：**这个 Modifier 影响的是 Measure、Placement，还是 Draw？**例如：

```kotlin
.padding(...)
```

首先是 Layout Modifier。它会影响 Measurement。而：

```kotlin
.background(...)
```

主要影响 Draw，不会给组件额外增加布局尺寸。因此它们虽然都写在同一个：

```kotlin
Modifier
```

链上，却承担完全不同的阶段职责。

#### 14. 到这里，child 到底是谁？

现在可以把前面一直使用的 “child” 这个词彻底收紧。对于：

```kotlin
Modifier.layout { measurable, constraints ->
    val placeable = measurable.measure(constraints)
}
```

口语里说：

```text
measure child
```

实际指的是：**当前 Layout Modifier 所包裹的内侧可测量内容。**在：

```kotlin
Modifier
    .layout { ... }
    .background(...)
    .border(...)
    .padding(...)
```

中，链的结构是：

```text
Custom Layout
└── Background
    └── Border
        └── Padding
            └── Text
```

但从 **Measurement** 的角度，真正会参与尺寸变换的是：

```text
Custom Layout
    ↓
Padding
    ↓
Text
```

`background` 和 `border` 位于内侧链中，却不会额外改变测量尺寸。因此：

```kotlin
measurable
```

最好长期理解成：**当前 Layout Modifier 向内包裹的那个可测量对象。**调用：

```kotlin
measurable.measure(...)
```

之后得到：

```kotlin
Placeable
```

则表示：**这部分内侧内容完成当前 Measurement 之后的结果。**当前 Layout Modifier 不需要知道里面到底经过了多少层 Modifier 才得出这个结果。它只需要面对：

```text
Measurable
    ↓ measure()
Placeable
```

这一层抽象。

#### 本阶段应留下的模型

现在重新看：

```kotlin
Modifier
    .layout { ... }
    .background(...)
    .border(...)
    .padding(...)
```

应该首先看到它的包裹关系：

```text
Custom Layout
└── Background
    └── Border
        └── Padding
            └── Text
```

Measurement：

```text
父级 Constraints
        ↓
Custom Layout
        ↓
Padding 修改内部 Constraints
        ↓
Text 完成测量


Text Size
        ↓
Padding 加回自己的空间
        ↓
Custom Layout 得到 Placeable
        ↓
Custom Layout 再决定自己最终多大
```

然后：

```kotlin
layout(width, height) {
    placeable.placeRelative(x, y)
}
```

把较小的内侧 Placeable 摆进当前 Layout 自己的区域。至于绘制：

```text
Draw Modifier 位于 Layout 外侧
→ 可以覆盖 Layout 最终报告的整个区域

Draw Modifier 位于 Layout 内侧
→ 只覆盖 Layout 所包裹的内侧区域
```

于是最开始那个实验中的颜色终于可以完整解释：

```text
橙色
=
外层 Box 的 background
=
用于显示 custom Layout 对父级占据的整个区域


蓝色
=
custom Layout 内侧的 background
=
用于显示 custom Layout 测量得到的 wrapped content 区域
```

到这里，`Modifier.layout()` 最难建立的心智模型已经基本完成：**Modifier 不是简单的函数调用顺序，而是一条具有外层和内层关系的链；Measurement、Placement、Draw 会分别利用这条链完成不同阶段的工作。**下一阶段只需要把 `Modifier.layout()` 收束到真实开发中的使用边界，并连接到下一节真正负责多子项布局的 `Layout()`。

### 第四阶段：`Modifier.layout()` 的实际开发边界——什么时候该用，什么时候不该用

前三个阶段已经解决了 `Modifier.layout()` 的核心运行模型：父级通过 `Constraints` 向内限制尺寸，当前 Layout Modifier 可以决定用什么 Constraints 测量内侧 `Measurable`，得到 `Placeable` 后再决定自己向外报告的尺寸，最后在 Placement 阶段决定内侧内容的位置。

这一阶段不再增加复杂实验，而是解决真实开发中的选择问题：**什么时候应该自己写 `Modifier.layout()`，什么时候应该优先使用现成 Modifier，以及什么时候需求已经超出了 `Modifier.layout()` 的职责。**

---

#### 1. `Modifier.layout()` 的本质：改造“一个内容”的布局行为

先把它的能力压缩成三个动作：

```kotlin
Modifier.layout { measurable, constraints ->
    val placeable = measurable.measure(...)

    layout(width, height) {
        placeable.placeRelative(x, y)
    }
}
```

它允许当前 Modifier：

```text
① 决定用什么 Constraints 测量内侧内容

② 根据 Placeable 决定自己向父级报告多大

③ 决定这个 Placeable 在自己的区域里放在哪里
```

这里始终只有：

```kotlin
measurable: Measurable
```

一个待测量对象。这也是 `Modifier.layout()` 最重要的职责边界：**它适合改造某一个 Composable 已有内容的测量与摆放行为。**例如：

```text
让内容只能按照某种特殊宽度测量
根据 child 的尺寸再增加额外空间
根据测量结果计算特殊偏移
把 child 放到一个非常规位置
```

这些都属于它擅长的问题。

---

#### 2. 能用 `padding()` 时，不要自己写 `layout()`

例如需求只是：内容四周留 16dp。直接：

```kotlin
Modifier.padding(16.dp)
```

即可。没有必要自己写：

```kotlin
Modifier.layout { measurable, constraints ->
    // 减 Constraints
    // measure
    // 再把 padding 加回来
    // 再 place
}
```

虽然从这一节学到的机制上看，完全可以自己实现类似行为，但这不是实际项目里的合理选择。前面的学习价值在于：**现在能够解释 `padding()` 为什么会影响 Measurement。**而不是以后每次 padding 都自己造一个 Layout Modifier。

---

#### 3. `padding()` 和 `offset()` 解决的是两个不同问题

这两个 Modifier 日常非常容易同时出现，但经过 7.1 后应该能够准确区分。`padding()` 会参与 Measurement。例如：

```kotlin
Modifier.padding(16.dp)
```

概念上会发生：

```text
父级 Constraints
      ↓
padding 为自己保留空间
      ↓
把更小的 Constraints 给内侧内容
      ↓
child 测量
      ↓
padding 把自己的空间加回来
      ↓
向外报告最终尺寸
```

因此 padding 会影响整个布局尺寸。而：

```kotlin
Modifier.offset(
    x = 20.dp,
    y = 10.dp
)
```

核心目的不是重新定义 child 应该有多大，而是：**在已经确定尺寸之后改变它的 placement。**因此可以先建立这样的选择模型：

```text
希望组件真的占据更多 / 更少布局空间
        ↓
padding / size / 自定义 layout 等


尺寸基本不变，只想把它放到另一个位置
        ↓
offset
```

这也是 Measure 和 Placement 分开的实际价值：很多位置变化根本不需要改变测量结果。

---

#### 4. `size()` 解决的是“我要多大”，而不是完整重写布局协议

例如：

```kotlin
Modifier.size(120.dp)
```

它表达的需求非常直接：在父级 Constraints 允许的情况下，希望当前内容按照这个目标尺寸进行布局。如果只是：

```text
固定宽度
固定高度
限定最大宽度
填满父级
```

通常首先考虑：

```kotlin
.width(...)
.height(...)
.size(...)
.fillMaxWidth()
.fillMaxSize()
.widthIn(...)
.heightIn(...)
.sizeIn(...)
```

而不是直接进入：

```kotlin
Modifier.layout { ... }
```

`Modifier.layout()` 真正有价值的场景，是尺寸决策已经不能用一个简单参数表达，而需要：

```text
先测 child
    ↓
读取它的测量结果
    ↓
根据这个结果计算自己的尺寸或位置
```

例如：

```text
自己的宽度 = child.width + 某个动态空间

child 的 x = (自己的宽度 - child.width) / 2
```

这时自定义布局逻辑才开始真正有必要。

---

#### 5. 一个实用判断：布局规则是否依赖 `Placeable`

可以用这个问题快速判断是否值得考虑 `Modifier.layout()`：**我的布局决策，需要先知道 child 实际测量出来多大吗？**如果答案是否定的，例如：

```text
永远 padding 16dp
永远 offset 20dp
永远宽 200dp
```

通常已经有现成 Modifier。如果答案是：“我要先 measure，知道 child 最终是 `w × h`，然后才能算我自己的尺寸或位置。” 例如：

```kotlin
val placeable = measurable.measure(...)

val width = placeable.width + ...
val height = f(placeable.height)

val x = g(placeable.width)
```

这就进入了 `Modifier.layout()` 真正有价值的区域。它的优势不是“比普通 Modifier 更高级”，而是：**允许布局策略依赖真实的测量结果。**

---

#### 6. `place()` 与 `placeRelative()` 的选择

前三阶段一直使用：

```kotlin
placeable.placeRelative(x, y)
```

这里需要补齐一个实际开发边界。除了：

```kotlin
placeRelative(x, y)
```

还可以看到：

```kotlin
place(x, y)
```

两者最大的区别出现在横向坐标和 RTL 布局方向。`placeRelative()` 的横向位置按照当前 `LayoutDirection` 解释。例如：

```kotlin
placeable.placeRelative(
    x = 20,
    y = 0
)
```

在 LTR 环境中可以理解成：从左侧方向偏移 20px；而在 RTL 环境中会按照相对布局方向处理。因此对于：

```text
Start
End
```

这种具有语言方向含义的位置，通常优先：

```kotlin
placeRelative(...)
```

如果需求明确是物理坐标：

```text
永远距离绝对左边 20px
```

则：

```kotlin
place(...)
```

更加符合语义。这和你之前制作 `AdaptiveBubbleShape` 时处理 Start / End 镜像，本质上属于同一个国际化问题：**“左/右”和“Start/End”不是同一个概念。**这里掌握选择边界即可，不需要继续展开 Placement API 全家桶。

---

#### 7. `Modifier.layout()` 什么时候开始不够用了？

现在看一个结构：

```kotlin
Text(
    modifier = Modifier.layout { measurable, constraints ->
        ...
    }
)
```

这里只有：

```kotlin
measurable
```

一个。它非常适合：

```text
当前内容
    ↓
我修改它的布局方式
```

但是假设开始需要这样的东西：

```text
┌─────────────────────────────┐
│ Icon    Title        Button │
│                             │
│         Content             │
└─────────────────────────────┘
```

现在问题已经变成：

```text
我要测 Icon
我要测 Title
我要测 Button
我要测 Content

然后根据它们之间的尺寸关系
决定整个容器多大

最后分别计算四个组件的位置
```

这已经不是：“修改一个 child 的布局行为。” 而是：**“我就是这个父布局，我要负责多个 child。”** 这时应该进入下一节：

```kotlin
Layout(...)
```

而不是尝试继续用 `Modifier.layout()` 硬做。所以可以形成非常清晰的边界：

```text
单个已有内容
需要改变自己的测量 / 尺寸 / placement
        ↓
Modifier.layout()


多个 child
需要定义它们之间的测量与摆放规则
        ↓
Layout()
```

这就是 7.1 与 7.2 最重要的分界线。

#### 8. 表层 API 透视：为什么 `Modifier.layout()` 能完成这一整套工作

不进入 `LayoutModifierNode` 源码，只看公开 API 的结构。`Modifier.layout()` 的核心签名可以简化理解为：

```kotlin
fun Modifier.layout(
    measure: MeasureScope.(
        measurable: Measurable,
        constraints: Constraints
    ) -> MeasureResult
): Modifier
```

三个关键角色现在都已经认识。

`Measurable`：

```text
等待当前层测量的内侧内容
```

`Constraints`：

```text
当前层收到的尺寸约束
```

`MeasureResult`：

```text
当前层完成 Measurement 后，
向外提供的布局结果
```

而代码：

```kotlin
layout(width, height) {
    placeable.placeRelative(x, y)
}
```

负责创建这个测量结果。概念上可以看成：

```text
Modifier.layout
        │
        ▼
MeasureScope
        │
        ├── Measurable
        ├── Constraints
        │
        ▼
measure(...)
        │
        ▼
Placeable
        │
        ▼
layout(width, height) { placement }
        │
        ▼
MeasureResult
```

这也是为什么 `Modifier.layout()` 一个 lambda 就能够同时描述：

```text
Measurement
+
Placement
```

公开 API 已经把当前应用层需要的布局协议完整暴露出来。这里就没有必要继续追 `LayoutModifierNode`、Coordinator 或 `LayoutNode`。这些内容在后面的章节有真正需要的时候再下钻。官方自定义布局文档可以留作以后查阅：[Custom layouts](https://developer.android.com/develop/ui/compose/layouts/custom)。

#### 9. 7.1 应达到的最终选择模型

以后真实开发遇到位置或尺寸需求，可以按照这个顺序判断：

```text
现成 Modifier 能不能表达？
        │
        ├── padding()
        ├── size / width / height
        ├── sizeIn()
        ├── offset()
        └── 其他标准 Modifier
        │
        ▼
       能
        │
        └── 直接使用


       不能
        │
        ▼
是否只是修改一个已有内容的
Measure / Size / Placement？
        │
        ├── 是 → Modifier.layout()
        │
        └── 否
             │
             ▼
是否需要自己管理多个 child？
             │
             └── 是 → Layout()
```

因此，`Modifier.layout()` 不应该成为日常布局的默认工具。它的位置更准确地说是：**标准 Layout Modifier 无法表达需求时，用来对单个内容的 Measure / Size / Placement 协议进行定制。**

到这里，7.1 所需要的应用层深度已经足够。继续研究 Node、Coordinator 或 Modifier 内部布局实现，对当前阶段的真实开发收益已经明显下降，可以停止下钻。

下一节 `7.2 Layout` 会在完全相同的：

```text
Constraints
→ Measure
→ Placeable
→ Size
→ Placement
```

心智模型上继续前进，但这一次不再只处理一个 `Measurable`，而是开始真正承担**多个子组件的父布局职责**。
