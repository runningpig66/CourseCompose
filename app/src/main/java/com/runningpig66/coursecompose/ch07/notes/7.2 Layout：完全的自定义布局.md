### 第一阶段：第一次成为“父布局”——建立 `Layout()` 的完整主链路

7.1 中使用 `Modifier.layout()` 时，视角始终围绕**一个被 Modifier 包裹的组件**：拿到一个 `Measurable`，测量得到一个 `Placeable`，决定当前这一层的尺寸，然后把它放进去。

`Layout()` 把这个模型提升了一层。现在不再是“修改一个孩子怎么布局”，而是**自己成为父布局**：接收多个直接子项 → 测量这些子项 → 根据测量结果决定自己的尺寸 → 再决定每个子项在自己内部的位置。

Compose 官方对自定义布局的描述也是这三步：**measure children → decide own size → place children**；当需要手动布局多个 Composable 时，使用的就是 `Layout`。[Android Developers](https://developer.android.com/develop/ui/compose/layouts/custom?authuser=4&utm_source=chatgpt.com)

这一阶段暂时不研究“应该给 child 什么 Constraints”。代码里先采用最直接的测量方式，把完整主链真正跑通；约束传播是下一阶段的核心。

#### 1. 第一份完整实验：`Sec0702A_BasicCustomLayout.kt`

先直接运行下面这个文件。不要给 `BasicVerticalLayout` 额外添加 `fillMaxWidth()`、`fillMaxSize()` 等尺寸 Modifier，我们下一阶段会专门研究它们为什么会影响测量结果。

```kotlin
private const val TAG = "Sec0702A"

                .fillMaxSize()
                .padding(innerPadding)
                .padding(24.dp),
            verticalArrangement = Arrangement.spacedBy(24.dp)
        ) {
            Text(
                text = "Layout() basic experiment",
                style = MaterialTheme.typography.titleMedium
            )

            BasicVerticalLayout(
                modifier = Modifier.border(
                    width = 2.dp,
                    color = MaterialTheme.colorScheme.outline
                )
            ) {
                Box(
                    modifier = Modifier
                        .width(120.dp)
                        .height(24.dp)
                        .background(MaterialTheme.colorScheme.primaryContainer),
                    contentAlignment = Alignment.Center
                ) {
                    Text("A")
                }

                Box(
                    modifier = Modifier
                        .width(200.dp)
                        .height(96.dp)
                        .background(MaterialTheme.colorScheme.secondaryContainer),
                    contentAlignment = Alignment.Center
                ) {
                    Text("B")
                }

                Box(
                    modifier = Modifier
                        .width(150.dp)
                        .height(48.dp)
                        .background(MaterialTheme.colorScheme.tertiaryContainer),
                    contentAlignment = Alignment.Center
                ) {
                    Text("C")
                }
            }
        }
    }

@Composable
private fun BasicVerticalLayout(
    modifier: Modifier = Modifier,
    content: @Composable () -> Unit
) {
    Layout(
        modifier = modifier,
        content = content
    ) { measurables, constraints ->
        log(
            TAG,
            "measure start: childCount=" +
                    "${measurables.size}, constraints=$constraints"
        )

        val placeables = measurables.mapIndexed { index, measurable ->
            val placeable = measurable.measure(constraints)

            log(
                TAG,
                "child[$index] measured: " +
                        "${placeable.width} x ${placeable.height}"
            )

            placeable
        }

        val desiredWidth = placeables.maxOfOrNull { it.width } ?: 0
        val desiredHeight = placeables.sumOf { it.height }

        val layoutWidth = constraints.constrainWidth(desiredWidth)
        val layoutHeight = constraints.constrainHeight(desiredHeight)

        log(
            TAG,
            "parent size: $layoutWidth x $layoutHeight"
        )

        layout(
            width = layoutWidth,
            height = layoutHeight
        ) {
            var y = 0

            placeables.forEachIndexed { index, placeable ->
                log(
                    TAG,
                    "place child[$index]: x=0, y=$y"
                )

                placeable.placeRelative(0, y)

                y += placeable.height
            }
        }
    }
}
```

#### 2. `content` 到底给了 `Layout()` 什么

第一次看到：

```
Layout(
    modifier = modifier,
    content = content
) { measurables, constraints ->
```

最值得弄清楚的是 `measurables`。在本例中，`content` 中直接放入了三个 `Box`：

```
BasicVerticalLayout {
    Box { ... }
    Box { ... }
    Box { ... }
}
```

这三个 `Box` 都形成了 `BasicVerticalLayout` 的直接可测量子节点，因此进入 measure block 时：

```
measurables.size == 3
```

Logcat 第一行应该能直接证明这一点：

```
measure start: childCount=3, ...
```

这里不要把 `Measurable` 理解成“已经测好尺寸的组件”。它更接近：**这个 child 现在可以被父布局拿去测量。**此时父布局还不知道：

```
A 最后到底多宽？
B 最后到底多高？
C 在当前 Constraints 下还能不能保持自己声明的尺寸？
```

因此第一步必须调用：

```
measurable.measure(constraints)
```

返回：

```
Placeable
```

7.1 已经见过这个对象，所以这里只需要把数量关系升级一下：

```
Modifier.layout()

1 Measurable
    ↓ measure()
1 Placeable
```

现在变成：

```
Layout()

List<Measurable>
    ↓ 分别 measure()
List<Placeable>
```

**从这里开始，自定义父布局实际上就是在操作一组 `Placeable`。**

------

#### 3. 为什么一定要先 measure child

看这里：

```
val placeables = measurables.mapIndexed { index, measurable ->
    measurable.measure(constraints)
}
```

测量结束以后，我们才拥有：

```
placeable.width
placeable.height
```

这些尺寸已经是像素值，而且是 child 在当前约束条件下真正测出来的结果。于是父布局才能继续计算：

```
val desiredWidth = placeables.maxOfOrNull { it.width } ?: 0
val desiredHeight = placeables.sumOf { it.height }
```

这个算法的含义非常明确。因为三个孩子要竖着排列，所以父布局的理想宽度取：

```
max(A.width, B.width, C.width)
```

而父布局的理想高度取：

```
A.height + B.height + C.height
```

注意这里已经出现了 `Layout()` 与普通“设置尺寸”的根本区别。父布局并不是预先知道：“我应该是 200dp × 176dp。” 而是：“我先让孩子们按照我的规则完成测量，然后根据他们真正测出来的尺寸计算自己应该多大。” 因此一般的父子布局关系是：

```
父节点收到 Constraints
        ↓
父节点测量 children
        ↓
获得 Placeable.width / height
        ↓
根据 children 的结果计算自己的尺寸
```

这就是为什么自定义布局的顺序天然是：**测量 children → 决定 parent size。**

------

#### 4. `constraints.constrainWidth()` 在这里承担什么角色

我们首先算出了理想尺寸：

```
val desiredWidth = placeables.maxOfOrNull { it.width } ?: 0
val desiredHeight = placeables.sumOf { it.height }
```

但最后没有直接：

```
layout(desiredWidth, desiredHeight)
```

而是经过：

```
val layoutWidth = constraints.constrainWidth(desiredWidth)
val layoutHeight = constraints.constrainHeight(desiredHeight)
```

原因和 7.1 完全一致：`Layout()` 自己也是别人家的 child。它不能因为自己内部算出了某个理想尺寸，就无视上层 parent 给它的 `Constraints`。因此这里存在两个不同概念：

```
desiredWidth / desiredHeight
        ↓
布局算法认为自己想要多大

layoutWidth / layoutHeight
        ↓
在 incoming Constraints 下最终允许上报多大
```

这一阶段只需要保持这个区别。至于接下来那个更难的问题——如果父布局最终只能这么大，它当初是不是就不应该把收到的 `constraints` 原样给所有 child？这正是第二阶段要正式解决的问题，现在不要提前展开。

------

#### 5. `layout()`：父布局正式宣布“我有多大”

完成测量和尺寸计算以后：

```
layout(
    width = layoutWidth,
    height = layoutHeight
) {
    ...
}
```

这里的两个数字描述的是：**`BasicVerticalLayout` 自己的尺寸。**不是 A 的尺寸，不是 B 的尺寸，也不是整个屏幕的尺寸。这也是为什么 UI 上给它加的：

```
Modifier.border(...)
```

最终会围住整个 A + B + C。`Layout()` 本身就是 UI 树中的一个布局元素。它有自己的：

```
width
height
position
Modifier
children
```

因此可以把当前结构理解成：

```
Column
|── Text
└── BasicVerticalLayout
    ├── Box A
    ├── Box B
    └── Box C
```

`Column` 负责摆放 Text 和 `BasicVerticalLayout`。而 `BasicVerticalLayout` 又负责摆放 A、B、C。这就是布局树一层一层工作的方式。

------

#### 6. placement：位置坐标属于父布局自己的坐标系

测量阶段结束后，我们已经知道每个 child 多大，也知道父布局自己多大。接下来才是 placement：

```
var y = 0

placeables.forEach { placeable ->
    placeable.placeRelative(
        x = 0,
        y = y
    )

    y += placeable.height
}
```

第一项：

```
A → (0, 0)
```

然后：

```
y = A.height
```

第二项：

```
B → (0, A.height)
```

然后：

```
y = A.height + B.height
```

第三项：

```
C → (0, A.height + B.height)
```

这里的 `(x, y)` 都不是屏幕坐标。它们描述的是：**child 相对于 `BasicVerticalLayout` 左上角的位置。**因此如果整个 `BasicVerticalLayout` 被外面的 `Column` 放到屏幕 `(40, 200)`，我们的代码仍然只需要写：

```
placeable.placeRelative(0, y)
```

父布局不需要知道自己的全局屏幕位置。每一层只处理**自己的局部坐标系**。这个原则以后写日历、时间轴、拖拽布局时会一直存在。

#### 7. 现在看 Logcat，应该验证什么

不要重点盯具体像素数字，因为 `120.dp` 最终是多少 px 取决于设备 density。真正需要验证的是几个关系。首先：

```
childCount=3
```

说明父布局确实拿到了三个直接 children。然后三个 child 分别产生三个实际测量结果：

```
child[0] measured: ...
child[1] measured: ...
child[2] measured: ...
```

接着观察父宽度：

```
parent width = 三个 child width 中最大的一个
```

父高度：

```
parent height = 三个 child height 之和
```

最后 placement 应该类似：

```
place child[0]: x=0, y=0
place child[1]: x=0, y = child[0].height
place child[2]: x=0, y = child[0].height + child[1].height
```

如果这四个关系全部能从日志和 UI 同时观察出来，那么 `Layout()` 第一条完整运行链已经建立起来了。

#### 8. 做一次非常简单但有价值的修改

把 B：

```
.width(200.dp)
.height(72.dp)
```

改成例如：

```
.width(260.dp)
.height(100.dp)
```

重新运行。不要只是看“B 变大了”。重点观察三个连锁变化。B 的测量结果首先变化：

```
child[1].width ↑
child[1].height ↑
```

因为 B 现在成为最宽 child，所以：

```
BasicVerticalLayout.width ↑
```

因为父高度是三个 child 高度之和，所以：

```
BasicVerticalLayout.height ↑
```

最后，因为 C 位于 B 后面：

```
C 的 y 坐标 ↓
```

准确说是数值变大、视觉位置向下移动。这个实验说明一个很重要的关系：

```
child measurement
      ↓
parent size calculation
      ↓
child placement
```

三者不是三段互不相关的代码。**前面的测量结果就是后面父尺寸和位置算法的数据来源。**

#### 10. `Layout()` 与 7.1 的对应关系

现在可以把两个 API 放到同一个模型中，而不需要重新学习一套东西。

7.1：

```
Modifier.layout { measurable, constraints ->
    val placeable = measurable.measure(constraints)

    layout(...) {
        placeable.placeRelative(...)
    }
}
```

7.2：

```
Layout(...) { measurables, constraints ->
    val placeables = measurables.map {
        it.measure(constraints)
    }

    layout(...) {
        placeables.forEach {
            it.placeRelative(...)
        }
    }
}
```

最核心的变化只有两个。

第一，原来的：

```
Measurable
```

变成：

```
List<Measurable>
```

第二，你的身份发生了变化：

```
Modifier.layout()
修改一个已有组件的布局行为
```

变成：

```
Layout()
自己就是父布局，负责一组 children
```

所以 7.1 建立的：

```
Constraints
→ measure
→ Placeable
→ layout size
→ placement
```

没有被推翻。7.2 真正做的是把它升级为：

```
Constraints
→ measure child 0
→ measure child 1
→ measure child 2
→ 多个 Placeable
→ 根据全部测量结果计算 parent size
→ layout(...)
→ 分别 placement
```

这就是本阶段需要牢固建立的主模型。

#### 表层 API 透视

当前常用写法：

```
Layout(
    content = content,
    modifier = modifier
) { measurables, constraints ->
    ...
}
```

最后这个 lambda 本质上承担的是该 `Layout` 的测量策略。官方 API 将完整形式抽象为 `MeasurePolicy`；我们目前使用的写法让普通自定义布局不需要先手写一个 `MeasurePolicy` 对象。`MeasurePolicy` 更完整的能力还涉及 intrinsic measurement，这属于 7.3，现在没有必要展开。[Android Developers](https://developer.android.com/reference/kotlin/androidx/compose/ui/layout/package-summary?authuser=0&utm_source=chatgpt.com)

当前只需要建立这组对应关系：

```
content
→ 提供 children

modifier
→ 修饰这个 Layout 自己

measurables
→ 当前父布局可测量的直接 children

constraints
→ 当前 Layout 从自己的 parent 收到的约束

measure(...)
→ child 从 Measurable 变成 Placeable

layout(width, height)
→ 当前 Layout 决定自己的最终尺寸

placeRelative(...)
→ 当前 Layout 决定每个 child 的局部位置
```

到这里第一阶段已经完成。下一阶段真正困难的地方不再是 `Layout()` 的语法，而是一个父布局最核心的职责：**收到父级 `Constraints` 之后，究竟应该怎样为不同 children 设计它们各自的 `Constraints`。**那一步才会让我们从“会写一个自制 Column”进入“真正会写自定义布局算法”。

### 第二阶段：父约束不等于子约束——真正开始设计 `Constraints`

第一阶段已经建立了 `Layout()` 的完整主链：

```text
多个 Measurable
→ measure()
→ 多个 Placeable
→ 计算父布局尺寸
→ placement
```

但第一阶段有一处是故意写得最简单的：

```kotlin
measurable.measure(constraints)
```

也就是把当前 `Layout` 从自己父节点收到的 `constraints`，原封不动地交给每一个 child。这段代码**并不天然错误**。如果这恰好符合当前父布局的布局规则，它完全可以这样写。真正的问题在于：`constraints` 描述的是“当前 Layout 自己允许多大”，并不自动等价于“每一个 child 也应该允许这么大”。

从这一阶段开始，写自定义布局真正困难的部分出现了：**父布局需要主动设计每个 child 的测量约束。**

---

#### 1. 先让问题明确暴露出来

这次我们故意给自定义布局一个非常明确的固定空间：

```text
280dp × 140dp
```

三个孩子仍然分别想要：

```text
A = 120 × 24
B = 200 × 96
C = 150 × 48
```

它们原本总高度是：

```text
24 + 96 + 48 = 168dp
```

已经超过父布局允许的 `140dp`。这正好可以观察父布局究竟应该怎样处理自己的空间预算。

创建：`Sec0702B_ChildConstraints.kt`

```kotlin

@Composable
private fun NaiveVerticalLayout(
    modifier: Modifier = Modifier,
    content: @Composable () -> Unit
) {
    Layout(
        modifier = modifier,
        content = content
    ) { measurables, constraints ->

        log(
            TAG,
            "[Naive] incoming = $constraints"
        )

        val placeables = measurables.mapIndexed { index, measurable ->

            log(
                TAG,
                "[Naive] child[$index] constraints = $constraints"
            )

            val placeable = measurable.measure(constraints)

            log(
                TAG,
                "[Naive] child[$index] result = " +
                    "${placeable.width} x ${placeable.height}"
            )

            placeable
        }

        val desiredWidth = placeables.maxOfOrNull { it.width } ?: 0
        val desiredHeight = placeables.sumOf { it.height }

        val layoutWidth = constraints.constrainWidth(desiredWidth)
        val layoutHeight = constraints.constrainHeight(desiredHeight)

        log(
            TAG,
            "[Naive] desired = $desiredWidth x $desiredHeight, " +
                "final = $layoutWidth x $layoutHeight"
        )

        layout(
            width = layoutWidth,
            height = layoutHeight
        ) {
            var y = 0

            placeables.forEach { placeable ->
                placeable.placeRelative(
                    x = 0,
                    y = y
                )

                y += placeable.height
            }
        }
    }
}

@Composable
private fun RemainingHeightVerticalLayout(
    modifier: Modifier = Modifier,
    content: @Composable () -> Unit
) {
    Layout(
        modifier = modifier,
        content = content
    ) { measurables, constraints ->

        log(
            TAG,
            "[Budget] incoming = $constraints"
        )

        var remainingHeight = constraints.maxHeight

        val placeables = measurables.mapIndexed { index, measurable ->

            val childMaxHeight =
                if (constraints.hasBoundedHeight) {
                    remainingHeight
                } else {
                    Constraints.Infinity
                }

            val childConstraints = constraints.copy(
                minWidth = 0,
                minHeight = 0,
                maxHeight = childMaxHeight
            )

            log(
                TAG,
                "[Budget] child[$index] constraints = $childConstraints"
            )

            val placeable =
                measurable.measure(childConstraints)

            log(
                TAG,
                "[Budget] child[$index] result = " +
                    "${placeable.width} x ${placeable.height}"
            )

            if (constraints.hasBoundedHeight) {
                remainingHeight =
                    (remainingHeight - placeable.height)
                        .coerceAtLeast(0)
            }

            placeable
        }

        val desiredWidth =
            placeables.maxOfOrNull { it.width } ?: 0

        val desiredHeight =
            placeables.sumOf { it.height }

        val layoutWidth =
            constraints.constrainWidth(desiredWidth)

        val layoutHeight =
            constraints.constrainHeight(desiredHeight)

        log(
            TAG,
            "[Budget] desired = $desiredWidth x $desiredHeight, " +
                "final = $layoutWidth x $layoutHeight"
        )

        layout(
            width = layoutWidth,
            height = layoutHeight
        ) {
            var y = 0

            placeables.forEach { placeable ->
                placeable.placeRelative(
                    x = 0,
                    y = y
                )

                y += placeable.height
            }
        }
    }
}
```

#### 3. 一个最关键的区别：`Constraints` 属于谁

这里要把一个关系彻底分开。当前 `Layout` 收到：

```kotlin
{ measurables, constraints ->
```

这里的 `constraints` 表示：**我的 parent 允许“我这个 Layout”有多大。**例如：

```text
当前 Layout：
必须 280 × 140
```

但现在轮到当前 Layout 测量 A 时，当前 Layout 已经成为了 **A 的 parent**。于是它必须回答另一个问题：**我允许 A 有多大？**这两份 Constraints 完全可以不同。关系实际上是：

```text
更外层 parent
      │
      │ Constraints A
      ▼
Current Layout
      │
      │ 自己设计 Constraints B
      ▼
Child
```

所以：

```text
incoming Constraints
```

和：

```text
child Constraints
```

是两个不同角色。这是第二阶段最重要的心智模型。

---

#### 4. 为什么首先要把 `minWidth` 和 `minHeight` 放掉

看正确版本：

```kotlin
val childConstraints = constraints.copy(
    minWidth = 0,
    minHeight = 0,
    maxHeight = childMaxHeight
)
```

当前父布局自己的 incoming constraints 是：

```text
width  = 280
height = 140
```

但是我们没有要求：

```text
每个 child 也必须至少 280 × 140
```

所以先把：

```text
minWidth
minHeight
```

降为：

```text
0
```

此时第一项 A 收到的约束大致变成：

```text
0 <= width  <= 280
0 <= height <= 140
```

A 自己想要：

```text
120 × 24
```

完全合法，于是：

```text
A = 120 × 24
```

这时你会第一次真正看到一个非常重要的父子关系：

```text
Parent 自己必须 280 宽
```

完全不代表：

```text
Child 也必须 280 宽
```

最终完全可以出现：

```text
Parent width = 280

A width = 120
B width = 200
C width = 150
```

剩下的空间怎么处理，是 placement 的问题，例如以后可以左对齐、居中、右对齐。**父布局尺寸和 child 尺寸本来就不是同一个东西。**

---

#### 5. 现在回收你上一阶段自己想到的问题

你当时问：测完第一个 child 后，是不是应该把它占掉的尺寸从 incoming Constraints 中剪掉，再传给下一个 child？答案是：**你的方向是对的，但不能机械地“从整个 Constraints 里减掉 child”。**

首先必须问：这个父布局的布局规则是什么？我们现在实现的是一个**竖直排列，并且所有 children 共同分享有限高度预算**的 Layout。所以真正被兄弟之间连续消耗的是：

```text
height
```

而不是 width。开始时：

```text
remainingHeight = 140
```

测量 A：

```text
A.height = 24
```

剩余：

```text
140 - 24 = 116
```

于是 B 收到：

```text
maxHeight = 116
```

B 想要：

```text
96
```

可以满足。所以：

```text
B.height = 96
```

继续扣掉：

```text
116 - 96 = 20
```

C 原本想要：

```text
48
```

但现在只剩：

```text
maxHeight = 20
```

所以最终：

```text
C.height = 20
```

整个结果正好变成：

```text
A = 24
B = 96
C = 20
----------------
总高度 = 140
```

所以你的直觉可以精确修正成：**如果多个 siblings 在某个轴上共享一份有限空间预算，那么前面 child 的实际测量结果，可以用于计算后面 child 在该轴上的剩余 `max` Constraint。**这就是：

```kotlin
remainingHeight = remainingHeight - placeable.height
```

真正表达的东西。

---

#### 6. 为什么 width 没有跟着减

这是理解 `Constraints` 设计特别重要的一点。

三个 children 是：

```text
A
B
C
```

竖着排列：

```text
┌──────────────┐
│ A            │
│ B            │
│ C            │
└──────────────┘
```

A 占了一部分高度之后，B 的可用高度确实减少了。但是 A 宽 120，并不意味着：

```text
B 只能使用 280 - 120 = 160
```

因为 A 和 B 并不是横向竞争同一段空间。它们都可以独立使用父布局完整的：

```text
maxWidth = 280
```

所以我们的算法是：

```text
maxWidth
一直保持 280

maxHeight
140
 ↓
116
 ↓
20
```

如果将来写一个横向布局，逻辑才会反过来：

```text
remainingWidth
```

不断减少，而每个 child 仍然可以拥有完整的最大高度。所以不要记：“测完一个 child 就从 Constraints 减掉它。” 应该记：**Constraints 怎样变化，由 parent 的空间分配算法决定。**这句话才具有普适性。

---

#### 7. `min` 和 `max` 在父子传播中的职责完全不同

目前的代码：

```kotlin
constraints.copy(
    minWidth = 0,
    minHeight = 0,
    maxHeight = childMaxHeight
)
```

其实同时做了两件性质不同的事情。第一件事：

```text
minWidth = 0
minHeight = 0
```

意思是：父布局不把“自己被要求至少多大”强加给 child。第二件事：

```text
maxHeight = remainingHeight
```

意思是：父布局主动限制 child 最多还能使用多少公共高度。因此可以先建立这个很有用的直觉：

```text
min 更容易表达“至少必须占多少”
max 更容易表达“最多允许使用多少”
```

而对于我们这个简单纵向 Layout：

```text
Parent incoming min
      ↓
主要约束 Parent 自己

Parent incoming max
      ↓
可以成为设计 child 上限的重要依据
```

当然，这不是所有 Layout 必须遵循的死规则。某些父布局确实会把自己的 minimum requirement 继续传给 child；是否这样做仍然取决于布局语义。

---

#### 8. Parent 最终仍然必须遵守自己的 Constraints

不要因为我们现在重新设计了 child constraints，就忘掉第一阶段的另一半。正确版本测完以后：

```text
A = 120 × 24
B = 200 × 96
C = 150 × 20
```

父布局理想尺寸为：

```text
desiredWidth = 200
desiredHeight = 140
```

但是 incoming constraints 要求父布局：

```text
width = 280
height = 140
```

因此：

```kotlin
val layoutWidth = constraints.constrainWidth(desiredWidth)
val layoutHeight = constraints.constrainHeight(desiredHeight)
```

最终得到：

```text
layoutWidth  = 280
layoutHeight = 140
```

这说明一次完整的自定义父布局测量实际上存在**两个方向**：

```text
          incoming Constraints
                 │
                 ▼
             Parent
            /   |   \
           /    |    \
 child Constraints  child Constraints
        ↓        ↓        ↓
        A        B        C
        │        │        │
        └── Placeables ───┘
                 │
                 ▼
          Parent desired size
                 │
                 ▼
      incoming Constraints 再次约束
                 │
                 ▼
          Parent final size
```

上面是约束向下传播。下面是测量结果向上汇总。这是 `Layout()` 最值得建立的整体心智模型之一。

其他代码完全不要动。现在 children 总共只想要：

空白。这非常值得观察，因为它再次证明：

```text
children 总共需要 168
```

```text
parent 最终必须占 220
```

#### 10. `hasBoundedHeight` 为什么出现在代码里

代码中还有这一小段：

```kotlin
val childMaxHeight =
    if (constraints.hasBoundedHeight) {
        remainingHeight
    } else {
        Constraints.Infinity
    }
```

这里先只建立一个应用层认识。如果：

```kotlin
constraints.hasBoundedHeight
```

为 `true`，说明父布局确实有一个有限的：

```text
maxHeight
```

例如：

```text
140
220
800
```

那么：

```text
remainingHeight
```

这个概念才真正有意义。但有些布局环境可能得到：

```text
maxHeight = Infinity
```

意思是：这个方向没有一个有限的最大高度预算。此时就不存在：

```text
一共只有 140，A 用掉 24，还剩 116
```

这种数学模型。因此我们保留：

```text
Constraints.Infinity
```

不做有限预算扣减。这里暂时不要扩展到滚动容器、Lazy Layout 等更复杂情况。当前需要知道的只有：**写自定义 Layout 时，不应该默认 `maxWidth` / `maxHeight` 永远都是一个普通的有限数字。**以后遇到需要用 `maxWidth`、`maxHeight` 做除法、减法、列宽计算时，这个意识尤其重要。

---

#### 11. 这不是在教一条“正确的 Column 算法”

这一点需要特别明确，否则很容易把今天这个实验记成错误的固定模板。我们今天定义的规则是：三个 children 共享父布局有限的高度预算，前面的 child 使用多少，后面的 child 就少多少。所以我们设计了：

```kotlin
remainingHeight
```

另外一个自定义 Layout 完全可以采用其他规则。例如类似 `Box` 的重叠布局：

```text
A
B
C
```

全部叠在同一个区域。那么 A 使用了 100dp 高度，并不意味着 B 的：

```text
maxHeight
```

要减少 100。它们完全可能都收到：

```text
maxHeight = 140
```

因为它们不按纵向共享空间。所以真正应该长期记住的不是：

```kotlin
remainingHeight -= placeable.height
```

而是：**`Layout()` 给了 Parent 制定 child measurement policy 的权力。**Parent 收到 incoming constraints 后，需要根据自己的布局语义，为不同 child 构造真正合适的 Constraints。

#### 12. 第二阶段最终心智模型

第一阶段的模型：

```text
Constraints
→ measure children
→ Placeables
→ parent size
→ placement
```

现在应该升级成：

```text
Parent 收到 incoming Constraints
            ↓
根据自己的布局规则
为每个 Child 设计 Constraints
            ↓
measure()
            ↓
获得每个 Placeable 的实际尺寸
            ↓
这些结果又可以影响
后续 Child 的 Constraints
            ↓
汇总所有 Placeable
计算 Parent desired size
            ↓
Parent 再遵守自己的 incoming Constraints
            ↓
得到 Parent final size
            ↓
placement
```

这里最核心的是中间新增的这一层：

```text
incoming Constraints
        ≠
child Constraints
```

二者有时可以恰好相同，但那应该是**父布局算法主动做出的决定**，而不是因为 `Layout()` 给了一个 `constraints` 参数，就默认把它原样塞进所有 `measure()`。到这里，上一阶段你自己产生的“是不是应该把前一个 child 占掉的空间减掉”的疑问已经完整闭环。下一阶段我们就不再用这种人为制造问题的小型纵向布局了，而是把现在掌握的：

```text
设计 child Constraints
→ 测量多个 child
→ 汇总结果
→ 计算 Parent
→ placement
```

真正用到一个**二维布局算法**里。

#### Addition 1：补齐 `Constraints` 的边界语义与 `clipToBounds()`

前面的实验里还有两个需要补完整的概念：第一，`Constraints` 除了“一个普通范围”和“一个确定尺寸”，还存在**无界**这一种情况；第二，`layout(width, height)` 决定了布局节点自己的尺寸，但**不会自动把这个尺寸变成绘制裁剪区域**。

先把 `Constraints` 的几种状态统一起来。以高度为例，最常见的是下面三种：

```text
minHeight = 0
maxHeight = 140

→ 有界范围：child 最终高度可以在 0..140 之间
```

```text
minHeight = 140
maxHeight = 140

→ 精确约束：child 最终高度只能是 140
```

```text
minHeight = 0
maxHeight = Constraints.Infinity

→ 无界：没有最大高度限制
```

无界并不要求 `minHeight` 也必须是 `Infinity`。例如理论上完全可以存在：

```text
minHeight = 50
maxHeight = Constraints.Infinity
```

它表达的是“至少 50，但向上没有有限的最大值”。因此 `hasBoundedHeight` 判断的核心就是：

```kotlin
maxHeight != Constraints.Infinity
```

只要 `maxHeight` 是一个有限值，无论它是：

```text
0..140
50..140
140..140
```

都属于 bounded。反过来，只要：

```text
maxHeight = Constraints.Infinity
```

就是 unbounded。这也补充了前面：

```kotlin
minHeight = 0
minWidth = 0
```

的准确含义。这里的 `0` 表示**父布局不给 child 强加额外的最小尺寸要求**，并不表示整个轴“没有约束”。例如：

```text
minHeight = 0
maxHeight = 140
```

child 仍然最多只能有 140 高。

---

再看代码中的：

```kotlin
var remainingHeight = constraints.maxHeight
```

以及：

```kotlin
val childMaxHeight =
    if (constraints.hasBoundedHeight) {
        remainingHeight
    } else {
        Constraints.Infinity
    }
```

这里保留 `hasBoundedHeight` 判断是有意义的。`Constraints.Infinity` 在语义上表示的是**没有上限**，不应该把它当成“一笔特别大的有限高度预算”。如果父布局高度有限：

```text
maxHeight = 140
```

那么“剩余高度”有明确意义：

```text
140
→ A 用掉 24
→ 剩 116
→ B 用掉 96
→ 剩 20
```

但如果：

```text
maxHeight = Infinity
```

就不存在“总共有 Infinity 高，然后 A 用掉 24，还剩 Infinity - 24”这样的布局语义。此时 parent 根本没有一笔有限预算需要逐项消耗，因此后续 child 继续收到：

```text
maxHeight = Infinity
```

即可。即使 `Constraints.Infinity` 在实现层最终由某个整数常量表示，也不应该依赖：

```kotlin
Constraints.Infinity - childHeight
```

这种算术。因为一旦减法发生，得到的就不再是 `Infinity` 这个“无界”语义，而变成了某个有限整数。这里判断 bounded / unbounded，处理的是**布局语义**，而不是为了避免一次普通整数减法。

---

最后补齐本实验里 `clipToBounds()` 的现象。

第一组布局最终执行：

```kotlin
layout(
    width = layoutWidth,
    height = layoutHeight
)
```

得到：

```text
280 × 140
```

这表示当前 `Layout` **向自己的 parent 报告尺寸是 280×140**。但是它仍然可以在自己的 placement block 中写：

```kotlin
childA.placeRelative(0, 0)
childB.placeRelative(0, 140)
childC.placeRelative(0, 280)
```

也就是说，child 完全可能被放到父布局自身边界之外。因此：

```text
layout size
```

和：

```text
drawing clip region
```

不是同一个概念。如果没有：

```kotlin
.clipToBounds()
```

超出父布局 280×140 区域的 B、C 仍然可以继续绘制，于是它们会进入下面其他 UI 所在的区域，形成截图中那种重叠效果。加入：

```kotlin
.clipToBounds()
```

之后，相当于明确要求：只保留当前节点 bounds 内的绘制结果，超出的部分裁掉。所以可以先记住这一组关系：

```text
measure / layout
→ 决定节点有多大、child 放在哪里

layout bounds
≠ 自动裁剪边界

clipToBounds()
→ 把绘制限制在当前节点 bounds 内
```

至于为什么父节点已经只有 140 高，child 仍然能够在边界外绘制；以及 `layout`、draw Modifier、裁剪、兄弟节点绘制顺序最终怎样嵌套，这属于后面的 **7.9 布局和绘制与 Modifier 链条的嵌套层级关系**。7.2 当前只需要掌握上面的应用层规则。

### 第三阶段：二维布局算法——从多个测量结果计算整张网格

前两阶段已经解决了两个基础问题：`Layout()` 如何拿到多个 child，以及 parent 为什么不能机械地把自己的 incoming `Constraints` 原样传给每个 child。现在进入真正的自定义布局算法：**parent 不只是纵向累加尺寸，而是根据多个 child 的测量结果计算二维几何关系。**

这一阶段做一个简化的三列网格。它还不是完整日历，但已经具备日历网格最核心的布局结构：固定列数、每列等宽、每个 child 高度可以不同、每一行的高度由这一行最高的 child 决定。

#### 1. 实验目标与完整代码

创建：`Sec0702C_CalendarGridLayout.kt`

运行后会看到六个不同高度的色块组成两行三列。整个自定义 `Layout` 宽度固定为 `300.dp`，因此每个 child 都会被 parent 强制测量为三分之一宽。

```kotlin
private const val TAG = "Sec0702C"

@Composable
fun Sec0702C_CalendarGridLayout() {
    Scaffold { innerPadding ->
        Column(
            modifier = Modifier
                .fillMaxSize()
                .padding(innerPadding)
                .padding(24.dp),
            verticalArrangement = Arrangement.spacedBy(16.dp)
        ) {
            Text(
                text = "3-column custom grid",
                style = MaterialTheme.typography.titleMedium
            )

            CalendarGridLayout(
                columns = 3,
                modifier = Modifier
                    .width(300.dp)

@Composable
private fun CalendarGridLayout(
    columns: Int,
    modifier: Modifier = Modifier,
    content: @Composable () -> Unit
) {
    require(columns > 0)

    Layout(
        modifier = modifier,
        content = content
    ) { measurables, constraints ->

        require(constraints.hasBoundedWidth) {
            "CalendarGridLayout requires a bounded width."
        }

        val layoutWidth = constraints.maxWidth
        val cellWidth = layoutWidth / columns

        log(
            TAG,
            "incoming=$constraints, " +
                "layoutWidth=$layoutWidth, cellWidth=$cellWidth"
        )

        val placeables = measurables.mapIndexed { index, measurable ->
            val childConstraints = constraints.copy(
                minWidth = cellWidth,
                maxWidth = cellWidth,
                minHeight = 0
            )

            val placeable = measurable.measure(childConstraints)

            val row = index / columns
            val column = index % columns

            log(
                TAG,
                "child[$index] row=$row column=$column " +
                    "size=${placeable.width} x ${placeable.height}"
            )

            placeable
        }

        val rowCount =
            (placeables.size + columns - 1) / columns

        val rowHeights = IntArray(rowCount)

        placeables.forEachIndexed { index, placeable ->
            val row = index / columns

            rowHeights[row] = maxOf(
                rowHeights[row],
                placeable.height
            )
        }

        val desiredHeight = rowHeights.sum()

        val layoutHeight = constraints.constrainHeight(desiredHeight)

        val rowTopOffsets = IntArray(rowCount)

        var accumulatedHeight = 0

        rowHeights.forEachIndexed { row, rowHeight ->
            rowTopOffsets[row] = accumulatedHeight
            accumulatedHeight += rowHeight
        }

        log(
            TAG,
            "rowHeights=${rowHeights.contentToString()}, " +
                "desiredHeight=$desiredHeight, " +
                "layoutHeight=$layoutHeight"
        )

        layout(
            width = layoutWidth,
            height = layoutHeight
        ) {
            placeables.forEachIndexed { index, placeable ->
                val row = index / columns
                val column = index % columns

                val x = column * cellWidth
                val y = rowTopOffsets[row]

                log(
                    TAG,
                    "place child[$index]: " +
                        "row=$row column=$column x=$x y=$y"
                )

                placeable.placeRelative(
                    x = x,
                    y = y
                )
            }
        }
    }
}
```

这一次不要只看最终网格长什么样。真正需要追的是：**为什么 parent 在测量结束以后已经拥有了足够的信息，可以计算整张网格。**

---

#### 2. 第一步：Parent 先定义“列”的规则

这个 Layout 的业务规则首先不是“child 想多宽”，而是：

```text
整个 Grid 有 3 列
每列等宽
```

父布局宽度被外面的 Modifier 固定成：

```kotlin
.width(300.dp)
```

因此进入 measure block 后，宽度方向属于 bounded，而且这里还是一个精确宽度。为了避免把代码写成只适用于当前演示的巧合，我们先明确这个 Layout 的算法前提：

```kotlin
require(constraints.hasBoundedWidth) {
    "CalendarGridLayout requires a bounded width."
}
```

因为下面马上要做：

```kotlin
val layoutWidth = constraints.maxWidth
val cellWidth = layoutWidth / columns
```

如果 `maxWidth` 是 `Constraints.Infinity`，所谓“把总宽度平均分成三列”本身就没有定义。这里不是 Compose 强制所有 Grid 都必须 bounded，而是**这个具体布局算法需要一个有限总宽度，因此 parent 可以明确要求这个前提成立。**假设设备 density 换算后父布局宽度是 `900px`：

```text
layoutWidth = 900
columns = 3

cellWidth = 300px
```

于是 Parent 已经决定了三个列区域：

```text
|----- 300 -----|----- 300 -----|----- 300 -----|
      column 0         column 1         column 2
```

这一步甚至发生在 child 真正测量之前。因为“每列多宽”是 **parent 的布局规则**，不是 child 的测量结果。

---

#### 3. 这一次把 child 强制成固定宽度，是有意的

第二阶段刚刚看到一个错误：

```kotlin
measurable.measure(constraints)
```

导致每一个 child 都被错误地强制成 Parent 自己的 `280 × 140`。这一阶段我们却主动写：

```kotlin
val childConstraints = constraints.copy(
    minWidth = cellWidth,
    maxWidth = cellWidth,
    minHeight = 0
)
```

这里：

```text
minWidth = cellWidth
maxWidth = cellWidth
```

意味着：每个 child 的宽度必须等于一个单元格的宽度。这一次的“强制尺寸”不是错误，而是 Grid 本身的布局语义。例如 A 即使自己写：

```kotlin
.width(20.dp)
```

只要普通 `width()` 最终面对的是：

```text
minWidth = 100dp
maxWidth = 100dp
```

它最后还是会被测成 `100dp` 宽。因为在这个 Grid 中：

```text
child 的宽度
由 Parent 的列规则决定
```

而：

```text
child 的高度
暂时仍然主要由 child 自己决定
```

所以我们只固定 width：

```text
width = cellWidth
```

高度方向则：

```text
minHeight = 0
```

同时保留 incoming `maxHeight`。这已经是在真正设计一个 `MeasurePolicy`：**不同轴可以采用完全不同的测量策略。**

---

#### 4. `index / columns` 和 `index % columns`：从一维 children 得到二维位置

`Layout()` 给我们的仍然只是：

```text
List<Measurable>
```

例如：

```text
index 0 → A
index 1 → B
index 2 → C
index 3 → D
index 4 → E
index 5 → F
```

它并没有替你提供“行”和“列”。二维结构是 Parent 自己算出来的：

```kotlin
val row = index / columns
val column = index % columns
```

对于 `columns = 3`：

```text
index    row    column

0         0       0
1         0       1
2         0       2

3         1       0
4         1       1
5         1       2
```

所以：

```text
row    = index / 3
column = index % 3
```

这就是一个非常典型的布局算法特征：Composition 只提供了一串 children；二维空间关系是 Layout 自己赋予这些 children 的。将来做 7 列日历时完全一样：

```text
column = index % 7
row = index / 7
```

这里已经非常接近真实日历的基本结构了。

---

#### 5. 为什么一行的高度必须等所有 child 测完以后才能知道

现在六个 child 被测量成类似：

```text
A = cellWidth × 48dp
B = cellWidth × 80dp
C = cellWidth × 56dp

D = cellWidth × 72dp
E = cellWidth × 40dp
F = cellWidth × 64dp
```

第一行：

```text
A    B    C
48   80   56
```

如果三个 child 的顶部都在同一个 `y`，那么第二行应该从哪里开始？不能使用：

```text
48
```

否则 B 会和第二行重叠。不能使用：

```text
56
```

同样装不下 B。这一行真正占据的高度必须是：

```text
max(48, 80, 56) = 80
```

所以代码需要统计：

```kotlin
val rowHeights = IntArray(rowCount)

placeables.forEachIndexed { index, placeable ->
    val row = index / columns

    rowHeights[row] = maxOf(
        rowHeights[row],
        placeable.height
    )
}
```

最终：

```text
rowHeights[0] = 80
rowHeights[1] = 72
```

这就是这一阶段相对于第二阶段真正新增的东西。第二阶段的简单 VerticalLayout 可以：

```text
测 A
→ A 高度直接决定 B 的 y

测 B
→ B 高度直接决定 C 的 y
```

但 Grid 不行。因为一行的高度不是由某一个 child 单独决定的，而是：

```text
这一行所有 children 的测量结果
             ↓
            max
             ↓
          rowHeight
```

所以 Parent 必须先收集多个 `Placeable`，再计算更高一层的布局信息。

---

#### 6. Parent 高度由“行”决定，而不是直接把所有 child 高度相加

现在：

```text
row 0 height = 80
row 1 height = 72
```

所以：

```kotlin
val desiredHeight = rowHeights.sum()
```

结果：

```text
desiredHeight = 80 + 72 = 152dp
```

注意这里不能再像第一阶段的 VerticalLayout 一样：

```kotlin
placeables.sumOf { it.height }
```

因为 A、B、C 横向共享第一行，它们并不是上下依次占据空间。如果直接把六个 child 高度全部相加：

```text
48 + 80 + 56 + 72 + 40 + 64
```

得到的根本不是 Grid 所需要的高度。所以到了二维布局以后，**child 的尺寸不能直接等价于 parent 的尺寸公式。**中间多了一层由 Parent 定义的数据结构：

```text
Placeable dimensions
        ↓
   rowHeights
        ↓
 parent height
```

这也是自定义布局最核心的能力之一：Parent 可以根据多个 child 的测量结果，推导出自己需要的中间几何信息。

---

#### 7. Placement：先计算列坐标，再计算行坐标

列坐标非常直接：

```kotlin
val x = column * cellWidth
```

所以三列：

```text
column 0 → x = 0
column 1 → x = cellWidth
column 2 → x = cellWidth * 2
```

行坐标则不能简单写：

```kotlin
row * 某个固定高度
```

因为我们这个 Grid 允许每行高度不同。第一行是：

```text
80
```

第二行是：

```text
72
```

如果未来还有第三行，它的 `y` 应该是：

```text
80 + 72
```

因此我们先根据 `rowHeights` 算出每一行顶部的位置：

```kotlin
val rowTopOffsets = IntArray(rowCount)
var accumulatedHeight = 0

rowHeights.forEachIndexed { row, rowHeight ->
    rowTopOffsets[row] = accumulatedHeight
    accumulatedHeight += rowHeight
}
```

得到：

```text
rowTopOffsets[0] = 0
rowTopOffsets[1] = 80
```

如果还有第三行：

```text
rowTopOffsets[2] = 80 + 72 = 152
```

于是每个 child 最终位置就是：

```kotlin
val x = column * cellWidth
val y = rowTopOffsets[row]
```

这时整个二维算法已经闭合：

```text
index
 ↓
row / column
 ↓
column → x
row    → rowTopOffsets → y
 ↓
placeRelative(x, y)
```

---

#### 8. 这里和第二阶段的“remainingHeight”有一个关键区别

第二阶段那个 VerticalLayout 的布局规则是：

```text
前面的 child 使用掉高度
→ 后面的 child 可用高度减少
```

所以测量顺序本身参与了 Constraints 的设计。这次 Grid 不这么做。例如第一行：

```text
A   B   C
```

A 高 48 并不意味着 B 只能使用：

```text
maxHeight - 48
```

因为 A 和 B 位于同一行，它们在纵向上并不是首尾相接，而是在同一个纵向区域内并排存在。所以 A、B、C 可以分别独立测量自己的高度，然后：

```text
max(A.height, B.height, C.height)
```

才决定第一行最终需要多高。这正好说明上一阶段真正需要保留的原则：**child Constraints 的设计取决于 Parent 的布局算法。**VerticalLayout 和 GridLayout 面对的都是多个 children，但因为空间分配规则不同，测量策略也不同。

把 B：

```kotlin

```

改成：


只改这一处。重新运行以后，重点观察三个变化。首先：

```text

80 → 120
```

于是：


接着：


所以第二行的：


会整体向下移动 `40dp`。最终 Parent：


#### 10. 当前算法的边界

这个教学 Grid 有两个有意保留的限制。第一，它要求宽度 bounded，因为我们用：

```kotlin
constraints.maxWidth / columns
```

计算等宽列。如果未来需要支持横向无界环境，就必须重新定义列宽来源，而不是直接继续使用这套算法。第二，它**没有尝试把所有 rows 强行压缩进有限的 `maxHeight`**。children 测量完成以后，如果：

```text
desiredHeight > constraints.maxHeight
```

那么：

```kotlin
constraints.constrainHeight(desiredHeight)
```

会让 Parent 最终高度受限，但已经摆放好的 children 仍可能超出 Parent bounds。是否压缩 child、允许 overflow、裁剪、滚动，属于具体组件应该制定的下一层策略，不能由 `Layout()` 自动替我们决定。这和第二阶段 Addition 中建立的：

```text
layout size ≠ clip bounds
```

完全衔接。

---

#### 本阶段建立的二维布局模型

现在 `Layout()` 的心智模型已经不只是：

```text
measure children
→ parent size
→ placement
```

而是进一步变成：

```text
Parent 定义布局规则
        ↓
根据规则设计 Child Constraints
        ↓
每个 Measurable 只负责返回自己的 Placeable
        ↓
Parent 汇总多个 Placeable 的尺寸
        ↓
建立中间几何数据
row / column / rowHeight / rowTopOffset
        ↓
计算 Parent 自己的尺寸
        ↓
根据二维坐标放置每个 child
```

到这里，`Layout()` 已经从“把多个 Box 竖着摆起来”真正进入了**自定义布局算法**。

下一阶段不需要再换一个类似案例重复这些计算，而是处理一个普通 `Layout()` 非常关键的规则：**同一个 `Measurable` 在一次 measure pass 中为什么不能为了“先看看尺寸”而反复 `measure()`，以及 child A 的测量结果能不能合法地决定 child B 的 Constraints。**

### 第四阶段：Single-pass Measurement——测量顺序可以有依赖，但同一个 child 只能正式测一次

上一阶段的 Grid 采用的是“先把所有 child 各测一次，再汇总行高”的算法。这一阶段换一种更关键的情况：**后一个 child 的 Constraints 依赖前一个 child 的实际测量结果。**Compose 允许这样做：

```text
measure A
→ 得到 A 的 Placeable
→ 根据 A.height 计算 B 的 Constraints
→ measure B
```

限制在于：**同一次 measure pass 中，同一个 `Measurable` 不能为了试探尺寸反复调用 `measure()`。**这一阶段把这两件事一起跑通。

---

#### 1. 实验：A 的实际高度决定 B 还能使用多少空间

```kotlin
@Composable
private fun DependentMeasurementLayout(
    modifier: Modifier = Modifier,
    content: @Composable () -> Unit
) {
    Layout(
        modifier = modifier,
        content = content
    ) { measurables, constraints ->

        require(measurables.size == 2) {
            "DependentMeasurementLayout requires exactly 2 children."
        }

        log(
            TAG,
            "incoming=$constraints"
        )

        /*
         * A 是顶部 child。
         *
         * Parent 决定：
         * - A 使用完整可用宽度；
         * - 高度由 A 自己决定，但不能超过 Parent 的 maxHeight。
         */
        val headerConstraints = constraints.copy(
            minWidth = constraints.maxWidth,
            maxWidth = constraints.maxWidth,
            minHeight = 0
        )

        val headerPlaceable =
            measurables[0].measure(headerConstraints)

        log(
            TAG,
            "A result=${headerPlaceable.width} x ${headerPlaceable.height}"
        )

        /*
         * 故意违反 single-pass measurement。
         *
         * 改 RUN_DOUBLE_MEASURE_TEST = true 后，
         * 同一个 measurables[0] 会在本次 measure pass 中再次被 measure。
         */
        if (RUN_DOUBLE_MEASURE_TEST) {
            measurables[0].measure(headerConstraints)
        }

        /*
         * B 的可用高度依赖 A 的实际测量结果。
         *
         * Parent 总高度 180dp；
         * 如果 A 实际占 48dp，
         * B 最多还能使用 132dp。
         */
        val remainingHeight =
            if (constraints.hasBoundedHeight) {
                (constraints.maxHeight - headerPlaceable.height)
                    .coerceAtLeast(0)
            } else {
                Constraints.Infinity
            }

        val bodyConstraints = constraints.copy(
            minWidth = constraints.maxWidth,
            maxWidth = constraints.maxWidth,
            minHeight = 0,
            maxHeight = remainingHeight
        )

        log(
            TAG,
            "B constraints=$bodyConstraints"
        )

        val bodyPlaceable =
            measurables[1].measure(bodyConstraints)

        log(
            TAG,
            "B result=${bodyPlaceable.width} x ${bodyPlaceable.height}"
        )

        /*
         * 这个 Layout 本身已经被外面的 width(300.dp)、height(180.dp)
         * 约束为固定尺寸。
         */
        val layoutWidth =
            constraints.maxWidth

        val layoutHeight =
            constraints.maxHeight

        layout(
            width = layoutWidth,
            height = layoutHeight
        ) {
            headerPlaceable.placeRelative(
                x = 0,
                y = 0
            )

            bodyPlaceable.placeRelative(
                x = 0,
                y = headerPlaceable.height
            )
        }
    }
}
```

#### 2. 这里真正新增的是“测量结果可以参与后续测量”

前面几个例子的算法大致都是：

```text
准备 child Constraints
→ measure 所有 children
→ 再分析所有 Placeable
```

这一次变成：

```text
构造 A Constraints
→ measure A
→ 得到 A.height
→ 计算 remainingHeight
→ 构造 B Constraints
→ measure B
```

代码中的依赖关系非常直接：

```kotlin
val headerPlaceable = measurables[0].measure(headerConstraints)
val remainingHeight = constraints.maxHeight - headerPlaceable.height
val bodyConstraints = constraints.copy(maxHeight = remainingHeight)
val bodyPlaceable = measurables[1].measure(bodyConstraints)
```

所以 `Layout()` 的 measure block 并不要求：所有 child 必须先统一准备好 Constraints，然后一起测量。Parent 可以按照自己的算法决定测量顺序，并让**已经完成的测量结果参与后续 child 的 Constraints 计算**。

这在真实自定义布局里很常见。例如顶部工具栏先占掉实际高度，剩余内容区域再根据真实剩余空间测量；或者先测某个固定区域，再让另一个区域使用余下尺寸。

---

#### 3. Single-pass 限制的准确含义

合法的是：

```text
Measurable A → measure 一次
Measurable B → measure 一次
Measurable C → measure 一次
```

测量顺序可以是：

```text
A → B → C
```

也可以因为算法需要变成其他顺序。真正受限制的是：

```text
A.measure(...)
↓
看看 A 多大
↓
换一套 Constraints
↓
A.measure(...) 再来一次
```

普通 `Layout()` 中，同一个 child 在一次 measure pass 里不能这样正式测两遍。所以不能设计这样的算法：

```kotlin
val firstTry = measurable.measure(
    Constraints(maxWidth = 500)
)

// 看 firstTry.width 后觉得不满意

val finalResult = measurable.measure(
    Constraints(maxWidth = 300)
)
```

这个思路等于：“我先真正测一次试试看，再决定正式怎么测。” Compose 的普通布局流程不允许这样使用同一个 `Measurable`。

---

#### 4. 亲自验证重复 `measure()`

代码顶部现在是：

```kotlin
private const val RUN_DOUBLE_MEASURE_TEST = false
```

先确认正常版本已经成功运行，然后改成：

```kotlin
private const val RUN_DOUBLE_MEASURE_TEST = true
```

重新运行。执行到：

```kotlin
val headerPlaceable = measurables[0].measure(headerConstraints)
```

A 已经测量过一次。随后：

```kotlin
measurables[0].measure(headerConstraints)
```

又对同一个 `Measurable` 调用一次 `measure()`。此时 Compose 会在运行时拒绝这种重复测量，通常会抛出与“同一个 Measurable 被多次 measure”相关的异常。实验结束后把：

```kotlin
RUN_DOUBLE_MEASURE_TEST
```

恢复为 `false`。这里真正要留下的经验只有一句：**一个 child 的正式测量机会只有一次，因此第一次构造它的 Constraints 时，Parent 就应该已经知道自己想怎样测它。**

---

#### 5. 为什么 Compose 要这样限制

这个限制让一次正常 layout pass 保持清晰的单向关系：

```text
Parent 给 Child 一套 Constraints
        ↓
Child 返回一个测量结果
        ↓
Parent 使用这个结果完成自己的布局算法
```

如果同一个 child 可以任意反复测量：

```text
测一次
→ 看结果
→ 改条件
→ 再测
→ 再看结果
→ 再测
```

一次布局就可能逐渐变成试探式求解，父子测量依赖也会复杂很多。所以普通 Compose Layout 使用 single-pass measurement，把正常布局算法限制在一个更容易预测的模型里。

这一层理解已经够支持应用开发，不需要现在下钻 `LayoutNode` 内部如何记录 measurement state；后面的布局底层章节如果需要，再看实现。

---

#### 6. 这和下一节 `IntrinsicSize` 有什么关系

这里会自然产生一个问题：如果我真的需要在正式测量以前知道 child 大概想要多大呢？例如：

```text
我想先知道 Text 天然需要多高
→ 再根据这个信息决定整个布局怎么测
```

这类需求不能靠：

```kotlin
measure()
→ 看看
→ 再 measure()
```

解决。Compose 另外提供了 **intrinsic measurement** 这套机制，让 Parent 可以在正式 measure 之前查询某些“内在尺寸”信息。它正好就是下一节 7.3 的主题。

当前不要提前把 `minIntrinsicWidth()`、`maxIntrinsicHeight()` 等 API 展开。只需要明确边界：

```text
正式测量：
measure()
→ single-pass

正式测量之前想查询尺寸倾向：
Intrinsic measurement
→ 7.3
```

另外，如果问题进一步变成：“我要先测量某部分，然后根据测量结果决定接下来到底组合哪些 Composable。” 那已经不是普通 `Layout()` 只改变 Constraints 能解决的事情，而是后面 `SubcomposeLayout()` 的能力范围。

---

#### 7. 7.2 到这里应该形成的完整心智模型

经过四个阶段，现在普通 `Layout()` 可以统一成一个完整模型：

```text
Parent 收到 incoming Constraints
        ↓
Parent 根据自己的布局规则
设计每个 Child 的 Constraints
        ↓
按算法需要的顺序 measure children
        ↓
每个 Measurable 在本次 pass 中正式 measure 一次
        ↓
前面 Child 的 Placeable
可以参与后面 Child 的 Constraints 计算
        ↓
Parent 汇总 Placeable 的尺寸
计算自己的几何数据和 desired size
        ↓
Parent 自己仍然遵守 incoming Constraints
        ↓
layout(width, height)
        ↓
place children
```

现在你真正拥有的已经不是“会写 `Layout()` 语法”，而是自定义父布局最核心的三个设计问题：

```text
1. Parent 收到了什么 Constraints？

2. 每个 Child 应该收到什么 Constraints？

3. Child 测量完成以后，Parent 怎样利用这些结果决定自己的尺寸和坐标？
```

普通应用层自定义布局，绝大多数问题都可以先从这三个问题开始拆。`Layout()` 本身到这里已经达到真实 App 开发需要的深度。下一节 7.3 再进入一个新的问题：**正式 measure 之前，Parent 怎样提前询问 child 的 intrinsic size。**
